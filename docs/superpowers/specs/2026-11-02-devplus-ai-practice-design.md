## 1. Цель и рамки

### Что сказал заказчик

- Практика с AI-ассистентом по образцу Hello Interview: два формата, Structured и Open-Ended.
- В практику входит оценка не только результата, но и того, как человек работает с AI.

### Решения исполнителя

- **Open-Ended (локальный проект)** строится первым. Студент скачивает стартовый репозиторий, работает у себя с любым AI-инструментом, архивом сдаёт проект, отвечает на debrief-вопросы и получает разбор. Браузерный редактор не нужен.
- **Structured (в браузере)** строится вторым. Задача из 2–4 последовательных фаз на одной кодовой базе (например: починить баг → добавить фичу → оптимизировать). У каждой фазы свои публичные и скрытые тесты. Редактор Monaco, кнопки «Run» (публичные тесты) и «Сдать фазу» (скрытые).
- **AI-ассистента платформа не встраивает.** В обоих форматах студент пользуется своим инструментом. Встроенный ассистент стоил бы денег за каждый ход и усложнил бы архитектуру; вернёмся, если команда попросит.
- **Оценка складывается из двух частей:**
  1. тесты: доля пройденных скрытых тестов (детерминированно);
  2. рубрика «работа с AI» из четырёх разделов, оценивает судья: *Решение задачи*, *Контроль над AI*, *Проверка результата*, *Коммуникация*.
- **Зачёт:** доля скрытых тестов не ниже порога задачи (по умолчанию 0,8) **и** балл рубрики не ниже `ai_threshold` задачи (по умолчанию 0,6). Обе цифры показываются отдельно.
- **Процесс работы видно двумя путями:** debrief-вопросы (обязательно) и необязательное вложение — экспорт переписки с AI-ассистентом (текст, до 200 КБ).
- **Язык:** Python 3.12 в первой версии. Тесты — `pytest`.
- **Таймер мягкий:** показывается оценка времени, сдача после неё допускается с отметкой «позже срока». Команда из ~20 человек, принуждения нет.

### Критерии успеха

- Студент проходит путь целиком: скачал старт, сделал, сдал, ответил на вопросы, получил результат тестов и разбор рубрики.
- Скрытые тесты, рубрика и эталон не попадают в браузер и в скачиваемый старт. Закреплено тестом.
- Чужой код запускается только в песочнице; его вывод, архив и вложение считаются недоверенными данными на каждом шаге.
- Эталонное решение каждой задачи проходит все её скрытые тесты, а стартовое состояние не проходит. Проверяется тестом по реальной `content/` в песочнице.
- Стоимость одной оценки ограничена размером входа и `max_tokens` (раздел 3); фактическая стоимость записывается в попытку.

### Не входит

- Облачная IDE, терминал и сессии агента в браузере, перехват запросов AI через шлюз (как у LeetCode).
- Встроенный AI-ассистент платформы.
- Языки кроме Python, сборка Docker-образов студентом, сеть из песочницы.
- Прокторинг, публичные рейтинги, шаринг решений.
- Алгоритмические задачи с одним файлом (отдельная часть подпроекта 5).

## 2. Задачи (контент)

Файлы лежат по схеме `content/<NN-модуль>/tasks/<slug>/`. **[Решение исполнителя]** Та же папочная схема, что у Code Review, но **загрузчик свой** в `projects` (у Code Review тоже свой): общий загрузчик означал бы зависимость от ещё не реализованной спеки, а дублирование небольшое. Загрузчик Тренажёра папки молча пропускает, конфликта нет.

**Docker-образы.** Оба ignore-файла рассчитаны на плоские `tasks/*.yaml`, поэтому `hidden/` и `task.yaml` из папок уедут в web-образ, а `starter/` и `hidden/` не попадут в API-образ. **[Решение исполнителя]** Правим оба файла: web-образ (`/.dockerignore`) исключает всё в `tasks/<slug>/`, кроме `task.mdx`; API-образ (`apps/api/Dockerfile.dockerignore`) пропускает `tasks/<slug>/**`. Скрытые тесты остаются в `content/`. Проверка: в собранном web-образе нет `task.yaml`, `hidden/`, `starter/` (отдельная цель Makefile).

```
task.mdx     условие и README студента: контекст, что делать, правила
task.yaml    метаданные и скрытая часть, читает только API
starter/     стартовый репозиторий, который скачивает студент
hidden/      скрытые тесты, видит только песочница
```

`task.yaml`:

```yaml
title: ...
kind: open_ended            # open_ended | structured
estimate_min: 60
runtime: python-3.12
pass_ratio: 0.8             # доля скрытых тестов для зачёта
ai_threshold: 0.6           # порог рубрики «работа с AI»; задаётся здесь, значение по умолчанию 0.6
rubric:                     # формат RubricSection; 4 раздела «работы с AI» + опционально до 4 своих
  - {name: Решение задачи, description: ..., weight: 3}
debrief:                    # 3–5 вопросов, студент отвечает текстом
  - id: verify
    text: Как ты проверил, что решение работает, кроме тестов из задания?
phases:                     # только для structured, 2–4 фазы
  - id: fix
    title: ...
    public_tests: tests/public_fix.py
    hidden_tests: hidden/fix/
    weight: 1
```

Правила, которые проверяет загрузчик и тест по `content/`:

- В `rubric` не больше 10 разделов; имена совпадают с описанными в задаче.
- Пути тестов существуют; в `hidden/` нет файлов, которые попадают в `starter/`.
- `phases` есть только у `structured`, фаз 2–4; у `open_ended` их нет.
- Для `open_ended` в `debrief` 3–5 вопросов; каждый ограничен 2000 символами ответа.

Стартовый набор (привязан к модулям, контент появится первым):

- Open-Ended: сервис с rate limiting (модуль 7), очередь задач с повторами (модуль 5), цикл LLM-агента с инструментами (модуль 11).
- Structured: кэш с багом в инвалидации (баг → TTL → защита от stampede), webhook-сервис (баг → идемпотентность → пакетная обработка).

## 3. Модуль бэкенда `apps/api/app/modules/projects/`

```
tasks.py         загрузчик задач из content/, валидация
sandbox.py       клиент песочницы (Judge0), интерфейс Sandbox + FakeSandbox для тестов
archive.py       безопасная распаковка архива студента
grading.py       запуск тестов, сборка входа судьи, подсчёт зачёта
models.py        ProjectAttempt, PhaseResult
schemas.py, service.py, router.py, providers.py, worker.py (Taskiq-задача)
```

- Из оценщика берётся только то, что экспортирует `app.modules.evals.service`: `LLMClient`, `judge`, `RubricSection`, `LlmJudgeGrader`, `Grade`. **[Решение исполнителя]** Сейчас в `__all__` их нет, поэтому одной небольшой правкой `evals.service` реэкспортирует их, а `judge()` получает необязательный параметр с системным промптом (штатный `JUDGE_SYSTEM` написан про «ответ языковой модели», а не про работу человека с AI). Поведение по умолчанию не меняется. Та же правка нужна Code Review и делается один раз тем, кто строит первым. Контракт import-linter для `projects`.
- **Лимит стоимости.** `evals_run_cost_limit_usd` действует в executor и на одиночный вызов судьи не распространяется. **[Решение исполнителя]** Стоимость ограничена сверху размером входа (ответы debrief, вложение до 200 КБ, статистика) и `max_tokens`; фактическая `cost_usd` пишется в попытку. Предварительной оценки нет. `shortcut: без предварительной оценки стоимости, добавить, если оценка станет дорогой.`
- Задача оценки исполняется в Taskiq-воркере оценщика; та же схема подключения dishka к воркеру. Задача регистрируется в `app/worker.py` по имени. При старте воркера выполняется `recover()` по образцу evals: попытки в `grading`, зависшие после перезапуска, переводятся в `failed` без списания лимита.
- **Очередь воркера.** В воркере `--max-async-tasks 2`, а оценка с опросом Judge0 занимает слот на минуты. **[Решение исполнителя]** «Run» в Structured не идёт через очередь: API вызывает Judge0 синхронно (`wait=true`, до 30 секунд), не больше одного Run на пользователя одновременно и 30 в час. В очередь воркера уходят только оценки («Сдать фазу», финальная оценка). `shortcut: оценки и прогоны оценщика делят один воркер, вынести отдельную очередь, если оценки начнут ждать.`

### Песочница

**[Решение исполнителя, требует проверки]** Judge0 CE, отдельный docker-сервис в своей внутренней docker-сети, порты наружу не публикуются. Достучаться до него могут только API (синхронный Run) и воркер (оценки). У Judge0 свои Postgres и Redis, не общие с приложением. Multi-file программа передаётся как zip, внутри `run`-скрипт, запускающий `pytest`. Это закрывает открытый вопрос «Judge0 или Piston» в пользу Judge0, потому что он изолирует процессы без доступа воркера к docker-сокету хоста (вместо этого ему нужны привилегии самого контейнера Judge0).

Первый шаг плана — spike на один день: доказать, что в Judge0 запускается `pytest` со скрытыми тестами, снимается результат тестов, действуют лимиты CPU/памяти/времени, сети нет. Spike отдельно проверяет: есть ли Python 3.12 в образе Judge0 CE (если нет, нужен свой образ языка или версия, которая есть); работает ли Judge0 на cgroup v2 хоста (известная проблема версии 1.13); достаточно ли привилегированного контейнера на этом VPS. Если spike не проходит, возвращаемся к вопросу Judge0 или Piston до остальной реализации. `shortcut: Judge0 на одном VPS, при росте нагрузки отдельный хост для песочницы.`

Ограничения прогона: 30 секунд CPU на запуск, 512 МБ памяти, без сети, вывод до 1 МБ.

**Зависимости.** **[Решение исполнителя]** Сети в песочнице нет, поэтому `pip install` невозможен. В первой версии задачи используют только stdlib и `pytest`, вшитые в образ. Задача про цикл LLM-агента приносит поддельный LLM в `starter/` сама. Список разрешённых пакетов расширяется вшиванием в образ, по одной задаче.

**Модель угроз результата тестов.** Код студента и скрытые тесты работают в одной песочнице и одном процессе pytest, и Judge0 возвращает только stdout. **[Решение исполнителя]** Защищаемся от побега из песочницы и от случайной подмены, но не от целенаправленного обмана: команда из ~20 человек, соревнования и награды нет. Что делаем:
- раннер запускает `pytest -c /dev/null -p no:cacheprovider` из каталога, который контролирует платформа; `conftest.py`, `pytest.ini`, `pyproject.toml` и `sitecustomize` из архива студента не подхватываются (проект кладётся как пакет, хранимая платформой конфигурация перекрывает его);
- результат печатается раннером после завершения pytest в строке с одноразовым nonce, который знает только платформа; разбирается последняя такая строка;
- скрытые тесты копируются в песочницу в момент запуска, в архиве студента их нет.
`shortcut: код студента может прочитать hidden/ и подделать вывод, потому что работает в том же процессе. Если появятся награды или рейтинг, запускать скрытые тесты отдельным процессом и отдельной песочницей.`

### Таблицы

```
project_attempts
  id            uuid PK
  user_id       uuid FK → users ON DELETE CASCADE
  task_key      text NOT NULL            -- "<module>/<slug>"
  kind          text NOT NULL            -- open_ended | structured
  status        text NOT NULL            -- started | submitted | grading | graded | failed
  started_at, submitted_at timestamptz
  late          boolean NOT NULL default false

```

`shortcut: архивы лежат в томе docker на одном VPS, переехать на S3-совместимое хранилище, когда понадобится больше одного хоста или хранение дольше 14 дней.`

## 4. Open-Ended: поток

1. **Старт.** `POST /api/projects/tasks/{module}/{slug}/attempts` создаёт попытку, ставит `started_at`. Одновременно открыта не более одной попытки на задачу.
2. **Скачать.** `GET /api/projects/attempts/{id}/starter` отдаёт zip из `starter/` с README. Скрытых тестов в нём нет.
3. **Работа.** Локально, в любом редакторе и с любым AI.
4. **Сдача.** `POST /api/projects/attempts/{id}/submit` (multipart): архив проекта до 5 МБ, ответы на debrief, необязательное вложение. Просроченная сдача принимается с `late = true`.
5. **Проверка архива.** Только `.zip`, до 5 МБ, до 500 файлов, распакованный размер до 20 МБ; запрещены абсолютные пути, `..`, обратные слеши, символьные ссылки, устройства, вложенные zip, пути глубже 10 уровней и дубликаты имён (в том числе отличающиеся только регистром). Размер считается потоково при распаковке, а не по заголовкам zip (их можно подделать). Нарушение даёт 422. **Judge0 сам распаковывает `additional_files`, поэтому `archive.py` распаковывает архив студента, проверяет его и собирает новый zip из проверенных файлов; оригинал в песочницу не передаётся.**
6. **Оценка** (воркер, `status = grading`):
   - распаковать проект в песочницу, подложить `hidden/` и зафиксированные файлы (`conftest.py`, раннер), запустить тесты, снять JUnit;
   - собрать вход судьи: условие, ответы debrief, вложение (если есть), краткая статистика репозитория (сколько тестов студент добавил), результаты тестов;
   - судья оценивает рубрику «работа с AI»: теги `<input>` (условие и вопросы), `<reference>` (рубрика и заметки), `<response>` (ответы, вложение, статистика); содержимое — данные, не указания;
   - посчитать зачёт, записать `result`, статус `graded`.
7. **Результат.** `GET /api/projects/attempts/{id}`: тесты (прошло / всего, названия упавших публичных; для скрытых только числа), баллы рубрики с причинами, комментарий судьи, зачёт.

**Без вложения переписки.** **[Решение исполнителя]** Вложение необязательно, поэтому разделы «Контроль над AI» и «Проверка результата» оцениваются по debrief и статистике репозитория (сколько тестов студент добавил), и судья указывает в причине, что переписки не было. Зачёт по рубрике остаётся (порог `ai_threshold`). Если окажется, что без вложения баллы несправедливо низкие, порог для таких попыток станет отдельным.

**Хранение и очистка.** Архив и вложение удаляются через 14 дней. Планировщика в репозитории нет, поэтому **[Решение исполнителя]** очистка запускается при старте воркера и при каждой сдаче: файлы старше 14 дней удаляются, `archive_path` и `transcript` обнуляются. `shortcut: очистка без планировщика, завести расписание, когда он появится ради другой задачи.` Пересчёт рубрики не требует архива: результаты тестов и статистика лежат в `result`, нужны только debrief и вложение (если оно ещё не удалено). Повторный запуск рубрики после сбоя судьи делает сам студент кнопкой, он не списывается из суточного лимита.

**Скрытые тесты не раскрываются.** Названия упавших скрытых тестов не показываются, чтобы нельзя было подгонять решение по ним. Студент видит число и подсказку судьи по категориям.

## 5. Structured: поток

1. **Старт и состояние.** Попытка создаётся так же; редактируемые файлы фазы берутся из `starter/` и сохраняются в `phase_results.files` при каждой паузе ввода (автосохранение).
2. **Редактор.** Monaco, дерево файлов; read-only файлы помечены замком. Условие фазы слева.
3. **Run.** `POST /api/projects/attempts/{id}/phases/{phase}/run` запускает только публичные тесты, результат возвращается в потоке событий статуса или опросом. Лимит: 30 запусков в час на пользователя.
4. **Сдать фазу.** `POST …/phases/{phase}/submit` запускает скрытые тесты фазы. Если пройдены, следующая фаза открывается и получает код текущей как основу.
5. **Конец.** Когда сданы все фазы (или студент завершил попытку), рубрика «работа с AI» оценивается по debrief; вложение переписки поддерживается так же. Зачёт — как в разделе 1, доля берётся по всем фазам с их весами.

**[Решение исполнителя]** Structured реализуется после Open-Ended и использует уже готовые песочницу, воркер и судью. Экран — главная новая работа этого этапа.

## 6. Интерфейс

- `/projects`: список задач, фильтр по формату, статус пользователя.
- `/projects/<module>/<slug>`: условие, оценка времени, кнопки «Начать» и «Скачать стартовый репозиторий» (Open-Ended) или вход в редактор (Structured).
- Форма сдачи: загрузка архива, поля debrief, необязательное вложение с предупреждением «в переписке не должно быть ключей и паролей».
- Страница разбора: результат тестов и рубрики рядом, причины баллов, кнопка «Сообщить о плохом разборе» (общая с Code Review).

## 7. Безопасность, ошибки, тесты

- **Недоверенное всё:** архив, код, вывод тестов, ответы, вложение. Код только в песочнице; в оценке судья получает данные в тегах. Модель угроз результата тестов описана в разделе 3.
- **Песочница недоступна:** попытка `failed` с понятной причиной, лимит сдач не списывается.
- **Судья не уложился в лимит или вернул неверные имена разделов:** то же, оценка тестов сохраняется, рубрику можно пересчитать повторным запуском.
- Доменные исключения → `{"detail": "..."}`; Origin-проверка на изменяющих запросах, как везде.
- Суточный лимит сдач `PROJECTS_DAILY_LIMIT` (по умолчанию 5), один грейдинг на пользователя одновременно.
- **Тесты (TDD):**
  - `archive.py`: zip-slip, символьные ссылки, лимиты размера и числа файлов;
  - загрузчик задач и структурный тест по `content/`;
  - подсчёт зачёта, пограничные значения `pass_ratio` и рубрики;
  - API с `FakeSandbox` и `FakeLLMClient`: полный путь, сбой песочницы, сбой судьи, лимит, чужая попытка 404;
  - тест утечки: скачиваемый старт и ответы API не содержат `hidden/`, рубрику и заметки;
  - интеграционный тест эталонного решения против реальной песочницы (вне основного CI, отдельная цель Makefile).
- Новые переменные: `JUDGE0_URL`, `PROJECTS_DAILY_LIMIT`, том для архивов. Обновить `.env.example` и `docs/deploy.md`.
- Тесты `archive.py` дополнительно: дубликаты и регистр, обратные слеши, вложенный zip, глубина путей, поддельный размер в заголовке zip.
- Проверка образов: в собранном web-образе нет `task.yaml`, `hidden/`, `starter/` (раздел 2).
- Тест `recover()`: попытка в `grading` после старта воркера становится `failed`, лимит не списан.

## 9. Открыто для заказчика

- Подходит ли Judge0 по эксплуатации (привилегированный контейнер на том же VPS). Если нет, решение откладывается до spike.
- Нужен ли встроенный ассистент в Structured. Принято: нет.
- Хранить ли вложения переписки после оценки. Принято: хранятся вместе с попыткой, удаляются через 14 дней с архивом.
- Защита от целенаправленной подделки результата тестов. Принято: нет, только от побега из песочницы и случайной подмены (раздел 3). Если появятся награды или рейтинг, решение пересматривается.

## 1. Цель и рамки

### Что сказал заказчик

- Практика с AI-ассистентом по образцу Hello Interview: два формата, Structured и Open-Ended.
- В практику входит оценка не только результата, но и того, как человек работает с AI.

### Решения исполнителя

- **Open-Ended (локальный проект)** строится первым. Студент скачивает стартовый репозиторий, работает у себя с любым AI-инструментом, архивом сдаёт проект, отвечает на debrief-вопросы и получает разбор. Браузерный редактор не нужен.
- **Structured (в браузере)** строится вторым. Задача из 2–4 последовательных фаз на одной кодовой базе (например: починить баг → добавить фичу → оптимизировать). У каждой фазы свои публичные и скрытые тесты. Редактор Monaco, кнопки «Run» (публичные тесты) и «Сдать фазу» (скрытые).
- **AI-ассистента платформа не встраивает.** В обоих форматах студент пользуется своим инструментом. Встроенный ассистент стоил бы денег за каждый ход и усложнил бы архитектуру; вернёмся, если команда попросит.
- **Оценка складывается из двух частей:**
  1. тесты: доля пройденных скрытых тестов (детерминированно);
  2. рубрика «работа с AI» из четырёх разделов, оценивает судья: *Решение задачи*, *Контроль над AI*, *Проверка результата*, *Коммуникация*.
- **Зачёт:** доля скрытых тестов не ниже порога задачи (по умолчанию 0,8) **и** балл рубрики не ниже 0,6. Обе цифры показываются отдельно.
- **Процесс работы видно двумя путями:** debrief-вопросы (обязательно) и необязательное вложение — экспорт переписки с AI-ассистентом (текст, до 200 КБ).
- **Язык:** Python 3.12 в первой версии. Тесты — `pytest`.
- **Таймер мягкий:** показывается оценка времени, сдача после неё допускается с отметкой «позже срока». Команда из ~20 человек, принуждения нет.

### Критерии успеха

- Студент проходит путь целиком: скачал старт, сделал, сдал, ответил на вопросы, получил результат тестов и разбор рубрики.
- Скрытые тесты, рубрика и эталон не попадают в браузер и в скачиваемый старт. Закреплено тестом.
- Чужой код запускается только в песочнице; его вывод, архив и вложение считаются недоверенными данными на каждом шаге.
- Эталонное решение каждой задачи проходит все её скрытые тесты, а стартовое состояние не проходит. Проверяется тестом по реальной `content/` в песочнице.
- Одна оценка укладывается в лимит стоимости прогона оценщика.

### Не входит

- Облачная IDE, терминал и сессии агента в браузере, перехват запросов AI через шлюз (как у LeetCode).
- Встроенный AI-ассистент платформы.
- Языки кроме Python, сборка Docker-образов студентом, сеть из песочницы.
- Прокторинг, публичные рейтинги, шаринг решений.
- Алгоритмические задачи с одним файлом (отдельная часть подпроекта 5).

## 2. Задачи (контент)

Файлы лежат по схеме `content/<NN-модуль>/tasks/<slug>/`. **[Решение исполнителя]** Та же папочная схема, что у Code Review; загрузчик общий для обоих подпроектов.

```
task.mdx     условие и README студента: контекст, что делать, правила
task.yaml    метаданные и скрытая часть, читает только API
starter/     стартовый репозиторий, который скачивает студент
hidden/      скрытые тесты, видит только песочница
```

`task.yaml`:

```yaml
title: ...
kind: open_ended            # open_ended | structured
estimate_min: 60
runtime: python-3.12
pass_ratio: 0.8             # доля скрытых тестов для зачёта
rubric:                     # формат RubricSection; 4 раздела «работы с AI» + опционально до 4 своих
  - {name: Решение задачи, description: ..., weight: 3}
debrief:                    # 3–5 вопросов, студент отвечает текстом
  - id: verify
    text: Как ты проверил, что решение работает, кроме тестов из задания?
phases:                     # только для structured, 2–4 фазы
  - id: fix
    title: ...
    public_tests: tests/public_fix.py
    hidden_tests: hidden/fix/
    weight: 1
```

Правила, которые проверяет загрузчик и тест по `content/`:

- В `rubric` не больше 10 разделов; имена совпадают с описанными в задаче.
- Пути тестов существуют; в `hidden/` нет файлов, которые попадают в `starter/`.
- `phases` есть только у `structured`, фаз 2–4; у `open_ended` их нет.
- Для `open_ended` в `debrief` 3–5 вопросов; каждый ограничен 2000 символами ответа.

Стартовый набор (привязан к модулям, контент появится первым):

- Open-Ended: сервис с rate limiting (модуль 7), очередь задач с повторами (модуль 5), цикл LLM-агента с инструментами (модуль 11).
- Structured: кэш с багом в инвалидации (баг → TTL → защита от stampede), webhook-сервис (баг → идемпотентность → пакетная обработка).

## 3. Модуль бэкенда `apps/api/app/modules/projects/`

```
tasks.py         загрузчик задач из content/, валидация
sandbox.py       клиент песочницы (Judge0), интерфейс Sandbox + FakeSandbox для тестов
archive.py       безопасная распаковка архива студента
grading.py       запуск тестов, сборка входа судьи, подсчёт зачёта
models.py        ProjectAttempt, PhaseResult
schemas.py, service.py, router.py, providers.py, worker.py (Taskiq-задача)
```

- Из оценщика берётся только то, что экспортирует `app.modules.evals.service`. Контракт import-linter для `projects`.
- Задача оценки исполняется в Taskiq-воркере оценщика; та же схема подключения dishka к воркеру.

### Песочница

**[Решение исполнителя, требует проверки]** Judge0 CE, отдельный docker-сервис, достижимый только из воркера. Multi-file программа передаётся как zip, внутри `run`-скрипт, запускающий `pytest`. Это закрывает открытый вопрос «Judge0 или Piston» в пользу Judge0, потому что он изолирует процессы без доступа воркера к docker-сокету хоста (вместо этого ему нужны привилегии самого контейнера Judge0).

Первый шаг плана — spike на один день: доказать, что в Judge0 запускается `pytest` с зависимостями из `requirements.txt` и скрытыми тестами, снимается JUnit-отчёт, действуют лимиты CPU/памяти/времени, сети нет. Если spike не проходит, возвращаемся к вопросу Judge0 или Piston до остальной реализации. `shortcut: Judge0 на одном VPS, при росте нагрузки отдельный хост для песочницы.`

Ограничения прогона: 30 секунд CPU на запуск, 512 МБ памяти, без сети, вывод до 1 МБ.

### Таблицы

```
project_attempts
  id            uuid PK
  user_id       uuid FK → users ON DELETE CASCADE
  task_key      text NOT NULL            -- "<module>/<slug>"
  kind          text NOT NULL            -- open_ended | structured
```

## 4. Open-Ended: поток

1. **Старт.** `POST /api/projects/tasks/{module}/{slug}/attempts` создаёт попытку, ставит `started_at`. Одновременно открыта не более одной попытки на задачу.
2. **Скачать.** `GET /api/projects/attempts/{id}/starter` отдаёт zip из `starter/` с README. Скрытых тестов в нём нет.
3. **Работа.** Локально, в любом редакторе и с любым AI.
4. **Сдача.** `POST /api/projects/attempts/{id}/submit` (multipart): архив проекта до 5 МБ, ответы на debrief, необязательное вложение. Просроченная сдача принимается с `late = true`.
5. **Проверка архива.** Только `.zip`, до 5 МБ, до 500 файлов, распакованный размер до 20 МБ; запрещены абсолютные пути, `..`, символьные ссылки и устройства. Нарушение даёт 422.
6. **Оценка** (воркер, `status = grading`):
   - распаковать проект в песочницу, подложить `hidden/` и зафиксированные файлы (`conftest.py`, раннер), запустить тесты, снять JUnit;
   - собрать вход судьи: условие, ответы debrief, вложение (если есть), краткая статистика репозитория (сколько тестов студент добавил), результаты тестов;
   - судья оценивает рубрику «работа с AI»: теги `<input>` (условие и вопросы), `<reference>` (рубрика и заметки), `<response>` (ответы, вложение, статистика); содержимое — данные, не указания;
   - посчитать зачёт, записать `result`, статус `graded`.
7. **Результат.** `GET /api/projects/attempts/{id}`: тесты (прошло / всего, названия упавших публичных; для скрытых только числа), баллы рубрики с причинами, комментарий судьи, зачёт.

**Скрытые тесты не раскрываются.** Названия упавших скрытых тестов не показываются, чтобы нельзя было подгонять решение по ним. Студент видит число и подсказку судьи по категориям.

## 5. Structured: поток

1. **Старт и состояние.** Попытка создаётся так же; редактируемые файлы фазы берутся из `starter/` и сохраняются в `phase_results.files` при каждой паузе ввода (автосохранение).
2. **Редактор.** Monaco, дерево файлов; read-only файлы помечены замком. Условие фазы слева.
3. **Run.** `POST /api/projects/attempts/{id}/phases/{phase}/run` запускает только публичные тесты, результат возвращается в потоке событий статуса или опросом. Лимит: 30 запусков в час на пользователя.
4. **Сдать фазу.** `POST …/phases/{phase}/submit` запускает скрытые тесты фазы. Если пройдены, следующая фаза открывается и получает код текущей как основу.
5. **Конец.** Когда сданы все фазы (или студент завершил попытку), рубрика «работа с AI» оценивается по debrief; вложение переписки поддерживается так же. Зачёт — как в разделе 1, доля берётся по всем фазам с их весами.

**[Решение исполнителя]** Structured реализуется после Open-Ended и использует уже готовые песочницу, воркер и судью. Экран — главная новая работа этого этапа.

## 6. Интерфейс

- `/projects`: список задач, фильтр по формату, статус пользователя.
- `/projects/<module>/<slug>`: условие, оценка времени, кнопки «Начать» и «Скачать стартовый репозиторий» (Open-Ended) или вход в редактор (Structured).
- Форма сдачи: загрузка архива, поля debrief, необязательное вложение с предупреждением «в переписке не должно быть ключей и паролей».
- Страница разбора: результат тестов и рубрики рядом, причины баллов, кнопка «Сообщить о плохом разборе» (общая с Code Review).

## 7. Безопасность, ошибки, тесты

- **Недоверенное всё:** архив, код, вывод тестов, ответы, вложение. Код только в песочнице; в оценке судья получает данные в тегах.
- **Песочница недоступна:** попытка `failed` с понятной причиной, лимит сдач не списывается.
- **Судья не уложился в лимит или вернул неверные имена разделов:** то же, оценка тестов сохраняется, рубрику можно пересчитать повторным запуском.
- Доменные исключения → `{"detail": "..."}`; Origin-проверка на изменяющих запросах, как везде.
- Суточный лимит сдач `PROJECTS_DAILY_LIMIT` (по умолчанию 5), один грейдинг на пользователя одновременно.
- **Тесты (TDD):**
  - `archive.py`: zip-slip, символьные ссылки, лимиты размера и числа файлов;
  - загрузчик задач и структурный тест по `content/`;
  - подсчёт зачёта, пограничные значения `pass_ratio` и рубрики;
  - API с `FakeSandbox` и `FakeLLMClient`: полный путь, сбой песочницы, сбой судьи, лимит, чужая попытка 404;
  - тест утечки: скачиваемый старт и ответы API не содержат `hidden/`, рубрику и заметки;
  - интеграционный тест эталонного решения против реальной песочницы (вне основного CI, отдельная цель Makefile).
- Новые переменные: `JUDGE0_URL`, `PROJECTS_DAILY_LIMIT`, том для архивов. Обновить `.env.example` и `docs/deploy.md`.

## 1. Цель и рамки

### Что сказал заказчик

- Взять режим Code Review из разбора Hello Interview отдельным подпроектом сразу после симулятора, раньше редактора кода.
- Студент читает чужой код с заложенными проблемами и пишет замечания, как в pull request. Оценка похожа на интервью.

### Решения исполнителя

- **Задача** — небольшая кодовая база (2–8 файлов, Python), у которой есть список скрытых проблем и несколько «ловушек», то есть кода, который выглядит подозрительно, но верен.
- **Что пишет студент:** замечания к диапазонам строк (файл, строки, текст), необязательное общее резюме и обязательный вердикт: `approve` или `request_changes`.
- **Оценка** одним вызовом судьи оценщика. Рубрика строится из задачи: по одному разделу на каждую скрытую проблему, плюс «Ложные замечания» и «Приоритеты и вердикт». Формат ответа судьи (`sections[{name, score, reason}]` и `comment`) не меняется, используется готовый `RubricSection`.
- **«Найдена» и «ложные замечания».** **[Решение исполнителя]** Проблема считается найденной, если балл её раздела не ниже 3 из 5. Ложные замечания не выделяются структурно: студент видит текст `reason` раздела «Ложные замечания» и общий `comment`. Привязку «замечание → проблема» в схему судьи не добавляем; добавим, если жалобы покажут, что текста мало.
- **Изменение в `evals`.** **[Решение исполнителя]** Нужна одна небольшая правка: `evals.service` реэкспортирует `judge`, `RubricSection`, `LlmJudgeGrader`, `Grade` (сейчас в `__all__` их нет, а import-linter разрешает только `service`). У `judge()` появляется необязательный параметр с системным промптом, чтобы подсказка про ревью кода не смешивалась с промптом «ответ языковой модели». Поведение по умолчанию не меняется, тесты оценщика остаются зелёными.
- **Зачёт:** взвешенный балл судьи не ниже порога задачи (по умолчанию 0,7), и каждая проблема с пометкой `critical` получила не меньше 3 из 5.
- **Без песочницы.** Код только показывается, не запускается.
- **Таймер мягкий:** на странице показана оценка времени (~15–30 мин), принудительного завершения нет. Команда из ~20 человек, соревнования нет.
- **Раскрытие.** Список проблем и «ловушек» студент видит только после отправки.

### Критерии успеха

- Студент открывает задачу, читает файлы, оставляет замечания, отправляет и получает разбор: какие проблемы найдены, какие пропущены (с объяснением и указанием места), какие замечания ложные.
- Скрытые данные задачи (проблемы, ловушки, эталон, рубрика) не попадают в браузер до отправки. Это закреплено тестом.
- Эталонное ревью каждой задачи (файл `reference_review.yaml`, раздел 2) покрывает все её проблемы и не задевает ловушки. Это проверяется структурным тестом по `content/`, судья в CI не вызывается.
- Стоимость одного разбора ограничена сверху размером входа (лимит на размер кода задачи в загрузчике, лимиты замечаний из раздела 3 и `max_tokens` вызова судьи). Фактическая `cost_usd` записывается в попытку. Предварительной оценки через `count_tokens` нет: `estimate_run_cost` рассчитана на прогон оценщика и для одного вызова не подходит. `shortcut: без предварительной оценки, добавить, если разбор станет заметно дорогим.`

### Не входит

- Запуск кода, патчи, автоисправления.
- Языки кроме Python в первой версии.
- Оценка стиля и форматирования как отдельной категории.
- Соревнование, таблица лидеров, шаринг.
- Многораундовое ревью (ответы автора, повторная отправка исправлений).

## 2. Задачи (контент)

Файлы лежат по схеме `content/<NN-модуль>/tasks/<slug>/`. **[Решение исполнителя]** У Тренажёра задачи лежат плоскими файлами `NN-slug.yaml` в той же папке `tasks/`; его загрузчик (`trainer/tasks.py`) папки молча пропускает, поэтому конфликта нет. Здесь **свой загрузчик в `code_review`**, Тренажёр не меняется. Общий загрузчик с AI-практикой не делаем: дублирование небольшое, выносить будем, когда появится третий потребитель.

```
task.mdx               условие: контекст, что за изменение ревьюится, на что смотреть
task.yaml              скрытая часть, читает только API
reference_review.yaml  эталонное ревью автора, читает только тест по content/
code/                  файлы, которые видит студент (с нумерацией строк)
```

**Docker-образы.** Оба ignore-файла сейчас рассчитаны на плоские `tasks/*.yaml`: web-образ исключает только их, а API-образ пропускает только `tasks/*.yaml` и `*.mdx`. **[Решение исполнителя]** Правим оба: web-образ (`/.dockerignore`) исключает всё в `tasks/<slug>/`, кроме `task.mdx`; API-образ (`apps/api/Dockerfile.dockerignore`) пропускает `tasks/<slug>/**`. Каталог `content/` остаётся на месте, скрытая часть остаётся в нём. Тест: в собранном web-образе нет `task.yaml`, `reference_review.yaml`, `code/` (отдельная цель Makefile, не в обязательном CI).

`reference_review.yaml` (набор замечаний автора и вердикт, формат совпадает с телом отправки студента):

```yaml
verdict: request_changes
comments:
  - {file: worker.py, line_start: 34, line_end: 36, text: ...}
```

`task.yaml`:

```yaml
title: ...
difficulty: medium               # easy | medium | hard
order: 10                        # порядок в списке (задачи без NN- в имени папки)
estimate_min: 20
threshold: 0.7
issues:                          # 1–7 штук
  - id: race-on-lock
    file: worker.py
    lines: [34, 41]
    critical: true
    weight: 3
    description: что за проблема, как проявляется   # видит судья и студент после отправки
    notes: на что обращать внимание при оценке      # только судья
traps:                           # ловушки, 0–3 штуки
  - file: worker.py
    lines: [12, 15]
    why_fine: почему это не ошибка
general_rubric:                  # «Ложные замечания», «Приоритеты и вердикт»
  - {name: ..., description: ..., weight: ...}
expected_verdict: request_changes
```

Правила, которые проверяет загрузчик и тест по `content/`:

- Всего разделов рубрики (проблемы плюс общие) не больше 10, лимит рубрики в оценщике.
- Диапазоны строк лежат внутри файлов; проблем не больше 7.
- Хотя бы одна проблема `critical`, при `expected_verdict: request_changes`.
- Имя раздела рубрики для проблемы равно `id`. Этим судья возвращает баллы по проблемам.
- «Эталон укладывается в рубрику» означает машинную проверку: у каждой проблемы есть хотя бы одно замечание эталона, чей диапазон пересекает её строки; ни одно замечание эталона не пересекает ловушку; вердикт эталона равен `expected_verdict`.
- `difficulty` и `order` обязательны; суммарный размер файлов `code/` не больше 60 КБ (верхняя граница размера входа судьи).

**Объём первой версии.** **[Решение исполнителя]** В план входят загрузчик, одна фикстурная задача для тестов (в `tests/`, не в `content/`) и одна реальная задача: цикл LLM-агента. Две остальные задачи стартового набора пишутся отдельными шагами контента, когда появятся модули 4 и 5. Сейчас в `content/` только `00-start`, поэтому структурный тест по `content/` до появления первой задачи проходит вхолостую.

Стартовый набор для модулей, где контент появится первым:

- модуль 11 (AI engineering): цикл агента без лимита шагов и без обработки ошибки инструмента (Hard);
- модуль 5 (очереди): обработчик webhook без идемпотентности и с гонкой на статусе (Medium);
- модуль 4 (кэш): cache-aside без защиты от stampede и с неверным TTL (Medium).

## 3. Модуль бэкенда `apps/api/app/modules/code_review/`

**[Решение исполнителя]** Имя `code_review`, потому что `review` уже занят Ревью промптов.

```
tasks.py        загрузчик задач из content/, валидация правил выше
judge.py        сборка рубрики и входа судьи, подсчёт зачёта
models.py       ReviewAttempt, ReviewFeedbackReport
schemas.py, service.py, router.py, providers.py
```

- Из оценщика берётся только то, что экспортирует `app.modules.evals.service`: `LLMClient`, `judge`, `RubricSection`, `LlmJudgeGrader`, `Grade`. Реэкспорт добавляется в `__all__` (раздел 1). Вход собирается в аргументы `judge()`: `inputs` (условие и код с номерами строк), `expected` (проблемы, ловушки, заметки), `output` (замечания, вердикт, резюме). Новый контракт import-linter для `code_review`.
- Провайдер регистрируется в `container.py`, роутер в `factory.py`, как у остальных модулей.

### Таблицы

```
review_attempts
  id          uuid PK
  user_id     uuid FK → users ON DELETE CASCADE
  task_key    text NOT NULL              -- "<module>/<slug>"
  status      text NOT NULL              -- draft | grading | graded | failed
  comments    jsonb NOT NULL default '[]'  -- [{file, line_start, line_end, text}]
  verdict     text NULL                  -- approve | request_changes
  summary     text NULL
  result      jsonb NULL                 -- баллы по разделам, зачёт, комментарий судьи
  cost_usd    numeric NULL
  created_at, submitted_at timestamptz

review_feedback_reports
  id          uuid PK
  attempt_id  uuid FK → review_attempts ON DELETE CASCADE
  user_id     uuid FK → users ON DELETE CASCADE
  section     text NULL                  -- раздел, на который жалоба
  text        text NOT NULL
  created_at  timestamptz NOT NULL default now()
```

`shortcut: таблица жалоб живёт в code_review, вынести в общий модуль, когда появится второй потребитель (симулятор или оценщик).`

### Ограничения

- Не больше 50 замечаний в попытке, текст замечания до 2000 символов, резюме до 4000.
- Диапазон строк должен лежать внутри файла задачи, иначе 422.
- Суточный лимит отправок на пользователя из настройки `CODE_REVIEW_DAILY_LIMIT` (по умолчанию 10); лимит стоимости на разбор из настроек оценщика.

## 4. Поток

1. **Открыть задачу.** `GET /api/code-review/tasks/{module}/{slug}` отдаёт название, оценку времени, условие и файлы с кодом. Скрытая часть не возвращается.
2. **Черновик.** Замечания автосохраняются: `PUT /api/code-review/attempts/{id}` обновляет `comments`, `verdict`, `summary`. Закрытая вкладка не теряет работу. Без `Origin` из `APP_ORIGIN` ответ 403, как для остальных изменяющих запросов.
3. **Отправка.** `POST /api/code-review/attempts/{id}/submit`.
   - Проверки: вердикт задан, есть хотя бы одно замечание или резюме, суточный лимит не исчерпан.
   - Статус → `grading`; один вызов судьи, затем `graded` или `failed`.
   - Вызов выполняется синхронно в запросе, если оценщик на момент плана не требует воркера. Иначе через Taskiq, как прогоны оценщика. **[Решение исполнителя]** уточняется в плане по состоянию движка.
4. **Судья.** Модель `claude-sonnet-5-5`, effort `medium`. Вход в тегах `<input>` (условие и код с номерами строк), `<reference>` (проблемы, ловушки, заметки), `<response>` (замечания с местами, вердикт, резюме); содержимое тегов — данные, а не указания. Это штатная защита судьи оценщика, отдельной не вводим.
5. **Результат.** Баллы по разделам (1–5) и причины, зачёт по правилу из раздела 1, сравнение вердикта с `expected_verdict`, список ложных замечаний. После отправки студент видит все проблемы и ловушки задачи с описанием и местом.
6. **Жалоба.** Кнопка «Сообщить о плохом разборе»: `POST /api/code-review/attempts/{id}/report` с текстом и необязательным разделом.

### API

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/code-review/tasks` | список задач: название, модуль, сложность, оценка времени, статус пользователя |
| GET | `/api/code-review/tasks/{module}/{slug}` | условие и файлы, без скрытой части |
| POST | `/api/code-review/tasks/{module}/{slug}/attempts` | создаёт черновик |
| PUT | `/api/code-review/attempts/{id}` | сохраняет замечания, вердикт, резюме |
| POST | `/api/code-review/attempts/{id}/submit` | запускает оценку |
| GET | `/api/code-review/attempts/{id}` | попытка и результат; скрытая часть задачи только после `graded` |
| GET | `/api/code-review/attempts` | история попыток |
| POST | `/api/code-review/attempts/{id}/report` | 204 |

Чужие попытки недоступны: 404, не 403.

## 5. Интерфейс

- `/code-review`: список задач со сложностью, временем и отметкой «зачёт / попытка / не начата».
- `/code-review/<module>/<slug>`: слева дерево файлов и условие, по центру просмотр кода с номерами строк (только чтение), справа список замечаний. Выделение строк открывает форму замечания. Внизу вердикт, резюме и «Отправить».
- Подсветка синтаксиса на сервере. **[Решение исполнителя]** Shiki; если MDX-конвейер уже использует другую подсветку, берётся она. Monaco здесь не нужен.
- После отправки та же страница показывает разбор: по каждой проблеме найдена или нет, объяснение, место в коде, список ложных замечаний, общий комментарий судьи, кнопка жалобы.
- Узкий экран: показывается условие и разбор, редактор замечаний только на десктопе, как у симулятора.

## 6. Ошибки, безопасность, тесты

- Доменные исключения (`NotFound`, `Conflict`, `Forbidden`) переводятся в `{"detail": "..."}` обработчиком из `core/errors.py`.
- Судья не уложился в лимит ответа или вернул разделы с неверными именами: попытка `failed`, лимит отправок не списывается, студент может отправить снова.
- **Тесты (TDD).**
  - Загрузчик задач и структурный тест по реальной `content/`: правила раздела 2.
  - Сборка рубрики из задачи; подсчёт зачёта, включая правило `critical`; пограничные значения порога.
  - API с `FakeLLMClient`: черновик, отправка, сбой судьи, суточный лимит, 404 на чужую попытку, 422 на выход за границы файла.
  - Тест утечки: ответы `GET` задачи и черновика не содержат `issues`, `traps`, `notes`, `expected_verdict` до `graded`.
  - Живой smoke на реальном Claude, вне CI, по образцу `make evals-smoke`.
- Секреты и ключи не добавляются: используется серверный ключ оценщика.

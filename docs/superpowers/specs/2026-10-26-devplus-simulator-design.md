## 1. Цель и рамки

### Что сказал заказчик

- **Назначение.** Тренажёр system design к интервью, по мотивам PRISM. Студент открывает задачу, рисует архитектуру из компонентов, сервер прогоняет её через сценарии нагрузки и отказов, Claude разбирает рассуждения.
- **Зачёт** складывается из симуляции и AI-разбора сразу, а не только из сценариев.
- **Что пишет студент.** Три поля по фреймворку интервью: «Требования и допущения», «Оценка нагрузки», «Ключевые решения и компромиссы».
- **Доска для схем.** Симулятор заменяет архитектурную часть подпроекта «Доска для схем». От доски остаются ER-диаграммы, их делаем позже.
- **Подход A.** Аналитический движок на сервере (Python), canvas на React Flow.

### Предположения, с которыми заказчик согласился

- Задачи лежат файлами в git, как задачи Тренажёра промптов. На старте три задачи модуля 10: сокращатель ссылок, чат, лента.
- В MVP 9 компонентов и рёбра `sync`/`async`.
- Модель детерминированная: потоки и очереди, без поштучной симуляции и без анимации пакетов.
- «Прогнать» бесплатен и мгновенен на открытых сценариях. «Отправить» запускает скрытые сценарии и AI-разбор с лимитом стоимости.
- Редактор рассчитан на десктоп, на узком экране только условие.

### Критерии успеха

- Студент проходит задачи модуля 10 целиком: рисует схему, прогоняет её, отправляет и получает зачёт или разбор.
- Разбор понятен: какой сценарий не прошёл, какой узел сломался первым и почему, что исправить, плюс оценка рассуждений по разделам рубрики.
- Скрытые сценарии, рубрика и эталон не попадают в браузер. Это закреплено тестами.
- Эталонная схема каждой задачи проходит все сценарии, а наивная (User → Server → Database) нет. Это проверяет тест по реальной `content/`.

### Не входит (задачи на будущее)

- Learn-стадии эволюции архитектуры.
- Режим Design & Fix: починить сломанную систему.
- Stress test со ступенчатой нагрузкой и поиском точки слома.
- Шаринг попыток, экспорт в PNG и PDF.
- AI-интервью в несколько раундов.
- Компоненты второй волны: Service с circuit breaker, ретраи и timeouts, autoscaling, API Gateway, Search Index, Blob Storage, WebSocket, 3rd-party API.
- Движок в браузере (TS в Web Worker) для мгновенных ползунков.
- Мобильный редактор.

- Провайдер регистрируется в `container.py`, роутер в `factory.py`.

### Таблица `sim_attempts`

```
sim_attempts  id uuid PK, user_id → users, task_key text,           -- "<module>/<slug>"
              graph jsonb, answers jsonb,                             -- {requirements, estimates, tradeoffs}
              scenarios jsonb, findings jsonb,                        -- результаты всех сценариев и правил
              review jsonb NULL, review_error text NULL,              -- AI-разбор или причина сбоя
              score numeric NULL, passed bool, cost_usd numeric(10,6),
              created_at timestamptz
              INDEX (user_id, task_key, created_at)
```

- «Решено» = у пользователя есть попытка по задаче с `passed=true`. Отдельно не хранится.
- `review` содержит итоговый балл, разделы рубрики с баллом 1–5 и комментарием и общий вывод.

### Права

- Попытки видит только автор. Чужая попытка даёт 404.
- Задачи и каталог компонентов видят все вошедшие пользователи.

## 3. Модель симуляции

### Каталог компонентов MVP

Ёмкость указана на одну копию, задержка — базовая. Константы живут только в `catalog.py`, веб получает их через API.

| Тип | Параметры (пределы) | Ёмкость, rps | Задержка, мс |
|---|---|---|---|
| User | — | — | — |
| CDN | `hit_ratio` 0–0.99 | 100 000 | 5 |
| Rate Limiter | `limit_rps` > 0 | 50 000 | 2 |
| Load Balancer | `replicas` 1–100 | 50 000 | 2 |
| Server | `replicas` 1–100 | 1 000 | 30 |
| Cache | `hit_ratio` 0–0.99, `replicas` 1–100 | 50 000 | 2 |
| Database | `read_replicas` 0–100, `shards` 1–100 | 2 000 | 20 |
| Queue | `max_size` 1–10 000 000 | 20 000 | 5 |
| Worker | `replicas` 1–100 | 500 | 50 |

Рёбра: `kind` — `sync` или `async`; `ratio` 0–10, по умолчанию 1. `ratio` означает, сколько вызовов по ребру приходится на один входящий запрос. Рёбра в Queue и Worker всегда `async`.

### Нагрузка

Задача задаёт `peak_rps` и `read_ratio`. Сценарий умножает `peak_rps` на `multiplier`. Весь поток входит через узел User.

### Расчёт

Один проход по узлам в топологическом порядке по всем рёбрам.

1. **Поток.** Ребро передаёт ребёнку `λ_served(родитель) × ratio`, чтения и записи отдельно.
   - CDN и Cache передают дальше `(1 − hit_ratio)` чтений. Записи идут насквозь.
   - Rate Limiter пропускает не больше `limit_rps`. Остальное — «отклонено».
   - Database: копий `1 + read_replicas` на шард. Чтения делятся на все копии, записи идут только в primary. `shards` делит и то, и другое.
2. **Загрузка.** `μ = ёмкость × копии`, `ρ = λ / μ`. Обслуживается `min(λ, μ)`, остальное — ошибки узла. У Database загрузка считается отдельно для primary (записи и своя доля чтений) и для реплик, в отчёт идёт худшая.
3. **Задержка узла:** `base / (1 − min(ρ, 0.95))`. Это средняя оценка, а не p99; в UI она подписана «средняя задержка».
4. **Сквозная задержка** по sync-рёбрам: `L(v) = свой + Σ ratio × L(child)`. Async-рёбра в задержку пользователя не входят.
5. **Доля успеха** по sync-рёбрам: `s(v) = served/λ × Π (1 − min(1, ratio × (1 − s(child))))`. Ошибка запроса пользователя = `1 − s(User)` с учётом отклонённых rate limiter'ом.
6. **Очередь.** Worker'ы забирают из Queue `min(λ_queue, μ_workers)` и передают дальше по своим рёбрам. Это нагрузка, например, на Database. Если `λ_queue > μ_workers`, backlog растёт на `(λ_queue − μ_workers) × duration_s`. Сверх `max_size` сообщения теряются: `loss = max(0, backlog − max_size) / (λ_queue × duration_s)`.
7. **Числа.** NaN или inf в любом результате — ошибка движка, а не результат.

### Структурные ошибки

Они блокируют расчёт и возвращаются списком:
- узлов User не ровно один;
- есть цикл;
- есть узел с рёбрами, недостижимый от User (узел совсем без рёбер — не ошибка, а предупреждение `ISOLATED_NODE`; в расчёт он не входит);
- есть узел без исходящих рёбер, который не Database, Cache, CDN или Worker (запрос «уходит в никуда»);
- ребро ссылается на несуществующий узел.

### Сценарии

- **`normal`:** `multiplier: 1`.
- **`spike`:** `multiplier: k`, `duration_s: N`. Длительность влияет только на backlog очереди.
- **`failure`:** `{type, mode}`.
  - Отказывает узел этого типа с наибольшей `ρ` в сценарии `normal` (при равенстве — первый по id).
  - `mode: replica` убирает одну его копию. У Database сначала убирается реплика (failover сохраняет записи); если реплик нет, узел падает целиком.
  - `mode: node` или последняя копия: узел отказывает целиком. Обход есть только у Cache, CDN и Rate Limiter с детьми: узел удаляется, его входящий поток уходит детям по их `ratio`. У остальных узлов (Server, Load Balancer, Queue, Worker, Database) и у терминальных поток становится ошибками.
- **Цели сценария:** `max_latency_ms`, `max_error_rate`, `max_message_loss` (по умолчанию 0). Сценарий пройден, если выполнены все цели.

### Результат сценария

- Вердикт и сквозные метрики: средняя задержка, доля ошибок, отклонено, потеряно сообщений.
- По каждому узлу: `λ`, `μ`, `ρ`, задержка, ошибки, backlog.
- Узкое место — узел с максимальной `ρ`.
- Объяснение по-русски из тех же чисел: «Database получает 3 200 rps при ёмкости 2 000: 38% запросов теряется».
- Окраска узлов по `ρ`: < 0.7 зелёный, < 0.9 жёлтый, < 1 оранжевый, ≥ 1 красный.

## 4. Правила архитектуры

Каждая находка содержит код, важность, текст «почему плохо» и id узла.

**Критичные** (блокируют зачёт):
- `STORAGE_EXPOSED`: ребро User → Database или Cache.
- `QUEUE_NO_CONSUMER`: у Queue нет исходящего ребра в Worker.
- `CACHE_BEHIND_DB`: Cache стоит после Database на пути запроса.

**Предупреждения** (показываются и передаются в AI-разбор):
- `SINGLE_SERVER`: у Server одна копия, перед ним нет Load Balancer.
- `REPLICAS_WITHOUT_LB`: у Server больше одной копии, а Load Balancer перед ним нет.
- `NO_CACHE_READ_HEAVY`: `read_ratio ≥ 0.8`, а на пути чтений нет ни Cache, ни CDN.
- `DB_NO_REPLICAS`: у Database `read_replicas = 0`.
- `WORKER_WITHOUT_QUEUE`: в Worker не входит ребро из Queue.
- `DEEP_SYNC_CHAIN`: sync-путь длиннее 5 узлов (не считая User).
- `ISOLATED_NODE`: у узла нет рёбер.

## 5. Задачи

### Файлы

`content/<NN-модуль>/simulator/<NN-задача>.mdx` и одноимённый `.yaml`.
- `module` и `slug` берутся из имён без префикса `NN-`.
- MDX: frontmatter `title`, `summary`; текст по шаблону «Контекст / Требования / Что проверяется».
- Битый YAML, пара без второго файла, неизвестное поле и повтор slug дают исключение с именем файла.
- Задачи кэшируются в памяти процесса, как в Тренажёре.

### Формат YAML

```yaml
scale: { peak_rps: 5000, read_ratio: 0.9 }
scenarios:
  - { id: normal, title: Обычная нагрузка, visible: true, multiplier: 1,
      max_latency_ms: 150, max_error_rate: 0.01 }
  - { id: spike, title: Всплеск ×3, visible: true, multiplier: 3, duration_s: 60,
      max_latency_ms: 300, max_error_rate: 0.05 }
  - { id: db-down, title: Отказ базы, visible: false, multiplier: 1,
      failure: { type: Database, mode: replica },
      max_latency_ms: 300, max_error_rate: 0.05 }
review:
  threshold: 0.7
  rubric:                       # формат RubricSection оценщика
    - { name: Требования и допущения, description: …, weight: 1 }
    - { name: Оценка нагрузки, description: …, weight: 1 }
    - { name: Архитектура, description: …, weight: 1 }
    - { name: Компромиссы, description: …, weight: 1 }
  reference: |                  # заметки эталонного решения, видит только судья
    …
reference_graph: { nodes: […], edges: […] }   # эталонная схема, только для теста
```

Хотя бы один сценарий должен быть `visible: true` и хотя бы один `visible: false`.

### Видимость

- **До отправки** браузер получает условие (MDX), `scale` и открытые сценарии с целями.
- **После отправки** браузер получает названия и вердикты всех сценариев с объяснениями. Числа целей и параметры скрытых сценариев не отдаются.
- `review` (рубрика, порог, `reference`) и `reference_graph` не отдаются никогда.

### Стартовые задачи (модуль 10)

`01-url-shortener`, `02-chat`, `03-news-feed`. Каждая с 2 открытыми и 3–4 скрытыми сценариями, рубрикой из 4 разделов и эталонной схемой.

## 6. Отправка и AI-разбор

### `POST /api/simulator/tasks/{module}/{task}/attempts`

1. Проверить вход (раздел 8). Проверить суточный лимит: не больше 20 попыток за последние 24 часа без `review_error`, иначе 429 «Лимит отправок на сегодня исчерпан».
2. Структурные ошибки дают 422 «Схема не прогоняется: …». Claude не вызывается.
3. Прогнать все сценарии и правила.
4. Оценить стоимость разбора. Выше $0.10 — 400 по формату оценщика.
5. **AI-разбор.** Судья оценщика, модель `claude-sonnet-5-5`, effort `medium`. На вход он получает:
   - условие задачи;
   - граф в компактном текстовом виде («Server ×3 → Cache (hit 0.8) → Database (реплик 2)»);
   - результаты всех сценариев и находки правил;
   - три ответа студента;
   - `reference`.

   На выходе — балл 1–5 и комментарий по каждому разделу рубрики плюс общий вывод. Итоговый балл 0..1 считается как в оценщике.
6. **Зачёт:** все сценарии пройдены, критичных находок нет, `score ≥ threshold`.
7. Сохранить попытку и вернуть её.

Запрос синхронный. Пометка в коде: `shortcut: синхронный вызов Claude, перенести в worker, если ответы станут дольше минуты`.

### Сбой AI-разбора

Сбой — это API-ошибка, отказ, обрезанный ответ или ответ не по схеме. Тогда:
- попытка сохраняется с результатами сценариев и правил, `review_error` = понятная причина, `passed=false`;
- в суточный лимит она не считается;
- причина пишется в лог без текстов студента.

## 7. API (сводно)

| Метод и путь | Назначение |
|---|---|

## 8. Веб

### Страницы

- `/simulator`: заголовок «Симулятор», задачи по модулям, у решённых «✓ решено». Ссылка «Симулятор» в шапке.
- `/simulator/[module]/[task]`: рабочее место.

### Рабочее место

- **Слева «Компоненты» и «Инспектор».**
  - Компонент можно перетащить на canvas или выбрать с клавиатуры (Enter ставит его в центр). При наведении появляется описание.
  - Инспектор показывает параметры выбранного узла; форма строится из каталога API.
- **Центр — canvas на `@xyflow/react`.**
  - Связи тянутся от порта к порту. Клик по ребру открывает выбор `sync`/`async` и поле `ratio`.
  - Delete удаляет; есть Ctrl+Z / Ctrl+Y, zoom и fit.
  - Пустой canvas подсказывает: «Добавь User и опиши, куда идут запросы».
- **Справа вкладки:**
  - «Условие»: MDX, масштаб, открытые сценарии с целями.
  - «Ответы»: три поля, до 5 000 символов каждое.
  - «Результаты»:
    - после «Прогнать» — ✓ или ✗ по открытым сценариям, задержка, ошибки, узкое место, объяснение и находки правил (клик выделяет узел);
    - после «Отправить» — плюс вердикты скрытых сценариев, AI-разбор по разделам, балл и «Зачтено» или «Не зачтено»;
    - переключатель сценария красит узлы по `ρ` и подписывает «λ / μ rps».
  - «Попытки»: дата, балл, итог. По клику открывается схема попытки только для просмотра.
- **Кнопки «Прогнать» и «Отправить».** Заблокированы, пока идёт запрос. «Отправить» показывает «Разбираем решение…».
- **Черновик** (граф и ответы) сохраняется в `localStorage` по задаче; есть кнопка «Начать заново».
- **Ширина меньше 1024 px:** «Редактор доступен на компьютере», условие читается.

## 9. Сквозные вопросы

### Проверки на входе

Pydantic, 422 с русским текстом:
- тип узла из каталога, параметры в пределах каталога;
- уникальные id, рёбра ссылаются на существующие узлы;
- до 50 узлов и 100 рёбер;
- ответы до 5 000 символов каждый, без NUL.

### Тесты (по TDD)

- **Движок:**
  - около 10 golden-схем с ожидаемыми числами: перегруженный сервер; тот же сервер с кэшем; реплики БД под чтением; шарды под записью; backlog и потеря в очереди; отказ узла с обходом; отказ БД без реплик; rate limiter во всплеске;
  - свойства: больше копий не увеличивает ошибки; кэш не увеличивает нагрузку на Database; результат без NaN и inf.
- **Правила:** на каждое правило тест «срабатывает» и «не срабатывает».
- **Задачи:** тест по реальной `content/`: эталон каждой задачи проходит все сценарии без критичных находок, наивная схема User → Server → Database не проходит.
- **API (`FakeLLMClient`):**
  - `run`, `attempts`, сбой судьи, суточный лимит, 422 на структурные ошибки без вызова Claude;
  - скрытые сценарии, рубрика, `reference` и `reference_graph` не появляются ни в одном ответе. Проверка по ключам и по строкам.
- **Веб:**
  - Vitest: преобразование граф ↔ API, черновик;
  - Playwright: собрать схему, «Прогнать» показывает вердикт, «Отправить» на фейке показывает итог.

### Логи и безопасность

- Каждая запись лога попытки несёт `attempt_id` и `task_key`, без текстов студента.
- Ответы студента идут судье через `judge` оценщика, который экранирует теги данных.

### Дорожная карта

- Симулятор становится подпроектом 3 сразу после оценщика.
- «Контент», «Редактор и запуск кода» и «Визуализатор алгоритмов» сдвигаются на шаг.
- «Доска для схем» превращается в «ER-диаграммы».

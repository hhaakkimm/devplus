## 1. Цель и рамки

### Что сказал заказчик

- **Механизм.** Оценщик промптов на общем движке «промпт → датасет → прогон → оценщики → отчёт».
- **Режимы:** Тренажёр, Лаборатория и Ревью (отдельный режим, LLM-критик без прогона).
- **Провайдер.** Только Claude (Anthropic API).
- **Расходы.** Оценка стоимости до запуска и жёсткий лимит на один прогон.
- **Промпт.** Системный промпт и шаблон пользователя с `{{переменными}}`, один ход.
- **Агентный режим** (tool use и агентный цикл) уходит в задачи на будущее.
- **Датасеты.** Импорт и экспорт JSONL плюс форма правки кейса.
- **Задачи Тренажёра.** Файлы в репозитории, скрытые кейсы видит только сервер.
- **Доступ.** Личное по умолчанию плюс «поделиться с командой».
- **Исполнение.** Модуль в API и отдельный worker с очередью на Redis (Taskiq).
- **Бэкапы БД** входят в объём: в обзорной спеке они нужны до запуска Лаборатории.

### Предположения, с которыми заказчик согласился

- Ключ Anthropic API один на команду и лежит в env сервера.
- Расшаренное другие видят, запускают и копируют, а правит только автор. Прогоны видит тот, кто запустил, и автор промпта.
- Оценщики на Python-коде откладываются до песочницы из подпроекта 4.
- В этом подпроекте Тренажёр получает 2 примера задач. Задачи модуля 11 пишутся в подпроекте 3 «Контент».

### Критерии успеха

1. Создать промпт и датасет, запустить прогон, получить баллы по кейсам, стоимость и задержку, сравнить две версии.
2. Получить ревью промпта и одной кнопкой проверить переписанную версию на датасете.
3. Решить задачу Тренажёра и за секунды получить «Зачтено» или «Не зачтено».
4. Прогон с ожидаемой стоимостью выше лимита не запускается, а при перерасходе по ходу останавливается.
5. Бэкап БД делается каждый день, и восстановление проверено.

### Не входит (задачи на будущее)

- агентный режим;
- экономный прогон через Batches API;
- другие провайдеры;
- оценщики на Python-коде;
- ручная разметка ответов людьми;
- многоходовые диалоги.

### Правила

- **Версия промпта неизменяема.** Правка создаёт новую версию с `number + 1`.
- **Результат прогона хранит снимок входа (`input_vars`).** Правка датасета не меняет старые прогоны.
- **Зачёт в Тренажёре не хранится отдельно.** Задача решена, если у пользователя есть прогон с `source=trainer`, нужным `task_slug` и `passed=true`.
- **Ревью свободного текста создаёт промпт «Ревью от <дата>».** Версия 1 — исходник, версия 2 — переписанный вариант.

### Права

| Действие | Кто может |
|---|---|
| Видеть, запускать, копировать промпт или датасет | Автор; все, если `shared` |
| Править промпт или датасет (новая версия, кейсы, имя, `shared`) | Только автор |
| Видеть прогон | Кто запустил и автор промпта |
| Видеть ревью | Только автор ревью |

Чужое без доступа отвечает 404, а не 403, чтобы не выдавать, что объект существует.

## 3. Движок прогона

### Запуск: `POST /api/evals/runs`

Тело: `prompt_version_id`, `dataset_id`, `graders`, `cost_limit_usd` (по желанию, не выше `EVALS_RUN_COST_LIMIT_USD`).

1. Проверить доступ к версии и датасету. Проверить, что все переменные шаблона есть в каждом кейсе. Если чего-то не хватает, ответ 422 со списком позиций кейсов.
2. Посчитать ожидаемую стоимость:
   - один вызов `count_tokens` на системный промпт и первый отрендеренный кейс даёт соотношение «символы → токены», его применяем ко всем кейсам;
   - ожидаемая длина ответа — длина эталона по тому же соотношению или 300 токенов, если эталона нет;
   - стоимость судьи считается по той же схеме: вход — кейс плюс ответ плюс рубрика, выход — 400 токенов.
3. Если ожидаемая стоимость больше лимита, ответ 400 `{"detail": "Ожидаемая стоимость $X превышает лимит $Y"}`.
4. Создать `runs` со статусом `queued`, поставить задачу `execute_run(run_id)` в Taskiq, ответ 201 с прогоном.

`POST /api/evals/runs/estimate` принимает то же тело. Он выполняет шаги 1–2 и возвращает `{estimated_cost_usd, cost_limit_usd}`, ничего не создавая.

### Исполнение: `RunExecutor.execute(run_id)`

Задача Taskiq — тонкая обёртка над этим методом.

1. Заблокировать строку прогона. Если статус не `queued`, выйти: так задача идемпотентна. Иначе поставить `running` и `started_at`.
2. Кейсы идут параллельно, одновременно не больше `EVALS_CONCURRENCY`. Новый кейс не стартует, если флаг перерасхода уже поднят. Каждый кейс:
   1. Отрендерить шаблон.
   2. Вызвать `LLMClient.complete(...)`.
   3. Прогнать оценщики (раздел 4).
   4. Записать `run_results`.
   5. Атомарно прибавить `cases_done` и `cost_usd` (`UPDATE … RETURNING`).
   6. Если `cost_usd > cost_limit_usd`, поднять флаг перерасхода.
3. Итог:
   - посчитать `score_avg` и `pass_rate` по завершённым кейсам;
   - для Тренажёра посчитать `passed = pass_rate ≥ pass_threshold`;
   - статус: `over_budget` при флаге, `failed`, если у всех кейсов `error`, иначе `done`;
   - записать `finished_at`.
4. При старте worker все прогоны в статусе `running` получают `failed` с ошибкой «Прерван: worker перезапущен». Повторно их не запускаем.

### Ошибки кейса

Ошибка кейса не роняет прогон: пишется `error`, `score = 0`, `passed = false`.

| Ситуация | Что делаем |
|---|---|
| В кейсе нет переменной (датасет правили после проверки) | Ошибка кейса «Нет переменной X» |
| `stop_reason: refusal` | Ошибка кейса «Модель отказалась отвечать (<category>)» |
| `stop_reason: max_tokens` | Ответ оценивается как есть, `truncated = true` |
| 429 / 5xx / сеть | SDK повторяет (2 попытки), затем ошибка кейса |
| Ответ не по `output_schema` | Не бывает: structured outputs гарантируют схему |

### Клиент Claude

```python
class LLMClient(Protocol):
    async def complete(self, request: CompletionRequest) -> Completion: ...
    async def count_tokens(self, request: CompletionRequest) -> int: ...
```

- **`CompletionRequest`:** `model`, `system`, `user`, `effort`, `max_tokens`, `output_schema | None`.
- **`Completion`:** `text`, `json | None`, `stop_reason`, `refusal_category | None`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `latency_ms`.
- **`AnthropicLLMClient`** работает на `anthropic.AsyncAnthropic` (SDK 1.x):
  - adaptive thinking, effort из запроса;
  - `cache_control` на системный промпт;
  - `output_config.format`, если задана схема;
  - потоковый режим с `get_final_message()`, если `max_tokens > 16000`.
- **Fallback на другую модель:**
  - в прогонах выключен, иначе прогон измерил бы не ту модель, которую выбрали;
  - у судьи и критика включён (`fallbacks: "default"` с бета-заголовком `server-side-fallback-2026-07-01`);
  - каждая попытка оплачивается, поэтому токены `Completion` суммируются по `usage.iterations`, а не берутся из верхнеуровневого `usage` (он описывает только ответившую попытку).
- **`FakeLLMClient`** для тестов и e2e. Ответы детерминированы и берутся из словаря «отрендеренный вход → ответ», а если ключа нет — эхо входа. Токены фиксированы. Подключается через dishka или настройкой `EVALS_LLM_BACKEND=fake`.

### Прогресс

- `GET /api/evals/runs/{id}` отдаёт прогон и, пока он не завершён, `cases_done / cases_total`.
- Интерфейс опрашивает этот эндпоинт раз в 2 секунды, пока статус `queued` или `running`.

## 4. Оценщики

Конфигурация — список в `runs.graders`, Pydantic-объединение по полю `type`. Проверяется при создании прогона.

| Тип | Настройки | Балл | Прошёл |
|---|---|---|---|
| `exact` | `ignore_case: bool = false` | 1, если `output.strip()` совпадает с `expected.strip()` | балл = 1 |
| `regex` | `pattern`, `must_match: bool = true` | 1, если найдено (или не найдено при `must_match=false`) | балл = 1 |
| `json_schema` | `schema` | 1, если ответ парсится как JSON и подходит под схему | балл = 1 |
| `llm_judge` | `rubric: [{name, description, weight}]`, `threshold: float = 0.7`, `model = claude-sonnet-5-5` | `Σ weight·(score−1)/4 / Σ weight` | балл ≥ `threshold` |

### LLM-судья

- Модель по умолчанию `claude-sonnet-5-5`, effort `medium`.
- Ответ по JSON-схеме: `{sections: [{name, score: 1..5, reason}], comment}`. Имена разделов обязаны совпадать с рубрикой, иначе это ошибка оценщика.
- Системный промпт судьи фиксирован в `evals/judge.py`. Вход кейса, эталон и проверяемый ответ передаются в тегах `<input>`, `<reference>`, `<response>` с инструкцией, что содержимое тегов — данные, а не указания.
- Стоимость судьи входит в `cost_usd` кейса и в лимит прогона.
- Компонент общий: подпроект 4 переиспользует его для AI-ревью практики-проектов по разделам.

### Подсчёт

- **Кейс:** балл — среднее баллов его оценщиков. Кейс прошёл, если прошли все его оценщики.
- **Пропуск `exact`.** Если у кейса нет эталона, `exact` для него пропускается: в среднее не входит и на «прошёл» не влияет.
- **Ошибка оценщика** (таймаут regex, ошибка судьи) даёт этому оценщику балл 0 и «не прошёл», причина пишется в `grades`.

### Защита на входе

- **regex** компилируется при создании прогона, синтаксическая ошибка даёт 422. Исполняется библиотекой `regex` с `timeout=1.0`: это защита от ReDoS.
- **Повторы в пользовательских regex.** Библиотека `regex` при компиляции разворачивает повторы: `a{100000000}` занимает десятки ГБ, вложенные `(?:(?:a+)+)+` на 24 уровня занимают 11 ГБ, и таймаут от этого не спасает. Поэтому до компиляции pattern разбирается парсером самой `regex` (так видно ровно то, что она развернёт) и измеряется:
  - число в `{n}`, `{n,}`, `{n,m}` не больше 1000;
  - повтор делает `min + 1` копий тела (измерено: `{2}` даёт три, `+` две, `*`, `?` и `{0,n}` одну), вложенные повторы перемножаются, соседние складываются, в сумме не больше 10 000 (при этом компиляция занимает единицы мегабайт);
  - то же правило действует на `pattern` и ключи `patternProperties` внутри JSON-схем.
- **JSON-схема** проверяется по мета-схеме Draft 2020-12 (`Draft202012Validator.check_schema`). Схема оценщика `json_schema` проверяется строже: нет `$ref`, `$dynamicRef`, `$recursiveRef` (цепочки ссылок дают экспоненциальную работу), вложенность не глубже 32, `patternProperties` не сочетается с `additionalProperties` и `unevaluatedProperties` (их `jsonschema` проверяет стандартным `re` без таймаута). Ключевые слова `pattern` и `patternProperties` исполняются библиотекой `regex`, на всю проверку ответа одним кейсом даётся 1 секунда, превышение даёт ошибку оценщика «Таймаут регулярного выражения».
- **Размеры:** `pattern` до 1 КБ, `schema` до 64 КБ, `rubric` до 10 разделов, оценщиков в прогоне до 5, `weight` раздела рубрики от 0 (не включая) до 100.

## 5. Режимы: страницы и API

В шапке добавляются ссылки «Лаборатория», «Ревью», «Тренажёр».

### Лаборатория

| Страница | Содержимое |
|---|---|
| `/lab` | Вкладки «Промпты» и «Датасеты»: мои и расшаренные, у чужих указан автор. Кнопки «Новый промпт» и «Новый датасет» |
| `/lab/prompts/[id]` | Форма версии, список версий, «Новая версия», «Поделиться», «Копировать», «Запустить», список прогонов |
| `/lab/datasets/[id]` | Таблица кейсов, «Импорт JSONL», «Экспорт JSONL», форма кейса |
| `/lab/runs/[id]` | Статус и прогресс, сводка (средний балл, доля прошедших, стоимость, задержка p50 и p95), таблица кейсов: вход, ответ, оценки, пояснения судьи, пометка «обрезан» |
| `/lab/compare?a=…&b=…` | Два прогона рядом по `position`, разница балла по каждому кейсу |

- **Формат JSONL:** одна строка — `{"variables": {...}, "expected": "..."}`, поле `expected` необязательно.
- **Ошибки импорта** отвечают 422 с номерами строк. Импорт заменяет кейсы датасета целиком.
- **Диалог «Запустить»:** выбор датасета, оценщиков и лимита, затем ожидаемая стоимость (`estimate`), затем «Запустить».

### Ревью

- **`/review`.** Поле для системного промпта и шаблона (вместе до 20 000 символов) или выбор существующей версии, кнопка «Разобрать».
- **`POST /api/review`** вызывает критика: `claude-opus-5-5`, effort `high`, JSON-схема:

```
{ sections: [{name: "Цель"|"Контекст"|"Формат вывода"|"Примеры"|"Граничные случаи",
              score: 1..5, comment}],
  issues:   [{severity: "high"|"medium"|"low", text}],
  rewritten: {system, user_template} }
```

- **Предупреждение о переменных.** Если в `rewritten` другой набор `{{переменных}}`, показываем: «Переписанная версия использует другие переменные — на текущих датасетах она не запустится».
- **«Проверить улучшение»:** выбор датасета и оценщиков, два прогона `source=review` (исходная и переписанная версии), переход на `/lab/compare`.

### Тренажёр

- **`/trainer`** — задачи по модулям с отметкой «решено».
- **`/trainer/[module]/[task]`:**
  - условие из MDX;
  - форма: системный промпт и шаблон; модель, effort и `max_tokens` задаёт задача;
  - кнопка «Отправить»;
  - результат: «Зачтено» или «Не зачтено», балл и «прошёл / не прошёл» по каждому кейсу без содержимого, стоимость;
  - история попыток.
- **Файлы задачи:** `content/<NN-модуль>/tasks/<NN-задача>.mdx` (условие: «Контекст», «Задача», «Что проверяется») и `.yaml` с тем же именем:

```yaml
model: claude-haiku-5-5
effort: low
max_tokens: 512
variables: [text]
pass_threshold: 0.8
graders: [{type: exact, ignore_case: true}]
cases:
  - variables: {text: "..."}
    expected: "..."
```

- **Скрытые кейсы не уходят в браузер.** API для прогонов с `source=trainer` отдаёт по кейсам только `position`, `score` и `passed`, без `input_vars`, `output` и `grades`. Это закреплено тестом.
- **Проверка шаблона.** Шаблон пользователя обязан содержать все `variables` задачи, иначе 422 с понятным текстом.
- **Два примера задач в модуле `00-start`:**
  - «Извлеки даты в ISO 8601» (`exact`);
  - «Вежливый ответ на жалобу клиента» (`llm_judge` с рубрикой «Вежливость», «Решение проблемы», «Краткость»).
- **YAML читает только API.** Образ `api` теперь собирается из корня репозитория и копирует `content/**/tasks/*.yaml` в `/app/content`. Web рендерит только MDX.

## 6. Сквозные вопросы

### Тесты (по TDD)

- **API** (pytest с фейком `LLMClient` через dishka):
  - лимит до запуска даёт 400;
  - перерасход по ходу даёт `over_budget`, готовые результаты сохраняются;
  - ошибка кейса не роняет прогон;
  - повторный `execute` ничего не делает;
  - прерванные прогоны помечаются при старте worker;
  - каждый оценщик, включая таймаут regex и несовпадение разделов у судьи;
  - матрица прав из раздела 2;
  - скрытые кейсы Тренажёра не утекают;
  - ревью свободного текста создаёт промпт с двумя версиями;
  - импорт JSONL с ошибками отвечает 422 с номерами строк.
- **Worker.** `RunExecutor` тестируется напрямую. Задача Taskiq проверяется с `InMemoryBroker`.
- **Web.** Vitest на разбор `{{переменных}}` и JSONL. Playwright: путь Лаборатории до диалога с оценкой стоимости и одна отправка в Тренажёре. API и worker в e2e работают с `EVALS_LLM_BACKEND=fake`.
- **Живая проверка вручную:** `make evals-smoke` — один запрос к `claude-haiku-5-5`. В CI не входит.

### Конфигурация

| Переменная | По умолчанию | Где |
|---|---|---|
| `ANTHROPIC_API_KEY` | — | `.env`, `app.env`; в CI отсутствует |
| `REDIS_URL` | `redis://localhost:6379/0` | все окружения |
| `EVALS_RUN_COST_LIMIT_USD` | `5` | |
| `EVALS_CONCURRENCY` | `4` | кейсов одного прогона одновременно |
| `EVALS_LLM_BACKEND` | `anthropic` | `fake` только в тестах и e2e |

- Worker выполняет не больше 2 прогонов одновременно (`max_async_tasks`).
- Ключ API в браузер не уходит.

### Ограничения на входе

- до 1000 кейсов в датасете;
- кейс до 32 КБ;
- файл JSONL до 5 МБ;
- системный промпт и шаблон версии вместе до 50 000 символов;
- промпт для ревью до 20 000 символов;
- имя промпта или датасета до 200 символов.

### Инфраструктура

- **Dev compose:** добавляется `redis:7`, опубликован на `127.0.0.1:6379`. `make dev` поднимает также worker (`make worker`).
- **Prod compose:** добавляются `redis` и `worker`. Worker — тот же образ `api`, команда `taskiq worker app.worker:broker`, `depends_on`: `migrate` завершён, `redis` здоров.
- **CI:** job `api` и `e2e` получают сервис Redis.

### Бэкапы БД

- Сервис `backup` в prod compose: образ `postgres:17` плюс `aws-cli`, свой Dockerfile в `infra/backup/`. Раз в сутки (03:00 UTC) он делает `pg_dump --clean --if-exists | gzip` и загружает дамп в S3-совместимое хранилище.
- Переменные: `BACKUP_S3_ENDPOINT`, `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY`, `BACKUP_S3_SECRET_KEY`.
- Хранение 14 дней задаётся правилом жизненного цикла бакета, процедура описана в `docs/deploy.md`.
- Восстановление: `gunzip | psql` в пустую БД, затем `alembic current` подтверждает ревизию. Процедура в `docs/deploy.md`.
- Локальная проверка на MinIO, поднятом отдельным compose-файлом только для проверки.
- Провайдера хранилища выбирает заказчик при настройке VPS.

### Логи и безопасность

- Все записи worker о прогоне несут `run_id`.
- Стоимость и токены хранятся по каждому кейсу.
- Защита судьи от инъекций через теги, таймаут regex, лимиты размеров, проверка прав на каждом эндпоинте и закрытые скрытые кейсы — см. разделы 2–5.

# devplus: обзор платформы и подпроект 1 «Минимальное ядро»

- **Дата:** 2026-10-18
- **Статус:** утверждена 2026-10-18
- **Дорожная карта:** `docs/roadmap.html`

Документ фиксирует общую картину платформы: цель, подпроекты, архитектуру, программу обучения и сквозные правила. Также он задаёт дизайн первого подпроекта, минимального ядра. У оценщика промптов и остальных подпроектов будут свои спецификации.

---

## 1. Цель и рамки

### Что сказал заказчик

- **Что это.** Веб-приложение для подготовки к интервью: system design, алгоритмы и весь путь от «что такое интернет» до «приложение у клиента».
- **Инструменты:**
  - редактор кода с запуском, в том числе компилируемых языков;
  - интерактивный канвас для визуализации деревьев и графов и для рисования схем БД и архитектуры.
- **Темы:** интернет, бэкенд, фронтенд, БД, шины данных, Redis, Kafka, RabbitMQ, Celery, Docker, Kubernetes, балансировщики, микросервисы и монолиты, выбор стека; отдельно архитектура систем, highload и AI engineering (prompt, context, harness, agent loop, evals, разработка с AI).
- **Оценщик промптов.** Нужна отдельная система оценки промптов: общий движок для учебного тренажёра и для рабочего инструмента команды, плюс отдельный режим ревью текста промпта.
- **Аудитория.** Сначала для себя и команды, позже публичный продукт, затем, возможно, подписка.
- **Стек:** Next.js на фронтенде, FastAPI на бэкенде, DI через dishka, разработка в режиме ponytail.

### Предположения, с которыми заказчик согласился

- В команде до ~20 человек.
- «Реддит» в списке тем — это RabbitMQ.
- Интерфейс и контент только на русском, технические термины на английском.
- Уроки хранятся как MDX-файлы в git, правки идут через pull request.

### Критерии успеха на этапе «для команды»

- Участник команды входит через GitHub, видит программу обучения, читает уроки и отмечает прогресс.
- Оценщик промптов работает в трёх режимах: Тренажёр, Лаборатория, Ревью. Критерии будут в его спецификации.
- Платформа развёрнута на VPS и обновляется автоматически после пуша в `main`.

## 2. Архитектура и репозиторий

Выбран подход «модульный монолит и фоновые воркеры». Микросервисы отклонены из-за накладных расходов, которые для команды из ~20 человек не окупаются. Вариант «Next.js как основной бэкенд» отклонён: два бэкенда, два ORM, данные в двух местах.

### Сервисы

| Сервис | Технологии | Роль | Когда появляется |
|---|---|---|---|
| `caddy` | Caddy | TLS (Let's Encrypt), маршрутизация: `/api/*` → api, остальное → web | ядро |
| `web` | Next.js (App Router), TypeScript, Tailwind, shadcn/ui | Страницы, отрисовка MDX | ядро |
| `api` | FastAPI, Pydantic v2, SQLAlchemy 2 (async) + asyncpg, Alembic, dishka | Бизнес-логика, аккаунты, данные | ядро |
| `postgres` | PostgreSQL | Основное хранилище | ядро |
| `migrate` | образ `api`, команда `alembic upgrade head` | Одноразовый прогон миграций перед стартом `api` | ядро |
| `redis` | Redis | Очередь задач и кэш | оценщик |
| `worker` | библиотеку очереди выбираем в спеке оценщика | Фоновые прогоны промптов | оценщик |

### Потоки данных

- **Один origin.** Браузер ходит на один домен. Caddy отправляет `/api/*` в FastAPI, остальное в Next.js. CORS не нужен, cookie работают на одном origin.
- **SSR.** Серверные компоненты Next.js вызывают API по внутренней сети docker (`http://api:8000`) и пробрасывают cookie пользователя.
- **Типы.** FastAPI отдаёт OpenAPI-схему. Из неё генерируется TS-клиент (`openapi-typescript` + `openapi-fetch`) в `packages/api-client`. CI проверяет, что клиент актуален.

### Границы модулей и DI

- Каждый модуль бэкенда: `router` → `service` → `models`, плюс `schemas` и `providers`.
- Модуль обращается к другому только через его `service`. Импортировать чужие `models` и ходить в чужие таблицы запрещено. Правило проверяет `import-linter` в CI.
- **DI только через dishka** (`dishka.integrations.fastapi`):
  - каждый модуль объявляет свой `Provider` в `providers.py`, контейнер собирается в `core` из провайдеров всех модулей;
  - область `APP`: настройки, engine БД, HTTP-клиенты (в том числе клиент GitHub);
  - область `REQUEST`: `AsyncSession`, сервисы, текущий пользователь;
  - сервисы не собираются через цепочки FastAPI `Depends`.
- Подключение dishka к воркеру решаем вместе с выбором очереди в спецификации оценщика.

### Инструменты

- **Python:** uv, ruff (линтер и форматтер), mypy.
- **TypeScript:** pnpm, ESLint, Prettier.

## 3. Подпроект 1: минимальное ядро

### Вход

- GitHub OAuth: `GET /api/auth/github/login` → GitHub → `GET /api/auth/github/callback`.
  - В callback проверяем параметр `state`.
  - Создаём или обновляем пользователя по `github_id`.
- **Список доступа.** Пускаем только логины из переменной окружения `ALLOWED_GITHUB_LOGINS` (через запятую, без учёта регистра). Остальные попадают на страницу «нет доступа».
  - Чтобы добавить человека, достаточно поправить `.env` и перезапустить `api`.
  - Пометка в коде: `shortcut: allowlist в env, заменить на регистрацию при публичном запуске`.
- **Сессия:**
  - случайный токен (`secrets.token_urlsafe(32)`) в cookie `session` с флагами `HttpOnly`, `Secure` (в проде), `SameSite=Lax`, `Path=/`;
  - в БД хранится только SHA-256 хэш токена;
  - срок жизни 30 дней;
  - просроченная сессия равна отсутствию сессии.
- **Выход:** `POST /api/auth/logout` удаляет сессию и cookie.
- **CSRF.** Изменяющие запросы принимают только методы POST, PUT и DELETE. Заголовок `Origin` у них должен совпадать с `APP_ORIGIN`, иначе ответ 403.

### Уроки

- Файлы лежат по схеме `content/<NN-slug-модуля>/<NN-slug-урока>.mdx`.
  - Во frontmatter обязательны `title` и `summary`.
  - У каждого модуля есть `_module.json` с полями `title` и `description`.
  - Порядок модулей и уроков задаёт префикс `NN-`.
- Slug урока: `<slug-модуля>/<slug-урока>` без числовых префиксов. Пример: `internet/dns`.
- Next.js читает `content/` при сборке и отрисовывает MDX на сервере. API об уроках ничего не знает.
- В ядре лежит один пример урока, «Как пользоваться devplus», для проверки отрисовки. Настоящий контент — подпроект 3.

### Прогресс

- На странице урока кнопка «Отметить пройденным». Повторное нажатие снимает отметку.
- На главной показана программа обучения: модули со счётчиком «пройдено X из Y» и список уроков с отметками.
- API проверяет только формат slug: `^[a-z0-9-]+/[a-z0-9-]+$`, не длиннее 200 символов.
  - Пометка в коде: `shortcut: если переименовать урок, прогресс по нему потеряется; ввести манифест уроков, если переименования станут частыми`.

### Страницы

- `/`: программа обучения с прогрессом.
- `/lessons/<module>/<lesson>`: урок.
- `/no-access`: для пользователей вне списка доступа.
- Шапка: логотип, аватар, кнопка «Выйти».
- Без сессии любая страница, кроме `/no-access`, перенаправляет на вход.

### Модель данных

```
users
  id          uuid PK
  github_id   bigint UNIQUE NOT NULL
  login       text NOT NULL
  name        text NULL
  avatar_url  text NULL
  created_at  timestamptz NOT NULL default now()

sessions
  token_hash  text PK               -- sha256 токена
  user_id     uuid FK → users ON DELETE CASCADE
  created_at  timestamptz NOT NULL default now()
  expires_at  timestamptz NOT NULL

lesson_progress
  user_id      uuid FK → users ON DELETE CASCADE
  lesson_slug  text NOT NULL
  completed_at timestamptz NOT NULL default now()
  PRIMARY KEY (user_id, lesson_slug)
```

Модули владеют таблицами так: `users` и `sessions` принадлежат `auth`, `lesson_progress` принадлежит `progress`. Модуль `progress` получает текущего пользователя через dishka из `auth`.

### API

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/auth/github/login` | 302 на GitHub |
| GET | `/api/auth/github/callback` | 302 на `/` или `/no-access` |
| POST | `/api/auth/logout` | 204 |
| GET | `/api/me` | `{id, login, name, avatar_url}` или 401 |
| GET | `/api/progress` | `{completed: [{lesson_slug, completed_at}]}` |
| PUT | `/api/progress/{module}/{lesson}` | 204, идемпотентно |
| DELETE | `/api/progress/{module}/{lesson}` | 204, идемпотентно |
| GET | `/api/health` | `{status: "ok"}`, проверяет соединение с БД |

### Не входит в ядро

Поиск, роли и админка, вход по email, Redis, отдельная работа над тёмной темой.

### Шаблон урока

1. **Зачем это знать.** 1–2 абзаца с реальной ситуацией из работы.
2. **Теория.** Текст и схемы. До появления доски схемы делаем в Mermaid или как картинки.
3. **Как спрашивают на интервью.** Типичные вопросы и сильный ответ на каждый в 2–3 предложения.
4. **Самопроверка.** Вопросы с ответами в `<details>`.
5. **Практика.** Задачи в инструменте платформы. Раздел появляется, когда готов нужный инструмент.
6. **Что почитать дальше.** 2–4 ссылки.

### Как пишем контент

На каждый модуль отдельный цикл:
1. Вместе составляем список уроков.
2. Пишем уроки по шаблону.
3. Когда готов инструмент, добавляем задачи.

## 5. Сквозные вопросы

### Ошибки

- Сервисы бросают доменные исключения (`NotFound`, `Forbidden`, `Unauthorized`, `Conflict`).
- Один обработчик в `core/errors.py` переводит их в HTTP-статус и ответ `{"detail": "..."}`. Это тот же формат, что у FastAPI.
- Ошибки валидации остаются стандартными 422.
- На непредвиденную ошибку пользователь получает 500 `{"detail": "Internal Server Error"}`. В лог пишется полный stack trace и `request_id`.
- **Web:** `error.tsx` и `not-found.tsx`. Если API ответил 401, перенаправляем на вход.

### Логи

- Стандартный `logging` пишет в stdout в формате JSON.
- Middleware проставляет каждому запросу `request_id` (берёт из заголовка `X-Request-ID` или генерирует) и возвращает его в ответе.

### Тесты (по TDD)

- **API.**
  - pytest и httpx `AsyncClient` против настоящего Postgres: в docker локально, отдельным контейнером-сервисом в CI.
  - Каждый тест работает в транзакции, которая в конце откатывается.
  - Клиент GitHub подменяется фейком через переопределение провайдера dishka.
- **Web.** Vitest для загрузчика уроков: обход `content/`, frontmatter, порядок, slug.
- **Smoke-тест на Playwright.** Сессия создаётся сразу в тестовой БД, cookie выставляется в браузер. Сценарий: главная → урок → «Отметить пройденным» → счётчик на главной вырос.
  - Обходного эндпоинта входа в приложении нет.
- **Контент.** Если какой-то MDX-файл сломан, падает `next build`.

### Конфигурация и секреты

- `pydantic-settings` читает переменные окружения.
- В git лежит только `.env.example`. Настоящий `.env` хранится на сервере и у разработчиков локально.
- Переменные ядра: `DATABASE_URL`, `GITHUB_CLIENT_ID`, `GITHUB_CLIENT_SECRET`, `ALLOWED_GITHUB_LOGINS`, `APP_ORIGIN`, `COOKIE_SECURE`.
- Два OAuth-приложения GitHub: локальное и продовое.

### Локальная разработка

- `make dev` поднимает Postgres через `docker-compose.dev.yml` и запускает `api` (uvicorn `--reload`) и `web` (`next dev`) напрямую на машине.
- В режиме разработки Next.js проксирует `/api/*` на `localhost:8000` через `rewrites`, поэтому origin остаётся один.

### CI в GitHub Actions, на каждый PR

- ruff, mypy, import-linter, pytest;
- ESLint, `tsc --noEmit`, Vitest, `next build`;
- `make gen-client && git diff --exit-code`;
- Playwright smoke-тест;
- Dependabot для pip, npm и GitHub Actions.

### CD, на пуш в `main`

1. Собираем образы `web` и `api` с тегом по SHA коммита и пушим в GHCR.
2. По SSH на VPS: `docker compose pull && docker compose up -d`.
3. Сервис `migrate` отрабатывает до старта `api` (через `depends_on: condition: service_completed_successfully`).
4. Откат: деплой предыдущего тега.

### Безопасность

- HTTPS и заголовки безопасности через Caddy (HSTS, `X-Content-Type-Options`, `Referrer-Policy`).
- Флаги cookie и проверка `Origin`, как описано в разделе 3.
- В БД не хранятся сами токены сессий, только их хэши.

## 8. Как ведём разработку

- **Процесс superpowers:** брейнсторм → спецификация → план (`writing-plans`) → реализация. Каждый подпроект и каждый модуль контента проходит этот цикл.
- **Режим ponytail:**
  - минимальное полное изменение, без кода «на будущее»;
  - известные ограничения помечаются комментарием `shortcut: <ограничение>, <когда менять>`;
  - валидация, безопасность и обработка ошибок не урезаются.
- **TDD** для любой нетривиальной логики.
- После каждого утверждённого шага обновляется `docs/roadmap.html`.

# Telegram Mini App

**Статус:** утверждена 2026-11-17 (решение пользователя в чате: «утверждаю»)

## Зачем

Команда должна заходить в devplus с телефона одним тапом из Telegram, без компьютера и без входа через GitHub при каждом открытии. Сайт уже открывается на телефоне в браузере. Mini App добавляет запуск из чата с ботом и вход без повторной авторизации.

Нативные HTML-виджеты Telegram (Bot API 10.4) не подходят: 4 КБ в сжатом виде, нет сети и ввода с клавиатуры, только личные чаты. Мы используем обычный Mini App, то есть наше веб-приложение в WebView Telegram.

## Цели и не цели

**Цели.** Открыть devplus из бота. Войти без GitHub после первой привязки. Не потерять прогресс и результаты квизов: они остаются у того же пользователя в `users`.

**Не цели.**
- Telegram как отдельный способ регистрации: пускаем по-прежнему только логины из allowlist GitHub.
- Уведомления, рассылки, обработка сообщений бота. Бот только держит кнопку меню, обработчика сообщений нет.
- Адаптация симулятора, code review и Лаборатории под телефон.
- Telegram Web (страница во фрейме): `shortcut: поддерживаем нативные клиенты iOS, Android, desktop; в Telegram Web SameSite=lax cookie может не сохраниться, менять, если команда пользуется Telegram Web.`

**Антицель.** Telegram-аккаунт, который заходит как отдельный пользователь без прогресса.

## Подходы к привязке

1. **Привязка через GitHub один раз (выбран).** Вход по `initData`; если `telegram_id` не привязан, Mini App открывает системный браузер, пользователь проходит GitHub OAuth, сервер записывает `telegram_id` существующему пользователю. Всё на телефоне, без новой инфраструктуры.
2. **Привязка кодом через бота.** Надёжно, но нужен обработчик сообщений бота (webhook или polling): новый процесс и новая поверхность атаки.
3. **Allowlist Telegram ID в env.** Проще всего, но создаёт отдельного пользователя без прогресса. Противоречит цели.

## Что делаем

### Данные

Alembic-миграция:
- `users.telegram_id` `BigInteger`, nullable, unique.
- Таблица `telegram_link_requests` `(token_hash PK, telegram_id BigInteger, first_name, username nullable, user_id FK users nullable, expires_at timestamptz)`. `first_name` и `username` берутся из подписанной `initData` при `link-start` и показываются на странице подтверждения. `user_id` пуст, пока GitHub-вход не пройден. Токен одноразовый и живёт 10 минут. В базе хранится только хэш (`hash_token`, как у сессий). Просроченные строки удаляем при создании новой: `shortcut: чистка при записи, вынести в фон, если таблица разрастётся.`

### API (модуль `auth`)

Остальные модули не затрагиваются. Ответ об ошибке везде `{"detail": "..."}`.

1. **`POST /api/auth/telegram`**, тело `{init_data: str}`. Проверка подписи:
   - `secret = HMAC_SHA256(key="WebAppData", msg=bot_token)`;
   - `data_check_string` из пар `key=value` без `hash`, по алфавиту, через `\n`;
   - сравнение через `secrets.compare_digest` (в байтах);
   - `auth_date` не старше 1 часа.

   Ответы: `200` и cookie `session` (те же параметры, что после GitHub); `401` подпись неверна или `initData` устарела; `404` `telegram_id` не привязан; `403` логин пользователя уже не в allowlist.
2. **`POST /api/auth/telegram/link-start`**, тело `{init_data}`. Проверка та же. Создаёт строку в `telegram_link_requests` (с `telegram_id`, `first_name`, `username` из `initData`) и возвращает `{url}`: `{APP_ORIGIN}/api/auth/telegram/link?token=<token>`. `401` при плохой подписи.
3. **`GET /api/auth/telegram/link?token=...`** открывается в системном браузере. Проверяет токен (есть, не просрочен), кладёт его в cookie `tg_link` (httponly, `path=/api/auth`, 10 минут) и запускает обычный GitHub OAuth (state-cookie и редирект как в `/auth/github/login`).
4. **`GET /api/auth/github/callback`** расширяется: если есть cookie `tg_link`, то после проверки state и allowlist сессия **не** создаётся и привязки ещё нет. Токен проверяется (есть, не просрочен, `user_id` пуст), в заявку записывается `user_id` пользователя, прошедшего GitHub (если пользователя нет, он создаётся, как при обычном входе), и браузер уходит на `/tg/confirm`.
5. **`GET /api/auth/telegram/link/pending`** (по cookie `tg_link`): возвращает `{telegram: {id, first_name, username}, login}`, то есть чей Telegram и к какому GitHub-аккаунту его привяжут. `404`, если заявки нет, она просрочена или `user_id` ещё пуст.
6. **`POST /api/auth/telegram/link/confirm`** (по cookie `tg_link`): единственное место, где привязка записывается.
   - токен проверяется ещё раз и **удаляется** (одноразовость), cookie `tg_link` сбрасывается;
   - `users.telegram_id` записывается пользователю из заявки;
   - если этот `telegram_id` уже у другого пользователя, `BadRequest`;
   - если у этого пользователя был другой `telegram_id`, он заменяется: владение GitHub-аккаунтом доказано;
   - ответ `204`, web переходит на `/tg/linked`.

   Кнопки «Отмена» нет на сервере: человек просто закрывает страницу, заявка истекает сама. `shortcut: отмена без запроса, добавить DELETE заявки, если понадобится.`

   Любая ошибка в ветке с `tg_link` (токена нет, просрочен или уже использован; логин вне allowlist) перехватывается в `GET /api/auth/telegram/link` и в callback: токен и cookie `tg_link` удаляются, редирект на `/tg/link-failed?reason=<код>`. Пользователь в системном браузере видит читаемый текст, а не JSON и не `/no-access` с обычной кнопкой GitHub. Ошибки `pending` и `confirm` (включая занятый `telegram_id`) страница `/tg/confirm` показывает на месте. *(Решение автора.)*

   Без `tg_link` поведение callback не меняется.

### Web (`apps/web`)

- **`/tg`**: клиентская страница вне авторизованных layout-групп. Подключает `telegram-web-app.js`, вызывает `ready()` и `expand()`, отправляет `initData` на `POST /api/auth/telegram`.
  - `200`: переход на `/`;
  - `404`: кнопка «Войти через GitHub». Она вызывает `link-start` и открывает `url` через `Telegram.WebApp.openLink`. Вход повторяется при событии `activated` (Bot API 8.0) и при `visibilitychange`, а также по кнопке «Я вошёл, продолжить» как запасному пути: Telegram может держать WebView живым в фоне, и события приходят не везде. *(Решение автора.)*
  - `403`: переход на `/no-access`;
  - `401`: текст «Открой приложение из Telegram».
- **`/tg/confirm`**: страница для системного браузера. Берёт `pending` и показывает «Привязать Telegram *Имя (@username, id N)* к аккаунту *login*?» с кнопкой «Привязать» (`confirm`, затем переход на `/tg/linked`) и пояснением «Если ты не запрашивал привязку, закрой страницу».
- **`/tg/linked`** и **`/tg/link-failed`**: статические страницы для системного браузера («Готово, вернись в Telegram» и читаемое сообщение по `reason`).
- **Сессия внутри Mini App.** `/tg` ставит cookie `miniapp=1` (не httponly, `path=/`, SameSite lax). Пока она есть, `redirectOnAuthError` (`lib/session.ts`) отправляет 401 на `/tg`, а не на GitHub-вход в самом WebView, и кнопка выхода скрыта: следующий запуск входит заново по `initData`. Это единственная правка вне `/tg` и модуля `auth`. *(Решение автора: иначе просроченная сессия открывала бы GitHub OAuth внутри WebView.)*
- **Телефонный вид.** Проверяем уроки, квизы и прогресс при ширине 390 px. Правим только то, что мешает читать урок или проходить квиз.

### Конфиг и деплой

- `TELEGRAM_BOT_TOKEN` в `Settings` с пустым значением по умолчанию и в `.env.example`. Пока он пуст, `/api/auth/telegram*` отвечают `404`, остальное приложение работает: существующие окружения (prod compose, CI, `make dev`, тесты) не ломаются. *(Решение автора: ревьюер указал, что обязательная переменная сломает все окружения до её установки.)*
- Бота создаёт пользователь в BotFather (`/newbot`), URL кнопки меню или Main Mini App: `{APP_ORIGIN}/tg`. Домен уже на HTTPS через Caddy.
- Описать шаги в `docs/deploy.md`.

## Безопасность

- Подпись `initData` проверяется на сервере, `initDataUnsafe` не используется.
- Привязка требует прохождения GitHub OAuth и allowlist: Telegram сам по себе доступа не даёт.
- Подтверждение закрывает подмену. `link-start` доступен любому пользователю бота, так что чужую ссылку привязки можно подсунуть коллеге. Поэтому после GitHub-входа привязка записывается только по явному `confirm`, а на странице видно, чей это Telegram. Остаточный риск: человек подтвердит, не прочитав. Для команды в 20 человек принимаем.
- Токен привязки одноразовый, хранится хэшем, живёт 10 минут.
- Токен бота нигде не логируется и не попадает в клиент.

## Не делаем

- Отвязка Telegram из интерфейса: `shortcut: отвязка вручную через SQL, делать, если понадобится.`
- Локальная проверка в самом Telegram: нужен HTTPS-туннель. Логика проверяется тестами с вычисленной подписью.
- Автоматический вход из Telegram Web.

## Проверка

- pytest: корректная `initData` и привязанный пользователь дают `200` и session cookie; изменённый `hash` даёт `401`; устаревшая `auth_date` даёт `401`; непривязанный даёт `404`; логин вне allowlist даёт `403`; `link-start` создаёт токен с именем и username; callback с `tg_link` записывает `user_id` в заявку, **не** привязывает `telegram_id` и не выдаёт сессию; `pending` возвращает имя Telegram и логин GitHub; `confirm` привязывает и удаляет заявку; без `confirm` привязки нет; токен одноразовый (повторный `confirm` даёт ошибку); просроченный токен даёт ошибку; `telegram_id`, занятый другим пользователем, даёт ошибку при `confirm`; обычный GitHub-вход без `tg_link` работает как раньше.
- pytest: при пустом `TELEGRAM_BOT_TOKEN` все `/api/auth/telegram*` отвечают `404`.
- `make migrate-check`, `make gen-client`, `make lint`, `make test`.
- Руками на телефоне: открыть бота, привязать, закрыть и открыть заново (вход без GitHub), пройти квиз и увидеть прежний прогресс.

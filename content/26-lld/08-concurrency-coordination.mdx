Узнай, как координировать работу между потоками.

🗓️ **Coordination** — это про то, как потоки общаются друг с другом и передают работу. Один поток производит задачи, другой их потребляет. Один сервис отправляет запрос, другой его обрабатывает. Как независимым путям выполнения подавать друг другу сигналы, не сжигая CPU и не портя состояние?

## Проблема

Представь, что ты строишь планировщик задач для веб-приложения. Часть работы просто не должна выполняться в пути запроса. Она занимает слишком много времени, и если запускать её синхронно, каждый вызов API окажется заблокирован.

Поэтому такую работу выносят в фон. Пользователи регистрируются, и им нужно отправить приветственные письма. Они загружают фото профиля, которые нужно ресайзить. Админы запрашивают ежемесячные отчёты, на генерацию которых уходят минуты. API-обработчики ставят задачи в очередь, а пул worker-потоков обрабатывает их асинхронно.

Концептуально архитектура проста: API-обработчики производят задачи, worker'ы их потребляют, а между ними находится что-то, что координирует передачу.

Coordination

При стабильной нагрузке это работает хорошо, но по краям начинают появляться трещины.

Для начала посмотрим, что происходит, когда worker'ы готовы работать, а работы нет. Самый наивный подход — просто проверять очередь снова и снова, пока что-нибудь не появится.

Busy-waiting (антипаттерн)

```
while True:
    if queue:
        task = queue.pop(0)
        execute(task)
```

Это busy-waiting, и последствия могут быть катастрофическими. Каждый worker крутится в плотном цикле, сжигая CPU и не делая ничего полезного. Если на восьмиядерной машине работают восемь worker'ов, ты можешь потратить 100% вычислительных ресурсов просто на проверку пустой очереди. Когда задачи наконец приходят, свободного CPU для их выполнения не остаётся.

Можно попробовать это исправить, добавив sleep, когда работы нет.

Sleep-polling (антипаттерн)

```
import time

while True:
    if queue:
        task = queue.pop(0)
        execute(task)
    else:
        time.sleep(0.1)
```

Это снижает нагрузку на CPU, но теперь ты променял расточительность на latency. Задача, которая пришла через 1 мс после того, как worker уснул, ждёт почти 100 мс до начала обработки. Спишь дольше — система кажется вялой. Спишь меньше — снова сжигаешь CPU.

Теперь перевернём проблему. Что будет, если producer'ы быстрее consumer'ов?

Допустим, ушла маркетинговая рассылка, и 50 000 пользователей одновременно кликнули по ссылке. Каждый запрос ставит в очередь фоновую работу.

```
09:00:00.000 - Queue size: 0
09:00:00.100 - Queue size: 5,000
09:00:00.200 - Queue size: 12,000
09:00:00.300 - Queue size: 23,000
09:00:00.400 - Queue size: 38,000
09:00:00.500 - Queue size: 50,000
```

Твои восемь worker'ов обрабатывают, скажем, около 100 задач в секунду, а значит, на разбор очереди из тысяч задач уйдут минуты. Но убивает тебя не сама задержка. Настоящая проблема — память. Каждая задача в очереди — это объект в heap, который занимает память. Если очередь не ограничена и продолжает принимать новые задачи, она растёт и растёт, пока в конце концов ты не получишь OutOfMemoryError. Тогда падает весь сервис. Не только фоновая обработка, а вообще всё. API ложится, и всё перестаёт работать.

Это проблема координации. Как потокам общаться и упорядочивать свою работу? Им нужно подавать друг другу сигналы («работа готова»), эффективно ждать, не сжигая CPU, и справляться со случаем, когда одна сторона быстрее другой. Нужно решить три задачи:

1. **Эффективное ожидание** — consumer'ы должны спать, когда работы нет, и просыпаться сразу, как только она появляется
2. **Backpressure** — producer'ы должны замедляться, когда consumer'ы не справляются, чтобы не исчерпать память
3. **Thread safety** — сам механизм координации должен корректно обрабатывать конкурентный доступ без порчи данных

## Решения

Есть два принципиально разных подхода к этим задачам. **Координация через shared state** использует структуры данных, к которым напрямую обращаются несколько потоков, например очередь, в которую producer'ы кладут задачи, а consumer'ы забирают. **Координация через message passing** вообще обходится без shared state. У каждого компонента есть свой inbox, и общаются компоненты, отправляя сообщения.

Рассмотрим оба.

### Координация через shared state

Самый распространённый подход к координации использует общие структуры данных. Потоки общаются, читая и записывая одну и ту же память. Producer добавляет элемент в очередь, consumer его забирает. Очередь — это shared state, а примитивы синхронизации, такие как locks и condition variables, следят за тем, чтобы потоки не мешали друг другу.

#### Wait/Notify (Condition Variables)

Wait/notify — низкоуровневый примитив координации потоков. Его полезно знать, но на собеседовании напрямую его вряд ли придётся использовать. Если хочешь «перейти к сути», можешь пропустить этот раздел и сразу перейти к [Blocking Queues](#blocking-queues).

Помнишь проблему с polling'ом из введения? Worker'ы, которые крутятся в цикле и проверяют, есть ли работа, сжигают CPU без всякой пользы. Нам нужно, чтобы worker'ы действительно спали, когда делать нечего, и просыпались в тот же миг, как появляется работа. Именно это дают condition variables.

Паттерн работает так. У тебя есть lock, защищающий какое-то shared state, и condition variable, привязанная к этому lock. Когда потоку нужно дождаться, пока некоторое условие станет истинным, он вызывает wait на condition variable. При этом атомарно происходят две вещи.

1. Поток освобождает lock и засыпает.
2. Поток полностью перестаёт потреблять CPU. Он припаркован, пока его явно не разбудят.

Когда другой поток меняет shared state, он сигнализирует condition variable, чтобы разбудить ждущие потоки. Прежде чем продолжить, эти потоки должны заново захватить lock. Как только поток получает lock обратно, он просыпается и продолжает выполнение.

Конкретный API зависит от языка. В Java это методы wait/notify на объекте lock. В C++ есть std::condition\_variable с методами wait/notify. В Python есть threading.Condition с wait/notify. Go использует каналы, которые полностью скрывают этот паттерн. Базовый механизм везде один и тот же.

Вот сам паттерн:

wait\_notify.py

```
with condition:
    while not condition_is_met():
        condition.wait()  # Releases lock, sleeps until notified
    do_work()
    condition.notify_all()  # Wakes all waiting threads
```

Python'овский threading.Condition объединяет lock и condition variable. Оператор with берёт на себя захват lock. wait() освобождает lock и засыпает. notify\_all() будит все ждущие потоки. Lock снова захватывается до того, как wait() вернёт управление.

Цикл while здесь обязателен. Когда поток просыпается из wait(), он должен перепроверить условие: пока его уведомляли и пока он заново захватывал lock, другой поток мог уже забрать то, чего он ждал. К тому же JVM может будить потоки спонтанно, без какого-либо вызова notify(), поэтому всегда нужно убеждаться, что условие по-прежнему выполняется.

Выигрыш по сравнению с polling'ом огромен. При polling'е на основе sleep worker'ы либо тратят CPU впустую (короткий sleep), либо дают высокую latency (длинный sleep). С wait/notify worker'ы не потребляют CPU, пока простаивают, и просыпаются сразу, как только появляется работа.

##### Сложности

Самое каверзное в condition variables — решить, будить один поток или все. Вот почему это важно.

Допустим, у тебя очередь, в которой и producer'ы, и consumer'ы ждут на одной и той же condition variable. Три producer'а заблокированы в ожидании места в очереди. Два consumer'а заблокированы в ожидании элементов. Consumer заканчивает обработку элемента и освобождает место. Он сигнализирует condition variable, чтобы разбудить один ждущий поток.

Какой поток проснётся? Runtime выбирает произвольно. Он может выбрать другого consumer'а, хотя consumer'ам нужны элементы, а не место. Этот consumer просыпается, видит, что очередь по-прежнему пуста, и снова засыпает. А producer'ы, которым действительно нужно узнать о свободном месте, продолжают спать, и никто не продвигается вперёд.

Безопасное решение — будить все потоки, а не один. Теперь, когда освобождается место, просыпаются все ждущие потоки. Consumer'ы видят, что очередь по-прежнему пуста, и снова засыпают. Producer'ы видят, что место есть, один из них его занимает, и работа продолжается.

Но у пробуждения всех потоков есть цена. Если ждут 50 потоков, а продолжить реально может только один, ты зря разбудил 49. Они все конкурируют за lock, проверяют условие, видят, что оно не выполнено, и снова засыпают. Это куча впустую потраченных context switch'ей.

Решение получше — использовать отдельные condition variables. Одну для «очередь не пуста», на которой ждут только consumer'ы. Другую для «очередь не заполнена», на которой ждут только producer'ы. Теперь, когда consumer освобождает место, он сигнализирует условие «not full» и будит только producer'ов. Когда producer добавляет элемент, он сигнализирует условие «not empty» и будит только consumer'ов, так что лишних пробуждений больше нет.

#### Blocking Queues

Wait/notify даёт строительные блоки для координации потоков, но реализовывать его с нуля приходится редко. В большинстве языков есть blocking queue, которая делает всю работу за тебя.

Blocking queue — это просто thread-safe очередь со специальным поведением, когда она пуста или заполнена. Если ты пытаешься забрать элемент из пустой очереди, вызов блокируется, а не возвращается сразу. Твой поток засыпает, используя под капотом condition variables. Когда другой поток добавляет элемент, он будит тебя, и ты получаешь этот элемент. То же самое в обратную сторону, когда очередь заполнена: попытка добавить элемент блокируется, пока не освободится место.

Это именно то, что нужно для задач producer-consumer. Producers вызывают put, чтобы добавить элементы. Consumers вызывают take, чтобы забрать их, а очередь берёт на себя всю синхронизацию, всё ожидание и все сигналы. Backpressure получается из коробки: producers блокируются, когда очередь заполнена. Эффективное ожидание тоже получается само собой: consumers спят, пока очередь пуста.

Blocking queues встречаются и в resource pooling (см. [статью Scarcity](/lessons/lld/concurrency-scarcity)), где в них лежат сами объекты ресурсов, а не задачи. Здесь мы смотрим на них как на канал связи между потоками, через который передаётся работа.

Вот task scheduler из введения, теперь с рабочим кодом:

task\_scheduler.py

```
import queue
from typing import Callable

class TaskScheduler:
    def __init__(self):
        self._queue = queue.Queue(maxsize=1000)

    def submit_task(self, task: Callable) -> None:
        self._queue.put(task)  # Blocks if queue is full

    def worker_loop(self) -> None:
        while True:
            task = self._queue.get()  # Blocks if queue is empty
            task()
```

Python's queue.Queue предоставляет блокирующие операции. put() блокируется, если очередь заполнена, get() блокируется, если она пуста. Ограничить размер очереди можно через maxsize. Вся синхронизация потоков происходит внутри очереди.

Блокирующая операция удаления блокируется, когда очередь пуста, а под капотом использует паттерн wait/notify. Очередь берёт всю синхронизацию на себя, поэтому несколько producers и consumers могут работать одновременно, не портя состояние.

В Python get() блокируется, пока очередь пуста, и возвращается, как только появляется элемент. Без аргументов он блокируется бесконечно, пока элемент не появится.

На интервью BlockingQueue — твой ответ по умолчанию для задач producer-consumer. «Я возьму blocking queue, чтобы consumers эффективно ждали, а синхронизацию взяла на себя очередь».

##### Сложности

Главная ошибка — создать неограниченную очередь. У LinkedBlockingQueue без аргумента capacity нет ограничения по размеру. Это возвращает проблему исчерпания памяти из введения. Всегда передавай capacity: new LinkedBlockingQueue&lt;>(1000).

Как выбрать capacity? Обычно размер буфера считают исходя из того, какой всплеск нагрузки нужно выдержать. Если твои workers обрабатывают 100 задач в секунду и ты хочешь поглотить 10-секундный всплеск трафика, не блокируя producers, нужен буфер на 1 000 задач. Если буфер слишком маленький, producers будут часто блокироваться, и это ударит по throughput. Если слишком большой, под нагрузкой снова будет избыточное потребление памяти.

Что происходит, когда очередь заполняется? Есть три варианта:

* **Блокировать producers** через put(). Подходит для внутренних pipeline, где замедление допустимо. Batch job, который кормит стадию обработки, может подождать.
* **Timeout и отказ** через offer(timeout). Подходит для request path, где останавливаться нельзя. Верни пользователю 503 или «попробуйте позже».
* **Отбросить и залогировать** через offer() (без timeout, сразу возвращает false). Подходит для нагрузок, где потери допустимы, например для analytics events: под нагрузкой их можно отбрасывать.

Ещё одна деталь, которую стоит понимать, — InterruptedException. И put(), и take() бросают это исключение, поэтому его нужно обработать. Оно возникает, когда другой поток прерывает твой поток, пока тот заблокирован в ожидании. Хуже всего — поймать его и проигнорировать. Тогда твой код проглатывает сигнал о том, что кто-то пытается остановить поток. Либо пробрасывай исключение выше, объявив его в сигнатуре метода, либо, если ловить всё-таки приходится, восстанови статус прерывания вызовом Thread.currentThread().interrupt(), чтобы код выше по стеку знал, что поток был прерван.

Graceful shutdown — ещё один частый follow-up на интервью. Твои workers сидят в take() и вечно ждут задач. Как их остановить при завершении приложения? Есть три варианта.

**1. Прервать (interrupt) потоки workers.** Когда ты прерываешь поток, заблокированный в take(), он просыпается и бросает InterruptedException. Worker ловит его, выходит из цикла и чисто завершается. Это самый простой подход.

**2. Использовать poll с timeout.** Вместо вечной блокировки в take() используй poll(timeout). Worker ждёт задачу не дольше заданного timeout. Если ничего не пришло, poll возвращает null. Это даёт возможность периодически проверять флаг остановки. Когда запрошена остановка, ты ставишь флаг, и workers заметят это не позже чем через один timeout и завершатся.

**3. Использовать паттерн poison pill.** Создай специальную sentinel-задачу, которая означает «завершайся». Когда запрошена остановка, отправь в очередь по одной poison pill на каждого worker. Каждый worker нормально обрабатывает задачи, пока не вытащит poison pill. Увидев её, он выходит из цикла и завершается. Это хорошо работает, когда потоки нельзя прерывать или не хочется использовать timeout.

### Координация через передачу сообщений

Есть принципиально другой взгляд на координацию. Вместо того чтобы несколько потоков обращались к общим структурам данных, представь, что у каждого потока есть собственное приватное состояние, а общаются они только отправкой сообщений.

Это actor model. Actor — независимая единица вычисления с тремя свойствами: у него есть mailbox (очередь входящих сообщений), он обрабатывает сообщения по одному и может отправлять сообщения другим actors. Никакого общего состояния. Никаких locks. Каждый actor внутри однопоточный, поэтому о конкурентном доступе внутри actor можно не беспокоиться.

Модель появилась в 1970-х, но практическое распространение получила с Erlang, вокруг которого построили целый язык и runtime. Сегодня реализации actors есть в Akka (Scala/Java), Orleans (.NET) и в библиотеках для большинства популярных языков. Goroutines с channels в Go сильно опираются на похожие идеи, хотя это не actors в строгом смысле.

#### Actor Model

Actor на удивление прост. Это просто объект с mailbox и обработчиком сообщений. Когда ты отправляешь actor сообщение, оно попадает в его mailbox. Actor достаёт сообщения из mailbox по одному и обрабатывает их. Поскольку одновременно обрабатывается только одно сообщение, внутреннее состояние actor никогда не сталкивается с конкурентным доступом.

actor\_example.py

```
import threading
import queue
from abc import ABC, abstractmethod

class Actor(ABC):
    def __init__(self):
        self.mailbox = queue.Queue()
        self.running = True
        self.thread = threading.Thread(target=self._run)
        self.thread.start()

    def _run(self):
        while self.running:
            try:
                message = self.mailbox.get(timeout=0.1)
                self.on_receive(message)
            except queue.Empty:
                continue

    def send(self, message):
        self.mailbox.put(message)

    @abstractmethod
    def on_receive(self, message):
        pass

    def stop(self):
        self.running = False
        self.thread.join()
```

Actor в Python использует queue.Queue как mailbox и работает в выделенном потоке. Timeout в get() позволяет потоку периодически проверять флаг running, чтобы чисто завершаться. В production часто используют библиотеки вроде Pykka или async-фреймворки.

Заметил, что в обработчике сообщений нет locks? Actor обрабатывает одно сообщение за раз, поэтому onReceive() никогда не выполняется конкурентно сам с собой. Любое состояние actor читается и меняется последовательно. Можно держать изменяемые поля, счётчики, cache, всё что угодно, без синхронизации внутри логики actor. Сам mailbox всё же требует синхронизации, когда несколько потоков отправляют сообщения одному actor: BlockingQueue использует locks внутри, чтобы справляться с конкурентными вызовами send().

Actors собирают всю синхронизацию в одной чётко определённой границе (mailbox) и выносят её из бизнес-логики. Ты меняешь россыпь locks по всему коду на одну проверенную реализацию очереди, которая отвечает за весь конкурентный доступ.

Сравни с координацией через shared state. С blocking queue несколько потоков-workers берут задачи из одной очереди и могут обрабатывать задачи, которые трогают одни и те же данные. Чтобы защитить эти общие данные, нужны locks или другая синхронизация. С actors каждый actor единолично владеет своими данными. Координация идёт через передачу сообщений, а не через общую память.

Вот email service из предыдущих примеров, переосмысленный через actors:

email\_actor.py

```
class EmailActor(Actor):
    def __init__(self):
        super().__init__()
        self.email_client = EmailClient()

    def on_receive(self, request):
        self.email_client.send(request.to, request.subject, request.body)

# Usage: no shared state, no locks needed
class SignupHandler:
    def __init__(self, user_repository):
        self.email_actor = EmailActor()
        self.user_repository = user_repository

    def handle_signup(self, request):
        user = self.user_repository.save(User(request.email))

        # Send message to actor - returns immediately
        self.email_actor.send(EmailRequest(
            to=user.email,
            subject="Welcome!",
            body="Thanks for signing up..."
        ))
```

Паттерн actor чётко отделяет request path от фоновой обработки. handle\_signup() возвращается сразу после отправки сообщения. Actor обрабатывает письма в своём темпе, изолированно от потока веб-запроса.

Структура похожа на версию с blocking queue, но ментальная модель другая. С blocking queues ты думаешь об общих данных и синхронизации. С actors ты думаешь о сообщениях и владении. Actor владеет email client. Больше никто его не трогает. Взаимодействие явное: всё происходит через send().

##### Когда использовать actors

Actors хороши, когда есть много независимых сущностей, которым время от времени нужно общаться. Представь чат, где каждая пользовательская сессия — это actor, игровой сервер, где actor — каждый игрок или игровая комната, или торговую систему, где actor — каждый order book. У каждой сущности своё состояние, она обрабатывает события последовательно и при необходимости отправляет сообщения другим сущностям.

Модель хорошо масштабируется. Поскольку actors не делят состояние, их можно распределить по машинам. Сообщение actor на другом сервере отправляется так же, как локальному. Erlang и Akka строят целые распределённые системы на этом свойстве.

Но actors подходят не всегда. Для простых задач producer-consumer, где нужно просто передать работу из одного потока в другой, blocking queue проще и прямолинейнее. Абстракция actors не нужна, когда хватает очереди. Actors добавляют концептуальную нагрузку: теперь приходится думать о типах сообщений, жизненном цикле actors и гарантиях доставки сообщений.

Практическое правило: если твоя задача звучит как «обработать эти задачи в фоне», используй blocking queue. Если задача звучит как «скоординировать множество независимых сущностей со своим состоянием», присмотрись к actors.

На собеседованиях blocking queue по-прежнему остаётся ответом по умолчанию для producer-consumer. Но если интервьюер спрашивает про альтернативные подходы или ты проектируешь систему с большим числом stateful-сущностей (игровые серверы, чаты, торговые платформы), actors стоит упомянуть. Скажи: «Другой подход — actor model, где каждая сущность обрабатывает свои сообщения последовательно. Это убирает shared state внутри каждого actor».

##### Сложности

Actor model меняет один набор проблем на другой. Тебе больше не нужно беспокоиться о locks и race conditions на shared state, но появляются новые заботы.

**Переполнение mailbox.** Как и blocking queues, mailbox у actors может переполниться, если producers быстрее, чем actor успевает обрабатывать. Большинство фреймворков позволяют настроить размер mailbox и поведение при переполнении: отбрасывать сообщения, блокировать отправителей или применять backpressure.

**Порядок сообщений.** Сообщения от actor A к actor B приходят по порядку. Но если и A, и C отправляют сообщения в B, порядок их чередования не определён. Если твоя логика зависит от глобального порядка между отправителями, с actors всё усложняется.

**Отладка.** Когда в системе из actors что-то идёт не так, баг может быть в том, как текут сообщения, а не в каком-то одном фрагменте кода. Проследить запрос через несколько actors сложнее, чем пройтись по одному call stack.

**Паттерны request-response.** Actors общаются асинхронно. Если нужно отправить сообщение и дождаться ответа, этот паттерн придётся построить самому: отправить сообщение с callback-адресом, а затем ждать ответное сообщение. Некоторые фреймворки предоставляют паттерны «ask», которые скрывают эту сложность.

## Типовые задачи

Producer-consumer на собеседованиях появляется не как абстрактная задача про структуру данных. Он приходит в виде практических систем, где часть работы нужно выполнять асинхронно. Когда научишься узнавать такие задачи, ты поймёшь, когда браться за blocking queue или actor.

### Асинхронная обработка запросов

Это самый частый паттерн координации на собеседованиях. Пользователи делают запросы, которые требуют работы, но часть этой работы медленная и не обязана выполняться в рамках запроса. Ты хочешь ответить пользователю сразу, а тяжёлую работу сделать в фоне.

API handler — это producer. Он получает запрос, делает минимум работы, нужной для ответа пользователю, а затем передаёт задачу на фоновую обработку. Workers или actors — это consumers. Они обрабатывают задачи асинхронно.

Возьмём email-сервис. Когда пользователь регистрируется, нужно отправить ему приветственное письмо. Подключение к почтовому серверу и отправка сообщения занимают 500ms. Если делать это синхронно, каждый запрос на регистрацию будет отвечать полсекунды. Пользователь видит спиннер и гадает, не сломалось ли что-то. Вместо этого ты передаёшь задачу отправки письма и отвечаешь сразу. Отправкой занимается фоновая обработка.

С blocking queue:

email\_service.py

```
import queue
from dataclasses import dataclass

@dataclass
class EmailTask:
    recipient: str
    template: str
    data: str

class EmailService:
    def __init__(self):
        self._email_queue = queue.Queue(maxsize=10000)

    # API handler (producer)
    def signup(self, email: str, name: str) -> None:
        # Fast: Save user to database
        user_repository.save(email, name)

        # Fast: Enqueue background work
        self._email_queue.put(EmailTask(email, "welcome", name))

        # Return immediately - user sees instant response

    # Worker thread (consumer)
    def email_worker(self) -> None:
        while True:
            task = self._email_queue.get()
            # Slow: Connect to email server and send
            email_client.send(task.recipient, task.template, task.data)
```

`queue.Queue` в Python берёт на себя все детали работы с потоками. `put()` блокируется, если очередь полна, `get()` блокируется, если она пуста. Для веб-фреймворков workers обычно запускают в отдельных потоках или используют асинхронную очередь задач вроде Celery для production-нагрузок.

Теперь handler регистрации быстрый. Он сохраняет пользователя в базу, создаёт объект задачи на отправку письма, кладёт его в очередь и возвращает успех. Всё это занимает миллисекунды. Пользователь сразу видит сообщение об успехе и не ждёт, пока письмо реально отправится.

Тем временем твои worker-потоки в фоне забирают задачи из очереди. Один из них берёт задачу с письмом и вызывает email-сервис, чтобы реально его отправить. Если email-сервис медленный, не страшно. Этот worker заблокируется, но API handler давно закончил работу. Если email-сервис вообще недоступен, задача просто остаётся в очереди, пока worker не сможет её обработать или пока ты не реализуешь retry-логику. Пользователь ничего из этого не видит. Он уже получил свой ответ об успехе.

#### Примеры

Та же структура встречается во многих задачах на собеседованиях.

**Image Upload Service**: Пользователи загружают фото профиля. Фото нужно ресайзить, сжимать и загружать в S3. Это занимает секунды. Upload API сохраняет оригинал во временное место, ставит в очередь задачу на обработку и сразу возвращает успех. Workers забирают задачи, ресайзят изображения, загружают их в S3 и обновляют базу новыми URL.

**Payment Processing**: Пользователь завершает checkout. Нужно списать деньги с карты, отправить чек на email, обновить inventory и создать shipping label. Эти операции задействуют внешние сервисы, которые медленные или могут падать. Сохрани заказ, поставь в очередь задачу на выполнение заказа, ответь пользователю. Многошаговым процессом занимаются workers. Один сбой не блокирует весь поток.

**Report Generation**: Админ запрашивает ежемесячный отчёт на миллионы строк. Генерация занимает 10 минут. HTTP-запрос падает по таймауту через 30 секунд. Сохрани запись отчёта со статусом «pending», поставь в очередь задачу на генерацию и верни «Ваш отчёт генерируется». Workers забирают задачи, выполняют запрос, генерируют CSV, загружают его в S3 и помечают отчёт готовым. Админ делает polling или получает уведомление, когда отчёт готов.

Когда видишь «обработать это после завершения запроса» или «это слишком долго делать синхронно», берись за координацию. Скажи: «Я использую blocking queue, чтобы развязать API и фоновую работу. Handler ставит задачи в очередь и сразу возвращает ответ. Workers обрабатывают их асинхронно».

### Обработка всплесков трафика

Всплески трафика — это когда нагрузка приходит волнами, а не равномерно. Новостной сайт получает пик, когда выходит срочная новость. Интернет-магазин видит наплыв в Black Friday. Сервис продажи билетов выдерживает шквал запросов, когда в продажу поступают билеты на концерт. Большую часть времени твоя система спокойно справляется со 100 запросами в секунду, но иногда на несколько минут получает 10 000 запросов в секунду.

Наивный подход — масштабировать workers под пиковую нагрузку. Если пик составляет 10 000 запросов в секунду, а каждый worker обрабатывает 10 в секунду, нужно 1 000 workers. Но эти workers простаивают 99% времени, и ты тратишь деньги на серверы, которые тебе не нужны.

Координация решает это с помощью буфера. Ты рассчитываешь workers под обычную нагрузку, скажем, 100 workers. Когда приходит всплеск, очередь поглощает пик. Запросы накапливаются в очереди, пока workers перерабатывают их в обычном темпе. После окончания всплеска workers вычищают очередь, и всё возвращается в норму. Ты сгладил 100-кратный пик до равномерной обработки с ограниченной очередью.

Вот как это выглядит:

ticket\_service.py

```
import queue
from dataclasses import dataclass

@dataclass
class PurchaseRequest:
    user_id: str
    event_id: str
    quantity: int

class TicketService:
    def __init__(self):
        # Sized for 10-second burst at 10,000 req/s
        self._purchase_queue = queue.Queue(maxsize=100000)

    # API handler (producer) - handles bursts
    def purchase_ticket(self, user_id: str, event_id: str, quantity: int) -> None:
        request = PurchaseRequest(user_id, event_id, quantity)

        # Enqueue request - returns immediately even during spike
        try:
            self._purchase_queue.put(request, timeout=0.1)
        except queue.Full:
            raise ServiceUnavailableException("Too many requests, try again")

    # Worker pool sized for normal load (100 workers)
    def purchase_worker(self) -> None:
        while True:
            request = self._purchase_queue.get()
            # Process at normal rate - database, payment, inventory
            process_purchase(request)
```

`put(request, timeout=0.1)` выбрасывает `queue.Full`, если в очереди не появилось места за время timeout. Это даёт backpressure без бесконечной блокировки запроса. Исключение можно поймать и превратить в HTTP 503.

При обычной нагрузке очередь почти пуста. Запросы проходят сразу. Во время всплеска очередь заполняется, но не переполняется. Workers продолжают обработку в своём устойчивом темпе. Пользователям, возможно, придётся подождать подтверждения лишние пару секунд, но их обслужат. Без очереди пик перегрузил бы твою базу и обрушил сервис.

#### Примеры

Всплески трафика возникают всегда, когда нагрузка непредсказуема или зависит от событий.

**News Site**: Большую часть времени сайт видит 1 000 просмотров страниц в минуту. Выходит срочная новость, и за минуту приходит 100 000 просмотров. Веб-серверы ставят события просмотров в очередь. Analytics workers обрабатывают их с постоянной скоростью. Очередь поглощает пик. Без неё твоя analytics-база будет раздавлена, и весь сайт замедлится.

**Email Campaign**: Компания рассылает маркетинговое письмо 1 миллиону подписчиков. В течение нескольких минут 200 000 пользователей переходят по ссылке. Каждый клик запускает работу на бэкенде: логирование события, персонализацию контента, отслеживание конверсий. API ставит события кликов в очередь. Workers обрабатывают их равномерно. Очередь не даёт пику обрушить систему трекинга.

**Batch Job Completion**: Ночной ETL-джоб заканчивает обработку 10 миллионов записей. Для каждой нужно отправить уведомление о завершении. Отправка 10 миллионов уведомлений разом перегрузила бы твой сервис уведомлений. Вместо этого ставишь в очередь все 10 миллионов. Workers отправляют уведомления с контролируемой скоростью. Внешний сервис никогда не видит пика.

**Webhooks**: Ты получаешь webhook-события от платёжного провайдера. Обычно это 100 в минуту. Во время flash sale приходит 10 000 за минуту. Твой webhook handler ставит события в очередь. Workers их обрабатывают: обновляют заказы, отправляют чеки, запускают выполнение заказов. Очередь не даёт всплеску исчерпать connection pool к базе.

Когда видишь «трафик непредсказуем» или «нагрузка приходит всплесками», берись за координацию. Скажи: «Я использую blocking queue, чтобы буферизовать запросы во время всплесков. Workers обрабатывают с постоянной скоростью, а очередь сглаживает пик. Размер очереди я подберу исходя из ожидаемой длительности всплеска и пиковой скорости».

## Итоги

Coordination — это то, как потоки общаются и передают друг другу работу. Две парадигмы решают эту задачу по-разному.

**Coordination через shared state** использует структуры данных, к которым обращаются сразу несколько потоков, и главная рабочая лошадка здесь — blocking queue. Producers кладут задачи, consumers забирают их, а синхронизацию берёт на себя очередь. На интервью это правильный выбор по умолчанию для задач producer-consumer.

**Coordination через message passing** полностью обходится без shared state. Actors владеют своими данными и общаются через сообщения. Каждый actor обрабатывает сообщения последовательно, поэтому внутри actor блокировки не нужны. Такой подход хорошо подходит для систем с множеством независимых сущностей, у каждой из которых есть своё состояние.

Когда на интервью ты видишь асинхронную обработку, пройдись по такому дереву решений:

Coordination Decision Tree

В большинстве задач на интервью ответ — bounded `BlockingQueue` с `put()` для producers и `take()` для consumers. Если интервьюер спросит, как ты будешь справляться с переполнением очереди, объясни, что размер нужно выбирать исходя из ожидаемой длительности всплеска: если workers обрабатывают 100 задач в секунду и ты хочешь пережить 10-секундный spike, тебе нужна ёмкость на 1 000 задач. Если producer работает на пути обработки запроса, где блокировка недопустима, используй `offer(timeout)` и возвращай вызывающей стороне ошибку, когда очередь заполнена.

Если интервьюер спросит про альтернативы или в задаче много независимых сущностей со своим состоянием, упомяни actors. Главная идея в том, что actors по своему устройству исключают shared state: каждый actor единолично владеет своими данными и обрабатывает сообщения последовательно.

Паттерн всегда один и тот же: producers создают работу, consumers её обрабатывают, а что-то координирует передачу. Когда ты узнаёшь такую структуру в задаче на интервью — фоновая отправка писем, обработка изображений, analytics pipelines, сглаживание нагрузки при bursty-трафике, — бери blocking queue и worker pool. Для систем с множеством stateful-сущностей, которым нужно общаться между собой, подумай, не упростят ли дизайн actors.

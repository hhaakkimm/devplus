Узнай самые важные концепции для собеседований по system design, собранные менеджерами и staff-инженерами из FAANG.

Обновлено 16 февраля 2026

Core concepts — это фундаментальные принципы и техники, на которых строится любое собеседование по system design. В отличие от конкретных технологий (Redis, Kafka) или паттернов под отдельные задачи, это технологически нейтральные строительные блоки, которые встречаются почти в каждой задаче на проектирование.

Думай о core concepts как о словаре и грамматике system design. Прежде чем обсуждать, как масштабировать Instagram или спроектировать сервис вызова такси, нужно понимать, что такое caching, когда делать shard базы данных и как на самом деле работают сети. Интервьюеры считают, что ты это знаешь, и будут проверять твоё понимание, когда ты предлагаешь это использовать.

![Иллюстрация](/content/in-a-hurry--core-concepts/47ad0a514f.svg)

Overall Structure

На этой странице — краткий обзор каждой core concept: ровно столько контекста, чтобы понять, что это такое, почему это важно и когда к этому стоит обращаться. Каждый раздел ведёт на более подробную статью, где разобраны все детали, типичные ошибки и советы именно для собеседований. Если мало времени, этого обзора хватит для рабочего понимания. Если ты всерьёз хочешь освоить system design, читай полные статьи.

## [Networking Essentials](/lessons/core-concepts/networking-essentials)

Сети — одна из тем, в которую можно погружаться бесконечно глубоко, но для собеседований по system design нужно знать практические вещи, которые всплывают при проектировании распределённых систем. На базовом уровне нужно понимать, как сервисы общаются друг с другом и что происходит, когда эти соединения обрываются или тормозят.

Самое важное решение — выбор протокола для коммуникации. В большинстве систем ты по умолчанию возьмёшь HTTP поверх TCP. Он хорошо изучен, работает везде и покрывает 90% сценариев. Интервьюер будет ожидать именно этого, если у тебя нет конкретной причины выбрать что-то другое.

![Иллюстрация](/content/in-a-hurry--core-concepts/3c8a66c19b.svg)

Networking Layers

WebSockets и Server-Sent Events (SSE) нужны, когда требуются обновления в реальном времени. Главное отличие: SSE однонаправленный — клиент делает начальный HTTP-запрос, чтобы открыть соединение, а затем сервер отправляет данные по этому соединению (например, live-счёт матча или уведомления). Клиент не может отправлять дополнительные данные по тому же SSE-соединению. WebSockets обеспечивают настоящую двустороннюю коммуникацию, где обе стороны свободно отправляют сообщения (например, чат или совместное редактирование). SSE проще в реализации и лучше работает со стандартной HTTP-инфраструктурой, но WebSockets необходимы, когда клиентам нужно часто отправлять данные обратно на сервер. Подробнее о разных подходах читай в нашем руководстве по паттерну [Realtime Updates](/lessons/patterns/realtime-updates).

Оба варианта — это stateful-соединения, а значит, просто поставить их за обычный load balancer нельзя. Придётся подумать о persistence соединений и о том, что произойдёт, если упадёт сервер с тысячами активных соединений.

gRPC стоит упомянуть для внутреннего взаимодействия между сервисами, когда критична производительность. Он использует бинарную сериализацию и HTTP/2, поэтому заметно быстрее, чем JSON поверх HTTP. Но для публичных API его не используют, потому что браузеры не поддерживают gRPC нативно (gRPC-Web существует как обходной путь, но требует proxy и не поддерживает все возможности gRPC). Типичный паттерн — REST для внешних API и gRPC внутри.

Load balancing — ещё одна область, которую интервьюеры любят разбирать. Load balancer уровня 7 (Layer 7) работает на уровне приложения и может маршрутизировать запросы по реальному содержимому HTTP-запроса. Можно отправлять вызовы API в один сервис, а запросы веб-страниц — в другой. Load balancer уровня 4 (Layer 4) работает на уровне TCP, он быстрее, но «глупее»: просто распределяет соединения, не заглядывая в содержимое. Для WebSockets обычно нужна балансировка на Layer 4, потому что поддерживается постоянное TCP-соединение.

Частая ошибка — предлагать WebSockets там, где отлично подошли бы HTTP с long polling или Server-Sent Events. WebSockets сильно усложняют поддержку stateful-соединений в масштабе. Обращайся к ним, только когда нужна двусторонняя коммуникация в реальном времени, а не просто потому, что в условии задачи упомянут «real-time».

География и latency важнее, чем думают многие кандидаты. Запрос из Нью-Йорка в Лондон имеет минимальную latency около 80 мс только из-за скорости света в оптоволокне — ещё до какой-либо обработки. Если системе нужна низкая latency по всему миру, понадобятся региональные деплойменты с данными, реплицированными или разбитыми на partition по географии. Именно поэтому существуют CDN — они отдают статический контент с edge-серверов рядом с пользователями.

Все подробности читай в нашем руководстве [Networking Essentials](/lessons/core-concepts/networking-essentials).

## [API Design](/lessons/core-concepts/api-design)

Почти в каждом интервью по system design тебе нужно будет набросать API, через которые клиенты взаимодействуют с твоей системой. Хорошая новость: большинству интервьюеров не нужен идеальный дизайн API. Они хотят увидеть, что ты можешь придумать разумные endpoints и перейти к более сложным архитектурным задачам. При этом небрежный дизайн API может выдать недостаток опыта, так что базу знать стоит.

В 90% интервью по умолчанию используй REST. Он сопоставляет ресурсы с URL и использует HTTP-методы для работы с ними. Например, /users/\{id\} для получения пользователя, POST /events/\{id\}/bookings для создания бронирования. REST хорошо известен, работает везде, и интервьюер будет считать, что ты используешь именно его, если не предложишь что-то другое.

Частая ошибка — тратить слишком много времени на дизайн API в интервью. Ты должен уметь набросать 4-5 ключевых endpoints за пару минут и двигаться дальше. Если ты всё ещё прорабатываешь детали API на десятой минуте интервью, ты копаешь слишком глубоко.

Есть несколько концепций, которые стоит упомянуть, когда они к месту. Если ты возвращаешь большие наборы результатов, понадобится pagination. Cursor-based лучше подходит для данных в реальном времени, где новые элементы добавляются часто, но для большинства случаев хватит и offset-based. Для аутентификации используй JWT-токены для пользовательских сессий и API-ключи для вызовов между сервисами. А если твою систему могут завалить боты или злоупотребления, упомяни rate limiting. Но не углубляйся ни в одну из этих тем, если только интервьюер прямо не попросит.

Прочитай наш полный разбор [API Design](/lessons/core-concepts/api-design), ориентированный на интервью.

## [Data Modeling](/lessons/core-concepts/data-modeling)

Data modeling — одна из тех вещей, которые кажутся простыми, но сильно влияют на всю систему. Решения о том, какие данные хранить и как их структурировать, напрямую влияют на производительность, масштабируемость и на то, насколько больно будет строить и поддерживать систему.

![Иллюстрация](/content/in-a-hurry--core-concepts/ef31fec05b.svg)

Data Modeling

Первый большой выбор — relational или NoSQL. Реляционные базы вроде Postgres отлично подходят, когда у тебя структурированные данные с чёткими связями и нужна строгая консистентность. Например, аккаунты пользователей связаны с заказами, а заказы с товарами. Ты можешь выражать сложные запросы на SQL, использовать транзакции для сохранения консистентности данных и задавать ограничения внешних ключей. NoSQL-базы вроде DynamoDB или MongoDB выигрывают, когда нужны гибкие схемы (структура данных часто меняется) или нужно горизонтально масштабироваться на множество серверов без сложных join.

Внутри реляционных баз ты услышишь про нормализацию и денормализацию. Нормализация означает разбиение данных по таблицам, чтобы избежать дублирования. У тебя есть таблица users, таблица orders и таблица products. Каждый заказ ссылается на ID пользователя и ID товара вместо того, чтобы копировать полные данные пользователя и товара в каждую запись заказа. Так данные остаются консистентными (обнови название товара один раз, и оно обновится везде), но для получения полных данных нужны join. Join становятся дорогими, когда таблицы огромные или ты соединяешь сразу несколько таблиц.

Денормализация идёт в обратную сторону. Ты дублируешь данные, чтобы избежать join и ускорить чтение. Вместо того чтобы каждый раз делать join с таблицей users при показе заказа, ты сохраняешь имя пользователя прямо в каждой записи заказа. Теперь можно получить заказ и показать его, не обращаясь к другой таблице. Минус — обновления. Если пользователь меняет имя, его нужно обновить в таблице users и в каждой записи заказа, куда оно было скопировано. Для систем с преобладанием чтения, где данные редко меняются, этот компромисс часто оправдан.

В интервью безопасный вариант по умолчанию — начать с нормализованной реляционной модели, а затем денормализовать конкретные hot paths, если обнаружишь проблемы с производительностью чтения. Не предлагай денормализацию сразу, если у тебя нет чёткой причины. Интервьюеры хотят увидеть, что ты понимаешь компромиссы, а не слепо применяешь техники.

NoSQL-базы заставляют думать иначе. В DynamoDB нужно проектировать partition key и sort key исходя из паттернов доступа. Если ты строишь приложение для соцсети и самый частый запрос — «получить все посты пользователя X», ты используешь user\_id как partition key. Тогда этот запрос становится быстрым обращением к одной partition. Но запросы вроде «получить все посты с хэштегом Y» потребуют сканирования всей таблицы, потому что ты не проектировал под этот паттерн доступа. Запросы нужно знать заранее и проектировать вокруг них.

Подробнее читай в нашей статье [Data Modeling](/lessons/core-concepts/data-modeling).

## [Индексы в базах данных](/lessons/core-concepts/db-indexing)

Индексы нужны, чтобы запросы к базе выполнялись быстро. Без индекса поиск пользователя по email означает сканирование каждой строки в таблице users. Если у тебя 10 миллионов пользователей, придётся проверить 10 миллионов строк. С индексом по колонке email база может сразу перейти к нужной строке за миллисекунды.

Самый распространённый индекс — B-tree. Он хранит данные отсортированными в древовидной структуре, которая поддерживает и точный поиск (найти пользователя с email X), и range-запросы (найти все заказы между датой A и датой B). Большинство реляционных баз данных по умолчанию создают именно B-tree индексы. Hash-индексы быстрее для точных совпадений, но не умеют range-запросы, поэтому встречаются реже. Также бывают специализированные индексы: full-text индексы для поиска (найти документы с определёнными словами) и геопространственные индексы для запросов по местоположению (найти рестораны в радиусе 5 миль).

![Иллюстрация](/content/in-a-hurry--core-concepts/9817afc772.svg)

Индексы в базах данных

На интервью думай о своих паттернах запросов и предлагай индексы по полям, к которым часто обращаешься. Если ты ищешь пользователей по email для аутентификации, проиндексируй колонку email. Если достаёшь заказы пользователя, проиндексируй колонку `user\_id` в таблице заказов. Для составных запросов вроде «найти события в Сан-Франциско 25 декабря» может понадобиться compound-индекс сразу по city и date.

Когда нужно больше, чем поддерживает основная база, понадобятся внешние системы. Elasticsearch — стандартный выбор для full-text поиска (например, поиск по твитам или документам). Для геопространственных запросов в Postgres популярно расширение PostGIS. Такие внешние индексы обычно синхронизируются с основной базой через change data capture (CDC), а значит, поисковый индекс слегка отстаёт от основной базы. Данные, которые ты читаешь из поискового индекса, будут немного устаревшими, но для задач поиска это почти всегда приемлемо. Компромисс того стоит: он позволяет искать так, как основная база не умеет.

Подробный разбор читай в нашем руководстве [Database Indexing](/lessons/core-concepts/db-indexing).

## [Кеширование](/lessons/core-concepts/caching)

Кеширование всплывает почти в каждом интервью по system design, обычно когда ты замечаешь, что базу заваливает запросами на чтение. Идея простая: хранить часто запрашиваемые данные в быстрой памяти (например, в Redis), чтобы для большинства чтений вообще не обращаться к базе.

Разница в производительности огромная. Cache hit в Redis занимает около 1 мс против 20–50 мс для типичного запроса к базе. Когда ты обслуживаешь миллионы запросов, ускорение в 20–50 раз имеет значение. Ты также снижаешь нагрузку на базу, позволяя ей обрабатывать больше записи и не масштабируя её раньше времени.

![Иллюстрация](/content/in-a-hurry--core-concepts/e04105f25b.svg)

Внешнее кеширование

Паттерн, который ты будешь использовать в 90% случаев, — cache-aside с Redis. При чтении сначала проверяй cache. Если данные там есть, возвращай их. Если нет, делай запрос к базе, сохраняй результат в cache с TTL и возвращай его. Это просто реализовать, и подход работает для большинства систем с преобладанием чтения.

Но кеширование вносит настоящую сложность. Труднее всего инвалидация. Когда пользователь обновляет профиль в базе, нужно удалить или обновить закешированную копию. Иначе следующее чтение вернёт устаревшие данные. Стратегий несколько. Можно инвалидировать запись в cache сразу после записи, использовать короткие TTL и мириться с некоторой устарелостью или скомбинировать оба способа. Правильный выбор зависит от того, насколько свежими должны быть данные.

Нужно также думать о cache stampede. Когда популярная запись в cache истекает, множество параллельных запросов одновременно получают промах и набрасываются на базу, чтобы её пересоздать. Такой thundering herd может резко поднять нагрузку на базу и положить всю систему. Предотвратить это можно блокировкой (только один запрос пересоздаёт запись, остальные ждут), досрочным пересчётом (обновлять записи до истечения срока) или разнесением TTL, чтобы записи не истекали одновременно. Связанная, но отдельная проблема — полный отказ cache. Если Redis падает целиком, каждый запрос идёт в базу. Защита здесь включает небольшой fallback cache внутри процесса, circuit breaker для сброса нагрузки или плавную деградацию, пока Redis не восстановится.

Частая ошибка — кешировать всё подряд. Кешируй только данные, которые часто читаются и редко меняются. Если ты кешируешь данные, меняющиеся при каждом запросе, ты просто добавляешь latency и сложность без всякой пользы. Сначала профилируй систему, потом кешируй горячие пути.

CDN-кеширование — это другое. Оно предназначено для статических ресурсов вроде изображений, видео и JavaScript-файлов, которые отдаются с edge-локаций рядом с пользователями. In-process кеширование подходит для небольших значений, которые редко меняются, например feature flags или конфигурации. Но для основных данных приложения по умолчанию используется внешний cache на Redis.

Узнай больше в нашей статье [Caching](/lessons/core-concepts/caching) или посмотри, как кеширование вписывается в паттерн [Scaling Reads](/lessons/patterns/scaling-reads).

## [Sharding](/lessons/core-concepts/sharding)

Sharding появляется в разговоре, когда ты перерос одну базу данных и тебе нужно разложить данные по нескольким независимым серверам. Это происходит, когда ты упираешься в лимиты по хранилищу (один инстанс Postgres упирается в потолок на уровне TB), по write throughput (десятки тысяч записей в секунду) или по read throughput, с которым не справляются даже replica.

![Иллюстрация](/content/in-a-hurry--core-concepts/ab7e865c7d.svg)

Sharding

Самое важное решение — выбор shard key. Он определяет, как данные распределяются, и влияет на всё остальное в твоём дизайне. Для приложения, ориентированного на пользователя, вроде Instagram, шардирование по `user_id` означает, что все посты, лайки и комментарии пользователя лежат на одном shard. Запросы в рамках одного пользователя работают быстро, потому что обращаются только к одному shard. Зато глобальные запросы вроде «трендовые посты среди всех пользователей» становятся дорогими: нужно обратиться к каждому shard и агрегировать результаты. Это и есть компромисс.

Большинство систем используют hash-based sharding: ты хешируешь shard key и берёшь остаток от деления (modulo), чтобы выбрать shard. Так данные распределяются равномерно и не возникает hot spots. Range-based sharding может подойти, если паттерны доступа естественным образом делятся на части (например, в multi-tenant SaaS, где каждая компания запрашивает только свои данные), но тут легко получить hot spots, если один диапазон получает больше трафика. Directory-based sharding использует lookup table, чтобы решать, где лежат данные. Это гибко, но добавляет зависимость и latency к каждому запросу, поэтому на интервью это редко оправдано.

Самая большая ошибка с sharding — делать его слишком рано. Хорошо настроенная одиночная база с read replica выдержит намного больше, чем думает большинство кандидатов. Прежде чем предлагать sharding, посчитай ёмкость. Если у тебя 10K записей в секунду и 100GB данных, sharding тебе пока не нужен. Поднимай эту тему, когда цифры это оправдывают, а не как стратегию масштабирования по умолчанию.

Sharding создаёт новые проблемы, которые нужно учитывать. Cross-shard транзакции становятся почти невозможными, поэтому границы shard нужно проектировать так, чтобы их избегать. Если перевод между пользователями в твоём банковском приложении требует обновить счета на разных shard, понадобятся распределённые транзакции или saga, а они сложные и медленные. Hot spots возникают, когда один shard получает несоразмерно много трафика (представь, что на shard Тейлор Свифт обрушивается шквал запросов, пока остальные простаивают). А resharding — это больно: нельзя просто добавить новый shard, не перемещая огромные объёмы данных.

На интервью упоминай sharding после того, как обосновал, почему одной базы не хватит. Затем чётко назови выбранный shard key и объясни компромисс (быстро для запросов X, медленно для запросов Y). Большинству интервьюеров этого достаточно.

Полный разбор смотри в нашем руководстве по [Sharding](/lessons/core-concepts/sharding), а о том, как sharding вписывается в паттерн, читай в [Scaling Writes](/lessons/patterns/scaling-writes).

## [Consistent Hashing](/lessons/core-concepts/consistent-hashing)

Consistent hashing решает конкретную проблему, которая возникает в распределённых cache и шардированных базах данных. Когда ты используешь простое hash-распределение (`hash(key) % N`, чтобы выбрать сервер, на котором хранятся данные), добавление или удаление сервера меняет N. Это значит, что почти каждый ключ теперь попадает на другой сервер, и большую часть данных придётся перемещать. При миллионах записей в cache или в базе это катастрофа.

Consistent hashing решает проблему, располагая и серверы, и ключи на виртуальном кольце. Ты хешируешь каждый ключ и помещаешь его на кольцо, после чего ключ принадлежит следующему серверу, который встретится при движении по часовой стрелке. Когда ты добавляешь новый сервер, нужно переместить только ключи между этим новым сервером и предыдущим. Когда ты удаляешь сервер, только его ключи переезжают на следующий сервер на кольце. Всё остальное остаётся на месте.

![Иллюстрация](/content/in-a-hurry--core-concepts/ebb88e1ffd.svg)

Consistent Hashing

Выигрыш огромный. При простом modulo-хешировании добавление одного сервера в кластер из 10 серверов означает перемещение примерно 90% данных. При consistent hashing ты перемещаешь только около 10% (ключи, принадлежавшие затронутому диапазону). Благодаря этому серверы можно добавлять и убирать динамически, не устраивая масштабную миграцию данных.

Этот паттерн встречается во многих местах. Распределённые cache вроде Memcached и Redis Cluster используют его, чтобы распределять ключи по узлам cache. Распределённые базы данных вроде Cassandra и DynamoDB используют его для sharding. Некоторые load balancer применяют его, чтобы назначать запросы backend-серверам так, чтобы распределение было стабильным, когда серверы появляются и пропадают. CDN используют его для маршрутизации запросов на edge-серверы.

На интервью тебе редко нужно объяснять, как работает consistent hashing, если об этом не спросят напрямую. Достаточно сказать «будем использовать consistent hashing для распределения данных по узлам cache», когда речь о распределённом cache, или «будем использовать consistent hashing для shard key», когда обсуждаешь sharding базы данных. Интервьюеру обычно нужно лишь убедиться, что ты знаешь об этой технике.

Главный момент, когда стоит о нём заговорить, — обсуждение эластичного масштабирования. Если твоей системе нужно добавлять или убирать узлы cache или shard базы данных в зависимости от нагрузки, упомяни consistent hashing как механизм, который делает это практичным без массового перемещения данных.

Подробности читай в нашей статье [Consistent Hashing](/lessons/core-concepts/consistent-hashing).

## [CAP Theorem](/lessons/core-concepts/cap-theorem)

CAP theorem возникает, когда ты проектируешь распределённые системы и решаешь, как будут вести себя данные при сбоях. Она утверждает, что одновременно можно получить только два из трёх свойств: Consistency (все узлы видят одни и те же данные), Availability (каждый запрос получает ответ) и Partition tolerance (система работает, даже когда сетевые соединения между узлами рвутся). Поскольку в распределённых системах сетевые partition неизбежны, на самом деле ты выбираешь между consistency и availability.

Вот что это значит на практике. Если ты выбираешь consistency, то при сетевой partition некоторые узлы будут отказываться обслуживать запросы, вместо того чтобы вернуть потенциально устаревшие данные. Система может «лечь», но пока она работает, данные всегда корректны. Если ты выбираешь availability, каждый узел продолжает обслуживать запросы даже во время partition. Пользователи всегда получают ответ, но разные узлы могут какое-то время хранить разные данные, пока partition не исчезнет.

![Иллюстрация](/content/in-a-hurry--core-concepts/4d7b3aa531.svg)

CAP Theorem

Для большинства систем availability — правильный выбор по умолчанию. Пользователи спокойно переносят слегка устаревшие данные (твоя лента в Instagram отстаёт на 2 секунды), но не переносят, когда приложение недоступно. Ленты соцсетей, рекомендательные системы и аналитические дашборды прекрасно работают с eventual consistency: система гарантирует, что все узлы сойдутся к одному состоянию, если достаточно долго не будет новых обновлений. Это отличается от weak consistency, которая не даёт такой гарантии сходимости.

Strong consistency важна там, где устаревшие данные приводят к реальным бизнес-проблемам. Системам учёта товаров нужны точные остатки, иначе ты продашь больше, чем есть. Банковским системам нужны корректные балансы счетов, иначе откроется путь для мошенничества. Системы бронирования вроде Ticketmaster должны не допускать двойного бронирования одного и того же места. В таких системах чтение устаревших данных даже в течение нескольких секунд может стоить реальных денег или испортить пользовательский опыт.

Не обязательно выбирать одну модель для всей системы. Обычно для разных частей одного приложения требования к consistency разные. В e-commerce-системе описания товаров и отзывы могут быть eventually consistent (какая разница, если отзыв появится через 5 секунд), а остатки на складе и обработка заказов требуют strong consistency, чтобы не допустить перепродажи.

Стоит помнить, что CAP theorem описывает поведение только во время сетевых partition, а они случаются относительно редко. В обычной работе реальный компромисс — между consistency и latency. Это отражает теорема PACELC: при Partition выбирай между Availability и Consistency; Else (в остальных случаях) выбирай между Latency и Consistency. На практике это значит, что даже когда сеть в порядке, strong consistency добавляет latency, потому что узлам нужно координироваться, прежде чем отвечать.

На собеседованиях, когда ты упоминаешь replication или распределённые данные, интервьюер может спросить про consistency. Безопасный ответ — eventual consistency, если только задача прямо не связана с деньгами, остатками или бронированием ограниченных ресурсов.

Подробнее читай в нашем разборе [CAP Theorem](/lessons/core-concepts/cap-theorem).

## [Numbers to Know](/lessons/core-concepts/numbers-to-know)

Как обсуждалось в [Delivery Framework](/lessons/sd-prep/delivery), в начале собеседования не нужно делать прикидки на салфетке (back-of-the-envelope calculations). Интервьюеров интересует не это. Важно делать их тогда, когда нужно принять решение. Нужно ли делать shard базы данных? Справится ли один инстанс Redis с нагрузкой на cache? Без примерных цифр на эти вопросы не ответить.

Фокус в том, чтобы знать, какие цифры брать. Современное железо намного мощнее, чем думает большинство кандидатов. Хорошо настроенный сервер базы данных обрабатывает десятки тысяч запросов в секунду. Один инстанс Redis обрабатывает сотни тысяч операций в секунду. Если ты держишь в голове цифры времён 2010 года, ты будешь предлагать sharding и caching гораздо раньше, чем нужно.

Начни с цифр по latency, потому что они влияют почти на каждое проектное решение. Доступ к памяти занимает наносекунды. Чтение с SSD — микросекунды. Сетевые вызовы внутри дата-центра — 1–10 миллисекунд. Вызовы между континентами — от десятков до сотен миллисекунд. Когда ты решаешь, стоит ли кешировать что-то и оправдана ли сложность географического распределения, важна именно эта разница.

Считай ёмкость в контексте, когда это действительно нужно. Если интервьюер спрашивает «сколько серверов нам нужно», вот тогда и доставай цифры. Проговори ход расчёта. «Ожидаем 50K запросов в секунду, каждый сервер потянет примерно 5K запросов, значит, нужно около 10 серверов плюс запас». Интервьюер хочет увидеть, как ты продумываешь математику, а не слышать заученные факты.

Объём хранилища важен для решений о sharding. Один инстанс Postgres спокойно справляется с несколькими терабайтами. Sharding не нужен, пока ты не дойдёшь до десятков или сотен терабайт. Если кто-то предлагает sharding на 500GB, он добавляет огромную сложность без причины.

| Component | Key Metrics | Scale Triggers |
| --- | --- | --- |
| **Caching** | - ~1 миллисекунда latency - 100k+ операций/секунду - Ограничение по памяти (до 1TB) | - Hit rate &lt; 80% - Latency > 1ms - Использование памяти > 80% - Cache churn/thrashing |
| **Databases** | - До 50k транзакций/секунду - Latency чтения &lt; 5ms (с cache) - Ёмкость хранилища 64 TiB+ | - Write throughput > 10k TPS - Latency чтения > 5ms без cache - Потребность в географическом распределении |
| **App Servers** | - 100k+ одновременных соединений - 8-64 ядра @ 2-4 GHz - 64-512GB RAM стандартно, до 2TB | - Загрузка CPU > 70% - Latency ответа > SLA - Соединения близки к 100k на инстанс - Память > 80% |
| **Message Queues** | - До 1 миллиона сообщений/сек на broker - Сквозная latency &lt; 5ms - До 50TB хранилища | - Throughput близок к 800k сообщений/сек - Число partition ~200k на кластер - Растущий consumer lag |

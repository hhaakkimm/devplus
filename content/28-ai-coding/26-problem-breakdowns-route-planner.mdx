Тебе дана сеть станций (Network), соединённых рёбрами. Каждое ребро имеет время в пути (в минутах) и название линии («Blue», «Express» и т. д.). Некоторые рёбра односторонние. Основной метод планировщика принимает начальную и конечную станции и возвращает маршрут с минимальным суммарным временем в пути, где пересадка на другую линию стоит дополнительные 5 минут. Второй метод планировщика принимает те же входные данные плюс ограничение на количество пересадок между линиями.

На тестовой карте из поставки есть три маршрута от Central до Airport.

```
Green:  Central → Park → Airport                        4 + 6   = 10 min
Red:    Central → Harbor → Airport                      5 + 3   = 8 min
Blue:   Central → Mall → Stadium → Airport              2 + 3 + 2 = 7 min  (best)
```

Маршрут по Blue выигрывает при трёх участках, хотя по числу участков ты бы выбрал двухучастковый маршрут по Red.

Штраф за пересадку выглядит мелкой деталью, но вся задача строится вокруг него. Из-за него стоимость следующего ребра зависит от того, по какой линии ты приехал, и именно этот факт ломает все решения, кроме последнего.

## Решение 1, BFS по числу переходов

[BFS](https://www.hellointerview.com/learn/code/breadth-first-search/introduction) — первый алгоритм, за который берутся большинство людей, услышав «кратчайший путь». Шаблон короткий. Ты держишь очередь частичных путей и множество посещённых станций (visited). На каждом шаге достаёшь из начала очереди элемент и добавляешь в конец всех непосещённых соседей. Поиск останавливается, когда пункт назначения впервые выходит из очереди, и этот путь возвращается.

![Иллюстрация](/content/aicoding--problem-breakdowns--route-planner/0e3198edc0.svg)

Три маршрута от Central до Airport, раскрашенные по линиям

На диаграмме показаны все три маршрута от Central до Airport на тестовой карте из поставки. BFS сначала обходит соседей Central, затем соседей этих соседей и так далее. До Airport можно добраться за два перехода по линии Red и по линии Green, поэтому BFS вернёт один из них (тот, что раньше попадёт в очередь). Маршрут по Blue занимает три перехода, и BFS его не выберет, хотя именно у него наименьшее суммарное время.

BFS

```
def find_route(self, start, end):
    if not self.network.has_station(start) or not self.network.has_station(end):
        return None
    if start == end:
        return Route([start], 0, 0)

    queue = deque([(start, [start], None, 0, 0)])
    visited = {start}

    while queue:
        station, path, line, total_time, transfers = queue.popleft()
        if station == end:
            return Route(path, total_time, transfers)
        for conn in self.network.get_neighbors(station):
            if conn.destination in visited:
                continue
            visited.add(conn.destination)
            is_transfer = line is not None and line != conn.line
            queue.append((
                conn.destination,
                path + [conn.destination],
                conn.line,
                total_time + conn.travel_time + (5 if is_transfer else 0),
                transfers + (1 if is_transfer else 0),
            ))
    return None
```

Каждая запись в очереди хранит накопленное время в пути и число пересадок, хотя BFS игнорирует эти веса при выборе следующего ребра. Благодаря этому аккумулятору возвращаемый маршрут хотя бы приходит с корректным временем и числом пересадок, пусть и не самый быстрый.

Множество visited ключуется только по станции, и для BFS по числу переходов это правильно. BFS исследует все станции в одном переходе от старта раньше любой станции в двух переходах, поэтому в момент, когда станция впервые достаётся из очереди, расстояние до неё равно минимальному числу рёбер от старта. На взвешенном графе именно этот приём делает BFS неверным, потому что наименьшее число переходов и наименьшее время — это разные вопросы.

### Сложность

Пусть V — число станций, E — число соединений. Каждая станция попадает в очередь не более одного раза благодаря множеству visited, а каждое ребро просматривается не более одного раза с каждого конца, поэтому обход занимает O(V + E).

### Где ломается

На тестовой карте из поставки BFS возвращает маршрут по Red за 8 минут, хотя лучший настоящий ответ — 7 минут по Blue. Это промах на 12% на крошечном графе. На сетке 50×50 промах больше в абсолютных числах: BFS возвращает маршрут за 441 минуту при истинном минимуме 387. Время в пути по рёбрам на сетках лежит между 1 и 9 минутами, поэтому маршрут с несколькими лишними рёбрами, каждое из которых оказалось дешёвым, обгонит маршрут с меньшим числом рёбер, каждое из которых оказалось дорогим.

Решение — ранжировать частичные маршруты по накопленному весу, а не по числу переходов.

###### Pattern: Graph Search & Pathfinding

Кратчайшее время в пути по транспортной карте — это алгоритм Дейкстры, взвешенный родственник BFS. Ты расширяешь станцию с наименьшей стоимостью на данный момент, а бухгалтерию оставляешь priority queue.

## Решение 2, Dijkstra с ключом по станции

Подходящее семейство для кратчайших путей с неотрицательными весами — [алгоритм Дейкстры](https://www.hellointerview.com/learn/code/graphs/shortest-path-algorithms). Вместо FIFO-очереди ты используешь min-heap с ключом по накопленному времени от старта. Обычная очередь зафиксировала бы станцию на том пути, который добрался до неё первым, а при разной стоимости рёбер он не обязательно самый дешёвый. Каждая итерация достаёт самый дешёвый незавершённый путь, фиксирует (settle) эту станцию, закрепляя её время, и добавляет всех соседей с обновлённым итогом.

![Иллюстрация](/content/aicoding--problem-breakdowns--route-planner/334e963f6b.svg)

Dijkstra посреди работы на тестовой карте, heap виден

На диаграмме показан Dijkstra на полпути от Central до Airport на тестовой карте из поставки. Все промежуточные станции уже зафиксированы с итоговым временем: Central — 0, Mall — 2, Park — 4, Harbor — 5, Stadium — 5. В heap остались только три ожидающих прибытия в Airport, и самое дешёвое из них — прибытие по линии Blue со временем 7. Извлечение значения 7 фиксирует Airport, и поиск заканчивается правильным ответом на этой карте.

Dijkstra, visited с ключом по станции

```
def find_route(self, start, end):
    if not self.network.has_station(start) or not self.network.has_station(end):
        return None

    counter = 0
    heap = [(0, counter, start, None, [start], 0)]
    visited = {}

    while heap:
        time, _, station, line, path, transfers = heapq.heappop(heap)

        if station == end:
            return Route(path, time, transfers)

        if station in visited and visited[station] <= time:
            continue
        visited[station] = time

        for conn in self.network.get_neighbors(station):
            is_transfer = line is not None and line != conn.line
            counter += 1
            heapq.heappush(heap, (
                time + conn.travel_time + (5 if is_transfer else 0),
                counter,
                conn.destination,
                conn.line,
                path + [conn.destination],
                transfers + (1 if is_transfer else 0),
            ))
    return None
```

Каждая запись в heap хранит текущую линию, и по ней при расширении вычисляется штраф за пересадку. Когда ты проходишь по ребру, стоимость равна connection.travel\_time плюс 5, если линия соседа отличается от линии, по которой ты приехал. Проверка «null или та же линия» покрывает два случая без штрафа: первый переход из стартовой станции, когда предыдущей линии нет, и любой последующий переход по той же линии. Монотонный счётчик в кортеже heap детерминированно разрешает ничьи, когда у двух записей одинаковое время, так что heap никогда не сравнивает сами данные.

Проблема в множестве visited, которое ключуется только по станции. Такой ключ утверждает, что при первом фиксировании станции самого дешёвого прибытия в неё тебе хватит навсегда. Для обычного взвешенного графа это верно. Здесь — нет, потому что из-за штрафа за пересадку стоимость отправления со станции зависит от линии, по которой ты приехал, а ключ только по станции эту информацию выбрасывает.

### Где ломается

Представь два способа добраться до B. Можно ехать Start → A → B целиком по линии Red за 2 минуты в сумме, или Start → B напрямую по линии Blue за 3 минуты. Из B есть ребро по Blue до End стоимостью 1 минута. Самый быстрый маршрут до End — Start → B → End, который всё время остаётся на Blue и занимает 4 минуты без пересадок.

Dijkstra с ключом по станции его упускает. Он фиксирует B по прибытию через Red со временем 2, потому что 2 меньше 3, и помечает B как завершённую. Когда он расширяет B в сторону End, отправление по Blue после прибытия по Red стоит пересадки в 5 минут, поэтому End получает 2 + 1 + 5 = 8. Прибытие в B по Blue продолжило бы путь до End вообще без пересадки, но оно отбрасывается в момент извлечения, потому что B уже помечена как посещённая со временем 2. Алгоритм возвращает 8, когда правильный ответ — 4.

Это не надуманный крайний случай. На сетке 50×50 из поставки Dijkstra с ключом по станции возвращает маршрут за 389 минут при истинном минимуме 387, и на остальных сетках он тоже ошибается. Тестовую карту он решает верно только потому, что на ней нет места, где прибытие не по той линии обходится дороже позже.

«Наименьшего времени до B» недостаточно, чтобы продолжать поиск. Нужно ещё знать, по какой линии ты туда приехал.

## Решение 3: Dijkstra по состоянию (station, line)

Для обычного маршрута исправление такое: единицей состояния нужно считать (station, line), а не одну только station. Два прибытия в B, одно по Red и одно по Blue, — это два разных узла в графе, по которому ищет Dijkstra, потому что стоимость продолжения пути из каждого из них разная. Всё остальное в Dijkstra остаётся прежним; меняется только ключ в visited map: вместо station\_id он становится (station\_id, line\_id).

![Иллюстрация](/content/aicoding--problem-breakdowns--route-planner/2006c733d6.svg)

Граф станций и граф состояний для Downtown и Midtown

Левая часть схемы — вид по станциям: две станции и два ребра между ними на разных линиях. Правая часть — вид по состояниям. Начальное состояние объединяет Downtown с null-линией, потому что ты ещё не проехал ни по одному ребру. Остальные два состояния — Midtown, в который попали по ребру Express, и Midtown, в который попали по ребру Crosstown. Dijkstra работает на графе состояний. Прибытия на одну и ту же станцию по разным линиям — это отдельные узлы, и у каждого есть шанс быть раскрытым.

Dijkstra с visited по ключу (station, line)

```
def find_route(self, start, end):
    if not self.network.has_station(start) or not self.network.has_station(end):
        return None

    counter = 0
    heap = [(0, counter, start, None)]
    best = {(start, None): 0}
    parent = {(start, None): None}
    transfers = {(start, None): 0}

    while heap:
        time, _, station, line = heapq.heappop(heap)
        state = (station, line)
        if time > best[state]:
            continue
        if station == end:
            return self._build_route(parent, state, time, transfers[state])

        for conn in self.network.get_neighbors(station):
            is_transfer = line is not None and line != conn.line
            new_time = time + conn.travel_time + (5 if is_transfer else 0)
            next_state = (conn.destination, conn.line)
            if new_time < best.get(next_state, math.inf):
                best[next_state] = new_time
                parent[next_state] = state
                transfers[next_state] = transfers[state] + (1 if is_transfer else 0)
                counter += 1
                heapq.heappush(heap, (new_time, counter, conn.destination, conn.line))
    return None

def _build_route(self, parent, state, total_time, transfers):
    stations = []
    while state is not None:
        stations.append(state[0])
        state = parent.get(state)
    stations.reverse()
    return Route(stations, total_time, transfers)
```

Проверка visited опирается на best[state] — минимальное время, записанное для именно этой пары (station, line). Релаксация ребра предлагает соседу новое время-кандидата через текущее состояние, и best, parent и счётчик пересадок обновляются только тогда, когда это время лучше уже записанного. Последний момент важен для возвращаемого пути. Если записывать parent pointer при каждом push, а не только при улучшении, то более плохое прибытие может перезаписать parent у состояния раньше, чем зафиксируется лучшее, и восстановленные станции перестанут соответствовать возвращаемому времени.

Когда line входит в состояние, обычный маршрут считается корректно везде. На тестовой карте он возвращает 7, а на трёх grid-картах — истинные минимумы 387, 469 и 239. Прежний контрпример теперь разрешается как надо: Start → B → End возвращается с временем 4.

## Решение 4: Dijkstra по состоянию (station, line, transfers)

С обычным маршрутом всё решено. Метод с ограничением на пересадки — то место, где (station, line) перестаёт работать, и это другой сбой, чем в прошлый раз.

Представь Start → A → B, где Start → A идёт по Red, а A → B по Blue, так что путь в B этим способом требует одной пересадки. Другой вариант, Start → B напрямую, остаётся на Blue и требует нуля пересадок, но стоит дороже по времени. Из B единственное ребро до End идёт по Yellow. Теперь запроси самый быстрый маршрут из Start в End максимум с одной пересадкой.

Верный ответ — Start → B → End. Он приходит в B по Blue с нулём потраченных пересадок, а затем тратит единственную разрешённую пересадку на переход с Blue на Yellow до End. Но ключ (station, line) фиксирует B на Blue через более дешёвое прибытие с одной пересадкой через A, потому что у него меньше время. Когда позже из очереди достаётся прибытие в B на Blue с нулём пересадок, проверка visited видит более раннюю и более дешёвую запись и отбрасывает его. У оставшегося состояния единственная пересадка уже потрачена, так что переход по Yellow до End стал бы второй пересадкой и отсекается. Поиск возвращает null-маршрут, хотя допустимый существует.

Time-domination, то есть отбрасывание более медленного прибытия, как только появилось более быстрое, здесь не работает, потому что число пересадок — это ограничение, а не просто стоимость. Состояние, которое дешевле по времени, но потратило больше пересадок, не доминирует над более медленным состоянием, у которого пересадки ещё остались: именно оно может оказаться единственным, способным законно дойти до конца. Значит, число пересадок тоже нужно включить в состояние. Ключ visited становится (station\_id, line\_id, transfers\_used), и прибытие отбрасывается, только если раньше было прибытие на ту же станцию, по той же линии, с тем же числом потраченных пересадок и не медленнее.

Dijkstra с состоянием (station, line, transfers) и parent pointers

```
def find_route(self, start, end):
    return self._search(start, end, math.inf)

def find_route_with_max_transfers(self, start, end, max_transfers):
    if max_transfers < 0:
        return None
    return self._search(start, end, max_transfers)

def _search(self, start, end, max_transfers):
    if not self.network.has_station(start) or not self.network.has_station(end):
        return None

    bounded = max_transfers != math.inf
    counter = 0
    start_state = (start, None, 0) if bounded else (start, None)
    heap = [(0, counter, start, None, 0)]
    best = {start_state: 0}
    parent = {start_state: None}

    while heap:
        time, _, station, line, used = heapq.heappop(heap)
        state = (station, line, used) if bounded else (station, line)
        if time > best[state]:
            continue
        if station == end:
            return self._build_route(parent, state, time, used)

        for conn in self.network.get_neighbors(station):
            is_transfer = line is not None and line != conn.line
            new_used = used + (1 if is_transfer else 0)
            if new_used > max_transfers:
                continue
            new_time = time + conn.travel_time + (5 if is_transfer else 0)
            next_state = (conn.destination, conn.line, new_used) if bounded else (conn.destination, conn.line)
            if new_time < best.get(next_state, math.inf):
                best[next_state] = new_time
                parent[next_state] = state
                counter += 1
                heapq.heappush(heap, (new_time, counter, conn.destination, conn.line, new_used))
    return None

def _build_route(self, parent, state, total_time, transfers):
    stations = []
    while state is not None:
        stations.append(state[0])
        state = parent.get(state)
    stations.reverse()
    return Route(stations, total_time, transfers)
```

Оба метода планировщика теперь работают через один helper. Обычный find\_route передаёт бесконечный cap, и в этом случае helper использует ключ (station, line), а не (station, line, transfers), поскольку при недостижимом cap число пересадок ничего не ограничивает. Метод с ограничением на пересадки передаёт реальный cap и получает ключ (station, line, transfers). Отказ от измерения transfers при бесконечном cap как раз и не даёт циклу с чередованием линий породить неограниченное число состояний по пересадкам на больших grid-картах.

Путь восстанавливается по parent pointers, а не по списку, скопированному в каждую запись heap. Каждый раз, когда релаксация проходит успешно, ты записываешь предшествующее состояние, а когда destination достаётся из очереди, проходишь по pointers назад до старта и разворачиваешь результат. Стоимость построения пути переносится с каждого push на один раз в конце.

### Сложность

Пусть V — число станций, E — число рёбер, L — число различных линий. Обычный маршрут ищет по состояниям (station, line), поэтому его сложность O((V·L + E·L) log(V·L)). Поиск с ограничением на пересадки добавляет измерение transfers, ограниченное cap T, и получается O((V·L·T + E·L·T) log(V·L·T)). На поставляемых картах L ≤ 6, а cap небольшие, так что оба множителя — маленькие константы. Поиск с ограничением на пересадки на grid 60×60 завершается примерно за 10 миллисекунд.

### Итог

Все поставляемые тесты проходят, а две adversarial-карты, ломавшие прежние решения, теперь разрешаются корректно. Обычный метод возвращает истинный минимум на тестовой карте, на второй встроенной карте и на всех трёх grid-картах. Метод с ограничением на пересадки возвращает Start → B → End на контрпримере выше и справляется со случаем нуля пересадок. Отрицательный cap возвращает null: любой маршрут использует не меньше нуля пересадок, а ноль уже превышает cap ниже нуля.

## Бенчмарки (Python)

В скобках рядом с каждым временем указано время в пути, которое вариант вернул для обычного маршрута. Знак ✗ помечает неверное возвращённое значение. Строки идут от маленькой тестовой карты Central → Airport и стандартной карты Downtown → Uptown до трёх случайных сеток. У решения 4 своего столбца нет: его обычный маршрут выполняет тот же поиск по (station, line), и времена совпадают с последним столбцом.

| Датасет | BFS | Dijkstra (ключ station) | Dijkstra (ключ station, line) |
| --- | --- | --- | --- |
| Central → Airport (тестовая карта) | 2µs (10 ✗) | 3µs (7) | 5µs (7) |
| Downtown → Uptown (стандартная) | 2µs (7) | 3µs (7) | 7µs (7) |
| 50×50, из угла в угол, seed=1 | 1.1ms (441 ✗) | 5.2ms (389 ✗) | 5.3ms (387) |
| 60×60, из угла в угол, seed=2 | 1.7ms (532 ✗) | 8.3ms (476 ✗) | 7.8ms (469) |
| 50×50, внутри сетки, seed=3 | 1.0ms (265 ✗) | 4.6ms (248 ✗) | 4.9ms (239) |

BFS возвращает верное общее время на Downtown → Uptown только потому, что для этой пары маршрут с наименьшим числом пересадок случайно совпадает с маршрутом наименьшего времени. Не стоит воспринимать это как доказательство того, что BFS здесь работает правильно.

Dijkstra с ключом station выглядит нормально на двух маленьких картах, а потом ошибается на каждой сетке: возвращает 389, 476 и 248 при истинных минимумах 387, 469 и 239. На маленьких картах просто нет места, где приезд не на ту линию обходится дороже позже, поэтому баг остаётся незамеченным. Ключ (station, line) — самый дешёвый ключ, который действительно корректен для обычного маршрута. Его дополнительная стоимость по сравнению со сломанной версией — множитель L, который здесь крошечный.

## Выводы

Если ты сначала пришёл к BFS, то переход к Dijkstra и есть главный урок. Сигнал к нему — любой вес на ребре, сумму которых нужно минимизировать: время в пути, расстояния по дорогам, стоимость труб.

Более важный урок касается состояния. Дважды в этой задаче очевидный ключ оказывался слишком грубым. Ключ только по station выглядел верным, но терял линию, на которой ты приехал, а штраф за пересадку делал её частью стоимости. Ключ (station, line) выглядел верным для варианта с ограничением, но терял бюджет пересадок, а ограничение делало его частью того, что вообще допустимо. Каждый раз решение было одним: поднять недостающую часть в состояние. Если стоимость или правила задачи зависят от чего-то большего, чем текущий узел, ключ в visited должен включать это «что-то». Иначе поиск закроет состояние и выбросит тот приезд, который был нужен на самом деле. Здесь это были линия, а затем число пересадок. В других задачах это (node, remaining\_fuel), (node, parity) или (row, col, direction). Определи, от чего зависит остаток поиска, и положи это в состояние.

Переписывание на parent pointers — урок поменьше, но полезный. Внутри горячего цикла каждая копия списка в элементе heap — это работа, которую ты повторяешь снова и снова. Если ты тащишь путь с собой только ради того, чтобы один раз вернуть его в конце, восстанавливай его один раз в конце. А parent записывай только тогда, когда приезд действительно улучшает то, что у тебя было.

Pattern matching, parsing и обработка текста — от matching в стиле regex до написания простых parsers и interpreters.

Задачи на string matching попадаются в AI coding interviews, потому что они естественным образом раскладываются на несколько компонентов: здесь regex для извлечения полей, там state machine для отслеживания контекста, а может, и trie для быстрого поиска по известному набору. Умение так декомпозировать задачу — важный навык для software engineer. Можешь ли ты разбить запутанную задачу по обработке текста на чистые части? Можешь ли ты сказать AI, что строить для каждой из них, а затем правильно собрать всё вместе?

Подумай о log analyzers, которые извлекают структурированные данные из неряшливого вывода, о template engines, которые подставляют переменные внутрь строк, о config readers, validators для структурированных форматов и autocomplete по фиксированному словарю. Реальные инженеры пишут такое постоянно, поэтому эти задачи отлично подходят для формата интервью, который пытается имитировать настоящую работу.

Никто не ждёт, что ты придёшь и наизусть знаешь алгоритм KMP или Aho-Corasick. Интервьюеров интересует, сможешь ли ты понять, с каким именно типом задачи на строки имеешь дело, выбрать разумный подход и корректно реализовать его с помощью AI. Важно инженерное мышление.

## Как распознать паттерн

Задачи на string matching легко заметить в условии, потому что лексика выдаёт их с головой. Сложнее понять, *какой именно* подпаттерн подходит, ведь это toolkit-паттерн с четырьмя разными формами внутри.

Лексика, которая указывает на string matching:

* **Validate, match, find, extract, classify.** Это глаголы. Если любой из них встречается в условии, ты почти наверняка в этом паттерне.
* **Формат, описанный на примере.** «Каждая строка выглядит как LEVEL [timestamp] message» или «валидные IP выглядят как 1.2.3.4». Когда формат входных данных показан, а не описан полностью, от тебя ждут написания matcher.
* **Фиксированный словарь или схема.** Известные коды ошибок, ключи конфигурации, названия команд. Всё, где есть закрытый набор допустимых значений для проверки.

Когда ты распознал паттерн, следующий вопрос — *какой инструмент*. Используй эту таблицу:

| Если задача... | Бери... |
| --- | --- |
| Найти один фиксированный паттерн в тексте | Brute force string search |
| Сопоставить с множеством фиксированных паттернов | Trie |
| Проверить формат с различными режимами или фазами | Finite state machine |
| Извлечь структурированные поля из строки | Regex |

Самая частая ошибка в таких задачах — хвататься за один инструмент, когда задаче на самом деле нужна их комбинация. Log analyzer может использовать regex-извлечение под капотом у state machine, которая обрабатывает многострочные записи, или trie, который классифицирует извлечённые коды ошибок по известным сигнатурам. Раздел «[Объединяем части](#combining-the-pieces)» ниже разбирает это подробно.

## Основы pattern matching

Самый базовый вопрос в string matching: встречается ли этот паттерн в тексте, и где? Начни с brute force, потому что его часто достаточно, а умение понять, когда «достаточно» действительно достаточно, — тоже важный навык.

Brute force string search сдвигает окно по тексту и на каждой позиции проверяет, совпадает ли паттерн. В худшем случае это O(nm), где n — длина текста, а m — длина паттерна. Но на большинстве входных данных, которые ты увидишь на интервью, средний случай намного лучше: несовпадения обнаруживаются рано, и ты быстро двигаешься дальше.

![Иллюстрация](/content/aicoding--patterns--string-matching/inline1.svg)

Brute Force Pattern Search

```
def brute_force_search(text: str, pattern: str) -> list[int]:
    matches = []
    for i in range(len(text) - len(pattern) + 1):
        if text[i:i + len(pattern)] == pattern:
            matches.append(i)
    return matches
```

Код короткий, читаемый и корректный. Для одного паттерна и текста разумного размера это правильный ответ. Не усложняй. В следующем разделе разбирается, что брать, когда нужно сопоставлять сразу с *множеством* паттернов: именно тут brute force начинает дорого обходиться.

Начни с brute force и отметь, где он не укладывается по времени работы. Так тебе не придётся одновременно разбираться и с производительностью, и с корректностью. Это же даёт задел для тест-кейсов. Наивную версию тривиально проверить, поэтому её можно использовать как эталонный oracle, когда ты заменяешь её на что-то более быстрое.

## Trie для matching по множеству паттернов

Когда задача требует сопоставления с множеством паттернов (autocomplete, поиск по словарю, фильтрация строк лога по набору известных сигнатур ошибок), правильная структура данных — [trie](https://www.hellointerview.com/learn/code/trie/overview). Идея заранее построить структуру данных или скомпилировать паттерн экономит время, когда ты запускаешь поиск много раз, и ты будешь встречать это в string matching снова и снова.

![Иллюстрация](/content/aicoding--patterns--string-matching/inline2.svg)

Trie выше содержит слова "app", "ant", "top" и "ti". Узлы с двойной рамкой отмечают конец полного слова. Чтобы проверить, подходит ли строка, ты идёшь от корня символ за символом. Если дошёл до терминального узла, совпадение найдено. Если на каком-то шаге вывалился из trie, строки в твоём наборе нет.

Структура данных Trie

```
class TrieNode:
    def __init__(self):
        self.children: dict[str, "TrieNode"] = {}
        self.is_end = False

class Trie:
    def __init__(self):
        self.root = TrieNode()

    def insert(self, word: str) -> None:
        node = self.root
        for ch in word:
            if ch not in node.children:
                node.children[ch] = TrieNode()
            node = node.children[ch]
        node.is_end = True

    def search(self, word: str) -> bool:
        node = self.root
        for ch in word:
            if ch not in node.children:
                return False
            node = node.children[ch]
        return node.is_end

    def starts_with(self, prefix: str) -> bool:
        node = self.root
        for ch in prefix:
            if ch not in node.children:
                return False
            node = node.children[ch]
        return True
```

На интервью сам trie редко бывает всей задачей. Это строительный блок. Ты можешь использовать его внутри log parser для сопоставления с известными паттернами или как словарь, на котором держится autocomplete. Интервьюер хочет увидеть, что ты знаешь, когда trie — правильный выбор, и умеешь встроить его в более крупную систему.

Trie отлично подходит для генерации с помощью AI. Структура хорошо известна, и AI почти всегда выдаёт корректную реализацию. Если важна производительность, наивный trie с узлом на каждый символ работает медленно из-за pointer chasing и накладных расходов на каждый узел. По-настоящему быстрым его делают упаковка children в массивы фиксированного размера или сворачивание цепочек из одного потомка (radix trie). Попросив AI про «an efficient, cache-friendly trie» или «a radix trie», ты быстро получишь такую версию, не расписывая логику упаковки сам. Трать время на то, как ты используешь trie в более крупной задаче.

## Конечные автоматы (finite state machines)

Когда в задаче просят «проверить этот формат» или «найти строки, соответствующие шаблону», думай о конечных автоматах. Конечный автомат (finite state machine, FSM) — это набор состояний, набор переходов между ними в зависимости от входных символов и одно или несколько принимающих состояний. Если после обработки всего входа ты оказался в принимающем состоянии, строка подходит.

![Иллюстрация](/content/aicoding--patterns--string-matching/inline3.svg)

Автомат выше проверяет десятичные числа. S0 — начальное состояние, S3 (с двойной границей) — принимающее. Автомат читает цифры, затем точку, затем ещё цифры. Если он заканчивает в S3, вход — корректное десятичное число.

В коде конечный автомат — это обычно просто целое число (или enum), которое хранит текущее состояние, и таблица переходов:

Finite State Machine Decimal Validator

```
from enum import Enum

class State(Enum):
    START = 0
    INTEGER = 1
    DOT = 2
    DECIMAL = 3
    INVALID = 4

def is_valid_decimal(s: str) -> bool:
    state = State.START
    for ch in s:
        if state == State.START:
            if ch.isdigit():
                state = State.INTEGER
            else:
                state = State.INVALID
        elif state == State.INTEGER:
            if ch.isdigit():
                state = State.INTEGER
            elif ch == ".":
                state = State.DOT
            else:
                state = State.INVALID
        elif state == State.DOT:
            if ch.isdigit():
                state = State.DECIMAL
            else:
                state = State.INVALID
        elif state == State.DECIMAL:
            if ch.isdigit():
                state = State.DECIMAL
            else:
                state = State.INVALID
        if state == State.INVALID:
            return False
    return state == State.DECIMAL
```

Конечные автоматы встречаются часто. Валидация IP-адресов, CSV с полями в кавычках, упрощённый glob matching — всё это конечные автоматы под другой маской. Признак один: у формата есть режимы, зависящие от того, что было раньше: внутри строки в кавычках или снаружи, целая часть или дробная. Если ловишь себя на мысли, что нужно отслеживать «где я сейчас в формате», это конечный автомат.

Когда видишь задачу на конечный автомат, перед написанием кода набросай состояния и переходы в комментариях (или опиши их интервьюеру). Правильно нарисованная диаграмма состояний — это 90% работы. Код — лишь механический перевод этой диаграммы, и с переводом справится AI, если ты ясно опишешь состояния.

## Регулярные выражения

Regex — спорная тема на интервью. Одни его любят, другие избегают вовсе. В AI coding interview у regex есть удобная золотая середина: он отлично подходит для быстрого извлечения и валидации чётко заданных шаблонов, но перестаёт работать, как только нужно состояние, которое переносится между совпадениями.

Где regex уместен на интервью:

* Извлечение timestamp, IP или кодов ошибок из строк лога
* Валидация форматов вроде email-адресов или строк версий (приближённо: regex не умеет полностью валидировать email, но справляется с типичными случаями)
* Разбиение структурированного текста на поля
* Быстрый поиск и замена при раскрытии шаблонов

Где regex на интервью не подходит:

* Разбор вложенных структур (regex принципиально не справляется со сбалансированными скобками и вложенными тегами)
* Всё, где нужно сохранять состояние между совпадениями (это работа для конечного автомата)
* Многострочные записи, где одна запись занимает несколько строк

Regex Log Parser

```
import re

def parse_log_line(line: str) -> dict[str, str] | None:
    pattern = r"(\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}) \[(\w+)\] (.+)"
    match = re.match(pattern, line)
    if not match:
        return None
    return {
        "timestamp": match.group(1),
        "level": match.group(2),
        "message": match.group(3),
    }
```

В AI coding interview regex полезен для механических частей более крупной задачи. Если ты пишешь анализатор логов и первый шаг — извлечь структурированные поля из каждой строки, regex делает это быстро. AI тоже очень хорошо пишет regex-шаблоны, зачастую лучше большинства людей. Опиши простыми словами, что нужно найти, и AI обычно с первого раза выдаст рабочий шаблон. Только обязательно проверь его на граничных случаях.

С regex от AI будь осторожен. AI любит выдавать хитрые, плотные шаблоны, которые тяжело читать и ещё тяжелее отлаживать. Если ты не можешь с первого взгляда объяснить, что делает regex, попроси AI упростить его или разбить на именованные группы. На интервью поддерживаемость важнее изобретательности, так что лучше чуть более длинный читаемый шаблон, чем загадочный однострочник.

## Совмещение частей

Реальные задачи на интервью редко используют только одну из этих техник. Инструмент анализа логов может использовать конечный автомат для многострочных записей (stack trace занимает много строк, обычная запись лога — одну), regex для извлечения полей из каждой строки и trie для классификации извлечённых кодов ошибок по известному списку. Валидатор IP-адресов может использовать конечный автомат для структуры (цифры, точки, снова цифры) и brute force сравнение с deny-list.

Интервьюер оценивает, умеешь ли ты посмотреть на задачу, определить, какие части требуют какого подхода, и собрать их в работающую систему. Такая декомпозиция («Я возьму regex для извлечения полей из каждой строки, конечный автомат, чтобы отслеживать, в какой многострочной записи я нахожусь, и trie для классификации кодов ошибок») показывает, что ты умеешь разбирать большие задачи и решать их, комбинируя нужные части.

Каждый слой должен тестироваться независимо. Regex можно проверить на одной строке, конечный автомат — на небольшом многострочном входе, а поиск по trie — на известном и неизвестном коде.

Unit-тесты — твои друзья в таких задачах. AI пишет их быстро, и они окупаются при первой же поломке нижележащего слоя. Просить несколько кейсов на каждый слой стоит по мере его написания. Так ты поймаешь баги на том слое, где они появились, а не будешь распутывать весь pipeline в конце.

## Промпты для AI

Главное при промптинге задач на string matching — *разделять слои* в промпте. Анализатор логов раскладывается на извлечение (regex на каждую строку) → классификацию (trie или lookup по таблице) → агрегацию. Один промпт, который просит сделать всё сразу, даёт запутанный код, который трудно отлаживать. Три промпта, по одному на слой, дают код, который можно протестировать по отдельности, прежде чем собирать вместе.

Конкретно:

* **Проси один слой за раз.** «Напиши regex, который извлекает timestamp, level и message из одной строки. Про агрегацию пока не думай». Когда это заработает, отдельным промптом проси следующий слой. Это, пожалуй, самое важное, что убережёт тебя от ямы, которая засосёт на 45 минут.
* **Для regex описывай совпадение обычным языком и проси named groups.** «Извлеки timestamp, log level и message из каждой строки. Используй named groups». Плотный regex в одну строку мучительно отлаживать через полгода. Named groups читаются как документация.
* **Для state machine сначала набросай состояния.** Либо вслух интервьюеру, либо в комментариях перед кодом: «Три состояния: чтение целой части, чтение дробной части, accepting state. Переходы по цифрам, точкам и концу ввода».
* **Для trie просто попроси.** Структура достаточно стандартная, так что однострочный промпт даёт корректную реализацию. Трать время на то, как ты проходишь по тексту с её помощью.

## Проверка кода от AI

У кода для работы со строками есть характерные ошибки, в которых AI часто ошибается:

1. **Off-by-one при отслеживании позиции.** Классика: потребить на один символ больше или меньше. Часто встречается в написанных вручную matcher'ах и переходах state machine. Исправление обычно сводится к одному индексу, но чтобы его найти, нужно внимательно прочитать логику consume/advance.
2. **Нет обработки неожиданного ввода.** Что будет при пустом вводе? На строке, не соответствующей формату? На символе, для которого у state machine нет перехода? Happy path почти всегда работает, баги прячутся на unhappy path.
3. **Greedy и lazy в regex.** `.*` заберёт больше, чем ты хотел. Если regex совпадает со слишком большим куском, замени на `.*?` или используй более точный класс символов. AI часто по умолчанию пишет greedy и не замечает этого.
4. **Edge cases на границах структуры.** Пустые строки, пробелы в начале и в конце, ввод из одного символа, ввод максимальной ожидаемой длины. Прогони каждый случай явно. Тестовый набор от интервьюера обычно их не покрывает.

Чтобы проверить код для работы со строками, не читая каждую строку, тестируй по шагам. Собери regex, проверь на трёх входах. Добавь обёртку state machine, проверь на многострочном примере. Добавь lookup по trie, проверь на известном и неизвестном паттерне. Каждый шаг должен давать работающий код, прежде чем ты идёшь дальше. Это и хорошая инженерная практика, и хорошая стратегия на интервью: интервьюер видит, как ты шаг за шагом строишь проверенный фундамент, а не смотрит на стену непроверенного кода.

Для regex в частности: прогони его на трёх-четырёх adversarial-входах (пустая строка, частичное совпадение, несколько совпадений, спецсимволы). Если regex написал AI и он плотный, попроси упростить его до named groups, прежде чем принимать код.

## Когда что использовать

Ловушка в этих задачах — хвататься за тяжёлую артиллерию, когда хватило бы простого подхода. Подбирай инструмент под сложность:

* **split или find лучше regex**, когда формат фиксированный и простой. Если задача — «извлечь значение из строк key=value», правильный ответ — `split("=", 1)`, а не regex.
* **Regex — правильный инструмент** для извлечения полей из плоской структуры: строки логов, простые паттерны валидации, find-and-replace.
* **State machine лучше regex**, когда у формата есть отдельные режимы, зависящие от того, что было раньше. Внутри строки в кавычках или снаружи, чтение целой части или дробной. Состояние — это то, что regex и ad-hoc обработка строк моделируют плохо.
* **Trie лучше повторяющихся regex-совпадений**, когда ты сопоставляешь текст с набором фиксированных паттернов (autocomplete, lookup кодов ошибок). Один проход по trie заменяет N проверок regex.

Хвататься за самый тяжёлый инструмент из известных — негативный сигнал. Выбрать *правильный* инструмент и объяснить почему — именно это оценивает интервьюер.

## Чего ждут интервьюеры

Несколько сигналов в задачах на string matching:

* **Ты декомпозируешь до того, как писать код.** Назвать слои («regex для извлечения из строки, trie для классификации по ключевым словам, hash map для агрегации») — самый сильный отдельный ход. План важнее кода.
* **Ты подбираешь инструмент под задачу.** State machine для разбора key=value — overengineering; regex для задачи, где нужно отслеживать контекст между строками, — underengineering. Важна калибровка.
* **Ты тестируешь по шагам.** Сначала regex, потом обёртка state machine, в конце lookup по trie. Интервьюер хочет видеть, как ты строишь проверенный фундамент, а не стену непроверенного кода.
* **Ты осознанно обрабатываешь некорректный ввод.** Пропущенные поля, неожиданные символы, символы, для которых у state machine нет перехода. Сообщения об ошибках промышленного качества не нужны, но если ты вслух признаёшь случаи некорректного ввода, это отличает сильных кандидатов от слабых.

Задачи на string matching — одно из лучших мест, где можно отдать AI рутину, а самому сосредоточиться на интересном. Базовая структура trie, паттерны regex, каркас state machine — всё это хорошо известные паттерны, которые AI напишет правильно. Твой вклад — определить формат, обработать edge cases и соединить компоненты. Трать силы на это.

Интервьюеры не ждут, что ты уже писал анализатор логов с нуля. Большинство кандидатов не писали. Они ждут, что ты сможешь посмотреть на описание формата, понять структуру и систематически перевести её в код, с помощью AI. Готовность методично разбираться с незнакомым паттерном, а не паниковать или гадать, — один из самых сильных сигналов, которые может дать кандидат.

## Собираем всё вместе

Задачи на string matching каждый раз сводятся к одному и тому же workflow. Определи, какой подпаттерн подходит (или какая комбинация), разбей задачу на слои, проси AI писать по одному слою за раз и проверяй каждый слой, прежде чем собирать их вместе.

Самый сложный навык здесь — калибровка: понимать, когда хватит обычного split, когда regex — правильный инструмент, а когда он будет только мешать, и когда конечный автомат (state machine) аккуратно справится с режимами, с которыми ad-hoc обработка строк не справится. Если откалибруешься правильно, такие задачи станут одними из самых чистых в формате с AI: он отлично справляется с каждым отдельным слоем, как только ты объяснил, чем должен быть каждый слой.

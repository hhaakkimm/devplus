Композиция hash map, heap, tree и queue в собственные структуры — паттерн, который проверяет, понимаешь ли ты компромиссы, а не только API.

Весь workflow минут за девять: как распознать задачу на проектирование структуры данных, собрать две канонические композиции (LRU cache и median finder), вести AI по своему дизайну, а не слепо ему доверять, и проверить результат. Главы позволяют перейти к нужному месту. Подробный письменный разбор — ниже.

Некоторые задачи на кодинг сводятся к тому, чтобы построить правильный контейнер для твоих данных. Тебе могут предложить спроектировать LRU cache, реализовать median finder, отслеживать connected components или эффективно поддерживать range queries. Общее у всех этих задач в том, что выбор и композиция правильных структур данных определяют, уложится ли каждая операция в требуемую временную сложность.

Именно здесь AI coding interviews становятся интересными. AI-ассистент вполне может реализовать за тебя doubly-linked list или heap. Но собирать части воедино будешь ты: направлять AI, а не полагаться на него.

Этот паттерн немного отличается от других: тут важнее не найти решение, а знать, как собрать части вместе.

Интервьюеры не ждут, что ты помнишь все экзотические структуры данных. Мало кто приходит на интервью, зная внутреннее устройство Fibonacci heap наизусть. Они хотят увидеть, что ты можешь рассуждать о том, какие операции должны быть быстрыми, определить, какие примитивы их обеспечивают, и скомпоновать их в рабочее решение. Если ты можешь рассуждать так вслух, ты в отличной форме.

## Как распознать паттерн

Задачи на проектирование структур данных обычно заявляют о себе одним из двух способов. Либо в условии прямо сказано «design a data structure that...» (LRU cache, median finder, range tracker, autocomplete index), либо перечислен набор операций с конкретными требованиями к сложности («нужен O(1) lookup по ключу, O(1) вставка в начало, O(1) удаление самого старого элемента»).

Несколько признаков того, что перед тобой этот паттерн:

* **Несколько операций с конфликтующими требованиями.** Например, «добавление за O(log n) *и* получение медианы за O(1)». Ни один примитив не справляется с обеими, так что придётся комбинировать.
* **Явная формулировка «design a class».** Это прямая подсказка: интервьюер проверяет, можешь ли ты выбрать правильные примитивы и связать их между собой.
* **Знакомая фича продукта, которая соответствует известной форме.** Списки недавно использованного, статистика по sliding window, leaderboards, connected components, autocomplete, range queries: у каждой есть каноническая композиция.

Паттерн превращает требования к операциям в конкретный набор структур. Это различие важно, потому что AI отлично реализует то, что ты ему указал, но плохо выбирает саму композицию.

Хорошего кандидата от отличного в таких задачах отличает скорость распознавания. Когда ты видишь «O(1) lookup *и* O(1) удаление самого старого элемента», мозг должен сразу переходить к «hash map + linked list». ## Разбор примеров

### LRU Cache

Это каноническая задача на проектирование структуры данных, и не зря. Она заставляет скомбинировать две структуры, каждая из которых по отдельности задачу не решает, но вместе дают ровно те характеристики производительности, которые нужны.

LRU (Least Recently Used) cache поддерживает две операции: get(key) и put(key, value). Обе должны работать за O(1). Когда cache превышает свою capacity, вытесняется наименее недавно использованная запись.

Hash map даёт O(1) lookup по ключу, но не отслеживает порядок использования. Doubly-linked list идеально отслеживает порядок (самый свежий в head, самый старый в tail), но поиск конкретного узла по ключу занимает O(n). Объедини их: hash map даёт списку прямые указатели, а список даёт hash map порядок.

![Иллюстрация](/content/aicoding--patterns--data-structure-design/inline2.svg)

Дизайн работает так: на get(key) находим узел в hash map (O(1)), затем перемещаем этот узел в head linked list (O(1), потому что у тебя есть прямой указатель). На put(key, value), если ключ существует, обновляем значение и перемещаем в head. Если не существует, создаём новый узел в head и добавляем его в hash map. Если превышена capacity, удаляем tail-узел и убираем его ключ из hash map.

LRU Cache

```
class Node:
    def __init__(self, key=0, val=0):
        self.key = key
        self.val = val
        self.prev = None
        self.next = None

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.cache = {}
        self.head = Node()
        self.tail = Node()
        self.head.next = self.tail
        self.tail.prev = self.head

    def _remove(self, node: Node):
        node.prev.next = node.next
        node.next.prev = node.prev

    def _insert_head(self, node: Node):
        node.next = self.head.next
        node.prev = self.head
        self.head.next.prev = node
        self.head.next = node

    def get(self, key: int) -> int:
        if key not in self.cache:
            return -1
        node = self.cache[key]
        self._remove(node)
        self._insert_head(node)
        return node.val

    def put(self, key: int, value: int) -> None:
        if key in self.cache:
            self._remove(self.cache[key])
        node = Node(key, value)
        self.cache[key] = node
        self._insert_head(node)
        if len(self.cache) > self.cap:
            lru = self.tail.prev
            self._remove(lru)
            del self.cache[lru.key]
```

Обрати внимание на sentinel-узлы (head и tail). Они сильно упрощают граничные случаи, так что тебе не придётся отдельно обрабатывать ситуации «а что если список пуст» или «а что если я удаляю последний элемент». Это тот самый implementation detail, который AI часто делает правильно, если ты скажешь использовать sentinels, но может выдать код с багами, если не уточнишь. Явно проговаривай такие дизайнерские решения в своих промптах.

В задачах на проектирование структур данных именно ты должен вести дизайн, а AI оставь рутину реализации. Скажи AI *точно*, какие структуры комбинировать и как должен выглядеть API. Промпт «Implement an LRU cache using a hash map and doubly-linked list with sentinel nodes, supporting get and put in O(1)» даёт AI всё необходимое. Расплывчатые промпты вроде «implement an LRU cache» что-нибудь да выдадут, но решение может использовать shortcut с OrderedDict, который не покажет твоего понимания.

### Median Finder

Тебе нужна структура данных, которая позволяет добавлять числа по одному и в любой момент находить медиану. addNum должен работать за O(log n), а findMedian за O(1).

Трюк в том, чтобы держать два heap: max-heap для нижней половины чисел и min-heap для верхней. Медиана — это либо вершина max-heap (если в нём больше элементов), либо среднее двух вершин (если размеры равны). Каждый раз при добавлении числа ты кладёшь его в нужный heap и делаешь rebalance, чтобы размеры отличались не больше чем на один.

![Иллюстрация](/content/aicoding--patterns--data-structure-design/inline3.svg)

Почему два heap? Потому что нужен O(1) доступ к середине отсортированной последовательности, а поддержание полностью отсортированного массива сделало бы вставку O(n). Два heap дают вставку за O(log n) и при этом всегда держат два элемента, ближайших к медиане, на вершинах.

Median Finder

```
import heapq

class MedianFinder:
    def __init__(self):
        self.lo = []
        self.hi = []

    def addNum(self, num: int) -> None:
        heapq.heappush(self.lo, -num)
        heapq.heappush(self.hi, -heapq.heappop(self.lo))
        if len(self.hi) > len(self.lo):
            heapq.heappush(self.lo, -heapq.heappop(self.hi))

    def findMedian(self) -> float:
        if len(self.lo) > len(self.hi):
            return -self.lo[0]
        return (-self.lo[0] + self.hi[0]) / 2
```

В каждом языке два heap получаются немного по-разному, и стоит знать, какой heap в твоём языке по умолчанию, чтобы с первого раза сказать AI правильную вещь.

heapq в Python — только min-heap, поэтому мы инвертируем знак значений, чтобы имитировать max-heap для нижней половины. Это известный трюк, но о нём стоит сказать интервьюеру, чтобы он видел: ты делаешь это осознанно, а не копируешь код, который не понимаешь. Скажи AI: «use a negated min-heap for the max-heap since Python only has heapq».

Логику addNum стоит разобрать по шагам. Каждое новое число сначала попадает в max-heap (нижняя половина). Затем мы сразу переносим вершину max-heap в min-heap. Это гарантирует, что min-heap всегда получает большее из двух кандидатов. Наконец, если min-heap оказался больше, мы возвращаем его вершину обратно. В итоге в lo всегда столько же элементов, сколько в hi, или на один больше, и каждый элемент в lo меньше или равен каждому элементу в hi, благодаря чему findMedian тривиально корректен.

Частый follow-up: нужно ли ещё и удалять элементы. Тут всё усложняется, потому что heap не поддерживают эффективное удаление произвольного элемента. Стандартный подход — lazy deletion: помечаем элементы как удалённые и игнорируем их, когда они оказываются на вершине. Это отличный пример follow-up, где интервьюер проверяет, умеешь ли ты адаптировать свой дизайн, а не помнишь ли ты заученную более сложную версию.

### Union-Find

Union-Find (также называется disjoint-set data structure) отслеживает набор элементов, разбитых на некоторое число групп, и поддерживает две операции: union(a, b) объединяет группу, содержащую a, с группой, содержащей b, а find(a) возвращает идентификатор группы, которой принадлежит a (так что find(a) == find(b) отвечает на вопрос «эти два элемента в одной группе?»).

Классический пример: ты получаешь потоком связи между друзьями по одной и после каждой связи должен отвечать на вопрос «эти два пользователя в одной группе друзей?». Без Union-Find это обход графа на каждый запрос; с ним обе операции работают почти за константное время. Это правильный инструмент всякий раз, когда задача сводится к отслеживанию того, какие элементы сгруппированы вместе по мере поступления слияний: connected components в графах, классы эквивалентности, задачи на слияние аккаунтов, обнаружение избыточных рёбер в сетях.

Идея простая. Каждый элемент указывает на родителя. Чтобы проверить, находятся ли два элемента в одном множестве, идём по указателям на родителей, пока не дойдём до корня. Если у них общий корень, они в одном множестве. Чтобы объединить два множества, делаем так, чтобы один корень указывал на другой.

Наивная версия в худшем случае работает за O(n) на операцию (представь длинную цепочку). Две оптимизации сводят это к почти O(1) в амортизированном виде:

**Path compression**: когда ты находишь корень элемента, сделай так, чтобы каждый узел на пути указывал прямо на корень. В следующий раз поиск любого из этих узлов займёт один переход.

**Union by rank**: при слиянии двух множеств подвешивай более низкое дерево под более высокое. Так деревья остаются неглубокими.

Union-Find

```
class UnionFind:
    def __init__(self, n: int):
        self.parent = list(range(n))
        self.rank = [0] * n

    def find(self, x: int) -> int:
        if self.parent[x] != x:
            self.parent[x] = self.find(self.parent[x])
        return self.parent[x]

    def union(self, x: int, y: int) -> bool:
        rx, ry = self.find(x), self.find(y)
        if rx == ry:
            return False
        if self.rank[rx] < self.rank[ry]:
            rx, ry = ry, rx
        self.parent[ry] = rx
        if self.rank[rx] == self.rank[ry]:
            self.rank[rx] += 1
        return True

    def connected(self, x: int, y: int) -> bool:
        return self.find(x) == self.find(y)
```

Метод union возвращает False, если элементы уже были связаны. Это полезный сигнал для поиска избыточных рёбер в задачах на графы или для подсчёта числа различных компонент (начни с n компонент и вычитай единицу каждый раз, когда union возвращает True).

Union-Find — одна из тех структур, где реализация короткая, а область применения широкая. Она может встретиться в задаче про связность сети, группировку эквивалентных аккаунтов или поиск циклов в неориентированном графе. Не нужно заучивать все применения. Если ты понимаешь базовые операции (find, union, connected), то во время интервью сможешь распознать, когда задача подходит под этот паттерн.

Union-Find и BFS/DFS решают задачи про компоненты связности, так как же выбрать? Если ты обрабатываешь рёбра по одному (потоково или online), Union-Find подходит естественнее всего. Если весь граф известен заранее и его нужно обходить для других целей (кратчайший путь, топологический порядок), больше подходит BFS/DFS. На интервью короткое объяснение того, почему ты выбрал одно вместо другого, — сильный сигнал.

## Проектирование структуры

Самое сложное в задачах на проектирование структур данных — этап распознавания: посмотреть на требования задачи и понять, какие структуры брать. Хорошо работает такая схема рассуждений.

**Начни с операций.** Прежде чем думать о структурах данных, перечисли все операции, которые требует задача, и нужную для каждой временную сложность. «Мне нужен O(1) lookup по ключу, O(1) вставка в начало и O(1) удаление из любой позиции». Запиши этот список (или проговори его вслух для интервьюера), чтобы расплывчатая задача превратилась в конкретный набор требований.

**Сопоставь операции с примитивами.** Пройдись по списку и спроси себя: какой примитив даёт эту операцию с такой стоимостью? O(1) lookup по ключу — это hash map. O(1) вставка/удаление по краям — deque. O(log n) для min или max — heap. O(1) удаление из середины (при наличии указателя) — linked list. Чаще всего ни одна структура не удовлетворяет всем операциям, и в этом вся суть. Нужно скомбинировать две-три.

**Проверь конфликты.** Иногда две операции тянут в противоположные стороны. «Мне нужен отсортированный порядок *и* O(1) произвольный доступ по ключу» — частое противоречие. Sorted set даёт порядок, но доступ за O(log n); hash map даёт доступ за O(1), но без порядка. Решение часто в том, чтобы использовать обе структуры и поддерживать их синхронизацию. Именно в логике синхронизации прячутся баги, поэтому отметь её как место, которое нужно тщательно протестировать.

**Учти паттерны доступа.** Данные статичны (строятся один раз, запрашиваются много раз) или динамичны (постоянно меняются)? Статичные данные открывают варианты вроде отсортированных массивов с бинарным поиском, которые было бы слишком дорого поддерживать при частых обновлениях. Динамичные данные обычно ведут к деревьям, heap или структурам на основе хеширования. Подумай и о том, нужно ли обходить данные по порядку. Если задача просит «k ближайших элементов» или «все значения в диапазоне», нужна структура, которая поддерживает порядок, а значит, обычные hash map отпадают.

**Подумай об инвариантах.** У любой составной структуры данных есть инварианты — свойства, которые должны выполняться после каждой операции. Для LRU cache инвариант такой: hash map и linked list всегда согласованы в том, какие ключи существуют, а порядок в списке отражает давность обращений. Когда пишешь промпт для AI, упомяни эти инварианты. Это помогает AI сгенерировать корректный код и показывает интервьюеру, что ты думаешь о корректности, а не только о функциональности.

Объясняя дизайн интервьюеру, строй рассказ вокруг операций и компромиссов, а не вокруг названий конкретных структур данных. «Мне нужно вытеснение самого старого элемента за O(1) и lookup за O(1), поэтому я объединяю linked list с hash map» демонстрирует настоящее понимание. «Я возьму LRU cache, потому что уже видел эту задачу» демонстрирует заучивание, и интервьюеры отлично слышат эту разницу.

## Промптинг AI

Когда дизайн определён, его нужно донести до AI достаточно чётко, чтобы он выдал корректный код с первого раза. Несколько стратегий, которые хорошо работают:

**Назови структуры и их роли.** Не говори «реализуй эту структуру данных». Скажи: «Мне нужен класс MedianFinder с двумя heap: max-heap по имени lo для нижней половины и min-heap по имени hi для верхней», а затем объясни AI, как это сделать на твоём языке. Чем конкретнее промпт, тем меньше итераций потребуется.

Например: «используй heapq из Python с отрицанием значений для max-heap».

**Сначала задай API.** Расскажи AI, какие методы тебе нужны, что они принимают и что возвращают, до того как он напишет код. «У класса должны быть addNum(num: int) -> None и findMedian() -> float». Это не даст AI придумать другой интерфейс, который потом придётся согласовывать с остальным кодом.

**Заранее упомяни граничные случаи.** «Обработай случай, когда cache пуст» или «union должен возвращать False, если элементы уже в одном множестве». Если их не упомянуть, AI может обработать их, а может и нет. Не оставляй это на волю случая.

**Сначала структура данных, потом тесты.** Получи реализацию, просмотри её, и только потом проси AI сгенерировать тест-кейсы. Это эффективнее, чем просить всё сразу, и даёт возможность поймать структурные проблемы до того, как AI напишет тесты вокруг сломанной реализации.

Следи за тем, чтобы AI не срезал углы. В большинстве языков есть встроенное средство, которое полностью скрывает композицию, и если ты не скажешь «с нуля», AI часто возьмёт именно его. Формально это корректно, но скрывает связку hash map + linked list, а в ней и вся суть задачи. Прямо укажи в промпте, что реализовать нужно с нуля.

## Проверка кода, который написал AI

AI хорошо реализует примитивы, но на удивление плохо поддерживает инварианты между составными структурами. Именно туда и нужно смотреть:

1. **Согласованность инвариантов.** Когда две структуры хранят связанное состояние, они должны оставаться синхронизированными. В LRU cache hash map и linked list должны совпадать в том, какие ключи существуют; в median finder две heap должны сохранять инвариант по размеру после каждой операции. Проведи одну полную операцию через обе структуры и убедись, что в конце инвариант по-прежнему выполняется.
2. **Неудобные случаи.** Что происходит на пустой структуре, с единственным элементом, с дублирующимся ключом, с индексом за границами? Первая генерация AI обычно корректно обрабатывает happy path и молча ломается на одном из этих случаев. Назвать граничные случаи вслух до того, как ты принял код, — самый быстрый способ их поймать.
3. **Никаких скрытых обходных путей.** Если ты просил LRU cache, а получил встроенный аналог (OrderedDict в Python, LinkedHashMap в Java и т. д.), или просил heap, а получил отсортированный список, AI ушёл от композиции. Просмотри импорты и объявления полей класса: они должны соответствовать тому, что ты на самом деле просил.

Самая быстрая проверка на адекватность — мысленно прогнать несколько операций. Для LRU cache: добавь три элемента, обратись к первому (он должен переместиться в head), добавь четвёртый (least recently used должен вытесниться). Для median finder: добавь по порядку 1, 3, 2 и проверь, что медиана корректна после каждого добавления. Такие прогоны ловят большинство багов и показывают интервьюеру, что ты не принимаешь вывод AI вслепую.

## Когда использовать и какие есть альтернативы

У большинства задач на design структур данных есть «наивная» альтернатива, которую стоит явно отбросить, чтобы интервьюер видел, что ты её рассмотрел:

* **Обычный массив или список.** Если операции в основном на чтение, а входные данные ограничены, отсортированный массив с binary search обходит всё более хитрое. Не тянись к balanced BST, когда достаточно массива.
* **Один примитив.** Иногда задача действительно звучит как «используй hash map» или «используй heap». Собирай композицию только тогда, когда ни один отдельный примитив не покрывает набор операций.
* **Встроенные структуры языка.** OrderedDict в Python, LinkedHashMap в Java и std::set в C++ существуют именно для таких задач. Упомяни их на интервью («Здесь я мог бы взять OrderedDict, но реализую композицию явно, чтобы показать структуру»), и тебе засчитают знание готового решения, хотя ты им не воспользовался.

Два соседних паттерна, о которых стоит сказать отдельно, — graph search и topological sort. Если задача звучит как «отслеживай connected components по мере поступления рёбер по одному», это Union-Find. Если «найди кратчайший путь в графе», это [graph search](/lessons/ai-coding/patterns-graph-search). Если «упорядочи задачи по зависимостям», это [topological sort](/lessons/ai-coding/patterns-topological-sort). Design структур данных — правильный паттерн, когда проблема сводится к самим операциям, когда узкое место в том, *как* ты хранишь данные, а не в том, что ты с ними делаешь.

## Чего ждут интервьюеры

Несколько сигналов, за которыми интервьюеры следят в таких задачах:

* **Ты превращаешь требования в список операций, прежде чем тянуться к структурам.** «Мне нужен O(1) lookup, O(1) insert в head, O(1) remove из любого места» — это список покупок. Произнести его явно — правильный ход; сразу сказать «возьму hash map и linked list» значит пропустить рассуждение, которое интервьюер как раз оценивает.
* **Ты называешь инвариант, который поддерживает твоя композиция.** «Hash map и linked list всегда согласованы в том, какие ключи существуют, а порядок в списке отражает давность обращений». По названным инвариантам интервьюеры отличают тех, кто понимает дизайн, от тех, кто его заучил.
* **Ты ведёшь AI от дизайна, а не наоборот.** Скажи AI, какие примитивы композировать и каким должен быть API. Кандидат, который принимает всё, что AI сгенерировал первым, — тревожный знак; кандидат, который направляет его конкретными структурами и проверяет результат, — хороший сигнал.
* **Ты можешь назвать то, что не используешь.** «Я не использую встроенный тип cache из языка, потому что смысл в демонстрации композиции». Или: «Я рассматривал balanced BST, но hash map здесь быстрее, потому что упорядоченный обход не нужен». Показать альтернативы, которые ты отбросил, так же ценно, как выбрать правильную.

Такие задачи непропорционально хорошо вознаграждают подготовку. Число распространённых композиций невелико: hash map + linked list, две heap, union-find со сжатием путей, hash map + sorted set. Если ты уже по разу реализовал каждую из них до интервью, ты узнаешь паттерн за секунды, а не за минуты.

## Собираем всё вместе

Задачи на проектирование структур данных каждый раз сводятся к одним и тем же трём шагам. Переведи требования в список операций. Сопоставь каждую операцию с примитивом, который поддерживает её за нужную сложность. Собери примитивы вместе и назови инвариант, который их связывает.

AI правильно реализует любой отдельный примитив: doubly-linked list или heap он напишет за секунды. Твоя ценность в композиции: какие примитивы выбрать, как они делят состояние и какой инвариант поддерживает их согласованность. Когда эта часть готова, реализация становится механической.

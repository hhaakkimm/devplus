Тебе дан словарь, который сопоставляет слова с их частотами, и запрос, в котором может быть опечатка. Верни до maxSuggestions реальных слов, находящихся в пределах maxDistance операций редактирования от запроса. Ранжирование: сначала по edit distance (чем меньше правок, тем лучше), затем по частоте (среди слов с одинаковым расстоянием выигрывает более частое).

«Edit distance» здесь означает расстояние Левенштейна: минимальное число вставок, удалений или замен одного символа, необходимых, чтобы превратить одну строку в другую.

```
query: "helo"    → ["help", "hello", "he", "her", "here"]
query: "hourse"  → ["house", "horse", "hose"]
query: "thier"   → ["the", "this", "they", "her", "there"]
```

Бюджет задают два параметра. maxDistance по умолчанию равен 2, это практический верхний предел для опечаток в одном слове. maxSuggestions ограничивает длину результата и по умолчанию равен 5.

На тайбрейке стоит остановиться. При одинаковом расстоянии нужно показать первым более частое слово, потому что опечатка пользователя гораздо вероятнее была нацелена на частое слово, чем на редкое. «teh» должно давать подсказку «the», а не «he», хотя оба слова находятся в пределах 2 правок.

###### Паттерн: динамическое программирование

Edit distance — это каноническая задача на динамическое программирование. Ты заполняешь таблицу, где каждая ячейка переиспользует ответы на меньшие подзадачи, и экспоненциальный перебор превращается в простую сетку из обращений к уже посчитанным значениям.

## Решение 1: перебор всего словаря с полным DP

Самое очевидное прочтение задачи прямолинейно. Для каждого слова-кандидата из словаря считаем полный edit distance до запроса. Оставляем кандидатов, чьё расстояние не превышает maxDistance. Сортируем по (расстояние по возрастанию, частота по убыванию). Возвращаем первые maxSuggestions слов.

Если ты ещё не встречал расстояние Левенштейна, то вычисляется оно небольшой DP-таблицей (общий паттерн смотри в [основах динамического программирования](https://www.hellointerview.com/learn/code/dynamic-programming/fundamentals)). Пусть source и target — две строки. Строим сетку (m+1) × (n+1), где ячейка [i][j] хранит минимальное число правок, чтобы превратить первые i символов source в первые j символов target. Строки соответствуют символам source, а столбцы — символам target, поэтому dp[i][0] означает «удалить i символов из source, чтобы получить пустой target», а dp[0][j] — «вставить j символов target в пустой source». Первая строка и первый столбец заполняются значениями 0, 1, 2, ..., потому что превращение пустой строки в префикс длины k требует ровно k вставок (или k удалений в обратную сторону). Каждая остальная ячейка — минимум из трёх вариантов. Замена: dp[i-1][j-1] плюс 0, если символы совпадают, или плюс 1, если различаются. Вставка символа из target стоит dp[i][j-1] + 1. Удаление символа из source стоит dp[i-1][j] + 1.

Для наглядности возьмём превращение source = "cat" в target = "car". Таблица получается 4×4. Строка 0 равна [0, 1, 2, 3], потому что превращение пустого source в "", "c", "ca", "car" стоит 0, 1, 2, 3 вставки. Столбец 0 заполняется так же, только вниз. Ячейка [1][1] сравнивает c с c, это совпадение, поэтому она наследует dp[0][0] = 0. Ячейка [2][2] сравнивает a с a, тоже совпадение, и наследует dp[1][1] = 0. Ячейка [3][3] сравнивает t с r, это несовпадение, поэтому она равна min(dp[2][2] + 1, dp[2][3] + 1, dp[3][2] + 1) = 1. Эта единица в правом нижнем углу и есть ответ: одна замена превращает "cat" в "car".

Правая нижняя ячейка dp[m][n] — это и есть расстояние. Она отражает превращение всех m символов source во все n символов target, что по определению и есть полный edit distance между двумя строками. Одна DP-таблица даёт одно расстояние, а запускать её нужно по одному разу на каждое слово-кандидат.

![Иллюстрация](/content/aicoding--problem-breakdowns--spell-checker/179550ef7f.svg)

Перебор словаря из 50 088 слов с вычислением DP для каждого кандидата

На схеме показан перебор для запроса helo. Для каждого кандидата из словаря считается edit distance. Два кандидата получают расстояние 1, ещё три получают расстояние 2, и это и есть полезный результат. Остальные десятки тысяч кандидатов получают расстояние ≥ 3, но чтобы это выяснить, мы заплатили за полную DP-таблицу для каждого из них.

Полный перебор

```
def edit_distance(source: str, target: str) -> int:
    m, n = len(source), len(target)
    dp = [[0] * (n + 1) for _ in range(m + 1)]
    for i in range(m + 1):
        dp[i][0] = i
    for j in range(n + 1):
        dp[0][j] = j
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            sub = dp[i - 1][j - 1] + (0 if source[i - 1] == target[j - 1] else 1)
            ins = dp[i][j - 1] + 1
            dele = dp[i - 1][j] + 1
            dp[i][j] = min(ins, dele, sub)
    return dp[m][n]

def suggest(word: str, dictionary: dict[str, int], max_distance: int = 2, max_suggestions: int = 5) -> list[str]:
    scored = []
    for candidate, freq in dictionary.items():
        dist = edit_distance(word, candidate)
        if dist <= max_distance:
            scored.append((candidate, dist, freq))
    scored.sort(key=lambda r: (r[1], -r[2], r[0]))
    return [r[0] for r in scored[:max_suggestions]]
```

В коде стоит отследить несколько деталей. DP-таблица создаётся заново для каждого кандидата: каждый вызов editDistance строит новую сетку (m+1) × (n+1), заполняет её, возвращает число и выбрасывает сетку. На одном вызове стоимость аллокации невелика, но она накапливается, потому что эта функция запускается по разу на каждое слово словаря.

Ключ сортировки: (distance asc, frequency desc, word asc). Расстояние идёт первым, потому что меньше правок — всегда лучшее совпадение, а частота идёт вторым, чтобы среди кандидатов с одинаковым расстоянием первым показывалось более частое слово. Финальный тайбрейк по самому слову делает вывод стабильным, когда два кандидата совпадают по всем остальным ключам. Иначе порядок зависел бы от порядка обхода словаря.

Заметь и то, что фильтрация происходит после DP: проверка if dist &lt;= maxDistance — это постфактумный фильтр. Мы платим за полное вычисление расстояния, а потом выбрасываем большую часть результатов, хотя кандидата можно было отсеять, вообще ничего не вычисляя.

### Сложность

Пусть D — число записей в словаре, L — средняя длина кандидата, Q — длина запроса. Каждый вызов DP строит таблицу (Q+1) × (L+1), поэтому стоимость одного вызова равна O(Q · L). Перебор запускает это для каждой записи словаря, так что итого получается O(D · Q · L). Сортировка добавляет O(K log K) по K выжившим кандидатам, что пренебрежимо мало, когда K невелико.

### Где ломается

На тестовом словаре примерно из 90 слов запросы выполняются быстрее миллисекунды. Перебор тут не проблема.

На большом словаре из 50 088 слов каждый запрос занимает примерно 280 мс, потому что на каждый запрос приходится 50 088 полных DP-вычислений. Пакет из 10 запросов укладывается примерно в 2,7 с, то есть в тестовый бюджет 5 с, но до интерактивности далеко. Для проверки орфографии нужны однозначные миллисекунды, а 280 мс на запрос до этого очень далеки.

## Решение 2: отсекаем по длине до запуска DP

Идея в том, чтобы для большинства кандидатов вообще не запускать DP, а сначала проверить дешёвую нижнюю границу. Каждая из трёх операций редактирования меняет длину исходной строки не более чем на единицу: замена оставляет длину прежней, удаление убирает один символ, вставка добавляет один. Поэтому после k правок длина исходной строки может отличаться от длины целевой не более чем на k. Если нужно превратить строку из m символов в строку из n символов, понадобится минимум |m - n| операций, меняющих длину, а значит, edit distance не меньше |m - n|.

Если |len(candidate) - len(query)| уже превышает maxDistance, то и расстояние гарантированно превысит maxDistance, и кандидат не может быть подходящей подсказкой. Одно вычитание и один модуль дают этот ответ без запуска DP.

Например, если запрос — helo (длина 4), а maxDistance равен 2, любой кандидат с длиной вне диапазона [2, 6] отбрасывается. Эта проверка в одну строку пропускает полный DP для каждого кандидата длиной 1, 7, 8, 9, 10 и больше.

![Иллюстрация](/content/aicoding--problem-breakdowns--spell-checker/84aa04a20f.svg)

Фильтр по длине оставляет только кандидатов, чья длина лежит в полосе вокруг длины запроса

На схеме показан тот же запрос и тот же словарь. Пунктирная бирюзовая полоса обозначает диапазон длин [2, 6]. Кандидаты внутри полосы по-прежнему проходят через DP. Для кандидатов вне полосы выполняется только проверка длины и ничего больше. В словаре из 50,088 слов в полосу для запроса длиной 4 попадает всего 96 кандидатов, то есть мы пропускаем DP для 49,992 слов из 50,088.

Фильтр по длине

```
def edit_distance(source: str, target: str) -> int:
    m, n = len(source), len(target)
    dp = [[0] * (n + 1) for _ in range(m + 1)]
    for i in range(m + 1):
        dp[i][0] = i
    for j in range(n + 1):
        dp[0][j] = j
    for i in range(1, m + 1):
        for j in range(1, n + 1):
            sub = dp[i - 1][j - 1] + (0 if source[i - 1] == target[j - 1] else 1)
            ins = dp[i][j - 1] + 1
            dele = dp[i - 1][j] + 1
            dp[i][j] = min(ins, dele, sub)
    return dp[m][n]

def suggest(word: str, dictionary: dict[str, int], max_distance: int = 2, max_suggestions: int = 5) -> list[str]:
    scored = []
    word_len = len(word)
    for candidate, freq in dictionary.items():
        if abs(len(candidate) - word_len) > max_distance:
            continue
        dist = edit_distance(word, candidate)
        if dist <= max_distance:
            scored.append((candidate, dist, freq))
    scored.sort(key=lambda r: (r[1], -r[2], r[0]))
    return [r[0] for r in scored[:max_suggestions]]
```

Код почти не отличается от Решения 1, и важно только одно: проверка выполняется до вызова DP. Вычисление abs(len(candidate) - len(query)) занимает несколько инструкций, а построение полной DP-таблицы для сетки 8 × 6 — тысячи инструкций плюс аллокация. Если дешёвая проверка идёт первой, большинству кандидатов не приходится платить за дорогую. Всё остальное — сам DP, фильтрация, сортировка и срез — остаётся ровно таким же, как в Решении 1.

### Сложность

Асимптотика в худшем случае остаётся прежней, O(D · Q · L): если в словаре патологически много слов с длиной, близкой к длине запроса, пропустить мы ничего не сможем. На практике множитель при D сжимается до числа кандидатов в полосе, назовём его D'. В словаре из 50,088 слов D' ≈ 100 для коротких запросов и доходит примерно до 1,000, когда запрос достаточно длинный, чтобы зацепить одну из самых населённых групп по длине. Это сокращение работы на запрос на один-два порядка.

### Что получается на практике

На словаре из 50,088 слов каждый запрос ускоряется с ~280 мс до 1–2 мс, а худший случай (hourse, длина 6) укладывается примерно в 7 мс, потому что его полоса захватывает 900 записей длиной 8. Пакет из 10 запросов выполняется примерно за 22 мс.

По сравнению с 2.71 с у базового полного перебора это примерно в 123 раза быстрее на тех же входных данных, а пакет за 22 мс укладывается в тестовый лимит в 5 с с запасом более чем в 200 раз.

Если понадобится ещё больше скорости, есть два стандартных следующих шага. [BK-tree](https://en.wikipedia.org/wiki/BK-tree) индексирует словарь по попарным edit distance, так что неравенство треугольника позволяет отсекать целые поддеревья за один шаг. Работает это так: каждый узел хранит слово и группирует потомков по их edit distance до этого слова, поэтому запросу с максимальным расстоянием k нужно спускаться только в те дочерние узлы, чья метка группы попадает в диапазон [d - k, d + k], где d — расстояние от запроса до текущего узла. Banded DP по Ukkonen прекращает заполнять строку DP-таблицы, как только все её значения превышают maxDistance, и тем самым снижает стоимость самого DP на вызов. Оба варианта разумно упомянуть как дальнейшие шаги на собеседовании, но одного фильтра по длине уже хватает, чтобы укладываться в лимит этой задачи с запасом более чем в 200 раз.

## Бенчмарки

Оба варианта выдают побайтово идентичные списки подсказок, так что это сравнение показывает только то, сколько работы пропускает фильтр по длине.

| Датасет | Запросы | Полный перебор, всего | Фильтр по длине, всего | Ускорение |
| --- | --- | --- | --- | --- |
| test (~88 слов) | 4 | 0.8 мс | 0.7 мс | ~1.0× |
| **large (50,088 слов)** | **10** | **2.71 с** | **22 мс** | **123×** |

На маленьком тестовом словаре из 88 слов фильтр ничего не даёт: запустить DP на всех 88 словах так же быстро, как отфильтровать большинство и запустить DP на оставшихся единицах, поэтому в этих условиях выигрыш не заметен, пока словарь не станет большим. На словаре из 50,088 слов выигрыш растёт вместе с долей слов, лежащих вне полосы, а синтетический наполнитель сильно смещён в сторону длинных слов (40,000 из 50,088 записей имеют длину 10, ещё 9,000 — длину 9). Короткие запросы (длиной 3–5) отбрасывают на проверке длины более 99% словаря; у более длинных запросов отбрасывается меньше, но всё равно более 97%.

## Итоги

У DP есть дешёвая нижняя оценка, и её достаточно, чтобы отбросить большую часть словаря, ни разу не запуская полное вычисление. Кандидаты, которые сначала пишут версию с полным перебором и только потом думают о фильтрации, поступают абсолютно правильно: сама постановка задачи практически подталкивает к такому решению.

Стоит запомнить и более общий паттерн. Если у тебя есть дешёвая функция, которая занижает значение дорогой функции, ставь дорогую за дешёвой как проверку. Triangle-inequality pruning в метрических пространствах работает так же. Так же работают и bloom-filter prefilter перед поиском в множестве, и проверки bounding-box перед точным вычислением геометрического пересечения. Области разные, но приём один: сначала выполни простое отсечение, а потом уже тяжёлое вычисление.

Каждое решение в этой статье строит одну и ту же DP-таблицу одним и тем же способом. Меняется только то, как часто её приходится строить.

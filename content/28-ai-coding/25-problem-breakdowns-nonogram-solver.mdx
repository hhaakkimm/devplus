Тебе дана сетка из r строк и c столбцов. Для каждой строки и каждого столбца дана подсказка (clue): список целых чисел, описывающих длины подряд идущих блоков закрашенных клеток на этой линии, по порядку. Подсказка вроде [3, 1] означает: «блок из трёх закрашенных клеток, затем хотя бы одна пустая клетка, затем блок из одной закрашенной клетки». Специальная подсказка [0] означает, что линия полностью пустая.

Вот пример 5x5, решение которого рисует сердце. Левая панель — это то, что ты получаешь на вход: пустые клетки и подсказки по каждой оси, а правая панель показывает решённую сетку.

![Иллюстрация](/content/aicoding--problem-breakdowns--nonogram-solver/ccae55fee2.svg)

До и после для головоломки 5x5 с сердцем: пустая сетка с подсказками для строк и столбцов слева и решённая сетка справа

Подсказки строк идут слева от каждой сетки, подсказки столбцов — сверху. Каждый закрашенный блок в решении соответствует своей подсказке: слева направо для строк и сверху вниз для столбцов. Если корректного заполнения не существует, solver возвращает null.

Тестовый набор включает четыре размера: сначала 5x5, затем 10x10, затем 15x15 и в конце один 25x25. У каждого теста на время свой бюджет, и загвоздка в том, что подход, который проходит 10x10, может превысить бюджет на 15x15 на порядки.

###### Pattern: Backtracking

Ты заполняешь сетку, угадывая строку, переходя рекурсией к следующей и откатываясь, когда подсказки перестают сходиться. Предварительное вычисление вынужденных клеток лишь сокращает поиск до того, как в дело вступит backtracking.

## Решение 1: backtracking по клеткам

Самый прямой способ — [backtracking](https://www.hellointerview.com/learn/code/backtracking/overview). Идёшь по клеткам слева направо в каждой строке, сначала верхняя строка, потом следующая и так далее. В каждой клетке пробуешь FILLED, рекурсивно переходишь к следующей клетке, а если это поддерево поиска не дало результата, пробуешь EMPTY. Когда рекурсия доходит до правого нижнего угла, проверяешь, совпадают ли блоки каждой строки и каждого столбца со своими подсказками. Если да, готово. Если нет, откатываешься.

Чтобы отсекать ветви раньше, можно проверять блоки строки сразу после заполнения её последней клетки, а блоки столбца — только в нижней строке, потому что раньше столбец не завершён. Строка, блоки которой уже не совпадают с подсказкой, не может привести к корректной сетке независимо от того, что происходит ниже, поэтому остаток этой ветви пропускаешь.

![Иллюстрация](/content/aicoding--problem-breakdowns--nonogram-solver/9b08f384c8.svg)

Частично заполненная сверху вниз сетка с подсвеченной текущей клеткой и панелью трассировки рекурсии

На диаграмме показано состояние в середине рекурсии на головоломке 5x5 с сердцем. Строки 0 и 1 полностью расставлены, и обе проходят проверку по подсказкам строк. Строка 2 в процессе, рекурсия находится в клетке (2, 1), и FILLED ещё не применён. Строки 3 и 4 пока не тронуты.

Backtracking по клеткам

```
def solve(self) -> Optional[Nonogram]:
    puzzle = self.puzzle.clone()

    def backtrack(idx: int) -> bool:
        if idx == puzzle.rows * puzzle.cols:
            return puzzle.is_solved()
        r, c = divmod(idx, puzzle.cols)
        for state in (CellState.FILLED, CellState.EMPTY):
            puzzle.set_cell(r, c, state)
            valid = True
            if c == puzzle.cols - 1:
                if puzzle.extract_runs(puzzle.get_row(r)) != puzzle.get_row_clues(r):
                    valid = False
            if valid and r == puzzle.rows - 1:
                if puzzle.extract_runs(puzzle.get_col(c)) != puzzle.get_col_clues(c):
                    valid = False
            if valid and backtrack(idx + 1):
                return True
        puzzle.set_cell(r, c, CellState.UNKNOWN)
        return False

    if backtrack(0):
        return puzzle
    return None
```

Клонирование в начале сохраняет сетку вызывающего кода нетронутой: solver работает с копией, чтобы неудачный поиск не оставил исходную сетку наполовину заполненной. Проверка конца линии валидирует строку только тогда, когда только что была задана её последняя клетка, а столбец — только когда только что задана его последняя клетка, то есть в нижней строке: проверка в середине линии была бы лишней работой, потому что блоки неполной линии ещё не обязаны совпадать с подсказкой. Наконец, сброс при откате возвращает клетку в UNKNOWN после того, как и FILLED, и EMPTY для неё провалились; если этого не сделать, устаревшие значения в сетке сломают соседние ветви поиска.

### Сложность

Время в худшем случае — . У каждой клетки два варианта, клеток r · c, поэтому в дереве до  листьев. Отсечение по проверке линий сильно помогает на практике, но не меняет оценку худшего случая. Память: O(r · c) на сетку плюс O(r · c) на стек рекурсии.

Числа растут очень быстро. На сетке 5x5 дерево поиска ограничено 2²⁵, это примерно 33 миллиона листьев. На 10x10 это 2¹⁰⁰, то есть 10³⁰. Отсечение срезает с этого дерева огромный кусок, но не может превратить 10³⁰ во что-то, что завершится.

### Где ломается

Это решение расправляется с головоломками 5x5 примерно за 1.5 мс суммарно на всех трёх. Одна головоломка 10x10 среднего уровня работает дольше 300000 мс (пять минут) по реальному времени и так и не возвращается. Бюджет теста — 5000 мс, так что solver превышает его на порядки. Backtracking по клеткам полностью игнорирует подсказки. Возьмём строку длиной 10 с подсказкой [8]. Допустимых заполнений всего три (блок начинается в столбце 0, 1 или 2), и во всех трёх клетки в столбцах с 2 по 7 закрашены, то есть шесть клеток из десяти определены ещё до того, как ты что-либо угадал. Backtracking по клеткам этого не видит. Он пробует FILLED в столбце 0, FILLED в столбце 1, затем EMPTY в столбце 2 и обнаруживает нарушение подсказки строки, только когда рекурсия дойдёт до последней клетки строки. Каждое отклонение стоит целого поддерева впустую потраченной работы.

## Решение 2: backtracking по строкам

Исправить это можно так: перестать выбирать отдельные клетки и начать выбирать строки целиком. У каждой строки есть подсказка, и у каждой подсказки конечное число допустимых заполнений. Если перечислить их заранее, ты никогда не поставишь строку, которая нарушает собственную подсказку. Дерево поиска получается намного мельче: одна ветка на строку вместо одной ветки на клетку.

Эту работу делает вспомогательная функция, генератор вариантов для линии. Получив подсказку и длину линии, она возвращает все способы расположить блоки. Для подсказки [2, 1] и длины 5 есть три допустимых расположения.

![Подсказка [2, 1] на длине 5 с тремя допустимыми заполнениями, расположенными друг под другом](../img/aicoding--problem-breakdowns--nonogram-solver/ed117a65df.svg)

Подсказка [2, 1] на длине 5 с тремя допустимыми заполнениями, расположенными друг под другом

На диаграмме показаны все три. Минимальная длина для подсказки [2, 1] равна 2 + 1 + 1 = 4, где + 1 это обязательный пропуск между блоками. В общем случае для подсказки с блоками [r1, r2, ..., rk] минимальная длина линии равна sum(runs) + k - 1, где слагаемое k - 1 учитывает по одному обязательному пропуску между каждой парой соседних блоков. В линии 5 клеток, то есть остаётся одна клетка запаса, поэтому расположений три, а не одно и не десять.

Solver запускает этот helper один раз для каждой строки и получает список кандидатов-заполнений для каждой строки. Затем он делает backtracking по строкам. Для каждой строки он перебирает кандидатов, ставит заполнение в сетку и проверяет согласованность столбцов. Если блоки каждого столбца на текущий момент совместимы с подсказкой этого столбца, он рекурсивно переходит к следующей строке. Если какой-то столбец уже сбился с пути, solver пропускает это заполнение строки и пробует следующее.

Backtracking по строкам

```
def generate_line_possibilities(clues, length):
    if clues == [0]:
        return [tuple([CellState.EMPTY] * length)]
    n_runs = len(clues)
    min_len = sum(clues) + n_runs - 1
    if min_len > length:
        return []
    results = []

    def place(run_idx, pos, line):
        if run_idx == n_runs:
            results.append(tuple(line + [CellState.EMPTY] * (length - len(line))))
            return
        latest = length - (sum(clues[run_idx:]) + (n_runs - run_idx - 1))
        for start in range(pos, latest + 1):
            new_line = line + [CellState.EMPTY] * (start - pos) + [CellState.FILLED] * clues[run_idx]
            if run_idx < n_runs - 1:
                new_line.append(CellState.EMPTY)
            place(run_idx + 1, len(new_line), new_line)

    place(0, 0, [])
    return results

def solve(self) -> Optional[Nonogram]:
    puzzle = self.puzzle.clone()
    row_poss = [generate_line_possibilities(puzzle.get_row_clues(r), puzzle.cols)
                for r in range(puzzle.rows)]

    def column_consistent(col_idx, filled_rows):
        clues = puzzle.get_col_clues(col_idx)
        runs, length, trailing = [], 0, False
        for r in range(filled_rows):
            cell = puzzle.get_cell(r, col_idx)
            if cell == CellState.FILLED:
                length += 1
                trailing = True
            elif cell == CellState.EMPTY:
                if length > 0:
                    runs.append(length)
                    length = 0
                trailing = False
        if trailing and length > 0:
            if len(runs) >= len(clues) or length > clues[len(runs)]:
                return False
        elif not trailing and length > 0:
            runs.append(length)
        for i in range(len(runs)):
            if i >= len(clues) or runs[i] != clues[i]:
                return False
        if filled_rows == puzzle.rows:
            if puzzle.extract_runs(puzzle.get_col(col_idx)) != clues:
                return False
        return True

    def backtrack(row_idx):
        if row_idx == puzzle.rows:
            return puzzle.is_solved()
        for poss in row_poss[row_idx]:
            for c in range(puzzle.cols):
                puzzle.set_cell(row_idx, c, poss[c])
            if all(column_consistent(c, row_idx + 1) for c in range(puzzle.cols)):
                if backtrack(row_idx + 1):
                    return True
        for c in range(puzzle.cols):
            puzzle.set_cell(row_idx, c, CellState.UNKNOWN)
        return False

    if backtrack(0):
        return puzzle
    return None
```

Генератор вариантов идёт по блокам слева направо: первый блок ставится в самую раннюю возможную позицию (начиная со столбца 0), следующий блок в самую раннюю позицию после обязательного пропуска, и так далее, пока не будут расставлены все блоки, а хвост не дополнится значениями `EMPTY`. `latest` это индекс самого правого столбца, занятого к этому моменту в текущем рекурсивном кадре; он нужен, чтобы каждый следующий блок начинался после последнего завершённого блока плюс обязательный пропуск. Эта гарантия не даёт дереву исследовать раскладки, обречённые с самого начала. Кроме того, проверка согласованности столбцов должна быть частичной, потому что столбец не завершён, пока не расставлены все строки. Хвост `FILLED` означает, что столбец всё ещё внутри блока, так что последний блок подсказки может ещё расти; хвост `EMPTY` означает, что открытого блока нет, поэтому все блоки в частичном столбце уже должны быть расставлены и закрыты, а префикс завершённых блоков должен в точности совпадать с подсказкой (ошибка в этом случае с завершающим блоком здесь самый частый баг). Сброс строки при откате важен по той же причине, что и в backtracking по клеткам. Когда все кандидаты для строки провалились, solver возвращает клетки этой строки в `UNKNOWN`. Если этого не сделать, в сетке останется последнее опробованное заполнение, и когда родительская строка откатывается после одного из успехов нашей строки, вызывающий код видит то, что там осталось.

### Сложность

Если у строки в среднем P допустимых заполнений, а строк r, в дереве поиска до Pʳ листьев. Стоимость на лист равна O(r · c) на проход по столбцам. Это намного лучше, чем , когда P мало, и хорошо работает на сетках 10x10, где у большинства строк от нескольких до нескольких десятков возможных заполнений.

### Где ломается

На 10x10 backtracking по строкам решает средние головоломки суммарно меньше чем за 10 мс. На 15x15 картина другая. У строки из 15 клеток со средней подсказкой могут быть тысячи допустимых заполнений, а P¹⁵ при P в тысячах астрономически велико даже до отсечений. На большом датасете первая головоломка 15x15 решается примерно за 9000 мс, а вторая за 59000 мс, обе сильно превышают лимит в 5000 мс.

Backtracking по строкам использует подсказки столбцов только для отбраковки плохих веток, но никогда для выбора веток. Столбцы несут столько же информации, сколько и строки, а мы игнорируем половину этой информации, пока расстановка не будет готова.

## Решение 3: propagation с поиском как запасным вариантом

Перечисли варианты для *и* строк, и столбцов. Отфильтруй список вариантов каждой линии по уже известным клеткам. Если все оставшиеся варианты сходятся по значению конкретной клетки, эта клетка определена, какое бы заполнение ни было выбрано в итоге.

Когда все допустимые заполнения линии сходятся на одном значении для конкретной клетки, эта клетка определена независимо от того, какое заполнение выберут в итоге. Это называется overlap argument (аргумент пересечения), потому что он находит клетки, в которых все варианты заполнения «пересекаются» на одном значении. Возьмём одну линию длины 5 с подсказкой [4], где подсказке удовлетворяют только два заполнения.

![Два допустимых заполнения для подсказки [4] на длине 5, три клетки пересечения выделены как определённые](../img/aicoding--problem-breakdowns--nonogram-solver/34329d27aa.svg)

Два допустимых заполнения для подсказки [4] на длине 5, три клетки пересечения выделены как определённые

Оба заполнения ставят `FILLED` в столбцы 1, 2 и 3. Столбцы 0 и 4 в двух заполнениях различаются, поэтому они не определены. Столбцы 1, 2 и 3 можно сразу пометить как `FILLED` и идти дальше.

Для каждой строки и каждого столбца отфильтруй кандидатов по известным клеткам, найди клетки, в которых сходятся все оставшиеся кандидаты, и зафиксируй их. Фиксация клетки в строке r меняет то, что допустимо для столбца, пересекающего r, это может определить новые клетки, а те в свою очередь ограничат другие строки. Крути цикл, пока проход по сетке не перестанет давать новые определённые клетки. Каждый проход либо фиксирует хотя бы одну новую клетку, либо ничего не меняет, а клеток в сетке конечное число, поэтому цикл завершится не более чем за rows \* cols проходов, которые действительно что-то фиксируют.

После завершения propagation возможны два исхода. В счастливом случае все клетки известны, и головоломка решена вообще без поиска. Чаще propagation исчерпывает определённые ходы, пока часть клеток остаётся `UNKNOWN`. В этот момент головоломка локально неоднозначна, и чистая дедукция не может определить оставшиеся клетки без пробного предположения.

Здесь снова появляется backtracking, но в куда меньшей роли, чем в решениях 1 и 2. Выбери любую неизвестную клетку и предположи, что она `FILLED`. Склонируй текущее состояние (и сетку, и список кандидатов-заполнений каждой линии), чтобы можно было откатиться, если предположение неверно, поставь в клоне эту клетку в `FILLED` и снова запусти propagation. Если теперь propagation выводит противоречие, то есть у какой-то строки или столбца не осталось ни одного допустимого заполнения, предположение было неверным. Вернись к состоянию до предположения, попробуй `EMPTY` для той же клетки и снова запусти propagation. Если `EMPTY` тоже даёт противоречие, путь выше этого предположения обречён, и ты откатываешься на уровень выше.

Propagation берёт на себя большую часть проверки. Одно неверное предположение обычно за один-два прохода приводит к противоречию, поэтому каждая неудачная ветка быстро умирает. Дерево поиска остаётся мелким даже на головоломке 25x25, потому что к каждому узлу дерева привязан полный проход propagation, и он отбраковывает плохие ветки задолго до того, как им понадобилось бы расти дальше.

Propagation плюс запасной поиск

```
def generate_line_possibilities(clues, length):
    if clues == [0]:
        return [tuple([CellState.EMPTY] * length)]
    n_runs = len(clues)
    if sum(clues) + n_runs - 1 > length:
        return []
    results = []

    def place(run_idx, pos, line):
        if run_idx == n_runs:
            results.append(tuple(line + [CellState.EMPTY] * (length - len(line))))
            return
        latest = length - (sum(clues[run_idx:]) + (n_runs - run_idx - 1))
        for start in range(pos, latest + 1):
            new_line = line + [CellState.EMPTY] * (start - pos) + [CellState.FILLED] * clues[run_idx]
            if run_idx < n_runs - 1:
                new_line.append(CellState.EMPTY)
            place(run_idx + 1, len(new_line), new_line)

    place(0, 0, [])
    return results

def _filter_against(possibilities, line):
    return [p for p in possibilities
            if all(line[i] == CellState.UNKNOWN or line[i] == p[i] for i in range(len(line)))]

def _propagate(puzzle, row_poss, col_poss):
    changed = True
    while changed:
        changed = False
        for r in range(puzzle.rows):
            row = puzzle.get_row(r)
            row_poss[r] = _filter_against(row_poss[r], row)
            if not row_poss[r]:
                return False
            for c in range(puzzle.cols):
                if row[c] != CellState.UNKNOWN:
                    continue
                values = {p[c] for p in row_poss[r]}
                if len(values) == 1:
                    puzzle.set_cell(r, c, values.pop())
                    changed = True
        for c in range(puzzle.cols):
            col = puzzle.get_col(c)
            col_poss[c] = _filter_against(col_poss[c], col)
            if not col_poss[c]:
                return False
            for r in range(puzzle.rows):
                if col[r] != CellState.UNKNOWN:
                    continue
                values = {p[r] for p in col_poss[c]}
                if len(values) == 1:
                    puzzle.set_cell(r, c, values.pop())
                    changed = True
    return True

def _search(puzzle, row_poss, col_poss):
    if not _propagate(puzzle, row_poss, col_poss):
        return None
    if not puzzle.has_unknown_cells():
        return puzzle if puzzle.is_solved() else None
    for r in range(puzzle.rows):
        for c in range(puzzle.cols):
            if puzzle.get_cell(r, c) == CellState.UNKNOWN:
                for state in (CellState.FILLED, CellState.EMPTY):
                    np = puzzle.clone()
                    nrp = [list(x) for x in row_poss]
                    ncp = [list(x) for x in col_poss]
                    np.set_cell(r, c, state)
                    result = _search(np, nrp, ncp)
                    if result:
                        return result
                return None
    return None

def solve(self) -> Optional[Nonogram]:
    puzzle = self.puzzle.clone()
    row_poss = [generate_line_possibilities(puzzle.get_row_clues(r), puzzle.cols)
                for r in range(puzzle.rows)]
    col_poss = [generate_line_possibilities(puzzle.get_col_clues(c), puzzle.rows)
                for c in range(puzzle.cols)]
    return _search(puzzle, row_poss, col_poss)
```

Проход фильтрации урезает существующий список вариантов каждой линии, а не генерирует его заново, потому что генератор вызывается только один раз в начале решения. Фильтрация дешёвая: она идёт по существующему списку и оставляет записи, которые всё ещё совпадают с известными клетками, тогда как повторная генерация заново перечисляла бы все варианты линии (в худшем случае до ), а фильтрация обходит только существующий список (не больше текущего числа кандидатов) и делает на порядки меньше работы за проход. Вдобавок именно проверка на противоречие позволяет запасному поиску быстро завершаться. Если список какой-либо линии после фильтрации становится пустым, заполнить эту линию согласованно с известными клетками невозможно, поэтому функция propagation сразу возвращает false, а вызывающий код воспринимает это как неудачное предположение. Клонирование перед предположением тоже должно копировать и сетку, и списки вариантов для строк и столбцов: если клонировать только сетку, обе ветки будут делить одни и те же объекты списков, и фильтрация в одной ветке испортит другую. Это самый частый баг при написании такого solver.

### Почему это намного быстрее backtracking по строкам

Ключевой сдвиг в том, что propagation занимается арифметикой, а не поиском. Каждый проход propagation примерно линеен по сумме оставшихся кандидатов по всем линиям, так как каждый кандидат проверяется один раз на каждую клетку своей линии, а каждый проход либо даёт прогресс, либо цикл завершается. Хорошо составленная головоломка, а большинство тестовых именно такие, в основном решается одним propagation. Запасной backtracking включается только для клеток, которые нельзя определить логически, и поскольку propagation запускается после каждого предположения, неверные предположения быстро отсекаются.

### Где это оказывается

На больших головоломках 15x15 propagation логически разрешает большую часть сетки, несколько догадок закрывают остаток, и обе головоломки укладываются примерно в 16 мс суммарно. На огромной головоломке 25x25 propagation сам доходит почти до конца, а несколько догадок с повторной propagation завершают решение примерно за 187 мс. Каждый тест в наборе проходит свой бюджет с большим запасом.

Если ты клонируешь только сетку и забываешь про списки возможных вариантов, solver всё равно будет возвращать правильные ответы на малых и средних головоломках, потому что баг с общим состоянием на таких размерах проявляется редко. На 15x15 и 25x25 он выливается в периодические бесконечные циклы или неверные ответы: propagation начинает изменять списки, на которые родительский вызов всё ещё рассчитывает.

## Выводы

Эта лестница решений — компактная версия приёма, который встречается во многих задачах constraint satisfaction. Сначала берёшь голый backtracking. Затем меняешь единицу работы, чтобы каждый шаг использовал больше структуры задачи. Затем меняешь сам подход: вместо «поиск с отсечением» — «сначала дедукция, а поиск только когда дедукция исчерпана».

Propagation работает потому, что это то же самое, что делают люди, когда решают нонограмму на бумаге. Если смотреть на подсказку [8] в строке шириной 10 и отмечать средние шесть клеток как точно закрашенные, ничего не перебирая, то это и есть overlap-рассуждение. Механизация этой привычки превращает NP-полную задачу во что-то, что компьютер решает за миллисекунды.

Когда в следующий раз столкнёшься с задачей такой формы, задай себе три вопроса, прежде чем писать любой код поиска. Нужно понять, несут ли входные данные ограничения по более чем одной оси, можно ли дёшево перечислить допустимые варианты для каждой линии и существенно ли фиксация одной линии ограничивает другую. Если на все три вопроса ответ «да», бери propagation раньше, чем хитрое отсечение.

Кухня должна приготовить заказ, состоящий из нескольких блюд. Каждое блюдо готовится по рецепту, то есть по фиксированной последовательности шагов на станциях, и каждый шаг нужно назначить одному из трёх поваров. Цель — выполнить весь заказ как можно быстрее. Выбрать для каждого шага самого быстрого повара — хорошее начало, но порядок, в котором ты планируешь эти шаги, тоже важен. На нашем примере из трёх блюд смена этого порядка экономит 30 секунд.

## Подготовка

Заказ содержит список блюд. У каждого блюда есть рецепт, а рецепт — это упорядоченный список шагов на станциях с базовым временем в секундах. Станций три.

| Рецепт | Шаги |
| --- | --- |
| Burger | PREP 30 → GRILL 90 |
| Salad | PREP 30 → CHOP 60 |
| Pasta | PREP 30 → CHOP 60 → GRILL 90 |

Поваров трое, и каждый одни станции выполняет быстрее, чем другие. Фактическое время повара на шаге равно базовому времени шага, умноженному на коэффициент этого повара для данной станции.

| Повар | PREP | CHOP | GRILL |
| --- | --- | --- | --- |
| Alice | 1.5 | 1.5 | **0.5** |
| Bob | 1.5 | **0.5** | 1.5 |
| Carol | **0.5** | 1.5 | 1.5 |

У каждой станции ровно один специалист, который работает на ней вдвое быстрее базового времени, а двое остальных — в полтора раза медленнее. Поэтому быстрое время такое: PREP 15 (Carol), CHOP 30 (Bob) и GRILL 45 (Alice), а медленное втрое больше. Три правила делают расписание корректным. Шаги внутри блюда выполняются в порядке рецепта, повар делает один шаг за раз, а станция занята одним поваром в каждый момент времени. Makespan — это момент, когда заканчивается последний шаг, и именно его мы минимизируем.

Заказ [Burger, Salad, Pasta] достаточно мал, чтобы разобрать его вручную. Его оптимум — 105 секунд, а первые два решения дают по 135. Практические тесты проверяют каждое возвращённое расписание на соответствие целевому makespan. Эта цель в твой scheduler не передаётся.

Мы реализуем Kitchen.schedule(order), который возвращает Schedule с одним ScheduleEntry на каждый шаг блюда. В каждой записи указаны блюдо, повар, станция, а также время начала и конца. Этот метод строит план, не выполняя сами шаги. Записи, созданные одна за другой, могут описывать работу, которая пересекается по времени.

## Решение 1, жадный проход

Первая естественная попытка — идти по блюдам в том порядке, в котором они пришли. Для каждого шага каждого блюда ты отдаёшь шаг тому повару, который сможет закончить его раньше всех, и запускаешь его в самый ранний момент, когда это действительно допустимо. Этот самый ранний допустимый старт — наибольшее из трёх времён. Предыдущий шаг блюда должен быть завершён, повар должен быть свободен, и станция должна быть свободна.

Допустим, Pasta закончила PREP в 45, но Bob и станция CHOP заняты до 60. Тогда её CHOP должен начаться в max(45, 60, 60) = 60. Bob режет 30 секунд, поэтому шаг заканчивается в 90. Даже если другой повар свободен в 45, ему всё равно придётся ждать станцию до 60, а из-за более медленной нарезки он закончит позже. Код повторяет этот расчёт для каждого повара и выбирает самое раннее завершение.

Greedy schedule for Burger, Salad, Pasta finishing at 135

Читай таймлайн по одной станции за раз. Три PREP идут подряд у Carol с 0 до 45, потому что станция prep занята одним поваром в каждый момент времени, а выстроить три PREP по 15 секунд друг за другом — лучшее, что можно сделать. GRILL для Burger достаётся Alice с 15 до 60. CHOP для Salad выполняет Bob с 30 до 60, а CHOP для Pasta идёт следом у Bob с 60 до 90. Теперь посмотри на grill. Он свободен в 60, но GRILL для Pasta не может начаться, пока CHOP для Pasta не закончится в 90, поэтому grill простаивает с 60 до 90, а Pasta наконец жарится с 90 до 135. Makespan равен 135.

Greedy dish-order schedule

```
def schedule(self, order: Order) -> Schedule:
    chef_free = {chef.id: 0 for chef in self._chefs}
    station_free = {station: 0 for station in Station}
    entries = []

    for dish in order.dishes:
        previous_end = 0
        for step_index, (station, base) in enumerate(dish.recipe.ordered_steps):
            best = None
            for chef in self._chefs:
                start = max(previous_end, chef_free[chef.id], station_free[station])
                end = start + chef.time_for_step(station, base)
                if best is None or end < best[0]:
                    best = (end, start, chef)
            end, start, chef = best
            entries.append(ScheduleEntry(dish, step_index, station, chef, start, end))
            chef_free[chef.id] = end
            station_free[station] = end
            previous_end = end

    return Schedule(entries)
```

Карты доступности хранят конец последнего слота, который мы назначили для каждого ресурса. После планирования Burger Carol и PREP свободны в 15, а Alice и GRILL — в 60. Поэтому первый шаг Salad может использовать Carol с 15 до 30, хотя Burger закончится только в 60. `previous\_end` для каждого блюда начинается с нуля, потому что у этого блюда ещё нет предыдущего шага.

Это [greedy](https://www.hellointerview.com/learn/code/greedy/overview)-расписание соблюдает все три ограничения. Но после назначения слота мы его не двигаем и не ищем окна перед ним. Например, grill в этом расписании не используется с 60 до 90, но после назначения GRILL для Pasta в карте записано лишь то, что grill снова свободен в 135. Для поиска слота внутри этого прежнего окна пришлось бы отслеживать интервалы. Это решение только добавляет работу после последнего назначенного слота каждого ресурса, поэтому одного времени на ресурс достаточно.

### Сложность

O(общее число шагов × число поваров). Каждый шаг размещается ровно один раз, и при размещении перебираются все повара, чтобы найти самое раннее завершение. Нет ни backtracking, ни поиска, поэтому объём работы линеен по числу шагов.

### Где ломается

Заказ из трёх блюд завершается в 135 при цели 105. Заказы из четырёх и пяти блюд выходят на 165 и 195 против 120 и 135. В каждом случае планирование CHOP для Salad раньше CHOP для Pasta задерживает работу, которая идёт на grill.

## Ставим Pasta перед Salad

Жадный проход уже назначил каждый шаг его специалисту. Чтобы вернуть 30 секунд простоя grill, Pasta должна закончить нарезку раньше. Если отдать Pasta слот PREP раньше Salad, Bob нарежет Pasta с 30 по 60, как раз когда Alice закончит жарить Burger. Salad может подождать с CHOP, потому что после него у неё нет шага на grill.

## Решение 2: берём лучший готовый шаг

Хватит идти по блюдам в порядке ввода. Каждое незавершённое блюдо предлагает в кандидаты свой следующий неразмещённый шаг. Для каждого кандидата считаем самое раннее допустимое время старта и завершения по тем же трём временам доступности, что и раньше. Выбираем кандидата, который заканчивается раньше всех, фиксируем его и переводим это блюдо на следующий шаг.

Здесь «готовый шаг» — это следующий шаг, который мы можем поставить в план. Когда мы поставили PREP для Pasta с 30 по 45, мы можем поставить и её CHOP, но его старт всё равно не раньше 45.

Priority dispatch по готовым шагам

```
def schedule(self, order: Order) -> Schedule:
    dishes = order.dishes
    next_step = [0] * len(dishes)
    dish_ready = [0] * len(dishes)
    chef_free = {chef.id: 0 for chef in self._chefs}
    station_free = {station: 0 for station in Station}
    entries = []
    total = sum(len(dish.recipe.ordered_steps) for dish in dishes)

    for _ in range(total):
        best_key = None
        best_move = None
        for index, dish in enumerate(dishes):
            step_index = next_step[index]
            steps = dish.recipe.ordered_steps
            if step_index == len(steps):
                continue
            station, base = steps[step_index]
            chosen = None
            for chef in self._chefs:
                start = max(dish_ready[index], chef_free[chef.id], station_free[station])
                end = start + chef.time_for_step(station, base)
                if chosen is None or end < chosen[0]:
                    chosen = (end, start, chef)
            end, start, chef = chosen
            key = (end, start, index)
            if best_key is None or key < best_key:
                best_key = key
                best_move = (index, dish, step_index, station, chef, start, end)

        index, dish, step_index, station, chef, start, end = best_move
        entries.append(ScheduleEntry(dish, step_index, station, chef, start, end))
        chef_free[chef.id] = end
        station_free[station] = end
        dish_ready[index] = end
        next_step[index] += 1

    return Schedule(entries)
```

На [Burger, Salad, Pasta] оба решения ставят PREP для Burger первым, с 0 по 15. Решение 1 затем ставит GRILL для Burger с 15 по 60, потому что остаётся с Burger, пока у всех его шагов не появятся слоты. Dispatch сравнивает GRILL для Burger, который заканчивается в 60, с PREP для Salad и PREP для Pasta, любой из которых может закончиться в 30. Он выбирает PREP для Salad (ничью разрешает порядок ввода), а на следующем раунде ставит PREP для Pasta с 30 по 45.

Внешний цикл ставит по одной записи за раунд, пока у всех шагов не появятся слоты. Внутренний цикл сравнивает следующие шаги всех незавершённых блюд. next\_step[d] сдвигается только тогда, когда мы выбираем кандидата блюда d, поэтому рассмотрение CHOP для Pasta не делает её GRILL доступным, пока мы реально не поставим CHOP. Ключ сравнения (end, start, index) предпочитает более раннее завершение, затем более ранний старт, если завершения совпали, а затем более раннее блюдо, если совпали оба времени.

### Сложность

O(всего шагов × блюд × поваров). Для каждого размещаемого шага мы сравниваем по одному кандидату от каждого незавершённого блюда и перебираем всех поваров для этого кандидата. Из-за этих повторных сравнений dispatch дороже Решения 1, хотя каждый шаг он по-прежнему размещает всего один раз.

### Где ломается

На загруженных эталонных заказах dispatch помогает. Заказ из шести блюд улучшается с 225 до 210, а из девяти блюд — с 285 до 255. Но на трёх маленьких целевых заказах он даёт ничью с проходом в порядке блюд: 135, 165 и 195. Выбор шага с самым ранним завершением по-прежнему не учитывает работу, которая от него зависит.

###### Паттерн: Backtracking

Backtracking позволяет пробовать разные последовательности шагов блюд. Если добавить проверку по нижней оценке, мы можем перестать исследовать частичное расписание, когда оно не способно улучшить лучшее найденное полное расписание. Такое сочетание называется branch-and-bound.

## Решение 3: перебираем порядки

Когда у трёх PREP и GRILL для Burger уже есть слоты, dispatch сравнивает CHOP для Salad (30–60) с CHOP для Pasta (45–75). Он выбирает Salad, потому что она заканчивается раньше, не учитывая оставшийся шаг GRILL для Pasta. Поиск позволяет попробовать другой порядок PREP и CHOP, а затем сравнить полные расписания.

Это [branch-and-bound](https://www.hellointerview.com/learn/code/backtracking/overview): backtracking с проверкой, которая рано останавливает бесперспективные ветки. Каждый рекурсивный вызов хранит частичное расписание. Он выбирает следующий шаг одного блюда, назначает ему слот и рекурсивно вызывается с добавленным шагом. Когда у всех шагов есть слоты, мы сравниваем makespan с лучшим найденным полным расписанием. Затем возвращаемся к предыдущему выбору и пробуем другое блюдо.

Состояние хранит, докуда мы дошли с каждым блюдом и когда может стартовать его следующий шаг, а также доступность каждого повара и станции. Если блюда упорядочены как [Burger, Salad, Pasta], то при размещённом только PREP для Burger получаем next\_step = [1, 0, 0] и dish\_ready = [15, 0, 0]. Теперь Burger ждёт второй шаг, GRILL. Carol и PREP заняты до 15, а остальные ресурсы свободны с нуля.

Если следующим выбрать PREP для Salad, получим next\_step = [1, 1, 0] и dish\_ready = [15, 30, 0]. Теперь Carol и PREP освобождаются только в 30. Рекурсивный вызов исследует расписания, которые начинаются с этих двух размещений. Когда он возвращается, мы восстанавливаем состояние, в котором размещён только PREP для Burger, и пробуем PREP для Pasta в том же слоте 15–30. Каждая альтернатива стартует из одного и того же родительского состояния, поэтому резервирование, сделанное в одной ветке, не может случайно заблокировать работу в другой.

Простой перебор попробовал бы слишком много порядков. Нижняя оценка даёт оптимистичное время завершения частичного расписания. Мы сравниваем её с лучшим *полным* расписанием, которое реально нашли. Если ветка не может его побить даже при оптимистичных допущениях, мы прекращаем её исследовать. [Дерево пространства решений](https://www.hellointerview.com/learn/code/backtracking/solution-space-trees) ниже показывает, как эта проверка отсекает поддерево.

![Иллюстрация](/content/aicoding--problem-breakdowns--kitchen-orders/2c45c67f10.svg)

Дерево branch-and-bound с одним поддеревом, отсечённым по оценке

Оценку мы считаем из трёх величин. Рассмотрим частичное расписание, где у Burger и Salad есть все слоты, а CHOP для Pasta заканчивается в 90. Grill свободен с 60, когда закончился Burger, и осталось запланировать только GRILL для Pasta.

Первая величина — самое позднее время окончания, уже назначенное любому повару или станции. Здесь это 90. Добавление новых шагов не может сделать план короче, а перенос уже существующего резервирования означал бы исследование другой ветки.

Вторая величина смотрит на оставшуюся работу каждой станции. Grill занят до 60 и должен выполнить ещё один шаг на 45 секунд. Даже если блюдо и повар для этого шага готовы немедленно, grill не закончит раньше 60 + 45 = 105. Для каждого оставшегося шага мы берём длительность самого быстрого повара и предполагаем, что станция выполняет их подряд без пауз. Реальные зависимости могут заставить её ждать, но от этого она может закончить только позже.

Третья величина идёт по оставшемуся рецепту каждого блюда. CHOP для Pasta заканчивается в 90, и ей ещё нужно 45 секунд на grill, поэтому раньше 135 она не закончит, даже если Alice и grill свободны. Это ловит ожидание, которое оценка по станциям пропускает: grill может быть готов в 60, а Pasta — нет.

Должны выполняться все три ограничения, поэтому берём наибольшую оценку. Ветке нужно минимум 105 секунд на работу grill и минимум 135 на Pasta, значит, ей нужно минимум 135 в целом. Эти числа мы не складываем, потому что шаг GRILL для Pasta входит в обе оценки. Их максимум даёт нижнюю оценку без двойного учёта одной и той же работы.

Для этого частичного расписания оценка равна max(90, 105, 135) = 135. Если мы уже нашли полное расписание на 135 секунд, эта ветка не может его улучшить. Мы можем остановиться, не ставя последний шаг Pasta.

Поиск не начинается со знания, что ответ равен 105. Код стартует с лучшего makespan, равного бесконечности, чтобы ни одна ветка не отбрасывалась, пока нам не с чем сравнивать полное расписание. Первое полное расписание заменяет бесконечность своим реальным временем завершения. Ветка, в которой Pasta режется раньше Salad, может дойти до 105 и снизить это значение. С этого момента для отсечения достаточно оценки 105 или выше. Мы ищем лучший makespan, поэтому ещё одно расписание, которое лишь совпадает с лучшим, нам не нужно.

С поварами по умолчанию можно также убрать выбор повара из поиска. У каждой станции вместимость один и свой отдельный специалист. Возьмём любое допустимое расписание: если назначить каждый шаг специалисту его станции с тем же временем старта, оно может только стать короче. Конфликта поваров не возникает, потому что каждый специалист теперь работает только на одной станции, а шаги на ней и так не могут пересекаться. Значит, всегда есть расписание с одними специалистами, не хуже исходного. Если бы один повар был самым быстрым и на PREP, и на GRILL, это рассуждение не сработало бы, потому что обеим станциям мог бы понадобиться этот повар одновременно.

Повторяющиеся рецепты дают ещё один shortcut. Допустим, два блюда Salad ещё не начаты. Обоим нужен один и тот же PREP, а потом один и тот же CHOP, и оба готовы в нулевой момент. Если следующим выбрать PREP для Salad A, получатся те же варианты расписания, что и при выборе PREP для Salad B, просто с обменянными названиями. Seen set позволяет исследовать только один из этих выборов. Если их времена готовности различаются, мы оставляем оба, потому что один из них может раньше встроиться в расписание.

Memo позволяет не повторять работу в разных ветках. Например, одна ветка может поставить PREP для Salad A с 0 по 15 и для Salad B с 15 по 30, а другая — поменять их названия местами. В обеих Carol и PREP свободны с 30, при этом один Salad готов к CHOP в 15, а другой в 30. Любое оставшееся расписание, которое работает для одной ветки, работает и для другой.

Чтобы распознать такое совпадение, canonical записывает для каждого блюда рецепт, индекс следующего шага и время готовности, а затем сортирует эти записи. Перестановка двух одинаковых блюд больше не меняет результат. Этот результат мы объединяем с доступностью поваров и станций и получаем ключ для memo. Когда другая ветка приходит к тому же ключу, прошлый поиск уже рассмотрел все оставшиеся варианты. Сохранённый ключ позволяет пропустить эту работу, а полные записи расписания хранятся отдельно, чтобы мы могли вернуть реальное распределение блюд.

Поиск branch-and-bound

```
def schedule(self, order: Order) -> Schedule:
    chefs = self._chefs
    dishes = order.dishes
    steps = [list(dish.recipe.ordered_steps) for dish in dishes]
    lengths = [len(s) for s in steps]
    total = sum(lengths)
    stations = list(Station)

    fastest = {st: min(chefs, key=lambda c: c.time_for_step(st, 60)) for st in stations}
    fastest_dur = [[fastest[st].time_for_step(st, base) for st, base in s] for s in steps]
    tail = []
    for d in range(len(dishes)):
        acc = [0] * (lengths[d] + 1)
        for si in range(lengths[d] - 1, -1, -1):
            acc[si] = acc[si + 1] + fastest_dur[d][si]
        tail.append(acc)
    signature = [tuple((st.value, base) for st, base in s) for s in steps]

    best = {"makespan": float("inf"), "entries": None}
    memo = {}

    def lower_bound(next_step, dish_ready, chef_free, station_free):
        bound = max((*chef_free, *station_free))
        remaining = {st: 0 for st in stations}
        for d in range(len(dishes)):
            for si in range(next_step[d], lengths[d]):
                remaining[steps[d][si][0]] += fastest_dur[d][si]
        for i, st in enumerate(stations):
            bound = max(bound, station_free[i] + remaining[st])
        for d in range(len(dishes)):
            if next_step[d] < lengths[d]:
                bound = max(bound, dish_ready[d] + tail[d][next_step[d]])
        return bound

    def canonical(next_step, dish_ready):
        return tuple(sorted(
            (signature[d], next_step[d], dish_ready[d]) for d in range(len(dishes))
        ))

    def search(next_step, dish_ready, chef_free, station_free, entries):
        if len(entries) == total:
            makespan = max((*chef_free, *station_free))
            if makespan < best["makespan"]:
                best["makespan"] = makespan
                best["entries"] = list(entries)
            return

        bound = lower_bound(next_step, dish_ready, chef_free, station_free)
        if bound >= best["makespan"]:
            return

        key = (canonical(next_step, dish_ready), chef_free, station_free)
        if memo.get(key, float("inf")) <= bound:
            return
        memo[key] = bound

        candidates = []
        seen = set()
        for d in range(len(dishes)):
            si = next_step[d]
            if si == lengths[d]:
                continue
            mark = (signature[d], si, dish_ready[d])
            if mark in seen:
                continue
            seen.add(mark)
            station, base = steps[d][si]
            chef = fastest[station]
            ci = chefs.index(chef)
            pi = stations.index(station)
            start = max(dish_ready[d], chef_free[ci], station_free[pi])
            end = start + chef.time_for_step(station, base)
            candidates.append((end, d, ci, pi, station, chef, start, si))

        candidates.sort(key=lambda c: (c[0], c[1]))
        for end, d, ci, pi, station, chef, start, si in candidates:
            ns = list(next_step); ns[d] += 1
            dr = list(dish_ready); dr[d] = end
            cf = list(chef_free); cf[ci] = end
            sf = list(station_free); sf[pi] = end
            entry = ScheduleEntry(dishes[d], si, station, chef, start, end)
            search(tuple(ns), tuple(dr), tuple(cf), tuple(sf), entries + [entry])

    count = len(dishes)
    search((0,) * count, (0,) * count, (0,) * len(chefs), (0,) * len(stations), [])
    return Schedule(best["entries"])
```

Предвычисленные массивы избавляют поиск от необходимости пересчитывать одни и те же числа при каждом вызове. Для Pasta fastest\_dur равен [15, 30, 45]: это длительность каждого шага у профильного повара. Массив tail складывает эти длительности с конца. После всех шагов остаётся ноль секунд, перед GRILL осталось 45, перед CHOP — 30 + 45 = 75, а перед PREP — 15 + 75 = 90. Получается строка для Pasta: [90, 75, 45, 0].

Pasta — блюдо с индексом 2 в [Burger, Salad, Pasta]. Если её PREP заканчивается на 30-й секунде, индекс следующего шага равен 1, и оценка для блюда будет dish\_ready[2] + tail[2][1] = 30 + 75 = 105. Здесь предполагается, что CHOP и GRILL могут идти сразу друг за другом без ожидания. Благодаря хранению оставшихся длительностей в tail эта часть расчёта оценки превращается в обычный lookup. Массив signature отдельно хранит станции и базовые длительности каждого рецепта для проверок на одинаковые блюда.

Чтобы найти самого быстрого повара на каждой станции, код сравнивает их время на гипотетическом шаге в 60 секунд. Выходит 30 секунд у профильного повара и 90 у остальных. Реальные длительности шагов по-прежнему берутся из рецепта.

Оптимальное расписание для Burger, Salad, Pasta с завершением на 105

Разница в одной перестановке. Pasta заготавливается второй, а режется первой, так что её CHOP идёт с 30 по 60 у Bob. Поэтому Pasta попадает на гриль на 60-й секунде, ровно тогда, когда гриль освобождает Burger, и два шага на гриле идут встык: с 15 до 60 и с 60 до 105, без простоя. Это расписание оптимально, потому что двум шагам GRILL по 45 секунд нужно 90 секунд на одной станции, и ни один не может начаться раньше, чем закончится первый PREP на 15-й секунде. Ни одно допустимое расписание не может закончиться раньше, чем на 15 + 90 = 105.

### Сложность

В худшем случае поиск экспоненциален. При D блюдах в одном вызове может быть до D вариантов следующего шага. При S шагах всего полная ветка имеет глубину S. Это даёт грубую верхнюю оценку Dˢ полных последовательностей выбора, ещё до учёта того, что у блюд шаги заканчиваются. Вычисление оценок и ключей memo добавляет работы в каждом посещённом состоянии.

Отсечение и проверки повторных состояний делают небольшие заказы вполне решаемыми, но не дают полиномиальной гарантии для худшего случая. Кроме того, memo занимает память под каждое посещённое состояние, поэтому потребление памяти может расти вместе с поиском.

### Где выигрывает

Поиск выдаёт 105, 120 и 135 на трёх разобранных примерах и справляется с каждым заказом из бенчмарка в рамках лимита времени. Заказ из девяти блюд укладывается ровно в 240, то есть в целевое значение, примерно за секунду при лимите 2,5 секунды.

Общая задача, то есть расписание зависимых шагов на машинах с разной скоростью, называется flexible job-shop и является NP-hard. Эти небольшие кухонные заказы позволяют искать оптимум в рамках лимита времени. Не рассчитывай, что тот же поиск останется быстрым на гораздо больших заказах.

## Выводы

Greedy-проход заранее фиксирует порядок блюд. Dispatch выбирает среди блюд по одному шагу за раз, но никогда не пересматривает свой выбор. Поиск пробует альтернативы и сохраняет лучшее полное расписание, а нижняя оценка помогает пропускать ветки, которые его не улучшат.

На AI-assisted интервью начни с просьбы написать корректный планировщик на существующих классах. Например: «Реализуй Kitchen.schedule с локальными maps доступности поваров и станций. Для каждого шага выбирай повара, который закончит раньше, двигаясь в порядке блюд. Верни записи расписания, не меняя статус блюд». Прогони тесты на корректность и изучи timeline для заказа из трёх блюд, прежде чем просить более быстрое расписание.

Когда такой план не достигает целевого makespan, дай AI найденный тобой сбой. «Это занимает 135 секунд, потому что CHOP у Salad задерживает GRILL у Pasta. Вместо фиксации порядка блюд сделай поиск по следующему ещё не запланированному шагу каждого блюда. Покажи состояние и рекурсивный выбор, прежде чем реализовывать». Добейся работающего поиска на маленьком заказе, а потом по одному добавляй нижнюю оценку, ограничение на профильных поваров и проверки повторных состояний, перезапуская тесты после каждого изменения.

Три отдельные реализации на интервью не нужны. Начни с корректного расписания и используй падающие тесты, чтобы выбирать следующее изменение. Указывай в промпте реальный makespan или timeout, чтобы AI мог отличить плохие решения планировщика от слишком медленного поиска.

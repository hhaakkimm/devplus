Как использовать Redis на интервью по system design: caching, distributed locks, leaderboards, pub/sub и rate limiting, а также tradeoffs, о которых спрашивают интервьюеры.

Обновлено 11 июня 2026

В system design может встретиться головокружительное множество [технологий](/lessons/sd-prep/key-technologies), [концепций](/lessons/sd-prep/core-concepts) и [паттернов](/lessons/sd-prep/patterns), и именно поэтому Redis выделяется на их фоне своей универсальностью. Вместо того чтобы изучать десятки разных технологий, ты можешь выучить несколько полезных и освоить их как следует. Так у тебя больше шансов дотянуть до уровня, которого ждёт интервьюер.

Помимо универсальности, Redis хорош своей *простотой*. В нём много возможностей, похожих на структуры данных, к которым ты привык в коде (hashes, sets, sorted sets, streams и т. д.), и о них легко рассуждать в распределённой системе, когда знаешь несколько основ. Во многих базах данных много «магии» (optimizers, query planners и т. д.), а Redis намеренно остаётся простым и делает то, что умеет лучше всего: выполняет простые операции **быстро**.

## Основы Redis

Redis называет себя ["data structure store"](https://redis.io/docs/latest/) и написан на C. Он хранит всё в памяти и выполняет твои команды по одной в одном потоке, из-за чего он очень быстрый, а рассуждать о нём легко. Однопоточный дизайн выбран сознательно: выполнению команд не нужны locks, а для таких простых операций одно ядро редко становится узким местом. Новые версии выносят I/O и фоновую работу в другие потоки, но в голове стоит держать такую модель: одна команда за раз, строго по порядку.

Одна важная причина не использовать Redis — когда тебе нужна **durability**. У Redis есть два режима [persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/): RDB делает периодические snapshots (при падении теряется всё, что было после последнего), а AOF логирует каждую запись, но по умолчанию делает fsync только раз в секунду (при падении теряется до секунды подтверждённых записей). AOF можно настроить на fsync при каждой записи, но так делают немногие, потому что это стоит той скорости, ради которой Redis и берут. Это осознанный tradeoff команды Redis: гарантии «commit уже на диске», которую по умолчанию даёт реляционная база, у тебя не будет. Альтернативные реализации вроде [AWS MemoryDB](https://aws.amazon.com/memorydb/) немного жертвуют скоростью, чтобы дать настоящую durability на диске. Если она тебе нужна, она есть!

Redis — это key-value store. Ключи — строки, а значениями могут быть структуры данных: hashes, lists или sorted sets. Например, ключ leaderboard:game:123 может хранить sorted set с игроками и их очками.

Логическая модель Redis

Некоторые из основных структур данных, которые поддерживает Redis:

* Strings
* Hashes (объекты/словари)
* Lists
* Sets
* Sorted Sets (priority queues)
* Streams (append-only логи)
* Geospatial Indexes

В Redis 8 в ядро также входят вероятностные структуры вроде Bloom filters, а ещё JSON и поддержка time series. В более старых версиях всё это поставлялось в виде модулей Redis Stack.

Помимо простых структур данных, Redis поддерживает разные паттерны коммуникации вроде Pub/Sub и Streams, частично заменяя более сложные решения вроде [Apache Kafka](/lessons/key-technologies/kafka) или AWS SNS/SQS.

Выбор ключей важен, потому что в зависимости от [конфигурации инфраструктуры](#infrastructure-configurations) ключи могут храниться на разных нодах. По сути, то, как ты организуешь ключи, и есть то, как ты организуешь данные и масштабируешь свой Redis cluster.

### Команды

Redis использует простой wire protocol под названием [RESP](https://redis.io/docs/latest/develop/reference/protocol-spec/): команды и их аргументы передаются по сети почти в том виде, в каком ты набрал бы их руками. Поэтому CLI кажется таким прямолинейным. Ты буквально можешь подключиться к инстансу Redis и выполнить эти команды как есть.

```
SET foo 1  
GET foo     # Returns 1
INCR foo    # Returns 2
XADD mystream * name Sara surname OConnor # Adds an item to a stream
```

[Полный список команд](https://redis.io/commands/) удивительно легко читается, если сгруппировать его по структурам данных. Например, Sets в Redis поддерживают простые операции: добавить элемент в set (SADD), получить число элементов, или cardinality (SCARD), перечислить эти элементы (SMEMBERS) и проверить наличие (SISMEMBER). Это близкие аналоги того, что есть у Set в любом языке программирования общего назначения.

### Конфигурации инфраструктуры

Redis может работать как одна нода, с replica для высокой доступности (HA) или как cluster. В режиме cluster каждый ключ хешируется в один из 16 384 «hash slots», и каждый slot назначен какой-то ноде. Это sharding: каждая нода владеет частью slots и, следовательно, частью твоих ключей. Клиенты Redis кешируют соответствие slot → нода, поэтому они могут вычислить slot по ключу и подключиться напрямую к ноде, где лежат нужные им данные. Когда ты добавляешь ноду, slots (и ключи в них) мигрируют на неё.

![Иллюстрация](/content/deep-dives--redis/de775b09c8.svg)

Конфигурации инфраструктуры Redis

Представь hash slots как телефонную книгу: клиент хранит у себя локальную карту slots по нодам. Если slot переехал во время rebalancing или failover, сервер отвечает MOVED, и клиент обновляет свою карту (например, через CLUSTER SHARDS).

Ноды обмениваются состоянием cluster друг с другом (через gossip protocol), поэтому каждая нода знает полную карту slots. Если ты запросишь ключ не у той ноды, получишь ответ MOVED с указанием правильной. Нода не будет пересылать запрос за тебя, поэтому клиенты кешируют карту и стараются попасть в нужную ноду с первой попытки.

Пара слов о replicas, раз большинство production-развёртываний их используют. Репликация в Redis **асинхронная**. Primary подтверждает твою запись до того, как replica её увидела, поэтому когда primary падает и replica повышается до primary, последние подтверждённые записи могут просто пропасть. Это самая глубокая причина, по которой Redis не является system of record, и к ней мы ещё вернёмся, когда будем говорить про locks.

Зато на стороне чтения replicas отрабатывают своё. В режиме cluster клиент выполняет READONLY на своём соединении, чтобы разрешить чтение с replicas, и большинство клиентских библиотек выводят это в виде флага. Вне режима cluster ты просто направляешь read-трафик прямо на replica. В любом случае ты соглашаешься на чтения, которые отстают от primary на величину replication lag.

Кроме того, Redis cluster делает для тебя куда меньше, чем можно ожидать. Нет query router, который разбивает запрос по нодам и склеивает результаты. За редкими исключениями Redis ожидает, что все данные для одной команды лежат на одной ноде. Если это не так, ты получишь ошибку, а не медленный запрос. **Выбор структуры ключей — это и есть способ масштабировать Redis.**

Когда двум ключам нужно жить вместе, на помощь приходят hash tags. Хешируется только часть ключа внутри \{фигурных скобок\}, поэтому \{user:123\}:posts и \{user:123\}:likes всегда попадают в один slot, и по ним можно выполнить MULTI transaction.

## Performance

Redis работает очень, очень быстро. Один узел Redis может обрабатывать порядка 100k записей в секунду. Сама команда выполняется за микросекунды, а по сети чтение занимает меньше миллисекунды. Из-за такого масштаба некоторые антипаттерны для других баз данных с Redis становятся вполне допустимыми. Отправлять по одному запросу на каждый элемент списка (паттерн N+1) губительно для SQL-базы, но в Redis каждая команда стоит серверу микросекунды, а команды можно отправлять через pipeline (или использовать MGET) и платить одним round trip вместо сотни. Лучше всё равно этого избегать, но дизайн это не потопит.

Такая скорость целиком следует из того, что Redis работает в памяти. Он подходит не для каждого сценария, но для многих подходит отлично.

## Возможности

### Redis как cache

Самый распространённый сценарий использования Redis: cache. Соответствие прямое: ключи cache — это ключи Redis, закэшированные значения — значения Redis. Redis легко распределяет эту hash map по всем узлам кластера, поэтому масштабироваться можно без особых хлопот. Если нужно больше ёмкости, мы просто добавляем узлы в кластер.

Например, ты можешь закэшировать товар под ключом product:123, а значение хранить как JSON-blob или как Redis Hash с полями вроде name, price и inventoryCount.

Когда Redis используется как cache, на каждый ключ обычно ставят time to live (TTL). Redis гарантирует, что ты никогда не прочитаешь значение ключа после истечения TTL. Истечение срока решает проблему устаревших данных, но не нехватки памяти: по умолчанию Redis *отклоняет* записи, когда память заполнена. Для cache настраивают политику вытеснения, например allkeys-lru, чтобы Redis выбрасывал наименее недавно использованные ключи и освобождал место. Redis приближённо реализует LRU: он сэмплирует ключи, а не отслеживает точный порядок, и для cache этого более чем достаточно.

Такое использование Redis не решает одну из важнейших проблем cache: [проблему «hot key»](#hot-key-issues), когда один ключ получает непропорционально большую долю трафика. Это не особенность Redis. С тем же сталкиваются Memcached и даже масштабные базы данных вроде DynamoDB. Способы борьбы мы разберём [ниже](#hot-key-issues).

### Redis как distributed lock

Ещё одно частое применение Redis в system design: distributed lock. Иногда в системе есть данные, для которых нужно сохранять консистентность при обновлениях (например, очень популярный вопрос [Design Ticketmaster](/lessons/breakdowns/ticketmaster)), или нужно убедиться, что несколько человек не выполняют одно и то же действие одновременно (например, [Design Uber](/lessons/breakdowns/uber)).

Redis здесь подходит, потому что это один общий сервер, доступный всем твоим app-серверам, а каждая команда выполняется атомарно. Сам lock — это просто ключ, о котором все договорились, например lock:concert:343. Чтобы захватить его, пробуем создать этот ключ:

```
SET lock:concert:343 my-token NX EX 30
```

Флаг NX заставляет SET сработать, только если ключа ещё нет. Если команда сработала, lock твой. Если нет, его держит кто-то другой: подожди и повтори попытку. Параметр EX 30 ставит на ключ срок жизни 30 секунд, чтобы упавший процесс не удерживал lock вечно, а my-token — это случайное значение, уникальное для тебя, и через минуту станет ясно, зачем оно нужно.

Освобождение lock — это удаление ключа, но просто выполнять DEL не стоит. Твой lock мог истечь и быть захвачен кем-то другим, и слепое удаление снесёт *его* lock. Вместо этого проверь, что ключ всё ещё содержит твой token, и только тогда удаляй. Проверка и удаление выполняются как крошечный [Lua script](https://redis.io/docs/latest/develop/programmability/eval-intro/). Redis выполняет весь скрипт как одну команду в своём единственном потоке, и именно это делает его атомарным:

```
if redis.call("GET", KEYS[1]) == ARGV[1] then return redis.call("DEL", KEYS[1]) end
```

Кандидаты иногда спрашивают, не является ли это «optimistic locking». Это ровно наоборот: захват lock до начала работы — это pessimistic подход. Redis также поддерживает optimistic concurrency control: делаешь WATCH на ключ, выполняешь транзакцию через MULTI/EXEC, и транзакция прерывается, если отслеживаемый ключ тем временем изменился.

У этого lock на одном узле есть сбой, который мы видели в разделе про cluster: replication асинхронная, поэтому если primary умирает сразу после выдачи твоего lock, повышенная до primary replica может ничего о нём не знать и с радостью выдаст тот же lock кому-то другому. [Алгоритм Redlock](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/) создан как раз для того, чтобы пережить такую ситуацию: он захватывает lock на большинстве независимых узлов Redis. Имей в виду, что он спорный. Приостановленный или медленный клиент всё равно может действовать после того, как его lock истёк, а [критика Мартина Клеппмана](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html) подробно разбирает, как именно это ломается. Стандартная защита — fencing token: каждая выдача lock сопровождается возрастающим числом, а слой хранения отклоняет записи с устаревшим числом. В Redis для этого ничего встроенного нет.

Относись к lock в Redis как к инструменту повышения эффективности, который иногда даёт сбой, а не как к гарантии корректности. Если в твоём дизайне устаревший владелец lock испортит данные, обеспечивай инвариант там, где живут данные, или используй систему консенсуса вроде ZooKeeper или etcd. На практике row lock через SELECT ... FOR UPDATE или условный UPDATE ... WHERE version = X в твоей базе данных часто полностью заменяет distributed lock.

### Redis для leaderboard

Sorted set в Redis хранят упорядоченные данные, к которым можно обращаться за логарифмическое время, что делает их естественным выбором для leaderboard. Высокий write throughput и низкий read latency особенно полезны в масштабных приложениях, где что-то вроде SQL DB начнёт захлёбываться.

Возьмём для примера разбор [Post Search](/lessons/breakdowns/fb-post-search), где sorted set как раз работают: нужно найти посты с заданным ключевым словом (например, «tiger»), у которых больше всего лайков (например, «Tiger Woods made an appearance...» с 500 лайками).

Мы можем использовать sorted set в Redis, чтобы вести список самых залайканных постов для данного ключевого слова. Периодически можно удалять посты с низким рангом, чтобы экономить место.

```
ZADD tiger_posts 500 "SomeId1" # Add the Tiger woods post
ZADD tiger_posts 1 "SomeId2" # Add some tweet about zoo tigers
ZREMRANGEBYRANK tiger_posts 0 -6 # Remove all but the top 5 posts
```

ZADD устанавливает score для member и заменяет его, если member уже существует, поэтому повторное добавление поста с новым числом лайков просто меняет его ранг. А отрицательные индексы в ZREMRANGEBYRANK отсчитываются от наивысшего ранга: удаление рангов от 0 до -6 очищает всё от самого низкого score до шестого сверху, оставляя ровно топ-5.

### Redis для rate limiting

Структуры данных Redis также делают rate limiting простым. Распространённый алгоритм — fixed-window rate limiter, где мы гарантируем, что число запросов не превышает N за фиксированное окно времени W.

Реализация в Redis проста. Когда приходит запрос, мы увеличиваем (INCR) счётчик для текущего окна и проверяем ответ. Если счётчик превышает N, мы отклоняем запрос (обычно это 429 с заголовком Retry-After). Иначе обрабатываем его. Одна тонкость: expiry нужно ставить только когда INCR вернул 1, то есть на первом запросе окна. Если вызывать EXPIRE на каждом запросе, сброс постоянно отодвигается, и при стабильном потоке трафика новое окно никогда не наступит. Выполняй INCR и EXPIRE как один Lua script, тем же приёмом, что и при освобождении lock. Сбой между двумя командами оставил бы счётчик, который никогда не сбрасывается.

Если нужно sliding window, с ним справляются sorted set. Держи по одному sorted set на пользователя, где score — это timestamp запроса. На каждом запросе: ZREMRANGEBYSCORE удаляет записи старше окна, ZCARD считает оставшиеся, и если счёт меньше N, ZADD добавляет новый запрос. Выполняй эту последовательность как Lua script, чтобы она шла атомарно.

### Redis для proximity search

Redis нативно поддерживает геопространственные индексы с командами вроде GEOADD и GEOSEARCH. Базовые команды просты:

```
GEOADD key longitude latitude member # Adds "member" to the index at key "key"
GEOSEARCH key FROMLONLAT longitude latitude BYRADIUS radius unit # Searches the index at key "key" at specified position and radius
```

Команда поиска в данном случае выполняется за O(N+log(M)), где N — число элементов внутри выровненного по сетке bounding box вокруг области поиска, а M — число элементов, которые действительно попадают в твой радиус.

Почему у нас есть и N, и M? Геопространственные команды Redis под капотом используют [geohash](/lessons/key-technologies/proximity-search) (широта и долгота, закодированные в одно сортируемое значение и хранящиеся в sorted set). Поиск позиции в этом sorted set и даёт логарифмический член. Боксы geohash выровнены по сетке и квадратные, поэтому они неточны: первый проход собирает N кандидатов внутри боксов, а второй отфильтровывает их до M элементов в пределах точного радиуса.

### Redis для event sourcing

Redis streams — это append-only логи, похожие на topics в Kafka, и они служат строительным блоком для event-sourced архитектур, где ты хранишь упорядоченный лог событий и выводишь из него состояние. Producers добавляют записи командами вроде XADD, а consumer groups (XREADGROUP, XCLAIM) координируют, какой consumer обрабатывает какую запись. Одно предостережение, прежде чем опираться на слово «лог»: записи в stream долговечны ровно настолько, насколько позволяют настройки persistence, поэтому с настройками по умолчанию при сбое можно потерять последние записи. Это тот же компромисс, что и во врезке про durability в начале страницы.

![Иллюстрация](/content/deep-dives--redis/4f95ba647a.svg)

Redis streams и consumer groups

Work queue хорошо показывает, как эти части складываются вместе. Мы добавляем элементы в очередь через XADD и привязываем к stream одну consumer group для наших воркеров. В штатном сценарии воркер читает элемент через XREADGROUP, обрабатывает его и подтверждает. Consumer group отслеживает, какие элементы за каким воркером числятся как pending, и у каждой pending-записи есть idle time. Если воркер умирает посреди задачи, idle time его записи продолжает расти, пока другой воркер не заберёт её через XCLAIM (или XAUTOCLAIM) и не перезапустит работу. Этот же механизм означает, что элемент иногда может быть обработан дважды: Redis не может отличить медленный воркер от мёртвого. Делай обработку идемпотентной.

Так когда вместо этого нужен Kafka? Redis streams отлично подходят, если Redis уже есть в твоей архитектуре, а очередь скромная: фоновые задачи, fan-out уведомлений, распределение работы. Kafka оправдывает свою операционную сложность, когда нужны долгое хранение, replay для множества независимых consumers или надёжный упорядоченный throughput в масштабе, где потеря сообщения недопустима.

### Redis для Pub/Sub

Streams нужны для consumers, которым надо нагнать пропущенное. Когда важно доставить сообщение только тем, кто слушает прямо сейчас, Redis из коробки поддерживает паттерн publish/subscribe (Pub/Sub): сообщения рассылаются нескольким подписчикам в реальном времени. Это полезно для чатов, real-time уведомлений и любых сценариев, где нужно развязать producers и consumers сообщений (подробнее об этом в нашем паттерне [Realtime Updates](/lessons/patterns/realtime-updates)).

Часто говорят об ограничениях Redis Pub/Sub, которые уже неверны. Главное из них: в классическом cluster Pub/Sub каждое сообщение рассылалось на каждую ноду, поэтому добавление нод не добавляло ёмкости. Начиная с Redis 7, sharded Pub/Sub (SPUBLISH/SSUBSCRIBE) направляет каждый канал на shard, которому принадлежит его slot, и ёмкость растёт вместе с кластером.

Базовые команды просты:

```
PUBLISH channel message   # Sends a message to all subscribers of 'channel'
SUBSCRIBE channel         # Listens for messages on 'channel'
```

В cluster mode тебе понадобятся sharded-варианты (SPUBLISH/SSUBSCRIBE), которые хешируют канал в slot так же, как любой ключ.

Канал — это просто имя. Ничего не нужно создавать или настраивать: publishers отправляют сообщения в канал по имени, subscribers слушают его, и именно это приводит канал к существованию. Когда клиент подписывается на канал, он получает все сообщения, опубликованные в этот канал, пока соединение остаётся открытым. Это делает Pub/Sub отличным выбором для эфемерной коммуникации в реальном времени, но сообщения не сохраняются: если subscriber был offline в момент публикации, он это сообщение полностью пропустит.

Накладные расходы на соединения возникают **на ноду, а не на канал**. Subscriber держит одно соединение с нодой и получает по нему все каналы, на которые подписан, так что миллионы каналов не означают миллионы соединений. В sharded Pub/Sub каждый канал хешируется в slot так же, как ключ, а значит, subscriber нужны соединения только с теми нодами, которым принадлежат интересующие его каналы.

![Иллюстрация](/content/deep-dives--redis/0d5925fd16.svg)

Redis Pub/Sub

Redis Pub/Sub прост и быстр, но не durable. Доставка сообщений работает по схеме «at most once»: если subscriber был offline в момент публикации, он это сообщение полностью пропустит. Если нужны сохранность сообщений, гарантии доставки или возможность replay пропущенных сообщений, рассмотри Redis Streams или специализированный message broker вроде Kafka или RabbitMQ.

Pub/Sub хорошо подходит для сценариев на интервью, где нужно продемонстрировать паттерны real-time коммуникации, но будь готов обсудить его ограничения и случаи, когда понадобятся более сильные гарантии доставки.

Нужна offline-доставка или durable fan-out? Redis Streams — хороший вариант, а ещё можно скомбинировать Pub/Sub с очередью (например, SNS→SQS, Kafka) или с паттерном outbox (то есть записывать сообщения в базу данных), чтобы consumers могли нагнать пропущенное позже.

#### Можно ли написать свой Pub/Sub?

Некоторые кандидаты отшатываются от идеи использовать нативный Pub/Sub в Redis из-за опасений по поводу масштабируемости. Беспокойство обычно возникает из-за недопонимания: они предполагают, что Pub/Sub использует соединение на каждый канал, а это не так. Типичное предложение выглядит так:

> Вместо Redis Pub/Sub мы создадим ключ для каждого topic, значением которого будет набор адресов серверов-подписчиков. Тогда, когда пользователь захочет опубликовать сообщение в этот topic, он сможет найти ключ и отправить сообщение напрямую на эти серверы.

Возможно, у такого подхода есть применения, но у него есть серьёзные минусы.

Во-первых, увеличивается число сетевых hops. С Pub/Sub путь отправки сообщения выглядит так:

```
1. Client sends message to Pub/Sub node
2. Pub/Sub node dispatches message to all subscribers
```

Два сетевых hop. С самописным Pub/Sub путь выглядит так:

```
1. Client requests subscribers for topic key from Redis
2. Redis responds with servers to contact
3. Client sends message to each server
```

Три сетевых hop. Последний hop самый дорогой, потому что, скорее всего, TCP-соединения с каждым subscriber у нас ещё нет. Когда мы настраиваем Pub/Sub-соединение, мы устанавливаем (и держим открытым) TCP-соединение с каждой нодой. Благодаря этому сообщение отправляется быстро. В самописном подходе нам нужно устанавливать эти новые соединения с каждым сервером перед отправкой.

Во-вторых, нужно учесть стоимость резидентной памяти. С Pub/Sub мы отслеживаем только каналы с активными subscribers. Когда отключается последний subscriber канала, канал удаляется из памяти, а последующие публикации в него просто отбрасываются. В самописном подходе, когда сервер падает, нам нужно каким-то образом узнать об этом, чтобы удалить запись из нашей map. Для этого может понадобиться какой-то heartbeat-механизм, где каждый сервер сообщает «эй, я всё ещё жив и слушаю этот topic», явно или через TTL. Это добавляет в систему много сложности и лишнего трафика, особенно если topics много.

В итоге: если у тебя сценарий, похожий на Pub/Sub, используй Pub/Sub!

## Недостатки и способы их устранения

### Проблема hot key

Если нагрузка на ключи в Redis cluster распределена неравномерно, мы можем столкнуться с проблемой, которую называют «hot key». Чтобы проиллюстрировать её, представим, что мы используем Redis для кеширования информации о товарах в интернет-магазине. Товаров много, поэтому мы масштабируем cluster до 100 нод, и товары равномерно распределены между ними. Пока всё хорошо. Теперь представь, что однажды вокруг *одного конкретного товара* возникает такой всплеск интереса, что объём запросов к нему сравнивается с объёмом запросов ко всем остальным товарам вместе взятым.

![Иллюстрация](/content/deep-dives--redis/a5763eae2b.svg)

Проблема hot key

Теперь нагрузка на *один сервер* заметно выше, чем на остальные. Если у нас не было большого запаса по мощности, этот сервер начнёт отказывать.

Есть много возможных решений, и у всех свои компромиссы.

**Client-side caching.** Каждый app server держит небольшой in-memory cache для самых «горячих» товаров, так что большинство чтений такого товара вообще не доходит до Redis. Цена за это — второй cache, который нужно поддерживать согласованным: ты будешь отдавать данные, устаревшие на срок до TTL этого cache. Поэтому такой подход лучше всего работает с короткими TTL на небольшом наборе ключей.

**Key copies.** Храни одни и те же данные под несколькими ключами (product:123:1 … product:123:10), чтобы копии попадали в разные slot и оказывались на разных нодах, а читатели выбирали суффикс случайно. При этом читатели должны знать, какие ключи дублируются. На практике ты заранее решаешь (или определяешь в runtime), какие ключи «горячие», и хранишь этот список там, где его видят клиенты, а каждая запись в «горячий» товар теперь разветвляется на все его копии.

**Read replicas.** Добавление replica умножает пропускную способность на чтение, но есть две оговорки, которые интервьюеры любят проверять. Клиенты cluster по умолчанию читают с primary, поэтому replica разгружают систему, только если клиенты настроены на чтение с replica. И replica ничем не помогают, если hot key «горячий» по записи: каждая запись всё равно попадает на единственный primary, которому принадлежит slot.

На собеседовании распознай потенциальные проблемы hot key (+) и сам заранее спроектируй способы их устранения (++).

Все эти техники (и не только) мы разбираем в паттернах [Scaling Reads](/lessons/patterns/scaling-reads) и [Scaling Writes](/lessons/patterns/scaling-writes).

### Когда не стоит использовать Redis

Обозначим границу прямо. Не делай Redis своей system of record: из-за асинхронной репликации и окон потери данных при persistence подтверждённые записи могут пропасть. Не берись за него, если рабочий набор данных экономически не помещается в RAM: память — самое дорогое место для хранения данных. Не рассчитывай на гибкость запросов: здесь нет join, нет запросов по нескольким ключам, а в cluster операции с несколькими ключами работают только внутри одного slot (hash tags не в счёт). А когда нужны надёжные, воспроизводимые streams с долгим retention для множества независимых consumer, это работа для Kafka.

## Итоги

Redis — мощный, универсальный и простой инструмент, который можно использовать на собеседованиях по system design. Поскольку возможности Redis построены на простых структурах данных, последствия своих решений для масштабирования понять несложно: это позволяет углубиться в тему с интервьюером, не зная много деталей внутреннего устройства Redis.

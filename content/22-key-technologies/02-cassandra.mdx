Как использовать Cassandra на собеседованиях по system design: моделирование данных через partition key и clustering key, tunable consistency и когда стоит выбирать её вместо других баз данных.

Базы данных — фундаментальная и центральная часть system design, а одна из самых универсальных и популярных баз, которые стоит иметь в арсенале, — это [Cassandra](https://cassandra.apache.org/_/index.html). Cassandra изначально создали в Facebook для быстро растущей функции поиска по входящим сообщениям. С тех пор её взяли на вооружение [бесчисленные компании](https://cassandra.apache.org/_/case-studies.html), чтобы быстро масштабировать хранение данных, throughput и чтение. От Discord (разберём его ниже в этой статье) до Netflix, Apple и Bloomberg: Cassandra — это NoSQL-база данных, которая никуда не денется, и её используют самые разные компании для очень широкого круга задач.

Apache Cassandra — распределённая NoSQL-база данных с открытым исходным кодом. Она реализует partitioned wide-column модель хранения с eventually consistent семантикой. Это распределённая база, которая работает в кластере и масштабируется горизонтально на обычном (commodity) железе. Она сочетает идеи Dynamo (см. наш разбор [DynamoDB](/lessons/key-technologies/dynamodb)) и [Bigtable](https://static.googleusercontent.com/media/research.google.com/en//archive/bigtable-osdi06.pdf), чтобы справляться с огромными объёмами данных, большим числом запросов и гибкими требованиями к хранению.

В этом deep dive мы разберём возможности Cassandra, которые делают её привлекательной базой, особенно для system design. Мы обсудим самые важные внутренние механизмы Cassandra, чтобы понять, как она эти возможности обеспечивает. И наконец, поговорим о том, когда и как её использовать. Поехали!

## Основы Cassandra

Начнём с базовых понятий.

### Модель данных

В Cassandra есть набор базовых определений, которые задают, как ты хранишь данные и работаешь с ними.

* **Keyspace** — организационная единица верхнего уровня в Cassandra, аналог «базы данных» в реляционных системах вроде Postgres или MySQL. Keyspace задаёт стратегии репликации (о них позже) для управления избыточностью и доступностью данных. Ему также принадлежат все user-defined types (UDT), которые ты создаёшь.
* **Table** — живёт внутри keyspace и организует данные в строки. У каждой таблицы есть схема, определяющая её колонки и структуру primary key.
* **Row** — одна запись в таблице, идентифицируемая primary key. Каждая строка хранит значения в нескольких колонках.
* **Column** — собственно единица хранения данных. У колонки есть имя, тип и значение для конкретной строки. Не обязательно указывать все колонки в каждой строке таблицы Cassandra. Cassandra — это [wide-column база данных](https://www.scylladb.com/glossary/wide-column-database/), поэтому набор заданных колонок может отличаться от строки к строке. Из-за этого Cassandra гибче реляционных баз, где для каждой строки нужна запись в каждой колонке (даже если это NULL). Кроме того, у каждой колонки есть метаданные с timestamp, показывающие, когда она была записана. Если возникает конфликт записи колонки между replica, он разрешается по принципу «last write wins».

### Primary Key

Одна из важнейших конструкций в Cassandra — «primary key» таблицы. Каждая строка идентифицируется primary key. Primary key состоит из одного или нескольких partition key и может включать clustering key. Разберём, что означают эти термины.

* **Partition Key** — одна или несколько колонок, по которым определяется, в какой partition находится строка. О разбиении данных на partition мы поговорим позже в этом deep dive.
* **Clustering Key** — ноль или более колонок, определяющих порядок сортировки строк в таблице. Порядок данных важен в зависимости от потребностей моделирования, поэтому Cassandra даёт пользователям контроль над ним через clustering key.

Когда ты создаёшь таблицу в Cassandra через диалект Cassandra Query Language (CQL), primary key указывается как часть определения схемы. Ниже несколько примеров разных primary key с комментариями в коде:

```
-- Primary key with partition key a, no clustering keys
CREATE TABLE t (a text, b text, c text, PRIMARY KEY (a));

-- Primary key with partition key a, clustering key b ascending
CREATE TABLE t (a text, b text, c text PRIMARY KEY ((a), b))
WITH CLUSTERING ORDER BY (b ASC);

-- Primary key with composite partition key a + b, clustering key c
CREATE TABLE t (a text, b text, c text, d text, PRIMARY KEY ((a, b), c));

-- Primary key with partition key a, clustering keys b + c
CREATE TABLE t (a text, b text, c text, d text, PRIMARY KEY ((a), b, c));

-- Primary key with partition key a, clustering keys b + c (alternative syntax)
CREATE TABLE t (a text, b text, c text, d text, PRIMARY KEY (a, b, c));
```

Концепция primary key и её составляющие могут напомнить тебе [определение primary key в DynamoDB](/lessons/key-technologies/dynamodb). Эта концепция в обеих базах практически совпадает 1:1.

## Ключевые концепции

Когда ты вводишь Cassandra в ответе на system design интервью, одного умения ей пользоваться недостаточно. Нужно уметь объяснить, как она устроена, на случай если интервьюер начнёт задавать точечные вопросы, или если ты захочешь углубиться в детали хранения данных, scalability, эффективность запросов и так далее. Всё это влияет на твой дизайн. В этом разделе мы разберём важнейшие детали Cassandra, чтобы дать тебе нужный контекст.

### Partitioning

Один из фундаментальных аспектов Cassandra — схема partitioning данных. Техники partitioning в Cassandra очень надёжны, и их стоит понимать в целом для system design, чтобы применять в других частях дизайна (caching, load balancing и т. д.).

Cassandra достигает горизонтальной масштабируемости, разбивая данные на partition между многими узлами кластера. Для этого она использует [consistent hashing](/lessons/core-concepts/consistent-hashing). Consistent hashing — фундаментальная техника распределённых систем для разделения данных и нагрузки между машинами: она в первую очередь обеспечивает равномерность распределения и при этом минимизирует перемещение данных, когда узел входит в систему или покидает её.

В традиционной схеме хеширования выбирается число узлов, а узел для хранения значения определяется так: hash(value) % num\_nodes. Это, конечно, распределяет значения по узлам, но есть две проблемы:

1. Если число бакетов меняется (узел добавили или убрали), многие значения получат новые узлы. В распределённой системе вроде базы данных это означало бы чрезмерное перемещение данных между узлами.
2. Если со схемой хеширования не повезёт, много значений может попасть на один и тот же узел, и нагрузка между узлами будет неравномерной.

Чтобы это улучшить, consistent hashing использует другой подход.

Вместо того чтобы хешировать значение и брать остаток от деления для выбора узла, consistent hashing хеширует значение в диапазон целых чисел, который представляют в виде кольца. На кольце узлы соответствуют определённым значениям. Когда значение хешируется, получается целое число. Затем по кольцу идут по часовой стрелке до первого значения, соответствующего узлу. Значение хранится на этом узле.

![Иллюстрация](/content/deep-dives--cassandra/bffeca5250.svg)

Такая схема предотвращает чрезмерное перемещение значений при входе узла в систему или выходе из неё, потому что затрагивается один соседний узел. Если узел добавляется, он забирает часть значений у узла, следующего за ним при движении по кольцу по часовой стрелке. Если узел уходит, его значения переходят к следующему за ним узлу при движении по часовой стрелке.

Однако эта схема не решает проблему неравномерной нагрузки между узлами. Чтобы решить её, Cassandra сопоставляет физическим узлам распределённой системы сразу несколько узлов на кольце. Узлы на кольце называются vnodes (они же virtual nodes) и принадлежат физическим узлам. Так нагрузка распределяется по кластеру равномернее. Это также позволяет системе использовать ресурсы разных физических узлов: некоторые физические узлы могут быть более мощными машинами с большим количеством ресурсов, поэтому они могут отвечать за большее число vnodes. Ниже показано, как может выглядеть кластер: значения, называемые «токенами» (t1, t2 и т. д.), расположены на кольце, vnodes сопоставлены этим токенам, а разные физические узлы обозначены цветами vnodes.

### Replication

В Cassandra partition данных реплицируются на узлы кольца, благодаря чему она отлично подходит для дизайнов, которым нужна высокая доступность. Для keyspace задаются настройки replication, и они влияют на то, как Cassandra реплицирует данные.

На высоком уровне Cassandra выбирает узлы для replication данных, двигаясь по часовой стрелке от vnode, соответствующего хешу значения в схеме consistent hashing. Например, если Cassandra реплицирует данные на 3 узла, она хеширует значение в узел и идёт по часовой стрелке, чтобы найти ещё 2 vnodes, которые станут replica. Cassandra пропускает vnodes, находящиеся на том же физическом узле, что и vnodes, уже включённые в набор replica, чтобы при отказе одного физического узла не оказалось недоступно сразу несколько replica.

![Иллюстрация](/content/deep-dives--cassandra/e7655fe5d6.svg)

Replication

У Cassandra есть две «стратегии replication»: [NetworkTopologyStrategy](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html#network-topology-strategy) и [SimpleStrategy](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html#simple-strategy).

NetworkTopologyStrategy рекомендуется для production. Она учитывает дата-центры и стойки (rack), поэтому replica данных могут храниться в нескольких дата-центрах на случай аварии. Она также позволяет размещать replica на разных стойках на случай отказа стойки в дата-центре. Главная цель этой конфигурации — обеспечить достаточное физическое разделение replica, чтобы реальная авария или инцидент не затронул сразу многие из них.

SimpleStrategy проще: replica определяются просто движением по кольцу по часовой стрелке (именно её мы разбирали выше). Она подходит для простых развёртываний и тестирования.

Ниже приведён Cassandra CQL для задания разных конфигураций стратегий replication для keyspace:

```
-- 3 replicas
ALTER KEYSPACE hello_interview WITH REPLICATION = { 'class' : 'SimpleStrategy', 'replication_factor' : 3 };

-- 3 replicas in data center 1, 2 replicas in data center 2
ALTER KEYSPACE hello_interview WITH REPLICATION = {'class' : 'NetworkTopologyStrategy', 'dc1' : 3, 'dc2' : 2};
```

### Consistency

Как и любая распределённая система, Cassandra подчиняется [CAP Theorem](https://www.geeksforgeeks.org/the-cap-theorem-in-dbms/). Cassandra даёт гибкость в настройке consistency для чтения и записи, что позволяет «тюнить» компромисс между consistency и availability. Поскольку любой system design включает тот или иной анализ CAP theorem и компромиссы, важно понимать, какими рычагами ты располагаешь в Cassandra.

Cassandra не поддерживает транзакции и не даёт никаких ACID-гарантий. Она поддерживает только атомарные и изолированные записи на уровне строки внутри partition, и на этом всё. Подробнее можно прочитать [здесь](https://docs.datastax.com/en/cassandra-oss/2.2/cassandra/dml/dmlTransactionsDiffer.html).

Cassandra позволяет выбирать из набора «уровней consistency» для чтения и записи — это требуемое количество ответов узлов, чтобы запись или чтение считались успешными. В зависимости от используемой комбинации они обеспечивают разное соотношение consistency и availability. Диапазон от ONE, где должна ответить одна replica, до ALL, где должны ответить все replica. Подробнее об уровнях consistency можно прочитать [здесь](https://cassandra.apache.org/doc/latest/cassandra/architecture/dynamo.html#tunable-consistency).

Один из важных уровней consistency — QUORUM. QUORUM требует ответа большинства (n/2 + 1) replica. Применение QUORUM и к чтению, и к записи гарантирует, что записи видны при чтении, потому что хотя бы один общий узел обязательно участвует и в записи, и в чтении. Для наглядности возьмём набор из 3 узлов. 3/2 + 1 = 2, значит, для успеха записи и чтения нужно записать на 2 из 3 узлов и прочитать с 2 из 3 узлов. Это значит, что запись всегда будет видна при чтении, потому что хотя бы 1 из этих 2 узлов тоже видел запись.

![Иллюстрация](/content/deep-dives--cassandra/f926849854.svg)

Как правило, Cassandra стремится к «eventual consistency» для всех уровней consistency: все replica получают актуальные данные, если проходит достаточно времени.

### Query Routing

Любой узел Cassandra может обработать запрос клиентского приложения, потому что каждый узел может выступать в роли «coordinator» запроса. Каждый узел Cassandra знает о других живых узлах кластера. Информацией о кластере они обмениваются по протоколу «gossip» (о нём позже). Узлы Cassandra также могут определить, где в кластере лежат данные: они выполняют вычисления consistent hashing и знают стратегию replication и уровень consistency, настроенные для этих данных. Когда клиент отправляет запрос, он выбирает узел, который становится coordinator, а coordinator отправляет запросы узлам, хранящим данные (набору replica).

### Модель хранения

Модель хранения Cassandra важно понимать, потому что на ней держится одна из её сильных сторон для system design: write throughput. Для такой скорости Cassandra использует индекс на основе структуры данных [Log Structured Merge Tree (LSM tree)](https://hackernoon.com/how-cassandra-stores-data-an-exploration-of-log-structured-merge-trees). LSM tree используется вместо B-tree, который является индексом по умолчанию для большинства баз данных (реляционные БД, DynamoDB).

Прежде чем переходить к деталям, важно объяснить, чем обработка записи в Cassandra отличается от других баз данных. Cassandra выбирает подход, при котором скорость записи важнее скорости чтения. Каждая операция create / update / delete превращается в новую запись (с некоторыми исключениями). Cassandra определяет «состояние» строки по порядку этих обновлений. Например, если строку создали, а потом обновили, Cassandra поймёт её состояние, посмотрев на создание и на последующее обновление, а не на одну-единственную строку. С удалениями то же самое: их можно считать «обновлениями-удалениями». При удалении строки Cassandra пишет запись «tombstone». LSM tree позволяет Cassandra эффективно определять состояние строки, при этом данные попадают в базу почти исключительно через «append only» записи.

Три конструкции, на которых держится индекс LSM tree:

1. **Commit Log** — по сути, [write-ahead log](https://en.wikipedia.org/wiki/Write-ahead_logging), который гарантирует durability записей на нодах Cassandra.
2. **Memtable** — отсортированная in-memory структура данных, в которой хранятся записываемые данные. Сортировка идёт по primary key каждой строки.
3. **SSTable** — она же «Sorted String Table». Неизменяемый (immutable) файл на диске с данными, сброшенными из предыдущей Memtable.

Когда все эти конструкции работают вместе, запись выглядит так:

1. Запись поступает на ноду.
2. Она записывается в commit log, чтобы не потеряться, если нода упадёт во время обработки записи или когда данные лежат только в Memtable.
3. Запись попадает в Memtable.
4. Когда достигнут пороговый размер или прошло определённое время, Memtable сбрасывается (flush) на диск в виде immutable SSTable.
5. При flush Memtable из commit log удаляются все сообщения, относящиеся к этой Memtable, чтобы экономить место. Они больше не нужны: Memtable уже лежит на диске в виде immutable SSTable.

На диаграмме ниже показаны эти шаги:

![Иллюстрация](/content/deep-dives--cassandra/be83433880.svg)

Модель хранения

Подведём итог: Memtable хранит свежие записи, объединяя записи по ключу в одну строку, и время от времени сбрасывается на диск как immutable SSTable. Commit log служит write-ahead log и гарантирует, что данные не потеряются, если они есть только в Memtable, а нода упала.

При чтении данных по конкретному ключу Cassandra сначала смотрит в Memtable, где лежат самые свежие данные. Если там данных по ключу нет, Cassandra с помощью [bloom filter](https://en.wikipedia.org/wiki/Bloom_filter) определяет, в каких SSTable на диске они могут быть. Затем она читает SSTable от новых к старым, чтобы найти актуальные данные строки. Данные в SSTable отсортированы по primary key, поэтому найти нужный ключ легко.

Поверх этого фундамента стоит усвоить ещё два понятия:

* **Compaction** — чтобы SSTable не разрастались из-за множества обновлений и удалений строк, Cassandra запускает compaction: данные объединяются в меньший набор SSTable, отражающих консолидированное состояние. Compaction также удаляет строки, которые были удалены, и вместе с ними убирает tombstone, существовавшие для этих строк. Процесс особенно эффективен, потому что все эти таблицы отсортированы.
* **SSTable Indexing** — Cassandra хранит файлы, указывающие на byte offset в файлах SSTable, чтобы быстрее читать данные с диска. Например, Cassandra может сопоставить ключ 12 с byte offset 984, то есть данные для ключа 12 лежат в SSTable по этому смещению. Это отчасти похоже на то, как B-tree указывает на данные на диске.

Подробнее про LSM tree читай в [этой статье](https://hackernoon.com/how-cassandra-stores-data-an-exploration-of-log-structured-merge-trees).

### Gossip

Ноды Cassandra обмениваются информацией по всему кластеру через «gossip» — peer-to-peer схему распространения информации между нодами. Когда у каждой ноды есть полная картина кластера, любая из них может участвовать во всех операциях базы. Это убирает любые single points of failure и делает Cassandra очень надёжной базой для систем, ориентированных на availability. Как это работает?

Ноды отслеживают разную информацию о кластере: какие ноды живы и доступны, какая у кластера schema и так далее. Для каждой известной ноды они ведут generation и version. Generation — это timestamp момента bootstrap ноды. Version — значение логических часов, которое увеличивается примерно раз в секунду. По всему кластеру эти значения образуют [vector clock](https://en.wikipedia.org/wiki/Vector_clock). Благодаря этому vector clock ноды могут игнорировать устаревшую информацию о состоянии кластера, полученную через gossip.

Ноды Cassandra регулярно выбирают, с какими другими нодами обменяться gossip, причём с вероятностным уклоном в сторону «seed»-нод. Seed-ноды назначаются Cassandra, чтобы выполнять bootstrap кластера, и служат гарантированными «hotspots» для gossip, чтобы все ноды общались по всему кластеру. Создавая такие «узкие места» (choke points), Cassandra исключает ситуацию, когда образуются суб-кластеры нод из-за того, что информация случайно не дошла до всего кластера. Cassandra следит, чтобы seed-ноды всегда можно было найти с помощью стандартных [механизмов service discovery](https://middleware.io/blog/service-discovery/).

### Отказоустойчивость

В распределённой системе вроде Cassandra ноды отказывают, и Cassandra должна эффективно обнаруживать и обрабатывать сбои, чтобы база могла эффективно записывать и читать данные. Как ей удаётся добиться этого в большом масштабе?

Для обнаружения сбоев во время gossip Cassandra использует технику [Phi Accrual Failure Detector](https://www.computer.org/csdl/proceedings-article/srds/2004/22390066/12OmNvT2phv): каждая нода самостоятельно решает, доступна другая нода или нет. Когда нода обменивается gossip с нодой, которая не отвечает, логика обнаружения сбоев Cassandra «осуждает» (convicts) эту ноду и перестаёт направлять на неё записи. Осуждённая нода может вернуться в кластер, когда снова начнёт отправлять heartbeat. Cassandra считает осуждённую ноду недоступной, но оставляет её в ring, пока администратор явно не изменит топологию. Это сделано для того, чтобы кратковременные сбои связи и перезапуски нод не приводили к ребалансировке данных в кластере.

Если записи направляются на ноды, которые считаются «offline», Cassandra использует технику «hinted handoffs». Когда coordinator-нода, пытающаяся записать данные, считает целевую ноду offline, она временно сохраняет данные записи у себя, чтобы запись могла пройти. Эти временные данные называются «hint». Когда offline-нода снова определяется как online, нода (или ноды), у которой есть hint, отправляет эти данные ранее недоступной ноде. Ниже показано, как это выглядит на практике.

Hinted handoffs в основном используются как краткосрочный способ уберечь offline-ноду от потери записей. Любая нода, которая долго остаётся offline, будет либо перестроена (rebuilt), либо пройдёт read repairs, потому что hints обычно живут недолго.

## Как использовать Cassandra

### Моделирование данных

Когда ты используешь Cassandra в system design, очень важно моделировать данные так, чтобы опираться на её архитектуру и сильные стороны.

Если ты пришёл из мира реляционных баз данных, моделирование данных в Cassandra поначалу может показаться странным. Реляционное моделирование строится вокруг «нормализованных» данных: у тебя есть одна копия каждого экземпляра *сущности*, а *связями* между сущностями ты управляешь через foreign key и JOIN-таблицы. Короче говоря, моделирование данных для реляционной базы *строится вокруг сущностей и связей между ними*. Однако в Cassandra нет понятия foreign key и ссылочной целостности, нет JOIN и так далее. Cassandra также не поощряет нормализацию данных. Вместо этого моделирование данных для Cassandra *строится вокруг запросов*.

Эффективность запросов в Cassandra сильно зависит от того, как хранятся данные. Кроме того, ей не хватает гибкости запросов, которая есть у реляционных баз: она не поддерживает JOIN и обслуживает запросы только к одной таблице. Поэтому, продумывая модель данных для Cassandra, в первую очередь нужно учитывать паттерны доступа («access patterns») приложения. Также важно понимать, какие данные нужны в каждой таблице, чтобы при необходимости «денормализовать» их (дублировать) между таблицами. Основные аспекты, которые нужно учесть:

* **Partition Key** — какие данные определяют partition, в котором лежат данные.
* **Partition Size** — насколько велик partition в самом экстремальном случае, может ли он расти бесконечно и так далее.
* **Clustering Key** — как нужно сортировать данные (и нужно ли вообще).
* **Data Denormalization** — нужно ли денормализовать некоторые данные между таблицами, чтобы поддержать запросы приложения.

Чтобы лучше это прочувствовать, полезно разобрать несколько примеров.

#### Пример: сообщения в Discord

Один из лучших способов научиться пользоваться инструментом вроде Cassandra — разобрать реальный пример, такой как Discord. Discord опубликовал хороший обзор того, как они используют Cassandra для хранения сообщений, [в своих блог-постах](https://discord.com/blog/how-discord-stores-billions-of-messages), и это хорошая модель того, как можно подходить к хранению сообщений в чат-приложениях в целом.

В каналах Discord бывает очень много сообщений. Пользователи обычно запрашивают свежие данные, ведь канал — это по сути большой групповой чат. Пользователь может загрузить последние сообщения и немного прокрутить вверх, поэтому сортировка данных в обратном хронологическом порядке имеет смысл.

Чтобы обслужить эти потребности, Discord изначально создал таблицу messages со следующей схемой:

```
CREATE TABLE messages (
  channel_id bigint,
  message_id bigint,
  author_id bigint,
  content text,
  PRIMARY KEY (channel_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

Ты можешь спросить: почему используется message\_id, а не столбец с временной меткой вроде created\_at? Discord решил исключить возможность конфликтов primary key в Cassandra, присваивая сообщениям [Snowflake ID](https://blog.x.com/engineering/en_us/a/2010/announcing-snowflake). Snowflake ID — это по сути UUID, который можно сортировать по времени. Он лучше, чем created\_at, потому что коллизия Snowflake ID невозможна (это UUID), тогда как у временной метки, даже с точностью до миллисекунды, есть вероятность коллизии.

Эта схема позволяет Cassandra обслуживать сообщения канала через *один partition*. Partition key, channel\_id, гарантирует, что запрос обрабатывает один partition, и не нужно делать «scatter-gather» запрос по нескольким нодам, чтобы получить сообщения канала, что могло бы быть медленным и ресурсоёмким.

Однако эта схема не полностью удовлетворяла потребности Discord. В некоторых каналах Discord иногда бывает чрезвычайно большой объём сообщений. Со схемой выше Discord заметил, что Cassandra с трудом справляется с большими partition, соответствующими загруженным каналам. У больших partition в Cassandra обычно возникают проблемы с производительностью, и именно это и наблюдал Discord. Кроме того, каналы Discord постоянно растут вместе с активностью, и при достаточно долгой жизни рано или поздно столкнулись бы с проблемами производительности. Схему нужно было изменить.

Чтобы решить проблему больших partition, Discord ввёл понятие bucket и добавил его в часть primary key Cassandra, отвечающую за partition key. Bucket представлял 10 дней данных, определённых фиксированным окном, отсчитываемым от собственной эпохи Discord, DISCORD\_EPOCH, равной 1 января 2015 года. Сообщения даже самых загруженных каналов Discord за 10 дней наверняка поместятся в один partition Cassandra. Это также решило проблему монотонного роста partition: со временем появлялся новый partition, потому что создавался новый bucket. Наконец, Discord в большинстве случаев мог обслуживать запросы к одному partition, потому что самые свежие сообщения канала обычно лежали в одном bucket. Исключения — это 1) создание нового bucket по мере течения времени и 2) неактивные каналы Discord, на которые приходилась значительно меньшая часть запросов к таблице messages в Cassandra.

Обновлённая схема выглядит так:

```
CREATE TABLE messages (
  channel_id bigint,
  bucket int,
  message_id bigint,
  author_id bigint,
  content text,
  PRIMARY KEY ((channel_id, bucket), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

Примечательно, что Discord опирался на паттерны доступа к каналам, чтобы определить дизайн схемы, — отличный пример *моделирования данных, управляемого запросами*. Выбор primary key, включающего и partition key, и clustering key, тесно связан с тем, как приложение обращается к данным. Наконец, им пришлось подумать о размере partition при проектировании схемы. Все эти факторы учитываются при построении хорошей схемы Cassandra в system design в целом.

#### Пример: Ticketmaster

Рассмотрим ещё один пример использования Cassandra: интерфейс просмотра билетов в Ticketmaster. Это UI, который показывает свободные места на площадке мероприятия и позволяет пользователю выбрать места, а затем перейти к оформлению заказа и оплате.

Интерфейсу просмотра билетов в Ticketmaster не нужна строгая консистентность. Доступность билетов на мероприятие меняется, даже пока пользователь смотрит на UI. Если место выбрано и начат процесс покупки, система может проверить в консистентной базе данных, *действительно* ли место свободно. Кроме того, важно, чтобы UI просмотра работал всегда, ведь большинство пользователей просто смотрят, а лишь меньшинство доходит до оформления заказа.

Этот пример задуман простым и сфокусированным на моделировании данных, поэтому мы опускаем сложности, которые создают чрезвычайно популярные мероприятия (их назвали [«The Taylor Swift Problem»](https://www.educative.io/blog/taylor-swift-ticketmaster-meltdown)).

Размышляя, как смоделировать данные для UI просмотра билетов, можно считать «билетом» каждое место мероприятия. Если подумать о паттернах доступа нашей системы, станет ясно, что пользователи запрашивают данные по одному мероприятию за раз и хотят видеть как итоговое количество свободных мест, так и сами места. Порядок отображения мест пользователям не важен, ведь у них есть карта площадки, которая определяет, как они видят доступность мест. Первая версия схемы может выглядеть так:

```
CREATE TABLE tickets (
  event_id bigint,
  seat_id bigint,
  price bigint,
  -- seat_id is added as a clustering key to ensure primary key uniqueness; order
  -- doesn't matter for the app access patterns
  PRIMARY KEY (event_id, seat_id)
);
```

Со схемой выше приложение может обслуживать запросы о мероприятии через один partition, поскольку primary key имеет partition key event\_id. Приложение может запрашивать у partition информацию о ценах на мероприятие, суммарное количество доступных билетов и так далее.

Но у этой схемы есть проблемы. Для мероприятий с 10 000+ билетов базе данных нужно проделывать работу по подведению сводной информации на основе запроса пользователя (общая цена, общее количество билетов). Более того, эта работа может выполняться *очень часто* для популярных мероприятий, в UI просмотра билетов которых постоянно заходят пользователи. Как можно решить эти проблемы?

Одна из подсказок, как улучшить схему, скрыта в пользовательском опыте (UX) интерфейса просмотра билетов Ticketmaster. Представь, как это выглядит, когда пользователь начинает просматривать билеты. Он видит карту площадки с секциями. У каждой секции может быть всплывающее окно с общей информацией о доступности и ценах билетов в этой секции.

Если пользователь нажимает на интересующую секцию, UI Ticketmaster показывает отдельные места и информацию о билетах.

Этот UX подсказывает, что в таблицу tickets можно добавить понятие section\_id и сделать section\_id частью partition key. Это значит, что таблица tickets теперь обслуживает запрос на просмотр билетов отдельных мест в заданной секции. Новая схема выглядит так:

```
CREATE TABLE tickets (
  event_id bigint,
  section_id bigint,
  seat_id bigint,
  price bigint,
  PRIMARY KEY ((event_id, section_id), seat_id)
);
```

Эта схема лучше исходной. Она распределяет мероприятие по нескольким нодам кластера Cassandra, потому что каждая секция мероприятия лежит в отдельном partition. Это также значит, что каждый partition обслуживает меньше данных, поскольку количество билетов в partition ниже. Наконец, эта схема лучше соответствует потребностям в данных и паттернам доступа UI просмотра билетов Ticketmaster.

Ты можешь спросить: как теперь показать данные о билетах по всему мероприятию? Чтобы обслужить UI, который показывает все секции и общую информацию о доступности и ценах билетов, можно рассмотреть отдельную таблицу event\_sections.

```
CREATE TABLE event_sections (
  event_id bigint,
  section_id bigint,
  num_tickets bigint,
  price_floor bigint,
  -- section_id is added as a clustering key to ensure primary key uniqueness; order
  -- doesn't matter for the app access patterns
  PRIMARY KEY (event_id, section_id)
);
```

Таблица выше иллюстрирует идею «денормализации» данных в Cassandra. Вместо того чтобы заставлять базу делать агрегацию по таблице или опрашивать несколько таблиц / partition ради обслуживания приложения, лучше денормализовать информацию, например количество билетов и минимальную цену в секции, чтобы паттерн доступа для приложения был эффективным. Кроме того, статистика по секциям не обязана быть сверхточной: здесь допустима eventual consistency. Более того, Ticketmaster вообще не показывает в UI точное число билетов, а лишь общее значение вроде 100+.

Таблица выше партиционирована по event\_id. Cassandra придётся читать много секций одним запросом, но у событий число секций невелико (обычно &lt; 100), и этот запрос будет обслужен из одной partition. Значит, Cassandra может эффективно получить данные для отображения верхнеуровневого вида площадки.

В целом это показывает, как сильно паттерны доступа приложения и его UX влияют на моделирование данных в Cassandra.

## Продвинутые возможности

Помимо базовых сценариев использования Cassandra, стоит знать о некоторых продвинутых возможностях, которые у тебя есть. Ниже краткий список основных.

* **Storage Attached Indexes (SAI)** - SAI это относительно новая возможность Cassandra, которая даёт глобальные вторичные индексы по колонкам. Они позволяют гибко запрашивать данные: производительность хуже, чем при традиционных запросах по partition key, но всё же хорошая. Благодаря им пользователям Cassandra не приходится чрезмерно денормализовать данные ради менее частых паттернов запросов. Редкие запросы обычно не оправдывают накладные расходы на отдельную денормализованную таблицу. Подробнее можно почитать [здесь](https://cassandra.apache.org/doc/latest/cassandra/developing/cql/indexing/sai/sai-concepts.html).
* **Materialized Views** - Materialized views позволяют настроить Cassandra так, чтобы она материализовала таблицы на основе исходной таблицы. Они отчасти похожи на [SQL views](https://www.geeksforgeeks.org/sql-views/), только здесь таблица действительно «материализуется», отсюда и название. Это удобно: Cassandra может автоматически денормализовать данные за тебя. Так снижается сложность на уровне приложения: не нужно писать код, который записывает в несколько таблиц при изменении денормализованных данных. Подробнее о materialized views можно почитать [здесь](https://www.geeksforgeeks.org/sql-views/).
* **Search Indexing** - Cassandra можно подключить к распределённому поисковому движку, такому как ElasticSearch или Apache Solr, с помощью разных плагинов. Один из примеров: Stratio Lucene Index. Подробнее о нём можно почитать [здесь](https://cassandra.apache.org/doc/latest/cassandra/integrating/plugins/index.html#stratios-cassandra-lucene-index).

## Cassandra на интервью

### Когда использовать

Cassandra может быть отличным выбором для систем, которые опираются на её сильные стороны. Она хорошо подходит системам, где availability важнее consistency и есть высокие требования к масштабируемости. Cassandra быстро пишет и читает в больших масштабах, но особенно хороша для систем с высоким write throughput благодаря оптимизированному под запись слою хранения на основе LSM tree. Кроме того, wide-column дизайн Cassandra делает её отличным выбором для гибких схем или схем со множеством колонок, которые могут быть разреженными. Наконец, Cassandra раскрывается там, где у приложения или сценария есть несколько чётких паттернов доступа, вокруг которых можно строить схему.

### Ограничения

Cassandra подходит не для каждой системы. Она плохо подходит для дизайнов, где в приоритете строгая consistency, учитывая её сильный уклон в сторону availability. Также Cassandra не годится для систем, которым нужны сложные паттерны запросов, такие как JOIN по нескольким таблицам, ad hoc агрегации и т. п.

## Итоги

Надеюсь, теперь ты видишь, почему Cassandra — очень универсальный инструмент для распределённых систем. У неё отличный набор возможностей, но она не обязательно подходит каждой системе. Используя её, важно придерживаться подхода к моделированию данных, ориентированного на запросы (query-driven), чтобы получить максимум от Cassandra в плане скорости записи/чтения и масштабируемости. Когда ты погружаешься в детали system design, знание внутреннего устройства Cassandra играет ключевую роль в умении правильно использовать эту базу данных.

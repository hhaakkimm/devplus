Узнай, когда и как использовать PostgreSQL на собеседованиях по system design

Скорее всего, на собеседовании по system design тебе придётся обсуждать PostgreSQL. Неудивительно: в [опросе разработчиков Stack Overflow](https://survey.stackoverflow.co/2023/#section-most-popular-technologies-databases) эта база данных стабильно признаётся самой любимой, а пользуются ею компании от Reddit до Instagram, и даже сайт, который ты сейчас читаешь.

При этом важно понимать: хотя в PostgreSQL много функциональности и возможностей, интервьюер ищет не администратора баз данных. Ему нужно увидеть, что ты умеешь принимать взвешенные архитектурные решения. Когда стоит выбирать PostgreSQL? Когда лучше поискать что-то другое? Какие trade-offs нужно учитывать?

Я часто вижу, что кандидаты здесь спотыкаются. Они либо слишком глубоко уходят во внутреннее устройство PostgreSQL (рассказывают про MVCC и WAL, хотя интервьюеру нужно лишь понять, справится ли база с связями между данными), либо делают слишком общие заявления вроде «NoSQL масштабируется лучше, чем PostgreSQL», не вникая в нюансы.

В этом deep dive мы сосредоточимся на том, что нужно знать о PostgreSQL для собеседований по system design. Начнём с практического примера, разберём ключевые возможности и ограничения, которые должны влиять на твой выбор, и дойдём до типичных сценариев с собеседований.

Для этого deep dive мы предполагаем, что ты знаком с основами SQL. Если нет, в конце страницы я добавил [Приложение: основные концепции SQL](#appendix-basic-sql-concepts), чтобы ты мог освежить знания.

### Пример для контекста

Представь, что мы проектируем платформу социальной сети. Не такую огромную, как Facebook, а растущую, которой нужен прочный фундамент.

Нашей платформе нужно поддерживать несколько базовых связей:

* Пользователи могут создавать посты
* Пользователи могут комментировать посты
* Пользователи могут подписываться на других пользователей
* Пользователи могут лайкать и посты, и комментарии
* Пользователи могут создавать личные сообщения (DM) с другими пользователями

Именно такие сценарии и встречаются на собеседованиях. Связи между сущностями понятны, но нетривиальны, и есть интересные вопросы про консистентность данных и масштабирование.

Чем это интересно с точки зрения базы данных? У разных операций разные требования:

* Многошаговые операции, например создание DM-треда, должны быть атомарными (создание треда, добавление участников и сохранение первого сообщения должны произойти вместе)
* Связи комментариев и подписок требуют ссылочной целостности (нельзя оставить комментарий без существующего поста или подписаться на несуществующего пользователя)
* Счётчики лайков могут быть eventually consistent (не страшно, если обновление займёт несколько секунд)
* Когда кто-то запрашивает профиль пользователя, нам нужно эффективно получить его последние посты, число подписчиков и другие метаданные
* Пользователям нужно искать по постам и находить других пользователей
* По мере роста платформы нам придётся обрабатывать больше данных и более сложные запросы

Сочетание этих требований (сложные связи, разные требования к консистентности, поиск и запас на рост) делает этот пример идеальным для изучения сильных и слабых сторон PostgreSQL.

## Основные возможности и ограничения

Теперь, когда у нас есть пример, можно описать, что PostgreSQL умеет хорошо, а что нет. Большинство обсуждений PostgreSQL на system design строятся вокруг производительности чтения, возможностей записи, гарантий консистентности и репликации. Понимание этих базовых характеристик поможет тебе принимать взвешенные решения о том, когда использовать PostgreSQL в своём дизайне.

### Производительность чтения

Начнём с производительности чтения. Она критична, потому что в большинстве приложений чтений намного больше, чем записей. В нашем примере с соцсетью пользователи проводят куда больше времени за просмотром постов и профилей, чем за созданием контента.

На собеседованиях по system design не нужно погружаться во внутренности query planner. Вместо этого сосредоточься на практических паттернах производительности и на том, в каких случаях имеет смысл использовать разные типы индексов.

Когда пользователь открывает профиль, нам нужно эффективно получить все посты этого пользователя. Без правильного индекса PostgreSQL придётся просканировать каждую строку таблицы posts, чтобы найти подходящие посты, а с ростом данных это становится всё дороже. Если создать индекс по колонке user\_id в таблице posts, мы сможем быстро находить все посты конкретного пользователя без сканирования всей таблицы.

#### Базовое индексирование

Самый базовый способ ускорить чтение в PostgreSQL: индексы. По умолчанию PostgreSQL использует B-tree индексы, которые отлично подходят для:

* Точных совпадений (WHERE email = '[user@example.com](mailto:user@example.com)')
* Запросов по диапазону (WHERE created\_at > '2024-01-01')
* Сортировки (ORDER BY username, если колонка в ORDER BY совпадает с порядком колонок индекса)

По умолчанию PostgreSQL создаёт B-tree индекс по колонке primary key, но можно создавать индексы и по другим колонкам.

```
-- This is your bread and butter index
CREATE INDEX idx_users_email ON users(email);

-- Multi-column indexes for common query patterns
CREATE INDEX idx_posts_user_date ON posts(user_id, created_at);
```

Частая ловушка на собеседованиях: предлагать добавить индексы на каждую колонку. Помни, что каждый индекс:

* Замедляет запись (индекс нужно обновлять)
* Занимает место на диске
* Может вообще не использоваться, если query planner решит, что последовательное сканирование будет быстрее

#### Не только базовые индексы

Настоящая сила PostgreSQL в поддержке специализированных индексов. Они часто всплывают на собеседованиях по system design, потому что позволяют обойтись без отдельных специализированных баз данных:

**Full-Text Search** с помощью GIN индексов. Postgres поддерживает full-text search из коробки через GIN (Generalized Inverted Index) индексы. GIN индексы работают как алфавитный указатель в конце книги: они хранят соответствие каждого слова всем местам, где оно встречается. Поэтому они идеально подходят для full-text search, где нужно быстро находить документы с определёнными словами:

```
-- Add a tsvector column for search
ALTER TABLE posts ADD COLUMN search_vector tsvector;
CREATE INDEX idx_posts_search ON posts USING GIN(search_vector);

-- Now you can do full-text search
SELECT * FROM posts 
WHERE search_vector @@ to_tsquery('postgresql & database');
```

Для многих приложений такой встроенный поиск означает, что отдельный кластер [Elasticsearch](/lessons/key-technologies/elasticsearch) не нужен. Он поддерживает всё, от:

1. Стемминга слов (finding/find/finds совпадают)
2. Ранжирования по релевантности
3. Нескольких языков
4. Сложных запросов с AND/OR/NOT

Хотя full-text search в PostgreSQL мощный, он может не полностью заменить Elasticsearch во всех сценариях. Рассмотри Elasticsearch, когда тебе нужно:

* Более сложное вычисление релевантности
* Faceted search
* Fuzzy matching и функции вроде «search as you type»
* Распределённый поиск по очень большим наборам данных
* Продвинутая аналитика и агрегации

Для простых случаев начинай со встроенного поиска PostgreSQL. Добавляй Elasticsearch, только когда появляются конкретные требования, которые поиск PostgreSQL закрыть не может. Так архитектура остаётся проще, а операционная сложность ниже.

JSONB колонки с GIN индексами особенно полезны, когда постам нужны гибкие метаданные. Например, в нашей соцсети у каждого поста могут быть разные атрибуты: геолокация, упомянутые пользователи, хештеги или прикреплённые медиа. Вместо отдельных колонок под каждый вариант можно хранить всё это в JSONB колонке (так мы получаем гибкость добавлять новые атрибуты по мере необходимости, как в NoSQL базе данных!).

```
-- Add a JSONB column for post metadata
ALTER TABLE posts ADD COLUMN metadata JSONB;
CREATE INDEX idx_posts_metadata ON posts USING GIN(metadata);

-- Now we can efficiently query posts with specific metadata
SELECT * FROM posts 
WHERE metadata @> '{"type": "video"}' 
  AND metadata @> '{"hashtags": ["coding"]}';

-- Or find all posts that mention a specific user
SELECT * FROM posts 
WHERE metadata @> '{"mentions": ["user123"]}';
```

Geospatial Search с помощью PostGIS. Хотя PostGIS не входит в ядро PostgreSQL, это расширение добавляет мощные пространственные возможности. Так же как мы индексируем текст для быстрого поиска, PostGIS позволяет индексировать данные о местоположении для эффективных геопространственных запросов. Это отлично подходит для нашей соцсети, когда мы хотим показывать пользователям посты из их района:

```
-- Enable PostGIS
CREATE EXTENSION postgis;

-- Add a location column to posts (using geography for distance in meters)
ALTER TABLE posts
ADD COLUMN location geography(Point, 4326);

-- Create a spatial index
CREATE INDEX idx_posts_location
ON posts USING GIST(location);

-- Find all posts within 5km of a user
SELECT * FROM posts
WHERE ST_DWithin(
    location,
    ST_MakePoint(-122.4194, 37.7749)::geography, -- SF coordinates
    5000  -- 5km in meters
);
```

PostGIS мощный, он умеет работать с:

* Разными типами пространственных данных (точки, линии, полигоны)
* Различными вычислениями расстояний (great-circle, евклидово)
* Пространственными операциями (пересечения, вложенность)
* Разными системами координат

PostGIS настолько функционален, что такие компании, как Uber, сначала использовали его для всей своей системы подбора поездок. Позже они перешли на кастомные решения ради масштаба, но этот пример показывает, как далеко можно зайти с расширениями PostgreSQL, прежде чем понадобятся специализированные базы данных.

Тип индекса, использованный здесь (GiST), это универсальный фреймворк индексов, который PostGIS применяет для эффективных пространственных поисков с помощью [стратегий bounding-box](/lessons/key-technologies/proximity-search). Это значит, что запросы вроде «найти все посты в радиусе X километров» или «найти посты внутри этой границы» выполняются эффективно, без проверки каждой строки.

Как и в случае с full-text search, прежде чем тянуться к специализированной геопространственной базе данных, стоит рассмотреть PostGIS. Это ещё один пример того, как можно получить сложную функциональность и при этом сохранить простую архитектуру.

Более того, все эти возможности можно комбинировать и создавать богатые сценарии поиска. Например, мы можем найти все видеопосты в радиусе 5 км от Сан-Франциско, которые упоминают «food» в тексте и помечены тегом «restaurant»:

```
SELECT * FROM posts
WHERE search_vector @@ to_tsquery('food')
  AND metadata @> '{"type": "video", "hashtags": ["restaurant"]}'
  AND ST_DWithin(
    location,
    ST_MakePoint(-122.4194, 37.7749)::geography,
    5000
  );
```

#### Основы оптимизации запросов

Мы разобрали разные типы индексов в PostgreSQL, но оптимизация запросов — это не только выбор правильного типа индекса. Несколько продвинутых стратегий индексирования могут заметно ускорить чтение.

##### Covering-индексы

Когда PostgreSQL использует индекс, чтобы найти строку, ему обычно нужно сделать две вещи:

1. Найти значение в индексе, чтобы определить, где лежит строка
2. Прочитать саму строку из таблицы, чтобы получить остальные нужные тебе колонки

А что, если хранить все нужные данные прямо в индексе? Именно это и делают covering-индексы:

```
-- Let's say this is a common query in our social media app:
SELECT title, created_at 
FROM posts 
WHERE user_id = 123 
ORDER BY created_at DESC;

-- A covering index that includes all needed columns
CREATE INDEX idx_posts_user_include 
ON posts(user_id) INCLUDE (title, created_at);
```

Covering-индексы могут заметно ускорить запросы, потому что PostgreSQL может выполнить весь запрос только по индексу, не обращаясь к таблице. Цена за это — индекс занимает больше места, а записи становятся немного медленнее.

##### Partial-индексы

Иногда индексировать нужно только часть данных. Например, в нашей социальной сети большинство запросов, скорее всего, ищут активных пользователей, а не удалённых:

```
-- Standard index indexes everything
CREATE INDEX idx_users_email ON users(email);  -- Indexes ALL users

-- Partial index only indexes active users
CREATE INDEX idx_active_users 
ON users(email) WHERE status = 'active';  -- Smaller, faster index
```

Partial-индексы особенно эффективны, когда большинству запросов нужна только часть строк, когда у тебя много «неактивных» или «удалённых» записей, которые не нужно индексировать, или когда ты хочешь уменьшить общий размер индексов и накладные расходы на их поддержку. Индексируя только нужное подмножество данных, partial-индексы заметно улучшают и производительность запросов, и использование ресурсов.

##### Практические пределы производительности

Скорее всего, в нефункциональных требованиях ты обозначил цели по latency. В идеале ещё и выразил их числами! Значит, когда ты углубляешься в дизайн, тебе нужно держать в голове базовые цифры производительности. Это очень грубые оценки, потому что реальные значения сильно зависят от железа и конкретной нагрузки. Но для старта на интервью их должно хватить.

1. **Производительность запросов**:
   * Простые поиски по индексу: десятки тысяч в секунду на ядро (часто 50k+)
   * Join нескольких таблиц с индексами: от тысяч до десятков тысяч в секунду
   * Сложные аналитические запросы с агрегациями: сотни — низкие тысячи в секунду
   * Full-table scan: сильно зависит от того, помещаются ли данные в память

Для сравнения: простые записи упираются примерно в 5 000 в секунду на ядро (подробнее в разделе «Производительность записи» ниже). Чтение почти всегда быстрее записи, потому что чтению не нужны записи в WAL и обновления индексов.

2. **Пределы масштаба**:
   * Таблицы начинают становиться громоздкими после 100M строк
   * Full-text search хорошо работает до десятков миллионов документов
   * Сложные join становятся проблемой на таблицах больше 10M строк
   * Производительность заметно падает, когда working set не помещается в доступную RAM

Это не жёсткие пределы: PostgreSQL может справиться с гораздо большим при правильной оптимизации. Но это хорошие эмпирические ориентиры, когда пора задуматься о partitioning, [sharding](/lessons/core-concepts/sharding) или других стратегиях масштабирования.

Когда речь о производительности, память — король! Запросы, которые можно выполнить из памяти, быстрее запросов с обращением к диску на порядки. Как правило, стоит стараться держать working set (часто используемые данные) в RAM.

На интервью знание этих практических пределов показывает, что ты понимаешь не только как использовать PostgreSQL, но и когда стоит рассмотреть альтернативы или дополнительные стратегии оптимизации.

### Производительность записи

Хотя в большинстве нагрузок преобладает чтение, производительность записи часто важнее, потому что напрямую влияет на пользовательский опыт: никто не хочет ждать секундами после нажатия «Опубликовать», пока контент появится.

Когда в PostgreSQL происходит запись, выполняется несколько шагов, которые обеспечивают и производительность, и durability:

1. **Buffer cache + запись в WAL [память]**: при записи PostgreSQL изменяет страницы данных в своём shared buffer cache (помечая их как «грязные») и одновременно формирует запись в WAL. Оба действия происходят в памяти в рамках транзакции.
2. **Сброс WAL на диск [диск]**: при commit записи WAL сбрасываются на диск. Это последовательная запись, поэтому она относительно быстрая. Как только WAL на диске, транзакция считается durable: даже если сервер упадёт, PostgreSQL сможет проиграть WAL и восстановить закоммиченные изменения.
3. **Background writer [память → диск]**: «грязные» страницы из памяти периодически записываются в файлы данных на диске. Это происходит асинхронно через background writer, при слишком большом давлении на память или при checkpoint. Отложенная запись позволяет PostgreSQL объединять много изменений в batch и работать быстрее.
4. **Обновления индексов [память и диск]**: каждый индекс нужно обновить, чтобы он отражал изменения. Как и данные таблицы, изменения индексов тоже проходят через WAL ради durability. Поэтому большое количество индексов может сильно замедлять запись: каждому индексу нужны дополнительные записи в WAL и обновления в памяти.

Благодаря такой архитектуре PostgreSQL быстро пишет: основная работа происходит в памяти, а durability обеспечивается через WAL. Сама запись страниц данных на диск происходит позже и оптимизирована под batch-операции.

Практический вывод: производительность записи в первую очередь ограничена скоростью сброса WAL (дисковый I/O), потому что это синхронный шаг, который должен завершиться до подтверждения commit. Количество индексов тоже имеет значение, так как каждому индексу нужны собственные записи в WAL. Buffer cache помогает, принимая «грязные» страницы в памяти, чтобы потом записать их в файлы данных пачками, но именно сброс WAL определяет latency commit.

#### Ограничения throughput

Теперь мы знаем, что происходит при записи в PostgreSQL. Прежде чем оптимизировать, стоит понять практические пределы write throughput: они помогают решить, подходит ли PostgreSQL для твоей системы.

Хорошо настроенный инстанс PostgreSQL на добротном (не топовом) железе может выдержать:

* Простые insert: ~5 000 в секунду на ядро
* Update с изменением индексов: ~1 000–2 000 в секунду на ядро
* Сложные транзакции (несколько таблиц/индексов): сотни в секунду
* Bulk-операции: десятки тысяч строк в секунду

Эти цифры предполагают уровень изоляции транзакций PostgreSQL по умолчанию (Read Committed), при котором транзакции видят только данные, закоммиченные до начала их запроса. Если изменить уровень изоляции по умолчанию, эти цифры могут вырасти или упасть.

Что влияет на эти пределы? Несколько факторов:

* Железо: write throughput часто упирается в дисковый I/O для WAL
* Индексы: каждый дополнительный индекс снижает write throughput
* Репликация: если она настроена, синхронная репликация добавляет latency, потому что мы ждём подтверждения от replica
* Сложность транзакции: чем больше таблиц или индексов затронуто, тем медленнее транзакция
* Соединения: PostgreSQL форкает отдельный процесс ОС на каждое соединение, поэтому сотни соединений потребляют много памяти и CPU на переключение контекста. На практике перед PostgreSQL нужен connection pooler (например, PgBouncer), который мультиплексирует соединения приложения в меньший пул соединений с базой. Это особенно важно, когда запущено много инстансов приложения.

Помни, что речь идёт об одном узле! Так что если твоей системе нужен write throughput выше, скажем, 5k записей в секунду, это не значит, что PostgreSQL отпадает. Это значит лишь, что данные придётся делать shard по нескольким узлам/машинам.

#### Оптимизация производительности записи

Хорошо, один узел выдерживает около 5k записей в секунду. Что можно сделать? Как улучшить производительность записи, если нужно больше?

Есть несколько вариантов, от простых оптимизаций до архитектурных изменений:

1. Batch Processing
2. Vertical Scaling
3. Write Offloading
4. Table Partitioning
5. Sharding

Разберём каждый по очереди.

**1. Vertical Scaling**
Прежде чем переходить к сложным решениям, всегда можно просто обновить железо. Например, взять более быстрые NVMe-диски ради производительности WAL, добавить RAM, чтобы увеличить buffer cache, или перейти на CPU с большим числом ядер для более эффективной параллельной работы.

На интервью это обычно не самое убедительное решение, но с него хорошо начинать.

**2. Batch Processing**
Самая простая оптимизация — группировать записи в batch. Вместо того чтобы обрабатывать каждую запись по отдельности, мы собираем несколько операций и выполняем их в одной транзакции. Например, вместо вставки 1000 лайков по одному мы вставляем их все в одной транзакции. Это значит, что мы буферизуем записи в памяти нашего сервера, прежде чем коммитить их на диск. Риск очевиден: если мы упадём посреди batch, все записи из него будут потеряны.

```
-- Instead of 1000 separate inserts:
INSERT INTO likes (post_id, user_id) VALUES 
  (1, 101), (1, 102), ..., (1, 1000);
```

**3. Write Offloading**
Некоторые записи не обязаны выполняться синхронно. Например, аналитические данные, логи активности или агрегированные метрики часто можно обрабатывать асинхронно. Вместо того чтобы писать напрямую в PostgreSQL, можно:

1. Отправлять записи в message queue (например, Kafka)
2. Запустить фоновые workers, которые обрабатывают накопленные в очереди записи батчами
3. При необходимости держать отдельную аналитическую базу данных

Этот паттерн особенно хорошо подходит для логирования активности, аналитических событий, агрегации метрик и некритичных обновлений вроде временных меток «last seen». Такие записи не нужно выполнять мгновенно, и их можно обрабатывать в фоне, не влияя на основной пользовательский сценарий.

**4. Table Partitioning**

В больших таблицах partitioning может улучшить производительность и чтения, и записи за счёт разделения данных по нескольким физическим таблицам. Самый распространённый случай — partitioning по времени. Вернёмся к нашему примеру с социальной сетью: допустим, у нас есть таблица posts, которая растёт на миллионы строк в месяц:

```
CREATE TABLE posts (
    id SERIAL,
    user_id INT,
    content TEXT,
    created_at TIMESTAMP
) PARTITION BY RANGE (created_at);

-- Create partitions by month
CREATE TABLE posts_2024_01 PARTITION OF posts
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
```

Почему это помогает записи? Во-первых, разные сессии базы данных могут одновременно писать в разные partitions, что повышает concurrency. Во-вторых, при вставке данных индексы нужно обновлять только в нужной partition, а не во всей таблице. Наконец, массовую загрузку можно выполнять partition за partition, и большие объёмы данных загружаются эффективнее.

Заодно это помогает и чтению. Когда пользователи смотрят свежие посты, PostgreSQL достаточно просканировать только свежие partitions. Не нужно продираться через годы исторических данных.

Распространённый паттерн: держать свежие partitions на быстром хранилище (например, на NVMe-дисках), а старые переносить на более дешёвое. Пользователи получают быстрый доступ к свежим данным, а именно они обычно интересуют их больше всего.

Это отличная стратегия для данных с естественным жизненным циклом, например для постов в социальных сетях, где самыми актуальными остаются новые.

**5. [Sharding](/lessons/core-concepts/sharding)**
Это самое частое решение на интервью. Когда одного узла недостаточно, sharding позволяет распределить записи между несколькими инстансами PostgreSQL. Главное — чётко объяснить, по какому ключу ты делаешь shard и как распределяешь данные.

Например, можно рассмотреть sharding постов по user\_id. Тогда все данные пользователя живут на одном shard. Это важно, потому что при чтении мы хотим избежать cross-shard запросов, когда данные приходится собирать (scatter-gather) с нескольких shards.

Обычно shard делают по столбцу, по которому запрашивают чаще всего. Если мы, как правило, запрашиваем все посты конкретного пользователя, то делаем shard по user\_id.

Sharding добавляет сложности: придётся обрабатывать cross-shard запросы, поддерживать согласованные схемы на всех shards и управлять несколькими базами данных. Вводи его, только когда более простых оптимизаций недостаточно.

В отличие от DynamoDB, у PostgreSQL нет встроенного решения для [sharding](/lessons/core-concepts/sharding). Его придётся реализовывать вручную, а это может быть непросто. Как вариант, можно взять управляемые сервисы вроде [Citus](https://www.citusdata.com/), которые берут на себя многие сложности sharding.

### Replication

Мы обсудили, как оптимизировать производительность записи на одном узле, но в реальных системах replication обычно используют для двух ключевых целей:

1. Масштабирование чтения за счёт распределения запросов между replicas
2. Обеспечение high availability на случай отказа узлов

Replication — это процесс копирования данных из одной базы данных в одну или несколько других. Это важная часть истории масштабируемости и доступности PostgreSQL.

PostgreSQL поддерживает два основных типа replication: синхронную и асинхронную. При **асинхронной replication** (по умолчанию) primary сразу подтверждает запись клиенту, а изменения реплицирует на replicas в фоне. Это даёт лучшую производительность записи, но есть окно, в котором replicas отстают от primary: если primary откажет в этот момент, можно потерять недавние записи. При **синхронной replication** primary ждёт подтверждения записи минимум от одной replica и только потом отвечает клиенту. Это гарантирует, что закоммиченные данные есть на нескольких узлах, но добавляет latency к каждой записи, потому что primary приходится ждать подтверждения от replica. Понимать эти компромиссы важно на интервью: синхронная replication даёт более сильные durability и consistency ценой latency записи, а асинхронная — лучшую производительность, но с риском потери данных при failover.

Многие организации используют гибридный подход: держат небольшое число синхронных replicas для более сильной consistency и дополнительные асинхронные replicas для масштабирования чтения. PostgreSQL позволяет указать, какие replicas должны быть синхронными.

#### Масштабирование чтения

Самое частое применение replication — масштабирование производительности чтения. Создавая read replicas, ты распределяешь запросы на чтение между несколькими инстансами базы данных, а все записи отправляешь на primary. Это особенно эффективно, потому что большинство приложений в основном читают данные.

Вернёмся к примеру с социальной сетью. Когда пользователи просматривают ленту или профили, это всё операции чтения, и их может обработать любая replica. Primary нужен, только когда они создают посты или обновляют профиль. Теперь наш read throughput вырос в N раз, где N — число replicas.

Есть одна важная оговорка про read replicas: replication lag. Если пользователь что-то изменил и сразу пытается прочитать это обратно, он может не увидеть своего изменения, если попадёт на replica, которая ещё не догнала primary. Это известно как консистентность «read-your-writes».

#### High Availability

Вторая важная польза replication — high availability. Храня копии данных на нескольких узлах, ты переживаешь аппаратные сбои без простоя. Если primary откажет, одну из replicas можно повысить до нового primary.

Обычно failover включает:

1. Обнаружение того, что primary недоступен
2. Повышение replica до primary
3. Обновление информации о подключении
4. Перенаправление приложений на новый primary

На интервью подчеркни, что replication нужна не только для масштабирования, но и для надёжности. Можно сказать: «Мы используем replication не только для распределения нагрузки на чтение, но и чтобы сервис оставался доступным, даже если мы потеряем узел базы данных».

Большинство команд используют управляемые сервисы PostgreSQL (например, AWS RDS или GCP Cloud SQL), которые сами берут на себя сложности failover. На интервью достаточно знать, что failover возможен и примерно как он работает, — вдаваться в детали ручной настройки не нужно.

### Data Consistency

Если в нефункциональных требованиях ты выбрал consistency, а не availability, то PostgreSQL — сильный выбор. Он с самого начала строился так, чтобы давать строгие гарантии consistency через ACID-транзакции. Но нужно понимать, как на практике добиться той consistency, которая нужна твоей системе.

Типичная ошибка на интервью — сказать «Мы используем PostgreSQL, потому что он ACID-совместим», не умея объяснить, как именно ты будешь использовать свойства ACID для своих требований к consistency.

#### Transactions

Одна из самых частых тем для обсуждения на интервью — транзакции. Транзакция — это набор операций, которые выполняются вместе и должны либо все успешно завершиться, либо все провалиться. Это основа обеспечения consistency в PostgreSQL.

Рассмотрим простой пример: нужно перевести деньги между двумя банковскими счетами. Если мы списываем деньги с одного счёта, они обязательно должны быть зачислены на другой. Ни одна из операций не может произойти сама по себе:

```
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;
```

Эта транзакция обеспечивает atomicity: либо выполняются оба обновления, либо ни одно. Однако одних транзакций недостаточно для consistency во всех сценариях, особенно когда одновременно выполняется несколько транзакций.

##### Transactions и конкурентные операции

Транзакции обеспечивают consistency для одной последовательности операций, но всё усложняется, когда одновременно выполняется несколько транзакций. Помни, что в большинстве реальных приложений множество пользователей или сервисов пытаются читать и изменять данные одновременно.

Именно здесь многие кандидаты спотыкаются на интервью. Они понимают базовые транзакции, но не продумали, как поддерживать consistency, когда несколько операций выполняются одновременно.

Рассмотрим систему аукциона. Пользователи делают ставки на лоты, и мы принимаем ставку, только если она выше текущей максимальной. Одна транзакция может обеспечить атомарность проверки текущей ставки и размещения новой, но что произойдёт, если двое пользователей попытаются сделать ставку одновременно?

```
BEGIN;
-- Get current max bid for item 123
SELECT maxBid FROM Auction WHERE id = 123;

-- Application checks: is our bid ($100) higher than current maxBid?
-- If yes, place the bid and update the max
INSERT INTO bids (item_id, user_id, amount)
VALUES (123, 456, 100);

UPDATE Auction SET maxBid = 100 WHERE id = 123 AND maxBid < 100;
COMMIT;
```

Даже внутри транзакции при уровне изоляции PostgreSQL по умолчанию (Read Committed) у нас могут возникнуть проблемы с консистентностью, если два пользователя делают ставки одновременно. Обе транзакции могут прочитать один и тот же max bid до того, как любая из них сделает commit.

Вот как это приводит к неконсистентному состоянию:

1. Транзакция пользователя A читает текущий max bid: $90
2. Транзакция пользователя B читает текущий max bid: $90
3. Пользователь A ставит $100 и обновляет maxBid до $100
4. Пользователь A делает commit
5. Пользователь B, всё ещё видя старый maxBid в $90, ставит $95
6. `UPDATE ... AND maxBid < 100` у пользователя B обновляет 0 строк (так как A уже выставил $100), но `INSERT` всё равно проходит
7. Пользователь B делает commit

Теперь у нас неконсистентное состояние: запись о ставке в $95 существует, хотя её не должны были принимать после ставки в $100. Корень проблемы в том, что проверка и вставка не атомарны: другая транзакция может вклиниться между чтением и записью.

Есть два основных способа решить эту проблему с конкурентностью:

**1. Row-Level Locking**
Самое простое решение: заблокировать строку аукциона на время проверки и обновления ставок. Используя `FOR UPDATE`, мы говорим PostgreSQL заблокировать строки, которые мы читаем. Другим транзакциям, которые пытаются прочитать эти строки с `FOR UPDATE`, придётся ждать, пока наша транзакция не завершится. Так мы получаем консистентное представление данных на время изменений.

```
BEGIN;
-- Lock the item and get current max bid
SELECT maxBid FROM Auction WHERE id = 123 FOR UPDATE;

-- Place new bid if it's higher
INSERT INTO bids (item_id, user_id, amount) 
VALUES (123, 456, 100);

-- Update the max bid
UPDATE Auction SET maxBid = 100 WHERE id = 123;
COMMIT;
```

Поэтому, когда нужно гарантировать, что две операции выполняются атомарно, подчеркни интервьюеру, как именно ты этого добьёшься, а не ограничивайся фразой «будем использовать транзакции». В нашем случае лучше сказать: «будем использовать транзакции и row-level locking на строке аукциона».

**2. Более строгий уровень изоляции**
Как альтернатива, можно использовать более строгий уровень изоляции:

```
BEGIN;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;

-- Same code as before...

COMMIT;
```

Хотя serializable isolation предотвращает все аномалии консистентности, у неё есть цена: если две транзакции конфликтуют, одна из них будет откачена и ей придётся повторить попытку. Твоё приложение должно быть готово обрабатывать такие повторы.

PostgreSQL поддерживает три уровня изоляции, каждый из которых даёт разные гарантии консистентности:

1. **Read Committed** (по умолчанию) — уровень изоляции PostgreSQL по умолчанию, при котором запрос видит только данные, закоммиченные до его начала. По мере выполнения транзакции каждый запрос внутри неё может видеть новые коммиты других транзакций, завершившихся уже после старта нашей. Это даёт хорошую производительность, но может приводить к non-repeatable reads, когда один и тот же запрос возвращает разные результаты внутри одной транзакции.
2. **Repeatable Read** в PostgreSQL даёт более сильные гарантии, чем требует стандарт SQL. Он создаёт консистентный snapshot данных на момент начала транзакции, и, в отличие от других баз данных, реализация в PostgreSQL предотвращает и non-repeatable reads, И phantom reads. Это значит, что не только один и тот же запрос вернёт одинаковые результаты внутри транзакции, но и новые строки, подходящие под условия твоего запроса, не появятся, даже если другие транзакции закоммитят такие строки.
3. **Serializable** — самый строгий уровень изоляции, при котором транзакции ведут себя так, как будто они выполнялись одна за другой последовательно. Он предотвращает все виды аномалий конкурентности, но взамен требует в приложении логики повторов (retry) для обработки конфликтов транзакций.

Реализация Repeatable Read в PostgreSQL заметно строже, чем требует стандарт SQL. Другие базы данных на этом уровне могут допускать phantom reads, а PostgreSQL их предотвращает. Это значит, что Serializable может не понадобиться там, где в других базах он был бы нужен.

Итак, когда использовать row-locking, а когда более высокий уровень изоляции?

| Аспект | Serializable Isolation | Row-Level Locking |
| --- | --- | --- |
| **Конкурентность** | Ниже: при конфликте транзакциям может понадобиться retry | Выше: конфликты возникают только при обращении к одним и тем же строкам |
| **Производительность** | Больше накладных расходов: нужно отслеживать все зависимости чтения/записи | Меньше накладных расходов: блокируются только конкретные строки |
| **Сценарий использования** | Сложные транзакции, где трудно понять, что именно блокировать | Когда ты точно знаешь, какие строки нужно обновлять атомарно |
| **Сложность** | Просто реализовать, но нужна логика retry | Более явно в коде, но retry не нужны |
| **Обработка ошибок** | Нужно обрабатывать serialization failures | Нужно обрабатывать сценарии deadlock |
| **Пример** | Сложные финансовые расчёты по нескольким таблицам | Ставки на аукционе, обновление inventory |
| **Использование памяти** | Выше: отслеживается вся история транзакции | Ниже: отслеживаются только блокировки |
| **Масштабируемость** | Хуже масштабируется при росте числа конкурентных транзакций | Лучше масштабируется, когда конфликты редки |

Row-level locking обычно предпочтительнее, когда ты точно знаешь, какие строки нужно заблокировать. Serializable isolation стоит приберечь для случаев, когда транзакция слишком сложна, чтобы рассуждать о том, какие блокировки нужны.

Также стоит знать про **optimistic concurrency control** (OCC), который подходит к задаче совсем иначе. Вместо того чтобы заранее блокировать строки, ты читаешь данные вместе с номером версии (или timestamp), выполняешь работу, а при commit проверяешь, не изменилась ли версия. Если изменилась, значит, кто-то другой изменил строку раньше, и ты повторяешь попытку. В PostgreSQL нет встроенного синтаксиса для OCC, но его можно реализовать на уровне приложения с помощью столбца version:

```
-- Read the current state
SELECT maxBid, version FROM Auction WHERE id = 123;
-- Returns maxBid=90, version=5

-- Update only if nobody else changed it
UPDATE Auction SET maxBid = 100, version = 6
WHERE id = 123 AND version = 5;
-- If 0 rows updated, someone else got there first — retry
```

OCC хорошо работает, когда конфликты редки (большинство транзакций проходит без повторов) и ты хочешь избежать удержания блокировок. Он плохо подходит, когда конфликты частые: многим транзакциям придётся повторяться, и работа будет выполняться впустую.

## Когда использовать PostgreSQL (и когда нет)

На собеседовании по system design PostgreSQL должен быть твоим выбором по умолчанию, если у тебя нет конкретной причины взять что-то другое. PostgreSQL:

1. Даёт строгие гарантии ACID и при этом хорошо масштабируется с помощью replication и partitioning
2. Работает и со структурированными, и с неструктурированными данными благодаря поддержке JSONB
3. Включает встроенные решения для типичных задач, например full-text search и геопространственные запросы
4. Хорошо масштабирует чтение за счёт replication
5. Имеет отличный инструментарий и зрелую экосистему

Начни с PostgreSQL, а затем объясни, зачем тебе может понадобиться отойти от него. Это намного сильнее, чем начинать с нишевого решения и пытаться доказать, что оно лучше PostgreSQL.

PostgreSQL особенно хорош, когда тебе нужны:

* Сложные связи между данными
* Строгие гарантии consistency
* Богатые возможности запросов
* Сочетание структурированных и неструктурированных данных (JSONB)
* Встроенный full-text search
* Геопространственные запросы

Например, он отлично подходит для:

* E-commerce-платформ (inventory, заказы, данные пользователей)
* Финансовых систем (транзакции, счета, audit logs)
* Систем управления контентом (посты, комментарии, пользователи)
* Аналитических платформ (до разумного масштаба)

### Когда стоит рассмотреть альтернативы

При этом мы тут не фанатики. Есть веские причины смотреть дальше PostgreSQL.

**1. Экстремальный write throughput**
Если нужно обрабатывать миллионы записей в секунду, PostgreSQL будет с трудом справляться: каждая запись требует записи в WAL и обновления индексов, что создаёт узкие места по I/O даже на самом быстром хранилище. Даже с [sharding](/lessons/core-concepts/sharding) координация записей между множеством узлов PostgreSQL добавляет сложность и latency. В таких случаях можно рассмотреть:

* NoSQL-базы (например, [Cassandra](/lessons/key-technologies/cassandra)) для event streaming
* Key-value-хранилища (например, [Redis](/lessons/key-technologies/redis)) для счётчиков в реальном времени

**2. Глобальные multi-region-требования**
Когда нужен active-active deployment в нескольких регионах (где несколько регионов одновременно принимают записи), PostgreSQL упирается в принципиальные ограничения. Его архитектура с единственным primary означает, что один регион должен быть назначен основным для записи, а остальные работают как read replicas. Попытка настоящего active-active deployment создаёт серьёзные проблемы с consistency данных и разрешением конфликтов, потому что PostgreSQL не проектировался для одновременной записи на несколько primary. Синхронная replication между регионами тоже вносит существенную latency, так как изменения должны быть подтверждены удалёнными replicas до commit. В таких сценариях рассмотри:

* CockroachDB для глобального соответствия ACID
* [Cassandra](/lessons/key-technologies/cassandra) для eventual consistency в глобальном масштабе
* [DynamoDB](/lessons/key-technologies/dynamodb) для управляемых global tables

**3. Простые key-value-паттерны доступа**
Если твои паттерны доступа строго key-value (то есть ты просто сохраняешь и получаешь значения по ключу, без joins и сложных запросов), PostgreSQL избыточен. Его архитектура MVCC, WAL logging и сложный query planner добавляют overhead, который тебе не нужен. В таких случаях рассмотри:

* [Redis](/lessons/key-technologies/redis) для производительности in-memory
* [DynamoDB](/lessons/key-technologies/dynamodb) для управляемой масштабируемости
* [Cassandra](/lessons/key-technologies/cassandra) для нагрузок с преобладанием записи

Одна только масштабируемость — не хорошая причина выбирать альтернативу PostgreSQL. При правильном проектировании PostgreSQL выдерживает значительный масштаб.

## Итоги

PostgreSQL должен быть твоим выбором по умолчанию на собеседованиях по system design, если конкретные требования не диктуют иного. Сочетание соответствия ACID, богатого набора возможностей и вариантов масштабирования делает его подходящим для широкого круга задач: от простых CRUD-приложений до сложных транзакционных систем.

Обсуждая PostgreSQL на собеседовании, сосредоточься на анализе конкретных требований к consistency данных, паттернам запросов и масштабу, а не на следовании трендам. Будь готов обсудить ключевые trade-offs: ACID против eventual consistency, стратегии масштабирования чтения и записи, решения по индексам. Начинай с простого и добавляй сложность только по мере необходимости.

Богатый набор возможностей PostgreSQL часто избавляет от необходимости в дополнительных системах в твоей архитектуре. Его full-text search может заменить Elasticsearch, поддержка JSONB может убрать потребность в MongoDB, а PostGIS закрывает геопространственные задачи, для которых иначе понадобились бы специализированные базы данных. Встроенная replication часто даёт достаточные возможности масштабирования для многих сценариев. Для экстремального масштабирования записи или глобального распределения лучше подходят такие базы, как Cassandra или CockroachDB.

## Приложение: базовые концепции SQL

Прежде чем переходить к возможностям, специфичным для PostgreSQL, повторим, как SQL-базы данных организуют данные. Эти базовые концепции применимы к любой SQL-базе и составляют фундамент, на который мы будем опираться на протяжении всего deep dive.

### Принципы реляционных баз данных

PostgreSQL хранит данные в таблицах (их ещё называют relations). Представь таблицу как электронную таблицу со строками и столбцами. У каждого столбца есть определённый тип данных (например, текст, числа или даты), а каждая строка — это одна полная запись.

Допустим, мы проектируем социальную сеть. У нас может быть таблица users, которая выглядит так:

```
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(50) UNIQUE NOT NULL,
    email VARCHAR(255) UNIQUE NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

Эта команда создаст следующую таблицу (данные приведены просто для примера):

| id | username | email | created\_at |
| --- | --- | --- | --- |
| 1 | johndoe | [john@example.com](mailto:john@example.com) | 2024-01-01 10:00:00 |
| 2 | janedoe | [jane@example.com](mailto:jane@example.com) | 2024-01-01 10:05:00 |
| 3 | bobsmith | [bob@example.com](mailto:bob@example.com) | 2024-01-01 10:10:00 |

Когда регистрируется новый пользователь, мы добавляем в эту таблицу новую строку. У каждого пользователя есть уникальный id (это и означает PRIMARY KEY), и мы гарантируем, что у двух пользователей не будет одинаковых username или email (за это отвечает UNIQUE).

Но сами по себе пользователи не слишком интересны. Им нужна возможность публиковать контент. Вот тут и проявляется «реляционная» часть реляционных баз данных. Мы можем создать таблицу posts, связанную с users:

```
CREATE TABLE posts (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    content TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

| id | user\_id | content | created\_at |
| --- | --- | --- | --- |
| 1 | 1 | Hello, world! | 2024-01-01 10:00:00 |
| 2 | 1 | My first post | 2024-01-01 10:05:00 |
| 3 | 2 | Another post | 2024-01-01 10:10:00 |

Видишь REFERENCES users(id)? Это называется foreign key — он создаёт связь между posts и users. Каждый пост должен принадлежать существующему пользователю, и PostgreSQL сам следит за этим. Это одна из ключевых сильных сторон реляционных баз данных: они помогают поддерживать целостность данных, принудительно обеспечивая такие связи.

На интервью очень важно уметь объяснять эти связи. Их три основных типа:

* One-to-One: например, пользователь и настройки его профиля
* One-to-Many: как наши users и posts (у одного пользователя может быть много постов)
* Many-to-Many: например, пользователи и посты, которые они лайкнули (это мы разберём дальше)

Теперь представим, что мы хотим дать пользователям возможность лайкать посты. Так появляется связь many-to-many: один пользователь может лайкнуть много постов, а один пост могут лайкнуть много пользователей. Мы решаем это с помощью так называемой join-таблицы:

```
CREATE TABLE likes (
    user_id INTEGER REFERENCES users(id),
    post_id INTEGER REFERENCES posts(id),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (user_id, post_id)
);
```

Такая структура, когда мы разбиваем данные на отдельные таблицы и связываем их через relationships, называется «нормализацией». Она помогает нам:

1. Не дублировать данные (мы не храним информацию о пользователе в каждом посте)
2. Поддерживать целостность данных (если пользователь меняет username, он обновляется везде)
3. Сделать модель данных гибкой (мы можем добавлять новые атрибуты пользователя, не трогая posts)

Нормализация, как правило, хорошая практика, но иногда мы намеренно денормализуем данные ради производительности. Например, мы можем хранить количество лайков поста прямо в таблице posts, хотя его можно вычислить из таблицы likes. Этот компромисс между консистентностью данных и производительностью запросов — именно то, что стоит обсудить на интервью!

Понимать эти основы — таблицы, связи и нормализацию — важно. Именно они делают SQL-базы вроде PostgreSQL такими мощными для приложений, которым нужно поддерживать сложные связи между разными типами данных. На интервью то, что ты умеешь объяснить не только как использовать эти концепции, но и когда и зачем их применять (или нарушать), выделит тебя среди других кандидатов.

### Свойства ACID

Одна из самых сильных сторон PostgreSQL — строгое соблюдение свойств ACID (Atomicity, Consistency, Isolation и Durability). Если ты работал с такими базами, как MongoDB или Cassandra, ты знаком с eventual consistency или ослабленными гарантиями транзакций — это распространённые компромиссы в NoSQL-базах. PostgreSQL выбирает другой подход. Он гарантирует, что твои данные всегда соответствуют всем заданным правилам и ограничениям (таким как foreign keys, unique constraints и пользовательские проверки), а все транзакции выполняются полностью или не выполняются вообще, даже если ради этого приходится жертвовать частью производительности.

Каждое свойство ACID проще всего понять на жизненном примере — переводе денег между банковскими счетами.

#### Atomicity (всё или ничего)

Представь, что ты переводишь $100 со сберегательного счёта на расчётный. Это две операции:

1. Списать $100 со сберегательного счёта
2. Зачислить $100 на расчётный счёт

```
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE account_id = 'savings';
  UPDATE accounts SET balance = balance + 100 WHERE account_id = 'checking';
COMMIT;
```

Atomicity гарантирует, что либо выполнятся обе операции, либо ни одна. Если система упадёт после списания со сберегательного счёта, но до зачисления на расчётный, PostgreSQL откатит всю транзакцию. Твои деньги не растворятся в воздухе.

На интервью подчеркни, что atomicity предотвращает частичные сбои. Без неё распределённые системы могут оказаться в неконсистентном состоянии, из которого очень трудно восстановиться.

#### Consistency (целостность данных)

Consistency гарантирует, что транзакции могут переводить базу данных только из одного валидного состояния в другое. Например, допустим, у нас есть правило, что баланс счёта не может быть отрицательным:

```
CREATE TABLE accounts (
    account_id TEXT PRIMARY KEY,
    balance DECIMAL CHECK (balance >= 0),
    owner_id INTEGER REFERENCES users(id)
);
```

Если транзакция сделает твой баланс отрицательным, PostgreSQL отклонит всю транзакцию. Это отличается от NoSQL-баз, где такие правила часто приходится обеспечивать в коде приложения.

Как ни странно, consistency в ACID означает не совсем то же самое, что consistency в теореме CAP. В ACID consistency означает, что база данных всегда соблюдает все заданные правила и ограничения. В теореме CAP consistency означает, что база данных всегда возвращает корректный результат, даже если ради этого приходится жертвовать availability или partition tolerance.

#### Isolation (конкурентные транзакции)

Уровни изоляции определяют, как транзакции могут взаимодействовать с данными, которые изменяются другими конкурентными транзакциями. Стандарт SQL определяет четыре уровня изоляции, и PostgreSQL принимает все четыре, хотя реализует только три различных поведения (Read Uncommitted обрабатывается как Read Committed):

```
BEGIN;
SET TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- Default level
-- or REPEATABLE READ
-- or SERIALIZABLE
COMMIT;
```

Уровень «Read Committed», который в PostgreSQL используется по умолчанию, предотвращает только dirty reads (чтение незакоммиченных изменений). Он допускает non-repeatable reads и phantom reads. Подробную разбивку того, какие аномалии предотвращает каждый уровень, смотри в [документации PostgreSQL](https://www.postgresql.org/docs/current/transaction-iso.html).

Хотя стандарт SQL определяет четыре уровня изоляции, внутри PostgreSQL реализованы только три различных уровня. В частности, Read Uncommitted в PostgreSQL ведёт себя так же, как Read Committed. Это решение согласуется с архитектурой multiversion concurrency control (MVCC) в PostgreSQL, которая по своей природе исключает dirty reads на любом уровне изоляции.

| Уровень изоляции | Dirty Read | Nonrepeatable Read | Phantom Read | Serialization Anomaly |
| --- | --- | --- | --- | --- |
| Read uncommitted | Допускается, но не в PG | Возможно | Возможно | Возможно |
| Read committed | Невозможно | Возможно | Возможно | Возможно |
| Repeatable read | Невозможно | Невозможно | Допускается, но не в PG | Возможно |
| Serializable | Невозможно | Невозможно | Невозможно | Невозможно |

#### Durability (постоянное хранение)

Когда PostgreSQL сообщает, что транзакция закоммичена, изменения гарантированно сохранены надолго и защищены от сбоев и отключений питания. Это достигается с помощью Write-Ahead Logging (WAL): записи WAL сбрасываются на диск при коммите, и PostgreSQL может воспроизвести их, чтобы восстановить любые изменения, даже если сами страницы данных ещё не были записаны:

1. Изменения сначала записываются в лог
2. Лог сбрасывается на диск
3. Только после этого транзакция считается закоммиченной

Хотя durability гарантируется, за неё приходится платить производительностью. Некоторые приложения могут ослабить durability ради скорости (например, установив synchronous\_commit = off), и тогда часть записей, которые ещё не попали на диск, может быть потеряна при отключении питания или сбое.

### Почему ACID важен

На интервью тебе часто придётся выбирать между разными типами баз данных. Соответствие ACID — один из ключевых факторов в этом выборе:

* **Финансовые транзакции**: свойства ACID необходимы, чтобы деньги не терялись и не тратились дважды
* **Лайки в соцсетях**: возможно, тебя устроит eventual consistency
* **Аутентификация пользователей**: скорее всего, тебе понадобится ACID, чтобы избежать проблем с безопасностью
* **Аналитические данные**: возможно, ты поставишь производительность выше строгой консистентности

Строгое соблюдение ACID делает PostgreSQL отличным выбором для систем, где критична консистентность данных. Сегодня потери производительности из-за этого невелики, но о них всё равно стоит знать.

### Язык SQL

Хотя на интервью по system design тебе редко приходится писать настоящие SQL-запросы, понимание возможностей SQL помогает принимать более взвешенные архитектурные решения. К тому же, если ты проходишь собеседование на более junior-роль, тебя могут попросить написать несколько простых запросов, чтобы показать, как ты понимаешь базы данных.

#### Типы SQL-команд

SQL-команды делятся на четыре основные категории:

1. **DDL (Data Definition Language)**

   * Создаёт и изменяет структуру базы данных
   * Примеры: CREATE TABLE, ALTER TABLE, DROP TABLE

   ```
   CREATE TABLE users (
     id SERIAL PRIMARY KEY,
     email VARCHAR(255) UNIQUE
   );

   ALTER TABLE users ADD COLUMN username TEXT;
   ```
2. **DML (Data Manipulation Language)**

   * Управляет данными внутри таблиц
   * Примеры: SELECT, INSERT, UPDATE, DELETE

   ```
   -- Find all users who joined in the last week
   SELECT * FROM users 
   WHERE created_at > NOW() - INTERVAL '7 days';

   -- Update a user's email
   UPDATE users SET email = 'new@email.com' 
   WHERE id = 123;
   ```
3. **DCL (Data Control Language)**

   * Управляет правами доступа
   * Примеры: GRANT, REVOKE

   ```
   -- Give read access to a specific user
   GRANT SELECT ON users TO read_only_user;
   ```
4. **TCL (Transaction Control Language)**

   * Управляет транзакциями
   * Примеры: BEGIN, COMMIT, ROLLBACK

   ```
   BEGIN;
     -- Multiple operations...
   COMMIT;
   ```

На интервью тебя могут спросить не про конкретные запросы, а про паттерны доступа к базе данных. Например: «Как бы ты эффективно запрашивал эти данные?» или «Какие индексы ты бы создал?» Такие вопросы проверяют, насколько ты понимаешь концепции баз данных, а не синтаксис SQL.

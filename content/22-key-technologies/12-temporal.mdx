Узнай, как Temporal использует durable execution, чтобы многошаговые процессы продолжали работать несмотря на сбои, retry и долгие ожидания.

Представь, что ты строишь backend для ecommerce-компании. Когда клиент оформляет заказ, нужно:

1. Списать деньги с карты
2. Зарезервировать товар на складе
3. Запросить отправку
4. Дождаться доставки посылки
5. Отправить письмо с просьбой оставить отзыв

Если на минуту забыть о сбоях, можно представить себе что-то такое:

```
function processOrder(order):
    chargeCustomer(order)
    reserveInventory(order)
    requestShipment(order)

    while not isDelivered(order):
        sleep(5 days)

    sendReviewEmail(order)
```

Конечно, на практике ты вряд ли будешь пять дней держать запущенным серверный процесс, который всё это время что-то опрашивает. Ты разобьёшь процесс на части, сохранишь текущее состояние где-нибудь, а следующий шаг запустишь тогда, когда перевозчик сообщит о доставке посылки.

А что делать со сбоем, который случился посередине? Допустим, Stripe успешно списал деньги, и сразу после этого твой сервер упал. Когда его работу подхватывает другой сервер, как он узнает, было ли списание? Если он выполнит шаг заново, клиента могут списать дважды.

Конечно, можно самому построить инфраструктуру для решения этих задач, но это потребует много работы, в которой трудно не ошибиться.

Именно для таких задач и создан Temporal.

Temporal — один из способов решить эту проблему. Сервисы также можно координировать через события или использовать другую workflow-систему, например AWS Step Functions. В статье [Multi-step Processes](/lessons/patterns/multi-step-processes) разобраны эти подходы и их компромиссы. Здесь мы сосредоточимся на том, как работает Temporal.

## Строим durable execution с нуля

Temporal может показаться немного странным, когда впервые сталкиваешься с такими понятиями, как Workflows, Activities, replay и deterministic execution. Проще всего понять, зачем они нужны, если представить, что мы сами строим простую систему durable execution.

### Как пережить падение функции

Начнём с самого базового требования. Мы хотим, чтобы processOrder переживала падение сервера.

Первая проблема в том, что несколько шагов нашей функции взаимодействуют с системами за пределами процесса. chargeCustomer может вызывать Stripe, reserveInventory может обновлять базу данных, а requestShipment может отправлять запрос провайдеру доставки.

Если один из этих вызовов завершился успешно и сразу после этого сервер упал, нам нужна надёжная (durable) запись о том, что это произошло, чтобы не выполнить то же действие повторно.

Поэтому вместо прямого вызова этих функций представим, что каждая внешняя операция проходит через наш execution framework. Когда операция завершается, framework записывает и сам факт завершения, и возвращённый результат.

Например, после списания денег и резервирования товара история может выглядеть так:

```
ChargeCustomerCompleted {
    result: paymentId_123
}

ReserveInventoryCompleted {
    result: reservationId_456
}
```

Теперь предположим, что сервер упал до запроса отправки.

Процесса, который выполнял processOrder, больше нет, но результаты уже выполненной работы по-прежнему лежат в durable-хранилище.

Когда работу подхватывает другой сервер, он может запустить processOrder заново с самого начала.

На этот раз, когда функция просит framework выполнить внешнюю операцию, framework сначала проверяет, есть ли уже записанный результат для этой операции.

```
chargeCustomer(order)
→ ChargeCustomerCompleted already exists
→ return paymentId_123

reserveInventory(order)
→ ReserveInventoryCompleted already exists
→ return reservationId_456

requestShipment(order)
→ no completed result exists
→ execute it
→ record the result
```

Stripe повторно не вызывается, потому что завершённое списание уже есть в истории. Сервис склада тоже. С точки зрения processOrder эти функции просто возвращают те же значения, что и в первый раз.

Это предполагает, что framework успел записать завершение операции. Если Stripe отработал успешно, но сервер упал до того, как сообщил об успехе, framework может повторить операцию. Поэтому внешние побочные эффекты всё равно должны быть идемпотентными. Как безопасно обрабатывать такие retry, описано в паттерне [Multi-step Processes](/lessons/patterns/multi-step-processes).

Запуская функцию заново и подставляя ранее записанные результаты там, где работа уже выполнена, мы восстанавливаем состояние программы, не восстанавливая исходный процесс.

Это называется **replay**.

![Иллюстрация](/content/deep-dives--temporal/4c5bbfd672.svg)

Replay возвращает новому Worker сохранённые результаты платежа и резервирования товара до запроса отправки.

Пока история завершённых операций надёжно хранится, worker, выполняющий функцию, может исчезнуть, а другой worker позже восстановит выполнение.

Так в нашем framework естественным образом появляются два вида кода. Логику оркестрации можно воспроизводить (replay), а операции, взаимодействующие с внешним миром, нужно выполнять отдельно и записывать их результаты.

Temporal называет воспроизводимый код оркестрации **Workflow**, а внешние операции — **Activities**.

![Иллюстрация](/content/deep-dives--temporal/f9aed836a0.svg)

Workflow processOrder вызывает отдельные Activities: chargeCustomer обращается к Stripe, reserveInventory обновляет базу данных склада, а requestShipment вызывает API службы доставки.

### Делаем replay предсказуемым

Теперь наш framework умеет воспроизводить Workflow, но есть ещё одна проблема. Повторный запуск той же функции работает только в том случае, если она принимает те же решения, что и в первый раз.

Допустим, наша ecommerce-компания предлагает доставку в день заказа для заказов, оформленных до 17:00. Мы можем добавить такую логику:

```
function processOrder(order):
    chargeCustomer(order)
    reserveInventory(order)

    if currentTime() < 5:00 PM:
        requestSameDayPickup(order)
    else:
        requestNextDayPickup(order)

    waitUntilDelivered(order)
    sendReviewEmail(order)
```

Предположим, клиент оформляет заказ в 16:59.

Workflow списывает деньги, резервирует товар, видит, что ещё нет 17:00, и запрашивает забор в тот же день. Теперь наша история содержит примерно следующее:

```
ChargeCustomerCompleted
ReserveInventoryCompleted
RequestSameDayPickupCompleted
```

Затем сервер падает.

Через несколько минут другой worker воспроизводит processOrder с самого начала. Списание и резервирование товара возвращают ранее записанные результаты.

Но потом мы снова доходим до этой строки:

```
if currentTime() < 5:00 PM:
```

Сейчас уже 17:03.

Первое выполнение пошло по ветке requestSameDayPickup. Replay идёт по ветке requestNextDayPickup.

Это серьёзная проблема! В нашей истории следующим событием значится RequestSameDayPickupCompleted, а код, который мы воспроизводим, теперь просит выполнить requestNextDayPickup.

Replay работает только в том случае, если Workflow при восстановлении из одной и той же истории каждый раз идёт одним и тем же путём. Иными словами, код нашего Workflow должен быть **детерминированным (deterministic)**.

Один из способов решить проблему со временем — пустить само время через наш framework. Вместо прямого чтения системных часов машины Workflow запрашивает текущее время у framework.

При первом выполнении framework может вернуть 16:59 и записать достаточно информации, чтобы позже воспроизвести это значение. Во время replay он возвращает то же логическое время, а не то, которое случайно показывают часы нового worker.

Теперь Workflow идёт по той же ветке, и его выполнение по-прежнему соответствует истории.

Temporal накладывает то же ограничение на код Workflow. Как правило, из Workflow нельзя обращаться к внешнему миру или напрямую читать недетерминированные значения, например текущее время машины. Вместо этого SDK Temporal предоставляет безопасные для Workflow версии таких операций, как чтение текущего времени, чтобы они вели себя согласованно во время replay.

### Даём Workflow возможность ждать

Пока что наш Workflow делает только то, что происходит мгновенно. Но в исходном процессе обработки заказа было и вот это:

```
waitUntilDelivered(order)
```

Это может занять дни.

Прежде чем думать о том, как узнать, что посылка действительно доставлена, решим более простую версию задачи. Допустим, наш провайдер доставки сообщает, что доставка займёт пять дней, и мы просто хотим, чтобы Workflow подождал пять дней и продолжил работу.

Мы могли бы написать:

```
function processOrder(order):
    chargeCustomer(order)
    reserveInventory(order)
    requestShipment(order)

    sleep(5 days)

    sendReviewEmail(order)
```

Очевидно, что мы не хотим, чтобы sleep(5 days) буквально держал процесс worker живым пять дней. В работе могут находиться миллионы заказов одновременно, и большинство из них при этом ничего не делают, а просто ждут.

Значит, ожидание тоже должно быть durable.

Когда Workflow доходит до sleep(5 days), наш framework может вычислить, когда должен сработать таймер, и сохранить это в durable-хранилище.

```
TimerStarted {
    fireAt: May 15, 10:00 AM
}
```

На этом этапе Workflow больше нечего делать. Мы можем полностью остановить его выполнение и освободить worker для другой работы.

Нашему framework нужен фоновый scheduler, который проверяет таймеры, чей срок уже наступил. Он может хранить таймеры в durable-хранилище, упорядоченные по дедлайнам, чтобы не перебирать каждый ожидающий Workflow. Через пять дней scheduler находит наш таймер и записывает ещё одно событие.

```
TimerFired
```

При следующем запуске Workflow replay в какой-то момент снова доходит до таймера.

```
sleep(5 days)
→ TimerStarted already exists
→ TimerFired exists
→ continue
```

Если бы таймер ещё не сработал, Workflow просто снова остановился бы на этом месте.

Это значит, что Workflow может «спать» пять дней, пять месяцев или даже дольше, и при этом всё это время не нужен висящий процесс.

Temporal предоставляет эту абстракцию в виде **durable timers**. Его History Service хранит Timer Task с дедлайном. Фоновый timer processor читает эти задачи и обрабатывает их, когда подходит срок: записывает TimerFired и планирует запуск Workflow на свободном Worker. Как эти сервисы устроены вместе, мы разберём ниже.

Timer processor обслуживает много Workflow, и каждому спящему Workflow не нужен отдельный процесс. Если экземпляр History Service падает, другой экземпляр подхватывает работу и восстанавливает из storage незавершённые таймеры. Сбой может задержать срабатывание таймера, но сам таймер не пропадёт.

![Иллюстрация](/content/deep-dives--temporal/d1232f906f.svg)

Temporal хранит таймер между днём 0 и днём 5; Worker работает только когда Workflow начинает ждать и когда возобновляется.

### Пусть внешний мир разбудит Workflow

Пятидневный таймер подходит, если мы точно знаем, сколько хотим ждать. Но с доставкой так не получается.

Посылка может прийти завтра, а может идти неделю. На самом деле нам нужно, чтобы Workflow ждал, пока служба доставки не сообщит, что посылка доставлена.

Вернёмся к этому:

```
waitUntilDelivered(order)
```

Когда Workflow доходит до этого места, делать ему пока больше нечего, поэтому выполнение можно остановить.

Затем, три дня спустя, служба доставки присылает webhook с сообщением, что посылка доставлена.

Нашему фреймворку нужен способ передать эту информацию в уже запущенный Workflow. Проще всего добавить её в durable history Workflow.

```
ChargeCustomerCompleted
ReserveInventoryCompleted
RequestShipmentCompleted
PackageDelivered
```

Это новое событие заставляет Workflow выполниться снова. Когда replay доходит до waitUntilDelivered, событие доставки уже есть в history, и выполнение может продолжаться.

```
waitUntilDelivered(order)
→ PackageDelivered exists
→ continue

sendReviewEmail(order)
→ execute
→ record result
```

Таким образом, Workflow может простаивать днями или неделями и возобновляться, когда приходит новая информация, при этом всё это время не нужно держать живым процесс worker.

Temporal называет такой внешний ввод **Signal**. Signal позволяет другой системе отправить информацию в работающий Workflow. Temporal записывает эту информацию в history Workflow и будит Workflow, чтобы тот мог на неё отреагировать.

В нашем примере с заказом webhook от службы доставки может отправить Workflow Signal о том, что посылка доставлена. Тогда waitUntilDelivered(order) завершится, и можно будет отправить письмо с просьбой об отзыве.

![Иллюстрация](/content/deep-dives--temporal/36f68f35b5.svg)

Webhook службы доставки отправляет Signal в Temporal, тот записывает факт доставки и планирует продолжение Workflow на Worker.

## Что такое Temporal?

Мы начали с обычной функции и, решая по одной проблеме за раз, построили большую часть программной модели Temporal.

Temporal — это система оркестрации workflow, построенная вокруг durable execution. Workflow содержит воспроизводимую (replayable) логику оркестрации, а Activities выполняют работу, связанную с внешним миром. Temporal записывает результаты этой работы в durable execution history, что позволяет ему сделать replay Workflow и восстановить его состояние после сбоя.

Поскольку Workflow проходят через replay, их код должен быть детерминированным. Таймеры позволяют ждать, не держа worker живым, а Signals дают внешним системам возможность передать новую информацию уже работающему Workflow.

Благодаря этой модели наш процесс обработки заказа выглядит очень близко к простому последовательному коду, который мы изначально хотели написать:

```
workflow processOrder(order):
    chargeCustomer(order)
    reserveInventory(order)
    requestShipment(order)

    waitUntilDelivered(order)

    sendReviewEmail(order)
```

Теперь интересный вопрос: как Temporal всё это реализует?

## Temporal под капотом

Теперь, когда мы на высоком уровне понимаем, что такое Temporal, заглянем под капот.

На собеседовании по system design вам почти наверняка не понадобится знать внутреннее устройство Temporal. Можешь пропустить этот раздел, если тебе не любопытно.

Архитектура, лежащая в основе этой модели, примерно такая:

![Иллюстрация](/content/deep-dives--temporal/bc0548ea3c.svg)

Clients и Workers подключаются через Frontend. Frontend, History, Matching и Workers масштабируются как отдельные парки машин (fleet); History владеет shard, а Matching управляет partition Task Queue.

* **Frontend Service** — это stateless-точка входа в кластер Temporal. Clients и Workers подключаются к нему, а он маршрутизирует их запросы к нужному внутреннему сервису.
* **History Service** владеет durable-состоянием Workflow Executions. Он обрабатывает завершения Activity, Signals, таймеры и решения, принятые кодом Workflow.
* **Matching Service** управляет Task Queues, которые связывают Temporal с твоими Workers.
* **Workers** — это процессы твоего приложения, в которых работает твой код. Сам Temporal не выполняет код твоих Workflow или Activity внутри Temporal Service. Workers опрашивают (poll) Temporal в поисках работы, выполняют нужный код и отправляют результат обратно.

### Как хранится состояние Workflow

Кластер Temporal может отвечать за миллионы Workflow Executions, поэтому за все из них не может отвечать одна машина History Service.

Вместо этого Workflow Executions распределяются по фиксированному числу History Shards. Каждый экземпляр History Service владеет некоторым подмножеством этих shard и отвечает за обработку запросов и таймеров для Workflow внутри них. Если экземпляры History Service добавляются, удаляются или падают, владение этими shard может переходить между экземплярами.

Когда с одним из наших Workflow заказа что-то происходит, History Service выполняет state transition.

Например, предположим, что chargeCustomer успешно завершился.

Концептуально History Service делает примерно следующее:

![Иллюстрация](/content/deep-dives--temporal/1e40f6e67d.svg)

History Service обрабатывает завершение Activity и атомарно сохраняет обновление Event History, Mutable State и Transfer Task.

Temporal ведёт уже знакомую нам Event History, но также сохраняет нечто под названием Mutable State. Mutable State — это по сути materialized view текущего серверного состояния Workflow, включающее, например, ожидающие Activities, незавершённые таймеры и дочерние Workflows.

Большую часть этой информации теоретически можно было бы восстанавливать, сканируя Event History при каждом событии, но это было бы неоправданно дорого. Mutable State позволяет History Service эффективно отвечать на вопрос «что сейчас происходит с этим Workflow?», а Event History остаётся durable-записью, из которой это состояние можно восстановить.

History Service также должен гарантировать, что обновление состояния Workflow и планирование следующего шага не будут разорваны сбоем.

Допустим, Activity завершилась, и Workflow теперь нужно запустить снова. Temporal сохраняет обновлённое состояние вместе с durable внутренней задачей Transfer Task. Фоновый процессор в итоге отправляет эту задачу в Matching Service, который делает соответствующий Workflow Task доступным для Worker.

По сути это transactional outbox. Temporal может упасть после коммита состояния Workflow и всё равно знать, что получившуюся работу нужно рано или поздно отправить на выполнение.

![Иллюстрация](/content/deep-dives--temporal/65535d2467.svg)

Состояние Workflow и Transfer Task коммитятся вместе. Фоновый процессор читает сохранённую задачу и передаёт её в Matching, даже если History упал после коммита.

Таймеры используют тот же общий механизм. Таймер хранится как внутренняя задача Timer Task, привязанная к History shard. Когда наступает время срабатывания, Temporal записывает факт срабатывания таймера и создаёт работу, необходимую для повторного запуска Workflow.

В self-hosted развёртывании в роли durable storage могут выступать PostgreSQL, MySQL или Cassandra. Temporal сам управляет схемой базы данных для Event History, Mutable State и внутренних задач.

### Как Temporal избегает постоянного replay всего подряд

Replay даёт Temporal мощный механизм восстановления, но воспроизводить длинный Workflow по всей Event History при каждом событии было бы дорого.

Поэтому Workers кэшируют состояние Workflow в памяти.

Когда Workflow Worker впервые получает Workflow Task, он восстанавливает Workflow по Event History и затем хранит это восстановленное состояние в **Workflow Cache**.

После этого Temporal старается отправлять последующие Workflow Tasks этого Workflow обратно на тот же Worker. Эта оптимизация называется **Sticky Execution**.

![Иллюстрация](/content/deep-dives--temporal/0aecbd274f.svg)

Sticky queue направляет Workflow Tasks в cache Worker A. После сбоя Worker A обычная очередь отправляет работу на Worker B, который делает replay Event History.

Под капотом Worker опрашивает и обычную Task Queue, и свою **Sticky Queue**, привязанную к конкретному Worker. Как только Worker закэшировал Workflow, будущие Workflow Tasks можно направлять через эту sticky queue, а не заставлять другой Worker восстанавливать Workflow с нуля.

Но cache — это всего лишь оптимизация: если Worker падает или Workflow вытесняется из cache, другой Worker может восстановить Workflow по его durable history. Temporal отправляет следующий Workflow Task через обычную Task Queue, чтобы его подхватил любой доступный Worker.

Так что Event History обеспечивает корректность, а sticky execution и caching — производительность.

### Workers и Task Queues

Как же Temporal находит Worker, чтобы выполнить следующий фрагмент кода? Твоё приложение задаёт работе имя **Task Queue**, например payments, а Workers, которые умеют обрабатывать эту работу, ты настраиваешь опрашивать то же имя.

Task Queue — это именованный адрес назначения для работы. **Matching Service** — часть Temporal, которая управляет этими очередями и передаёт задачи опрашивающим их Workers. Когда History нужно запустить код, его фоновые процессоры отправляют задачу в Matching для соответствующей очереди. Matching передаёт её одному из Workers, ожидающих работу в этой очереди.

Есть два важных типа задач:

* **Workflow Task** говорит Worker'у выполнить код Workflow и определить, что должно произойти дальше.
* **Activity Task** говорит Worker'у выполнить операцию, например вызвать Stripe или отправить email.

Они необязательно должны выполняться на одних и тех же машинах.

Например, у нас может быть так:

![Иллюстрация](/content/deep-dives--temporal/42cb27a3f3.svg)

Отдельные Task Queue направляют Workflow заказов, Activity платежей, Activity доставки и Activity email-рассылок в соответствующие парки Worker'ов.

Это позволяет запускать разные виды Activity на совершенно разных парках Worker'ов. Для CPU-тяжёлой работы могут быть свои машины, для GPU-задач другой парк, а чувствительные Activity платежей могут работать в изолированном сервисе. Один процесс Worker'а может выполнять и код Workflow, и код Activity, если разделять их не нужно.

Matching ничего не должен знать о реализации этих Worker'ов. Он просто сопоставляет задачи с Worker'ами, которые опрашивают нужную Task Queue.

Эти очереди реализует сам Temporal. Если Worker уже опрашивает очередь, Matching может передать ему задачу напрямую. Иначе он хранит задачу в persistence database, пока не освободится Worker.

Сами Task Queue тоже можно партиционировать между инстансами Matching Service, чтобы увеличить throughput, так что активно используемую очередь не обязана обслуживать одна машина.

### Как масштабируется кластер

Одна из причин, по которой команды выбирают Temporal, в том, что число отслеживаемых процессов может расти без необходимости держать Worker под каждый из них. У нашего e-commerce-магазина могут быть миллионы заказов, ожидающих доставки, и лишь малая их часть готова выполнять какую-то работу прямо сейчас.

Эти ожидающие заказы всё равно занимают место в базе данных, но каждый из них не занимает Worker. Если приходит всплеск уведомлений о доставке, мы можем добавить Worker'ов для обработки писем с просьбой об отзыве. Объём вычислений Worker'ов зависит от работы, готовой к запуску, а не от количества всё ещё открытых заказов.

Temporal Service можно масштабировать отдельно, чтобы справляться с координацией. Больше инстансов Frontend обрабатывают API-трафик, больше инстансов History делят владение History Shard'ами, а больше инстансов Matching обслуживают партиции Task Queue. Если узким местом становятся обновления состояния Workflow, добавление прикладных Worker'ов этого не исправит: понадобится больше мощности в History или в его базе данных.

Так мы наращиваем мощности там, где нагрузка действительно растёт. Backlog писем требует больше email-Worker'ов. Растущая частота обновлений Workflow требует больше мощности в Temporal Service и persistence-слое.

## Когда использовать Temporal

Temporal хорошо подходит, когда у тебя есть многошаговый процесс, который должен переживать сбои или долгие периоды ожидания.

Типичный признак того, что тебе нужен Temporal, в том, что ты начал сам писать state machine. Нужно сохранять, какой шаг завершился, планировать, что произойдёт дальше, повторять упавшую работу и восстанавливаться после падения worker'а.

Стоит рассмотреть Temporal, когда

* **У процесса есть несколько зависимых шагов, которые должны выполняться надёжно.** Пайплайн постобработки YouTube разбивает видео на сегменты, параллельно транскодирует их и собирает результаты в готовые выходные файлы.
* **Процесс может оставаться открытым в ожидании чего-либо.** Подбор поездки в Uber ждёт ответа водителя или таймаута, прежде чем решить, пробовать ли следующего кандидата.
* **Нужно восстанавливаться после частичного выполнения.** Если worker обработки YouTube пропадает посреди DAG, Temporal может восстановить Workflow и продолжить планировать незавершённую работу.
* **Retry и восстановление становятся значимой частью логики твоего приложения.** В какой-то момент ты фактически строишь собственный workflow engine.

Для одной асинхронной задачи часто хватает очереди. Temporal становится полезным, когда нужно координировать весь процесс на множестве шагов и сбоев.

### Примеры из наших разборов задач

Мы предлагаем Temporal в трёх наших разборах задач по system design:

* **[Design Uber](/lessons/breakdowns/uber)** использует Workflow, чтобы предложить поездку одному водителю, подождать 10 секунд и перейти к следующему кандидату после отказа или таймаута.
* **[Design YouTube](/lessons/breakdowns/youtube)** использует Temporal для оркестрации DAG, который разбивает загруженные видео, параллельно обрабатывает сегменты и собирает результаты.
* **[Design a Flash Sale](/lessons/breakdowns/flash-sale)** показывает таймер Temporal как один из способов надёжно истекать резервации инвентаря вне Sale Service.

В каждом случае оркестрацию можно построить самому на состоянии в базе данных, очередях, таймерах и worker'ах. Temporal позволяет выразить эту оркестрацию напрямую в виде кода.

На интервью по system design помни, что не каждый интервьюер разрешит использовать Temporal.

В некоторых задачах надёжная оркестрация workflow и есть то, что тебя просят спроектировать. Если вставить Temporal в архитектуру, самую сложную часть интервью можно фактически решить одним блоком.

Хорошая новость в том, что, поняв, как работает Temporal, ты уже получаешь сильный образец того, как спроектировать такую систему самому.

### Ограничения

Temporal не подходит в каждом случае, когда нужна асинхронная работа.

1. **Простые фоновые задачи**
   Наш разбор [Design a Notification System](/lessons/breakdowns/notification-system) намеренно использует очередь вместо Temporal, потому что самое интересное в том дизайне как раз в раскрытии механики доставки и retry. Для одной независимой задачи обычная очередь вроде SQS может быть значительно проще.
2. **Стриминговые нагрузки**
   Temporal не заменяет Kafka или другую платформу потоковой обработки событий. Если задача в основном про непрерывную обработку потока событий большого объёма, используй систему, созданную для этого.
3. **Внешним побочным эффектам всё равно нужна идемпотентность**
   Temporal может повторять Activity, а значит, вызовы систем вроде Stripe или твоей базы данных могут выполниться больше одного раза. Эти операции всё равно нужно делать безопасными для повторного выполнения.
4. **У кода Workflow есть ограничения**
   Поскольку Temporal восстанавливает Workflow через deterministic replay, нельзя относиться к коду Workflow точно так же, как к обычному коду приложения. Операции, результат которых может меняться, например запросы к базе данных или вызовы внешних API, как правило, должны выполняться в Activity.

## Итоги

Temporal полезен, когда координация процесса сама превращается в серьёзную инженерную задачу. Нужно выполнить несколько шагов по порядку, обрабатывать сбои с помощью retries, а сам процесс может днями ждать внешнего события. Отслеживать всё это при падениях серверов может взять на себя Temporal, а твоё приложение описывает последовательность шагов в коде.

Но вместе с этим появляется и ответственность. Код workflow должен вести себя одинаково при replay, а внешние операции должны быть безопасны для повторного вызова. Temporal сохраняет историю выполнения и координирует восстановление, но решать, что делать, если платёж не прошёл, товар закончился или клиент отменил заказ, всё равно приходится твоему приложению.

На собеседовании начни с процесса, который ты проектируешь, и объясни, где ему нужно восстанавливаться после сбоев или ждать внешнего ввода. Если хватает очереди и worker, оставь всё просто. Если иначе тебе пришлось бы самому строить и поддерживать отслеживание состояния, retries и восстановление для многошагового процесса, то у тебя есть конкретная причина подключить Temporal.

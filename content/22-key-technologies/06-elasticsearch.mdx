Узнай, как с помощью Elasticsearch решать множество задач по system design.

Во многих задачах по system design есть поиск и извлечение данных: у меня много «вещей», и мне нужно находить среди них нужные. Большинство баз данных неплохо справляются с этим (например, Postgres с full-text index подходит для многих задач!), но при определённом масштабе или уровне сложности лучше взять специализированную систему. Обычно для этого нужны похожие возможности: сортировка, фильтрация, ранжирование, faceting и так далее. Тут на сцену выходит один из самых известных поисковых движков: **Elasticsearch**.

С точки зрения интервью этот deep dive раскрывает Elasticsearch с двух сторон:

1. Во-первых, ты узнаешь, как *пользоваться* Elasticsearch. Это мощный инструмент в твоём арсенале. Задача на поиск и извлечение данных, которая окажется слишком сложной для Elasticsearch, встречается редко. Если ты идёшь на интервью в стартап или на интервью по product architecture, знание Elasticsearch поможет. Если ты уже работал с ним, этот раздел можно пропустить!
2. Во-вторых, ты узнаешь, как Elasticsearch *работает* изнутри. Это выдающийся образец инженерии распределённых систем, и в нём сходится много идей, которые пригодятся и за пределами задач на поиск. А некоторые въедливые интервьюеры (я такой не один, честное слово!) могут попросить тебя представить, что Elasticsearch не существует, и самому объяснить некоторые из ключевых концепций. Чаще это бывает на ролях, связанных с инфраструктурой, особенно в облачных компаниях.

Elasticsearch — огромный проект, который развивается больше десяти лет, поэтому в нём масса возможностей, которых мы здесь не коснёмся. Но по мере того как мы будем погружаться в него всё глубже, постараемся разобрать самое важное. Поехали.

## Базовые концепции

Начнём с терминов. С точки зрения клиента важные понятия Elasticsearch — это documents, indices, mappings и fields.

![Иллюстрация](/content/deep-dives--elasticsearch/4ce4c463a4.svg)

Ключевые концепции

### Documents

**Documents** — это отдельные единицы данных, по которым ты ищешь. «Документ» не обязан быть сайтом или записью в блоге, так что не цепляйся за термин. Думай о нём как о любом JSON-объекте. Например, как о книгах в нашем книжном магазине:

```
{
  "id": "XYZ123",
  "title": "The Great Gatsby",
  "author": "F. Scott Fitzgerald",
  "price": 10.99,
  "createdAt": "2024-01-01T00:00:00.000Z"
}
```

### Indices

**Index** — это коллекция документов. Каждый документ связан с уникальным ID и набором fields — пар «ключ-значение», в которых лежат данные, по которым ты ищешь. Думай об index как о таблице в базе данных. Поиск выполняется по этим index и возвращает документы, которые соответствуют критериям поиска.

Обрати внимание: этот термин перегружает более общее слово «index», которым часто называют вспомогательные структуры данных, ускоряющие поиск. Чтобы не путаться, мы будем уточнять, о каком «index» идёт речь.

Мы создадим index для наших книг, но у нас могут быть index для любых сущностей, важных для бизнеса: отзывов, пользователей, заказов и так далее.

### Mappings и Fields

Наконец, **mapping** — это схема index. Она определяет, какие **fields** будут в index, тип данных каждого field и другие свойства, например как field обрабатывается и индексируется. В документ можно положить любые данные, но именно mapping определяет, по каким fields можно искать и какого типа в них данные.

Эти типы могут быть сколь угодно сложными. Например, внутри документов можно вкладывать объекты и массивы, использовать специальные геопространственные типы вроде geo\_point и geo\_shape, определять собственные analyzer или даже использовать embeddings для семантического поиска. Мы не будем разбирать всё это, но если подозреваешь, что для поиска тебе понадобится что-то ещё, велика вероятность, что в Elasticsearch это уже есть.

Вот пример mapping:

```
{
  "properties": {
    "id": { "type": "keyword" },
    "title": { "type": "text" },
    "author": { "type": "text" },
    "price": { "type": "float" },
    "createdAt": { "type": "date" }
  }
}
```

Mapping критически важен, потому что он сообщает Elasticsearch, как интерпретировать данные, которые ты сохраняешь. Например, в mapping выше мы определяем id как тип keyword. Это значит, что field id рассматривается как цельное значение, а не как строка, которую можно разбить на токены. Это важно, потому что позволяет искать и сортировать эффективнее. Обычно я ищу по одному значению id (думай: hash table!), а поиск по title может включать запросы, проверяющие, *содержит* ли заголовок определённое значение (думай: reverse index!).

Mapping также заметно влияет на производительность кластера: если включить в mapping много fields, которые на самом деле не используются в поиске, это увеличивает расход памяти каждого index. Это может привести к проблемам с производительностью и росту затрат. Допустим, у объекта User 10 fields, а искать разрешено только по двум. Если ты замапишь весь объект, то потратишь память на 8 fields, которые не используешь. Это важно, потому что значительная часть контроля над производительностью запросов достигается настройкой mapping и различных параметров кластера. К этому мы вернёмся позже.

## Базовое использование

Теперь пройдёмся по ряду операций: создадим index, сохраним немного данных и выполним поиск, чтобы получить представление об основной функциональности. У Elasticsearch удобный и аккуратный REST API, так что эти операции выполнять легко, хотя GUI и клиентов тоже хватает.

### Создание index

Простой PUT-запрос создаст index с dynamic mapping, 1 shard и 1 replica. Эти параметры можно изменить после создания index.

```
// PUT /books
{
  "settings": {
    "number_of_shards": 1,
    "number_of_replicas": 1
  }
}
```

### Настройка mapping

Если dynamic mapping не подходит (например, большинство полей в моих данных не нужны для поиска), я могу заранее задать mapping для index. Так Elasticsearch узнает, что определённые поля нужно считать доступными для поиска, и какие типы в них ожидать.

```
// PUT /books/_mapping
{
  "properties": {
    "title": { "type": "text" },
    "author": { "type": "keyword" },
    "description": { "type": "text" },
    "price": { "type": "float" },
    "publish_date": { "type": "date" },
    "categories": { "type": "keyword" },
    "reviews": {
      "type": "nested",
      "properties": {
        "user": { "type": "keyword" },
        "rating": { "type": "integer" },
        "comment": { "type": "text" }
      }
    }
  }
}
```

Здесь я заранее зарегистрировал поля, по которым хочу искать в своём книжном магазине. Когда я добавлю документы, Elasticsearch извлечёт значения этих полей и проиндексирует их, чтобы по ним можно было искать.

Mapping может быть очень сложным и меняться со временем, по мере того как добавляются данные и появляются новые сценарии использования. Один из примеров — вложенное поле review. Здесь каждый отзыв — это nested-документ со своими полями. Это отличается от плоской структуры, где каждый отзыв хранится как отдельный документ.

Решение о том, вкладывать ли отзывы в документы отдельных книг, во многом зависит от паттернов обновления данных и запросов, и именно за него может зацепиться придирчивый интервьюер. Если отзывы обновляются редко, а запрашиваются часто, эффективнее может быть вложить их в документы книг. В противном случае, скорее всего, стоит создать отдельный index для отзывов. Это похоже на компромисс между нормализацией и денормализацией, который тебе может быть знаком по работе с SQL-базами.

### Добавление документов

Итак, index и mapping у нас есть. Теперь нужно добавить в index документы! Для этого достаточно простого HTTP POST на endpoint /\_doc.

```
// POST /books/_doc
{
  "title": "The Great Gatsby",
  "author": "F. Scott Fitzgerald",
  "description": "A novel about the American Dream in the Jazz Age",
  "price": 9.99,
  "publish_date": "1925-04-10",
  "categories": ["Classic", "Fiction"],
  "reviews": [
    {
      "user": "reader1",
      "rating": 5,
      "comment": "A masterpiece!"
    },
    {
      "user": "reader2",
      "rating": 4,
      "comment": "Beautifully written, but a bit sad."
    }
  ]
}
```

Если я хочу добавить ещё один документ, я делаю ещё один запрос.

```
// POST /books/_doc
{
  "title": "To Kill a Mockingbird",
  "author": "Harper Lee",
  "description": "A novel about racial injustice in the American South",
  "price": 12.99,
  "publish_date": "1960-07-11",
  "categories": ["Classic", "Fiction"],
  "reviews": [
    {
      "user": "reader3",
      "rating": 5,
      "comment": "Powerful and moving."
    }
  ]
}
```

Каждый из этих запросов вернёт ID документа и данные о том, как документ был сохранён в кластере.

```
{
  "_index": "books",
  "_id": "kLEHMYkBq7V9x4qGJOnh",
  "_version": 1, // NOTE!
  "result": "created",
  "_shards": {
    "total": 2,
    "successful": 1,
    "failed": 0
  },
  "_seq_no": 0,
  "_primary_term": 1
}
```

Обрати особое внимание на поле \_version. Elasticsearch использует его, чтобы документ можно было обновлять атомарно.

### Обновление документов

Обновление документа похоже на его создание, но в URL нужно указать ID документа. Мы *можем* поднять цену, передав документ целиком:

```
// PUT /books/_doc/kLEHMYkBq7V9x4qGJOnh
{
  "title": "To Kill a Mockingbird",
  "author": "Harper Lee",
  "description": "A novel about racial injustice in the American South",
  "price": 13.99,
  "publish_date": "1960-07-11",
  "categories": ["Classic", "Fiction"],
  "reviews": [
    {
      "user": "reader3",
      "rating": 5,
      "comment": "Powerful and moving."
    }
  ]
}
```

В некоторых случаях это уместно, но так делать рискованно! Если другой процесс одновременно обновляет тот же документ, ты можешь перезаписать его изменения.

Чтобы от этого защититься, можно использовать поле \_version из примера выше и указать, что документ нужно обновлять, только если версия совпадает. Следующий запрос обновит документ, только если его версия равна 1. Иначе вернётся ошибка.

```
// PUT /books/_doc/kLEHMYkBq7V9x4qGJOnh?version=1
...
```

Эти ошибки дают клиентам возможность обработать конфликт и повторить запрос. Это простой пример [optimistic concurrency control](https://en.wikipedia.org/wiki/Optimistic_concurrency_control).

Наконец, endpoint \_update (обрати внимание на POST) позволяет обновить отдельные поля документа, не получая документ целиком.

```
// POST /books/_update/kLEHMYkBq7V9x4qGJOnh
{
  "doc": {
    "price": 14.99
  }
}
```

Чем это полезно клиентам, понятно, но помни, что Elasticsearch распределённый, асинхронный и конкурентный. Твой запрос потенциально отправляется на много разных узлов, и запросы могут приходить не по порядку. Явное указание семантики обновления гарантирует, что обновления пройдут так, как ты ожидаешь.

Запомни эти механики для вопросов по дизайну API на интервью. Некоторые компании и форматы интервью копают в дизайн API гораздо глубже, а изучение популярных open source проектов — отличный способ прокачать этот навык.

### Поиск

Итак, у нас есть index с документами. Как по ним искать? Elasticsearch делает это просто! Синтаксис запросов Elasticsearch очень похож на SQL, к тому же он основан на JSON, поэтому с ним очень удобно работать.

Простой запрос — найти книги со словом "Great" в названии:

```
// GET /books/_search
{
  "query": {
    "match": {
      "title": "Great"
    }
  }
}
```

Это тело в GET-запросе? И да, и нет. Elasticsearch отвечает на GET-запросы с телом, а если у тебя педантичный proxy, придётся упаковать этот объект в query string или использовать POST endpoint. Я написал так, чтобы было удобнее читать.

Также можно найти книги со словом "Great" в названии и ценой меньше 15 долларов:

```
// GET /books/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "title": "Great" } },
        { "range": { "price": { "lte": 15 } } }
      ]
    }
  }
}
```

Наконец, можно искать по вложенному полю "reviews" книги с отзывом "excellent":

```
// GET /books/_search
{
  "query": {
    "nested": {
      "path": "reviews",
      "query": {
        "bool": {
          "must": [
            { "match": { "reviews.comment": "excellent" } },
            { "range": { "reviews.rating": { "gte": 4 } } }
          ]
        }
      }
    }
  }
}
```

Ответ может выглядеть так:

```
{
  "took": 7,
  "timed_out": false,
  "_shards": {
    "total": 5,
    "successful": 5,
    "skipped": 0,
    "failed": 0
  },
  "hits": {
    "total": {
      "value": 2,
      "relation": "eq"
    },
    "max_score": 2.1806526,
    "hits": [
      {
        "_index": "books",
        "_type": "_doc",
        "_id": "1",
        "_score": 2.1806526,
        "_source": {
          "title": "The Great Gatsby",
          "author": "F. Scott Fitzgerald",
          "price": 12.99
        }
      },
      {
        "_index": "books",
        "_type": "_doc",
        "_id": "2",
        "_score": 1.9876543,
        "_source": {
          "title": "Great Expectations",
          "author": "Charles Dickens",
          "price": 10.50
        }
      }
    ]
  }
}
```

Мы используем mapping и применяем к данным набор ограничений/фильтров, чтобы получить результат. Результаты содержат ID документов подходящих книг, оценки на основе релевантности (об этом через минуту) и исходные документы (в нашем случае это JSON моих книг), если я явно не указал иное.

### Геопространственный поиск

Одна из самых мощных (и важных для интервью) возможностей Elasticsearch — нативная поддержка геопространственных данных. Если ты проектируешь что-то вроде Yelp, Uber или любого другого сервиса на основе геолокации, именно здесь Elasticsearch по-настоящему выигрывает у традиционной реляционной базы.

Elasticsearch поддерживает два основных геопространственных типа полей:

* **geo\_point**: хранит одну пару широта/долгота. Используй для таких вещей, как расположение ресторанов, check-in пользователей или адреса доставки.
* **geo\_shape**: хранит произвольные геометрии — полигоны, линии, окружности, ограничивающие прямоугольники. Используй для зон доставки, границ городов или зон покрытия сервиса.

Чтобы использовать геопространственный поиск, сначала нужно определить тип поля в mapping:

```
{
  "properties": {
    "name": { "type": "text" },
    "location": { "type": "geo_point" },
    "delivery_zone": { "type": "geo_shape" }
  }
}
```

Затем при добавлении документа укажи координаты:

```
// POST /restaurants/_doc
{
  "name": "Joe's Pizza",
  "location": { "lat": 40.7128, "lon": -74.0060 },
  "delivery_zone": {
    "type": "polygon",
    "coordinates": [[[-74.01, 40.71], [-74.00, 40.71], [-74.00, 40.72], [-74.01, 40.72], [-74.01, 40.71]]]
  }
}
```

Теперь можно выполнять геопространственные запросы. Самый распространённый — geo\_distance, который находит документы в радиусе от точки:

```
// GET /restaurants/_search
{
  "query": {
    "geo_distance": {
      "distance": "5km",
      "location": { "lat": 40.7128, "lon": -74.0060 }
    }
  }
}
```

Его можно комбинировать с другими фильтрами в bool query — например, найти итальянские рестораны в радиусе 2 миль, отсортированные по рейтингу. Именно такой многогранный поиск делает Elasticsearch естественным выбором для приложений на основе геолокации.

Под капотом Elasticsearch использует сочетание стратегий геопространственного индексирования — включая [geohashes](https://en.wikipedia.org/wiki/Geohash), [BKD trees](/lessons/key-technologies/proximity-search) (вариант k-d trees, оптимизированный для блочного хранения) и структуры, похожие на R-tree, — чтобы такие запросы работали быстро даже на миллионах документов. Тип geo\_point использует именно BKD tree для индексации координат, что позволяет Elasticsearch эффективно сужать пространство поиска по двум измерениям без ограничений обычного B-tree index по широте и долготе по отдельности.

### Сортировка

Когда мы сузили результаты до набора интересных, на наш взгляд, книг, как отсортировать их так, чтобы лучшие результаты оказались у пользователей вверху страницы?

Сортировка — важнейшая возможность Elasticsearch, позволяющая упорядочивать результаты поиска по определённым полям.

#### Базовая сортировка

Чтобы отсортировать результаты, используй параметр sort в поисковом запросе. Вот простой пример, который сортирует книги по цене по возрастанию:

```
// GET /books/_search
{
  "sort": [
    { "price": "asc" }
  ],
  "query": {
    "match_all": {}
  }
}
```

Можно сортировать и по нескольким полям. Например, по цене по возрастанию, а затем по дате публикации по убыванию:

```
// GET /books/_search
{
  "sort": [
    { "price": "asc" },
    { "publish_date": "desc" }
  ],
  "query": {
    "match_all": {}
  }
}
```

#### Сортировка по скрипту

Elasticsearch также позволяет сортировать по пользовательским скриптам (на языке "Painless"). Это полезно, когда нужно отсортировать по вычисляемому значению. Вот пример, который сортирует книги по цене со скидкой (10%), чего ты на практике никогда бы не стал делать, потому что порядок сортировки получится тем же:

```
// GET /books/_search
{
  "sort": [
    {
      "_script": {
        "type": "number",
        "script": {
          "source": "doc['price'].value * 0.9"
        },
        "order": "asc"
      }
    }
  ],
  "query": {
    "match_all": {}
  }
}
```

#### Сортировка по nested-полям

При работе с nested-полями нужно использовать nested sort. Он гарантирует, что значения для сортировки берутся из одного и того же nested-объекта. Вот как можно отсортировать книги по самому высокому рейтингу отзыва:

```
// GET /books/_search
{
  "sort": [
    {
      "reviews.rating": {
        "order": "desc",
        "mode": "max",
        "nested": {
          "path": "reviews"
        }
      }
    }
  ],
  "query": {
    "match_all": {}
  }
}
```

#### Сортировка по релевантности

Если порядок сортировки не указан, Elasticsearch сортирует результаты по оценке релевантности (\_score). Это настраивается, но алгоритм оценки по умолчанию тесно связан с [TF-IDF](https://en.wikipedia.org/wiki/Tf%E2%80%93idf) (Term Frequency-Inverse Document Frequency).

Если ты ещё не слышал про TF-IDF, потрать на него 10 минут и [почитай](https://en.wikipedia.org/wiki/Tf%E2%80%93idf): он полезен в самых разных контекстах!

### Пагинация и cursors

Последнее, что нужно решить после того, как мы определились с фильтрацией и сортировкой результатов, — как отдавать их пользователю, то есть как их пагинировать. Пагинация в Elasticsearch позволяет получать подмножество результатов поиска, как правило, чтобы показывать их на нескольких страницах. Нам нужно решить, как мы будем задавать результаты на каждой странице (по номеру или по критериям фильтрации), а также стоит ли хранить состояние или заново выполнять поисковый запрос на каждой странице/при каждом запросе.

#### Пагинация From/Size

Это самая простая форма пагинации, где ты задаёшь:

* from: индекс, с которого начинаются результаты
* size: количество возвращаемых результатов

Пример запроса:

```
// GET /my_index/_search
{
  "from": 0,
  "size": 10,
  "query": {
    "match": {
      "title": "elasticsearch"
    }
  }
}
```

Однако этот метод становится неэффективным при глубокой пагинации (например, за пределами 10 000 результатов) из-за накладных расходов на сортировку и получение всех предшествующих документов. Кластеру приходится извлекать и сортировать все эти документы при каждом запросе, а это может оказаться слишком дорого.

#### Search After

Этот метод эффективнее для глубокой пагинации. Он использует значения сортировки последнего результата как границу для следующего поиска. Elasticsearch возвращает подходящие документы, которые в порядке сортировки идут после этой границы, вместо того чтобы собирать и пропускать все предыдущие страницы.

Пример:

```
// GET /my_index/_search
{
  "size": 10,
  "query": {
    "match": {
      "title": "elasticsearch"
    }
  },
  "sort": [
    {"date": "desc"},
    {"_id": "desc"}
  ],
  "search_after": [1463538857, "654323"]
}
```

Параметр search\_after использует значения сортировки из последнего результата предыдущей страницы. Вот как это работает:

1. В первом запросе параметр search\_after не указывается.
2. Из результатов первого запроса ты берёшь значения сортировки последнего документа.
3. Эти значения сортировки становятся параметром search\_after для следующего запроса.

В примере выше:

* 1463538857 — это timestamp (значение поля date у последнего документа на предыдущей странице).
* "654323" — это \_id последнего документа на предыдущей странице.

Эти значения — закладка в отсортированных результатах, а не адрес на диске. Elasticsearch всё равно выполняет запрос для следующей страницы.

Если между запросами документы добавляются или изменяются, результаты могут сдвинуться относительно этой закладки. Ты можешь пропустить документ или увидеть его дважды. Если нужен согласованный срез данных, используй point in time (PIT). Кроме того, клиент должен сохранять значения сортировки последнего документа, а листать можно только вперёд.

#### Cursors

Cursors в Elasticsearch дают stateful-способ пагинации по результатам поиска и решают проблему «уплывающих» из-под ног документов. Cursors обеспечивают согласованность между запросами пагинации, поэтому требуют намного больше накладных расходов, чем уже рассмотренные методы.

Для пагинации на основе cursors Elasticsearch использует point in time (PIT) API вместе с search\_after:

1. **Создай PIT**:

```
// POST /my_index/_pit?keep_alive=1m
```

Это возвращает PIT ID.

2. **Используй PIT в поисковых запросах**:

```
// GET /_search
{
  "size": 10,
  "query": {
    "match": {
      "title": "elasticsearch"
    }
  },
  "pit": {
    "id": "46To...",
    "keep_alive": "1m"
  },
  "sort": [
    {"_score": "desc"},
    {"_id": "asc"}
  ]
}
```

3. **Для последующих страниц добавь search\_after**:

```
// GET /_search
{
  "size": 10,
  "query": {
    "match": {
      "title": "elasticsearch"
    }
  },
  "pit": {
    "id": "46To...",
    "keep_alive": "1m"
  },
  "sort": [
    {"_score": "desc"},
    {"_id": "asc"}
  ],
  "search_after": [1.0, "1234"]
}
```

4. **Закрой PIT, когда закончишь**:

```
// DELETE /_pit
{
  "id" : "46To..."
}
```

Использование PIT вместе с search\_after даёт согласованный срез данных на протяжении всей пагинации, даже если нижележащий индекс обновляется.

## Как это работает

Ура! Теперь, когда ты в общих чертах понимаешь, как использовать Elasticsearch на стороне клиента, логичный следующий шаг — разобраться, как он устроен внутри. Как реализована каждая из этих операций?

Elasticsearch можно рассматривать как high-level фреймворк оркестрации поверх Apache Lucene — сильно оптимизированной низкоуровневой библиотеки поиска. Elasticsearch берёт на себя аспекты распределённых систем: координацию кластера, API, агрегации и возможности реального времени, а «сердце» поиска — это Lucene.

Здесь хватит материала на несколько часов разговора, поэтому начнём с high-level архитектуры кластера Elasticsearch, а затем погрузимся в самые интересные части индексации и поиска.

## Архитектура кластера

### Типы нод

Elasticsearch — это *распределённый* поисковый движок. Когда ты поднимаешь кластер Elasticsearch, на самом деле ты запускаешь сразу несколько нод. Ноды бывают 5 типов, и тип задаётся при запуске инстанса.

* **Master Node** отвечает за координацию кластера. Это единственная нода, которая может выполнять операции уровня кластера: добавлять и удалять ноды, создавать и удалять индексы. Можно думать о ней как об «админе».
* **Data Node** отвечает за хранение данных. Именно здесь реально лежат твои данные. В большом кластере таких нод много.
* **Coordinating Node** отвечает за координацию поисковых запросов по кластеру. Это нода, которая получает поисковый запрос от клиента и отправляет его на нужные ноды. Это фронтенд твоего кластера.
* **Ingest Node** отвечает за приём данных. Здесь данные преобразуются и готовятся к индексации.
* **Machine Learning Node** отвечает за задачи машинного обучения.

Эти ноды взаимодействуют довольно прямолинейно. Вот диаграмма последовательности: Ingest-ноды загружают данные в Data-ноды, а затем к ним обращаются через Coordinating-ноды:

![Иллюстрация](/content/deep-dives--elasticsearch/ddc9008cb8.svg)

Диаграмма последовательности

Каждый инстанс Elasticsearch может относиться сразу к нескольким типам, а тип определяется конфигурацией ноды. Например, инстанс можно настроить как master-eligible-ноду И coordinating-ноду. В более сложных развёртываниях под каждый тип могут быть выделенные хосты (например, хост для ingest-ноды может упираться в CPU и иметь много процессоров, а хост для data-ноды — иметь быстрый disk I/O или больше памяти).

У каждого из этих типов нод есть и свои специализации. Например, data-ноды бывают hot, warm, cold или frozen в зависимости от того, насколько вероятно обращение к данным (например, свежие они или нет) и могут ли они меняться.

При старте кластера ты задаёшь список seed-нод (они master-eligible), которые запускают алгоритм leader election, чтобы выбрать master для кластера. В каждый момент времени активным master должна быть только одна нода, а остальные master-eligible ноды находятся в режиме ожидания.

Ingest- и coordinating-ноды интересны, но именно в data-нодах происходит вся магия поиска, так что начнём с них.

### Data-ноды

Основная задача data-нод — хранить документы и обеспечивать их быстрый поиск. Elasticsearch делает это, разделяя «сырые» данные \_source (помнишь, мы видели их в результатах поиска выше?) и индексы Lucene, которые используются при поиске. Можно представить это как отдельную document database.

Запросы выполняются в две фазы: сначала фаза «query», когда релевантные документы определяются с помощью оптимизированных структур данных индекса, а затем фаза «fetch», когда эти идентификаторы документов (опционально) извлекаются с нод.

Идеальные запросы — те, на которые можно ответить, вообще не обращаясь к исходным документам; иногда для этого нужные данные переносят в индекс через включаемые поля.

Data-ноды хранят наши индексы (из предыдущих разделов), которые состоят из shard и их replica. Внутри этих shard находятся индексы Lucene, которые состоят из сегментов Lucene.

![Иллюстрация](/content/deep-dives--elasticsearch/0a9479709c.svg)

Матрёшки Elasticsearch

Shard позволяют Elasticsearch делить данные (и соответствующие индексы) между хостами. Благодаря этому Elasticsearch распределяет и твои документы, и соответствующие структуры индекса по нескольким нодам кластера, что заметно повышает производительность и масштабируемость.

Поиск выполняется параллельно по всем релевантным shard, а результаты объединяются и сортируются на coordinating-ноде. Запросы, как правило, выполняются на coordinating-ноде, которая затем распределяет запрос по нужным shard.

Replica — это точная копия shard. Elasticsearch позволяет создавать одну или несколько копий shard твоего индекса; они называются replica shard, или просто replica.

Replica служат двум основным целям: высокая доступность и рост throughput. Если наш shard справляется с X TPS, то при Y replica мы справимся с X \* Y TPS (при прочих равных).

Coordinating-нода может использовать replica для повышения производительности поиска, распределяя поисковые запросы по всем доступным копиям shard (primary и replica) и фактически балансируя поисковую нагрузку по кластеру.

Наконец, shard в Elasticsearch соотносятся с индексами Lucene 1:1. Напомню, что Lucene — это низкоуровневая, сильно оптимизированная библиотека поиска в основе Elasticsearch. Многие операции, которые Elasticsearch выполняет над shard (merge, split, refresh, поиск), на деле проксируются в индексы Lucene под ними.

На этом этапе Elasticsearch можно сильно упростить: это куча доступности и масштабируемости поверх большого набора индексов Lucene.

#### CRUD сегментов Lucene

Индексы Lucene состоят из сегментов — базовой единицы нашего поискового движка. Сегменты — это **неизменяемые (immutable)** контейнеры проиндексированных данных. Дай этому слову осесть на секунду, прежде чем мы пойдём дальше. Разве нам не нужно уметь обновлять, добавлять и удалять документы в индексе Elasticsearch?

![Иллюстрация](/content/deep-dives--elasticsearch/c088eb29f4.svg)

Сегменты Lucene

Индексы Lucene работают так: записи накапливаются в батчи, из которых строятся segments. Когда мы вставляем документ, он не сразу попадает в индекс. Сначала он добавляется в segment. Когда набирается батч документов, мы строим segment и сбрасываем его на диск.

Когда segments становится слишком много, их можно слить (merge): мы создаём новый segment из тех, которые хотим объединить, и удаляем старые.

С удалениями всё хитрее: у каждого segment есть набор идентификаторов удалённых документов. Когда segment запрашивают по удалённому документу, он делает вид, что такого документа нет, но данные при этом всё ещё лежат на месте! Во время merge объединяемые segments вычищают удалённые документы.

Наконец, при обновлении мы на самом деле не изменяем segment. Вместо этого мы *мягко* удаляем (soft delete) старый документ и вставляем новый с обновлёнными данными. Старый документ будет вычищен позже, при merge. Благодаря этому удаления выполняются очень быстро, но до тех пор, пока мы не сольём и не почистим segments, остаются заметные потери производительности. В идеале так делать нужно нечасто!

Обрати внимание: обновления на самом деле работают *медленнее*, чем вставки, потому что нужно вести учёт soft-удалений. Отчасти поэтому Elasticsearch плохо подходит для данных, которые быстро и часто обновляются.

У такой иммутабельной архитектуры для Lucene есть ряд преимуществ:

1. Выше производительность записи: новые документы быстро добавляются в новые segments, не затрагивая существующие.
2. Эффективное кеширование: поскольку segments иммутабельны, их можно безопасно держать в памяти или на SSD, не беспокоясь о проблемах консистентности.
3. Проще конкурентность: операциям чтения не нужно переживать, что данные изменятся посреди запроса, поэтому конкурентный доступ упрощается.
4. Проще восстановление: после сбоя легче восстановиться из иммутабельных segments, ведь их состояние известно и консистентно.
5. Лучше сжатие: иммутабельные данные можно сжимать эффективнее, экономя место на диске.
6. Быстрее поиск: иммутабельность позволяет использовать оптимизированные структуры данных и алгоритмы поиска.

Но у такого дизайна есть и сложности: нужны периодические merge segments, а до очистки временно требуется больше места для хранения. В Elasticsearch и Lucene есть продуманные механизмы, которые позволяют эффективно управлять этими компромиссами.

Подобные дизайнерские решения (как обратить иммутабельность себе на пользу) очень важны на интервью по system design для систем, работающих с большими объёмами данных! Надеюсь, они подскажут тебе идеи для других систем, которые ты будешь проектировать.

#### Возможности segments в Lucene

Segments — это не просто контейнеры с данными документов: в них также лежат хорошо оптимизированные структуры данных для поисковых операций. Две самые важные из них — inverted index и doc values.

##### Inverted Index

Если Lucene — сердце Elasticsearch, то inverted index — сердце Lucene. По сути, чтобы сделать поиск быстрым, есть два пути:

1. Организовать данные в соответствии с тем, как ты хочешь их получать. Если нужно искать конкретные элементы, то плохой выбор — таблица, где приходится просматривать каждый элемент (O(n)), лучше — отсортированный список (O(log(n))), а лучшая стратегия — хеш-таблица (O(1)).
2. Скопировать данные и организовать копию по принципу из пункта (1).

Представим, что у нас 1 миллиард книг, и лишь в небольшом числе из них в названии встречается слово "lazy". Нужно написать код, который найдёт все книги со словом "lazy" как можно быстрее. Как это сделать?

![Иллюстрация](/content/deep-dives--elasticsearch/be8a4e4984.svg)

Inverted Index

Inverted index — это структура данных, хранящая отображение от содержимого, например слов или чисел, к его расположению в базе данных, а в нашем случае — в документах. Именно это делает поиск по ключевым словам в Elasticsearch быстрым. В нём перечислено каждое уникальное слово, встречающееся хоть в одном документе, и указаны все документы, в которых оно есть. В нашем случае это отображение строк вроде "lazy" на документы, содержащие этот токен (на схеме выше — документы #12 и #53).

Теперь, чтобы найти документы со словом "lazy", не нужно сканировать каждый документ: достаточно заглянуть в inverted index и найти нужные документы за константное время.

Мы использовали оба пункта (1) и (2): создав копии данных и грамотно их организовав, мы превратили сканирование за O(n) в поиск за O(1). Красиво!

##### Doc Values

А что, если теперь нужно отсортировать *эти* результаты по цене? Здесь в игру вступают doc values. В документах есть множество других полей, вроде автора, названия и так далее, а нам нужна только цена для всех найденных результатов. Это очень частая проблема для строково-ориентированных (row-oriented) баз данных, например реляционных! Даже если мне нужен всего один столбец, приходится читать всю строку и выбирать из неё нужное поле.

Секрет производительности аналитических рабочих лошадок вроде Spark или AWS Redshift в том, что они хранят данные в колоночном формате в непрерывных блоках памяти. Когда ты запрашиваешь столбец, ты по сути просто читаешь непрерывный блок памяти. Структура doc values делает именно это: хранит колоночное, непрерывное представление одного поля для всех документов в segment. Inverted index даёт нам отображение токенов на документы, а doc values — данные, которые нужны для финальной сортировки.

### Coordinating Nodes

Помнишь, мы говорили, что Elasticsearch — это распределённая система? Coordinating nodes принимают запросы от конечных клиентов и координируют их выполнение по всему кластеру. Это точка входа для пользовательского запроса: они разбирают запрос, определяют, какие узлы за него отвечают, и возвращают результаты пользователю.

Один из важнейших шагов выполнения на coordinating node — планирование запроса (query planning). **Query planners** — это алгоритмы, определяющие самый эффективный способ выполнить поисковый запрос. После того как coordinating node разобрала запрос, query planner оценивает, как лучше всего получить нужные документы. Это включает решение, использовать ли inverted index, выбор оптимального порядка выполнения частей запроса и организацию того, как объединять результаты от нескольких узлов.

#### Оптимизация порядка выполнения

Давай объясним это простыми словами. Ты ищешь среди миллионов документов строку "bill nye". В твоём inverted index у "bill" миллионы записей, а у "nye" — несколько сотен. Как поступить?

1. Можно построить hash set из всех документов, содержащих "nye", затем пройтись по документам, содержащим "bill", искать пересечение, а потом выполнить строковый поиск по "bill nye".
2. Можно построить hash set из всех документов, содержащих "bill", затем пройтись по документам, содержащим "nye", искать пересечение, а потом выполнить строковый поиск по "bill nye".
3. Можно загрузить все документы, содержащие "nye", и выполнить в них строковый поиск по "bill nye".
4. Можно загрузить все документы, содержащие "bill", и выполнить в них строковый поиск по "bill nye".
5. ...

Вариантов много! А разница в производительности между ними может достигать порядков.

Ведя статистику по типам имеющихся полей, популярным ключевым словам и длине документов, query planner в Elasticsearch выбирает среди вариантов тот, который минимизирует время ответа пользователю. Эта оптимизация критична для сохранения производительности по мере роста объёма и сложности данных.

Если ты готовишься к интервью по system design инфраструктурного типа, эти вопросы должны быть тебе знакомы. Query planners, добавляя слой статистики и уровень косвенности, позволяют системе динамически подстраиваться под данные в индексе. Умение работать с *зависимостью от данных* — как раз то, почему системы баз данных в целом так мощны!

## На собеседовании

Elasticsearch очевидно подходит ко многим вопросам по system design на собеседованиях. Любая задача со сложным поиском — скорее всего хороший кандидат. В большинстве случаев на интервью Elasticsearch подключают через Change Data Capture (CDC) к основному хранилищу данных, например Postgres или DynamoDB.

### Использование Elasticsearch

Что стоит помнить, когда используешь Elasticsearch на собеседовании:

1. Обычно не стоит использовать Elasticsearch как базу данных. Это в первую очередь поисковый движок, и при всей своей мощности он не предназначен для замены традиционной базы. В ранних версиях Elasticsearch было много проблем с consistency и durability, и многие проблемы, которые преследовали CouchDB, преследовали и Elasticsearch. Короче: если данные должны сохраняться, храни их где-то ещё.
2. Elasticsearch рассчитан на нагрузку с преобладанием чтения. Если система write-heavy, стоит рассмотреть другие варианты или добавить write buffer. Может показаться удобным добавить поле, например, с количеством лайков поста или счётчиком показов, но есть много причин, по которым из-за этого Elasticsearch будет испытывать трудности.
3. Учитывай модель eventual consistency в Elasticsearch. Результаты *будут* устаревшими, иногда существенно. Если твой сценарий этого не терпит, возможно, придётся рассмотреть альтернативы.
4. Elasticsearch — *не* реляционная база данных. Данные нужно денормализовать настолько, насколько возможно, чтобы поисковые запросы были эффективными. Для этого может потребоваться дополнительная логика трансформации на стороне записи. Стремись к тому, чтобы результаты выдавались за 1–2 запроса.
5. Не каждой задаче поиска он нужен! Если данных мало (&lt; 100k документов) или они редко меняются, есть много других и более быстрых решений. Посмотри, хватает ли простого запроса к основному хранилищу данных, и рассматривай Elasticsearch, только если его недостаточно.
6. Нужно следить за тем, чтобы Elasticsearch оставался синхронизированным с исходными данными. Сбои синхронизации приводят к drift и часто становятся источником багов при работе с Elasticsearch.

Помни: Elasticsearch — мощный инструмент, но не серебряная пуля. Будь готов обосновать, почему ты выбираешь Elasticsearch, а не другие варианты, и обсудить как его ограничения, так и сильные стороны.

### Чему можно научиться у Elasticsearch

Даже если мы не используем Elasticsearch, из его устройства можно взять ряд уроков для проектирования производительной инфраструктуры:

1. Immutability может быть мощным инструментом, если применять её на правильном уровне стека. Когда данные статичны, их проще кэшировать, сжимать и иначе оптимизировать. Кроме того, не нужно беспокоиться о проблемах синхронизации и целостности, которые гораздо сложнее решать с изменяемыми данными.
2. Разделив выполнение запросов и хранение данных, можно оптимизировать каждую часть независимо. Data nodes и coordination nodes в Elasticsearch прекрасно дополняют друг друга, потому что каждый тип узла сосредоточен на своей зоне ответственности.
3. Стратегии индексации заметно влияют на производительность поиска. Структура inverted index в Elasticsearch обеспечивает быстрый полнотекстовый поиск, а doc values позволяют эффективно сортировать и агрегировать. Проектируя системы, которым нужно быстро извлекать данные, подумай, как структурировать данные под самые частые паттерны запросов.
4. Распределённые системы дают масштабируемость и отказоустойчивость, но добавляют сложность. Кластерная архитектура Elasticsearch позволяет обрабатывать большие объёмы данных и высокую нагрузку запросов, но требует внимательного отношения к consistency данных и network partitions. Проектируя распределённые системы, всегда учитывай компромиссы между consistency, availability и partition tolerance (теорема CAP).
5. Важность эффективных структур данных трудно переоценить. Использование в inverted index Elasticsearch специализированных структур данных, таких как skip lists и finite state transducers, показывает, как подобранные под задачу структуры данных могут радикально повысить производительность в конкретных сценариях. Всегда учитывай паттерны доступа к данным, когда выбираешь или проектируешь структуры данных.

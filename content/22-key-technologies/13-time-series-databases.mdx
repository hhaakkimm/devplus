Разберём концепции, на которых построены time-series databases: LSM trees, append-only storage и delta encoding.

В этом deep dive мы рассмотрим паттерны, которые позволяют time-series databases работать с высоким throughput. Вместе эти идеи дают впечатляющий результат, но каждая из них по отдельности применима гораздо шире, особенно в infra-style вопросах на system design интервью. Мы хотим показать, что ни одна из этих идей не отличается особой сложностью: они простые, а вся магия в том, как их сочетают.

Прежде чем начать, важная оговорка про time series databases в целом: если у тебя есть данные в виде временных рядов, это ещё не значит, что тебе нужна time-series database! [Разбор задачи Top-K](/lessons/breakdowns/top-k) — классический пример, где TSDB кажется полезной, но на деле только усложняет задачу, потому что нам нужно сортировать и агрегировать огромное количество рядов, а для этого большинство TSDB не предназначены.

Будь осторожен и не хватайся за time-series database, когда лучше подойдёт универсальная база вроде Postgres или DynamoDB. Я советую выжимать из универсальных решений максимум и обращаться к специализированным технологиям вроде time-series database, только когда ты упёрся в настоящее узкое место, которое другим способом не решить. Понимание ограничений этих баз (в этом материале) поможет тебе понять, когда они уместны!

Давай разберёмся, как работают time series databases.

### Пример для мотивации

Представь, что ты проектируешь систему мониторинга для облачного провайдера. У тебя 100 000 серверов, каждый из которых каждые 10 секунд отправляет 5 метрик: загрузка CPU, память, disk I/O, сетевой трафик. Это 50 000 метрик в секунду, или 4,3 миллиарда точек данных в день. Пользователи хотят запрашивать эти данные, чтобы смотреть дашборды, настраивать алерты и разбирать проблемы за последнюю неделю.

Попробуем сохранить это в обычном Postgres:

```
CREATE TABLE metrics (
    timestamp TIMESTAMP,
    host VARCHAR(255),
    metric_name VARCHAR(255),
    value DOUBLE PRECISION
);
```

При 4,3 миллиарда строк в день за неделю получается ~30 миллиардов строк. Даже с индексами простые запросы вроде «покажи среднюю загрузку CPU для host-42 за последний час» становятся мучительно медленными, а производительность записи падает по мере добавления индексов. Хуже того, нужный write throughput (минимум 50 000 записей в секунду, а в пиках намного больше) раздавит один инстанс Postgres. Хранение тоже безумно неэффективно: в каждой строке повторно хранятся полное имя хоста и название метрики, из-за чего на одну точку данных уходит 50–100 байт, хотя реальная информация (timestamp и float) занимает всего 16 байт.

Можно сделать *намного* лучше.

Time-series databases вроде InfluxDB, TimescaleDB и Prometheus созданы именно под такую нагрузку. Так как же они работают?

## Строительные блоки

Давай поговорим обо всех компонентах, благодаря которым time series database работает так быстро. Данных в time series databases обычно так много, что единственный реальный вариант — хранение на диске. Поэтому начнём с того, что нам для этого понадобится.

### Append-Only Storage

Первая идея обманчиво проста: **если ты записываешь много данных, не обновляй их на месте**. Вместо этого всегда дописывай новые данные в конец файла.

Почему это важно? Посмотри, как записью занимаются традиционные базы данных. Когда ты обновляешь строку, базе нужно:

1. Найти расположение строки на диске
2. Прочитать текущие данные
3. Изменить их в памяти
4. Записать обновлённые данные обратно

Это random I/O, который чаще всего и становится причиной проблем с производительностью. На обычных жёстких дисках головка должна переместиться в нужное место. Это физический рычаг, который двигается внутри диска, и хотя HDD под такое оптимизированы, они всё равно выполняют лишь 100–200 операций в секунду. Даже SSD, хоть и гораздо быстрее справляются со случайными операциями, из-за своей архитектуры заметно лучше работают с последовательным доступом.

Append-only storage переворачивает подход. Каждая новая точка данных записывается в конец текущего файла. Никаких seek, никакого чтения перед записью — только последовательная запись. SSD выдерживают сотни тысяч последовательных записей в секунду, а даже обычные жёсткие диски справляются с десятками тысяч.

**Запись в традиционной БД:**

```
[Seek to block 4752] → [Read] → [Modify] → [Write] → [Seek to block 9201] → ...
```

**Append-only запись:**

```
[Write to end] → [Write to end] → [Write to end] → ...
```

Random vs. Sequential I/O

Но подожди: если мы только дописываем, как организовать данные для чтения? Здесь в игру вступает следующий компонент.

### LSM Trees (Log-Structured Merge Trees)

LSM trees — секретный ингредиент многих баз данных с высоким write throughput, включая InfluxDB, Cassandra и LevelDB. Возможно, ты помнишь эту идею из нашего [deep dive про Cassandra](/lessons/key-technologies/cassandra) или из [основной концепции про индексацию БД](/lessons/core-concepts/db-indexing): суть в том, чтобы превратить дорогие случайные записи в дешёвые последовательные, а затем периодически перестраивать данные в фоне, чтобы чтение стало эффективнее.

Вот как это работает:

**Шаг 1: запись в память (как в memtable)**
Когда приходят данные, они попадают во внутрипамятный буфер вроде memtable. Memtable обычно реализуется как отсортированная структура данных (например, red-black tree или skip list), поэтому данные остаются упорядоченными по ключу. Запись происходит молниеносно, потому что затрагивает только RAM.

Зачем держать данные отсортированными? Потому что при сбросе на диск мы хотим, чтобы итоговый файл тоже был отсортирован. Отсортированные файлы позволяют использовать binary search для точечных запросов, делают эффективными range-запросы (соседние ключи лежат рядом) и, что критично, дают возможность эффективно сливать несколько файлов с помощью merge sort во время compaction.

**Шаг 2: сброс на диск (как в SSTable)**
Когда memtable заполняется, она записывается на диск как неизменяемый отсортированный файл, который называется SSTable (Sorted String Table). Поскольку memtable уже отсортирована, сброс — это просто последовательная запись от начала до конца, то есть очень быстрая операция. После этого memtable очищается для новых данных.

**Шаг 3: фоновая compaction**
Со временем накапливается много SSTable. Чтение дорожает, потому что может потребоваться проверить несколько файлов. Compaction работает в фоне: сливает маленькие SSTable в более крупные, удаляя дубликаты и tombstones (маркеры удалённых данных).

![Иллюстрация](/content/deep-dives--time-series-databases/f70cb08d60.svg)

LSM Model

Прелесть такого подхода в том, что записи никогда не блокируются чтением. Memtable принимает новые данные, а фоновые потоки упорядочивают старые. Именно это разделение позволяет базам на основе LSM выдерживать устойчиво высокий write throughput.

LSM trees не бесплатны. Производительность чтения может страдать, потому что для поиска значения иногда нужно проверить несколько SSTable. Есть и write amplification: во время compaction данные перезаписываются многократно. Поэтому обращайся к LSM trees, когда у тебя нагрузка с интенсивной записью **и** ты готов пожертвовать частью производительности чтения ради производительности записи.

Итак, с append-only storage и LSM trees мы уже становимся похожи на [Cassandra](/lessons/key-technologies/cassandra). Добавим в картину ещё несколько элементов.

### Delta Encoding и сжатие

У данных временных рядов есть особое свойство: соседние значения часто похожи. Если ты записываешь загрузку CPU каждую секунду, значения могут быть 45.2%, 45.3%, 45.1%, 45.4%. Хранить полное значение каждый раз — пустая трата места.

Delta encoding хранит не абсолютные значения, а разницу между соседними:

```
Raw values:     [45.2] [45.3] [45.1] [45.4]
Delta encoded:  [45.2] [+0.1] [-0.2] [+0.3]
```

Дельты — это гораздо меньшие числа, и для их хранения нужно меньше бит.

Но подожди: разве integer и float не занимают всегда 32 или 64 бита? Не если использовать variable-length encoding. Техники вроде varint (variable-length integer) кодируют малые числа меньшим числом байт: число 1 может занять всего 1 байт, а 1 000 000 — 3 байта. Когда твои дельты крошечные (вроде +1 или -2), ты хранишь 1–2 байта вместо 8. Поэтому превращение больших абсолютных значений в маленькие дельты так сильно окупается.

Time-series databases идут ещё дальше и используют специализированные алгоритмы сжатия.

**Timestamps** используют delta-of-delta encoding. Timestamps во временных рядах часто регулярны, например, раз в 10 секунд. Разница между timestamps может быть постоянной или почти постоянной:

```
Raw timestamps:     1000, 1010, 1020, 1030, 1040
Deltas:             10  , 10  , 10  , 10  , 10  , ...
Delta-of-deltas:    10  , 0   , 0   , 0   , 0   , ...
```

Когда timestamps идеально регулярны, можно закодировать миллионы из них практически без накладных расходов. [Статья Facebook про Gorilla](https://www.vldb.org/pvldb/vol8/p1816-teller.pdf) показала, что эта техника позволяет сжимать timestamps в среднем до 1 бита на значение.

**Значения float** используют сжатие на основе XOR. Если выполнить XOR для двух похожих чисел с плавающей точкой, большинство битов окажутся нулями. После этого эти нули можно закодировать с помощью run-length encoding:

```
Value 1: 0 10000010 01101000101000111101011
Value 2: 0 10000010 01101000110000100000000
XOR:     0 00000000 00000000011000011101011
                    ^^^^^^^^^^ lots of leading zeros
```

Сохраняя только позицию первого отличающегося бита и значимые биты после него, ты существенно сжимаешь каждое значение. На практике для типичных временных рядов это даёт в среднем 1,37 байта на значение — огромное улучшение по сравнению с 8 байтами, которые нужны для необработанного double.

Большинство интервью не заходят на такой уровень детализации, так что не пытайся запоминать «1.37 bytes per value». Главная идея в том, что данные «на диске» (at rest), в которых много избыточности, можно хорошо сжать, а time series данные — отличный тому пример.

### Time-Based Partitioning (шардинг по времени)

Ещё одна ключевая концепция — организация данных по времени. Базы time series группируют данные в partition по временным окнам, например один partition на день или на неделю. Эти partition *не обязательно* живут на разных машинах, но при необходимости для масштабирования вполне могут.

Почему это так эффективно?

**Записи локализованы.** Все входящие данные попадают в текущий временной partition. Не нужно выбирать, какой из множества partition должен принять данные: это всегда partition «сейчас».

**Чтение эффективно.** Когда ты запрашиваешь «покажи данные за последний час», база точно знает, какие partition нужно просмотреть. Ей не нужно сканировать данные за прошлый месяц.

**Retention становится тривиальным.** Хочешь хранить только 7 дней данных? Просто удали partition старше 7 дней. Никаких дорогих запросов DELETE, сканирующих огромную таблицу: достаточно удалить старые файлы.

```
┌─────────────────────────────────────────────────────────┐
│  Query: "Last 2 hours of CPU data for host-42"          │
└─────────────────────────────────────────────────────────┘
                         │                                 
                         ▼                                 
┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
│ Nov 22  │ │ Nov 23  │ │ Nov 24  │ │ Nov 25  │ │ Nov 26  │
│  skip   │ │  skip   │ │  skip   │ │  skip   │ │ ← SCAN  │
└─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘
```

Эта стратегия партиционирования по времени встречается почти во всех базах time series. Ты увидишь её в TimescaleDB (там partition называются «chunks»), в Prometheus и в самописных системах.

Пока что мы говорили об оптимизации записи. А как насчёт чтения?

### Bloom Filters для оптимизации чтения

Вспомни, как работают LSM trees: со временем данные записываются в несколько SSTable. Чтобы найти значение, может понадобиться проверить несколько таких файлов. Каждая проверка — потенциальное чтение с диска. Худший случай — длинный запрос, который охватывает много partition, но ищет всего одно значение или небольшое их количество (например, собирает time series для одного хоста за длительный период).

Bloom filters (подробнее о них в нашем [разборе Data Structures for Big Data](/lessons/key-technologies/data-structures-for-big-data)) решают эту задачу изящно.

Bloom filter — это вероятностная структура данных, которая отвечает «точно нет» или «возможно, есть» без единой операции дискового I/O. Каждая SSTable хранит Bloom filter для всех содержащихся в ней ключей. Когда ты запрашиваешь конкретную серию, база сначала проверяет Bloom filter каждой SSTable. Если фильтр говорит «здесь нет», база полностью пропускает этот файл с абсолютной уверенностью. Ложноположительные срабатывания возможны (фильтр говорит «возможно», а ключа нет), а вот ложноотрицательных не бывает.

```
Query: "Get data for host=server-42"

SSTable-1 Bloom filter: "not here"     → skip (no disk read)
SSTable-2 Bloom filter: "not here"     → skip (no disk read)
SSTable-3 Bloom filter: "maybe here"   → check (disk read)
SSTable-4 Bloom filter: "not here"     → skip (no disk read)
```

На практике хорошо настроенный Bloom filter использует около 10 бит на ключ и даёт 1% ложноположительных срабатываний. Для базы с миллионами серий, разбросанных по десяткам SSTable, это превращает десятки чтений с диска всего в одно-два.

### Downsampling и Rollups

Bloom filters помогают с точечными запросами, но что насчёт агрегирующих запросов по большим временным диапазонам? Сырые метрики с разрешением 10 секунд отлично подходят для отладки недавних проблем, но такая детализация никому не нужна, когда смотришь на данные за прошлый год. Downsampling автоматически снижает разрешение старых данных, жертвуя точностью ради экономии места.

Типичная политика может выглядеть так:

* **Последние 24 часа:** полное разрешение (интервалы по 10 секунд)
* **Последние 7 дней:** средние за 1 минуту
* **Последние 30 дней:** средние за 5 минут
* **Последний год:** средние за 1 час

База вычисляет эти rollups в фоне и хранит предагрегированные значения (обычно min, max, sum, count), с помощью которых можно ответить на большинство запросов, не трогая сырые данные. Когда ты спрашиваешь «какой была средняя загрузка CPU в прошлом месяце?», база читает из таблицы rollup с 5-минутным разрешением — это в 288 раз меньше данных, чем в сырых 10-секундных.

```
Raw data (10s):     [45.2] [45.3] [45.1] [45.4] [45.0] [45.5] ... (8,640 points/day)
1-min rollup:       [min:45.0, max:45.5, avg:45.25, count:6] ... (1,440 points/day)
1-hour rollup:      [min:44.1, max:47.2, avg:45.8, count:360] ... (24 points/day)
```

Это форма предвычислений, которая меняет место на диске и write amplification на кратно более быстрое чтение исторических данных. Если хочешь увидеть downsampling в действии на конкретной задаче, посмотри наш [разбор Ad Click Aggregator](/lessons/breakdowns/ad-click-aggregator), где мы используем этот приём для обработки миллиардов рекламных событий.

Downsampling и rollups часто всплывают на интервью как предмет обсуждения требований. Интервьюер говорит: «нам нужно хранить 10-секундные сэмплы в течение года», а ты отвечаешь: «это огромный объём данных, думаю, мелкое разрешение нужно только за неделю, а дальше можно downsample до 5-минутных средних на месяц... подойдёт?» Главное здесь: (а) ты предвидишь будущую проблему, (б) объясняешь сложность и (в) предлагаешь альтернативу. Даже если интервьюер скажет «нет», он отметит твою способность мыслить за рамками жёстко заданных требований — это отличительная черта кандидата уровня staff+.

### Метаданные на уровне блоков

Наша последняя оптимизация — вариация идей планирования запросов, которые мы разбирали в [разборе Elasticsearch](/lessons/key-technologies/elasticsearch). При сканировании файлов с данными базы time series хранят метаданные о содержимом каждого блока, в частности минимальную и максимальную временные метки, а иногда и минимальное и максимальное значения. Это позволяет отсекать блоки (block pruning) во время выполнения запросов.

Если запрос ищет загрузку CPU выше 10%, а метаданные блока показывают, что в нём только данные в диапазоне 0–5%, база пропускает весь этот блок, не читая его. В сочетании с партиционированием по времени (которое уже ограничивает набор partition для проверки) это даёт ещё один уровень фильтрации, благодаря которому запросы остаются быстрыми даже при росте объёмов данных.

## Собираем всё вместе: storage engine для time-series

Теперь, когда мы разобрались с базовыми блоками, посмотрим, как они сочетаются в типичной архитектуре time-series базы данных.

### Модель данных

Time-series базы данных обычно организуют данные так:

* **Measurements** или **metrics** — аналог таблиц (например, "cpu\_usage", "memory")
* **Tags** — индексируемые метаданные для фильтрации (например, host="server-1", region="us-west")
* **Fields** — сами измеряемые значения (например, value=45.2)
* **Timestamps** — момент, когда было сделано измерение

Точка данных может выглядеть так:

```
cpu_usage,host=server-1,region=us-west value=45.2 1699999200000000000
└─────────────────────────────────────┘ └────────┘ └─────────────────┘
        measurement + tags               field          timestamp
```

Tags критически важны, потому что они индексируются. Запросы с фильтрацией по tags работают быстро. Fields не индексируются: это и есть те самые time-series данные, которые ты хранишь.

Разница между tags и fields многих сбивает с толку. Используй tags для метаданных, по которым будешь фильтровать (host, region, service). Используй fields для самих измеряемых значений. Ошибка здесь приводит либо к низкой производительности запросов, либо к проблеме cardinality explosion, о которой мы поговорим позже.

### Storage engine

Типичный storage engine для time-series объединяет паттерны, которые мы уже разобрали:

1. **Write Ahead Log (WAL):** данные сначала попадают в WAL ради durability. Если база упадёт, она сможет восстановить незакоммиченные данные из WAL.
2. **In-Memory Buffer:** данные также записываются в in-memory buffer, организованный по measurement и комбинации tags. Это memtable из нашего разговора про LSM.
3. **Flush на диск:** когда buffer достигает порога, он сбрасывается на диск как immutable-файл со сжатыми timestamps и значениями.
4. **Фоновая compaction:** маленькие файлы периодически сливаются в более крупные. Это сокращает число файлов, которые нужно проверять при запросах, и удаляет удалённые данные.

Формат файла сильно оптимизирован:

```
File Structure:
┌──────────────────────────────────────────────────────────────┐
│                          Header                              │
├──────────────────────────────────────────────────────────────┤
│  Block 1: Timestamps (delta-of-delta + varint encoded)       │
│  Block 1: Values (XOR compressed)                            │
├──────────────────────────────────────────────────────────────┤
│  Block 2: Timestamps                                         │
│  Block 2: Values                                             │
├──────────────────────────────────────────────────────────────┤
│                         ...                                  │
├──────────────────────────────────────────────────────────────┤
│                    Index (series → block offsets)            │
├──────────────────────────────────────────────────────────────┤
│                         Footer                               │
└──────────────────────────────────────────────────────────────┘
```

В конце каждого файла лежит индекс, который сопоставляет series key (measurement + комбинация tags) с блоками, где хранятся её данные. Поэтому поиск данных конкретной series — это seek к индексу, а затем seek к данным: две дисковые операции независимо от того, сколько данных в файле.

### Выполнение запроса

Когда ты делаешь запрос к time-series базе данных:

```
SELECT mean(value) FROM cpu_usage 
WHERE host = 'server-1' 
  AND time > now() - 1h
GROUP BY time(5m)
```

Query engine делает следующее:

1. **Определяет нужные partitions** по фильтру времени. Рассматриваются только partitions, которые пересекаются с запрошенным временным диапазоном.
2. **Находит series**, обращаясь к фильтру по tags (host='server-1') в in-memory tag index.
3. **Читает из buffer и файлов на диске.** В buffer лежат самые свежие данные, в файлах на диске — более старые. Результаты объединяются.
4. **Применяет агрегации** по мере чтения данных. Это потоковая операция: базе не нужно загружать все данные в память, чтобы посчитать среднее.

Главная идея в том, что time-series базы данных используют и временную локальность (свежие данные лежат в памяти или в свежих файлах), и локальность по series (связанные точки данных хранятся вместе), чтобы минимизировать обращения к диску.

### Пример: запрос с несколькими tags

Давай проследим полный пример и посмотрим, как данные проходят путь от ingestion до результатов запроса.

#### Шаг 1: Ingestion данных

Представь, что наша система мониторинга за несколько секунд записывает такие точки данных:

```
cpu_usage,host=server-1,region=us-west,env=prod value=45.2 1700000000000000000
cpu_usage,host=server-1,region=us-west,env=prod value=47.1 1700000010000000000
cpu_usage,host=server-2,region=us-west,env=prod value=62.3 1700000000000000000
cpu_usage,host=server-2,region=us-west,env=prod value=61.8 1700000010000000000
cpu_usage,host=server-3,region=us-east,env=prod value=38.9 1700000000000000000
cpu_usage,host=server-3,region=us-east,env=prod value=39.2 1700000010000000000
cpu_usage,host=server-4,region=us-east,env=staging value=71.0 1700000000000000000
cpu_usage,host=server-4,region=us-east,env=staging value=73.5 1700000010000000000
```

#### Шаг 2: Как организованы данные

Каждая уникальная комбинация measurement + tags образует «series». В наших данных 4 series:

```
Series 1: cpu_usage,host=server-1,region=us-west,env=prod
Series 2: cpu_usage,host=server-2,region=us-west,env=prod
Series 3: cpu_usage,host=server-3,region=us-east,env=prod
Series 4: cpu_usage,host=server-4,region=us-east,env=staging
```

В файле данных значения каждой series хранятся вместе в сжатых блоках. Вот как это выглядит на диске со всеми нашими приёмами сжатия:

```
┌─────────────────────────────────────────────────────────────────────────┐
│ Data File (partition for Nov 15, 2023)                                  │
├─────────────────────────────────────────────────────────────────────────┤
│ Block 0: Series 1 (server-1, us-west, prod)                             │
│                                                                         │
│   Raw timestamps:    [1700000000000000000, 1700000010000000000] (16 bytes)
│   Stored as:         base=1700000000, delta=10, Δ-of-Δ=[0]       (3 bytes)
│                                                                         │
│   Raw values:        [45.2, 47.1]                                (16 bytes)
│   Stored as:         [45.2, XOR-diff]                           (10 bytes)
│                                                                         │
├─────────────────────────────────────────────────────────────────────────┤
│ Block 1: Series 2 (server-2, us-west, prod)                             │
│   Raw:    ts=[1700000000, 1700000010], vals=[62.3, 61.8]        (32 bytes)
│   Stored: ts=base+Δ+[0], vals=[62.3, XOR-diff]                  (13 bytes)
├─────────────────────────────────────────────────────────────────────────┤
│ Block 2: Series 3 (server-3, us-east, prod)                             │
│   Raw:    ts=[1700000000, 1700000010], vals=[38.9, 39.2]        (32 bytes)
│   Stored: ts=base+Δ+[0], vals=[38.9, XOR-diff]                  (13 bytes)
├─────────────────────────────────────────────────────────────────────────┤
│ Block 3: Series 4 (server-4, us-east, staging)                          │
│   Raw:    ts=[1700000000, 1700000010], vals=[71.0, 73.5]        (32 bytes)
│   Stored: ts=base+Δ+[0], vals=[71.0, XOR-diff]                  (13 bytes)
├─────────────────────────────────────────────────────────────────────────┤
│ INDEX                                                                   │
│   "cpu_usage,host=server-1,region=us-west,env=prod"  → Block 0          │
│   "cpu_usage,host=server-2,region=us-west,env=prod"  → Block 1          │
│   "cpu_usage,host=server-3,region=us-east,env=prod"  → Block 2          │
│   "cpu_usage,host=server-4,region=us-east,env=staging" → Block 3        │
└─────────────────────────────────────────────────────────────────────────┘
```

Блок 0 показан полностью, остальные блоки записаны в компактной нотации. Обрати внимание: каждый блок занимает ~13 байт вместо 32, то есть экономия 60% только за счёт этих двух приёмов, и с ростом объёма данных эффект становится ещё заметнее.

База также поддерживает in-memory **tag index**, который сопоставляет значения tags с series. Если это выглядит знакомо, то так и есть: по сути это inverted index, та же структура данных, на которой работает [Elasticsearch](/lessons/key-technologies/elasticsearch). Только вместо соответствия слов документам у нас соответствие значений tags series.

```
Tag Index (in memory):
┌─────────────────────────────────────────────────────────────────────────┐
│ region=us-west  → [Series 1, Series 2]                                  │
│ region=us-east  → [Series 3, Series 4]                                  │
│ env=prod        → [Series 1, Series 2, Series 3]                        │
│ env=staging     → [Series 4]                                            │
│ host=server-1   → [Series 1]                                            │
│ host=server-2   → [Series 2]                                            │
│ host=server-3   → [Series 3]                                            │
│ host=server-4   → [Series 4]                                            │
└─────────────────────────────────────────────────────────────────────────┘
```

#### Шаг 3: Выполнение запроса с несколькими tags

Теперь выполним запрос: «Какая средняя загрузка CPU у production-серверов в us-west?»

```
SELECT mean(value) FROM cpu_usage 
WHERE region = 'us-west' AND env = 'prod'
  AND time >= 1700000000000000000 AND time <= 1700000010000000000
```

Вот как база обрабатывает этот запрос:

```
Query: region='us-west' AND env='prod'

Step 1: Consult the tag index
         region=us-west → [Series 1, Series 2]
         env=prod       → [Series 1, Series 2, Series 3]
         
Step 2: Intersect the sets
         [Series 1, Series 2] ∩ [Series 1, Series 2, Series 3] 
         = [Series 1, Series 2]
         
Step 3: Look up block locations in file index
         Series 1 → Block 0
         Series 2 → Block 1
         
Step 4: Read only blocks 0 and 1 from disk (skip blocks 2, 3!)
         Block 0: timestamps [1700000000, 1700000010], values [45.2, 47.1]
         Block 1: timestamps [1700000000, 1700000010], values [62.3, 61.8]
         
Step 5: Apply time filter (all points match in this case)
         
Step 6: Compute aggregation
         mean([45.2, 47.1, 62.3, 61.8]) = 54.1
```

#### Почему это было быстро

Tag index позволил найти подходящие series, не сканируя никакие данные. Мы прочитали ровно 2 блока с диска и полностью пропустили 2 блока серверов us-east. Данные внутри каждого блока уже организованы по series, поэтому ни сортировка, ни фильтрация внутри блоков не понадобились.

Сравни это с наивным подходом в Postgres:

```
-- PostgreSQL equivalent
SELECT AVG(value) FROM metrics 
WHERE region = 'us-west' AND env = 'prod'
  AND timestamp BETWEEN '2023-11-15 00:00:00' AND '2023-11-15 00:00:10';
```

Даже с индексами по region и env Postgres придётся:

1. Найти по индексам ID подходящих строк
2. Достать каждую строку из потенциально разбросанных по диску мест
3. Извлечь значение из столбца value в каждой строке
4. Посчитать среднее

Когда строк миллионы, эти разбросанные чтения с диска убивают производительность. Columnar-хранение, ориентированное на series, в time-series базе данных означает, что нужные тебе данные физически лежат рядом. Наши записи оптимизированы так, чтобы помогать чтениям!

### Где ломается

У этих преимуществ есть и обратная сторона. Особенно показательный пример — проблема cardinality.

Cardinality — это число уникальных комбинаций tags. Если у тебя 1 000 hosts и 50 названий метрик, получается 50 000 series. Это вполне управляемо. Но что если добавить tag user\_id с 10 миллионами уникальных пользователей? Внезапно у тебя уже 500 миллиардов потенциальных series.

Почему это проблема? Time-series базы данных держат в памяти индекс всех series. Для каждой уникальной комбинации tags нужна запись. При миллиардах series память заканчивается. Запросы тоже замедляются, потому что индекс становится огромным.

Именно поэтому user ID, request ID и любые другие значения с высокой cardinality можно хранить только как fields, но не как tags. По сути, записывать их мы можем, но при чтении теряем все преимущества time-series базы данных.

## Итоги

Проблема cardinality хорошо показывает главный урок про time-series базы данных: если можно сделать сильные допущения о данных (tags с низкой cardinality, очень регулярные данные, небольшие дельты между точками), можно построить систему, которая использует каждое из этих свойств и даёт огромный выигрыш в производительности. Но как только допущения нарушаются, все преимущества пропадают, и для такой задачи система оказывается хуже универсальной базы данных.

Именно здесь спотыкается большинство кандидатов. Не понимая, на каких допущениях о данных построена база, они предлагают решение, которое для их задачи работает хуже (или вообще не работает). Понимание этих допущений и особенностей базы — признак кандидата уровня staff+. Если ты не уверен, лучше опереться на то, что знаешь, чем импровизировать с технологией, которую не знаешь.

Подведём итог: time series базы данных используют ряд фундаментальных паттернов, чтобы добиться своей производительности, и эти паттерны не ограничиваются задачами с временными рядами:

* Append-only storage превращает random I/O в sequential I/O
* LSM trees обеспечивают высокий write throughput, откладывая организацию данных на фоновый compaction
* Delta encoding и специализированное сжатие используют структуру данных временных рядов
* Time-based partitioning локализует записи и делает retention тривиальным
* Bloom filters избавляют от лишних чтений с диска при проверке SSTables
* Downsampling и rollups меняют точность на экономию места для исторических данных
* Block-level metadata позволяет отсекать ненужное во время запросов

Так мы получаем практический выигрыш в производительности на порядок в 10–100 раз по сравнению с универсальной базой данных на целевой нагрузке.

Так что в следующий раз, когда увидишь систему, обрабатывающую миллионы событий в секунду, помни: это не магия. Это append-only логи, LSM trees, хитрое сжатие, Bloom filters, rollups и аккуратное моделирование данных.

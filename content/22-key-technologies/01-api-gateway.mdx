Узнай, когда и как эффективно использовать API Gateway на собеседованиях по system design.

## Что такое API Gateway?

Скорее всего, ты сегодня уже взаимодействовал с API Gateway, даже если не замечал этого. Это один из ключевых компонентов современных архитектур, особенно с ростом популярности микросервисов.

Представь стойку регистрации в роскошном отеле. Гостям не нужно знать, где находится служба уборки или техническое помещение, так и клиентам не нужно знать о внутренней структуре твоих микросервисов.

API Gateway служит единой точкой входа для всех клиентских запросов: он принимает их и маршрутизирует к нужным backend-сервисам. Как стойка регистрации занимается заселением, распределением номеров и запросами гостей, так и API Gateway управляет централизованным middleware: аутентификацией, маршрутизацией и обработкой запросов.

Развитие API Gateway идёт параллельно с ростом архитектуры микросервисов. Когда монолитные приложения стали разбивать на небольшие специализированные сервисы, потребность в централизованной точке управления стала очевидной. Без API Gateway клиентам пришлось бы знать о множестве сервисов и общаться с ними напрямую. Представь, что гостям отеля нужно искать отдельных сотрудников под каждый запрос.

API gateways — это тонкие, относительно простые компоненты с чёткой задачей. В этом deep dive мы сосредоточимся на том, что нужно знать для собеседований по system design, не усложняя лишнего.

## Основные обязанности

Главная функция gateway — маршрутизация запросов (request routing): он определяет, какой backend-сервис должен обработать каждый входящий запрос. Но это не всё, что он делает.

Забавно, но кандидаты часто вводят gateway на собеседовании по system design и подробно рассказывают, сколько всего он делает на уровне middleware, но ни разу не упоминают главную причину, ради которой он нужен, — маршрутизацию запросов.

Сегодня API gateways также используют для сквозных задач (cross-cutting concerns), или middleware: аутентификации, rate limiting, caching, SSL termination и многого другого.

### Путь запроса

Давай пройдём по запросу от начала до конца. Входящие запросы попадают в API Gateway от клиентов, обычно по HTTP, но это может быть gRPC или любой другой протокол. Затем gateway применяет настроенный тобой middleware и маршрутизирует запрос к нужному backend-сервису.

1. Валидация запроса
2. API Gateway применяет middleware (auth, rate limiting и т. д.)
3. API Gateway маршрутизирует запрос к нужному backend-сервису
4. Backend-сервис обрабатывает запрос и возвращает ответ
5. API Gateway преобразует ответ и возвращает его клиенту
6. При необходимости кеширует ответ для будущих запросов

#### 1) Валидация запроса

Прежде чем делать что-либо ещё, API Gateway проверяет, что входящие запросы правильно сформированы и содержат всю необходимую информацию. Валидация включает проверку корректности URL запроса, наличия обязательных заголовков и соответствия тела запроса (если оно есть) ожидаемому формату.

Ранняя валидация важна, потому что позволяет отловить очевидные проблемы до того, как они дойдут до твоих backend-сервисов. Например, если мобильное приложение отправляет некорректный JSON или забывает передать обязательный API key, нет смысла пускать такой запрос дальше в систему. Gateway может быстро отклонить его и вернуть понятное сообщение об ошибке, избавив backend-сервисы от траты времени и ресурсов на запросы, которые заведомо не могли завершиться успехом.

#### 2) Middleware

API Gateway можно настроить на выполнение различных задач middleware. Например, ты можешь захотеть:

* Аутентифицировать запросы с помощью JWT-токенов
* Ограничивать частоту запросов для защиты от злоупотреблений
* Терминировать SSL-соединения
* Логировать и мониторить трафик
* Сжимать ответы
* Обрабатывать CORS-заголовки
* Вести whitelist/blacklist IP-адресов
* Проверять размеры запросов
* Обрабатывать таймауты ответов
* Версионировать API
* Throttle-ить трафик
* Интегрироваться с service discovery

Из них наиболее популярны и актуальны для собеседований по system design аутентификация, rate limiting и whitelist/blacklist IP-адресов. Если решишь упомянуть middleware, делай это осмысленно и не трать на это слишком много времени.

Мой совет: когда добавляешь API Gateway в свою схему, просто скажи: «Я добавлю API Gateway для маршрутизации и базового middleware» — и иди дальше.

#### 3) Маршрутизация

Gateway поддерживает таблицу маршрутизации (routing table), которая сопоставляет входящие запросы с backend-сервисами. Обычно это сопоставление строится на комбинации:

* URL-путей (например, /users/\* направляется в user service)
* HTTP-методов (например, GET, POST и т. д.)
* Query-параметров
* Заголовков запроса

Например, простая конфигурация маршрутизации может выглядеть так:

```
routes:
  - path: /users/*
    service: user-service
    port: 8080
  - path: /orders/*
    service: order-service
    port: 8081
  - path: /payments/*
    service: payment-service
    port: 8082
```

Gateway быстро определяет, в какой backend-сервис отправить запрос, по пути, методу, query-параметрам и заголовкам, и пересылает запрос дальше.

#### 4) Взаимодействие с backend

Хотя большинство сервисов общаются по HTTP, иногда твои backend-сервисы могут использовать другой протокол, например gRPC, для внутреннего взаимодействия. В таком случае API Gateway может выполнять трансляцию между протоколами, хотя на практике это встречается довольно редко.

Таким образом, gateway преобразует запрос в нужный протокол перед отправкой в backend-сервис. Это удобно: сервисы могут использовать тот протокол или формат, который наиболее эффективен, а клиентам знать об этом не нужно.

#### 5) Преобразование ответа

Gateway преобразует ответ backend-сервиса в формат, запрошенный клиентом. Этот слой преобразования позволяет внутренним сервисам использовать наиболее эффективный протокол или формат, а клиентам при этом отдавать чистый и единообразный API.

Например:

```
// Client sends a HTTP GET request
GET /users/123/profile

// API Gateway transforms this into an internal gRPC call
userService.getProfile({ userId: "123" })

// Gateway transforms the gRPC response into JSON and returns it to the client over HTTP
{
  "userId": "123",
  "name": "John Doe",
  "email": "john@example.com"
}
```

#### 6) Caching

Перед отправкой ответа клиенту gateway может при необходимости закешировать ответ. Это полезно для часто запрашиваемых данных, которые редко меняются и, что важно, не зависят от пользователя. Если ты ожидаешь, что конкретный API-запрос будет возвращать один и тот же результат для одних и тех же входных данных, кеширование имеет смысл.

API Gateway также может реализовывать разные стратегии кеширования. Например:

1. **Кеширование полного ответа (Full Response Caching)**: кешируются целые ответы для часто запрашиваемых endpoints
2. **Частичное кеширование (Partial Caching)**: кешируются отдельные части ответов, которые меняются нечасто
3. **Инвалидация кеша (Cache Invalidation)**: используется инвалидация по TTL или по событиям

В каждом случае ответ можно кешировать в памяти или в распределённом cache, например Redis.

## Масштабирование API Gateway

Когда на интервью обсуждают масштабирование API Gateway, обычно рассматривают два направления: рост нагрузки и глобальное распределение.

### Горизонтальное масштабирование

Самый простой способ справиться с ростом нагрузки — горизонтальное масштабирование. API Gateway, как правило, stateless, поэтому они хорошо подходят для него. Можно добавить больше инстансов gateway за load balancer, чтобы распределять входящие запросы.

API Gateway в первую очередь известны маршрутизацией и middleware, но часто в них есть и возможности балансировки нагрузки. Тем не менее важно понимать разницу:

* **Балансировка между клиентом и gateway**: обычно этим занимается отдельный load balancer перед инстансами API Gateway (например, AWS ELB или NGINX).
* **Балансировка между gateway и сервисами**: сам API Gateway может балансировать нагрузку между несколькими инстансами backend-сервисов.

На интервью это обычно можно абстрагировать. Достаточно нарисовать один блок «API Gateway и Load Balancer». Не стоит увязать в деталях точек входа: они скорее отвлекают от основной функциональности системы.

### Глобальное распределение

Ещё один вариант, особенно хорошо подходящий для крупных приложений с пользователями по всему миру, — разместить API Gateway ближе к пользователям, как это делают с CDN. Обычно это включает:

1. **Региональные деплои**: разверни инстансы gateway в нескольких географических регионах
2. **Маршрутизация на основе DNS**: используй GeoDNS, чтобы направлять пользователей к ближайшему gateway
3. **Синхронизация конфигурации**: убедись, что правила маршрутизации и политики согласованы между регионами

## Популярные API Gateway

Давай посмотрим на самые популярные API Gateway.

### Managed-сервисы

Облачные провайдеры предлагают полностью управляемые решения API Gateway, которые хорошо интегрируются с их экосистемами. Это самый простой вариант, но и самый дорогой.

1. **[AWS API Gateway](https://aws.amazon.com/api-gateway/)**

   * Бесшовная интеграция с сервисами AWS
   * Поддерживает REST и WebSocket API
   * Встроенные возможности:
     + Request throttling
     + API-ключи и usage plans
     + Интеграция с AWS Lambda
     + Мониторинг через CloudWatch
2. **[Azure API Management](https://azure.microsoft.com/en-us/products/api-management/)**

   * Сильная поддержка OAuth и OpenID Connect
   * Конфигурация на основе политик
   * Портал для разработчиков с документацией по API
3. **[Google Cloud Endpoints](https://cloud.google.com/endpoints)**

   * Глубокая интеграция с сервисами GCP
   * Сильная поддержка gRPC
   * Автоматическая документация OpenAPI

### Open source решения

Для команд, которым нужно больше контроля или которые работают on-premises:

1. **[Kong](https://konghq.com/)**

   * Построен на NGINX
   * Обширная экосистема плагинов
   * Поддерживает как традиционные деплои, так и service mesh
2. **[Tyk](https://tyk.io/)**

   * Нативная поддержка GraphQL
   * Встроенная аналитика API
   * Поддержка нескольких дата-центров
3. **[Express Gateway](https://www.express-gateway.io/)**

   * Основан на JavaScript/Node.js
   * Лёгкий и удобный для разработчиков
   * Подходит для микросервисов на Node.js

## Когда предлагать API Gateway

Окей, но когда использовать API Gateway на интервью?

Коротко: используй его, когда у тебя микросервисная архитектура, и не используй, когда архитектура простая клиент-серверная.

В микросервисной архитектуре API Gateway становится почти обязательным. Без него клиентам пришлось бы знать о нескольких сервисах и общаться с ними напрямую, что ведёт к более жёсткой связанности и более сложному клиентскому коду. Gateway чётко разделяет внутреннюю архитектуру сервисов и внешний API.

Однако так же важно понимать, когда API Gateway избыточен. Для простых монолитных приложений или систем с одним типом клиента он добавляет лишнюю сложность.

Я упоминал это на протяжении всей статьи, но хочу, чтобы это было предельно ясно. Важно понимать каждый компонент, который ты добавляешь в свой дизайн, но API Gateway — не самая интересная часть. Гораздо вероятнее, что ты допустишь ошибку, потратив на него слишком много времени, а не слишком мало.

Обозначь его, скажи, что он займётся маршрутизацией и middleware, и двигайся дальше.

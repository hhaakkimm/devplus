## Разбор задачи

**📈 Что такое [Robinhood](https://robinhood.com/)?**
Robinhood — торговая платформа без комиссий для акций, ETF, опционов и криптовалют. В ней есть рыночные данные в реальном времени и базовое управление ордерами. Robinhood — не биржа как таковая, а брокер: он маршрутизирует сделки через маркет-мейкеров («биржи») и получает от этих бирж вознаграждение через [payment for order flow](https://en.wikipedia.org/wiki/Payment_for_order_flow).

### Справка: финансовые рынки

Прежде чем переходить к дизайну, нужно разобраться в нескольких базовых финансовых терминах:

* **Symbol**: сокращение, которым обозначают акцию (например, META, AAPL). Также известен как «тикер».
* **Order**: ордер на покупку или продажу акции. Может быть *market order* или *limit order*.
* **Market Order**: ордер, запускающий немедленную покупку или продажу акции по текущей рыночной цене. Целевой цены у него нет, указывается только количество акций.
* **Limit Order**: ордер на покупку или продажу акции по заданной цене. Указываются количество акций и целевая цена; такой ордер может находиться на бирже в ожидании исполнения или отмены его создателем.

Помимо этих финансовых деталей, стоит понимать, за что отвечает Robinhood как бизнес и как система. **Robinhood — это брокер, который взаимодействует с внешними организациями, непосредственно занимающимися исполнением и отменой ордеров.** Значит, мы строим брокерскую систему, которая обслуживает ордера клиентов и отдаёт им данные по акциям. *Биржу мы не строим.*

В рамках этой задачи можно считать, что Robinhood работает с «биржей», у которой есть такие возможности:

* **Order Processing**: синхронно размещает и отменяет ордера через request/response API.
* **Trade Feed**: позволяет подписаться на поток сделок по symbols. Каждый раз, когда происходит сделка, «пушит» клиенту данные: symbol, цену за акцию, количество акций и orderId.

В этом интервью интервьюер предлагает внешний API (биржу), который поможет построить систему. Кандидату выгодно коротко уточнить интерфейс биржи (API, и синхронные, и асинхронные), чтобы понимать, какими инструментами можно пользоваться. Допущения об интерфейсе обычно сильно влияют на весь дизайн, поэтому стоит согласовать детали с интервьюером.

### [Функциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Пользователи видят актуальные цены акций в реальном времени.
2. Пользователи управляют ордерами на акции (market / limit ордера, создание / отмена ордеров).

**Вне рамок (below the line)**

* Пользователи могут торговать вне торговых часов.
* Пользователи могут торговать ETF, опционами, криптовалютой.
* Пользователи видят [order book](https://www.investopedia.com/terms/o/order-book.asp) в реальном времени.

Этот вопрос сосредоточен на просмотре акций и размещении ордеров. Продвинутые торговые сценарии в него не входят, а просмотр исторических данных по акциям или портфелю не является основным. Если ты не уверен, на каких функциях сосредоточиться в таком насыщенном функциями приложении, как Robinhood, или в похожем, коротко обсуди это с интервьюером и выясни, какая часть системы волнует его больше всего.

### [Нефункциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Для управления ордерами система предпочитает высокую consistency: пользователям *критически важно* видеть актуальную информацию об ордерах, когда они торгуют.
2. Система должна масштабироваться на большое число сделок в день (20 млн daily active users, в среднем 5 сделок в день, тысячи symbols).
3. Система должна работать с низкой latency, когда отражает обновления цен по symbols и когда размещает ордера (меньше 200 мс).
4. Система должна минимизировать число активных клиентов, подключающихся к API внешней биржи. Потоки данных и клиентские соединения с биржей обычно стоят дорого.

**Вне рамок (below the line)**

* Система подключается к нескольким биржам для торговли акциями.
* Система управляет торговыми комиссиями / расчётами (можно считать, что комиссии вне рамок).
* Система вводит дневные лимиты на торговую активность.
* Система защищает от использования ботов.

### [API](/lessons/sd-prep/delivery)

API — основной интерфейс, через который пользователи будут взаимодействовать с системой. Важно определить его заранее, потому что он направит твой high-level design. Нам нужно описать по одному endpoint для каждого функционального требования.

Начнём с endpoint для получения symbol, который будет включать детали и данные о цене. Он может выглядеть так:

```
GET /symbol/:name
Response: Symbol
```

Endpoint для создания ордера может выглядеть так:

```
POST /order
Request: {
  position: "buy",
  symbol: "META",
  priceInCents: 52210,
  numShares: 10
}
Response: Order
```

Обрати внимание: мы используем priceInCents вместо price, чтобы избежать проблем с точностью чисел с плавающей точкой. Особенно в финансовых приложениях лучше использовать целые числа, чтобы избежать ошибок и [финансовых махинаций](https://screenrant.com/justice-league-incarnate-superman-iii-scheme-easter-egg).

Чтобы отменить ордер, endpoint может быть совсем простым:

```
DELETE /order/:id
Response: {
  ok: true
}
```

Наконец, чтобы получить список ордеров пользователя, запрос может быть таким:

```
GET /orders
Response: Order[] (paginated)
```

Для запросов, которые затрагивают аккаунт или ордера пользователя, клиент может передавать в заголовках session token или JWT. Сервер проверяет его, чтобы понять, кто делает запрос, а затем проверяет, может ли этот пользователь просматривать или изменять соответствующие ордера. Полагаться на userId из заголовков или тела запроса для этого нельзя, потому что клиент может изменить и то и другое.

## [High-level design](/lessons/sd-prep/delivery)

### 1) Пользователи видят актуальные цены акций

Первое требование к Robinhood — дать пользователям возможность видеть актуальную цену акций. Это может быть одна акция или несколько, в зависимости от того, что пользователь смотрит в UI. Чтобы дизайн оставался расширяемым, предположим, что пользователь может видеть сразу много живых цен. Чтобы это поддержать, разберём несколько вариантов.

#### Плохое решение: опрос биржи напрямую

##### Подход

В этом решении мы опрашиваем биржу напрямую за ценой по каждому symbol. Клиент опрашивает биржу каждые несколько секунд (по каждому symbol) и обновляет цену, показываемую пользователю, на основе ответа.

##### Сложности

Это простой подход, который не масштабируется и не минимизирует количество соединений и вызовов к бирже. У такого дизайна есть несколько фундаментальных проблем:

* **Избыточные вызовы к бирже**: это очень неэффективный способ получать информацию о цене с точки зрения объёма вызовов к бирже. Это polling, который выполняется без разбора, даже если цена не изменилась. Кроме того, множество клиентов запрашивают у биржи одну и ту же информацию, что расточительно. Если 5000 клиентов одновременно запрашивают цену, то цена для них не отличается, но мы тратим 5000 вызовов (и повторяем их), чтобы раздать эту информацию.
* **Медленные обновления**: при polling обновления цен symbol будут приходить медленнее, чем нам хотелось бы. В нефункциональных требованиях мы указали, что хотим довольно короткий SLA на доставку клиентам цен symbol (меньше 200 мс), и единственный способ гарантировать это в таком решении — опрашивать данные каждые 200 мс, что неразумно.

Для такого дизайна опрос биржи напрямую можно исключить как жизнеспособный вариант.

![Иллюстрация](/content/robinhood/bd440d31c7.svg)

Polling

#### Хорошее решение: опрос внутреннего cache

##### Подход

Это решение по-прежнему использует polling для получения цен, но опрашивается symbol service, который делает key-value look-up во внутреннем cache. Этот cache поддерживается в актуальном состоянии symbol price processor, слушающим цены на бирже.

Такой подход предотвращает лишние соединения с биржей: мы «проксируем» её сервисом, который слушает и записывает самое важное — цену symbol. Эта цена затем становится доступна клиентам Robinhood через polling.

##### Сложности

Этот подход определённо лучше, но у него всё ещё есть проблемы. Клиенты по-прежнему опрашивают без разбора, даже если цена не изменилась, что приводит к лишнему HTTP-трафику. К тому же так цены обновляются медленно: интервал polling определяет худший случай SLA для доставки обновления цены клиенту. Можно ли сделать лучше?

![Иллюстрация](/content/robinhood/bd51d96092.svg)

Polling Internal Cache

#### Отличное решение: обновления цен через Server Sent Events (SSE)

##### Подход

Отличный вариант здесь — Server Sent Events (SSE). SSE — это постоянное соединение (похожее на WebSocket), но оно однонаправленное и работает поверх HTTP, а не по отдельному протоколу. В нашем случае клиент не отправляет нам данные, поэтому SSE подходит лучше, чем WebSocket. Подробнее о том, как рассуждать при выборе между WebSocket и SSE, смотри наш [разбор FB Live Comments](/lessons/breakdowns/fb-live-comments).

###### Паттерн: Real-time Updates

Обновление цен акций в реальном времени — идеальный пример паттерна real-time updates. Здесь мы используем Server Sent Events (SSE), чтобы установить постоянные соединения, через которые наши серверы мгновенно отправляют клиентам изменения цен. Такой подход решает сетевые основы real-time коммуникации и при этом пользователи видят актуальные рыночные цены без неэффективного постоянного polling.

[Изучить этот паттерн](/lessons/patterns/realtime-updates)

Этот подход предполагает переработку нашего API: вместо этого у нас будет GET-запрос /subscribe с query-параметрами, содержащими symbol, на которые мы хотим подписаться. Наш backend затем может установить SSE-соединение между клиентом и symbol service и отправить клиенту начальный список цен symbol. Этот начальный список цен обслуживается из cache, который поддерживается в актуальном состоянии processor, слушающим биржу. Кроме того, этот processor отправляет цены нашему symbol service, чтобы тот мог передавать эти данные клиентам, подписанным на обновления цен по разным symbol.

##### Сложности

SSE приносит свои сложности, в основном связанные с поддержанием соединения между клиентом и сервером. Load balancer нужно настроить на поддержку «sticky sessions», чтобы пользователь и сервер могли сохранять соединение для передачи данных. Кроме того, постоянное соединение означает, что нужно продумать, как работают disconnect и reconnect. Наконец, нужно решить, как маршрутизировать соединения пользователей и данные по symbol. Несколько из этих деталей разобраны ниже в deep dives, так что оставайся с нами.

### 2) Пользователи управляют ордерами на акции

Второе требование к Robinhood — дать пользователям возможность управлять ордерами на акции. Пользователи должны иметь возможность создавать ордера (limit или market), отменять неисполненные ордера и просматривать список своих ордеров.

Рассмотрим варианты создания и отмены ордеров через биржу.

#### Плохое решение: отправка ордеров напрямую на биржу

##### Подход

Это решение предполагает прямое взаимодействие с биржей для отправки ордеров. Любые ордера, созданные клиентом, напрямую отправляются на биржу.

##### Сложности

Это «основной» способ отправки ордеров, который убирает любую latency, возникающую из-за backend-прокси перед биржей. Но он может привести к огромному числу клиентов биржи и конкурентных запросов, а это будет очень дорого. Кроме того, у клиента нет понятного способа узнать статус ордера, кроме polling биржи или прямой подписки на trade feeds, а оба варианта нежизнеспособны. Наконец, за отслеживание ордеров целиком отвечает клиент. Это плохо, потому что хранилище клиента нельзя считать надёжным: пользователь может удалить приложение, или может выйти из строя железо телефона.

Давай рассмотрим другие решения.

![Иллюстрация](/content/robinhood/a968539f5d.svg)

Send Direct

#### Хорошее решение: отправка ордеров в Dispatch Service через очередь

##### Подход

Это решение предполагает отправку ордеров в order service, который ставит их в очередь для order dispatch service. Так мы избегаем лишних клиентов биржи: исполнение ордеров на бирже проксирует order dispatch service. Этот сервис может взять на себя ответственность за эффективное взаимодействие с биржей. Order service отправляет ордера в dispatch service через очередь. Очередь защищает dispatch service от перегрузки, а объём очереди может служить метрикой, по которой dispatch service будет эластично масштабироваться.

##### Сложности

Этот подход движется в правильном направлении: он проксирует биржу и даёт путь к эластичному масштабированию при росте нагрузки на ордера (например, при всплесках торговой активности). Однако он перестаёт работать, когда мы вспоминаем про жёсткий SLA на ордера (цель: менее 200 мс).

Если представить моменты высокой нагрузки на очередь, например во время активных торгов и до того, как order dispatch service успел отмасштабироваться, ордера могут довольно долго доходить до биржи, и это способно нарушить наш целевой SLA. В особенно чувствительные моменты торгов это может быть очень плохо для пользователей. Представь пользователя, который хочет быстро купить акции или быстро отменить активный ордер. Недопустимо заставлять его ждать, пока наш dispatcher наконец обработает ордер или пока наш сервис поднимет новые машины из-за возросшей нагрузки на очередь.

Какие у нас есть ещё варианты?

![Иллюстрация](/content/robinhood/600a42a330.svg)

Dispatch Via Queue

#### Отличное решение: Order Gateway

##### Подход

Этот подход предполагает отправку ордеров напрямую из order service в order dispatch gateway. Gateway обеспечивает связь с биржей через внешний интернет от имени order service. Он делает так, что запросы к бирже выглядят как исходящие из небольшого набора IP.

В этом подходе наш gateway будет [AWS NAT gateway](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-nat-gateway.html), который позволяет нашим order services отправлять запросы на биржу, но при этом выглядеть под одним или небольшим числом IP (в терминах AWS это [elastic IPs](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/elastic-ip-addresses-eip.html)).

Поскольку gateway управляет исходящими запросами, этот подход полагается на то, что order service, принимающий запросы от клиента, сам участвует в управлении ордерами. Этот сервис исполняет бизнес-логику управления ордерами и масштабируется вверх и вниз в зависимости от объёма ордеров. Раз клиенты ходят в него напрямую, мы можем сделать критерий auto-scaling для этого сервиса довольно чувствительным (например, масштабироваться, когда средняя загрузка CPU по всему fleet достигает 50%) или держать этот сервис с запасом мощности, чтобы поглощать всплески торгов.

##### Сложности

Этот подход требует, чтобы наш order service делал больше для управления ордерами. Значит, его нужно писать так, чтобы он эффективно взаимодействовал и с клиентом, и с биржей (например, потенциально объединяя ордера в batch).

![Иллюстрация](/content/robinhood/197a84f958.svg)

Order Gateway

Теперь, когда мы знаем, как будем отправлять ордера на биржу, нужно также решить, как мы будем хранить ордера у себя, чтобы показывать их пользователю. Пользователь должен иметь возможность сделать GET /orders и увидеть все свои активные ордера, так как же хранить данные на нашей стороне, чтобы обслуживать этот запрос?

Чтобы отслеживать ордера, мы можем развернуть order database, которая обновляется при создании или отмене ордеров. Order database будет реляционной, чтобы обеспечить consistency через ACID-гарантии, и будет партиционирована по userId (ID пользователя, отправляющего изменения ордеров). Это ускорит запросы ордеров пользователя, так как запрос пойдёт на один узел.

Сам ордер будет содержать информацию об отправленном / отменённом ордере. Также он будет содержать данные о состоянии ордера (pending до отправки на биржу, submitted, когда он отправлен на биржу, и т. д.). Наконец, в ордере будет поле externalOrderId, которое заполняется ID, возвращённым биржей, когда order service синхронно отправляет ордер.

Кроме того, чтобы поддерживать эти ордера актуальными, нам понадобится некий trade processor, который следит за сделками на бирже (tailing) и проверяет, обновились ли ордера, которые мы храним у себя.

Заметим, что этот trade processor будет fleet машин, подключённых к бирже тем или иным способом для получения обновлений цен. Интерфейс взаимодействия здесь не так важен. В большинстве подобных систем клиент биржи вроде Robinhood настраивает webhook endpoint и регистрирует его на бирже, а биржа вызывает webhook при каждом обновлении. В случае webhooks у trade processor будет load balancer и fleet машин, обслуживающих этот webhook endpoint. Для простоты на нашей схеме trade processor изображён одним квадратом.

## [Deep dives](/lessons/sd-prep/delivery)

### 1) Как масштабировать live-обновления цен?

Стоит подумать, как система будет масштабировать live-обновления цен. Если много пользователей подписаны на обновления цен по нескольким акциям, система должна гарантировать, что обновления цен успешно доходят до пользователя через SSE.

Главная проблема, которую нужно решить: **как маршрутизировать обновления цен по символам на те серверы symbol service, к которым подключены пользователи, заинтересованные в этих символах?**

Чтобы сделать это масштабируемо, можно использовать [Redis pub/sub](https://redis.io/docs/latest/develop/interact/pubsub/) для публикации и подписки на обновления цен. Пользователи подписываются на обновления цен через symbol service, а symbol service следит за тем, чтобы быть подписанным через Redis на обновления цен по всем символам, которые интересны его пользователям. Обновлённая схема системы может выглядеть так:

![Иллюстрация](/content/robinhood/4b4adba028.svg)

Pub/Sub для обновлений цен

Хочешь узнать больше о Redis? Загляни в наш [разбор Redis](/lessons/key-technologies/redis): там подробно обсуждается, как Redis можно практически применять на интервью по system design.

Пройдём по всему процессу обновления цен:

1. Пользователь подписывается через сервер symbol service. Сервер хранит маппинг Symbol -> Set&lt;userId>, поэтому добавляет запись для каждого символа, на который подписан пользователь.
2. Сервер symbol service управляет подписками на Redis pub/sub для каналов, соответствующих каждому символу. Он следит, чтобы на каждый символ, на который подписан пользователь, была активная подписка. Если подписки нет, он подписывается на канал этого символа.
3. Когда цена символа меняется, это обновление обрабатывает symbol price processor и публикует его в Redis. Каждый сервер symbol service, подписанный на обновления цен этого символа, получает обновление через подписку. Затем он делает fan-out и отправляет это обновление всем пользователям, которым интересны обновления цен этого символа.
4. Если пользователь отписывается от символов или отключается (это определяется через какой-нибудь heartbeat-механизм), сервер symbol service проходит по всем символам, на которые тот был подписан, и удаляет его из Set&lt;userId>. Если у сервера symbol service больше не осталось пользователей, подписанных на какой-то символ, он может отписаться от Redis-канала этого символа.

Это будет масштабироваться, потому что нагрузка равномерно распределяется между серверами symbol service. Кроме того, система регулирует себя сама: она управляет тем, какие обновления цен доходят до серверов symbol service.

### 2) Как система отслеживает обновления ордеров?

Разбирая процесс отправки ордеров, стоит уточнить, как мы будем обеспечивать обновление order DB по мере того, как ордера обновляются на бирже.

Во-первых, из текущей схемы неясно, как trade processor может отразить в orders DB обновления, имея на руках только сделку. У trade processor нет эффективного способа найти сделку по externalOrderId, чтобы обновить строку в таблице Order, потому что таблица партиционирована по userId . Поэтому нужно отдельное key-value хранилище, которое сопоставляет externalOrderId с парой (orderId, userId), которой он соответствует. Для такого key-value хранилища можно взять, например, [RocksDB](https://rocksdb.org/). Это хранилище заполняет order service синхронно, после того как ордер отправлен на биржу.

Новое key-value хранилище позволяет trade processor быстро определить, относится ли сделка к ордеру из нашей системы, а затем найти ордер (перейти на shard по userId -> найти Order по orderId) и обновить его данные. Обновлённая схема системы может выглядеть так:

### 3) Как система обеспечивает консистентность ордеров?

Консистентность ордеров крайне важна, и её стоит разобрать подробно. Под консистентностью ордеров понимается, что ордера консистентно хранятся на нашей стороне и так же консистентно ведутся на стороне биржи. Как мы увидим дальше, для консистентности ордеров важна fault-tolerance.

Прежде чем углубляться, вернёмся к тому, как мы храним ордера. Наша order database будет горизонтально партиционированной реляционной базой (например, Postgres). Все обновления ордера происходят на одном узле (партиции, на которой он лежит). Все чтения ордеров тоже происходят на одном узле, потому что мы партиционируем по userId.

Когда создаётся ордер, система выполняет такой процесс:

1. Сохраняем ордер в order database со статусом pending. *Важно сохранять его первым, потому что тогда у нас остаётся запись о том, что клиент мог сделать. Если не сохранить его первым, клиент мог бы создать ордер на бирже, система могла бы упасть, и тогда у нас не было бы способа узнать, что есть незакрытый ордер.*
2. Отправляем ордер на биржу. Сразу получаем externalOrderId (отправка ордера синхронная).
3. Записываем externalOrderId в наше key-value хранилище и обновляем ордер в order database: статус submitted и externalOrderId, полученный от биржи.
4. Отвечаем клиенту, что ордер успешно создан.

Такой процесс выглядит вполне разумно, но он может сломаться, если сбои случатся на разных этапах. Рассмотрим несколько сбоев и способы их смягчения, если они угрожают консистентности:

* **Сбой при сохранении ордера**: если не удалось сохранить ордер, отвечаем клиенту ошибкой и останавливаем процесс.
* **Сбой при отправке ордера на биржу**: если не удалось отправить ордер на биржу, помечаем ордер как failed и отвечаем клиенту.
* **Сбой при обработке ордера после отправки на биржу**: если при обновлении базы после отправки на биржу произошла ошибка, можно завести «clean-up» job, который разбирается с висящими ордерами в статусе pending. Большинство API бирж предлагают при отправке ордера metadata-поле clientOrderId (см. [пример E\*TRADE](https://apisb.etrade.com/docs/api/order/api-order-v1.html#/definitions/PreviewOrderRequest)), поэтому «clean-up» job может асинхронно запросить у биржи, прошёл ли ордер, по этому идентификатору clientOrderId, и сделать одно из двух: 1) записать externalOrderId, если ордер прошёл, или 2) пометить ордер как failed, если не прошёл.

Теперь, когда мы разобрали создание ордера, рассмотрим отмену. Когда ордер отменяется, система выполняет такой процесс:

1. Обновляем статус ордера на pending\_cancel. *Делаем это первым, чтобы потом можно было разрешить неудавшиеся отмены.*
2. Отправляем отмену ордера на биржу.
3. Записываем отмену ордера в базу.
4. Отвечаем клиенту, что отмена прошла успешно.

Пройдёмся по разным сбоям, чтобы убедиться, что мы защищены от неконсистентности:

* **Сбой при обновлении статуса на pending\_cancel**: если не удалось сразу обновить статус ордера, отвечаем клиенту ошибкой и останавливаем процесс.
* **Сбой при отмене ордера**: если не удалось отменить ордер через биржу, можно ответить клиенту ошибкой и положиться на «clean-up» процесс, который просканирует ордера в pending\_cancel (убедится, что они отменены).
* **Сбой при сохранении статуса cancelled в БД**: если не удалось обновить статус ордера в БД, можно положиться на «clean-up» процесс по ордерам в pending\_cancel (убедиться, что они отменены, либо ничего не делать и просто обновить статус на cancelled, если они уже отменены).

Из анализа выше следует: 1) у нас есть чёткое понимание процессов создания и отмены ордеров, и 2) мы выявили необходимость фонового «clean-up» процесса, чтобы состояние ордеров становилось консистентным при сбоях на разных этапах процессов создания и отмены.

### Некоторые дополнительные deep dives, которые можно рассмотреть

Robinhood, как и большинство fintech-систем, — сложное и интересное приложение, и в этом разборе трудно охватить все возможные аспекты. Вот несколько дополнительных deep dives, которые можно рассмотреть:

1. **Избыточные обновления цен**: Если по набору акций проходит много сделок или обновлений цен, как система справится с нагрузкой и не перегрузит клиента? Эту тему может быть интересно разобрать.
2. **Ограничение обмена с биржей**: Мы уже разобрали, как «проксировать» биржу и избегать лишних одновременных соединений / клиентов, но стоит копнуть глубже и обсудить другие способы ограничить обмен с биржей, при этом сохранив масштабируемость и обслуживание всей пользовательской базы (например, можно рассмотреть батчинг ордеров в один запрос).
3. **Live-обновления ордеров**: Стоит разобрать, как система будет в реальном времени доставлять пользователю обновления по ордерам (например, если пользователь смотрит свои ордера в приложении, он видит, как они исполняются в реальном времени, пока ждут ответа от биржи).
4. **Исторические данные о ценах и стоимости портфеля**: В этой схеме мы вообще не касались исторических данных о ценах и портфеле, но некоторые интервьюеры могут считать это требованием. Стоит подумать, как система сможет показывать историю цен (за разные временные окна) и историческую стоимость портфеля пользователя.

## [Чего ждут на каждом уровне](https://www.hellointerview.com/blog/the-system-design-interview-what-is-expected-at-each-level)

Что ж, получилось много. Возможно, ты думаешь: «А сколько из этого реально требуется от меня на интервью?» Давай разберёмся.

### Mid-level

**Ширина vs. глубина:** Mid-level кандидат в основном сосредоточен на ширине (80% против 20%). Ты должен уметь набросать high-level design, который покрывает определённые тобой функциональные требования, но многие компоненты при этом будут абстракциями, с которыми ты знаком лишь поверхностно.

**Проверка основ:** Интервьюер потратит некоторое время на проверку основ, чтобы убедиться, что ты понимаешь, что делает каждый компонент твоей системы. Например, если ты добавляешь API Gateway, будь готов к вопросу, что он делает и как работает (на высоком уровне). Короче говоря, интервьюер ничего не принимает на веру в отношении твоих знаний.

**Сочетание лидерства и ведомой роли:** Ты должен вести ранние этапы интервью, но интервьюер не ожидает, что ты сам будешь точно замечать проблемы в своём дизайне. Поэтому вполне нормально, что он возьмёт инициативу на себя на поздних этапах интервью, проверяя твою схему.

**Планка для Robinhood:** В этой задаче E4 кандидат чётко определит API endpoints и модель данных и придёт к high-level design, который работает для обновлений цен и размещения ордеров. Я не жду глубоких знаний конкретных технологий, но кандидат должен прийти к идеям эффективной доставки обновлений цен и согласованного управления ордерами. Также я ожидаю, что кандидат знает эффективные способы проксирования биржи, чтобы избежать лишних соединений / клиентов.

### Senior

**Глубина экспертизы:** От senior кандидата ожидают более глубоких знаний: примерно 60% ширины и 40% глубины. Это значит, что ты должен уметь погружаться в технические детали в тех областях, где у тебя есть практический опыт. Важно показать глубокое понимание ключевых концепций и технологий, relevant для задачи.

**Продвинутый system design:** Ты должен знать продвинутые принципы system design (разные технологии, их сценарии применения, как они сочетаются). Ключевое здесь — уверенно и ясно ориентироваться в этих темах.

**Объяснение архитектурных решений:** Ты должен чётко формулировать плюсы и минусы разных архитектурных вариантов, особенно их влияние на масштабируемость, производительность и поддерживаемость. Ты обосновываешь свои решения и объясняешь компромиссы, на которые идёшь.

**Решение проблем и проактивность:** Ты должен показывать сильные навыки решения проблем и проактивный подход. Это включает предвидение возможных сложностей в твоих схемах и предложение улучшений. Нужно уметь находить и устранять bottleneck, оптимизировать производительность и обеспечивать надёжность системы.

**Планка для Robinhood:** В этой задаче от E5 кандидатов ожидают, что они быстро пройдут начальный high-level design, чтобы потратить время на детальное обсуждение того, как обеспечить доставку цен в реальном времени и согласованность ордеров. Я ожидаю, что кандидат спроектирует разумное, масштабируемое решение для live-цен и хороший workflow обработки ордеров с вниманием к согласованности / fault tolerance.

### Staff+

**Упор на глубину:** От staff+ кандидата ожидают глубокого погружения в нюансы system design: я ищу примерно 40% ширины и 60% глубины. На этом уровне важно показать, что даже если ты не решал именно эту задачу, ты решил достаточно задач в реальном мире, чтобы уверенно спроектировать решение, опираясь на свой опыт.

Ты должен знать, какие технологии использовать не только в теории, но и на практике, и уметь опираться на прошлый опыт, объясняя, как они применяются для решения конкретных задач. Интервьюер знает, что ты разбираешься в мелочах (REST API, нормализация данных и т. д.), поэтому ты можешь пройти их на высоком уровне и оставить время для самого интересного.

**Высокая степень проактивности:** На этом уровне ожидается исключительная проактивность. Ты должен самостоятельно находить и решать проблемы, демонстрируя умение распознавать и закрывать ключевые вызовы в system design. Это значит не просто реагировать на проблемы по мере их появления, а предвидеть их и заранее вносить превентивные решения. Интервьюер должен вмешиваться только чтобы сфокусировать тебя, а не направлять.

**Практическое применение технологий:** Ты должен хорошо разбираться в практическом применении различных технологий. Твой опыт должен вести разговор, показывая чёткое понимание того, как разные инструменты и системы настраиваются в реальных сценариях под конкретные требования.

**Решение сложных задач и принятие решений:** Твои навыки решения проблем должны быть на высшем уровне. Это значит не только справляться со сложными техническими задачами, но и принимать взвешенные решения с учётом масштабируемости, производительности, надёжности и поддержки.

**Продвинутый system design и масштабируемость:** Твой подход к system design должен быть продвинутым, с упором на масштабируемость и надёжность, особенно под высокой нагрузкой. Это включает глубокое понимание distributed systems, load balancing, стратегий caching и других продвинутых концепций, необходимых для построения устойчивых, масштабируемых систем.

**Планка для Robinhood:** От staff-level кандидата ожидают высокого уровня глубины и качества решений, особенно для сложных сценариев, обсуждавшихся выше. Исключительные кандидаты подробно разбирают каждую из упомянутых тем и могут даже повернуть разговор в другую сторону, надолго сосредоточившись на теме, которая кажется им особенно интересной или релевантной. От них также ожидают твёрдого понимания компромиссов между разными решениями и умения чётко их объяснять, относясь к интервьюеру как к равному.

## Разбор задачи

**💾 Что такое Distributed Cache?**
Distributed cache — это система, которая хранит данные в виде пар «ключ-значение» в памяти на нескольких машинах в сети. В отличие от cache на одном узле, который ограничен ресурсами одной машины, distributed cache масштабируется горизонтально на множество узлов и справляется с огромными нагрузками. Узлы кластера работают вместе: партиционируют и реплицируют данные, обеспечивая высокую доступность и отказоустойчивость при выходе отдельных узлов из строя.

### [Функциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Пользователи должны иметь возможность устанавливать, получать и удалять пары «ключ-значение».
2. Пользователи должны иметь возможность настраивать время истечения срока жизни пар «ключ-значение».
3. Данные должны вытесняться по политике Least Recently Used (LRU).

**Вне рамок (below the line)**

* Пользователи должны иметь возможность настраивать размер cache.

Мы выбрали политику вытеснения LRU, но если интервьюер не сказал об этом явно, уточни у него, что именно он хочет увидеть. Есть, конечно, и другие политики вытеснения, которые можно реализовать: LFU, FIFO и кастомные политики.


### [Нефункциональные требования](/lessons/sd-prep/delivery)

На этом этапе интервью стоит спросить интервьюера, какой масштаб ожидается. Это сильно повлияет на дизайн, начиная с того, как ты сформулируешь нефункциональные требования.

Если бы я был твоим интервьюером, я бы сказал, что нужно хранить до 1TB данных и выдерживать пик до 100k запросов в секунду.

**Основные требования**

1. Система должна быть высокодоступной. Eventual consistency допустима.
2. Система должна поддерживать операции с низкой latency (&lt; 10ms для запросов get и set).
3. Система должна масштабироваться под ожидаемые 1TB данных и 100k запросов в секунду.

**Вне рамок (below the line)**

* Durability (сохранность данных после перезапусков)
* Гарантии strong consistency
* Сложные возможности запросов
* Поддержка транзакций

Обрати внимание: я делаю довольно много сильных допущений о том, что для нас важно. Обязательно подтверждай их с интервьюером. Скорее всего, ты уже пользовался cache и знаешь, сколько тут возможных компромиссов. Например, некоторых интервьюеров может волновать durability, так что просто спроси.

## [High-level design](/lessons/sd-prep/delivery)

Начнём с MVP, который закрывает основные функциональные требования. Он не обязан масштабироваться и быть идеальным. Это просто фундамент, на котором мы потом будем строить дальше. Мы пройдёмся по каждому функциональному требованию и убедимся, что high-level design его выполняет.

### 1) Пользователи должны уметь устанавливать, получать и удалять пары key-value

Начнём с самых основ. Пока никаких хитрых распределённых систем: просто работающий cache, который умеет get, set и delete.

По своей сути cache — это просто hash table. Она есть в любом языке программирования: dict в Python, HashMap в Java, map в Go. Для нашей задачи она идеальна, потому что даёт нам O(1) для поиска и вставки.

Интервьюер может попросить тебя набросать псевдокод. Вот как это может выглядеть:

```
class Cache:
    data = {}  # Simple hash table

    get(key):
        return self.data[key]

    set(key, value):
        self.data[key] = value

    delete(key):
        delete self.data[key]
```

Когда на design-интервью просят написать псевдокод, не переживай из-за синтаксиса. Сосредоточься на логике. Ты заметишь, что я не обрабатываю граничные случаи вроде «ключ не найден» или «ключ уже существует». Ничего страшного, дело не в этом.

Тем не менее, как всегда, стоит заранее уточнить это у интервьюера. «Я собираюсь написать псевдокод, ничего, если он не будет синтаксически корректным или в нём будут пропущены некоторые детали?»

Вот и всё. Три операции, и все O(1). Hash table сама берёт на себя разрешение коллизий и динамическое изменение размера.

Этот код можно запустить на одном сервере. Когда пользователь отправляет API-запрос, мы разбираем его, вызываем нужный метод у экземпляра Cache и возвращаем соответствующий ответ.

![Иллюстрация](/content/distributed-cache/33697e3b2a.svg)

Simple Cache

Конечно, до production это не дотягивает. Он развалится, если мы попробуем обработать реальный трафик или хранить слишком много данных. Но это надёжный фундамент, который удовлетворяет нашему основному функциональному требованию: хранению и получению пар key-value.

### 2) Пользователи должны уметь настраивать время жизни пар key-value

Добавим в наш cache expiration. Нам нужно хранить timestamp рядом с каждым значением и проверять его при чтении. Ещё понадобится способ очищать просроченные записи.

В псевдокоде ниже показано, как изменить cache, чтобы он поддерживал TTL (Time To Live). Ключевые изменения:

1. Вместо одних только значений мы теперь храним кортежи (value, expiry\_timestamp)
2. Метод get() перед возвратом записи проверяет, не истекла ли она
3. Метод set() принимает необязательный параметр TTL и вычисляет expiry timestamp

Это позволяет автоматически удалять записи из cache по истечении заданного времени. Без этого не обойтись, если мы хотим держать cache свежим и не отдавать устаревшие данные.

```
# Check the expiry time of the key on get
get(key):
    (value, expiry) = data[key]
    if expiry and currentTime() > expiry:
        # Key has expired, remove it
        delete data[key]
        return null
        
    return value

# Set the expiry time of the key on set
set(key, value, ttl):
    expiry = currentTime() + ttl if ttl else null
    data[key] = (value, expiry)
```

Базовый TTL так работает, но есть проблема: просроченные ключи удаляются, только когда к ним обращаются. Значит, cache может заполниться просроченными записями, которые уже никто не запрашивает.

Чтобы это исправить, нам нужен фоновый процесс (его часто называют «janitor»), который периодически сканирует cache и удаляет просроченные записи:

```
cleanup():    
    # Find all expired keys and delete
    for key, value in data:
        if value.expiry and current_time > value.expiry:
            delete data[key]
```

![Иллюстрация](/content/distributed-cache/f3aa07aeac.svg)

Simple Cache with TTLs

Этот процесс очистки может запускаться по расписанию (скажем, раз в минуту) или когда нагрузка на память достигает определённых порогов. Здесь приходится выбирать между нагрузкой на CPU (проверка записей) и эффективностью использования памяти (быстрое удаление просроченных данных).

Теперь у нас есть поддержка TTL, но нужно ещё учесть ограничения по памяти. Тут в игру вступает следующее требование: LRU eviction.

### 3) Данные должны вытесняться по политике LRU

Теперь нужно решить, что происходит, когда cache заполняется. Мы будем использовать политику Least Recently Used (LRU): она удаляет записи, к которым не обращались дольше всего.

Обязательно убедись, что ты согласовал с интервьюером именно LRU cache. У него может быть в голове другая политика eviction, или он может даже попросить сделать реализацию настраиваемой.

Тут есть сложность: нам нужно и быстро находить элементы, И отслеживать, какие из них использовались давнее всего. Если взять только hash table, мы будем быстро находить элементы, но не будем знать порядок обращений. Если взять только список, мы сможем отслеживать порядок, но поиск элементов будет медленным.

Решение — объединить две структуры данных:

1. Hash table для поиска за O(1). Она даёт мгновенный доступ к любому элементу cache
2. Doubly linked list для отслеживания порядка обращений. Он позволяет точно хранить историю того, какие элементы и когда использовались

Вместе эти структуры позволяют построить эффективный LRU cache, в котором и get, и set работают за O(1).

Когда мы добавляем элемент или обращаемся к нему:

1. Создаём объект Node, содержащий key, value и время истечения
2. Добавляем в hash table запись, которая сопоставляет key с этим Node
3. Вставляем Node в начало doubly-linked list (сразу после dummy head)
4. Если достигнут лимит ёмкости, удаляем наименее недавно использованный элемент и из hash table, и из linked list

Doubly-linked list хранит точный порядок обращений: в голове списка находятся самые недавно использованные элементы, а в хвосте — наименее недавно использованные. Когда нужно вытеснить элемент, мы просто удаляем узел прямо перед dummy tail.

Например, если мы добавляем элементы A, B, C в cache ёмкостью 2:

1. Добавляем A: [A]
2. Добавляем B: [B -> A]
3. Добавляем C: cache заполнен, вытесняем A (наименее недавно использованный), получаем [C -> B]

Когда мы обращаемся к существующему элементу, мы:

1. Находим его Node в hash table (O(1))
2. Удаляем Node с текущей позиции в списке (O(1))
3. Перемещаем его в начало списка (O(1))

Так часто используемые элементы остаются у головы и защищены от вытеснения, а редко используемые дрейфуют к хвосту, откуда их в итоге удалят, когда понадобится место.

Hash table даёт нам поиск за O(1), а doubly-linked list — обновление порядка обращений за O(1). Объединяя их, мы получаем лучшее из двух миров: быстрый доступ и эффективное отслеживание LRU.

Вот псевдокод реализации:

```
class Node # Node in our doubly-linked list storing values and expiry times

class Cache:
    get(key):
        # get the node from the hash table
        node = data[key]
        
        # Check if the entry has expired
        if node.expiry and currentTime() > node.expiry:
            # Remove expired node from both hash table and linked list
            delete data[key]
            delete node
            return null
            
        # Move node to front of list
        move_to_front(node)
        return node.value

    set(key, value, ttl):
        # Calculate expiry timestamp if TTL is provided
        expiry = currentTime() + ttl if ttl else null
        
        if key in data:
            # Update existing entry
            node = data[key]
            node.value = value
            node.expiry = expiry
            move_to_front(node)
        else:
            # Add new entry
            node = Node(key, value, expiry)
            data[key] = node
            add_node(node)
            
            # If over capacity, remove least recently used item
            if size > capacity:
                lru = tail.prev
                delete lru
                delete data[lru.key]

    cleanup():
        expired_keys = []
        
        # Scan from LRU end towards head
        current = tail.prev
        while current != head:
            if current.expiry and currentTime() > current.expiry:
                expired_keys.add(current.key)
            current = current.prev
            
        # Remove expired entries
        for key in expired_keys:
            node = data[key]
            delete data[key]
            delete node
```

Примеры кода здесь призваны проиллюстрировать ключевые идеи и намеренно упрощены для наглядности. В production-реализации пришлось бы учесть множество дополнительных вопросов, включая thread safety, обработку ошибок, мониторинг и оптимизации производительности.

![Иллюстрация](/content/distributed-cache/e53762929c.svg)

Simple LRU Cache

Самое изящное в этой реализации то, что все операции (get, set и даже eviction) остаются O(1). Когда мы обращаемся к элементу или добавляем его, мы перемещаем его в начало списка. Когда нужно вытеснить, удаляем с конца.

## [Deep dives](/lessons/sd-prep/delivery)

Честно говоря, до этого момента у нас было скорее low level design интервью, чем чистый system design. Но в deep dives всё меняется: здесь мы обсуждаем, как превратить один in-memory cache instance в распределённую систему, которая удовлетворяет нашим нефункциональным требованиям.

В таких вопросах по инфраструктуре работает тот же подход: старайся сам вести разговор к deep dives, чтобы закрыть нефункциональные требования. Но интервьюер, скорее всего, сам вмешается и начнёт задавать уточняющие вопросы, так что будь готов к гибкости.

Вот некоторые вопросы, которые я обычно задаю (или кандидат может поднять их сам, проактивно).

### 1) Как сделать cache высокодоступным и отказоустойчивым?

Наш high-level design отлично работает на одной ноде, но что будет, если она откажет? В production cache должен оставаться доступным, даже когда что-то идёт не так. Давай посмотрим, как этого добиться.

Главная сложность здесь в репликации данных: нам нужно несколько копий данных на разных нодах. Но это порождает целый ряд новых вопросов:

1. Сколько копий хранить?
2. На каких нодах их хранить?
3. Как синхронизировать копии между собой?
4. Что делать, если ноды падают или не могут связаться друг с другом?

Есть несколько проверенных паттернов для решения этой задачи. У каждого свои компромиссы между consistency, availability и сложностью.

Эти паттерны применяются далеко не только в распределённых cache: это базовые строительные блоки для обеспечения высокой доступности и отказоустойчивости в любой распределённой системе, от баз данных до очередей сообщений.

#### Плохое решение: синхронная репликация

###### Подход

Самый простой подход — держать несколько replica для каждого shard. Когда приходит запись, мы синхронно обновляем все replica и отвечаем только после того, как каждая из них подтвердила запись. Это просто, но если какая-то replica медленная или недоступна, страдают latency записи и availability.

Синхронную репликацию предпочитают для cache, которым нужны строгие гарантии consistency (нашему они не нужны).

![Иллюстрация](/content/distributed-cache/be2c8ad4bf.svg)

Синхронная репликация

###### Сложности

Главные недостатки следуют из самой синхронности. Операции записи должны дождаться подтверждения от всех replica, прежде чем завершиться, и это может заметно сказаться на latency. Если какая-то replica становится недоступной, страдает availability всей системы: запись не может пройти без полного консенсуса. Кроме того, с добавлением новых replica эти проблемы усугубляются: каждая новая replica повышает вероятность задержек или сбоев, и горизонтально масштабировать систему становится сложно.

По крайней мере для нашего случая это не подходит. Нам нужно ставить availability и производительность выше consistency.

#### Хорошее решение: асинхронная репликация

###### Подход

Другой вариант — сразу обновлять одну primary-копию, а изменения на replica распространять асинхронно, подтверждая запись, как только её признал только primary. Это хорошо соответствует модели eventual consistency, которую принимает большинство cache (и которая у нас входит в нефункциональные требования), поэтому для cache с нашими требованиями такой вариант подходит лучше синхронной репликации.

У асинхронности есть несколько ключевых преимуществ. Во-первых, запись работает быстрее, потому что не нужно ждать подтверждения от replica. Во-вторых, выше availability: запись проходит, даже если replica недоступны. В-третьих, система лучше масштабируется при добавлении replica, поскольку они не влияют на latency записи. И наконец, это естественный выбор для cache, где некоторая устарелость данных допустима.

![Иллюстрация](/content/distributed-cache/cc3c34f362.svg)

Асинхронная репликация

###### Сложности

Основные компромиссы тоже связаны с асинхронностью. Replica могут какое-то время отдавать устаревшие данные, пока изменения не распространятся по всей системе. Поскольку все записи идут через один primary, сложное разрешение конфликтов не нужно: порядок всех обновлений определяет primary. Однако восстановление после сбоев усложняется: нужно отслеживать, какие обновления могли быть пропущены, пока replica были недоступны, и корректно синхронизировать их, когда они вернутся в строй. Кроме того, если primary откажет, нужен механизм, который повысит одну из replica до нового primary, а это добавляет сложность и потенциальный простой во время failover.

#### Хорошее решение: peer-to-peer репликация

###### Подход

При peer-to-peer репликации все ноды равноправны, и каждая может принимать и чтения, и записи. Изменения распространяются по другим нодам с помощью [gossip-протоколов](https://en.wikipedia.org/wiki/Gossip_protocol): ноды периодически обмениваются информацией о своём состоянии со случайно выбранными peer.

Это даёт масштабируемость и availability, потому что нет единой точки отказа. Получив запись, нода может сразу её обработать, а затем асинхронно разослать изменение своим peer. Gossip-протокол гарантирует, что изменения в итоге дойдут до всех нод кластера.

![Иллюстрация](/content/distributed-cache/c054415e74.svg)

Peer-to-peer репликация

###### Сложности

Несмотря на отличную масштабируемость и availability, у peer-to-peer репликации есть серьёзные сложности. Реализация сложнее, чем у других подходов: каждой ноде нужно поддерживать соединения с несколькими peer и разрешать конфликты. Модель eventual consistency означает, что разные ноды могут какое-то время хранить разные значения для одного и того же ключа. Кроме того, нужно тщательно продумать стратегии разрешения конфликтов на случай конкурентных обновлений на разных нодах.

Все перечисленные подходы могут быть хорошими в зависимости от твоего конкретного случая и ограничений. Например, Redis по умолчанию использует асинхронную репликацию, хотя и предоставляет команду WAIT, которая позволяет клиентам дождаться подтверждения от replica, если это нужно (это иногда называют «semi-synchronous» поведением). Другие распределённые системы позволяют настраивать тип репликации, чтобы выбрать подходящие компромиссы для твоей нагрузки.

На интервью я бы обсудил варианты с интервьюером. Скорее всего, ему важнее не то, какой выбор ты сделаешь, а то, что ты знаешь о существовании вариантов и понимаешь их компромиссы.

Учитывая наши требования, я бы предложил интервьюеру два варианта:

1. Асинхронная репликация — хороший баланс между availability и простотой
2. Peer-to-peer — максимальная масштабируемость

На самом деле единственно верного ответа здесь нет.

### 2) Как сделать cache масштабируемым?

Надёжный cache на одной ноде — хорошее начало, но он не справится с амбициозными нефункциональными требованиями: хранить 1TB данных и выдерживать 100k запросов в секунду. Чтобы сохранить низкий latency и высокую availability по мере роста, нужно распределить нагрузку между несколькими машинами. Здесь в игру вступают стратегии масштабирования, и одна из главных тактик — разумно распределять данные и запросы.

Эффективно уместить 1TB данных на одной ноде, не упёршись в ограничения по памяти и производительности, нельзя. Нужно разбить пары key-value на части — сделать **shard** — и разложить их по нескольким нодам. Если сделать это правильно, каждая нода будет хранить посильную часть набора данных, и мы сможем масштабироваться горизонтально, просто добавляя машины.

В чём разница между partitioning и sharding? Формально partitioning означает разделение данных внутри одной базы данных или системы, а sharding — именно разделение данных между несколькими машинами или нодами. Однако на практике эти термины используют как взаимозаменяемые: когда кто-то говорит о «partitioning» в контексте распределённых систем, скорее всего, он имеет в виду распределение данных по разным нодам (sharding). Важно понимать саму идею разделения данных, какой бы термин ни использовался.

Количество нод можно оценить, исходя из требований и к throughput, и к объёму хранилища. Начнём с throughput. Допустим, мы замерили, что один хост выдерживает 20 000 запросов в секунду, тогда для нашего throughput нужно минимум 100 000 / 20 000 = 5 нод. Если добавить запас на пики трафика и возможные отказы нод, стоит закладывать минимум около 8 нод.

Теперь хранилище. Типичный инстанс AWS с 32GB RAM после вычета системных накладных расходов надёжно использует под данные cache около 24GB. Раз нам нужно хранить 1TB (1024GB) данных, потребуется примерно 1024GB / 24GB = 43 ноды только под хранение. С запасом на рост данных и операционные накладные расходы стоит планировать около 50 нод.

Обрати внимание: оценки throughput (20k запросов в секунду) и объёма памяти (24GB доступно из 32GB RAM) выше приблизительные и приведены для иллюстрации. Реальная производительность сильно зависит от железа, конфигурации cache, паттернов доступа и характера кэшируемых данных. Всегда проводи бенчмарки на своей нагрузке, чтобы определить, какая ёмкость нужна на самом деле.

Раз расчёт по хранилищу (50 нод) превышает расчёт по throughput (8 нод), закладываться нужно на хранилище. Большее число нод нам даже на руку: оно даёт большой запас по throughput. Конечно, это грубые оценки, и реальные цифры зависят от многих факторов: выбранных типов инстансов, среднего размера кэшируемых значений, соотношения чтений и записей, требований к репликации и ожидаемого роста. Но для наших целей примем, что в кластере будет 50 нод!

Итак, у нас 50 нод, но как понять, на какой ноде должна храниться конкретная пара ключ-значение?

### 3) Как обеспечить равномерное распределение ключей по нодам?

Ответ: [consistent hashing](/lessons/core-concepts/consistent-hashing).

Уверен, ты уже читал про consistent hashing, но давай быстро освежим основную идею.

Без consistent hashing наивное решение — использовать обычный модуль, чтобы определить, на какой ноде хранить пару ключ-значение. Например, при 4 нодах можно взять hash(key) % 4, и результат будет номером ноды, на которой должна лежать эта пара.

Это отлично работает, пока число нод фиксировано, но что будет, когда ты добавишь или уберёшь ноду?

Consistent hashing — это техника, которая помогает распределять ключи по нодам cache и при этом минимизирует число ключей, которые нужно перемапить при добавлении или удалении нод. Вместо простой арифметики по модулю (при которой почти все ключи пришлось бы перемапить при изменении числа нод) consistent hashing размещает и ноды, и ключи в кольцевом пространстве ключей.

Так что вместо hash(key) % 4 мы используем consistent hashing с хеш-функцией вроде [MurmurHash](https://en.wikipedia.org/wiki/MurmurHash), чтобы получить позицию на кольце. Получив позицию, мы двигаемся по кольцу по часовой стрелке до первой ноды. Именно на ней и нужно хранить пару ключ-значение!

![Иллюстрация](/content/distributed-cache/3da5990d30.svg)

Consistent hashing

Зачем всё это нужно?

Затем, что теперь при добавлении или удалении ноды перемапить нужно только ключи из диапазона этой ноды, а не перераспределять все ключи по всем нодам, как было бы, если бы наш модуль поменялся с hash(key) % 4 на hash(key) % 5 или hash(key) % 3.

Подробнее о consistent hashing читай в [разборе Cassandra](/lessons/key-technologies/cassandra).

### 4) Что делать, если есть hot key, который очень часто читают?

Тебе наверняка зададут классический уточняющий вопрос: а что насчёт hot key?

Честно говоря, это обычно свойство клиента или пользователя cache, а не самого cache. Тем не менее на интервью это всплывает часто, так что лучше подготовить продуманный ответ.

Hot key — типичная проблема распределённых систем кэширования. Они возникают, когда некоторые ключи получают несоразмерно больше трафика, чем остальные: представь данные вирусного твита или счётчик остатков товара на флеш-распродаже. Когда слишком много запросов концентрируется на одном shard с такими популярными ключами, возникает hotspot, который может ухудшить производительность всего этого shard.

Есть два разных типа проблем с hot key, которые нужно уметь обрабатывать:

1. **Hot reads**: ключи, которые получают очень большой объём запросов на чтение, например данные вирусного твита, которые одновременно пытаются посмотреть миллионы пользователей
2. **Hot writes**: ключи, которые получают много конкурентных запросов на запись, например счётчик голосов в реальном времени.

###### Паттерн: Scaling Reads

Сценарии с hot key в распределённых cache отлично демонстрируют проблемы **scaling reads**. Когда миллионы пользователей одновременно запрашивают один и тот же вирусный контент, привычные допущения о кэшировании перестают работать.

[Изучить этот паттерн](/lessons/patterns/scaling-reads)

Сначала разберём стратегии для hot reads, а потом подходы к hot writes.

#### Плохое решение: вертикальное масштабирование всех нод

###### Подход

Самый простой вариант — нарастить железо на всех нодах кластера, чтобы они справлялись с hot key. Это значит увеличить CPU, память и пропускную способность сети везде. Это прямолинейно, но все ноды при этом считаются равными вне зависимости от их реальной нагрузки.

###### Сложности

Это дорогое и неэффективное решение: мы улучшаем ресурсы всех нод, хотя высокая нагрузка только на некоторых. Оно также не решает первопричину hot key и всё равно может привести к узким местам, если ключи станут по-настоящему горячими. Стоимость растёт линейно с числом нод, поэтому для больших кластеров такой подход неустойчив.

#### Хорошее решение: выделенный cache для hot key

###### Подход

Эта стратегия предполагает отдельный слой кэширования специально для hot key. Когда ключ определяется как «горячий» по результатам мониторинга, он переносится в этот специализированный уровень, который работает на более мощном железе и оптимизирован под высокий throughput. Такой уровень можно распределить географически и разместить ближе к пользователям для лучшей производительности.

![Иллюстрация](/content/distributed-cache/845c978f68.svg)

Выделенный cache для hot key

###### Сложности

Поддержание consistency между основным cache и cache для hot key усложняет систему. Нужен продвинутый мониторинг для выявления hot key и механизмы продвижения и понижения ключей между уровнями. Добавляются и операционные расходы на поддержку отдельной инфраструктуры кэширования. Систему нужно аккуратно настраивать, чтобы определить, когда ключи следует продвигать, а когда понижать.

#### Хорошее решение: read replica

###### Подход

Мы говорили об этом в разделе про high availability и репликацию. Напомню: мы создаём несколько копий одних и тех же данных на разных нодах. Так легко распределить запросы на чтение между replica.

###### Сложности

Read replica хорошо распределяют нагрузку на чтение, но у них большие накладные расходы по хранилищу и пропускной способности сети, поскольку реплицировать приходится целые ноды. Этот подход также требует аккуратного управления replication lag и consistency между primary и replica нодами. Вдобавок растёт операционная сложность: нужно поддерживать и мониторить несколько копий одних и тех же данных, обрабатывать сценарии failover и обеспечивать корректную синхронизацию между всеми replica. Это решение может оказаться избыточным, если высокая нагрузка приходится лишь на небольшое подмножество ключей.

#### Отличное решение: копии hot key

###### Подход

В отличие от read replica, которые копируют целые ноды, этот подход выборочно копирует только те ключи, на которые приходится высокий трафик чтения. Система создаёт несколько копий hot key на разных нодах, чтобы распределить нагрузку на чтение. Получается более точечное решение для конкретных hotspot.

Вот как это работает:

1. Сначала система отслеживает паттерны доступа к ключам и находит hot key, которые часто читаются
2. Когда ключ становится «горячим», вместо одной копии user:123 система создаёт несколько копий с разными суффиксами:
   * user:123#1 -> копия хранится на Node A
   * user:123#2 -> копия хранится на Node B
   * user:123#3 -> копия хранится на Node C
3. Эти копии распределяются по разным нодам через consistent hashing
4. При чтении клиенты случайно выбирают один из ключей с суффиксом, распределяя нагрузку на чтение по нескольким нодам
5. При записи система должна обновить все копии, чтобы сохранить consistency

Например, если "product:iphone" становится hot key во время флеш-распродажи со 100 000 чтений в секунду, но всего 1 записью в секунду:

* Без копий: одна нода обрабатывает все 100 000 чтений в секунду
* С 4 копиями: каждая копия обрабатывает ~25 000 чтений в секунду, но запись должна обновлять все 4 копии

Этот подход рассчитан именно на hot key с преобладанием чтений. Если ключ горячий и по чтению, и по записи, такой подход может даже ухудшить ситуацию из-за накладных расходов на поддержание consistency между копиями.

![Иллюстрация](/content/distributed-cache/4f27128167.svg)

Копии hot key

###### Сложности

Главная сложность — держать все копии синхронизированными при изменении данных. Когда мы обновляем hot key, нужно обновить все его копии на разных нодах. Можно попытаться обновлять все копии одновременно (атомарные обновления), но это сильно усложняет систему. При этом большинство распределённых cache-систем, включая нашу, проектируются как eventually consistent: допустимо, что копии какое-то время расходятся, лишь бы они сходились к одному значению. Это сильно упрощает задачу, потому что идеальная синхронизация не нужна.

Есть и накладные расходы: нужен мониторинг для обнаружения hot keys и управление жизненным циклом копий — когда их создавать и когда удалять, если ключ перестал быть hot. Подход лучше всего работает, когда hot keys в основном читают и пишут в них редко.

Главное, что стоит показать интервьюеру: ты понимаешь, что hot keys — реальная эксплуатационная проблема, которую нельзя игнорировать. Обсуждая эти способы смягчения заранее, ты показываешь, что продумал практические сложности работы распределённого cache в большом масштабе и у тебя есть конкретные подходы к ним. Именно такое понимание эксплуатации отличает теоретические знания от практического опыта в system design.

### 5) Что делать, если в hot key очень много записей?

Hot writes похожи на hot reads, но они немного сложнее и у них другой набор компромиссов.

#### Отличное решение: Write Batching

###### Подход

Write batching решает проблему hot writes так: собирает несколько операций записи за короткое окно времени и применяет их как одно атомарное обновление. Вместо того чтобы обрабатывать каждую запись по отдельности сразу после её поступления, клиент буферизует записи на короткое время (обычно 50–100 мс), а затем объединяет их в одну операцию. Этот подход особенно эффективен для счётчиков, метрик и других случаев, где важнее итоговое состояние, чем отслеживание каждого отдельного обновления.

Представь вирусное видео, которое получает 10 000 обновлений просмотров в секунду. Вместо 10 000 отдельных операций, выставляющих новые значения (например, views=1, views=2, views=3 и так далее), write batching может собирать обновления 100 мс, а затем выполнить одну операцию, которая выставит итоговое значение на 1 000 больше. Так нагрузка на запись на ноде cache снижается на порядок, а точность остаётся приемлемой. Компромисс — небольшая задержка до видимости записи, но для многих сценариев она допустима с учётом значительного выигрыша в производительности.

###### Сложности

Главная сложность write batching — баланс между задержкой батча и видимостью записи. Более длинные окна снижают нагрузку на систему, но увеличивают время, через которое записи становятся видимы. Кроме того, усложняется обработка сбоев в течение окна батчинга: если обработчик батчей падает, нужны механизмы, чтобы восстановить или повторно воспроизвести буферизованные записи. Также батчинг вносит небольшую неконсистентность в операции чтения, поскольку в буфере всегда есть какое-то количество ожидающих записей. Этот подход лучше всего подходит для метрик и счётчиков, где допустима eventual consistency, и может не подойти там, где запись должна быть видна немедленно.

#### Отличное решение: Sharding Hot Key With Suffixes

###### Подход

Key sharding использует другой подход к hot writes: один hot key разбивается на несколько подключей, распределённых по разным нодам. Именно его мы разбираем во многих других разборах Hello Interview.

Вместо одного счётчика или значения, на которое приходят все записи, система распределяет записи по нескольким shard с помощью суффиксов. Например, hot-ключ счётчика "views:video123" можно разбить на 10 shard: от "views:video123:1" до "views:video123:10". Когда приходит запись, система случайно выбирает один из этих shard и обновляет его.

Так нагрузка на запись эффективно распределяется по нодам кластера. В нашем примере с вирусным видео и 10 000 записей в секунду 10 shard снизят нагрузку до примерно 1 000 операций в секунду на shard. Чтобы прочитать суммарное значение, системе достаточно сложить значения со всех shard. Эта техника особенно мощная, потому что работает с любой операцией, которую можно разложить на части и собрать обратно, а не только с простыми счётчиками.

###### Сложности

Основная сложность key sharding — усложнение чтения: теперь нужно агрегировать данные из нескольких shard. Это может увеличить latency чтения и расход ресурсов, то есть мы по сути меняем производительность записи на производительность чтения. Есть и сложность с поддержанием консистентности между shard при сбоях или ребалансировке. Число shard нужно выбирать аккуратно: слишком мало — нагрузка не распределится как следует, слишком много — чтение станет неоправданно сложным. Наконец, подход может не подойти для операций, которые нельзя легко разложить на части, например для тех, где нужно сохранять строгий порядок или атомарность по всем обновлениям.

### 6) Как обеспечить производительность cache?

Наш дизайн с одной нодой начинался просто и быстро: поиск и запись выполнялись за O(1) и обслуживались прямо из памяти. Но когда мы растим систему до большого распределённого cache на десятки или даже сотни нод, задача меняется. Внезапно производительность определяется не только тем, как быстро работает hash table в памяти. Важно, как быстро клиенты находят нужную ноду, насколько эффективно несколько запросов объединяются вместе и как мы избегаем лишнего сетевого трафика.

Когда мы начинаем масштабироваться горизонтально, полагаться только на локальные оптимизации производительности уже нельзя. Даже если каждая отдельная нода работает очень быстро, взаимодействие между нодами и клиентами и накладные расходы на сетевые hops могут давать заметную latency. Нередко запрос, который раньше обслуживался за микросекунды, замедляется, потому что ему приходится несколько раз пройти по сети, дождаться установки соединений или обработать множество мелких запросов по отдельности.

Хорошая новость в том, что мы уже решили эту проблему в каждом из предыдущих решений. Request batching, который помог нам с hot writes, — ещё и эффективный общий приём для снижения latency, поскольку он сокращает число round trip между клиентом и сервером.

Consistent hashing, о котором мы говорили в решении про sharding, тоже эффективный общий приём для снижения latency: нам не нужно обращаться к центральному сервису маршрутизации, чтобы узнать, на какой ноде лежат данные, и мы экономим один round trip.

Единственное, что я бы ещё упомянул на интервью, если зададут этот вопрос, — connection pooling. Постоянно разрывать и заново устанавливать сетевые соединения между клиентом и серверами — верный способ тратить время впустую. Вместо того чтобы создавать новое соединение на каждый запрос, клиентам стоит держать пул открытых постоянных соединений. Тогда для запросов всегда есть готовый канал, не нужны дорогие handshake с round trip, а tail latency (те самые p95 и p99, от которых может зависеть, будет ли пользователь доволен) заметно снижается.

## Итоговая схема

Итак, соберём всё вместе. На каждой ноде у нас будут две структуры данных:

1. Hash table для хранения пар ключ-значение
2. Linked list для политики вытеснения LRU

Что касается масштабирования, здесь всё зависит от того, какие из описанных выше подходов ты выберешь: в итоге дизайн может немного отличаться. Допустим, ты выбрал:

1. Asynchronous replication для high availability и обработки чтений hot key.
2. Consistent hashing для шардинга и маршрутизации.
3. Случайные суффиксы для распределения записей hot key по нодам.
4. Write batching и connection pooling, чтобы снизить сетевой latency и overhead.

## [Чего ждут на каждом уровне](/lessons/sd-prep/what-is-expected-at-each-level)

### Mid-level

С кандидатами уровня mid-level мы обычно тратим больше времени на раздел high-level design (он же low-level design) и меньше на раздел про масштабирование. Я ожидаю, что они смогут подобрать правильную комбинацию структур данных, чтобы уложиться в наши требования по latency, и самостоятельно придут к базовым ответам про масштабируемость и доступность. Например, поймут, зачем нужна replication, и найдут разные способы её реализовать.

### Senior

От senior-кандидатов я ожидаю, что часть про low-level design пройдёт довольно просто, а основное время мы потратим на разговор о масштабировании. Я хочу увидеть, как они взвешивают trade-offs и принимают решения с учётом требований к системе. Они должны знать базовые стратегии работы с hot reads/writes и говорить о таких вещах, как consistent hashing, как о чём-то само собой разумеющемся.

### Staff+

Я обычно не задаю этот вопрос staff-инженерам: к этому уровню такие концепции, скорее всего, уже даются естественно, а значит, это не лучший вопрос для оценки staff-инженера.

## Разбор задачи

**🚦 Что такое Rate Limiter?**
Rate limiter контролирует, сколько запросов клиент может сделать за определённый промежуток времени. Он работает как регулировщик движения для твоего API: например, пропускает 100 запросов в минуту от пользователя, а все лишние отклоняет с ответом HTTP 429 "Too Many Requests". Rate limiter'ы защищают от злоупотреблений, не дают всплескам трафика перегрузить серверы и обеспечивают справедливое использование для всех пользователей.

### [Функциональные требования](/lessons/sd-prep/delivery)

В этом разборе мы спроектируем **rate limiter на уровне запросов** для API платформы социальных сетей. Это значит, что мы ограничиваем отдельные HTTP-запросы (публикацию твитов, получение ленты, загрузку фото), а не действия более высокого уровня или бизнес-операции. Мы сосредоточимся на серверной реализации, которая управляет трафиком и защищает наши системы. Клиентское ограничение скорости полезно как дополнительный подход (о нём поговорим позже), но серверное необходимо для безопасности и защиты системы, поскольку клиентам нельзя доверять в том, что они будут сами себя ограничивать.

**Основные требования**

1. Система должна идентифицировать клиентов по user ID, IP-адресу или API key, чтобы применять подходящие лимиты.
2. Система должна ограничивать HTTP-запросы на основе настраиваемых правил (например, 100 API-запросов в минуту на пользователя).
3. При превышении лимитов система должна отклонять запросы с HTTP 429 и добавлять полезные заголовки (сколько лимита осталось, время сброса).

**Вне рамок (below the line)**

* Сложные запросы и аналитика по данным rate limiting
* Долгосрочное хранение данных rate limiting


### [Нефункциональные требования](/lessons/sd-prep/delivery)

На этом этапе стоит спросить интервьюера об ожидаемом масштабе. Мы строим это для API стартапа с тысячами запросов в день или для крупной платформы, которая обрабатывает миллионы запросов в секунду? Масштаб полностью меняет выбор дизайна.

Предположим, что мы проектируем под значительную, но реалистичную нагрузку: 1 миллион запросов в секунду при 100 миллионах daily active users.

**Основные требования**

1. Система должна добавлять минимальные накладные расходы по latency (&lt; 10 мс на проверку запроса).
2. Система должна быть высокодоступной. Eventual consistency допустима: небольшие задержки в применении лимитов между узлами приемлемы.
3. Система должна справляться с 1M запросов в секунду при 100M daily active users.

**Вне рамок (below the line)**

* Гарантии strong consistency между всеми узлами

### [Определение основных сущностей](/lessons/sd-prep/delivery)

Rate limiter'ы могут казаться простыми инфраструктурными компонентами, но на деле в них участвует несколько важных сущностей, которые нужно правильно смоделировать:

**Rules**: политики rate limiting, которые задают лимиты для разных сценариев. Каждое правило определяет параметры вроде числа запросов на временное окно, к каким клиентам оно применяется и какие endpoints охватывает. Например: «аутентифицированные пользователи получают 1000 запросов в час» или «search API допускает 10 запросов в минуту на IP».

**Clients**: сущности, которых мы ограничиваем. Это могут быть пользователи (идентифицируются по user ID), IP-адреса, API key или их комбинации. У каждого клиента есть связанное состояние rate limiting, которое отслеживает его текущее потребление относительно применимых правил.

**Requests**: входящие API-запросы, которые нужно проверить по правилам rate limiting. Каждый запрос несёт контекст: идентичность клиента, запрашиваемый endpoint и timestamp, который определяет, какие правила применяются и как учитывать потребление.

Эти сущности работают вместе: когда приходит **Request**, мы определяем **Client**, находим применимые **Rules**, сверяем текущее потребление с этими правилами и решаем, пропустить запрос или отклонить. Взаимодействие этих сущностей и лежит в основе нашего rate limiter'а.

### API

Rate limiter — это инфраструктурный компонент, который вызывают другие сервисы, чтобы проверить, можно ли пропустить запрос. Интерфейс простой:

```
isRequestAllowed(clientId, ruleId) -> { passes: boolean, remaining: number, resetTime: timestamp }
```

Этот метод принимает идентификатор клиента (user ID, IP-адрес или API key) и идентификатор правила, а затем возвращает, нужно ли пропустить запрос с учётом текущего потребления. Он также отдаёт информацию для заголовков ответа, таких как X-RateLimit-Remaining и X-RateLimit-Reset.

## [High-level design](/lessons/sd-prep/delivery)

Начнём с MVP, который закрывает основные функциональные требования. Он не обязан масштабироваться и быть идеальным: это просто фундамент, на котором мы потом будем строить дальше. Мы пройдём по каждому функциональному требованию и убедимся, что high-level design его выполняет.

### 1) Система должна идентифицировать клиентов по user ID, IP-адресу или API key, чтобы применять подходящие лимиты

Прежде чем кого-то ограничивать, нужно принять два ключевых решения. Во-первых, где в архитектуре должен находиться rate limiter? От этого зависит, к какой информации у нас есть доступ и как rate limiter интегрируется с остальной системой. Во-вторых, как мы различаем клиентов, чтобы применять правильные лимиты к правильным пользователям? Эти решения связаны: выбор места размещения влияет на то, какую информацию о клиенте легко получить, а стратегия идентификации определяет, где rate limiter имеет смысл развернуть.

**Где разместить rate limiter?**

Есть три основных варианта, и у каждого свои компромиссы:

#### Плохое решение: In-Process

###### Подход

Rate limiting встроен прямо в код каждого application server или микросервиса. Когда приходит запрос, сервер проверяет локальные счётчики в памяти, обновляет их и решает, пропустить запрос или отклонить. Это очень быстро, потому что всё происходит в памяти: никаких сетевых вызовов и внешних зависимостей.

![Иллюстрация](/content/distributed-rate-limiter/6b05f9a3c8.svg)

In-Process Rate Limiter

###### Сложности

Главная проблема в том, что каждый сервер знает только о собственном трафике, а не о глобальной картине. Допустим, ты хочешь ограничить пользователей до 100 запросов в минуту. Если за load balancer стоят 5 application server и запросы распределяются равномерно, каждый сервер может видеть от пользователя по 20 запросов в минуту и думать: «всё нормально, это сильно меньше 100». Но глобально пользователь делает 100 запросов в минуту по всем серверам вместе.

Хуже того, если load balancer меняет способ маршрутизации трафика или один сервер получает больше нагрузки, чем другие, лимиты становятся совершенно непредсказуемыми. Пользователь может пропустить 100 запросов через один сервер и ещё 100 через другой, итого 200.

Такой подход работает, только если у тебя один application server или если тебя устраивают приблизительные лимиты, которые могут отличаться от заданных в число раз, равное количеству серверов.

#### Хорошее решение: Dedicated Service

###### Подход

Rate limiter становится отдельным микросервисом, который стоит между клиентами и application server. Когда запрос приходит на application server, тот сначала делает API-вызов к сервису rate limiting: «Разрешить ли этот запрос от пользователя 12345?» Rate limiter проверяет свои централизованные счётчики и отвечает либо «да, пропускай», либо «нет, отклоняй с 429».

Такая архитектура даёт гораздо больше гибкости. Application server могут передавать богатый контекст при проверке лимита: тариф пользователя, статус аккаунта, конкретный вызываемый API endpoint или даже сложную бизнес-логику вроде «разрешить дополнительные запросы во время Black Friday». Можно также завести разные сервисы rate limiting для разных частей системы, каждый под свои задачи.

Важнее всего то, что сервис rate limiting хранит глобальное состояние, поэтому может точно применять лимиты на все application server сразу. Если нужно 100 запросов в минуту глобально, ты получишь ровно это, независимо от числа серверов.

![Иллюстрация](/content/distributed-rate-limiter/0fb312dfd4.svg)

Dedicated Service Rate Limiter

###### Сложности

Главный минус — latency. Каждый запрос к системе теперь требует дополнительного сетевого round trip, прежде чем его можно будет обработать. Даже если rate limiter быстрый (скажем, 10 мс), это всё равно 10 мс сверху к каждому запросу. На большом масштабе это складывается.

Ты также добавил ещё одну точку отказа. Если сервис rate limiting упадёт, придётся решать: fail open (пропускать все запросы, рискуя перегрузкой) или fail closed (отклонять все запросы, по сути отключая твой API)? Ни один вариант не хорош.

Есть и операционная сложность. Теперь у тебя появился ещё один сервис, который нужно деплоить, мониторить, масштабировать и поддерживать. Сам сервис rate limiting должен быть highly available, а это значит: резервирование, health check и, скорее всего, какая-то репликация данных.

Наконец, нужно аккуратно обрабатывать сетевые проблемы. Что если rate limiter медленно отвечает? Ждать (добавляя ещё больше latency) или прервать по timeout и действовать наугад? А если между application server и rate limiter случится network partition?

#### Отличное решение: API Gateway/Load Balancer

###### Подход

Rate limiter работает на самой границе системы, встроенный в твой API gateway или load balancer. Каждый входящий запрос сначала попадает в rate limiter, и только потом доходит до application server. Rate limiter изучает запрос (проверяет IP-адрес, заголовки аутентификации пользователя, API key), применяет подходящие лимиты и либо пересылает запрос дальше, либо сразу возвращает HTTP 429.

Это самый популярный подход в production-системах: он концептуально прост и обеспечивает надёжную защиту. Твои application server никогда не видят заблокированные запросы, поэтому могут целиком сосредоточиться на обработке легитимного трафика. Для любителей аналогий: rate limiter работает как вышибала в клубе. Нарушителей разворачивают у входа, а не после того, как они уже зашли внутрь и устроили проблемы, как было в нашем «хорошем» подходе.

![Иллюстрация](/content/distributed-rate-limiter/3887bc35b6.svg)

API Gateway Rate Limiter

###### Сложности

Главное ограничение — контекст. Rate limiter имеет доступ только к информации из самого HTTP-запроса: заголовкам, URL, IP-адресу и базовым токенам аутентификации. Он не видит более глубокую бизнес-логику или пользовательский контекст, который может жить на уровне приложения. Например, правило вроде «премиум-пользователи получают лимиты в 10 раз выше» реализовать непросто, если только премиум-статус не закодирован в JWT-токене или чём-то подобном.

Остаётся и вопрос, где хранить состояние rate limiting. Gateway нужен быстрый доступ к счётчикам и timestamp, а это обычно означает in-memory хранилище вроде Redis. Но тогда появляются внешние зависимости, и нужно обрабатывать случаи, когда Redis работает медленно или недоступен.

Подробно о том, как сделать это эффективно, поговорим в deep dives!

Для нашего дизайна выберем подход с API Gateway. Это самый распространённый паттерн, и он даёт централизованный контроль без дополнительных сетевых вызовов на каждый запрос. Теперь можно переключиться на следующий вопрос: как идентифицировать клиентов?

**Как идентифицировать клиентов?**

Раз мы выбрали подход с API Gateway, наш rate limiter имеет доступ только к информации из самого HTTP-запроса. Это URL/путь запроса, все HTTP-заголовки (Authorization, User-Agent, X-API-Key и т. д.), query-параметры и IP-адрес клиента. Технически мы можем делать внешние вызовы к базам данных или другим сервисам, но это добавляет latency, которой мы хотим избежать, поэтому ограничимся самим запросом.

Сначала нужно решить, что делает «клиента» уникальным. От выбранного ключа зависит, как применяются лимиты. Есть три основных варианта:

* **User ID**: идеально для API с аутентификацией. Каждый залогиненный пользователь получает собственную квоту. Обычно он передаётся в заголовке Authorization в виде JWT-токена.
* **IP-адрес**: подходит для публичных API или когда нет пользовательских аккаунтов. Но учитывай пользователей за NAT или корпоративными firewall. IP-адрес обычно передаётся в заголовке X-Forwarded-For.
* **API key**: распространён в API для разработчиков. У каждого владельца ключа свои лимиты. Чаще всего ключ передаётся в заголовке X-API-Key.

Самое время задать интервьюеру несколько вопросов. Все ли пользователи аутентифицированы? Это API для разработчиков, требующий API key? И так далее.

На практике, скорее всего, понадобится комбинация. Например, аутентифицированные пользователи получают лимиты выше, чем анонимные IP, а премиум-пользователи — ещё выше. Это отражает реальные системы, которые применяют не один глобальный лимит, а несколько слоёв правил. Например:

* **Лимиты на пользователя**: «Alice может делать 1000 запросов в час»
* **Лимиты на IP**: «Этот IP может делать 100 запросов в минуту»
* **Глобальные лимиты**: «Наш API выдерживает 50 000 запросов в секунду суммарно»
* **Лимиты на endpoint**: «Search API ограничен 10 запросами в минуту, а обновления профиля — 100 в минуту»

Твой rate limiter должен проверять все применимые правила и применять самое строгое. Если Alice израсходовала 50 из своих 1000 запросов, но её IP упёрся в лимит 100 запросов, она будет заблокирована.

### 2) Система должна ограничивать запросы на основе настраиваемых правил

Теперь переходим к сердцу rate limiting: алгоритму, который решает, пропустить запрос или отклонить. Именно здесь принимаются настоящие инженерные решения, но на собеседованиях по system design этот вопрос обычно не в центре внимания (в отличие от low-level design). Нужно показать, что ты знаешь разные варианты, и сделать выбор. Реализовывать алгоритм, даже в виде псевдокода, скорее всего, не придётся.

В production-системах используют четыре основных алгоритма. Они по-разному балансируют точность, расход памяти и сложность. Разберём каждый и поймём, когда его стоит выбирать.

#### Fixed Window Counter

Самый простой подход: время делится на фиксированные окна (например, минутные), и в каждом окне считаются запросы. Для каждого пользователя мы храним счётчик, который обнуляется в начале нового окна. Если счётчик превысил лимит, новые запросы отклоняются до начала следующего окна.

Например, при лимите 100 запросов в минуту окна могут быть такими: 12:00:00-12:00:59, 12:01:00-12:01:59 и так далее. Пользователь может сделать 100 запросов в каждом окне, а потом должен ждать начала следующего.

![Иллюстрация](/content/distributed-rate-limiter/c1eea12145.svg)

Fixed Window Counter

Реализовать это очень просто: достаточно hash table, которая сопоставляет ID клиента паре (counter, window\_start\_time). Основная проблема — граничные эффекты: пользователь может сделать 100 запросов в 12:00:59 и сразу же ещё 100 в 12:01:00, то есть фактически получить 200 запросов за 2 секунды. Кроме того, возможна «starvation»: если пользователь выбрал лимит в начале окна, ему приходится ждать остаток окна.

```
{
  "alice:12:00:00": 100,
  "alice:12:01:00": 5,
  "bob:12:00:00": 20,
  "charlie:12:00:00": 0,
  "dave:12:00:00": 54,
  "eve:12:00:00": 0,
  "frank:12:00:00": 12,
}
```

#### Sliding Window Log

Этот алгоритм хранит для каждого пользователя лог временных меток отдельных запросов. Когда приходит новый запрос, ты удаляешь все метки старше окна (например, старше одной минуты), а затем проверяешь, не превышает ли оставшееся количество лимит.

Это даёт идеальную точность. Ты всегда смотришь ровно на последние N минут запросов, независимо от того, когда пришёл текущий. Никаких граничных эффектов и несправедливых всплесков.

![Иллюстрация](/content/distributed-rate-limiter/4801996001.svg)

Sliding Window Log

Минус — расход памяти. Если пользователь делает 1000 запросов в минуту, нужно хранить 1000 временных меток. При миллионах пользователей память быстро становится проблемой. Есть и вычислительные накладные расходы: на каждый запрос приходится просматривать лог временных меток.

#### Sliding Window Counter

Это хитрый гибрид: скользящее окно приближённо вычисляется на основе фиксированных окон с небольшой математикой. Ты держишь счётчики для текущего и предыдущего окна. Когда приходит запрос, ты оцениваешь, сколько запросов пользователь «должен был» сделать в настоящем скользящем окне, взвешивая предыдущее и текущее окна в зависимости от того, насколько далеко ты продвинулся по текущему окну.

Например, если прошло 30% текущей минуты, ты берёшь 70% запросов предыдущей минуты плюс 100% запросов текущей.

Точность получается намного лучше, чем у fixed window, а памяти нужно минимум: всего два счётчика на клиента. Взамен это лишь приближение, которое предполагает равномерное распределение трафика внутри окон, да и математику бывает непросто реализовать правильно.

#### Token Bucket

Представь, что у каждого клиента есть ведро, в которое помещается определённое число токенов (burst capacity). Токены добавляются в ведро с постоянной скоростью (refill rate). Каждый запрос забирает один токен. Если токенов нет, запрос отклоняется.

Например, ведро вмещает 100 токенов (допускает всплески до 100 запросов) и пополняется со скоростью 10 токенов в минуту (устойчивая скорость 10 запросов в минуту). Клиент может сразу сделать 100 запросов, а потом должен ждать, пока токены пополнятся.

Так учитываются и устойчивая нагрузка (refill rate), и кратковременные всплески (размер ведра). Алгоритм к тому же прост в реализации: для каждого клиента достаточно хранить (tokens, last\_refill\_time). Сложности — подобрать правильный размер ведра и refill rate и справиться с «cold start», когда простаивавшие клиенты начинают с полными вёдрами.

![Иллюстрация](/content/distributed-rate-limiter/fb4e3ed423.svg)

Token Bucket

Для нашей системы мы выберем алгоритм Token Bucket. Он лучше всего сочетает простоту, эффективное использование памяти и работу с реальными паттернами трафика. Такие компании, как Stripe, используют этот подход, потому что он естественно подходит для всплесковой природы API-трафика и при этом обеспечивает общий лимит.

Теперь перед нами новая проблема. Мы понимаем, как Token Bucket работает концептуально, но где и как на самом деле хранить ведро каждого пользователя? Для каждого ведра нужно отслеживать два значения: текущее количество токенов и время последнего пополнения. Это состояние должно быть общим для всех экземпляров нашего API gateway.

Если хранить вёдра в памяти внутри каждого экземпляра gateway, мы вернёмся к той же проблеме координации, которую обсуждали для in-process rate limiting. Load balancer распределяет запросы пользователей по нескольким gateway. Каждый gateway будет вести собственную версию ведра пользователя и видеть лишь часть его трафика.

Например, если Alice делает 50 запросов, которые попадают на Gateway A, и 50 запросов, которые попадают на Gateway B, каждый gateway решит, что Alice сделала всего 50 запросов, и пропустит их все. Но глобально Alice сделала 100 запросов, и её нужно ограничить. Без централизованного состояния наш алгоритм бесполезен.

Для этого можно взять что-то вроде [Redis](/lessons/key-technologies/redis). Redis — быстрое in-memory хранилище данных, доступное всем нашим экземплярам gateway. Redis может стать единым источником истины для всего состояния token bucket. Когда любому gateway нужно проверить или обновить лимит пользователя, он обращается к Redis.

Вот как именно работает алгоритм Token Bucket с Redis:

1. Запрос пользователя Alice с user ID alice приходит на Gateway A.
2. Gateway обращается к Redis, чтобы получить текущее состояние ведра Alice, командой HMGET alice:bucket tokens last\_refill. Команда HMGET возвращает значения нескольких полей Redis hash. В нашем случае мы получаем текущее количество токенов (tokens) и временную метку last\_refill для ведра Alice.
3. Gateway вычисляет, сколько токенов нужно добавить в ведро Alice, исходя из времени, прошедшего с последнего пополнения. Если ведро обновлялось 30 секунд назад, а refill rate — 1 токен в секунду, gateway добавляет 30 токенов к текущему количеству, но не больше максимальной ёмкости ведра.
4. Затем gateway атомарно обновляет состояние ведра Alice с помощью транзакции Redis, чтобы избежать race condition:

   ```
   MULTI
   HSET alice:bucket tokens <new_token_count>
   HSET alice:bucket last_refill <current_timestamp>
   EXPIRE alice:bucket 3600
   EXEC
   ```

   Блок MULTI/EXEC гарантирует, что все команды выполнятся как одна атомарная операция. Команды HSET обновляют поля hash новым количеством токенов и временной меткой, а EXPIRE автоматически удаляет ведро после 1 часа неактивности, чтобы не допустить утечек памяти.
5. Наконец, gateway принимает окончательное решение на основе обновлённого количества токенов Alice. Если доступен хотя бы 1 токен, gateway пропускает запрос и уменьшает счётчик токенов на 1. Если токенов не осталось, gateway отклоняет запрос.

Но подожди: здесь есть race condition!

Несмотря на транзакцию MULTI/EXEC, в нашей реализации всё ещё есть тонкий race condition. Проблема в том, что операция чтения (HMGET) выполняется вне транзакции. Если два запроса для одного пользователя приходят одновременно, оба gateway читают одно и то же начальное количество токенов, оба решают, что запрос можно пропустить, и оба обновляют ведро. В итоге мы можем пропустить 2 запроса, хотя доступен был только 1 токен.

Решение — перенести всю логику «прочитать, вычислить, обновить» в одну атомарную операцию. В Redis это делается с помощью Lua scripting. Lua-скрипты атомарны, поэтому всё решение rate limiter'а становится свободным от race condition. Вместо отдельных операций чтения и записи мы отправляем в Redis Lua-скрипт, который читает текущее состояние, вычисляет новое количество токенов и обновляет ведро одним атомарным шагом.

###### Паттерн: Dealing with Contention

Race condition в распределённых счётчиках — классическая задача на **dealing with contention**. Когда несколько потоков или процессов одновременно пытаются обновить один и тот же ресурс, можно потерять обновления, даже если отдельные операции атомарны. Решение — расширить атомарную границу так, чтобы она охватывала всю последовательность read-modify-write.

[Изучить этот паттерн](/lessons/patterns/dealing-with-contention)

Почему Redis здесь подходит идеально:

* Скорость — отклик меньше миллисекунды для простых операций
* Автоматическая очистка — EXPIRE удаляет вёдра неактивных пользователей после 1 часа без активности
* High availability — можно реплицировать на несколько экземпляров Redis
* Атомарные операции — транзакция MULTI/EXEC исключает race condition между gateway

В итоге мы получаем точный и согласованный rate limiting на всех экземплярах gateway. Попадёт 100-й запрос Alice на Gateway A, B или C, все они видят одно и то же состояние token bucket и применяют один и тот же лимит.

### 3) При превышении лимитов отклоняй запросы с HTTP 429 и полезными заголовками

Теперь нужно решить, что происходит, когда пользователь упирается в rate limit. Кажется, что тут всё просто (вернуть ошибку), но есть важные дизайн-решения, которые влияют и на пользовательский опыт, и на производительность системы.

**Отбрасывать запросы или ставить в очередь?**

Первое решение: сразу отклонять лишние запросы или откладывать их в очередь на потом. Большинство rate limiter'ов идут по пути «fail fast»: при превышении лимитов они сразу возвращают HTTP-статус 429. Его мы и реализуем.

Альтернатива — ставить лишние запросы в очередь и обрабатывать их, когда лимит пользователя сбросится. Звучит дружелюбно к пользователю, но проблем это создаёт больше, чем решает. Запросы в очереди занимают память и ресурсы на обработку. Пользователи могут решить, что их запросы упали, и начать повторять их, создавая ещё больше нагрузки. И хуже всего то, что задержки при обработке очереди делают время ответа твоего API непредсказуемым.

Есть нишевые случаи, когда очередь оправданна, например системы пакетной обработки, которые могут позволить себе ждать, но для интерактивных API быстрый отказ почти всегда правильный выбор.

**Как сделать ответ полезным?**

429 — стандартный HTTP-статус для «Too Many Requests». Он существует в спецификации HTTP именно для этой цели.

Отклоняя запрос, мы возвращаем HTTP 429 «Too Many Requests» вместе с заголовками, которые помогают клиенту понять, что произошло и как восстановиться. Ключевые заголовки:

* X-RateLimit-Limit: потолок rate limit для этого запроса (например, "100")
* X-RateLimit-Remaining: количество оставшихся запросов в текущем окне (например, "0")
* X-RateLimit-Reset: когда лимит сбросится, в виде Unix timestamp (например, "1640995200")

Некоторые системы также добавляют Retry-After, который говорит клиенту, сколько секунд подождать перед следующей попыткой.

Вот как может выглядеть полный ответ 429:

```
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1640995200
Retry-After: 60
Content-Type: application/json

{
  "error": "Rate limit exceeded",
  "message": "You have exceeded the rate limit of 100 requests per minute. Try again in 60 seconds."
}
```

Эти заголовки позволяют корректно написанным клиентам реализовать нормальные стратегии backoff. Клиент видит, когда именно повторить запрос, а не заваливает твой API заведомо неудачными запросами.

Что касается интервью, обычно достаточно упомянуть, что ты знаешь: в ответ нужно вернуть 429 и соответствующие заголовки.

## [Deep dives](/lessons/sd-prep/delivery)

До сих пор мы проектировали простой rate limiter на одной ноде (то есть с одним инстансом Redis). Теперь нужно обсудить, как масштабировать его до 1M запросов/секунду на 10M пользователей, сохраняя высокую доступность и низкий latency.

В таких задачах про распределённые системы стоит вести разговор к тем deep dives, которые отвечают твоим нефункциональным требованиям. Но интервьюеры, скорее всего, будут вмешиваться с уточняющими вопросами, так что будь готов к гибкости.

### 1) Как масштабироваться до 1M запросов/секунду?

В нашем текущем дизайне несколько API gateway обращаются к одному инстансу Redis. Для небольших нагрузок это работает нормально, но на целевом масштабе в 1M запросов/секунду математика не сходится. Типичный инстанс Redis обрабатывает примерно 100 000–200 000 операций в секунду в зависимости от сложности операции. Каждая наша проверка rate limit требует нескольких операций в Redis: минимум HMGET, чтобы получить состояние, и HSET, чтобы его обновить. Поэтому один инстанс Redis реалистично потянет где-то 50 000–100 000 проверок rate limit в секунду, после чего станет узким местом.

При 1M запросов/секунду нужно распределить нагрузку на Redis между несколькими инстансами. Но это не так просто, как поднять ещё несколько серверов Redis: нужен способ партиционировать данные rate limiting, чтобы каждый запрос знал, с каким инстансом Redis ему разговаривать.

###### Паттерн: Scaling Writes

Rate limiter'ы — классический пример задач на **scaling writes**: миллионы обновлений счётчиков в секунду. Каждая проверка rate limit требует атомарных операций read-modify-write, чтобы обновить token bucket'ы или счётчики запросов на распределённых shard'ах Redis.

[Изучить этот паттерн](/lessons/patterns/scaling-writes)

Стратегия шардирования зависит от наших правил rate limiting. Напомню, ранее мы выделили несколько типов клиентов: user ID для аутентифицированных пользователей, IP-адреса для анонимных и API-ключи для доступа разработчиков. Шардировать нужно консистентно, чтобы все запросы клиента всегда попадали на один и тот же инстанс Redis. Если пользователь "alice" то попадает на shard 1, то на shard 2, её состояние rate limiting разваливается на части и становится бесполезным.

Для этого нужен алгоритм распределения, например [consistent hashing](/lessons/core-concepts/consistent-hashing). Для аутентифицированных пользователей мы хешируем user ID, чтобы определить, на каком shard Redis хранятся их данные rate limit. Для анонимных хешируем IP-адрес. Для запросов с API-ключом хешируем сам ключ. Так состояние rate limiting каждого клиента живёт ровно на одном shard, а нагрузка равномерно распределяется по всем shard'ам.

![Иллюстрация](/content/distributed-rate-limiter/1a16e8b559.svg)

Шардирование Redis

Каждому API gateway нужна логика маршрутизации, чтобы определить, к какому shard Redis обращаться. Когда приходит запрос, gateway извлекает подходящий идентификатор (user ID, IP или API-ключ), применяет алгоритм распределения и направляет проверку rate limit на нужный инстанс Redis. Алгоритм Token Bucket остаётся точно таким же, мы просто общаемся с разными инстансами Redis вместо одного.

С 10 shard'ами Redis, каждый из которых обрабатывает ~100k операций/секунду, мы должны потянуть целевые 1M запросов/секунду.

В продакшене, скорее всего, ты будешь использовать Redis Cluster, а не управлять отдельными инстансами Redis самостоятельно. Redis Cluster автоматически делает то шардирование данных, которое мы только что описали: делит ключи на 16 384 hash slot'а и распределяет эти slot'ы между несколькими нодами Redis. Когда ты сохраняешь ключ rate limit вроде alice:bucket, Redis Cluster сам определяет, на какой ноде его хранить, исходя из hash slot'а ключа. Так что вместо собственной логики consistent hashing в API gateway ты просто подключаешься к Redis Cluster, а он сам занимается маршрутизацией.

### 2) Как обеспечить высокую доступность и отказоустойчивость?

Теперь, когда мы масштабировались до нескольких shard'ов Redis, каждый shard становится критичным компонентом системы. Если любой shard Redis падает, все пользователи, чьи данные rate limiting лежат на этом shard, теряют rate limiting. Это создаёт проблемы с доступностью и может привести к каскадным сбоям, если пользователи начнут агрессивно повторять запросы, не получая корректных ответов о rate limit.

Когда shard Redis становится недоступен, нужно принять принципиальное решение о режиме отказа. Есть два варианта:

#### Хорошее решение: Fail-Closed

###### Подход

Когда rate limiter не может достучаться до Redis, отклоняй все запросы с HTTP 503 «Service Unavailable» или HTTP 429. Это самый строгий вариант: не проходит ни один запрос, о котором мы не можем проверить, что он укладывается в лимиты.

###### Сложности

Фактически это отключит твой API на время сбоя Redis. Пользователи видят неудачные запросы, даже если backend-сервисы здоровы. На практике это часто создаёт проблемы хуже той, которую rate limiting должен был решать. Увидев ошибки 503, пользователи могут агрессивно повторять запросы, создавая ещё больше нагрузки на твои системы.

Тем не менее у fail-closed есть вполне законные сценарии. Финансовые системы, обрабатывающие платежи, могут предпочесть отклонить транзакции, а не рисковать обработкой без rate limit'ов. Среды с повышенными требованиями к безопасности, где неконтролируемый доступ хуже простоя, тоже могут выбрать этот подход.

#### Хорошее решение: Fail-Open

###### Подход

Когда rate limiter не может достучаться до Redis, пропускай все запросы так, будто rate limiting отключён. API gateway пропускает проверки rate limit и пересылает запросы напрямую в backend-сервисы. Так твой API остаётся доступным, даже когда у инфраструктуры rate limiting проблемы.

###### Сложности

Очевидный минус: временно теряется защита rate limit'ами. Во время сбоев Redis злоумышленники потенциально могут завалить твои backend-сервисы запросами. Что ещё важнее, **это может вызвать каскадные сбои**: если Redis упал из-за того, что ты и так под высокой нагрузкой, fail-open отправит весь этот трафик вниз по цепочке, потенциально обрушив всю систему.

Для платформ соцсетей это особенно опасно во время вирусных событий, когда скачки трафика и так нагружают систему. Fail-open может превратить сбой rate limiter'а в полный отказ платформы.

Как видишь, оба варианта «хорошие», потому что выбор зависит от конкретных требований системы!

Для нашей социальной платформы мы выберем fail-closed. Это может показаться нелогичным, ведь нам нужна высокая доступность, но на практике сбои rate limiter'а часто совпадают со всплесками трафика, когда защита нужна больше всего. Во время вирусных событий, если Redis упадёт, а мы выберем fail-open, внезапный поток твитов, обновлений ленты и уведомлений может перегрузить наши backend-базы данных, и сбой rate limiter'а превратится в отказ всей платформы. Короткие периоды отклонённых запросов лучше, чем каскадный коллапс системы.

Конечно, выбор режима отказа — это лишь ограничение ущерба. Лучше всего вообще не допускать сбоев Redis с помощью архитектуры высокой доступности. Стандартное решение для доступности Redis — репликация master-replica. У каждого shard'а Redis есть одна или несколько read replica, которые постоянно синхронизируются с master'ом. Когда master падает, одна из replica автоматически повышается до нового master'а. Особенно хорошо это работает с Redis Cluster: в нём есть встроенные механизмы failover, которые обнаруживают отказ master'а и повышают replica без ручного вмешательства. Компромисс — рост стоимости инфраструктуры и необходимость учитывать лаг синхронизации replica, хотя репликация в Redis обычно работает очень быстро.

![Иллюстрация](/content/distributed-rate-limiter/981e1a44b3.svg)

Redis Failover

Мы нечасто говорим об этом в наших разборах (просто потому, что обычно есть более интересные темы), но мониторинг и алертинг важны для поддержания высокой доступности. Нужно отслеживать метрики здоровья Redis: загрузку CPU, потребление памяти и сетевую связность по всем shard'ам. Также нужен мониторинг на уровне приложения: доля успешных проверок rate limiting, latency ответов и алерты, которые срабатывают при переходе в режим fail-open. Цель — обнаруживать проблемы и реагировать на них достаточно быстро, чтобы пользователи не заметили деградации сервиса.

### 3) Как минимизировать накладные расходы на latency?

Каждая проверка rate limit требует сетевого round trip до Redis, а это добавляет latency к пользовательским запросам. Операции Redis обычно занимают меньше миллисекунды, но сетевые издержки могут добавлять по несколько миллисекунд на запрос. При 1M запросов в секунду эта latency может стать проблемой.

Самая важная оптимизация — connection pooling. Вместо того чтобы открывать новое TCP-соединение с Redis для каждой проверки rate limit, твои API gateway поддерживают пул постоянных соединений. Это убирает издержки на TCP handshake (которые могут составлять 20–50 мс в зависимости от сетевого расстояния) и позволяет переиспользовать соединения для многих запросов. Большинство клиентов Redis управляют connection pooling автоматически, но размер пула нужно подбирать под объём запросов и время ответа Redis.

Самый большой выигрыш по latency даёт географическое распределение. Размещай инфраструктуру rate limiting ближе к пользователям, например API gateway и кластеры Redis в нескольких регионах. Пользователь из Токио, который обращается к инстансу Redis в Вирджинии, увидит намного более высокую latency, чем при обращении к инстансу в том же регионе. Компромисс — сложность с консистентностью данных между регионами, но для rate limiting часто можно принять eventual consistency между регионами в обмен на меньшую latency.

Есть и другие оптимизации, которые стоит упомянуть вкратце, не углубляясь: локальный cache состояния rate limit может работать, но это рискованно, так как устаревшие данные в cache могут привести к неверным решениям по rate limiting. Redis pipelining или Lua-скрипты позволяют объединять операции и сокращать число round trip'ов. Request batching помогает, когда от одного пользователя одновременно приходит несколько запросов. Однако эти оптимизации усложняют систему и обычно не нужны, если ты как следует реализовал connection pooling и географическое распределение. На собеседовании я бы, скорее всего, не стал их упоминать, пока об этом прямо не спросят.

### 4) Как обрабатывать hot key (сценарии с вирусным контентом)?

Hot key часто упоминают в обсуждениях system design, и техники работы с ними мы разбираем в нашем [паттерне scaling reads](/lessons/patterns/scaling-reads). Для rate limiting hot key могут возникать как из-за абьюзивного трафика, так и из-за легитимных клиентов с большим объёмом запросов.

###### Паттерн: Scaling Reads

Хотя rate limiter в основном обрабатывает записи (обновления счётчиков), сценарии с hot key создают экстремальную нагрузку в духе **scaling reads**, когда тысячи запросов с одного IP или от одного пользователя одновременно приходят на проверки rate limit и перегружают отдельные shard'ы Redis.

[Изучить этот паттерн](/lessons/patterns/scaling-reads)

Подумай, что нужно, чтобы создать hot key в нашем rate limiter'е. Один пользователь или IP должен генерировать достаточно запросов, чтобы перегрузить shard Redis, то есть речь о десятках тысяч запросов в секунду от одного источника. Часто это признак абьюза (DDoS-атаки, неправильно настроенные боты), но так могут вести себя и легитимные клиенты с большим объёмом запросов: аналитические системы, data pipeline'ы или мобильные приложения с агрессивным обновлением данных.

Для разных сценариев нужны разные стратегии:

**Для легитимных клиентов с большим объёмом запросов:**

* **Client-side rate limiting**: Поощряй добросовестных клиентов реализовывать собственный rate limiting, чтобы сглаживать паттерны трафика. Это не даёт легитимным пользователям случайно создавать hot shard'ы и снижает нагрузку на сервер. Многие API SDK включают встроенный client-side rate limiting, который учитывает заголовки ответов сервера.
* **Request queuing/batching**: Позволь клиентам объединять несколько операций в один запрос, чтобы уменьшить общее число нужных проверок rate limit.
* **Premium-тарифы**: Предложи более высокие лимиты для продвинутых пользователей, которым они нужны, возможно, с выделенной инфраструктурой.

**Для абьюзивного трафика:**

* **Автоматическая блокировка**: Когда клиент постоянно упирается в rate limit (скажем, 10 раз в минуту), временно блокируй его IP/API key целиком, добавив в blocklist. Этот список можно хранить в одном из shard'ов Redis и проверять только при cache miss.
* **Защита от DDoS**: Используй сервисы вроде Cloudflare или AWS Shield, которые могут обнаруживать и блокировать вредоносный трафик до того, как он доберётся до твоего rate limiter'а.

Главная мысль в том, что client-side rate limiting — ценное дополнение к защите на стороне сервера. Доверять клиентам в вопросах безопасности нельзя, но поощрение добросовестного поведения в экосистеме твоего API снижает нагрузку на инфраструктуру и не даёт легитимным пользователям случайно спровоцировать сценарий с hot shard.

Вполне возможно, что легитимные пользователи будут делить общие IP-адреса (корпоративные NAT, публичный WiFi), но к этому нужно подготовиться заранее при проектировании rate limit'ов, а не пытаться обрабатывать hot key постфактум. Задавай более высокие лимиты для rate limiting по IP и по возможности опирайся на лимиты для аутентифицированных пользователей.

### 5) Как обрабатывать динамическую конфигурацию правил?

До сих пор мы считали правила rate limiting статичными: пользователь X получает Y запросов в минуту. Но production-системам нужна гибкость, чтобы менять лимиты без деплоя нового кода. Может понадобиться временно поднять лимиты во время запуска продукта, дать премиум-клиентам более высокие лимиты или быстро снизить лимиты, если ты видишь необычные паттерны трафика.

Есть два основных подхода к динамическому обновлению конфигурации:

#### Хорошее решение: конфигурация на основе polling

###### Подход

Храни конфигурацию правил в базе данных или в отдельном сервисе конфигурации. Твои API gateway периодически опрашивают его на предмет изменений (скажем, каждые 30 секунд) и обновляют свою логику rate limiting. Это самый распространённый подход: его просто реализовать, и он покрывает большинство случаев.

Сервис конфигурации может быть простой таблицей в базе данных со столбцами client\_type, endpoint, requests\_per\_minute и так далее. Gateway запрашивают эту таблицу по расписанию и кэшируют результаты локально.

###### Сложности

Главный минус — задержка обновления. Всегда есть окно между изменением правила и моментом, когда оно вступит в силу на всех gateway. Если нужно экстренно снизить лимиты из-за атаки, изменение может распространяться до 30 секунд. В большинстве операционных сценариев такая задержка приемлема, но в срочных ситуациях она может быть проблемой.

#### Отличное решение: конфигурация на основе push

###### Подход

Используй push-систему, в которой изменения конфигурации сразу рассылаются всем API gateway. Именно для этого был создан [ZooKeeper](/lessons/key-technologies/zookeeper): распределённое управление конфигурацией с уведомлениями в реальном времени. ZooKeeper хранит данные конфигурации и немедленно уведомляет всех подключённых клиентов (твои API gateway) при любом изменении. Другие варианты — Redis pub/sub или собственные сервисы конфигурации, которые поддерживают постоянные соединения с gateway.

Когда оператор меняет правило rate limit, сервис конфигурации сразу уведомляет все подключённые gateway, и они обновляют свои правила в течение нескольких секунд.

![Иллюстрация](/content/distributed-rate-limiter/fc2786baef.svg)

ZooKeeper

###### Сложности

Этот подход сильно усложняет систему. Нужно обрабатывать обрывы соединений, следить, чтобы все gateway получили обновления, и разбираться с частичными сбоями, когда одни gateway обновились успешно, а другие нет. Кроме того, нужны запасные механизмы на случай, если push-система недоступна.

Такая операционная сложность обычно оправдана только для систем, которым нужны очень быстрые обновления правил, например при инцидентах безопасности или в сценариях высокочастотного трейдинга.

## [Чего ждут на каждом уровне](https://www.hellointerview.com/blog/the-system-design-interview-what-is-expected-at-each-level)

### Mid-level

Кандидат уровня mid-level в основном сосредоточен на ширине (80% к 20%) и должен уметь составить high-level design, который закрывает функциональные требования, хотя многие компоненты будут абстракциями, которые ты понимаешь лишь поверхностно. Интервьюер потратит время, чтобы убедиться, что ты понимаешь, что делает каждый компонент: если ты упомянул Redis, жди вопросов о том, как он работает и почему ты его выбрал. Ты должен вести обсуждение на ранних этапах, таких как сбор требований и выбор базового алгоритма, но не стоит ожидать, что ты сам заметишь все изъяны дизайна. Конкретно в этой задаче нужно чётко объяснить один алгоритм rate limiting (Token Bucket вполне подойдёт), разумно разместить rate limiter в архитектуре (API Gateway), назвать Redis решением для общего состояния, а на вопрос о масштабировании понять, что Redis нужно шардировать (shard), и примерно представлять, как это работает.

### Senior

От senior-кандидата ожидают больше технической глубины (60% ширины и 40% глубины): ты должен уверенно обсуждать trade-offs между разными алгоритмами rate limiting и объяснять свой выбор. Нужно без особых подсказок разбираться в концепциях распределённых систем, таких как consistent hashing, Redis Cluster и connection pooling, знать, что операции в Redis должны быть атомарными, и предложить транзакции MULTI/EXEC. Ты должен чётко объяснять trade-offs между стратегиями fail-open и fail-closed, обсуждать плюсы и минусы разных вариантов размещения rate limiter и самостоятельно находить потенциальные проблемы: hot keys, вопросы доступности Redis, возможности для оптимизации latency. Конкретно для rate limiting кандидаты уровня E5 должны быстро пройти базовое обсуждение алгоритмов, чтобы уделить время проблемам распределённых систем, уверенно обсуждать стратегии шардирования Redis и сценарии failover, а также иметь своё мнение о подходах к управлению конфигурацией.

### Staff+

Кандидаты уровня Staff+ должны демонстрировать глубокое понимание распределённого rate limiting в продакшене (40% ширины и 60% глубины) и опираться на реальный опыт работы с системами похожего масштаба. От тебя ждут исключительной проактивности. Ты должен сам находить edge cases, обсуждать требования к observability и предлагать операционные процедуры без подсказок. У тебя должно быть твёрдое мнение о выборе технологий, основанное на опыте, ты естественно рассуждаешь о multi-region деплоях и консистентности данных между географическими регионами, а вопросы о постепенных rollout и canary-деплоях воспринимаешь как рутину. Кандидатам уровня Staff+ этот вопрос часто не задают, потому что эти концепции даются им естественно, но если его всё же задали, нужно быстро заложить основы дизайна и потратить большую часть времени на продакшен-эксплуатацию, режимы отказов и проблемы интеграции систем, которые знакомы только по реальному опыту.

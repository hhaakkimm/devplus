## Разбор задачи

**📰 Что такое [Google News](https://news.google.com/)?**
Google News — это цифровой сервис, который собирает и показывает новостные статьи от тысяч издателей по всему миру в прокручиваемом интерфейсе, чтобы пользователи были в курсе текущих событий.

### [Функциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Пользователи должны видеть агрегированную ленту новостных статей от тысяч издателей-источников со всего мира
2. Пользователи должны иметь возможность «бесконечно» прокручивать ленту
3. Пользователи должны иметь возможность кликнуть на статью и перейти на сайт издателя, чтобы прочитать её полностью

**Вне рамок (below the line):**

* Пользователи должны иметь возможность настраивать ленту под свои интересы
* Пользователи должны иметь возможность сохранять статьи, чтобы прочитать позже
* Пользователи должны иметь возможность делиться статьями в социальных сетях


### [Нефункциональные требования](/lessons/sd-prep/delivery)

Для новостной платформы availability важнее, чем consistency: пользователи скорее предпочтут слегка устаревший контент, чем вообще никакого.

**Основные требования**

1. Система должна отдавать приоритет availability над consistency (CAP theorem)
2. Система должна масштабироваться до 100 миллионов daily active users с пиками до 500 миллионов
3. Система должна обеспечивать низкую latency загрузки ленты (&lt; 200 мс)

**Вне рамок (below the line):**

* Система должна защищать данные и приватность пользователей
* Система должна справляться со всплесками трафика во время срочных новостей
* Система должна иметь надлежащий мониторинг и observability
* Система должна быть устойчивой к сбоям API издателей

## Подготовка

### План решения

Прежде чем погружаться в проектирование, я буду следовать фреймворку: последовательно пройду по функциональным требованиям, а нефункциональные использую, чтобы направлять deep dives. Для Google News нужно аккуратно сбалансировать scalability и производительность, чтобы выдержать высокую нагрузку.

### [Определение основных сущностей](/lessons/sd-prep/delivery)

Я люблю начинать с общего обзора основных сущностей, которые нам понадобятся. На этом этапе не обязательно знать каждую колонку и каждую деталь — мы займёмся ими позже, когда картина станет яснее. Выделив ключевые сущности сейчас, мы направим ход рассуждений и заложим прочный фундамент.

Когда рассказываешь про дизайн сущностей, сосредоточься на связях между ними и их назначении, а не на перечислении каждого атрибута.

Чтобы выполнить ключевые функциональные требования, нам понадобятся следующие сущности:

1. **Article**: представляет новостную статью с атрибутами вроде id, title, summary, thumbnail URL, publish date, publisher ID, region и media URLs. Это наша основная сущность контента.
2. **Publisher**: представляет источник новостей с атрибутами вроде id, name, URL, feed URL и region. Издатели — источник нашего контента.
3. **User**: представляет пользователей системы с атрибутами вроде id и region (который можно определить по IP или задать явно). Даже для анонимных пользователей мы храним базовую информацию.

На реальном интервью это может быть простой короткий список, как здесь. Просто обязательно проговори сущности с интервьюером, чтобы убедиться, что вы понимаете всё одинаково.

### [API](/lessons/sd-prep/delivery)

API — основной способ взаимодействия пользователей с нашей системой новостной ленты. Если определить его заранее, остальной дизайн получится структурированнее. Я создам endpoints для каждого из основных требований.

Чтобы пользователи могли смотреть агрегированную ленту новостных статей:

```
// Get a page of articles for the user's feed
GET /feed?page={page}&limit={limit}&region={region} -> Article[]
```

Пока мы используем простую offset-based pagination, но у неё есть проблемы с производительностью при бесконечной прокрутке. В deep dive мы заменим её на cursor-based pagination, чтобы лучше соответствовать требованиям к масштабу и удобству для пользователя.

Для просмотра конкретной статьи API endpoint не нужен: браузер сам перейдёт на сайт издателя, когда пользователь кликнет на статью, на основании поля url в объекте статьи.

## [High-Level Design](/lessons/sd-prep/delivery)

Будем строить дизайн постепенно: разберём функциональные требования по одному и добавим нужные компоненты по ходу дела. Для Google News нужно решить две задачи: собирать контент от тысяч издателей и эффективно доставлять его миллионам пользователей.

### 1) Пользователи должны видеть агрегированную ленту новостных статей от тысяч издателей по всему миру

Когда пользователь заходит в Google News, он должен увидеть персонализированную ленту свежих новостных статей. Здесь две отдельные задачи: собрать контент от издателей и эффективно отдать его пользователям.

Начнём со сбора данных от издателей. Для этого нужен **Data Collection Service**: фоновый процесс, который непрерывно собирает контент из тысяч новостных источников:

1. **Data Collection Service**: опрашивает RSS-фиды и API издателей каждые 3-6 часов, в зависимости от того, как часто обновляется каждый издатель.
2. **Publishers**: тысячи новостных источников по всему миру, которые отдают контент через RSS-фиды или API
3. **Database**: хранит собранные статьи, издателей и метаданные
4. **Object Storage**: хранит миниатюры (thumbnails) для статей

![Иллюстрация](/content/google-news/b6f453f1a8.svg)

Data Collection

Workflow нашего Data Collection Service:

1. Data Collection Service запрашивает у базы данных список издателей и URL их RSS-фидов, а затем опрашивает их один за другим.
2. Извлекает содержимое статей и метаданные, а также скачивает медиафайлы для использования в качестве thumbnails.
3. Сохраняет файлы thumbnails в Object Storage, а данные статей с URL медиафайлов записывает в Database

Что такое RSS? RSS — это простой XML-формат, который позволяет издателям синдицировать свой контент на другие сайты и в ридеры. Это распространённый формат для новостных агрегаторов вроде Google News: он простой, стандартизированный, и многие издатели его уже поддерживают. RSS-фиды к тому же относительно легко парсить, поэтому для нашей системы это хороший выбор.

RSS работает поверх HTTP. Достаточно сделать GET-запрос на URL RSS-фида, чтобы получить контент. В ответ приходит XML-документ с заголовком статьи, ссылкой и другими метаданными.

Ты можешь спросить: зачем скачивать картинку и хранить её в нашем Object Storage, если можно просто ссылаться на URL исходного изображения на стороне издателя? Хороший вопрос. Дело в том, что мы хотим отдавать изображения пользователям быстро и эффективно и не зависеть от серверов издателя, которые могут быть медленными, перегруженными или вообще упасть. Кроме того, мы хотим стандартизировать качество и размер изображений, чтобы пользовательский опыт был единообразным.

Теперь, когда данные поступают, их нужно отдавать пользователям. Для этого добавим **Feed Service**, который обрабатывает запросы пользователей:

1. **Client**: пользователи работают с Google News через веб-браузеры или мобильные приложения и запрашивают свою персонализированную ленту новостей
2. **API Gateway**: маршрутизирует входящие запросы, занимается аутентификацией, rate limiting и валидацией запросов, а затем передаёт их нужным сервисам
3. **Feed Service**: обрабатывает запросы пользователей на ленту: запрашивает релевантные статьи с учётом региона пользователя и форматирует ответ для клиента

Feed Service мы отделяем от Data Collection Service по нескольким ключевым причинам: у них совершенно разные требования к масштабированию (read-heavy против write-heavy), разная частота обновлений (real-time против batch) и разные операционные потребности (работа для пользователей против фоновой обработки).

![Иллюстрация](/content/google-news/d2aa5d963a.svg)

Query Articles

Когда пользователь запрашивает ленту новостей:

1. Client отправляет GET-запрос на /feed?region=US&limit=20
2. API Gateway направляет запрос в Feed Service
3. Feed Service запрашивает в Database свежие статьи для региона пользователя, отсортированные по дате публикации
4. Database возвращает данные статей, включая метаданные и URL медиафайлов, указывающие на Object Storage
5. Feed Service форматирует ответ и возвращает его клиенту через API Gateway

### 2) Пользователи должны иметь возможность «бесконечно» прокручивать ленту

Пользователи ожидают, что ленту новостей можно прокручивать непрерывно, без ручной пагинации. Для этого нужна пагинация, которая умеет подгружать новые порции контента по мере прокрутки.

Опираясь на существующую архитектуру, расширим Feed Service так, чтобы он поддерживал простую offset-based пагинацию: номера страниц и размеры страниц для получения порций статей.

Когда пользователь впервые загружает ленту:

1. Client отправляет GET-запрос на /feed?region=US&limit=20&page=1 (первая страница)
2. Feed Service запрашивает первые 20 статей для региона пользователя, отсортированные по дате публикации
3. В ответе приходят статьи и метаданные пагинации (total\_pages, current\_page)
4. Client запоминает номер текущей страницы для следующего запроса

Когда пользователь прокручивает ленту и подходит к концу текущего контента:

1. Client автоматически отправляет GET-запрос на /feed?region=US&limit=20&page=2
2. Feed Service вычисляет offset (page-1 \* limit) и получает следующие 20 статей
3. Запрос к базе данных забирает статьи с помощью OFFSET и LIMIT
4. Процесс повторяется, пока пользователь продолжает прокручивать страницы

Это простая основа для бесконечной прокрутки, хотя у неё есть ограничения по производительности и консистентности, к которым мы вернёмся в deep dives.

### 3) Пользователи должны иметь возможность кликнуть на статью и перейти на сайт издателя, чтобы прочитать её полностью

Здесь всё просто: браузер делает всё за нас. Когда пользователь кликает на статью, браузер переходит по URL статьи, сохранённому в нашей базе данных, и сразу открывает сайт издателя с полным текстом.

Сайты вроде Google News — это агрегаторы, и сами они контент не хостят. Они лишь ведут на сайт издателя, когда пользователь кликает на статью.

В настоящем Google News клики по статьям отслеживаются в аналитике, чтобы понимать поведение пользователей и улучшать рекомендации. Мы считаем это вне рамок задачи, но вот как это работало бы: ссылки на статьи вели бы на tracking endpoint Google, например GET /article/\{article\_id\}, который логирует событие клика и возвращает 302 redirect на сайт издателя. Эти данные о кликах помогают обучать рекомендательные алгоритмы и измерять вовлечённость.

Итак, пока всё довольно просто. Давай добавим немного сложности в deep dives.

## [Deep dives](/lessons/sd-prep/delivery)

Сейчас у нас есть базовая работающая система, которая закрывает основные функциональные требования Google News: пользователи видят агрегированные новости, бесконечно скроллят ленту и переходят на сайты издателей. Но у текущего дизайна есть серьёзные ограничения, особенно в части консистентности пагинации и скорости отдачи ленты при больших нагрузках. Вернёмся к нефункциональным требованиям и посмотрим, как улучшить систему, чтобы она выдерживала 100M DAU с низким latency и глобальным распределением.

### 1) Как улучшить консистентность и эффективность пагинации?

Наша текущая пагинация на основе offset имеет серьёзные ограничения, когда новые статьи публикуются постоянно. Представь, что пользователь листает ленту в разгар новостного дня, когда статьи выходят каждые несколько минут. При классической постраничной пагинации, если пользователь находится на второй странице и в начало ленты добавляются новые статьи, контент сдвигается вниз, и при запросе третьей страницы он может увидеть дубликаты или вообще пропустить часть материалов. Получается неприятный опыт: одни и те же статьи появляются по нескольку раз, а важные срочные новости пропускаются.

Тысячи издателей по всему миру публикуют статьи в течение дня, так что в пиковые периоды мы можем получать 50–100 новых статей в час. Пользователь, который листает ленту всего 10 минут, легко может несколько раз столкнуться с этим дрейфом пагинации: увидеть дубликаты или пропустить новые материалы, опубликованные, пока он читал.

Что можно сделать вместо этого?

#### Хорошее решение: курсоры на основе timestamp

##### Подход

Гораздо лучше использовать курсоры на основе timestamp вместо номеров страниц. Когда пользователь запрашивает ленту в первый раз, мы возвращаем статьи вместе с курсором, который представляет timestamp последней статьи в ответе. В следующих запросах клиент передаёт этот курсор, а мы выбираем статьи, опубликованные раньше этого timestamp: WHERE published\_at &lt; cursor\_timestamp ORDER BY published\_at DESC LIMIT 20.

Это устраняет проблему дрейфа пагинации, потому что мы всегда запрашиваем данные относительно фиксированной точки во времени, а не сдвигающегося offset. Новые статьи не влияют на пагинацию более старого контента, ведь мы фильтруем по границе timestamp. Курсор служит стабильной точкой отсчёта, которая остаётся валидной независимо от того, сколько нового контента добавится выше.

Пока у нас есть индекс по колонке published\_at, такой запрос будет эффективным.

##### Сложности

Главное ограничение курсоров на основе timestamp проявляется, когда у нескольких статей одинаковые timestamp, а в системах агрегации новостей это случается часто. Многие издатели импортируют статьи пачками или используют автоматизированные системы, которые присваивают один и тот же timestamp сразу нескольким статьям, опубликованным одновременно. Когда мы запрашиваем статьи раньше определённого timestamp, мы можем потерять статьи, у которых timestamp в точности совпадает с курсором.

В ленте появляются пробелы: пользователи пропускают статьи, опубликованные в тот же момент, что и граница курсора. В периоды высокой новостной активности или при обработке RSS-фидов, которые обновляют сразу много статей, проблема коллизий timestamp становится заметнее и может привести к тому, что пользователи пропустят заметный объём контента.

#### Отличное решение: составной курсор с ID статьи

##### Подход

Более продуманное решение объединяет timestamp и ID статьи, создавая уникальный курсор с полным порядком. Мы формируем составной курсор вроде "2024-01-15T10:30:00Z\_article123", в котором есть и timestamp, и уникальный ID статьи. Так порядок остаётся полным, даже если у статей одинаковые timestamp: ID статьи служит необходимым tie-breaker.

Запрос к базе превращается в WHERE (published\_at, article\_id) &lt; (cursor\_timestamp, cursor\_id) ORDER BY published\_at DESC, article\_id DESC LIMIT 20. Здесь используется сравнение кортежей в SQL, которое эффективно обрабатывает составной порядок. Мы создаём составной индекс по (published\_at, article\_id), чтобы такие запросы оставались быстрыми даже при миллионах статей.

Это даёт консистентную пагинацию независимо от добавления нового контента и аккуратно обрабатывает коллизии timestamp. Курсор остаётся стабильным и предсказуемым, поэтому пользователи не видят дубликатов и не теряют контент из-за проблем пагинации. Крупные платформы вроде Twitter и Instagram используют похожие составные курсоры для пагинации своих лент.

##### Сложности

Главный компромисс — немного более сложная генерация и разбор курсора. Приложению нужно работать с составными курсорами, в которых есть и timestamp, и ID, а значит, аккуратно реализовывать кодирование и декодирование. Запросы к базе тоже чуть сложнее, хотя современные базы данных эффективно справляются со сравнением кортежей.

Расходы на хранение немного растут, потому что курсоры длиннее, но на фоне получаемых преимуществ это пренебрежимо мало. Составной индекс по (published\_at, article\_id) занимает дополнительное место, но это оправданная инвестиция ради скорости запросов и консистентной пагинации.

#### Отличное решение: монотонно возрастающие ID статей

##### Подход

Ещё более простое решение, дающее тот же результат, — с самого начала проектировать ID статей монотонно возрастающими. Вместо случайных UUID можно использовать UUID, упорядоченные по времени (например, ULID), или auto-increment ID в базе, которые естественным образом растут с каждой новой статьёй. Раз мы собираем статьи хронологически, у новых статей ID всегда будут больше, чем у старых.

Теперь пагинация становится невероятно простой: в качестве курсора мы используем ID статьи. Запрос выглядит так: WHERE article\_id &lt; cursor\_id ORDER BY article\_id DESC LIMIT 20. Никаких составных курсоров, никакой работы с timestamp и никаких сложных сравнений кортежей. Курсор — это просто одно значение ID, которое клиент передаёт обратно для получения следующей страницы.

Это полностью убирает проблему коллизий timestamp, потому что каждая статья получает уникальный упорядоченный идентификатор независимо от времени публикации. Базе нужен только простой индекс по колонке article\_id, а запросы получаются максимально быстрыми и простыми. Многие современные системы используют ULID (Universally Unique Lexicographically Sortable Identifiers), которые сочетают преимущества UUID с хронологическим порядком.

##### Сложности

Главное ограничение: стратегию ID нужно продумать заранее, на этапе проектирования системы. Если ты уже используешь случайные UUID или timestamp в качестве первичных ключей, миграция на монотонные ID потребует аккуратной миграции данных. Также нужно убедиться, что система генерации ID выдерживает высокий throughput и не становится узким местом.

В распределённых системах нужно координировать генерацию ID между несколькими инстансами, чтобы сохранить порядок, хотя с этим хорошо справляются генерация ULID или централизованные сервисы ID. Несмотря на эти нюансы, для хронологических данных вроде новостных лент это зачастую самое простое и производительное решение.

Реализовав cursor-based пагинацию с монотонно возрастающими ID статей, мы получаем консистентную пагинацию, которая аккуратно обрабатывает новый контент и при этом укладывается в требование latency менее 200 мс для запросов ленты.

### 2) Как добиться низкого latency (&lt; 200 мс) для запросов ленты?

Сейчас в нашем high-level design каждый запрос ленты идёт напрямую в базу данных, и при больших нагрузках это создаёт серьёзные узкие места. При 100 миллионах DAU, каждый из которых может обновлять ленту 5–10 раз в день, мы получаем от 500 миллионов до 1 миллиарда запросов ленты в сутки. Даже с эффективной индексацией выборка из миллионов статей и фильтрация по региону на каждый запрос могут увести время ответа далеко за пределы нашей цели в 200 мс.

###### Паттерн: Scaling Reads

Агрегаторы новостей вроде Google News — яркий пример сценариев **scaling reads**: миллиарды запросов ленты при относительно небольшом числе записей статей. Это требует агрессивного кеширования региональных лент и заранее вычисленных рейтингов статей. Главное здесь в том, что потребление новостей многократно превышает их создание, поэтому оптимизация чтения критична для ответа быстрее 200 мс.

[Изучить этот паттерн](/lessons/patterns/scaling-reads)

Как сделать это эффективнее?

#### Хорошее решение: Redis cache с TTL

##### Подход

Когда речь заходит о запросах с низким latency, первое, что должно приходить на ум, — это кеширование.

Мы можем кэшировать свежие статьи по регионам в Redis (или любом другом in-memory cache) с time-to-live (TTL). Для каждого региона заводим отдельный ключ: feed:US, feed:UK и так далее. Последние статьи хранятся в sorted set, упорядоченном по timestamp. Когда пользователь запрашивает ленту, мы сначала проверяем Redis и обращаемся к базе данных только при cache miss. Важно, что TTL действует на всю ленту целиком, а не на отдельные статьи (в sorted set в Redis так нельзя).

![Иллюстрация](/content/google-news/fc15f6129a.svg)

Redis cache

Мы ставим на эти записи TTL в 30 минут. Так cache остаётся достаточно свежим, а нагрузка на базу данных заметно снижается. Hit rate у cache должен быть очень высоким, потому что большинство пользователей запрашивают недавние статьи, а время ответа Redis обычно укладывается в 200 мс. Такая схема выдерживает гораздо больше запросов и при этом даёт приемлемую производительность для большинства пользователей.

Это классический паттерн cache-aside: при cache miss мы запрашиваем региональную ленту из базы данных, кладём результат в Redis с TTL и возвращаем данные пользователю. Последующие запросы для того же региона попадают в cache, пока он не истечёт.

Поскольку мы используем sorted set в Redis, пагинация по-прежнему работает эффективно. Следующие N статей после заданного score можно получить командой ZREVRANGEBYSCORE со значением курсора.

##### Сложности

Хотя нагрузка на базу данных заметно снижается, cache miss по-прежнему требует дорогих запросов к базе, которые могут нарушить наши требования по latency. Из-за TTL пользователи могут не видеть новые статьи до 30 минут. Для новостной платформы, где важна своевременная доставка контента, это нарушает требование к свежести.

Когда cache истекает, все пользователи, запрашивающие ленту региона, одновременно идут в базу данных. Возникает thundering herd: сотни параллельных дорогих запросов перегружают базу. В результате производительность периодически проседает, иногда на несколько минут, пока cache заполняется заново. Пользовательский опыт получается неровным: одни запросы быстрые (cache hit), другие очень медленные (cache miss или обновление cache).

#### Отличное решение: кэшированные ленты в реальном времени через CDC

##### Подход

Самое эффективное решение: заранее вычислять и кэшировать ленты для каждого региона, а обновлять их сразу же с помощью Change Data Capture (CDC). Предвычисленные ленты хранятся в Redis как sorted set с ID статей и необходимыми метаданными, сгруппированные по регионам. Когда публикуется новая статья, триггеры CDC сразу обновляют нужные региональные cache, не дожидаясь истечения TTL.

Работает это так: наш Data Collection Service сохраняет новые статьи в базу данных, что порождает события CDC. Эти события читают Feed Generation Workers, которые сразу определяют, какие региональные ленты нужно обновить, исходя из региона и релевантности статьи. Затем они добавляют новую статью в подходящие sorted set в Redis, используя её timestamp как score, так что хронологический порядок поддерживается автоматически.

![Иллюстрация](/content/google-news/05059c7027.svg)

Кэшированные ленты в реальном времени через CDC

Раз TTL больше не работает, нужен другой способ не дать cache расти бесконечно. Вместо него мы храним в каждой региональной ленте только последние N статей (обычно 1 000–2 000). При добавлении новой статьи мы вставляем её через Redis ZADD с timestamp в качестве score, а затем сразу вызываем ZREMRANGEBYRANK с отрицательными индексами, чтобы удалить самые старые статьи сверх лимита. Так каждый региональный cache остаётся компактным, а пользователю всё равно хватает контента, чтобы пролистать несколько страниц.

Для запросов ленты мы просто читаем предвычисленные sorted set операциями ZREVRANGE, которые выполняются меньше чем за 5 мс. Если нужны полные метаданные статьи, их можно хранить прямо в cache или получать через вторичный cache по ID статей. Это стабильно обеспечивает время ответа меньше 200 мс и при этом даёт мгновенную свежесть контента.

##### Сложности

Главный компромисс: пайплайн генерации лент усложняется, а требования к инфраструктуре растут. Нужно поддерживать инфраструктуру CDC, очереди сообщений и worker-процессы, которые обновляют cache. Систему сложнее эксплуатировать и отлаживать, а за всем пайплайном приходится внимательно следить через мониторинг.

Расходы на хранение растут, потому что мы по сути дублируем данные статей в региональных cache. Впрочем, это решается разумными ограничениями на размер для старого контента. Ещё нужно обрабатывать крайние случаи вроде повреждения cache или падения worker'ов, а для этого нужны надёжная обработка ошибок и механизмы перестроения cache. Несмотря на эти сложности, такой подход используют крупные новостные платформы и социальные сети, потому что он даёт лучший баланс между производительностью и свежестью.

### 3) Как сделать так, чтобы статьи появлялись в лентах в течение 30 минут после публикации?

Наш текущий подход, опрос RSS-лент издателей раз в 3–6 часов, создаёт серьёзную проблему: к тому моменту, когда мы находим срочную новость, пользователи уже узнали о ней из соцсетей, push-уведомлений или других источников новостей. В нынешней быстрой новостной среде задержка в несколько часов делает нашу ленту устаревшей и неактуальной. Когда происходит крупное событие, будь то стихийное бедствие, политические изменения или объявление, двигающее рынки, пользователи ожидают увидеть его в своей ленте через минуты, а не через часы.

Чаще всего, особенно когда вопрос задают кандидатам уровня mid-level или junior, интервьюер просит принять ingestion pipeline за «чёрный ящик». Я решил разобрать его здесь, потому что более senior кандидатов нередко просят рассказать, как это реализовать, хотя бы на высоком уровне.

Вот как можно резко сократить время обнаружения.

#### Хорошее решение: более частый опрос RSS

##### Подход

Самое прямолинейное решение: резко увеличить частоту опроса RSS и добавить умное планирование с учётом характеристик издателей. Вместо проверки всех лент раз в 3–6 часов мы вводим многоуровневую систему опроса: издателей с высоким приоритетом (крупные новостные издания, источники срочных новостей) опрашиваем каждые 5–10 минут, источники со средним приоритетом каждые 30 минут, а источники с низким приоритетом (еженедельные журналы, нишевые издания) каждые 2–3 часа.

Наш Data Collection Service хранит в базе данных приоритет издателя, чтобы отслеживать историческую картину публикаций каждого источника. Издатели вроде CNN, BBC или Reuters, которые публикуют десятки статей в день и часто первыми сообщают о крупных событиях, получают класс «high-priority» и попадают в очередь быстрого опроса. Для каждого уровня приоритета система использует отдельные worker-процессы. Worker'ы с высоким приоритетом работают в непрерывных циклах опроса и между циклами «спят» всего 5–10 минут.

![Иллюстрация](/content/google-news/7a8193c0f8.svg)

Более частый опрос RSS

Опрос устроен так:

1. Worker'ы с высоким приоритетом запрашивают из базы данных издателей с пометкой «high-priority» и опрашивают их RSS-ленты каждые 5–10 минут, отправляя HTTP GET-запросы на URL каждой ленты.
2. Когда обнаруживаются новые статьи (по сравнению GUID статей или timestamp публикации с данными в нашей базе), их сразу обрабатывает наш content ingestion pipeline.
3. Worker'ы запоминают заголовки last-modified и ETag из RSS-ответов, чтобы не обрабатывать лишнее, если ленты не менялись.

##### Сложности

Это создаёт серьёзные инфраструктурные сложности и последствия для стоимости. При 10 000+ издателей и опросе источников с высоким приоритетом каждые 5–10 минут мы делаем уже 100 000+ HTTP-запросов в час вместо нынешних 2 000–3 000. Это заметно увеличивает расходы на серверы и рискует перегрузить серверы небольших издателей слишком частыми запросами, из-за чего наши IP-адреса могут заблокировать.

Кроме того, это не решает фундаментального ограничения: мы по-прежнему реагируем, а не действуем на опережение. Даже при опросе раз в 5 минут срочная новость может появиться в нашей системе с задержкой до 5 минут, плюс время на обработку. Во время крупных событий, когда на счету каждая минута, такая задержка всё равно делает нашу платформу медленной по сравнению с источниками реального времени вроде соцсетей.

И, пожалуй, самое важное: RSS-ленты есть не у всех издателей! У многих новых издателей RSS либо ограничен, либо отсутствует вовсе.

#### Хорошее решение: интеллектуальный web scraping

##### Подход

Чтобы получать контент от издателей, у которых нет RSS-лент или которые обновляют их редко, нужен web scraping: программа заходит на новостные сайты и извлекает новые статьи прямо из их HTML-структуры. Наша система scraping хранит в базе данных шаблоны сайтов и CSS-селекторы, по которым определяется контент статей на крупных новостных сайтах.

Реальная инфраструктура скрапинга очень похожа на наш [разбор web crawler](/lessons/breakdowns/web-crawler). Crawler заходит на главные страницы и страницы категорий издателей в поиске ссылок на новые статьи: ищет элементы с классами вроде "article-headline", "story-link" или "news-item" и вытаскивает из них URL, заголовки и время публикации. На схеме мы многое из этого абстрагируем, потому что это не главный фокус задачи.

Для каждого целевого сайта скраперы ведут базу fingerprint'ов уже виденных статей (по хешам URL или контрольным суммам контента), чтобы отличать новый контент от старого. Когда находится новая статья, скрапер переходит по её URL и извлекает полный контент: заголовок, текст, автора и дату публикации. Извлечённый контент нормализуется в наш стандартный формат статьи и попадает в тот же pipeline обработки, что и контент из RSS.

![Иллюстрация](/content/google-news/900bad025f.svg)

Интеллектуальный веб-скрапинг

Как и в случае с RSS, нам нужно умное расписание: популярные новостные сайты скрапятся каждые 10-15 минут, а небольшие можно проверять раз в час.

Так мы совмещаем лучшее из двух миров: получаем свежесть RSS и охват веб-скрапинга.

##### Сложности

Веб-скрапинг требует больших затрат на поддержку: сайты часто меняют HTML-структуру, и наша логика извлечения ломается. Он также медленнее и менее надёжен, чем разбор RSS, плюс есть юридические риски при извлечении контента с сайтов, которые скрапинг запрещают.

Тем не менее мы используем скрапинг стратегически, как fallback для издателей без RSS, а не как основной метод. Такой гибридный подход (RSS, когда он есть, и скрапинг, когда без него никак) даёт полное покрытие и при этом держит операционную сложность под контролем.

#### Отличное решение: webhooks от издателей и резервный polling

##### Подход

Оптимальное решение переворачивает модель из pull в push: мы реализуем webhooks, с помощью которых издатели сами сообщают нам о новой публикации сразу после выхода. Если предположить, что у нас действительно 100M DAU, то издатели должны быть кровно заинтересованы в том, чтобы их статьи попадали на нашу платформу.

Мы можем сделать webhook-эндпоинт POST /webhooks/article-published, который издатель вызывает в момент публикации статьи, передавая метаданные статьи или даже полный payload с контентом. Так нам не нужно самим искать новые статьи: нам о них просто рассказывают!

Наша webhook-инфраструктура состоит из высокодоступного эндпоинта, способного выдерживать внезапные пики трафика, когда появляется крупная новость и сразу несколько издателей уведомляют нас одновременно. Эндпоинт валидирует входящие webhook-payload'ы, извлекает данные статьи и сразу ставит контент в очередь на обработку через наш стандартный ingestion pipeline. Чтобы защититься от спама и подтвердить подлинность контента, понадобится аутентификация webhook'ов через shared secrets или API keys.

Контент издателей, которые подключили наши webhooks, мы можем обработать в течение нескольких секунд после публикации. Payload содержит основные метаданные: URL статьи, заголовок, время публикации и, опционально, полный текст. Система сразу запускает обновление cache для соответствующих региональных лент, так что новый контент появляется в лентах пользователей в течение 30 секунд после публикации.

Резервный RSS-polling и веб-скрапинг мы оставляем для издателей, которые webhooks не поддерживают. Получается гибридная система: real-time обновления там, где это возможно, и регулярный polling во всех остальных случаях.

![Иллюстрация](/content/google-news/1896ea4495.svg)

Webhooks от издателей с резервным polling

##### Сложности

Главное ограничение в том, что webhooks требуют координации и согласия издателей, и мы не можем внедрить их в одностороннем порядке, как polling или скрапинг. Многим небольшим издателям не хватает технических ресурсов на интеграцию webhooks, а некоторые могут не хотеть добавлять внешние зависимости в свой процесс публикации.

Этот вопрос отлично подходит для предметного диалога с интервьюером. Начни с вопросов и наращивай решение постепенно. Можно ли считать ingestion pipeline чёрным ящиком? Если нет, ведут ли наши издатели RSS-ленты? Раз у нас такой большой трафик, можно ли предположить, что издатели захотят внедрить webhooks, чтобы сообщать нам о новых статьях?

Комбинируя частый RSS-polling для сотрудничающих издателей, интеллектуальный веб-скрапинг для сайтов без лент и webhooks для премиальных real-time партнёрств, мы добиваемся того, что срочные новости появляются в лентах пользователей за минуты, а не за часы.

### 4) Как эффективно работать с медиаконтентом (изображения и видео)?

Поскольку мы отправляем пользователей на сайты издателей, а не хостим полные статьи, требования к медиа гораздо проще: в ленте нужны только thumbnail'ы, чтобы статьи выглядели привлекательно и пользователи быстро узнавали нужный контент. Но когда ленты смотрят 100M+ пользователей в день, даже доставка thumbnail'ов должна быть быстрой и недорогой.

Когда мы собираем статьи через RSS или скрапинг, мы извлекаем URL основного изображения каждой статьи и скачиваем копию, чтобы сгенерировать более качественные thumbnail'ы. Нам нужны собственные копии, потому что изображения на сайтах издателей могут медленно загружаться, менять URL или пропадать, а это сломает ленту.

Разберём варианты хранения и доставки thumbnail'ов.

#### Плохое решение: хранение blob'ов в базе данных

##### Подход

Хранить thumbnail'ы прямо в базе данных как бинарные данные рядом с метаданными статьи. При сборе статьи мы скачиваем основное изображение, уменьшаем его до размера thumbnail'а (например, 300x200) и сохраняем бинарные данные в базе.

Это настолько плохо, что мы даже не рассматриваем такой вариант в нашем high-level design. Но здесь его стоит упомянуть, чтобы показать, почему это плохая идея.

##### Сложности

Даже небольшие thumbnail'ы (20-50KB каждый), умноженные на миллионы статей, создают серьёзные проблемы с производительностью базы данных. Запросы становятся медленными, бэкапы огромными, а память сервера БД занята данными изображений вместо того, чтобы работать на быстрые запросы. Это не масштабируется дальше нескольких тысяч статей.

Базы данных предназначены для структурированных данных, а не для бинарных. Если у тебя большие бинарные blob'ы, всегда храни их в object storage!

#### Хорошее решение: хранение в S3 с прямыми ссылками

##### Подход

Хранить thumbnail'ы в Amazon S3, а в базе данных держать только их URL. При сборе статьи мы скачиваем оригинальное изображение, генерируем thumbnail (300x200, размер подобран для веба), загружаем его в S3 и сохраняем S3 URL в метаданных статьи.

Так обязанности правильно разделены: S3 отвечает за хранение файлов, а база данных занимается структурированными данными. Thumbnail'ы загружаются из S3 прямо в браузеры пользователей, что снижает нагрузку на наши application-серверы.

Именно это у нас сейчас и есть в high-level design.

##### Сложности

Пользователи из разных стран сталкиваются с высоким latency при загрузке thumbnail'ов из удалённых регионов S3. Расходы на S3 egress растут при миллионах просмотров thumbnail'ов в день. Нет поддержки разных плотностей экрана (retina и обычные дисплеи) и медленных сетевых соединений.

#### Отличное решение: S3 + CloudFront CDN с несколькими размерами

##### Подход

Чтобы пользователи по всему миру не страдали от высокого latency при загрузке thumbnail'ов из удалённых регионов S3, можно отдавать thumbnail'ы через CDN.

Храним thumbnail'ы в S3 и раздаём их через CloudFront CDN для глобального распространения. Мы генерируем несколько размеров thumbnail'ов (150x100 для мобильных, 300x200 для десктопа, 600x400 для retina-дисплеев) и используем HTML-атрибуты srcset или клиентскую логику, чтобы запрашивать подходящую версию в зависимости от устройства и плотности экрана.

![Иллюстрация](/content/google-news/0a278f43e7.svg)

S3 + CloudFront CDN с несколькими размерами

CloudFront кэширует thumbnail'ы на edge-локациях по всему миру, обеспечивая время загрузки менее 200 мс в любой точке.

##### Сложности

Минус в том, что хранение нескольких вариантов thumbnail'ов обходится дороже, но эти затраты невелики по сравнению с выигрышем в производительности. CDN-кэширование сокращает число запросов к S3 более чем на 90%, заметно снижая общие расходы и обеспечивая оптимальный пользовательский опыт.

Используя хранение в S3 с раздачей через CloudFront CDN и несколько размеров thumbnail'ов, мы обеспечиваем быструю загрузку thumbnail'ов по всему миру и держим расходы на хранение минимальными. Раз пользователи переходят на сайты издателей за полным текстом статей, нам нужно улучшать только просмотр ленты: быстро загружающимися thumbnail'ами подходящего размера.

### 5) Как справляться с пиками трафика во время срочных новостей?

Breaking news события создают огромные всплески трафика, с которыми не справляется традиционное масштабирование. Когда происходят крупные события — выборы, стихийные бедствия или новости о знаменитостях, — наша обычная нагрузка в 100M daily active users может за считаные минуты вырасти до 10M одновременных пользователей. В такие моменты все хотят получить свежие обновления одновременно, и возникает идеальный шторм из read-трафика, способный положить неподготовленную систему.

Realistically, 10M одновременных пользователей — это очень много и, скорее всего, завышенная оценка, но так задача интереснее, и многие интервьюеры именно так и давят, требуя спроектировать систему под такие полуреалистичные сценарии.

К счастью, у Google News есть естественное преимущество, которое делает масштабирование куда проще, чем в других системах: потребление новостей по своей природе региональное. Пользователям в первую очередь нужен быстрый доступ к местным и национальным новостям своего региона. Да, некоторые читают и международные новости, но подавляющая часть трафика приходится на региональный контент: американцам нужны новости США, европейцам — новости ЕС, и так далее.

Это значит, что мы можем разместить инфраструктуру рядом с пользователями в каждом регионе, и каждому региональному деплойменту нужно обрабатывать только контент и трафик своей территории. Вместо одной огромной глобальной системы мы строим несколько небольших региональных, которые гораздо проще масштабировать и эксплуатировать.

Будем считать, что каждый региональный деплоймент должен выдерживать 10M одновременных пользователей, запрашивающих feed. Поэтому пройдёмся по каждому компоненту нашей схемы и зададим три вопроса: каковы требования к ресурсам на пике, удовлетворяет ли им текущий дизайн, и если нет, как масштабировать компонент под новое требование?

**Feed Service (Application Layer)**

Нашему Feed Service нужно обработать 10M одновременных пользователей, запрашивающих feed. Даже если каждый пользователь обновит feed всего один раз за время breaking news события, это всё равно 10M запросов, которые нужно быстро обработать. Один application server обычно выдерживает от 10 000 до 100 000 одновременных соединений в зависимости от сложности ответа и железа.

Так что одним сервером, каким бы мощным он ни был, тут не обойтись.

Решение — горизонтальное масштабирование с auto-scaling groups. Мы разворачиваем несколько инстансов Feed Service за load balancer'ами и используем cloud auto-scaling, который автоматически поднимает новые инстансы, когда загрузка CPU или памяти превышает определённые пороги. При грамотной балансировке 10M запросов распределяются между десятками инстансов application server, и каждый обрабатывает посильную долю трафика.

Главное преимущество в том, что Feed Service — stateless, поэтому горизонтальное масштабирование делается просто. Новые инстансы поднимаются за секунды и гасятся, когда трафик спадает, так что за ресурсы мы платим только в периоды высокой нагрузки.

**Database Layer**

Больше всего проблем при всплесках трафика возникает у базы данных. Даже при эффективных индексах один инстанс базы не справится с 10M одновременных read-запросов. Дисковая подсистема, пропускная способность сети и CPU становятся узкими местами, которые не обойти одним лишь апгрейдом железа.

Хорошая новость: у нас уже есть cache, который должен сильно снизить нагрузку на базу. Все read-запросы на получение feed должны попадать в cache, а значит, проблема масштабирования переезжает с базы на cache.

**Cache Layer (Redis)**

Наш Redis cache становится критичным при всплесках трафика, потому что он основной источник предвычисленных региональных feed. Когда 10M пользователей запрашивают feed одновременно, даже наши оптимизированные запросы к cache могут перегрузить один инстанс Redis, который выдерживает всего ~100k запросов в секунду.

Решение — read replicas. Каждому региональному Redis master добавляем несколько read replicas, чтобы распределить нагрузку на чтение. Поскольку на регион у нас всего ~2 000 свежих статей, каждый master легко хранит весь региональный контент без сложного [шардирования](/lessons/core-concepts/sharding): задача масштабирования сводится исключительно к read throughput.

А если вы не используете Redis? Не проблема! Принцип тот же. Используйте consistent hashing, чтобы [шардировать](/lessons/core-concepts/sharding) данные между несколькими инстансами, и убедитесь, что у каждого есть одна-две replica для нагрузки на чтение и failover.

Посчитаем. При 10M одновременных пользователей во время всплеска и примерно 100k запросов в секунду на один инстанс Redis нам нужно 100 инстансов Redis в сумме.

Realistically, столько на регион не нужно. Одни регионы популярнее других, и мы можем масштабироваться вверх и вниз в зависимости от спроса.

Настроить это несложно: операции записи, такие как новые статьи и обновления cache, идут на master, а read-операции для запросов feed балансируются между всеми replicas по алгоритмам round-robin или least-connections. Если Redis Sentinel управляет кластером и master падает, одна из replicas автоматически повышается до master. Replication lag у Redis обычно меньше 200ms, что вполне приемлемо для новостных feed: пользователи таких мелких задержек не заметят.

![Иллюстрация](/content/google-news/d4a1877a11.svg)

Redis Scaling

Так мы эффективно справляемся со всплесками трафика, сохраняя операционную сложность под контролем. Во время breaking news событий мы можем быстро поднять дополнительные read replicas в затронутых регионах, чтобы выдержать возросшую нагрузку, а когда трафик нормализуется, снова их убрать.

Региональный подход даёт пользователям время ответа cache менее 50ms от ближайшего кластера, всплески трафика в одном регионе не влияют на другие, а каждый регион можно масштабировать независимо, исходя из локальных паттернов использования. Во время breaking news событий затронутые регионы могут добавлять read replicas, пока остальные работают на базовой мощности.

### 6) Как поддержать ленты новостей по категориям (Sports, Politics, Tech и т. д.)?

Наш текущий дизайн поддерживает только региональные ленты вроде feed:US и feed:UK, но настоящие новостные платформы организуют контент по категориям: Sports, Politics, Technology, Business, Entertainment. Пользователи ждут, что смогут смотреть конкретные темы, а не просто смешанную региональную ленту.

Google News показывает 25+ категорий, в каждой из которых сотни статей в день. При 100M пользователей в день в пиковые часы может приходить до 10M запросов к отдельным категориям: Sports в сезон игр, Politics во время выборов, Tech во время крупных запусков продуктов. Наша текущая структура региональных cache не способна эффективно справиться с такой детальной фильтрацией.

Представь, что происходит крупное спортивное событие и 10M пользователей одновременно запрашивают ленту Sports. Системе пришлось бы запрашивать из базы данных статьи о спорте, фильтровать результаты и формировать ответ для каждого запроса. Даже с региональным кешированием мы бы миллионы раз обращались к базе за одним и тем же контентом Sports, и это стало бы узким местом по производительности.

#### Плохое решение: фильтрация запросами к базе с колонкой category

##### Подход

Самое простое решение: добавить в таблицу Article колонку category и изменить Feed Service так, чтобы он фильтровал по категории в реальном времени. Когда пользователь запрашивает /feed?region=US&category=sports, сервис выполняет запрос к базе с WHERE region = 'US' AND category = 'sports' ORDER BY published\_at DESC LIMIT 20.

Для этого нужны минимальные изменения в существующей архитектуре. Мы добавляем извлечение категории при ingestion статей: из метаданных RSS-ленты, из анализа структуры веб-страницы или простым сопоставлением ключевых слов с заголовками и текстом статей. Издатели часто указывают категорию в своих RSS-лентах тегами вроде &lt;category>Sports&lt;/category>, поэтому для многих источников извлечение получается простым.

В Feed Service добавляется логика фильтрации по категориям. API-эндпоинт становится гибче и поддерживает запросы вроде /feed?region=US&category=sports или /feed?region=UK&category=technology. Запрос к базе использует составной индекс по (region, category, published\_at), чтобы фильтрация и сортировка работали эффективно.

##### Сложности

На большом масштабе возникают серьёзные проблемы с производительностью. Каждый запрос категории требует обращения к базе, то есть 50M пиковых запросов превращаются в 50M операций над базой. Даже при правильных индексах база становится узким местом: параллельные запросы конкурируют за ресурсы, а пулы соединений исчерпываются.

С кешированием тоже всё непросто. Результаты по категориям не получается кешировать эффективно, потому что каждая комбинация категории и региона требует отдельного управления cache. При 25 категориях и 10 регионах получается 250 разных ключей cache, у каждого свои паттерны инвалидации и свой объём трафика. Cache miss обходится дорого, так как запускает запрос к базе с фильтрацией по конкретной категории.

#### Хорошее решение: предвычисленные ленты категорий в Redis

##### Подход

Более масштабируемый подход: заранее вычислять и кешировать ленты для каждой комбинации категории и региона в Redis sorted sets. Вместо фильтрации в базе в реальном времени мы поддерживаем отдельные sorted sets вроде feed:sports:US, feed:politics:UK и feed:technology:CA, в которых лежат уже отфильтрованные статьи в хронологическом порядке.

Архитектура опирается на существующее кеширование региональных лент, но с более мелкой гранулярностью. Во время ingestion статей наши Feed Generation Workers определяют категорию каждой статьи и одновременно обновляют несколько Redis sorted sets. Когда в US публикуется статья о спорте, она добавляется и в feed:US (региональная лента), и в feed:sports:US (лента категории): ID статьи выступает как member, а timestamp как score.

Запросы к ленте становятся молниеносными, потому что это простые операции над Redis sorted set. Запрос /feed?region=US&category=sports&limit=20 превращается в ZREVRANGE feed:sports:US 0 19, который выполняется быстрее 5ms. Пользователи стабильно получают ответ быстрее 200ms, даже во время пиков трафика, когда миллионы людей смотрят конкретные категории.

##### Сложности

Главное ограничение: расход памяти и сложность управления cache. При 25 категориях и 10 регионах мы поддерживаем 250+ отдельных sorted sets вместо 10. В каждой ленте категории примерно 1 000–2 000 статей, так что требования к памяти Redis заметно растут по сравнению с простыми региональными лентами.

Инвалидация cache усложняется: когда статьи устаревают, их нужно удалять из нескольких sorted sets. Одна статья может входить и в региональную ленту, и в ленты категорий, поэтому очистка должна быть согласованной сразу по нескольким ключам cache. При большом потоке публикаций операции обслуживания cache могут сказываться на производительности чтения.

#### Отличное решение: фильтрация в памяти

##### Подход

На мой взгляд, предыдущее решение избыточно. Можно просто изменить наши региональные ленты так, чтобы каждая закешированная статья содержала информацию о категории, а при запросе конкретной категории фильтровать результаты в памяти.

Когда мы кладём статьи в feed:US, то вместо одних только ID статей в качестве members храним полные метаданные статей в виде JSON-строк. Каждая закешированная статья содержит всё необходимое для фильтрации по категории: заголовок, описание, URL, категорию, регион и timestamp публикации.

Типичная запись в cache выглядит так:

```
{
  "id": "123",
  "title": "NBA Finals Game 7 Results",
  "description": "Warriors defeat Celtics in thrilling finale",
  "url": "https://espn.com/nba/finals/game7",
  "category": "sports",
  "region": "US",
  "published_at": "2024-06-21T22:30:00Z"
}
```

Когда пользователи запрашивают ленты конкретных категорий вроде /feed?region=US&category=sports, наш Feed Service достаёт весь региональный cache командой ZREVRANGE feed:US 0 999, получая 1 000 самых свежих статей. Затем сервис фильтрует эти данные в памяти, оставляя только статьи с category === "sports", и возвращает пользователю страницу нужного размера.

Логика фильтрации простая и быстрая. Чтение 1 000 закешированных статей из Redis занимает меньше 10ms, а фильтрация в памяти приложения добавляет всего 1–2ms обработки. Для категорий с приличным представительством в региональном cache легко найти 20–50 подходящих статей, не обращаясь к базе.

Это требует минимальных изменений в существующей архитектуре. Наш CDC pipeline уже заполняет региональные cache, поэтому нужно лишь изменить формат закешированных данных, добавив метаданные категории. Feed Service дополняется простой логикой фильтрации, которая обрабатывает закешированные результаты перед пагинацией.

Расход памяти остаётся разумным, поскольку статьи не дублируются между несколькими cache. Каждая статья хранится один раз в своём региональном cache, сколько бы категорий пользователи ни запрашивали. Управление cache остаётся простым: те же ограничения по размеру и те же политики TTL.

Это пример того, что лучшее решение часто оказывается самым прямолинейным.

### 7) Как генерировать персонализированные ленты на основе поведения и предпочтений пользователя при чтении?

Наша текущая система отдаёт всем пользователям в одном географическом регионе одну и ту же региональную ленту, но современные новостные платформы предлагают персонализированный опыт. Пользователи ждут ленты, в которых приоритет отдан интересным им темам, издателям, которым они доверяют, и контенту, похожему на статьи, с которыми они уже взаимодействовали.

Сама функция ранжирования и скоринга обычно представляет собой ML-модель, но для наших целей мы можем её абстрагировать. Это всё-таки не собеседование на MLE!

#### Плохое решение: скоринг рекомендаций в реальном времени

##### Подход

Самый простой подход: оценивать статьи относительно предпочтений пользователя в реальном времени, прямо во время запроса ленты. Система хранит профили пользователей с историей чтения, предпочтениями по темам и поведенческими данными, а при запросе ленты запускает алгоритмы рекомендаций, чтобы ранжировать контент по релевантности.

Реализация включает отслеживание поведения пользователя (клики, время чтения, шеры) и явных предпочтений (подписки на темы, любимые издатели). Когда пользователь запрашивает ленту, сервис рекомендаций оценивает свежие статьи относительно его профиля по таким факторам, как совпадение по теме, предпочтения по издателю и свежесть контента. Collaborative filtering находит паттерны вроде «пользователи, которые читали A и B, также интересуются C», чтобы показывать похожий контент.

##### Сложности

Скоринг в реальном времени разрушает наши требования по latency. Оценка тысяч статей относительно 100M профилей пользователей означает миллиарды вычислений в час, и на ответ уходят несколько секунд вместо целевых 200ms. Вычислительные затраты становятся непомерными, а производительность катастрофически падает во время пиков трафика, когда миллионам пользователей одновременно нужна персонализация.

#### Хорошее решение: предвычисленные кеши лент пользователей

##### Подход

Pre-compute personalized feeds для active-пользователей в Redis sorted sets вида `feed:user:12345`. Background workers непрерывно обновляют эти feeds по мере появления новых статей, оценивая контент по релевантности интересам и паттернам чтения каждого пользователя, а не по хронологии.

Система объединяет явные предпочтения (подписки на темы, любимые издатели) с поведенческими сигналами (клики, время чтения, shares), чтобы строить профили пользователей. Когда публикуются статьи, recommendation workers определяют подходящих пользователей и добавляют статьи в их персонализированные feeds с соответствующими relevance scores.

Для ежедневно активных пользователей заводятся отдельные персонализированные cache, а для неактивных feeds генерируются on-demand из category cache. Cache обновляется инкрементально: предпочтения пользователя меняются постепенно, по мере того как он взаимодействует с разными темами.

##### Сложности

Требования к памяти взрываются из-за отдельных cache для миллионов пользователей. Хранение 1 000 статей на пользователя для 50M active-пользователей даёт 50 миллиардов записей в cache, что в 200–500 раз больше, чем при category caching. Устаревание cache портит UX, когда интересы быстро меняются, а персонализированные feeds могут пропустить глобально важные breaking news, которые должны увидеть все.

#### Отличное решение: гибридная персонализация с динамической сборкой feed

##### Подход

Оптимальное решение хранит лёгкие векторы предпочтений пользователей (всего несколько килобайт на пользователя) и собирает персонализированные feeds on-demand, смешивая заранее вычисленные category feeds. Вместо 100M пользовательских cache мы поддерживаем несколько сотен category cache и персонализируем через умную сборку.

Пользователю, которого интересуют технологии, feed собирается из 60% `feed:technology:US`, 30% `feed:business:US` и 10% `feed:trending:US`. Алгоритм смешивания использует вектор предпочтений пользователя, чтобы определить оптимальные пропорции. Во время breaking news система временно повышает веса trending-контента, сохраняя личные предпочтения.

Это опирается на уже существующую инфраструктуру category cache, снижает требования к памяти в 100 раз и при этом даёт релевантный персонализированный опыт. Machine learning подстраивает пропорции смешивания по паттернам engagement, а fallback-стратегии поддерживают производительность при высоком трафике.

##### Сложности

Глубина персонализации ниже, чем у полноценных recommendation engines. Алгоритмы сборки нужно аккуратно настраивать, чтобы сбалансировать персонализацию и разнообразие контента: слишком узкие интересы могут пропустить важные глобальные истории, а слишком широкие дадут ощущение обезличенной ленты.

Реализуя гибридную персонализацию с динамической сборкой feed, мы даём персонализированные новости, которые масштабируются до 100M+ пользователей и укладываются в требование по времени ответа до 200 мс. Подход балансирует индивидуальные интересы пользователя с редакторской важностью и trending-контентом, так что в feed попадают и релевантные, и глобально значимые новости.

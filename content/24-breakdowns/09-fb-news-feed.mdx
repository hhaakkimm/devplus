## Разбор задачи

**📰 Что такое News Feed в Facebook**
Facebook — социальная сеть, которая первой запустила [News Feed](https://en.wikipedia.org/wiki/Feed_(Facebook)) — продукт, показывающий свежие истории пользователей из твоего социального графа.

Это классическая задача по system design, связанная с fan-out и управлением данными. Давай считать, что мы работаем с однонаправленными связями «follow», а не с двунаправленными «friend», которые были важнее для самых первых версий Facebook.

Начнём с требований.

### [Функциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Пользователи должны иметь возможность создавать посты.
2. Пользователи должны иметь возможность добавлять в друзья / подписываться на других людей.
3. Пользователи должны иметь возможность просматривать ленту постов от людей, на которых они подписаны, *в обратном хронологическом порядке* (сначала новые).
4. Пользователи должны иметь возможность листать свою ленту.

**Вне рамок (below the line):**

* Пользователи должны иметь возможность ставить лайки и комментировать посты.
* Посты могут быть приватными или иметь ограниченную видимость.

В рамках этой задачи (как и большинства задач по system design, если на то пошло) мы можем считать, что пользователи уже аутентифицированы, а их user ID хранится в сессии или JWT.


### [Нефункциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Система должна быть высокодоступной (availability важнее consistency). Мы допускаем устаревание поста до 1 минуты (eventual consistency).
2. Публикация постов и просмотр ленты должны быть быстрыми: ответ за &lt; 500 мс.
3. Система должна выдерживать огромное число пользователей (2 млрд).
4. Пользователи должны иметь возможность подписываться на неограниченное число пользователей, а на каждого пользователя должно быть возможно подписаться неограниченному числу пользователей.

Конкретные числа в нефункциональных требованиях помогают принимать решения при проектировании. Система с задержкой в единицы миллисекунд требует совершенно другой архитектуры, чем «быстрая» система, которой можно отвечать секунду.

## Подготовка

### План решения

Самое сложное в этом дизайне — пользователи, которые подписаны на огромное количество людей, или люди с огромным числом подписчиков (проблема, известная как «fan-out»). Нам нужно быстро закрыть базовые требования, чтобы потом углубиться именно в это. Для этой задачи (как и для многих!) последовательное прохождение по функциональным требованиям даёт интервью естественную структуру, так и поступим.

### [Определение основных сущностей](/lessons/sd-prep/delivery)

Начав с основных сущностей, мы получаем набор терминов, которыми будем пользоваться до конца интервью. Это также помогает понять модель данных, которая понадобится для реализации функциональных требований.

Для News Feed основные сущности очевидны. Связь между пользователями мы выделим в отдельную сущность:

1. **User**: пользователь нашей системы.
2. **Follow**: однонаправленная связь между пользователями нашей системы.
3. **Post**: пост, созданный пользователем нашей системы. Посты может создавать любой пользователь, и они показываются в лентах тех, кто подписан на автора.

На реальном интервью это может быть простой короткий список вроде этого. Главное — проговори сущности с интервьюером, чтобы убедиться, что вы понимаете друг друга одинаково.

Основные сущности

### [API](/lessons/sd-prep/delivery)

API — это основной интерфейс, с которым будут работать пользователи. Важно определить его на раннем этапе, потому что он направляет high-level design. Мы можем построить API, определив эндпоинты, необходимые для каждого из функциональных требований.

Для первого требования нам нужно создавать посты:

```
POST /posts 
{
    "content": { }
}
// -> 200 OK
{
    "postId": // ...
}
```

Содержимое мы оставим пустым, чтобы учесть расширенный контент или другие структурированные данные, которые мы можем захотеть включить в пост. Что касается аутентификации, мы скажем интервьюеру, что токены аутентификации передаются в заголовке запроса, и не будем углубляться в детали, пока нас об этом не попросят.

Дальше нам нужно уметь подписываться на людей. Для этого возьмём простой RESTful PUT-эндпоинт. Подписывается аутентифицированный пользователь (из его JWT), а [id] — это пользователь, на которого он хочет подписаться.

```
PUT /users/[id]/follow
{ }
// -> 200 OK
```

Здесь действие follow бинарное. Используя PUT, мы гарантируем идемпотентность, так что запрос не упадёт, если пользователь нажмёт «подписаться» дважды. Отписка (вне рамок) делалась бы через DELETE. Тело нам не нужно, но мы оставим заглушку на всякий случай и пойдём дальше.

Последнее требование — возможность просматривать ленту и листать её.

```
GET /feed?pageSize={size}&cursor={timestamp?}
{
    items: Post[],
    nextCursor: string
}
```

Это может быть простой GET-запрос. Мы добавили параметры, позволяющие пользователю листать ленту. Поскольку по требованиям посты возвращаются в обратном хронологическом порядке, при пролистывании ленты пользователь будет смотреть более старые посты. Мы будем использовать timestamp как «cursor», обозначающий самый старый из уже увиденных постов, так что каждая страница вернёт N постов старше этого timestamp.

Пока мы не будем погружаться в структуру Post, чтобы оставить время на более интересные части интервью.

Особенно для более senior-кандидатов важно сосредоточить усилия на «интересных» аспектах интервью. Если тратить слишком много времени на очевидные элементы, то и времени на более интересные части остаётся меньше, и интервьюер получает сигнал, что ты, возможно, не отличаешь сложные части от тривиальных, а для senior-инженеров это критически важный навык. «Вернусь к этому, если останется время» — отличная стратегия!

Итак, у нас есть API, давай займёмся high-level design, который за ними стоит.

## [High-Level Design](/lessons/sd-prep/delivery)

### 1. Пользователи должны уметь создавать посты.

Для первого требования нужно создавать посты и получать к ним доступ по ID. Начнём с самого простого и будем усложнять по ходу дела.

Для начала, раз мы знаем, что система будет масштабироваться, поставим [горизонтально масштабируемый сервис за API gateway/load balancer](/lessons/core-concepts/api-design). Кеширование пока пропустим, до него мы ещё дойдём. Благодаря API gateway и load balancer мы можем справляться с ростом трафика, просто добавляя хосты. Каждый хост *stateless*, потому что он только пишет в базу данных (чтения мы пока не трогаем), так что масштабировать его очень легко: достаточно добавить ещё хостов!

Пользователи отправляют в наш API gateway запрос на создание поста, он передаётся на один из эндпоинтов post service, тот создаёт событие вставки (insert event) и отправляет его в нашу базу данных. Всё просто.

![Иллюстрация](/content/fb-news-feed/dd78ebd784.svg)

Simple Post Creation

В качестве базы данных подойдёт любое key-value хранилище. Для этого приложения возьмём DynamoDB за её простоту и масштабируемость. DynamoDB позволяет выделить очень высокий throughput, если нагрузка равномерно распределена по partition.

Отлично, посты создавать мы умеем. Идём дальше.

### 2. Пользователи должны уметь добавлять в друзья/подписываться на других людей.

С функциональной точки зрения подписка или добавление в друзья — это установление связи между двумя пользователями. Это связь «многие ко многим», и мы можем смоделировать её как граф. Обычно для графа используют специализированную графовую базу данных (например, Neo4j) или [triple store](https://en.wikipedia.org/wiki/Triplestore). Но нам хватит простого key-value хранилища, а граф мы смоделируем сами.

Графовые базы данных полезнее, когда нужно обходить граф или делать над ним сложные выборки. Обычно для этого приходится переходить между разными узлами: например, найти друзей ваших друзей или построить embedding для рекомендательной системы. Требования в этой задаче простые, поэтому мы оставим систему простой и избавим себя от неприятных вопросов вроде «как масштабировать Neo4j?». Полноценная графовая база данных для этой задачи не нужна.

Для этого сделаем простую таблицу Follow, где хранится вся связь целиком: userFollowing — partition key, userFollowed — sort key. Также можно создать Global Secondary Index (GSI) с обратной связью (то есть partition key — userFollowed, sort key — userFollowing), чтобы искать всех подписчиков конкретного пользователя.

Так мы можем выполнить все важные запросы:

* Чтобы проверить, подписан ли пользователь на другого пользователя, делаем запрос и по partition key, и по sort key (например, userFollowing:userFollowed). Это простой lookup!
* Чтобы получить всех пользователей, на которых подписан данный пользователь, делаем запрос по partition key (например, userFollowing). Это range query.
* Чтобы получить всех пользователей, которые подписаны на данного пользователя, делаем запрос к GSI по его partition key (например, userFollowed). Это тоже range query.

Для простоты можно положить эти данные в ещё одну таблицу DynamoDB. На практике AWS рекомендует [single-table design](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-table-design.html) для DynamoDB, но отдельные таблицы здесь делают обсуждение понятнее и вполне подойдут для интервью.

Начало хорошее. Продолжаем.

### 3. Пользователи должны уметь просматривать ленту постов от людей, на которых они подписаны.

Задачу просмотра ленты можно разбить на шаги, и с нашим текущим дизайном для этого понадобится лишь несколько изменений:

1. Сначала получаем всех пользователей, на которых подписан данный пользователь.
2. Затем получаем все посты этих пользователей.
3. Наконец, сортируем *все* эти посты по времени и возвращаем их пользователю.

Начнём с добавления feed service, который будет всё это делать. Он будет с большим перекосом в сторону чтения и с совсем другими паттернами запросов, чем у Post и Follow сервисов, поэтому логично вынести его отдельно.

###### Паттерн: Scaling Reads

Генерация news feed — это квинтэссенция нагрузки на чтение: пользователи постоянно заглядывают в ленту, но публикуют редко. Поэтому **scaling reads** здесь необходим: предвычисление лент для активных пользователей, кеширование свежих постов тех, на кого подписаны, и грамотная пагинация. Главное, что пользователи обычно читают только первые несколько элементов, поэтому агрессивное кеширование свежего контента даёт огромный выигрыш в производительности.

[Изучить этот паттерн](/lessons/patterns/scaling-reads)

Найти все посты конкретного пользователя в существующей таблице Posts непросто: у нас есть индекс в таблице Follow, чтобы быстро находить всех, на кого подписан пользователь, но в таблице Post нет индекса, чтобы быстро находить все посты набора пользователей. Это решается добавлением GSI в таблицу Post с creatorID в качестве partition key и временной меткой создания поста createdAt в качестве sort key. Так мы сможем быстро получать все посты набора пользователей в хронологическом порядке.

![Иллюстрация](/content/fb-news-feed/d8aeea2945.svg)

Naive Feed Service

Кажется, это работает. Для данного пользователя мы сначала запрашиваем из таблицы Follow всех, на кого он подписан. Затем запрашиваем все посты этих N пользователей из таблицы Post через её GSI. После этого сортируем все эти посты по временной метке и возвращаем результат пользователю!

Сейчас у тебя, возможно, уже звенят тревожные звоночки, и это хорошо. Здесь всплывает несколько красных флагов, и интервьюер ожидает, что ты быстро их заметишь, поэтому полезно проговорить их вслух:

1. Пользователь может быть подписан на очень много людей.
2. У каждого из них может быть очень много постов.
3. Общий набор постов может оказаться очень большим из-за (1) или (2).

Всё это нужно будет решить до того, как мы закончим! Но прежде чем погружаться в эти сложности, давай доведём до конца функциональные требования.

На реальном интервью я бы объяснил это интервьюеру именно так: «Я знаю, что это не будет масштабироваться, но я начну с наивного решения, а проблемы масштабирования решу отдельно».

Очень частая ошибка кандидатов, с которыми мы работаем, — увязнуть в деталях конкретной проблемы масштабирования, не имея (почти) полного дизайна. Если сначала охватить все требования вширь, а потом уже уходить вглубь, этой ситуации можно избежать — главное, продолжать двигаться быстро!

### 4. Пользователи должны уметь листать свою ленту.

Мы хотим поддержать «бесконечный скролл». Для этого нужно знать, что пользователь уже видел в своей ленте, и быстро получать следующую порцию постов. К счастью, «что пользователь уже видел в своей ленте» описывается довольно коротко: это временная метка самого старого поста, который он просмотрел. Поскольку пользователи просматривают посты от новых к старым, эта единственная временная метка показывает, где они остановились, и отлично работает как cursor для следующей порции постов.

Раз у нас уже есть GSI в таблице post, который сортирует посты по времени создания, мы можем использовать его напрямую, чтобы возвращать только посты старше cursor. Это выглядит так же, как в предыдущем функциональном требовании, с одним добавлением:

1. Сначала получаем всех пользователей, на которых подписан данный пользователь.
2. Затем получаем все посты этих пользователей, **которые старше входной временной метки**.
3. Наконец, сортируем *все* эти посты по времени и возвращаем их пользователю.

Отлично! У нас есть работающая система, в которой небольшое число пользователей может подписываться на небольшое число пользователей с небольшим числом постов и просматривать свои ленты!

Теперь вернёмся к некоторым проблемам, которые мы отметили ранее, и разберём их в deep dives.

## [Deep dives](/lessons/sd-prep/delivery)

### 1) Как обработать пользователей, которые подписаны на большое количество людей?

Во-первых, если пользователь подписан на большое количество людей, запросы к таблице Follow будут возвращаться долго. Получив список всех, на кого он подписан, нам придётся сделать огромное число запросов к таблице Post, чтобы собрать его ленту. Это называется **fan-out on read**: один запрос на чтение порождает множество других запросов. Когда важна latency, fan-out on read может стать серьёзной проблемой, поэтому это хорошая тема для обсуждения на собеседовании по system design.

Нередко для обработки одного входящего запроса генерируются десятки или сотни запросов, но тысячи запросов нужны реже, особенно для сервиса, который должен отвечать пользователям с низкой latency.

Что можно сделать вместо этого? Первым делом стоит подумать, как посчитать ленту при *записи*, то есть при создании поста, а не в момент чтения. Это называется **fan-out on write**: вместо того чтобы собирать ленту по запросу пользователя, мы заранее считаем её при создании постов. И это действительно хороший ход мысли!

Хотя сам вопрос подталкивает к тому, как обрабатывать большое число подписок, разумно спросить интервьюера: «можем ли мы изменить продукт для таких случаев?» Например, в Facebook максимальное число друзей ограничено 5 000. Установить максимум подписок или сделать для таких пользователей немного другой опыт — очень распространённый подход в production-системах такого рода. Заметит ли пользователь со 100 тысячами подписок, что посты появляются на пару минут позже?

Для пользователей, подписанных на большое количество людей, можно завести таблицу PrecomputedFeed. Вместо запросов к таблицам Follow и Post мы будем читать из этой предвычисленной таблицы. Тогда при создании нового поста нам достаточно просто добавить его в нужные ленты.

Каждая запись в таблице PrecomputedFeed имеет ключ userId, а значение — список ID постов в обратном хронологическом порядке, ограниченный небольшим числом постов (скажем, около 200). Запись должна быть компактной, чтобы минимизировать занимаемое место. Поскольку мы обращаемся к этой таблице только по ID пользователя, нам не нужны secondary indexes.

Часто спрашивают: «А что, если пользователь пролистает назад на 100 страниц своей \{ленты, результатов поиска и т. д.\}?» Вопрос справедливый, но большинство систем такое просто не поддерживают (попробуй пролистать Google на несколько десятков страниц вглубь), потому что реальные пользователи так не делают.

В конечном счёте это фиксированное число 200 можно увеличить или уменьшить в зависимости от того, как это влияет на пользователей, дочитывающих ленту до конца, и от соотношения затрат. Если нужно отдать больше контента тем, кто дошёл до конца ленты, мы всегда можем вернуться к наивному решению с запросами к базовым таблицам Follow и Post.

![Иллюстрация](/content/fb-news-feed/60544be8bb.svg)

Добавляем таблицу Feed

Давай быстро проверим, сколько места потребует это решение, прежде чем двигаться дальше. Допустим, каждый postID занимает 10 байт, тогда для хранения 200 постов на пользователя нужно 2KB. При 2B пользователей получается 4TB на все ленты. Для современной системы это вполне разумно.

Полезное эмпирическое правило: прикинуть, во сколько долларов обходится один пользователь, tenant или объект. 2KB данных стоят доли цента в месяц, а Facebook зарабатывает порядка $100 в год на пользователях из США. Так что это вполне приемлемо.

Хотя это резко улучшило производительность чтения, возникла новая проблема: когда пользователь с большим числом подписчиков создаёт пост, нужно эффективно записать его в миллионы лент. Разберём это дальше.

### 2) Как обработать пользователей с большим числом подписчиков?

Когда у пользователя много подписчиков, при создании поста возникает похожая проблема fan-out: нам нужно *записать* данные в миллионы записей Feed!

Поскольку в нефункциональных требованиях мы допустили некоторую неконсистентность, у нас есть короткое окно времени (&lt; 1 минуты) на эти записи.

#### Плохое решение: отправить все запросы разом

##### Подход

Наивный подход: просто отправить все запросы одновременно из Post Service при создании поста. Это не сработает.

В худшем случае мы пытаемся записать новую запись Post в миллионы лент.

##### Сложности

Такой подход практически нереализуем как из-за ограничений на число соединений с одного хоста Post Service, так и из-за доступной latency. Даже если в лучшем случае он *всё же* работает, нагрузка на Post Service становится крайне неравномерной: один хост Post Service может писать в миллионы лент, а другой почти простаивать. Из-за этого систему трудно масштабировать.

#### Хорошее решение: async workers

##### Подход

Вариант получше — использовать async workers за очередью. Поскольку наша система допускает некоторую задержку между записью поста и моментом, когда он должен появиться в лентах, мы можем ставить запросы на запись в очередь, а парк workers будет их обрабатывать и обновлять ленты.

Подойдёт любая очередь, которая поддерживает at-least-once delivery сообщений и хорошо масштабируется. Amazon Simple Queue Service (SQS) отлично подходит.

Когда создаётся новый пост, мы добавляем в очередь SQS запись с ID поста и ID создателя. Каждый worker находит всех подписчиков этого создателя и добавляет пост в начало их записи в ленте.

![Иллюстрация](/content/fb-news-feed/aa8d59fae2.svg)

Async workers для создания постов

###### Сложности

Throughput workers, обновляющих ленты, должен быть огромным. Для небольших аккаунтов с малым числом подписчиков это не проблема: мы запишем всего в несколько сотен лент. Для мега-аккаунтов с миллионами подписчиков у workers очень много работы. Мы учтём это в отличном решении.

Также нужно помнить, что объём работы для каждой записи в очереди разный. Задача на рассылку поста пользователя с 1M подписчиков — это несоизмеримо больше работы, чем задача для 1k подписчиков. Возможно, такие задачи придётся разбивать.

#### Отличное решение: async workers с гибридными лентами

##### Подход

Отличный вариант развивает идею async workers, описанную выше. Мы создаём async feed workers, которые берут задачи из общей очереди и пишут в наши предвычисленные ленты.

![Иллюстрация](/content/fb-news-feed/9bbd573042.svg)

Async workers для создания постов

Но можно поступить умнее: мы сами выбираем, для каких аккаунтов предвычислять ленты, а для каких нет.

Для Justin Bieber (и других аккаунтов с огромным числом подписчиков) вместо записи в ленты 90+ миллионов подписчиков мы можем добавить в таблицу Follow флаг, который показывает, что эта конкретная подписка *не* предвычисляется. В очереди для async workers мы будем игнорировать запросы для таких пользователей.

При чтении, когда пользователь запрашивает ленту через Feed Service, мы берём его (частично) предвычисленную ленту из таблицы Feed и объединяем её с недавними постами тех аккаунтов, которые не предвычисляются.

Такой гибридный подход позволяет выбирать между fan-out on read и fan-out on write отдельно для каждого аккаунта, а для большинства пользователей мы будем делать понемногу и того, и другого. Это отличный принцип system design! В большинстве ситуаций нам не нужно универсальное решение: можно придумать, как умно решить разные типы проблем, и скомбинировать эти решения.

###### Сложности

Объединение лент во время чтения, а не во время записи, означает, что Feed Service должен выполнять больше вычислений. Порог, начиная с которого аккаунт исключается из предвычисления, можно настраивать.

### 3) Как справиться с неравномерным чтением постов?

До сих пор наш feed service читал напрямую из таблицы Post, когда пользователь запрашивал ленту. Большинство постов читают несколько дней, после чего к ним больше не обращаются. Но у некоторых постов (особенно от аккаунтов с большим числом подписчиков) число чтений в первые несколько часов будет *огромным*.

DynamoDB, как и многие key-value stores, может масштабироваться до очень высокого throughput, *если выполняются определённые условия*. Одно из важнейших условий — равномерная нагрузка на весь keyspace. Под капотом у DynamoDB физические машины с реальными ограничениями, как и у любой другой базы данных. Если Post1 получает 500 запросов в секунду, а Post2–Post1000 получают 0 запросов в секунду, это неравномерная нагрузка!

К счастью для нас, посты создаются гораздо чаще, чем редактируются. Но как решить проблему hot keys в таблице Post?

#### Хорошее решение: Post cache с большим keyspace

##### Подход

A good solution is to put a distributed cache between the readers of the Post table and the table itself. Posts are edited very rarely, so we can set a long time to live (TTL) on them and have the cache evict the least recently used (LRU) posts. As long as the cache is big enough to hold the most recent posts, the vast majority of requests to the Post table will hit the cache instead. If we have N hosts with M memory each, the cache can hold as many posts as fit in N\*M.

When a post is edited (not created!), we simply invalidate the cache entry for that post ID.

![Иллюстрация](/content/fb-news-feed/0edc5ab542.svg)

Distributed Post Cache

We can use Redis for this and key by post ID, so posts are distributed evenly across the cluster.

##### Сложности

Главная сложность Post Cache в том, что у него [та же проблема hot key, что и у Post Table](/lessons/key-technologies/redis)! Если на одном неудачном shard/partition оказывается сразу несколько вирусных постов, хосты, которые его обслуживают, снова получают неравномерную нагрузку, и этот cache очень трудно масштабировать. Многие хосты при этом будут недоиспользованы.

![Иллюстрация](/content/fb-news-feed/a4468a58cc.svg)

Hot key issue

#### Отличное решение: Redundant Post Cache

##### Подход

Как и в Distributed Post Cache выше, отличное решение здесь — поставить cache между читателями Post table и самой таблицей. Посты редактируют очень редко, поэтому можно задать длинный time to live (TTL) и вытеснять из cache наименее недавно использованные посты (LRU). Пока cache достаточно велик, чтобы вместить самые популярные посты, подавляющее большинство запросов к Post Table будет попадать в cache.

Ключевое отличие от предыдущего подхода: вместо **шардированного** cache (где каждый пост живёт ровно на одном узле) мы используем **реплицированные** инстансы cache, и каждый из них может отдать любой пост. Load balancer распределяет запросы между этими инстансами, так что каждый независимо обрабатывает свою долю общего трафика. *Этим инстансам cache не нужно координироваться между собой*. Каждый инстанс может обслуживать один и тот же postID, а значит, трафик чтения вирусного поста распределяется между всеми N инстансами, а не бьёт по одному shard.

Это значит, что поначалу cache miss будет больше (для очень вирусного поста при N инстансах cache мы можем получить N запросов к базе вместо одного, если бы шардировали cache по postID). Но N запросов — это намного меньше, чем миллионы запросов, которые пришлось бы обрабатывать вообще без cache.

Оба варианта решают задачу, но здесь мы получаем в N раз больший throughput для hot key без какой-либо дополнительной координации.

![Иллюстрация](/content/fb-news-feed/4260a0979f.svg)

Redundant Post Cache

##### Сложности

В этом случае в cache поместится меньше разных постов, чем при распределении или партиционировании постов. Это, скорее всего, нормально: наше хранилище DynamoDB выдерживает *некоторый* разброс в read throughput и при этом остаётся быстрым.

## [Чего ждут на каждом уровне](https://www.hellointerview.com/blog/the-system-design-interview-what-is-expected-at-each-level)

Что ж, получилось много. Ты, наверное, думаешь: «Сколько из этого на самом деле от меня требуется на интервью?» Давай разберёмся.

### Mid-level

**Ширина vs. глубина:** mid-level кандидат в основном сосредоточен на ширине (80% против 20%). Ты должен уметь набросать high-level design, который покрывает определённые тобой функциональные требования, но многие компоненты при этом будут для тебя абстракциями, знакомыми лишь поверхностно.

**Проверка основ:** интервьюер потратит какое-то время на проверку основ, чтобы убедиться, что ты понимаешь, что делает каждый компонент твоей системы. Например, если ты добавил API Gateway, будь готов, что тебя спросят, что он делает и как работает (на высоком уровне). Словом, интервьюер ничего не принимает на веру в том, что касается твоих знаний.

**Смесь лидерства и ведомой роли:** ты должен вести интервью, особенно на ранних этапах, но от тебя не ждут, что ты сам с высокой точностью заметишь проблемы в своём дизайне. Поэтому вполне разумно, что на поздних этапах интервьюер перехватит инициативу и будет проверять твой дизайн вопросами.

**Планка для News Feed:** в этой задаче кандидат уровня E4 чётко определил API endpoints и модель данных и пришёл к рабочему high-level design, который отвечает требованиям. У него могут быть какие-то из «хороших» решений, но от него не ждут, что он закроет все возможные edge cases масштабирования в Deep Dives.

### Senior

**Глубина экспертизы**: от senior кандидата ждут более глубоких знаний — примерно 60% ширины и 40% глубины. Ты должен уметь уходить в технические детали в тех областях, где у тебя есть практический опыт. Важно показать глубокое понимание ключевых концепций и технологий, относящихся к задаче.

**Продвинутый system design**: ты должен знать продвинутые принципы проектирования систем. Например, необходимо знать подходы к fan-out. Также от тебя ждут, что ты итеративно найдёшь узкие места в производительности и предложишь улучшения. Ключевое здесь — уверенно и ясно ориентироваться в этих темах.

**Объяснение архитектурных решений**: ты должен чётко объяснять плюсы и минусы разных архитектурных вариантов, особенно их влияние на масштабируемость, производительность и поддерживаемость. Ты обосновываешь решения и объясняешь компромиссы, на которые идёшь.

**Решение проблем и проактивность**: ты должен показать сильные навыки решения проблем и проактивный подход. Это значит предвидеть возможные сложности в своих дизайнах и предлагать улучшения. Нужно уверенно находить и устранять узкие места, оптимизировать производительность и обеспечивать надёжность системы.

**Планка для News Feed:** в этой задаче от кандидатов уровня E5 ждут, что они быстро пройдут начальный high-level design, чтобы осталось время подробно обсудить как минимум 2 deep dives. Они также должны уметь обсуждать плюсы и минусы разных архитектурных вариантов, особенно их влияние на масштабируемость, производительность и поддерживаемость. Ожидается, что они сами поднимут часть потенциальных проблем с fanout и узкими местами в производительности.

### Staff+

**Упор на глубину**: от staff+ кандидата ждут глубокого погружения в нюансы system design — я рассчитываю примерно на 40% ширины и 60% глубины в твоём понимании. На этом уровне важно показать, что даже если ты не решал именно эту задачу, ты решил достаточно задач в реальном мире, чтобы уверенно спроектировать решение, опираясь на свой опыт.

Ты должен знать, какие технологии применять, не только в теории, но и на практике, и уметь опираться на прошлый опыт, объясняя, как их использовать для конкретных задач. Интервьюер знает, что мелочи ты знаешь (REST API, нормализацию данных и т. п.), поэтому их можно пробежать на высоком уровне, чтобы осталось время на самое интересное.

**Высокая степень проактивности**: на этом уровне ждут исключительной проактивности. Ты должен самостоятельно находить и решать проблемы, уверенно выявляя и разбирая ключевые сложности system design. Это значит не просто реагировать на проблемы по мере их появления, а предугадывать их и заранее закладывать решения. Интервьюер должен вмешиваться только для того, чтобы сфокусировать разговор, а не направлять его.

**Практическое применение технологий**: ты должен хорошо разбираться в практическом применении разных технологий. Твой опыт должен вести разговор и показывать, что ты ясно понимаешь, как разные инструменты и системы настраиваются в реальных сценариях под конкретные требования.

**Решение сложных задач и принятие решений**: навыки решения проблем должны быть на высшем уровне. Это значит не только справляться со сложными техническими задачами, но и принимать обоснованные решения с учётом масштабируемости, производительности, надёжности и сопровождения.

**Продвинутый system design и масштабируемость**: твой подход к проектированию должен быть продвинутым, с упором на масштабируемость и надёжность, особенно при высокой нагрузке. Это включает глубокое понимание распределённых систем, load balancing, стратегий кеширования и других продвинутых концепций, необходимых для построения устойчивых, масштабируемых систем.

**Планка для News Feed:** от staff+ кандидата ждут глубины и качества решений, особенно для сложных сценариев, которые мы разбирали выше. Staff-кандидат, скорее всего, пройдёт по всем deep dives (и/или по некоторым, которые мы не перечисляли). От него ждут, что он сам выявит потенциальные проблемы в системе и расскажет про тюнинг производительности для этой задачи.

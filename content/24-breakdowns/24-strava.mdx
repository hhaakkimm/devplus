## Разбор задачи

**🏃‍♂️🚴‍♀️ Что такое [Strava](https://www.strava.com/)?**
Strava — это приложение для фитнес-трекинга, которое позволяет пользователям записывать свои физические активности (в первую очередь бег и велоспорт) и делиться ими со своей сетью. Оно даёт подробную аналитику по результатам и маршрутам, а также позволяет пользователям взаимодействовать друг с другом.

Strava поддерживает множество видов активности, но в этой задаче мы сосредоточимся на беге и велоспорте.

### [Функциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Пользователи должны иметь возможность начинать, ставить на паузу, останавливать и сохранять свои пробежки и поездки.
2. Во время бега или поездки пользователи должны видеть данные об активности, включая маршрут, дистанцию и время.
3. Пользователи должны иметь возможность просматривать подробности своих завершённых активностей, а также активностей своих друзей.

**Вне рамок (below the line)**

* Добавление и удаление друзей (управление друзьями).
* Аутентификация и авторизация.
* Комментирование и лайки пробежек.

### [Нефункциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Система должна быть высокодоступной (availability >> consistency).
2. Приложение должно работать в удалённых местах без подключения к сети.
3. Приложение должно показывать спортсмену точную и актуальную локальную статистику во время бега или поездки.
4. Система должна масштабироваться до 10 миллионов одновременных активностей.

**Вне рамок (below the line)**

* Соответствие требованиям по защите данных, например GDPR.
* Продвинутые меры безопасности.

## Подготовка

### [Определение основных сущностей](/lessons/sd-prep/delivery)

Начнём с описания основных сущностей системы. Пока не нужно вдаваться в каждую деталь и в каждое поле. К тонкостям, например к отдельным полям, мы вернёмся, когда у нас сложится более цельная картина. Сейчас достаточно определить ключевые сущности: они помогут сформировать мышление и дадут прочную основу для перехода к описанию API.

Чтобы удовлетворить ключевые функциональные требования, выделим следующие основные сущности:

1. **User**: человек, который пользуется приложением. Содержит информацию профиля и настройки.
2. **Activity**: отдельная активность — бег или велоспорт. Включает тип активности (run/ride), время начала, время окончания, данные маршрута (GPS-координаты), дистанцию и длительность.
3. **Route**: набор GPS-координат, записанных во время активности (это также может быть просто поле сущности Activity).
4. **Friend**: связь между пользователями для обмена активностями (примечание: управление друзьями вне рамок, но сама концепция нужна для шеринга).

На реальном интервью это может быть просто короткий список, как здесь. Главное — проговори сущности с интервьюером, чтобы убедиться, что вы понимаете задачу одинаково.

### [API](/lessons/sd-prep/delivery)

Определим API, через которые мобильное приложение взаимодействует с backend-сервисами.

Наша цель — просто пройти по основным требованиям одно за другим и описать API, необходимые для их выполнения. Обычно они соответствуют функциональным требованиям один к одному, но бывает, что для одного требования нужно несколько endpoint'ов, а один endpoint закрывает сразу несколько требований (как в случае с endpoint'ом обновления состояния активности ниже).

Сначала определим endpoint для создания новой активности.

```
// Create a new activity
POST /activities -> Activity
{
    type: "RUN" | "RIDE"
}
```

Затем добавим endpoint для обновления состояния этой активности.

```
// Update the state of an activity
PATCH /activities/:activityId -> Activity
{
    state: "STARTED" | "PAUSED" 
}
```

Здесь мы используем PATCH, потому что хотим обновить только часть полей активности. PUT потребовал бы отправлять ресурс целиком, а с PATCH мы отправляем только обновляемые поля — это пусть и небольшое, но всё же улучшение эффективности.

На интервью PUT и PATCH функционально эквивалентны. Однако тебе могут попасться интервьюеры, которые строго следят за RESTful API и будут спорить об этом, так что лучше быть к этому готовым.

Для отслеживания данных активности добавим POST endpoint, который обновляет маршрут и дистанцию активности.

```
// Add a new location to the activity's route
POST /activities/:activityId/routes -> Activity
{
    location: GPSCoordinate,
}
```

Что касается шеринга активностей с друзьями, будем считать, что он происходит автоматически при сохранении активности. Поэтому вместо отдельного endpoint'а для шеринга можно просто обновить существующий endpoint изменения состояния активности, добавив состояние "COMPLETE".

```
// Mark an activity as complete using the same endpoint we use to update the activity state
PATCH /activities/:activityId -> Activity
{
    state: "COMPLETE"
}
```

Для просмотра активностей нам понадобится список, который показывает либо наши активности, либо активности наших друзей. В этом списке будет только базовая информация об активности: дистанция, длительность и дата.

```
// Get a list of activities for a user
GET /activities?mode={USER|FRIENDS}&page={page}&pageSize={pageSize} -> Partial<Activity>[]
```

Тип Partial&lt;Activity> просто означает, что мы возвращаем подмножество полей активности. Это делается, чтобы ограничить объём данных, передаваемых по сети. Эту нотацию использую я, она пришла из TypeScript, но ты можешь использовать любую удобную. Это лишь вопрос личных предпочтений.

Когда мы нажимаем на активность, хочется увидеть больше подробностей, например карту с маршрутом и дополнительные метрики или детали (они вне рамок этой задачи).

```
// Get an activity by id
GET /activities/:activityId -> Activity
```

## [High-Level Design](/lessons/sd-prep/delivery)

Давай разберём каждое функциональное требование и спроектируем компоненты, которые его закрывают. Лучшая стратегия, особенно если ты впервые видишь такую задачу, — начать с самой простой системы, которая удовлетворяет функциональным требованиям, а затем наращивать сложность под нефункциональные требования на этапе deep dives.

Меня часто спрашивают: «Если я уже знаю более сложный дизайн, всё равно стоит начинать с простого?» Ответ неоднозначный. Если у тебя есть продуманное, более сложное решение, вполне нормально показать его уже на этапе high-level design. Но важно соблюдать баланс. Если уйти в детали слишком рано, можно не успеть закрыть все функциональные требования и, по сути, не ответить на вопрос.

### 1) Users should be able to start, pause, stop, and save their runs and rides.

Нам нужна система, которая корректно обрабатывает и эндпоинт создания активности, и эндпоинт обновления её состояния.

Начнём с наброска самой простой клиент-серверной архитектуры:

![Иллюстрация](/content/strava/92c967bef9.svg)

Users should be able to start, pause, stop, and save their runs and rides.

1. **Client App**: пользователи работают с системой через мобильное приложение.
2. **Activity Service**: обрабатывает входящие запросы на создание и обновление активностей.
3. **Database**: хранит информацию об активностях, включая маршрут, дистанцию и время.

Пользователь открывает приложение и нажимает кнопку «Start Activity»:

1. Клиентское приложение отправляет POST-запрос на /activities, чтобы создать новую активность, и указывает, это пробежка или поездка на велосипеде.
2. Activity Service создаёт активность в базе данных и возвращает объект активности клиенту.
3. Если пользователь решает поставить активность на паузу или возобновить её, он отправляет PATCH-запрос на /activities/:activityId с новым состоянием, и Activity Service соответственно обновляет активность в базе данных.
4. Когда активность закончена, пользователь нажимает кнопку «Save Activity». Это запускает PATCH-запрос на /activities/:activityId с состоянием «COMPLETE».

Интересный момент дизайна — как учитывать время активности, когда пользователь ставит её на паузу. Наивный подход к подсчёту прошедшего времени: хранить startTimeStamp, а при завершении активности вычислять прошедшее время как разницу между текущим временем и startTimeStamp.

Но с паузой этот подход не работает. startTimeStamp остаётся прежним, и прошедшее время продолжает расти, а это неточно.

Один из распространённых способов решить это — хранить время в виде лога пар «обновление статуса + timestamp». Например, такой лог:

```
[
    { status: "STARTED", timestamp: "2021-01-01T00:00:00Z" },
    { status: "PAUSED", timestamp: "2021-01-01T00:10:00Z" },
    { status: "RESUMED", timestamp: "2021-01-01T00:15:00Z" },
    { status: "STOPPED", timestamp: "2021-01-01T00:20:00Z" }
]
```

Когда пользователь нажимает «Stop Activity», мы вычисляем прошедшее время, суммируя длительности между каждой парой timestamp'ов и исключая паузы. В примере выше прошедшее время составит 15 минут (10 минут + 5 минут).

Для такого простого требования это может показаться избыточным, но так проще естественным образом расширить систему: показывать атлетам, когда они были на паузе и как долго, а также разбивку «общее время» и «активное время».

### 2) While running or cycling, users should be able to view activity data, including route, distance, and time.

Пока активность идёт, нам нужно и обновлять состояние, и показывать пользователю данные об активности.

Первая и самая важная часть — точно отслеживать дистанцию и маршрут. Для этого мы записываем GPS-координаты пользователя с постоянным интервалом. Предполагаем, что у пользователя современный смартфон с GPS, поэтому по GPS-координатам можно считать дистанцию с помощью [формулы гаверсинусов](https://en.wikipedia.org/wiki/Haversine_formula).

![Иллюстрация](/content/strava/2dd07c241f.svg)

While running or cycling, users should be able to view activity data, including route, distance, and time.

Вот как это работает:

1. Клиентское приложение записывает GPS-координаты пользователя с постоянным интервалом: допустим, каждые 2 секунды для поездки на велосипеде и каждые 5 секунд для пробежки. Для этого мы используем встроенные сервисы геолокации iOS и Android:
   * Для iOS: используем фреймворк Core Location, а именно класс CLLocationManager. Обновления геолокации запускаем методом startUpdatingLocation() и реализуем delegate-метод locationManager(\_:didUpdateLocations:), чтобы получать новые координаты.
   * Для Android: используем Google Location Services API, часть Google Play Services. Можно взять класс FusedLocationProviderClient и вызвать метод requestLocationUpdates(), чтобы получать периодические обновления геолокации.
2. Затем клиентское приложение отправляет эти новые координаты на наш эндпоинт /activities/:activityId.
3. Activity Service обновляет таблицу Route в базе данных для этой активности: добавляет новые координаты и время, когда они были записаны.
4. Мы также обновляем поле distance: вычисляем расстояние между новой координатой и предыдущей по формуле гаверсинусов.

Знать, какие библиотеки и фреймворки использовать для получения GPS-координат, тебе совершенно не обязательно. Цель этого вопроса — проверить знание system design, а не мобильной разработки. Но важно понимать, что в большинстве современных смартфонов есть встроенный GPS и что мобильные приложения обычно получают эти данные через соответствующие библиотеки и фреймворки. Я привёл их здесь лишь для того, чтобы показать, как это выглядит на практике.

Внимательные читатели, вероятно, уже кричат в экран: им ясно, что отправлять эти обновления на сервер не нужно, а логику можно обрабатывать локально на клиенте. Вы правы. Мы вернёмся к этому в deep dive. На практике большинство кандидатов, которым я задаю этот вопрос, упускают такую оптимизацию, и мы доходим до неё позже в ходе интервью.

### 3) Users should be able to view details about their own completed activities as well as the activities of their friends.

Когда активности завершены, они уже сохранены в базе данных, и всё, что нужно было сделать, — обновить их состояние на «COMPLETE» через тот же эндпоинт, которым мы обновляли состояние активности.

Чтобы показать активности, достаточно запросить из БД активности в состоянии «COMPLETE» и отфильтровать их по query-параметру mode: показывать активности самого пользователя или его друзей. Это делается обычным WHERE.

Примеры запросов:

```
-- For mode = USER
SELECT * FROM activities 
WHERE state = "COMPLETE"
AND userId = :userId
LIMIT :pageSize OFFSET (:page - 1) * :pageSize

-- For mode = FRIENDS
SELECT * FROM activities 
WHERE state = "COMPLETE"
AND userId IN (SELECT friendId FROM friends WHERE userId = :userId)
LIMIT :pageSize OFFSET (:page - 1) * :pageSize
```

В таблице friends будет две колонки: userId и friendId. Будем считать отношения двусторонними, поэтому для каждой новой дружбы мы добавляем в таблицу две записи: одну с userId и friendId, а другую с теми же значениями, но в обратном порядке. Если сделать составной первичный ключ на (userId, friendId) и добавить индекс на userId, запрос списка друзей пользователя будет эффективным, а дубликаты дружб исключены.

Этот первый GET-запрос возвращает список активностей только с базовой информацией и activityId каждой активности. Когда пользователь нажимает на активность, мы можем сделать второй, более подробный GET-запрос по activityId и получить полные данные об активности.

![Иллюстрация](/content/strava/49eedd3c53.svg)

Users should be able to view details about their own completed activities as well as the activities of their friends.

Полный сценарий выглядит так:

1. Пользователь открывает в приложении страницу со списком активностей.
2. Клиент отправляет GET-запрос на /activities?mode=\{USER|FRIENDS\}&page=\{page\}&pageSize=\{pageSize\}, чтобы получить список активностей.
3. Список активностей отображается в UI, и пользователь нажимает на активность, чтобы посмотреть детали.
4. Клиент отправляет GET-запрос на /activities/:activityId, чтобы получить полные данные об активности и отобразить их на новой странице с деталями.

Чтобы показать карту, можно использовать комбинацию данных маршрута и Google Maps API. Мы передаём в Google Maps API массив координат, и он рисует линию, соединяющую все точки.

## [Deep dives](/lessons/sd-prep/delivery)

На этом этапе у нас есть базовая работающая система, которая удовлетворяет функциональным требованиям. Но есть несколько областей, в которые можно углубиться, чтобы улучшить эффективность, offline-функциональность, масштабируемость и realtime-шеринг.

Этот список deep dives, конечно, не исчерпывающий. Это подборка самых популярных направлений, в которые, по моему опыту, обычно уходит это интервью.

### 1) Как поддержать трекинг активностей в offline?

Многие атлеты тренируются в глухих местах без сетевого покрытия, но всё равно хотят записывать свои активности. Отсюда следует важный вывод, который меняет всю систему.

Ключевая идея: пока мы не поддерживаем realtime-шеринг активностей, мы можем записывать данные активности локально, прямо на устройстве клиента, и синхронизировать их с сервером только после завершения активности и/или когда пользователь снова онлайн.

Что важно, это решает сразу несколько проблем:

1. Мы можем трекать активности, не думая о надёжности сети на стороне клиента.
2. Даже когда у клиента хорошее сетевое соединение, мы экономим сетевой трафик: не отправляем обновления локации на сервер каждые несколько секунд (вместо этого данные уходят только по завершении пробежки или на паузе).
3. Показывать пользователю точные и актуальные данные об активности просто, потому что всё происходит синхронно на его устройстве.

Этот вопрос подсвечивает важный и часто упускаемый аспект system design: клиент как активный участник системы. У современных смартфонов и браузеров есть доступ к множеству сенсоров, значительному объёму памяти и вычислительной мощности, а также к большому локальному хранилищу. Многие кандидаты не замечают возможностей клиента и думают только о серверных решениях. Но в таких системах, как Strava, Dropbox или Spotify, клиент часто играет ключевую роль во всём дизайне: он позволяет реализовать offline-функциональность, снижает нагрузку на сервер и улучшает пользовательский опыт.

Как это работает на практике?

1. Как и в нашем high-level design, мы используем location-сервисы устройства, чтобы записывать GPS-координаты пользователя с постоянным интервалом.
2. Эти данные мы записываем локально на устройстве в буфер в памяти (например, массив пар «GPS-координаты + timestamp»).
3. Чтобы не потерять данные при выключении устройства или разрядке батареи, мы периодически, примерно каждые ~10 секунд, сохраняем этот буфер в локальное хранилище устройства:
   * Для iOS: можно использовать Core Data для больших структурированных наборов данных или UserDefaults для небольших объёмов простых данных типа ключ-значение.
   * Для Android: можно использовать базу Room для больших структурированных наборов данных или SharedPreferences для небольших объёмов простых данных типа ключ-значение.
4. Когда приложение открывается заново или активность возобновляется, мы сначала проверяем локальное хранилище на наличие сохранённых данных и загружаем их в буфер в памяти, а потом продолжаем записывать новые.
5. Когда активность завершена и устройство онлайн, мы отправляем все накопленные данные на сервер одним запросом. Для очень длинных активностей, возможно, придётся реализовать стратегию chunking, чтобы эффективно обрабатывать большие объёмы данных.
6. Также можно реализовать механизм фоновой синхронизации, который периодически пытается загрузить данные, когда появляется соединение, даже если активность ещё не завершена. Это баланс между эффективностью и сохранностью данных.
7. Когда получено подтверждение, что данные сохранены в нашей удалённой базе, мы можем удалить локальный буфер и снова готовы к работе.

Такой подход гарантирует, что даже при неожиданном выключении устройства мы потеряем максимум 10 секунд данных активности (или другой интервал периодического сохранения, который мы выберем). Однако важно соблюдать баланс между частотой GPS-трекинга и сохранения данных и расходом батареи.

![Иллюстрация](/content/strava/91ef025ac4.svg)

Как поддержать трекинг активностей в offline?

Конкретные детали реализации могут отличаться в зависимости от мобильной платформы и объёма хранимых данных. Для больших наборов данных локальная база SQLite может подойти лучше, чем UserDefaults или SharedPreferences. Но такие детали скорее относятся к интервью по Mobile System Design, а не к общему SWE-интервью.

Мы закончили первый deep dive, а у нас по-прежнему простая client-server архитектура. Почему? Особенно если в большинстве других наших разборов используются микросервисы? Правда в том, что единственно верного ответа тут нет. Но в нашем случае мы переложили на клиент так много нагрузки на запись, что у backend не так много работы. То, что осталось, всё равно нужно масштабировать, и мы к этому вернёмся, но отдельные микросервисы с независимым масштабированием нам не нужны, потому что значительного перекоса между чтением и записью по разным путям нет. Можно возразить, что так инженерной команде будет сложнее расти, когда все работают в одной кодовой базе, но если Meta, как известно, справляется, то справимся и мы.

### 2) Как масштабироваться до 10 миллионов одновременных активностей?

Теперь, когда мы трекаем активности локально, масштабировать backend стало довольно просто! Мы сократили число запросов к нашим backend-сервисам в 100 раз, потому что теперь данные отправляются только после завершения пробежки. Наша production engineering команда будет в восторге, а финансовый отдел тоже.

Но у нас всё ещё остаются потенциальные bottleneck, которые стоит разобрать.

Начнём с базы данных. При ~100M DAU, каждый из которых делает одну активность в день, мы получаем ~100M новых активностей в день. За год это ~36500M активностей, или ~36.5B.

Чтобы оценить, сколько места нужно на каждую активность, разобьём её на части:

* Базовые метаданные вроде статуса, userID, времени начала/окончания и т. д. должны быть довольно дешёвыми. Допустим, ~100 байт на активность.
* Самая дорогая часть — маршрут. Если средняя активность длится 30 минут, а GPS-координаты мы берём в среднем каждые ~3 секунды, то на активность будет около 600 точек. Каждой строке маршрута нужны поля широты и долготы, а также timestamp. Это ещё (8 байт + 8 байт + 8 байт) \* 600 = ~15KB.

15KB \* 36.5B = 547.5TB данных в год

Это немало, но далеко не неподъёмно. Вот что можно сделать:

1. Можно сделать shard нашей базы данных, чтобы разделить данные между несколькими инстансами. Шардировать можно по времени завершения активности, поскольку большинство наших запросов будут касаться недавних активностей.
2. Можно ввести data tiering. Вероятность того, что кто-то захочет посмотреть пробежку несколькими годами ранее, довольно низкая. Чтобы снизить расходы на хранение, можно переносить старые данные на более дешёвые уровни хранилища:
   * Hot-данные (недавние активности) остаются в быстром и дорогом хранилище
   * Warm-данные (возрастом 3–12 месяцев) переносятся в более медленное и дешёвое хранилище
   * Cold-данные (старше 1 года) переносятся в архивное хранилище вроде S3
3. При необходимости можно добавить caching. Если окажется, что мы часто запрашиваем одни и те же активности, cache снизит нагрузку на чтение из базы. Для меня это не приоритет, так как read throughput должен быть довольно низким, но это первое, что мы сделаем, если время загрузки станет неприемлемым.

###### Паттерн: Scaling Writes

Все стратегии, которые мы здесь обсудили, часто встречаются в системах, где нужно масштабировать запись. Эта задача типична для многих задач по system design, и полезно знать этот паттерн на случай, если интервьюер захочет копнуть глубже.

[Изучить этот паттерн](/lessons/patterns/scaling-writes)

Какую базу данных выбрать?

Непопулярное мнение: это не так уж важно. Данных много, но с ними вполне можно справиться; безумного read или write throughput у нас нет, а данные реляционные, но не слишком сильно. В реальности отлично подойдут все популярные крупные технологии баз данных.

Для Activity Service, учитывая, что и read, и write throughput должны быть довольно низкими, я не вижу причин разбивать его на независимо масштабируемые микросервисы. Вместо этого, когда мы упрёмся в память, CPU или сеть, можно просто масштабировать сервис горизонтально.

### 3) Как поддержать realtime-шеринг активностей с друзьями?

Один из частых follow-up вопросов на этом интервью: «что будет, если мы захотим позволить друзьям следить за активностью в реальном времени». В таком случае друзья видят не просто статистику уже завершённой активности, а могут наблюдать за тобой прямо во время пробежки или поездки на велосипеде, видя, как статистика и маршрут обновляются почти в реальном времени.

Это приближает дизайн к другим популярным realtime-системам, таким как [FB Live Comments](/lessons/breakdowns/fb-live-comments) или [Whatsapp](/lessons/breakdowns/whatsapp).

Чтобы друзья могли видеть активность в реальном времени, мы снова добавим периодические обновления на сервер во время активности. Логику для данных, которые видит сам пользователь, оставляем на устройстве, а координаты отправляем на сервер каждые 2-5 секунд. Получив обновление, сервер сохраняет его в базе данных и рассылает всем друзьям пользователя.

Наверняка ты сейчас думаешь: «WebSockets!» Это не ошибка: реализовать всё можно и на WebSockets, и на SSE, но я бы настоятельно утверждал, что это переусложнение задачи.

Можно завести real-time tracking service, который соединяется с клиентами друзей по WebSocket или SSE и рассылает им обновления через pub-sub, но это добавляет много лишней сложности.

Вместо этого два ключевых наблюдения говорят о том, что проще и эффективнее будет механизм polling:

1. Обновления предсказуемы: в отличие от Messenger или Live Comments, мы знаем, что следующее обновление придёт через 2-5 секунд. Это позволяет выбрать эффективный интервал для polling.
2. Точность в реальном времени не критична: друзьям не нужна информация с точностью до секунды. Задержка в несколько секунд допустима и заметно не ухудшит впечатление от использования.

###### Pattern: Real-time Updates

Один из самых важных моментов в паттерне realtime updates: нужно понимать, когда он не нужен! В нашем разборе паттерна есть простая блок-схема, по которой можно определить, какие протоколы использовать и как выстроить архитектуру backend.

[Изучить этот паттерн](/lessons/patterns/realtime-updates)

Исходя из этих наблюдений, можно реализовать простой механизм polling: клиенты друзей периодически запрашивают обновления с тем же интервалом, с которым устройство атлета отправляет их на сервер (со сдвигом на пару секунд, чтобы учесть latency).

Пользовательский опыт можно улучшить с помощью умной буферизации. Идея в том, чтобы намеренно отстава́ть в отображаемых данных о положении на один-два интервала обновления (например, на 5-10 секунд). Буферизация позволяет сделать анимацию движения атлета более плавной и непрерывной и убирает резкие скачки позиции, которые случаются при обновлениях в реальном времени. Друзьям, которые смотрят активность, будет казаться, что атлет постоянно движется, и это больше похоже на «прямую трансляцию». Мы жертвуем абсолютной точностью в реальном времени, зато заметно улучшаем визуальный опыт, который лучше соответствует ожиданиям пользователей от live-трекинга. Намеренная задержка также компенсирует сетевую latency, поэтому поведение получается более стабильным при разном качестве сети.

### 4) Как показать leaderboard лучших атлетов?

Ещё одно естественное расширение задачи: показывать leaderboard лучших атлетов по типу активности и дистанции. Можно фильтровать по стране, региону, городу и так далее.

Вот какие подходы возможны:

#### Плохое решение: наивный подход

##### Подход

Проще всего сделать запрос к DB по всем активностям, сгруппировать их по пользователям и просуммировать дистанцию. Будем считать, что у нас есть таблица пользователей с базовой информацией: имя, email, страна и т. д.

Это выглядело бы примерно так:

```
SELECT
    u.name,
    SUM(a.distance) as total_distance
FROM activities a
JOIN users u ON a.userId = u.userId
WHERE a.state = "COMPLETE"
AND a.type = "RUN"
GROUP BY u.userId
ORDER BY total_distance DESC
```

Естественно, такой запрос будет довольно медленным, потому что агрегация идёт по миллионам активностей. Оптимизировать его можно несколькими способами.

##### Сложности

У этого подхода серьёзные проблемы с масштабированием. С ростом числа активностей производительность запроса будет быстро падать. Для каждого запроса к leaderboard системе пришлось бы сканировать и агрегировать миллионы записей, что приводит к высокой latency и росту нагрузки на базу данных. Кроме того, такой метод не учитывает динамичность leaderboard: позиции могут часто меняться по мере появления новых активностей.

#### Хорошее решение: периодическая агрегация

##### Подход

Чтобы улучшить наивный подход, можно реализовать периодическую агрегацию. Для этого создаётся отдельная таблица leaderboard с заранее посчитанными суммами по каждому пользователю. Фоновая задача запускается с регулярным интервалом (например, раз в сутки) и обновляет агрегаты на основе новых активностей. Тогда запрос к leaderboard превращается в простой SELECT из предагрегированной таблицы с сортировкой по суммарной дистанции.

![Иллюстрация](/content/strava/19d097969b.svg)

Periodic Aggregation

##### Сложности

Такой метод заметно сокращает время ответа на запросы к leaderboard, но вносит eventual consistency. Leaderboard не отражает изменения в реальном времени, и пользователь может запутаться, если его последняя активность не сразу видна в рейтинге. К тому же подобрать оптимальную частоту обновлений непросто: слишком частые обновления могут перегрузить ресурсы системы, а редкие приводят к устаревшим данным.

#### Отличное решение: leaderboard в реальном времени на Redis

##### Подход

Для более масштабируемого решения в реальном времени можно использовать [Redis](/lessons/key-technologies/redis), in-memory хранилище структур данных. Для leaderboard мы возьмём Redis Sorted Sets: ID пользователей будут members, а их суммарные дистанции будут scores. Когда записывается новая активность, мы увеличиваем score пользователя в sorted set. Чтобы получить leaderboard, достаточно взять top N members из sorted set, и Redis делает это крайне эффективно.

Что делать, если нужна фильтрация по стране или по периоду времени?

Чтобы обработать фильтрацию по стране или по периоду времени, можно расширить подход на Redis:

1. Фильтрация по стране:
   * Можно создать отдельные sorted sets для каждой страны, например "leaderboard:run:USA", "leaderboard:run:Canada" и так далее.
   * При записи активности мы обновляем и глобальный leaderboard, и leaderboard конкретной страны.
   * Чтобы получить leaderboard по стране, мы просто обращаемся к соответствующему sorted set.

```
# Add an activity to the leaderboard (increment user's total distance)
redis.zincrby(f"leaderboard:run:global", distance, user_id)
redis.zincrby(f"leaderboard:run:USA", distance, user_id)

# Query the leaderboard (get top users by total distance)
redis.zrange(f"leaderboard:run:global", 0, -1, desc=True, withscores=True)
```

2. Для фильтрации по периоду времени подход посложнее: он сочетает sorted sets и hashes:
   * Мы используем комбинацию Redis sorted sets и hashes, чтобы хранить и timestamp, и дистанцию.
   * Для каждой активности мы сохраняем:
     1. Запись в sorted set: ID активности как member, timestamp как score.
     2. Запись в hash: ID активности как ключ, с полями для ID пользователя и дистанции.
   * При запросе leaderboard за конкретный период:
     1. Используем ZRANGEBYSCORE, чтобы получить ID активностей внутри нужного периода.
     2. Для этих ID активностей берём из hash соответствующие ID пользователей и дистанции.
     3. Агрегируем дистанции по ID пользователя в памяти.
     4. Сортируем агрегированные результаты и получаем итоговый leaderboard.

Вот пример псевдокода, как это может работать:

```
# When logging a new activity
activity_id = generate_unique_id()
redis.zadd("activities:timestamps", {activity_id: timestamp})
redis.hset(f"activity:{activity_id}", mapping={"user_id": user_id, "distance": distance})

# Querying the leaderboard for last 24 hours
now = current_timestamp()
day_ago = now - 24*60*60
activity_ids = redis.zrangebyscore("activities:timestamps", day_ago, now)

user_distances = {}
for activity_id in activity_ids:
    activity_data = redis.hgetall(f"activity:{activity_id}")
    user_id = activity_data["user_id"]
    distance = float(activity_data["distance"])
    user_distances[user_id] = user_distances.get(user_id, 0) + distance

# Sort users by total distance
leaderboard = sorted(user_distances.items(), key=lambda x: x[1], reverse=True)
```

Такой подход позволяет эффективно фильтровать по периоду времени и агрегировать дистанции, давая leaderboard в реальном времени, который можно настраивать под разные периоды. Результаты можно кэшировать с коротким TTL, чтобы ограничить агрегацию в памяти и при этом сохранить актуальность данных.

##### Сложности

Главная сложность этого подхода: обеспечить консистентность данных между Redis и нашей основной базой данных. Нужна надёжная система обработки сбоев и retry при обновлении Redis. Кроме того, нужно учитывать ограничения Redis по памяти: хранить полные данные leaderboard для всех возможных комбинаций типов активности, периодов времени и географических фильтров может быть слишком дорого по памяти. Чтобы снизить расход, возможно, придётся использовать стратегию кэширования: держать в Redis только самые часто запрашиваемые leaderboards, а более редкие считать по запросу.

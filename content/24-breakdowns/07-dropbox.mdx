## Разбор задачи

**☁️ Что такое [Dropbox](https://www.Dropbox.com/)**
Dropbox — облачный сервис для хранения файлов, который позволяет пользователям хранить файлы и делиться ими. Он обеспечивает безопасный и надёжный способ хранить файлы и получать к ним доступ откуда угодно и с любого устройства.

### [Функциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Пользователи должны иметь возможность загружать файл с любого устройства
2. Пользователи должны иметь возможность скачивать файл на любое устройство
3. Пользователи должны иметь возможность делиться файлом с другими пользователями и просматривать файлы, которыми поделились с ними
4. Файлы должны автоматически синхронизироваться между устройствами

**Вне рамок (below the line):**

* Пользователи должны иметь возможность редактировать файлы
* Пользователи должны иметь возможность просматривать файлы без скачивания

Стоит отметить, что существуют родственные задачи по system design, связанные с проектированием самого Blob Storage. В этой задаче они вне рамок, но можешь самостоятельно изучить, как устроен и спроектирован Blob Storage.


### [Нефункциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Система должна быть высокодоступной (availability важнее consistency).
2. Система должна поддерживать файлы размером до 50GB.
3. Система должна быть безопасной и надёжной. Мы должны уметь восстанавливать файлы, если они потеряны или повреждены.
4. Система должна обеспечивать максимально быструю загрузку, скачивание и синхронизацию (низкая latency).

**Вне рамок (below the line):**

* У системы должен быть лимит хранилища на пользователя
* Система должна поддерживать версионирование файлов
* Система должна сканировать файлы на вирусы и вредоносное ПО

Вот как это может выглядеть на твоей доске:

![Иллюстрация](/content/dropbox/27a445c23d.svg)

Нефункциональные требования

Многие кандидаты путаются с компромиссом CAP theorem в этой задаче. Помни: consistency стоит ставить выше availability, только если каждое чтение обязано получить самую свежую запись, иначе система сломается. Например, в приложении для торговли акциями, если пользователь в Германии покупает акцию AAPL, а сразу после него другой пользователь в США пытается купить акцию AAPL, нужно убедиться, что первая транзакция реплицирована в США, прежде чем продолжать. Но для файлового хранилища вроде Dropbox нормально, если пользователь в Германии загрузил файл, а пользователь в США не видит его несколько секунд.

## Подготовка

### План решения

Прежде чем переходить к проектированию системы, важно потратить минуту на то, чтобы спланировать подход. К счастью, для таких вопросов в стиле [product design](/lessons/sd-prep/introduction) план довольно прост: выстраивай дизайн последовательно, шаг за шагом проходя по функциональным требованиям. Так ты сохранишь фокус и не увязнешь в деталях. Когда функциональные требования будут закрыты, нефункциональные подскажут, куда идти в deep dives.

### [Определение основных сущностей](/lessons/sd-prep/delivery)

Я люблю начинать с общего обзора главных сущностей. На этом этапе не обязательно знать каждую колонку или деталь. Этими тонкостями мы займёмся позже, когда лучше поймём систему (во время high-level design). Сначала эти ключевые сущности направят наши рассуждения и заложат прочную основу для определения API.

Для Dropbox основные сущности предельно просты:

1. **File**: сырые данные, которые пользователи загружают, скачивают и которыми делятся.
2. **FileMetadata**: метаданные файла. Включают такую информацию, как имя файла, размер, mime type и пользователь, который его загрузил.
3. **User**: пользователь нашей системы.

На реальном интервью это может быть простой короткий список вроде этого. Просто обсуди сущности с интервьюером, чтобы убедиться, что вы понимаете всё одинаково.

![Иллюстрация](/content/dropbox/0f6d83f03b.svg)

Определение основных сущностей

Переходя к дизайну, помни о простой цели: создать систему, которая удовлетворяет всем функциональным и нефункциональным требованиям. Для этого я рекомендую сначала закрыть функциональные требования, а затем наслоить поверх них нефункциональные. Так ты сохранишь фокус и не увязнешь в деталях.

### [API](/lessons/sd-prep/delivery)

API — основной интерфейс, с которым будут взаимодействовать пользователи. Важно определить его заранее, поскольку он направит твой high-level design. Нам нужно определить по одному endpoint для каждого функционального требования.

Начнём с загрузки файла. Endpoint может выглядеть так:

```
POST /files
Request:
{
  File, 
  FileMetadata
}
```

Чтобы скачать файл, endpoint может быть таким:

```
GET /files/{fileId} -> File & FileMetadata
```

Имей в виду, что твои API могут меняться и эволюционировать по ходу работы. В нашем случае API загрузки и скачивания заметно изменятся, когда мы будем взвешивать компромиссы разных подходов в high-level design (подробнее об этом позже). Ты можешь заранее сообщить об этом интервьюеру, сказав: «Я набросаю несколько простых API, но могу вернуться и улучшить их, когда мы глубже погрузимся в дизайн».

Чтобы поделиться файлом, endpoint может выглядеть так:

```
POST /files/{fileId}/share
Request:
{
  User[] // The users to share the file with
}
```

Наконец, клиентам нужен способ запрашивать изменения файлов на удалённом сервере. Так мы узнаем, какие файлы нужно синхронизировать на локальное устройство.

```
GET /files/changes?since={timestamp} -> ChangeEvent[]
```

Каждый ChangeEvent включает fileId, тип изменения (created, updated, deleted) и обновлённые метаданные. Передавая временную метку since, клиент может эффективно получать только те изменения, которые произошли с момента его последней синхронизации.

Не используй userId из тела запроса или заголовков для определения того, кто делает запрос: клиент может подделать и то и другое. Вместо этого проверяй session token или JWT, определяй по нему текущего пользователя и проверяй его доступ к запрашиваемому файлу.

## [High-level design](/lessons/sd-prep/delivery)

### 1) Пользователь должен иметь возможность загружать файл с любого устройства

Главное требование к системе вроде Dropbox — давать пользователям загружать файлы. Когда речь о хранении файла, нужно решить две вещи:

1. Где хранить содержимое файла (сырые байты)?
2. Где хранить метаданные файла?

Для метаданных можно взять [NoSQL database](/lessons/sd-prep/key-technologies) вроде DynamoDB. [DynamoDB](https://aws.amazon.com/dynamodb/) — полностью управляемая NoSQL database от AWS. Наши метаданные слабо структурированы, связей почти нет, а основной паттерн запросов — получать файлы по пользователю. Поэтому DynamoDB — хороший выбор, но не зацикливайся на правильном выборе на интервью. На деле SQL database вроде PostgreSQL для этого случая подойдёт не хуже. Подробнее о том, как выбирать database (и почему это может не иметь значения), читай [здесь](/lessons/sd-prep/key-technologies).

Наша схема будет простым документом, и начать можно примерно с такого:

```
  {
    "id": "123",
    "name": "file.txt",
    "size": 1000,
    "mimeType": "text/plain",
    "uploadedBy": "user1"
  }
```

Что касается хранения самого файла, вариантов несколько. Давай разберём компромиссы каждого.

#### Плохое решение: загрузка файла на один сервер

##### Подход

Самый простой вариант — загружать файлы прямо на наш backend-сервер (назовём его File Service) и хранить их там. Endpoint POST /files принимает файл и метаданные, сохраняет файл в локальной файловой системе сервера, а метаданные — в нашей database. Для небольшого приложения это разумный подход, но он плохо масштабируется и ненадёжен.

![Иллюстрация](/content/dropbox/bf718298b7.svg)

Пользователь должен иметь возможность загружать файл с любого устройства

##### Сложности

У этого простого подхода есть ряд проблем. По мере роста числа файлов нам придётся добавлять серверу всё больше хранилища и/или масштабироваться горизонтально, добавляя серверы. Кроме того, он ненадёжен: если сервер упадёт, мы потеряем доступ ко всем файлам. Нужно более надёжное решение, которое переживает отказы серверов и легко масштабируется. К счастью, эта задача давно решена. Обе проблемы закрывает [Blob Storage](/lessons/sd-prep/key-technologies).

#### Хорошее решение: хранение файла в Blob Storage

##### Подход

Лучше хранить файл в сервисе Blob Storage, таком как Amazon S3 или Google Cloud Storage. Когда пользователь загружает файл на наш backend, мы отправляем его прямо в Blob Storage, а метаданные сохраняем в нашей database. В Blob Storage можно хранить (практически) неограниченное число файлов, потому что масштабирование он берёт на себя. Он и надёжнее: если наш сервер упадёт, доступ к файлам не пропадёт. Кроме того, можно использовать возможности Blob Storage, например lifecycle policies для автоматического удаления старых файлов и versioning для отслеживания изменений файлов, если это понадобится (хотя в рамках этой задачи это вне scope).

![Иллюстрация](/content/dropbox/c610bd7985.svg)

Хранение файла в Blob Storage

##### Сложности

Первая сложность этого подхода в том, что он сложнее. Нужно интегрироваться с сервисом Blob Storage и обработать случай, когда файл загружен, а метаданные не сохранены. А также случай, когда метаданные сохранены, а файл не загружен. Решить это можно транзакционным подходом: метаданные сохраняются, только если файл успешно загружен, и наоборот.

Вторая: при таком подходе (как на схеме выше) файл формально загружается дважды — один раз на наш backend и один раз в Blob Storage. Это избыточно. Решение — позволить пользователю загружать файл напрямую в сервис Blob Storage.

#### Отличное решение: загрузка файла напрямую в Blob Storage

##### Подход

Лучший вариант — позволить пользователю загружать файл в Blob Storage прямо с клиента. Это быстрее и дешевле, чем сначала загружать файл на наш backend. Мы можем использовать presigned URL: сгенерировать URL, по которому пользователь загрузит файл напрямую в сервис Blob Storage. Когда файл загружен, Blob Storage отправит уведомление нашему backend, и мы сохраним метаданные.

Presigned URL — это URL, дающие пользователю право загрузить файл в определённое место в сервисе Blob Storage. Мы генерируем presigned URL и отправляем его пользователю, когда он хочет загрузить файл. Если раньше наш API для загрузки был POST на /files, то теперь это трёхшаговый процесс:

1. Запросить у нашего backend pre-signed URL (он генерирует его через S3 SDK) и сохранить метаданные файла в нашей database со статусом "uploading."

   ```
   POST /files/presigned-url -> PresignedUrl
   Request:
   {
     FileMetadata
   }
   ```
2. Использовать presigned URL, чтобы загрузить файл в Blob Storage прямо с клиента. Это PUT-запрос напрямую на presigned URL, где тело запроса — это файл.
3. Когда файл загружен, сервис Blob Storage отправит уведомление нашему backend через [S3 Notifications](https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventNotifications.html). Затем наш backend обновит метаданные файла в database, выставив статус "uploaded".

![Иллюстрация](/content/dropbox/f3d27d1d88.svg)

Пользователь должен иметь возможность загружать файл с любого устройства

###### Паттерн: работа с большими blob

Прямая загрузка через presigned URL — классический пример эффективной передачи больших файлов. Этот паттерн (обход application-серверов при передаче данных, подписанные URL для безопасности и chunked uploads для надёжности) встречается во многих распределённых системах, которые загружают и скачивают большие файлы.

[Изучить этот паттерн](/lessons/patterns/large-blobs)

### 2) Пользователь должен иметь возможность скачивать файл с любого устройства

Следующий шаг — убедиться, что пользователи могут скачивать сохранённые файлы. Как и с загрузкой, подходов здесь несколько.

#### Плохое решение: скачивание через File Server

##### Подход

Чаще всего кандидаты предлагают сначала скачать файл из Blob Storage на наш backend-сервер, а затем ещё раз — с backend на клиент.

##### Сложности

Конечно, такое решение неоптимально: файл скачивается дважды, что и медленно, и дорого. Решить это можно так же, как с загрузкой: позволить пользователю скачивать файл напрямую из сервиса Blob Storage.

#### Хорошее решение: скачивание из Blob Storage

##### Подход

Лучше позволить пользователю скачивать файл напрямую из Blob Storage. Мы можем использовать presigned URL, чтобы сгенерировать URL, по которому пользователь скачает файл прямо из Blob Storage. Как и при загрузке, presigned URL даёт пользователю право скачать файл из определённого места в сервисе Blob Storage в течение ограниченного времени.

1. Запросить у нашего backend presigned URL для скачивания

```
GET /files/{fileId}/presigned-url -> PresignedUrl
```

2. Использовать presigned URL, чтобы скачать файл из сервиса Blob Storage напрямую на клиент.

![Иллюстрация](/content/dropbox/05a18ae5c0.svg)

Пользователь должен иметь возможность скачивать файл с любого устройства

##### Сложности

Хотя решение почти оптимально, его главное ограничение в том, что оно всё ещё может быть медленным для большой географически распределённой аудитории. Ваш Blob Storage находится в одном регионе, поэтому пользователи, далёкие от этого региона, будут скачивать медленнее. Решить это можно с помощью [content delivery network (CDN)](/lessons/sd-prep/key-technologies), который кэширует файл ближе к пользователю.

#### Отличное решение: скачивание через CDN

##### Подход

Лучший вариант — использовать content delivery network (CDN), чтобы кэшировать файл ближе к пользователю. CDN — это сеть серверов, распределённых по всему миру, которые кэшируют файлы и отдают их пользователям с ближайшего сервера. Это снижает latency и ускоряет скачивание.

Когда пользователь запрашивает файл, CDN может отдать его с ближайшего к пользователю сервера. Это намного быстрее, чем отдавать файл с нашего backend или из сервиса Blob Storage.

Для безопасности, как и с S3 presigned URL, мы можем сгенерировать URL, по которому пользователь скачает файл из CDN. Этот URL даёт пользователю право скачать файл из определённого места в CDN в течение ограниченного времени. Подробнее об этом — в наших [deep dives по безопасности](/lessons/breakdowns/dropbox).

![Иллюстрация](/content/dropbox/875658bb30.svg)

Пользователь должен иметь возможность скачивать файл с любого устройства

##### Сложности

CDN — относительно дорогое удовольствие. Поэтому обычно стараются разумно выбирать, какие файлы кешировать и на какой срок. С помощью cache control header можно указать, как долго файл должен лежать в CDN. Ещё можно добавить механизм cache invalidation, чтобы убирать файлы из CDN при их обновлении или удалении. Так в кеше остаются только часто запрашиваемые файлы, и мы не тратим деньги на кеширование тех, к которым почти не обращаются.

### 3) Пользователи должны иметь возможность делиться файлом с другими пользователями

Чтобы закрыть функциональные требования, нужно поддержать шаринг файлов с другими пользователями. Реализуем это по аналогии с Google Drive: достаточно ввести email пользователя, с которым хочешь поделиться файлом. Будем считать, что пользователи уже аутентифицированы.

Главный вопрос на интервью здесь — как сделать этот процесс быстрым и эффективным. Давай разберём по шагам.

#### Плохое решение: добавить sharelist в метаданные

##### Подход

Хорошее начало — просто добавить список пользователей, у которых есть доступ к файлу, прямо в метаданные файла. Когда пользователь делится файлом, мы добавляем адресата в список. Когда пользователь скачивает файл, мы проверяем, есть ли он в списке. Простой и рабочий подход.

```
{
  "id": "123",
  "name": "file.txt",
  "size": 1000,
  "mimeType": "text/plain",
  "uploadedBy": "user1",
  "sharelist": ["user2", "user3"]
}
```

##### Сложности

Когда пользователь открывает наш сайт, он ожидает увидеть список всех своих файлов и файлов, которыми с ним поделились. Получить список его собственных файлов легко: достаточно запроса по индексу на uploadedBy. А вот список файлов, которыми поделились с ним, при таком подходе получается медленно. Нам пришлось бы просканировать sharelist каждого файла и проверить, есть ли там этот пользователь.

#### Хорошее решение: cache для ускорения получения sharelist

##### Подход

Подход получше: помимо sharelist в метаданных файла, держать в cache список с обратной связью. Это отображение «пользователь → список файлов, которыми с ним поделились». Тогда, когда пользователь открывает наш сайт, мы быстро получаем список расшаренных ему файлов, просто найдя его userId в cache sharedFiles.

Запись в cache будет простой парой «ключ-значение», например такой:

```
user1:["fileId1", "fileId2"]
```

##### Сложности

Нужно держать список sharedFiles в синхронизации с sharelist в метаданных файла. Лучший способ — хранить это отображение «пользователь → список файлов» в той же базе данных и обновлять и sharelist, и список sharedFiles в одной транзакции.

#### Отличное решение: отдельная таблица для шаринга

##### Подход

Ещё один вариант — полностью нормализовать данные. Для этого создаём новую таблицу, которая связывает userId с fileId, где fileId — файл, которым поделились с данным пользователем. Тогда, когда пользователь открывает наш сайт, мы быстро получаем список расшаренных ему файлов, запросив из таблицы SharedFiles все записи с его userId.

Таблица SharedFiles будет выглядеть так:

```
| userId (Partition Key) | fileId (Sort Key) |
|-------------|-------------|
| user1       | fileId1     |
| user1       | fileId2     |
| user2       | fileId3     |
```

Здесь userId и fileId вместе образуют составной первичный ключ, что позволяет делиться с одним пользователем несколькими файлами. В терминах DynamoDB ты используешь userId как partition key, а fileId как sort key. В SQL-базе создаёшь составной первичный ключ по обеим колонкам.

В этом дизайне sharelist в метаданных файла больше не нужен. Достаточно запросить из таблицы SharedFiles все файлы, у которых userId совпадает с userId запрашивающего пользователя, и синхронизировать sharelist со списком sharedFiles уже не требуется.

##### Сложности

Такой запрос чуть менее эффективен, чем в предыдущем подходе, потому что теперь мы обращаемся по индексу, а не делаем простой key-value lookup. Но компромисс, скорее всего, оправдан: больше не нужно синхронизировать sharelist со списком sharedFiles.

### 4) Пользователи могут автоматически синхронизировать файлы между устройствами

Наконец, нужно сделать так, чтобы файлы автоматически синхронизировались между разными устройствами. На высоком уровне это работает так: копия файла хранится на каждом клиентском устройстве (локально) и в удалённом хранилище (то есть в «облаке»). Поэтому синхронизировать нужно в двух направлениях:

1. Local -> Remote
2. Remote -> Local

**Local -> Remote**

Когда пользователь изменяет файл на своей локальной машине, нужно синхронизировать эти изменения с удалённым сервером. Мы считаем удалённый сервер источником истины, поэтому важно как можно скорее привести его в консистентное состояние, чтобы другие локальные устройства узнали, что появились изменения, которые нужно забрать.

Для этого нужен клиентский sync agent, который:

1. Отслеживает изменения в локальной папке Dropbox с помощью файловых событий конкретной ОС (например, FileSystemWatcher в Windows или FSEvents в macOS)
2. При обнаружении изменения ставит изменённый файл в локальную очередь на загрузку
3. Затем через наш upload API отправляет изменения на сервер вместе с обновлёнными метаданными
4. Конфликты разрешаются по стратегии «last write wins»: если два пользователя редактируют один и тот же файл, сохранится самая свежая правка

Версионирование выходит за рамки этого разбора, но учти: обычно единственный экземпляр файла не перезаписывают. Вместо этого добавляют новый файл (или хотя бы новые chunks) и обновляют номер версии и указатель в метаданных.

**Remote -> Local**

В обратном направлении каждый клиент должен знать, когда на удалённом сервере происходят изменения, чтобы забрать их к себе.

Есть два основных подхода:

1. **Polling**: клиент периодически спрашивает сервер: «Что-нибудь изменилось с момента моей последней синхронизации?» Сервер обращается к БД и проверяет, есть ли у файлов, за которыми следит этот пользователь, timestamp updatedAt новее, чем время последней синхронизации. Это просто, но изменения обнаруживаются медленно, а если ничего не изменилось, мы впустую тратим bandwidth.
2. **WebSocket или SSE**: сервер держит открытое соединение с каждым клиентом и присылает уведомления, когда происходят изменения. Это сложнее, зато обновления приходят в реальном времени.

Для Dropbox можно использовать гибридный подход. Каждый клиент поддерживает одно WebSocket-соединение (или SSE) с сервером: не по одному на файл, а по одному на устройство/сессию. По этому соединению сервер присылает уведомления об изменениях файлов, к которым у пользователя есть доступ. Гибридность проявляется в том, как мы обеспечиваем надёжность:

* **Активные уведомления**: сервер отправляет события об изменениях через WebSocket-соединение в реальном времени, по мере их возникновения. Это даёт почти мгновенную синхронизацию любого изменения файла.
* **Периодический polling как страховка**: WebSocket-соединения могут обрываться, а сообщения — теряться. Чтобы это учесть, клиент также периодически (например, раз в несколько минут) опрашивает сервер через GET /files/changes?since=\{timestamp\}, чтобы подхватить пропущенные изменения. Так мы гарантируем eventual consistency, даже если WebSocket-соединение временно прерывалось.

Гибридный подход берёт лучшее из обоих миров: обновления в реальном времени через push-уведомления и polling как надёжный fallback, который гарантирует, что ни одно изменение не потеряется.

Final

* **Uploader**: это клиент, который загружает файл. Это может быть браузер, мобильное приложение или десктопное приложение. Он же отвечает за то, чтобы проактивно находить локальные изменения и отправлять обновления в удалённое хранилище.

File service не обрабатывает загрузку и скачивание файлов напрямую; это control plane, который координирует работу клиента и S3.
* **File Metadata DB**: здесь мы храним метаданные файлов: имя файла, размер, MIME type и пользователя, который загрузил файл. Также здесь лежит таблица shared files, которая сопоставляет файлы с пользователями, у которых есть к ним доступ. По этой таблице мы проверяем права, когда пользователь пытается скачать файл.
* **S3**: здесь файлы хранятся физически. Мы загружаем файлы прямо в S3 по presigned URL, которые генерирует file service.
* **CDN**: это content delivery network (например, CloudFront), которая кеширует файлы рядом с пользователем, чтобы снизить latency. Для скачивания вместо прямого presigned URL в S3 file service генерирует CDN signed URL. CDN забирает файл из S3 при первом запросе (cache miss) и отдаёт его с edge при последующих (cache hit). Это значит, что пользователи скачивают файлы с ближайшего edge-узла CDN, а не напрямую из региона S3.

### 1) Как поддержать большие файлы?

Первое, о чём стоит подумать в случае больших файлов, — это пользовательский опыт. Есть два ключевых момента, которые должны сразу бросаться в глаза и в итоге определять твой дизайн:

1. **Индикатор прогресса**: пользователи должны видеть прогресс загрузки, чтобы понимать, что всё работает, и сколько это займёт времени.
2. **Возобновляемая загрузка**: пользователи должны иметь возможность приостанавливать и возобновлять загрузку. Если пропало соединение или закрылся браузер, они должны продолжить с того места, где остановились, а не загружать заново 49GB, которые могли уже уйти до обрыва.

В каком-то смысле это суть задачи, и именно на ней я обычно трачу больше всего времени с кандидатами на реальном интервью.

Прежде чем углубляться в решения, давай отметим ограничения, с которыми сталкивается загрузка большого файла одним POST-запросом.

* **Timeouts**: у веб-серверов и клиентов обычно есть настройки timeout, чтобы не ждать ответа бесконечно. Один POST-запрос с файлом на 50GB легко может их превысить. Более того, это подходящий момент для быстрой прикидки на интервью. Если у нас файл 50GB, а скорость интернета 100Mbps, сколько будет длиться загрузка? 50GB \* 8 bits/byte / 100Mbps = 4000 секунд, затем 4000 секунд / 60 секунд/минуту / 60 минут/час = 1.11 часа. Это очень долго ждать без какого-либо ответа от сервера.
* **Ограничения браузера и сервера**: в большинстве случаев загрузить файл на 50GB одним POST-запросом вообще невозможно из-за ограничений, настроенных в браузере или на сервере. И браузеры, и веб-серверы часто ограничивают размер тела запроса. Хотя «сырые» веб-серверы вроде Apache и NGINX можно настроить на приём больших payload, у большинства современных сервисов, таких как Amazon API Gateway, жёсткие лимиты намного ниже, и увеличить их нельзя. В случае Amazon API Gateway, который мы используем в нашем дизайне, это всего 10MB.
* **Сетевые сбои**: большие файлы более уязвимы к сетевым сбоям. Если пользователь загружает файл на 50GB и соединение обрывается, ему придётся начинать загрузку с нуля.
* **Пользовательский опыт**: пользователи фактически не видят прогресса загрузки. Они не знают, сколько она займёт и работает ли вообще.

Чтобы обойти эти ограничения, можно использовать технику под названием «chunking»: разбить файл на небольшие части и загружать их по одной (или параллельно, в зависимости от пропускной способности сети). Chunking нужно делать на клиенте, чтобы файл был разбит на части до отправки на сервер (в нашем случае в S3). Очень частая ошибка кандидатов — разбивать файл на chunks на сервере, что по сути сводит смысл на нет: чтобы файл вообще попал на сервер, его всё равно приходится загружать целиком. Обычно мы разбиваем файл на части по 5-10 MB, но размер можно подстраивать под состояние сети и размер файла.

С chunks показать пользователю индикатор прогресса довольно просто. Достаточно отслеживать прогресс каждого chunk и обновлять progress bar по мере успешной загрузки каждого из них. Это намного лучше для пользователя, чем час смотреть на крутящийся индикатор.

Следующий вопрос: **как обеспечить возобновляемую загрузку?** Нам нужно отслеживать, какие chunks уже загружены, а какие нет. Для этого можно сохранять состояние загрузки в базе данных, а именно в таблице FileMetadata. Обновим схему FileMetadata, добавив поле chunks.

```
{
  "id": "123",
  "name": "file.txt",
  "size": 1000,
  "mimeType": "text/plain",
  "uploadedBy": "user1",
  "status": "uploading",
  "chunks": [
    {
      "id": "chunk1",
      "status": "uploaded"
    },
    {
      "id": "chunk2",
      "status": "uploading"
    },
    {
      "id": "chunk3",
      "status": "not-uploaded"
    }
  ]
}
```

Когда пользователь возобновляет загрузку, мы можем проверить поле chunks и понять, какие chunks уже загружены, а какие нет. После этого можно начать загружать только те chunks, которые ещё не загружены. Так пользователю не придётся начинать загрузку с нуля, если пропало соединение или закрылся браузер.

**Но как гарантировать, что поле chunks синхронизировано с реально загруженными chunks?**

Есть два подхода.

#### Хорошее решение: обновление по PATCH-запросу от клиента

##### Подход

Самый очевидный подход — поручить клиенту оркестрировать статусы chunks. Тогда flow выглядит так:

1. Клиент берёт файл, разбивает его на chunks и загружает их напрямую в S3.
2. S3 отвечает на загрузку каждого chunk сообщением об успехе.
3. После успеха клиент отправляет PATCH-запрос на наш backend, чтобы обновить поле chunks в таблице FileMetadata.

```
PATCH /files/{fileId}/chunks
Request:
{
  "chunks": [
    {
      "id": "chunk1",
      "status": "uploaded"
    },
  ]
}
```

##### Сложности

Проблема в том, что мы доверяем клиенту поддерживать синхронизацию поля chunks с реально загруженными chunks, а это риск для безопасности. Злоумышленник может отправить PATCH-запрос на наш backend и пометить все chunks как загруженные, фактически их не загружая. Хотя в этом случае он сможет испортить скачивание только своего файла, а не чужого, это всё равно риск, который может привести к неконсистентному состоянию, а его сложно отлаживать. Эту проблему можно решить, используя серверный подход, который гарантирует, что поле 'chunks' остаётся синхронизированным с реально загруженными chunks.

#### Отличное решение: серверная верификация chunks

##### Подход

Лучший подход — реализовать серверную верификацию загрузки chunks с помощью ETag. Поскольку S3 event notifications не срабатывают для отдельных частей multipart upload (только когда готов весь объект), нам нужно напрямую использовать multipart upload API в S3.

Каждый chunk получает ETag после успешной загрузки, и клиент может передать его в PATCH-запросе на наш backend. Затем backend может проверить эти ETag, вызвав S3 ListParts API, что позволяет эффективно валидировать сразу несколько chunks. Такой подход балансирует между удобством для пользователя и целостностью данных: мы принимаем обновления от клиента, чтобы показывать прогресс в реальном времени и давать мгновенную обратную связь, но периодически проверяем статус chunks на сервере, прежде чем пометить весь файл как «uploaded».

Короче говоря, доверяй, но проверяй.

Теперь поговорим о том, как идентифицировать файл и chunk. Когда ты пытаешься возобновить загрузку, самые первые вопросы такие: (1) Пытался ли я уже загружать этот файл? и (2) Если да, какие chunks я уже загрузил? Чтобы ответить на первый вопрос, нельзя наивно полагаться на имя файла. Два разных пользователя (или даже один и тот же) могут загрузить файлы с одинаковым именем. Вместо этого нужен уникальный идентификатор, который вычисляется из содержимого файла. Он называется fingerprint.

[Fingerprint](https://en.wikipedia.org/wiki/Fingerprint_(computing)) — это математическое вычисление, которое генерирует уникальное hash-значение на основе содержимого файла. Это значение, которое часто получают с помощью криптографических hash-функций вроде SHA-256, служит надёжным и уникальным идентификатором содержимого файла независимо от его имени и источника загрузки. Вычислив fingerprint, мы можем эффективно определить, загружался ли этот файл раньше (дедупликация) и можно ли возобновить незавершённую загрузку.

Обрати внимание: fingerprint идентифицирует *содержимое* файла, а не *запись* о файле. Два разных пользователя, загружающих один и тот же файл, получат одинаковый fingerprint. На практике fileId в таблице метаданных должен быть уникальным идентификатором (например, UUID), а fingerprint хранится в отдельном поле и используется для проверок дедупликации и возобновления загрузки.

Для возобновляемых загрузок нужно не только считать fingerprint всего файла, но и генерировать fingerprint для каждого отдельного chunk. Fingerprint на уровне chunk позволяет системе точно определить, какие части файла уже переданы.

Сделаем шаг назад и соберём всё вместе. Вот что происходит, когда пользователь загружает большой файл:

1. Клиент разбивает файл на части (chunk) по 5-10MB и считает fingerprint для каждого chunk. Он также считает fingerprint для всего файла, который используется для проверки дубликатов и возможности возобновить загрузку.
2. Клиент отправляет запрос, чтобы проверить, существует ли у этого пользователя файл с таким же fingerprint. Если существует и его статус "uploading", клиент может возобновить загрузку, получив текущие статусы chunk.
3. Если файла нет, клиент отправляет POST-запрос, чтобы инициировать multipart upload. Backend вызывает S3 API CreateMultipartUpload, чтобы получить uploadId, генерирует presigned URL для каждой части, сохраняет метаданные файла в таблице FileMetadata со статусом "uploading" и возвращает uploadId вместе с presigned URL для каждого chunk.
4. Затем клиент загружает каждый chunk в S3 по соответствующему presigned URL (для каждой части нужен собственный presigned URL с uploadId и partNumber). После загрузки каждого chunk клиент отправляет на наш backend PATCH-запрос со статусом chunk и ETag. Наш backend может проверить загрузку chunk через S3 API ListParts, а затем обновить поле chunks в таблице FileMetadata, пометив chunk как "uploaded".
5. Когда все chunk в нашем массиве chunks помечены как "uploaded", backend вызывает S3 API [CompleteMultipartUpload](https://docs.aws.amazon.com/AmazonS3/latest/API/API_CompleteMultipartUpload.html) со списком номеров частей и ETag. Это говорит S3 собрать все части в один объект. Только после того как S3 подтвердит успешную сборку, backend обновляет таблицу FileMetadata, помечая файл как "uploaded".

На протяжении всего процесса клиент отвечает за отслеживание прогресса загрузки и обновление интерфейса, чтобы пользователь видел, как далеко он продвинулся и сколько осталось.

Подход, который мы только что описали, не новый. Эту задачу уже решили облачные провайдеры хранилищ вроде Amazon S3. У них есть функция [Multipart Upload](https://docs.aws.amazon.com/AmazonS3/latest/userguide/mpuoverview.html), которая позволяет загружать большие объекты по частям. Это ровно то, что мы описали. Клиент разбивает файл на части и загружает каждую в S3. Затем S3 объединяет части в один объект. Есть даже удобный [JavaScript SDK](https://aws.amazon.com/blogs/compute/uploading-large-objects-to-amazon-s3-using-multipart-upload-and-transfer-acceleration/), который берёт на себя всё разбиение на chunk и загрузку.

При multipart upload в S3 event notifications срабатывают только когда весь multipart upload завершён (когда все части собраны), а не для загрузки отдельных частей. Чтобы отслеживать прогресс по отдельным частям, нужно использовать S3 API ListParts, который возвращает все загруженные части с их ETag для незавершённой загрузки.

На практике при проектировании системы вроде Dropbox ты бы положился на этот API. Однако почти наверняка на интервью не получится отделаться фразой «я бы использовал S3 Multipart Upload API», не объяснив, как он работает и как бы ты реализовал это сам, если бы пришлось. При этом дать интервьюеру понять, что ты знаком с multipart upload, всё же стоит: это показывает практический опыт.

Можно задаться вопросом, нужны ли нам тогда и chunked-скачивания. Не совсем. После вызова CompleteMultipartUpload S3 собирает все части в один объект. С этого момента скачивание работает как с обычным файлом. Клиент получает один presigned URL (или signed URL от CDN) и скачивает файл целиком. Для очень больших файлов S3 и HTTP нативно поддерживают [Range requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Range_requests), которые позволяют клиенту скачивать разные диапазоны байт параллельно или возобновить прерванное скачивание без повторного начала. Клиенту не нужно ничего знать о первоначальных границах chunk.

### 2) Как сделать загрузку, скачивание и синхронизацию максимально быстрыми?

Мы уже затронули несколько способов ускорить скачивание и загрузку, но можно сделать ещё больше, чтобы система работала максимально быстро. Напомню: для скачивания мы использовали CDN, чтобы кешировать файл ближе к пользователю. Благодаря этому файлу не нужно проделывать такой длинный путь до пользователя, что снижает latency и ускоряет скачивание. Для загрузки chunking, помимо пользы для возобновляемых загрузок, также заметно ускоряет сам процесс. Пропускная способность фиксирована (иными словами, труба имеет ограниченный размер), но chunking позволяет выжать максимум из того, что есть. Отправляя несколько chunk параллельно и подбирая размер chunk под состояние сети, мы можем максимально использовать доступную пропускную способность. Тот же подход с chunking можно применить и для синхронизации файлов. Когда файл меняется, нужно синхронизировать только те chunk, которые действительно изменились, а не весь файл, и синхронизация становится гораздо быстрее.

Стоит отдельно отметить один нюанс: если использовать chunk фиксированного размера (например, каждые 5MB), то вставка всего одного байта ближе к началу файла сдвигает границы всех последующих chunk, и *каждый* chunk после правки получает другой fingerprint. Из-за этого delta sync становится почти бесполезным. Решение — [Content-Defined Chunking (CDC)](https://en.wikipedia.org/wiki/Rolling_hash), где границы chunk определяются содержимым файла с помощью rolling hash (например, Rabin fingerprinting). При CDC небольшая правка затрагивает только chunk, непосредственно окружающие изменение, а подавляющее большинство chunk остаются прежними. Именно так системы вроде Dropbox на практике добиваются эффективного delta sync.

Помимо того, что мы уже обсудили, **можно также использовать сжатие, чтобы ускорить и загрузку, и скачивание**. Сжатие уменьшает размер файла, а значит, нужно передать меньше байт. Поскольку мы загружаем напрямую в S3, сжатие целиком происходит на стороне клиента: клиент сжимает файл перед загрузкой, а сжатые данные хранятся в S3 как есть. При скачивании клиент распаковывает файл после получения. Так наш backend остаётся вне пути данных, а выигрыш от меньшего объёма передачи сохраняется.

Но к сжатию нужно подходить с умом. Оно полезно, только если выигрыш во времени от передачи меньшего числа байт перевешивает время на сжатие и распаковку файла. Для некоторых типов файлов, особенно медиа вроде изображений и видео, степень сжатия настолько мала, что тратить время на сжатие и распаковку не стоит. Если взять любой .png с твоего компьютера и сжать его, то тебе повезёт, если размер уменьшится больше чем на пару процентов, так что это не окупается. У текстовых файлов, напротив, степень сжатия гораздо выше, и в зависимости от состояния сети это вполне может быть оправданно. Текстовый файл на 5GB может сжаться до 1GB или даже меньше, в зависимости от содержимого.

В итоге тебе стоит реализовать на клиенте логику, которая решает, сжимать ли файл перед загрузкой, исходя из типа файла, его размера и состояния сети.

Существует несколько алгоритмов сжатия, которые можно использовать для файлов. Самые распространённые — [Gzip](https://en.wikipedia.org/wiki/Gzip), [Brotli](https://en.wikipedia.org/wiki/Brotli) и [Zstandard](https://en.wikipedia.org/wiki/Zstandard). У каждого из них свои компромиссы между степенью сжатия и скоростью. Gzip используется чаще всех и поддерживается везде. Brotli обычно сжимает лучше, чем Gzip (особенно текст), и поддерживается всеми современными браузерами (Chrome, Firefox, Edge, Safari). Zstandard (zstd) даёт отличный баланс скорости и степени сжатия: он сжимает и распаковывает заметно быстрее Gzip при сопоставимой степени сжатия, и его можно настраивать в широком диапазоне компромиссов между скоростью и степенью сжатия. Для системы вроде Dropbox, где сжатие происходит на клиенте, Zstandard — хороший выбор благодаря высокой скорости сжатия, но лучший алгоритм зависит от конкретного сценария и от того, что поддерживает клиент.

Важный факт о сжатии: если нужно шифрование, всегда сжимай данные до шифрования. Шифрование по своей природе привносит в файл случайность, из-за чего его трудно сжать. Если сжать данные до шифрования, степень сжатия получится намного выше.

### 3) Как обеспечить безопасность файлов?

Безопасность — критически важный аспект любой системы хранения файлов. Нужно убедиться, что файлы защищены и доступны только авторизованным пользователям.

1. **Encryption in Transit**: Для большинства кандидатов это очевидно. Нужно использовать HTTPS, чтобы шифровать данные при передаче между клиентом и сервером. Это стандартная практика, и она поддерживается всеми современными браузерами.
2. **Encryption at Rest**: Файлы также нужно шифровать, когда они хранятся в S3. Это встроенная возможность S3, и включить её просто. При загрузке файла в S3 можно указать, что его нужно зашифровать. Тогда S3 зашифрует файл уникальным ключом и сохранит ключ отдельно от файла. Так даже если кто-то получит доступ к файлу, расшифровать его без ключа он не сможет. Подробнее о шифровании в S3 можно прочитать [здесь](https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingServerSideEncryption.html).
3. **Access Control**: Наш shareList или отдельная таблица/cache для шаринга — это базовый ACL. Как мы обсуждали ранее, ссылки для скачивания мы отдаём только авторизованным пользователям.

Но что будет, если авторизованный пользователь передаст ссылку для скачивания неавторизованному? Например, авторизованный пользователь может намеренно или случайно опубликовать ссылку на скачивание на публичном форуме или в соцсетях, и нам нужно убедиться, что неавторизованные пользователи не смогут скачать файл.

Здесь снова пригождаются signed URL, о которых мы говорили раньше. Когда пользователь запрашивает ссылку для скачивания, мы генерируем signed URL, который действителен лишь короткое время (например, 5 минут). Этот signed URL отправляется пользователю, и он может скачать по нему файл. Стоит отметить, что signed URL — это bearer-токены: любой, у кого есть действующая, не истёкшая ссылка, может скачать файл. Короткое окно действия ограничивает риск, но полностью не мешает передаче ссылки другим. Для сценариев с повышенными требованиями к безопасности можно добавить дополнительные ограничения, например привязку к IP, или потребовать использовать signed URL вместе с аутентификационными cookie.

Они также работают с современными CDN, такими как CloudFront, и являются возможностью S3. Вот как это устроено:

1. Генерация: signed URL генерируется на сервере и включает подпись, которая обычно учитывает путь URL, временну́ю метку истечения срока действия и, возможно, другие ограничения (например, IP-адрес). В случае CloudFront подпись создаётся с помощью приватного ключа поставщика контента.
2. Распространение: signed URL передаётся авторизованному пользователю, который может использовать его для прямого доступа к нужному ресурсу через CDN.
3. Проверка: когда CDN получает запрос с signed URL, он проверяет подпись с помощью соответствующего публичного ключа (зарегистрированного в CloudFront), а также срок действия и любые другие ограничения. Если подпись корректна и срок действия URL не истёк, CDN отдаёт запрошенный контент. Если нет, доступ запрещается.

### Mid-level

**Ширина против глубины:** Mid-level кандидат в основном сосредоточен на ширине (80% против 20%). Ты должен уметь набросать high-level design, который покрывает определённые тобой функциональные требования, но многие компоненты будут для тебя абстракциями, с которыми ты знаком лишь поверхностно.

**Проверка основ:** Интервьюер потратит какое-то время на проверку основ, чтобы убедиться, что ты знаешь, что делает каждый компонент твоей системы. Например, если ты добавляешь API Gateway, будь готов, что тебя могут спросить, что он делает и как работает (на высоком уровне). Короче говоря, интервьюер ничего не принимает на веру в отношении твоих знаний.

**Сочетание лидерства и ведомой роли:** Ты должен вести интервью, особенно на ранних этапах, но интервьюер не ждёт, что ты будешь сам с высокой точностью замечать проблемы в своём дизайне. Поэтому вполне разумно, что на поздних этапах он перехватит инициативу и будет вести интервью, проверяя твой дизайн на прочность.

**Планка для Dropbox:** В этой задаче кандидат уровня E4 чётко определит API endpoints и модель данных и придёт к high-level design, который работает для всех сценариев: загрузки, скачивания и шаринга. Я не жду, что кандидаты знают про pre-signed URL или про загрузку в S3 и скачивание из S3 напрямую, и не жду, что они сразу подумают о chunking. Однако я ожидаю, что, когда я задаю наводящие вопросы вроде «Сейчас ты загружаешь файл дважды, как этого избежать?» или «Как показать пользователю прогресс и при этом позволить возобновить загрузку?», кандидат способен порассуждать над проблемой и прийти к решению в диалоге.

### Senior

**Глубина экспертизы**: От senior-кандидата ждут более глубоких знаний: примерно 60% ширины и 40% глубины. Это значит, что ты должен уметь уходить в технические детали в тех областях, где у тебя есть практический опыт. Важно показать глубокое понимание ключевых концепций и технологий, relevant для задачи.

**Продвинутый system design**: Ты должен быть знаком с продвинутыми принципами system design. Например, знать, как использовать blob storage для больших файлов или как внедрить CDN для более быстрого скачивания. Ты должен уметь обсуждать компромиссы разных дизайнерских решений и обосновывать свой выбор опытом.

**Объяснение архитектурных решений**: Ты должен чётко формулировать плюсы и минусы разных архитектурных вариантов, особенно их влияние на scalability, производительность и сопровождаемость. Ты обосновываешь свои решения и объясняешь компромиссы, связанные с твоим выбором.

**Решение проблем и проактивность**: Ты должен демонстрировать сильные навыки решения проблем и проактивный подход. Это включает умение предвидеть возможные сложности в своих дизайнах и предлагать улучшения. Нужно уверенно находить и устранять bottleneck, оптимизировать производительность и обеспечивать надёжность системы.

**Планка для Dropbox:** В этой задаче от кандидатов уровня E5 ждут, что они быстро пройдут начальный high-level design, чтобы успеть подробно обсудить, как обрабатывать загрузку больших файлов в частности. Я ожидаю от них большей проактивности, чем от mid-level кандидатов: они продумывают несколько вариантов и приходят к разумному решению. Хотя это не строго обязательно, у многих кандидатов есть опыт работы с загрузкой файлов, и они могут напрямую рассказать о конкретных API (например, multipart upload) и о том, как они работают.

### Staff+

**Упор на глубину**: От staff+ кандидата ждут глубокого погружения в нюансы system design: я ищу примерно 40% ширины и 60% глубины в твоём понимании. На этом уровне важно показать, что даже если ты не решал именно эту задачу, ты решил достаточно задач в реальном мире, чтобы уверенно спроектировать решение, опираясь на свой опыт.

Ты должен знать, какие технологии использовать, причём не только в теории, но и на практике, и уметь опираться на прошлый опыт, чтобы объяснить, как они применяются для решения конкретных задач. Интервьюер знает, что ты разбираешься в мелочах (REST API, нормализация данных и т. д.), поэтому пройдись по ним на высоком уровне, чтобы осталось время на самое интересное.

**Высокая проактивность**: на этом уровне ожидается исключительная проактивность. Ты должен уметь самостоятельно находить и решать проблемы, показывая, что видишь и разбираешь ключевые сложности в system design. Это значит не просто реагировать на проблемы по мере их появления, а предвидеть их и заранее внедрять решения. Интервьюер должен вмешиваться только чтобы сфокусировать разговор, а не чтобы направлять его.

**Практическое применение технологий**: ты должен хорошо разбираться в практическом применении разных технологий. Твой опыт должен вести разговор: он должен показывать, что ты понимаешь, как различные инструменты и системы настраиваются в реальных сценариях под конкретные требования.

**Решение сложных задач и принятие решений**: навыки решения задач должны быть на высшем уровне. Это значит не только уметь справляться со сложными техническими вызовами, но и принимать обоснованные решения с учётом scalability, performance, reliability и сопровождения.

**Продвинутый system design и scalability**: твой подход к system design должен быть продвинутым, с упором на scalability и reliability, особенно под высокой нагрузкой. Сюда входит глубокое понимание распределённых систем, load balancing, стратегий caching и других продвинутых концепций, необходимых для построения надёжных масштабируемых систем.

**Планка для Dropbox:** от Staff-кандидата ожидают высокой глубины и качества решений, особенно для сложных сценариев, обсуждавшихся выше. Исключительные кандидаты подробно разбирают каждую из упомянутых тем и могут даже сами повернуть разговор в другую сторону, уделив много внимания теме, которая им особенно интересна или актуальна. От них также ждут уверенного понимания trade-offs между разными решениями и умения чётко их формулировать, общаясь с интервьюером как с равным.

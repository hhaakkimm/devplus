## Разбор задачи

**📄 Что такое [Google Docs](https://docs.google.com)?**
Google Docs — это браузерный редактор документов для совместной работы. Пользователи могут создавать документы с форматированным текстом и работать над ними вместе с другими в real-time.

В этом разборе мы спроектируем систему, которая поддерживает базовую функциональность Google Docs, и заглянем в WebSocket и системы совместного редактирования. Начнём с требований (как на настоящем интервью), а затем перейдём к полному дизайну по нашему [Delivery Framework](/lessons/sd-prep/delivery).

### [Функциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Пользователи должны иметь возможность создавать новые документы.
2. Несколько пользователей должны иметь возможность одновременно редактировать один и тот же документ.
3. Пользователи должны видеть изменения друг друга в real-time.
4. Пользователи должны видеть позицию курсора и присутствие других пользователей.

**Вне рамок (below the line)**

1. Сложная структура документа. Будем считать, что у нас простой текстовый редактор.
2. Права доступа и уровни совместной работы (например, кто имеет доступ к документу).
3. История документа и версионирование.

Каковы нефункциональные требования к системе?

### [Нефункциональные требования](/lessons/sd-prep/delivery)

**Основные требования**

1. Документы должны быть eventually consistent (то есть все пользователи в итоге должны видеть одно и то же состояние документа).
2. Обновления должны доставляться с низкой latency (&lt; 100 мс).
3. Система должна масштабироваться до миллионов одновременных пользователей и миллиардов документов.
4. Не более 100 одновременных редакторов на документ.
5. Документы должны быть долговечными (durable) и доступными, даже если сервер перезапустится.

Некоторые нефункциональные требования *упрощают* тебе работу! В нашем случае ограничение на число одновременных редакторов документа — отличное ограничение. Оно означает, что нам не нужно переживать из-за огромного throughput на одном документе, и мы можем сосредоточиться на основной функциональности.

К слову, Google Docs тоже сделал такой выбор: после определённого числа одновременных пользователей все новые участники могут подключиться только как читатели (что кое-что говорит об их архитектурных решениях).

## Подготовка

### План решения

Прежде чем проектировать систему, нужно коротко продумать, как мы будем действовать.

Для этой задачи мы начнём с проектирования системы, которая просто поддерживает наши функциональные требования, не слишком заботясь о масштабе и нефункциональных требованиях. Затем в deep dives мы будем возвращать эти вопросы по одному.

Для этого мы сначала перечислим «существительные» нашей системы, набросаем API, а потом начнём рисовать блоки.

### [Определение основных сущностей](/lessons/sd-prep/delivery)

Сначала определим несколько основных сущностей. Они помогают договориться о терминах с интервьюером, понять данные, которые лежат в центре дизайна, и дают подсказку о наших API и о том, как система будет собираться воедино. Проще всего пройтись по функциональным требованиям и подумать, какие «существительные» участвуют в их выполнении. Если задавать себе более глубокие вопросы о поведении системы («что происходит, когда...»), легче найти сущности, важные для твоего дизайна.

Для этой задачи на доске нужно всего несколько сущностей:

![Иллюстрация](/content/google-docs/7b012bbc44.svg)

Основные сущности

Мы будем объяснять их интервьюеру по ходу решения задачи.

* **Editor**: пользователь, редактирующий документ.
* **Document**: набор текста, которым управляет редактор.
* **Edit**: изменение, внесённое в документ редактором.
* **Cursor**: позиция курсора редактора в документе (и присутствие этого пользователя в документе).

### Определение API

Теперь перейдём к API, которые нужны для выполнения требований; они будут очень точно повторять наши функциональные требования. Для этой задачи нам, скорее всего, понадобятся REST API для управления самим документом. Нам также понадобится много двусторонней связи между каждым редактором и документом, который они вместе редактируют. В таком случае логично предположить, что для работы редактора нужен подход на основе WebSocket, поэтому мы определим несколько сообщений, которые будем отправлять по сети.

Разные интервьюеры могут уделять этому шагу больше или меньше внимания. Одни захотят глубоко разобраться в тонкостях сообщений (скатываясь в вопрос по low-level design), другие будут довольны тем, что у тебя есть несколько сообщений, определённых в общих чертах, и можно двигаться дальше. Здесь мы будем считать, что верно второе!

```
POST /docs
{
  title: string
} -> {
  docId
}

WS /docs/{docId}
  SEND {
    type: "insert"
    ....
  }

  SEND {
    type: "updateCursor"
    position: ...
  }

  SEND { 
    type: "delete"
    ...
  }

  RECV { 
    type: "update"
    ...
  }
```

Когда в твоём API есть WebSocket, ты говоришь о *сообщениях*, которые отправляешь по WebSocket, а не об endpoint'ах, к которым обращаешься по HTTP. Нотация полностью на твой выбор, но какой-то способ описать протокол или схему сообщений полезен, чтобы показать, что именно передаётся по сети.

## [High-level design](/lessons/sd-prep/delivery)

Набросав API, переходим к high-level design. С тактической точки зрения полезно сказать интервьюеру, что в API наверняка есть детали, которые нужно проработать, но к ним ты вернёшься позже, когда будешь дорабатывать решение.

Конечно, *здорово* уметь отполировать идеальный ответ, но времени у тебя в обрез! Если признать, что к каким-то вопросам ты вернёшься позже, и оставить место для корректировки дизайна по мере того, как узнаёшь больше, интервью будет двигаться продуктивно.

### 1) Пользователи должны иметь возможность создавать новые документы.

Первый шаг в нашем редакторе документов — дать пользователям возможность создавать новые документы. Это простой API: он принимает название и возвращает ID документа. К документу можно привязать много интересных метаданных (например, permissions, историю, теги и т. д.), поэтому разумно предположить, что сам документ и метаданные будут разделены. В этом API мы займёмся первой частью.

С точки зрения интервью, паттерн, который мы здесь используем, — простой горизонтально масштабируемый CRUD-сервис за API gateway — настолько распространён, что ты должен уметь рисовать такие схемы очень быстро. Не трать слишком много времени на подготовку сцены.

![Иллюстрация](/content/google-docs/10eddd9778.svg)

Basic Metadata

Интервьюер, скорее всего, спросит, какую базу данных мы здесь используем. Для этой задачи пока предположим простую базу Postgres: она даёт гибкие запросы, а если понадобится масштабироваться, мы всегда сможем сделать partition и replica позже.

### 2) Несколько пользователей должны иметь возможность одновременно редактировать один и тот же документ.

Для следующего требования нам придётся разобраться с записью в сам документ, а это связано и с проблемами consistency, и с проблемами масштабирования. Вот здесь становится интересно. В совместном редакторе несколько пользователей одновременно вносят частые правки в один и тот же документ — идеальный рецепт для проблем с consistency и contention!

Вопросы масштабирования мы отложим до deep dive позже в интервью, поэтому скажем интервьюеру, что вернёмся к ним, а пока сосредоточимся на consistency.

#### Разбор совместного редактирования

Сначала я объясню, почему обеспечить consistency в совместном редакторе непросто: начнём с негодного решения и постепенно придём к более правильному.

Я разберу основы, чтобы показать, как можно решить проблемы с consistency, но, как и раньше, эти базовые знания нужны, чтобы ты мог ответить на вопросы интервьюера, а вот тратить время интервью на то, чтобы обучать интервьюера этим концепциям, вряд ли стоит. Если ты уже в них разбираешься, пропусти этот раздел!

##### Отправка снапшотов (неправильно)

Представим, что при каждой правке пользователи отправляют весь документ целиком в Document Service. Document Service затем сохраняет документ в blob storage, например в S3.

![Иллюстрация](/content/google-docs/3c231e7b0b.svg)

Deficient Solution

Достаточно просто, правда? Не так быстро. Во-первых, такой дизайн невероятно неэффективен: при каждой правке мы передаём по сети весь документ. Для быстро печатающего человека это могут быть сотни КБ на каждое нажатие клавиши, ужас. Но есть и более серьёзная проблема.

Допустим, пользователи A и B одновременно редактируют один и тот же документ. Сначала в документе один абзац текста:

```
Hello!
```

* Пользователь A добавляет ", world" и получает Hello, world!, который и отправляет.
* Пользователь B удаляет "!" и получает Hello, который и отправляет.

Оба отправляют свои правки одновременно. Какой документ в итоге сохранится в blob storage, целиком зависит от того, чей запрос придёт последним. Если последней придёт правка пользователя A, документ будет Hello, world! Если последней придёт правка пользователя B, документ будет Hello. Пользовательский опыт ужасный: мы теряем все параллельные правки!

##### Отправка правок (теплее)

Решить эти проблемы можно, если осознать, что мы вносим в документ именно **правки**. Вместо того чтобы передавать по сети весь документ, можно передавать сами правки.

* Пользователь A добавляет ", world" и отправляет INSERT(5, ", world")
* Пользователь B удаляет "!" и отправляет DELETE(6)

Первую проблему мы решили! Теперь мы не передаём по сети весь документ, а значит, не нужно отправлять сотни КБ при каждом нажатии клавиши. Но появилась новая проблема.

Удаление пользователя B исходит из того, что на позиции 6 стоит восклицательный знак. Если правка пользователя A придёт после удаления пользователя B, мы получим Hello, world — хорошо. Но если правка пользователя B придёт после правки пользователя A, мы получим Hello world! — мы удалили запятую вместо восклицательного знака!

##### Подходы к совместному редактированию

Ключевой недостающий элемент в том, что каждая правка контекстна: она сделана на основе конкретного состояния документа. Работа с потоком правок порождает целый ряд проблем с consistency! Решить эту проблему можно двумя способами:

#### Хорошее решение: Operational Transformation (OT)

###### Подход

Один из способов выйти из положения — переинтерпретировать, то есть *преобразовать* (transform) каждую правку перед её применением. Идея в том, что правку каждого пользователя можно скорректировать с учётом правок, которые были до неё.

Мы соберём все правки документа на одном сервере. Дальше можно пакетами преобразовывать каждую правку с учётом предшествующих. Подробный разбор OT выходит за рамки этого дизайна (подробнее можно почитать [на странице в Википедии](https://en.wikipedia.org/wiki/Operational_transformation)), но давай рассмотрим простой пример.

DELETE(6) пользователя B пытается удалить символ на позиции 6, которым для него на момент создания правки был !. Проблема возникает, когда первой приходит правка пользователя A, INSERT(5, ", world"). Если не преобразовать правку пользователя B, мы получим Hello, world вместо Hello, world!.

Подход OT — преобразовывать операции перед их применением (а позже и перед отправкой обратно клиентам). В нашем случае, если правка пользователя A приходит раньше удаления пользователя B, мы можем преобразовать DELETE(6) пользователя B в DELETE(13), чтобы после применения правки пользователя A он удалил восклицательный знак, а не запятую.

OT потребляет мало памяти и работает быстро, но у него есть серьёзный компромисс.

###### Сложности

OT требует центрального сервера, который определяет итоговый порядок операций. Это позволяет масштабироваться на небольшое число соавторов, но не на огромное. Здесь нам помогают наши нефункциональные требования. Кроме того, OT непросто реализовать правильно, и в нём легко ошибиться.

#### Хорошее решение: Conflict-free Replicated Data Types (CRDTs)

##### Подход

Альтернатива переинтерпретации каждой правки — сделать каждую правку коммутативной, то есть такой, что её можно применять в любом порядке. Именно такой подход используют Conflict-free Replicated Data Types (CRDTs).

CRDTs позволяют представить правки как набор операций, которые можно применять в любом порядке и всё равно получать в точности один и тот же результат.

Для простых текстовых операций CRDTs делают это с помощью двух приёмов:

1. CRDTs представляют позиции с помощью уникальных идентификаторов, которые можно бесконечно дробить (концептуально как вещественные числа, хотя в реализациях обычно используют идентификаторы переменной длины). Эти позиции *никогда не меняются*, даже при вставках. Если нужно создать больше «места», всегда можно сгенерировать новый идентификатор между любыми двумя существующими.
2. CRDTs хранят «tombstones» для удалённого текста. Текст на самом деле никогда не удаляется из документа, но мы помним, что он удалён, и учитываем это перед показом документа пользователю.

Примечание: мы не сможем глубоко объяснить CRDTs (это тема для серьёзного исследования), но ты можешь почитать подробнее [на странице в Википедии](https://en.wikipedia.org/wiki/Conflict-free_replicated_data_type). Чтобы дать тебе интуицию, давай рассмотрим простой пример.

Допустим, два пользователя смотрят на «Hello!», где под каждым символом указан номер позиции:

```
H  e  l  l  o  !
```

```
0  1  2  3  4  5
```

Оба хотят вставить что-то после «Hello». Пользователь A хочет вставить «,», а пользователь B — « there». В OT это было бы непросто, потому что пришлось бы преобразовывать одну правку на основе другой. А с CRDTs нам нужно лишь убедиться, что каждый новый символ получает собственный уникальный номер позиции между 4 и 5.

Когда пользователь A хочет вставить «,», она выбирает произвольное число между 4 и 5 в качестве позиции для своей запятой, в данном случае 4.3:

```
H    e    l    l    o    ,    !
```

```
0    1    2    3    4    4.3    5
```

Пользователь B делает то же самое (в то же время), назначая произвольные числа между 4 и 5 для каждого символа, который он хочет вставить:

```
H     e     l     l     o         t     h     e     r     e    !
```

```
0     1     2     3     4    4.1  4.2   4.4   4.5   4.7   4.8  5
```

Самое интересное в том, что эти номера позиций задают total ordering: в каком бы порядке ни пришли правки, каждый клиент отсортирует символы одинаково и увидит один и тот же итоговый текст.

После применения обновлений к документу мы получаем следующую строку:

```
H     e     l     l     o         t     ,     h     e     r     e    !
```

```
0     1     2     3     4    4.1  4.2   4.3   4.4   4.5   4.7   4.8  5
```

В этом случае получается строка "Hello t,here!" — следствие того, что оба пользователя редактируют одну и ту же позицию. Есть много приёмов, которые помогают избежать таких конфликтов, но главная гарантия CRDT в другом: в каком бы порядке ни пришли правки, все клиенты сойдутся к одному и тому же документу.

CRDT элегантны тем, что не требуют центрального сервера. Пока все обновления рано или поздно доходят до всех клиентов, клиенты сходятся к одному документу. Поэтому CRDT хорошо подходят для peer-to-peer приложений. Кроме того, CRDT проще приспособить к offline-сценариям: можно хранить все правки в local storage и добавить их в «мешок» обновлений, когда редактор снова окажется онлайн.

Отличная open-source реализация CRDT — [Yjs](https://github.com/yjs/yjs). Я бы очень рекомендовал её для лёгких коллаборативных приложений.

###### Сложности

У преимуществ CRDT есть серьёзные недостатки. Расход памяти выше, потому что нужно помнить каждую правку, включая tombstones для текста, который был удалён давным-давно. Это значит, что документ только растёт и никогда не уменьшается. CRDT также менее эффективны по вычислениям, хотя есть и обходные пути! И наконец, обработка конфликтов может быть не слишком изящной. Для большинства real-time сценариев это не так страшно: обычно хватает индикатора курсора, чтобы мы с тобой не редактировали одно и то же место в одном документе. Но когда клиентам приходится буферизировать правки или уходить в offline, это может стать серьёзной проблемой.

В этой задаче мы будем использовать подход Operational Transformation (OT). Именно его использует Google Docs, и у него есть плюсы: он требует мало памяти, лучше приспособлен именно к тексту и опирается на централизованный сервер.

Если бы нам нужно было поддерживать большее число соавторов или peer-to-peer систему (например, на WebRTC!), мы могли бы использовать CRDT. Есть немало примеров промышленных CRDT, которые срезают углы (Figma — заметный пример), и по обоим подходам идёт много исследований и разработок.

Если тебе ближе видео, весь выбор между OT и CRDT мы тоже разбираем здесь.

С учётом этого мы можем обновить дизайн, чтобы решить проблему совместного редактирования. В обновлённой схеме правки отправляются на центральный сервер как операции, сервер преобразует их и только потом записывает в базу данных.

![Иллюстрация](/content/google-docs/6126d2e8ed.svg)

Document Service с Operational Transformation

Для новой Document Operations DB нам нужно что-то, куда можно очень быстро писать в append-only режиме (пока что). Cassandra подойдёт. Мы будем делать partition по documentId и сортировать по timestamp (его будет выставлять наш Document Service). Как только правка успешно записана в базу данных, мы можем подтвердить её пользователю. Требование к durability выполнено!

### 3) Пользователи должны видеть изменения друг друга в реальном времени.

Итак, теперь, когда у нас есть путь записи, поговорим о самом важном из оставшихся компонентов: чтении! Нужно обработать два пути:

* Во-первых, когда документ только что создан или давно не открывался, нужно загрузить его из базы данных и передать подключённым редакторам.
* Во-вторых, когда другой редактор вносит правку, мы должны получить уведомление, чтобы наш документ оставался актуальным.

#### При загрузке документа

Когда пользователь подключается впервые, ему нужна последняя версия документа. В этом случае, когда для документа устанавливается исходное WebSocket-соединение, мы можем отправить в него все ранее применённые операции. Поскольку все подключаются к одному и тому же серверу, можно считать, что все соединения стартуют с одного и того же состояния.

![Иллюстрация](/content/google-docs/1b89eaf5f4.svg)

Загрузка документа

#### Когда происходят обновления

Когда другой соавтор успешно вносит правку, каждый из оставшихся подключённых редакторов должен получить обновления. Поскольку все наши редакторы подключены к одному и тому же серверу, это просто: после записи операции в базу данных мы можем также отправить её всем клиентам, которые сейчас подключены к этому документу.

Следующий шаг может вас удивить: на клиенте нам **тоже** нужно выполнять operational transformation. Давай коротко разберёмся, почему так.

Когда пользователи правят свой документ, они ожидают увидеть изменения *мгновенно*. В каком-то смысле их изменения всегда сначала применяются к локальному документу и только потом отправляются на сервер. Что произойдёт, если другой пользователь успеет закоммитить правку на сервере *после* того, как мы применили своё локальное изменение, но *до* того, как оно будет записано на сервере?

OT даёт нам способ обрабатывать правки, пришедшие не по порядку. Напомню: OT берёт последовательность правок в произвольном порядке и переписывает их так, чтобы они всегда приводили к одному и тому же итоговому документу. То же самое мы можем сделать и здесь!

Итак, если пользователь A отправляет на сервер Ea, а пользователь B отправляет Eb (которая приходит после Ea), то порядок операций с точки зрения каждой стороны такой:

```
Server: Ea, Eb
User A: Ea, Eb
User B: Eb, Ea
```

Независимо от порядка, применяя OT к операциям, мы можем гарантировать, что каждый пользователь увидит один и тот же документ!

![Иллюстрация](/content/google-docs/405d5a6f3c.svg)

Отправка обновлений клиентам

### 4) Пользователи должны видеть позицию курсора и присутствие других пользователей.

Одна из важнейших функций коллаборативного редактора — «awareness», то есть возможность видеть, где редактируют твои соавторы. Это помогает избежать ситуаций, когда вы одновременно правите один и тот же фрагмент (всегда бардак!) или дублируете работу. Awareness по своей природе временная: нас по-настоящему интересует, где курсор соавтора **сейчас**, а не где он был час назад. Нас также не интересует, где курсор пользователя, когда он не подключён: это не имеет смысла. Эти данные **эфемерны** и живут вместе с соединением.

Эти свойства подсказывают, что хранить позицию курсора и присутствие других пользователей в самих данных документа не нужно. Вместо этого пользователи могут сообщать об изменениях позиции курсора в Document Service, который хранит их в памяти и рассылает всем остальным пользователям через тот же WebSocket. Когда подключается новый пользователь, Document Service может прочитать свойства других пользователей из памяти и отправить их подключившемуся. Наконец, Document Service может отслеживать разрывы сокетов и отключения и удалять таких пользователей из списка (рассылая при этом уведомление оставшимся пользователям).

Вот так у нас получился работающий коллаборативный редактор, который масштабируется до нескольких тысяч пользователей!

## [Deep dives](/lessons/sd-prep/delivery)

Когда основные функциональные требования закрыты, пора заняться нефункциональными требованиями и проблемами, которые мы создали по ходу дела.

### 1) Как масштабироваться до миллионов websocket-соединений?

Одно из самых слабых допущений в нашей системе — что всех пользователей можно обслужить с одного сервера Document Service. Это не выдержит миллионы одновременных пользователей и создаёт единую точку отказа для доступности.

Число серверов Document Service нужно масштабировать под число одновременных соединений. Когда я подключаюсь к Document Service, мне нужно либо (a) оказаться на том же сервере, что и все остальные пользователи этого документа, либо (b) знать, где подключены все остальные. (Похожую задачу смотри в разборе [Whatsapp](/lessons/breakdowns/whatsapp).)

###### Паттерн: Real-time Updates

Необходимость отправлять push-обновления клиентам через масштабируемый backend-сервис — классический пример паттерна real-time updates.

[Изучить этот паттерн](/lessons/patterns/realtime-updates)

![Иллюстрация](/content/google-docs/a08227938c.svg)

Websocket-соединения

Когда ты добавляешь в дизайн websocket, скорее всего, причина в том, что они *двунаправленные*: сообщения можно отправлять обратно клиентам. В традиционной клиент-серверной архитектуре речь в основном о стрелках слева направо: как клиенты подключаются к серверам, отправляют сообщения и получают ответ. Многие кандидаты не делают следующий шаг и не думают о стрелках **справа налево** на своих схемах: как внутренние сервисы общаются с клиентами?

Поскольку stateful-природа websocket доставляет много боли, их удобно обрабатывать на «краю» системы. Если завершать websocket-соединения как можно раньше и отдавать остальной системе «внутренний» API, остальные компоненты могут оставаться stateless и не заботиться о деталях websocket-соединений.

Решение здесь — масштабировать Document Service горизонтально и распределять соединения по серверам с помощью кольца consistent hash. Каждый сервер в нашей системе входит в hash ring и отвечает за свой диапазон значений хеша. Благодаря этому мы всегда знаем, какой сервер отвечает за документ, и все соединения идут именно туда. Для хранения конфигурации hash ring и координации серверов мы используем Apache [ZooKeeper](/lessons/key-technologies/zookeeper).

Когда клиенту нужно подключиться:

1. Сначала он может открыть HTTP-соединение с любым из серверов документов (например, через round robin), передав ID нужного документа.
2. Этот сервер проверит конфигурацию hash ring для данного ID документа и, если он не отвечает за этот диапазон хешей, ответит редиректом на адрес нужного сервера. Так клиенты в итоге подключаются напрямую к правильному серверу, без посредника.
3. Когда правильный сервер найден, HTTP-соединение апгрейдится до websocket-соединения. Socket-сервер хранит map из ID документа в соответствующий websocket, чтобы использовать его позже.
4. Мы загружаем все сохранённые ops (если они ещё не загружены) из Document Operations DB и готовы обрабатывать операции.

Поскольку все пользователи документа подключены к одному серверу, при обновлениях мы можем просто передавать их всем подключённым клиентам.

Прелесть [consistent hashing](https://www.hellointerview.com/learn/system-design/deep-dives/consistent-hashing) в том, что при добавлении или удалении серверов нужно перераспределять лишь небольшую часть соединений. Серверы периодически проверяют ZooKeeper на изменения в кольце и при необходимости могут инициировать перенос соединений.

![Иллюстрация](/content/google-docs/ce9d5c0882.svg)

Архитектура с consistent hash

Минус такого подхода в том, что при таких событиях масштабирования приходится переносить много state. Нужно не только переместить websocket-соединения вытесненных пользователей (отключив их и заставив переподключиться к правильному серверу), но и убедиться, что операции документа перенесены на нужный сервер.

На интервью нас могут попросить раскрыть это подробнее:

**Сложность масштабирования**

* При добавлении серверов нужно отслеживать и старое, и новое hash ring
* Во время переходов запросы, возможно, придётся отправлять на несколько серверов
* Отказы серверов требуют быстрого перераспределения соединений и обновления hash ring

**Сложности с управлением состоянием соединений**

* Нужен надёжный мониторинг отказов серверов и проблем с соединениями
* Нужно реализовать на клиенте логику переподключения на случай недоступности сервера

**Требования к capacity planning**

* Нужно убедиться, что у серверов достаточно ресурсов под их нагрузку по соединениям
* Нужно следить за распределением соединений, чтобы не допустить hotspot на серверах

### 2) Как держать объём хранилища под контролем?

Когда документов миллиарды, к управлению хранилищем нужно подходить продуманно. Выбрав OT вместо CRDT, мы уже сокращаем объём необходимого хранилища в несколько раз. И всё же, если каждый документ весит 50kb, это 50TB данных! Хуже того, если в документе миллионы операций, каждую из них придётся передать и применить на каждом клиенте, который подключается к документу!

Помни также, что все *активные* документы нужно держать в памяти Document Service. Этот объём нужно держать небольшим, чтобы не упереться в память.

Одно из самых естественных решений — периодически делать snapshot/compact операций. Идея в том, что нам не нужно хранить все операции в Document Operations DB (исключение — если нам нужно какое-то версионирование), и можно свернуть много операций в одну, сэкономив и на обработке, и на месте.

Есть много способов это сделать!

#### Хорошее решение: Offline Snapshot/Compact

##### Подход

Один из подходов — добавить новый Compaction Service, который периодически читает операции из Document Operations DB и записывает обратно snapshot, сворачивающий эти инструкции. У расписания много возможных параметров: можно искать большие документы, которые давно не сворачивались и в которые, скорее всего, давно не писали.

Поскольку это неизбежно меняет операции, которые идут следом, нужно убедиться, что наша запись не затрагивает живой документ. Это непростая распределённая транзакция, а так как для Document Operations DB мы используем Cassandra, нам доступны только транзакции на уровне строки.

Чтобы обеспечить атомарность на уровне документа, мы добавим в Document Metadata DB новое поле documentVersionId. Перед загрузкой документа мы достанем этот documentVersionId из Document Metadata DB, чтобы знать, какие операции документа извлекать.

Когда мы хотим изменить операции, мы можем записать новые операции и затем *переключить* (flip) documentVersionId. Мы позаботимся, чтобы все *flip* проходили через Document Service, чтобы не получить (ещё одну) race condition.

Compaction Service может:

1. Прочитать из БД операции заданного документа.
2. Свернуть эти операции в как можно меньшее их число (скорее всего, в одну операцию insert!).
3. Записать полученные операции под новым documentVersionId.
4. Попросить Document Service *переключить* documentVersionId со старой версии на новую.

Если у Document Service документ загружен, он отбросит команду flip, отложив compaction, который мог бы повредить существующие операции.

![Иллюстрация](/content/google-docs/a85504050e.svg)

Compaction Service

##### Сложности

Когда нужна такая оркестрация, в ней прячется много коварных багов. Хотя всё происходит offline, наш compaction service может стать основным источником записей и чтений, поэтому его нужно аккуратно throttle, чтобы не перегрузить систему.

#### Отличное решение: Online Snapshot/Compact операций

##### Подход

Другой подход — поручить периодический snapshot/compact операций самому Document Service. Поскольку Document Service единолично владеет документом, пока мы не масштабируем кластер, мы можем спокойно сворачивать операции, не беспокоясь о координации и консистентности. Более того, естественный момент для этого — когда документ простаивает и у него нет подключений: Document Service узнаёт об этом сразу. К тому же все существующие операции документа в этот момент уже у нас в памяти, что упрощает задачу.

Когда отключается последний клиент, мы можем:

1. Взять все существующие операции и передать их в отдельный процесс с низким приоритетом по CPU (nice) для compaction.
2. Записать полученные операции в БД под новым documentVersionId.
3. Переключить documentVersionId в Document Metadata DB.

![Иллюстрация](/content/google-docs/f91b051d02.svg)

Online Snapshot/Compact операций

##### Сложности

Если вынести compaction в document service, это может увеличить latency операций с документами (особенно в хвосте, на P99), поэтому нужно следить, чтобы compaction не занимал CPU без необходимости. Один из вариантов — запускать его в отдельном процессе с более низким приоритетом CPU.

### Ещё несколько deep dives, которые стоит рассмотреть

Google Docs — огромный продукт, над которым работают сотни и тысячи инженеров, так что охватить всё здесь не получится. Вот ещё несколько deep dives, которые можно рассмотреть:

1. **Read-Only Mode**: в Google Docs есть режим «только чтение», в котором пользователи могут просматривать документы, не мешая другим. Он к тому же заметно лучше масштабируется: один и тот же документ могут смотреть миллионы читателей. Как это можно реализовать?
2. **Versioning**: Google Docs позволяет возвращаться к предыдущим версиям документа. Как расширить наш подход со snapshot/compact, чтобы поддержать это?
3. **Memory**: потребление памяти в нашем Document Service может стать узким местом. Как его дополнительно оптимизировать?
4. **Offline Mode**: как можно расширить наш дизайн, если мы хотим, чтобы клиенты могли работать в offline-режиме? Какие дополнительные моменты нужно учесть в дизайне?

Я не обязательно ожидаю, что кандидат знает разницу между OT и CRDT, но жду, что он сможет рассказать о компромиссах и ограничениях баз данных и о том, как они могут повлиять на наш дизайн.

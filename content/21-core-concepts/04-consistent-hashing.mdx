Какую задачу решает consistent hashing, как он работает и как использовать его на собеседовании.

Если ты готовишься к system design интервью, ты наверняка уже встречал consistent hashing. Это базовый алгоритм распределённых систем, который используется для распределения данных по кластеру серверов.

В сети буквально тысячи материалов, которые его объясняют, но большинство из них, на мой взгляд, слишком академичны.

В этом deep dive мы сфокусированно разберём consistent hashing: какую проблему он решает, как работает и как применять его на интервью.

## Consistent Hashing на примере

Давай выстроим интуицию на примере.

Представь, что ты проектируешь систему продажи билетов вроде TicketMaster. Сначала система простая:

* Одна база данных хранит все данные о событиях
* Клиенты отправляют запросы, чтобы получить информацию о событиях
* Поначалу всё работает гладко

![Иллюстрация](/content/core-concepts--consistent-hashing/e01c94eda5.svg)

Client Server Database

Но успех приносит новые сложности. По мере того как платформа становится популярнее и принимает всё больше событий, одна база данных перестаёт справляться с нагрузкой. Нужно распределить данные по нескольким базам, этот процесс называется [sharding](/lessons/core-concepts/sharding).

![Иллюстрация](/content/core-concepts--consistent-hashing/7cbdab2eb1.svg)

Sharding

Вопрос, на который нужно ответить: **как понять, какие события хранить на каком инстансе базы данных?**

### Первая попытка: простое modulo hashing

Самый очевидный способ распределить данные по нескольким базам — modulo hashing.

1. Сначала берём ID события и пропускаем его через хеш-функцию, которая превращает его в число
2. Затем берём это число и вычисляем остаток от деления (%) на количество баз данных
3. Результат говорит, в какой базе нужно хранить это событие

![Иллюстрация](/content/core-concepts--consistent-hashing/3555d277c4.svg)

Modulo Hashing

В коде это выглядит так:

```
database_id = hash(event_id) % number_of_databases
```

Конкретный пример для 3 баз данных:

```
Event #1234 → hash(1234) % 3 = 1 → Database 1
Event #5678 → hash(5678) % 3 = 0 → Database 0
Event #9012 → hash(9012) % 3 = 2 → Database 2
```

Отлично! Это работает хорошо, пока не возникнет несколько проблем.

Первая проблема появляется, когда ты хочешь добавить четвёртый инстанс базы данных. Наивно кажется, что достаточно просто считать остаток от деления на 4 вместо 3.

```
database_id = hash(event_id) % 4
```

Ты меняешь код, выкатываешь в production, и вдруг нагрузка на базы данных взлетает до небес! И не только на четвёртую, а на все.

Дело в том, что изменение хеш-функции затронуло не только данные, которые должны попасть на новый инстанс, оно изменило то, на каком инстансе хранится почти *каждое* событие.

![Иллюстрация](/content/core-concepts--consistent-hashing/7c2a6317d0.svg)

Проблема при добавлении ноды

Например, событие #1234 раньше попадало в базу 1, а теперь hash(1234) % 4 = 0, и эти данные нужно перенести в базу 0.

То есть данные нужно переместить из базы 1 в базу 0. Это не единичный случай: большую часть данных придётся перераспределить между всеми инстансами, что вызывает огромное количество лишнего перемещения данных. Это приводит к резким скачкам нагрузки на базы, и пользователи либо не могут получить данные, либо сталкиваются с медленными ответами.

Рассмотрим ещё одну проблему простого modulo hashing.

Представь, что база данных упала. Причина может быть любой: от аппаратного сбоя до бага в софте. В любом случае нужно убрать её из пула баз и перераспределить данные между оставшимися инстансами, пока мы не поднимем новый.

Наша хеш-функция теперь меняется с database\_id = hash(event\_id) % 3 на database\_id = hash(event\_id) % 2, и мы упираемся в ту же самую проблему перераспределения, что и раньше.

![Иллюстрация](/content/core-concepts--consistent-hashing/0d62fc5799.svg)

Проблема при удалении ноды

Очевидно, простое modulo hashing не подходит. Встречай: **Consistent Hashing**.

### Consistent Hashing

Consistent hashing — это техника, которая решает проблему перераспределения данных при добавлении или удалении инстанса в распределённой системе. Ключевая идея в том, чтобы разместить и данные, и базы данных в кольцевом пространстве, которое часто называют «hash ring».

Вот как это работает:

1. Сначала создаём hash ring с фиксированным числом точек. Для простоты пусть будет 100.
2. Затем размещаем ноды баз данных на hash ring. Если у нас 4 базы, можно поставить их в точки 0, 25, 50 и 75.
3. Чтобы узнать, в какой базе хранить событие, мы сначала хешируем ID события, как и раньше, но вместо modulo просто находим значение хеша на кольце и двигаемся по часовой стрелке, пока не встретим инстанс базы данных.

На практике hash space у hash ring обычно составляет от 0 до 2^32 - 1, а не 0–100, но принцип тот же.

Как это решило нашу проблему? Посмотрим, что происходит при добавлении или удалении базы данных:

**Добавление базы данных (Database 5)**
Допустим, мы добавляем пятую базу в позицию 90 на нашем кольце. Теперь:

* Переносить нужно только события, которые хешируются в позиции между 75 и 90
* Раньше эти события шли в DB1 (в позиции 0)
* Все остальные события остаются ровно там, где были!

![Иллюстрация](/content/core-concepts--consistent-hashing/c48c276815.svg)

Hash Ring после добавления DB5

Если раньше нужно было перераспределять почти все данные, то с consistent hashing мы переносим только около 60% событий, которые были на DB1 (диапазон 75–90, то есть 15 из 25 единиц отрезка DB1), или примерно 15% всех событий.

**Удаление базы данных**
Аналогично, если Database 2 (в позиции 25) падает:

* Переносить нужно только события, которые были привязаны к Database 2
* Теперь эти события будут попадать в Database 3 (в позиции 50)
* Всё остальное остаётся на месте

![Иллюстрация](/content/core-concepts--consistent-hashing/373fbcc371.svg)

Hash Ring после удаления DB2

#### Virtual Nodes

Мы неплохо продвинулись, но осталась ещё одна проблема. В нашем примере с удалением базы 2 нам пришлось перенести все события из базы 2 в базу 3. Теперь у базы 3 вдвое больше нагрузки, чем у баз 1 и 4. Мы бы предпочли распределить нагрузку равномернее, чтобы база 3 не оказалась перегружена.

Решение — так называемые «virtual nodes». Вместо того чтобы ставить каждую базу в одну точку кольца, мы ставим её в несколько точек, хешируя разные вариации имени базы.

![Иллюстрация](/content/core-concepts--consistent-hashing/3142ec4145.svg)

Hash Ring с Virtual Nodes

Например, вместо того чтобы просто хешировать «DB1» и получать позицию 0, мы хешируем «DB1-vn1», «DB1-vn2», «DB1-vn3» и так далее, что может дать позиции 20, 35, 65 и т. д. Мы делаем это для каждой базы, и в результате virtual nodes естественным образом перемешиваются по кольцу.

Теперь, когда Database 2 падает:

* События, привязанные к «DB2-vn1», перераспределятся в Database 1
* События, привязанные к «DB2-vn2», попадут в Database 3
* События, привязанные к «DB2-vn3», попадут в Database 4
* И так далее...

Это значит, что нагрузка упавшей базы распределяется гораздо равномернее между всеми оставшимися базами, а не обрушивается на одного соседа. Чем больше virtual nodes на каждую базу, тем равномернее распределяется нагрузка.

Virtual nodes помогают и при добавлении новой базы. Без virtual nodes новая нода забирает нагрузку только у своего единственного соседа по часовой стрелке. С virtual nodes виртуальные позиции новой ноды разбросаны по кольцу, поэтому она забирает небольшую часть данных у нескольких существующих нод. Это даёт намного более сбалансированный кластер с самого начала, а не просто разгружает одного перегруженного соседа.

### Борьба с hot spots

Даже если virtual nodes равномерно распределяют данные, hot spots всё равно могут возникать. Hot spot — это ситуация, когда одна нода получает непропорционально много трафика, потому что некоторые ключи намного популярнее остальных. Представь систему продажи билетов, где концерт Taylor Swift генерирует в 100 раз больше чтений, чем любое другое событие.

Сам по себе consistent hashing это не решает, потому что он равномерно распределяет ключи, а не трафик. Вот несколько стратегий, которые используют реальные системы:

* Read replicas: реплицировать популярные ключи на несколько нод и балансировать чтения между ними. Это самый распространённый подход.
* Key-space salting: добавлять к hot-ключам случайный суффикс (например, taylor-swift-\{0..9\}), чтобы они хешировались в разные ноды. Тогда чтения разбегаются по этим нодам, а результаты агрегируются.
* Adaptive rebalancing: отслеживать трафик в реальном времени и переносить конкретные диапазоны ключей с перегруженных нод. Это операционно сложно, но некоторые системы (например, DynamoDB) делают это автоматически.

На интервью важно подчеркнуть различие: virtual nodes предотвращают структурный дисбаланс (неравномерное распределение ключей), а replication и key salting предотвращают дисбаланс по нагрузке (неравномерный трафик).

### Перемещение данных на практике

Consistent hashing говорит, где данные должны находиться, но он не телепортирует терабайты данных волшебным образом, когда нода падает. На практике большинство распределённых баз данных используют replication вместе с consistent hashing, чтобы справляться со сбоями вообще без перемещения данных.

Например, DynamoDB реплицирует каждый partition по трём availability zone. Когда primary-нода падает, одна из replica повышается до primary через consensus-алгоритм вроде Raft, и данные перемещать не нужно. Cassandra работает похожим образом: данные реплицируются на N последовательных нод кольца, поэтому чтения можно обслуживать с уцелевших replica.

Перемещение данных на практике происходит только при плановых изменениях состава кластера: когда добавляешь мощности или окончательно заменяешь node, чтобы восстановить replication factor. Но и тогда consistent hashing гарантирует, что нужно заново реплицировать лишь ограниченную долю ключей, а не весь датасет.

## Consistent Hashing в реальном мире

Наш пример был про масштабирование базы данных, но consistent hashing применим в любых сценариях, где нужно распределить данные по кластеру серверов. Это могут быть базы данных, конечно, но также cache, message broker'ы или просто набор application-серверов.

Consistent hashing (или его вариации) используется во многих высоконагруженных системах, на которые все полагаются. Например:

1. [Apache Cassandra](/lessons/key-technologies/cassandra): использует consistent hashing для распределения данных по кольцу
2. [Amazon's DynamoDB](/lessons/key-technologies/dynamodb): использует consistent hashing под капотом для размещения partition
3. [Content Delivery Networks (CDNs)](https://en.wikipedia.org/wiki/Content_delivery_network): используют consistent hashing, чтобы определить, какой edge-сервер должен кэшировать конкретный контент

Не каждая распределённая система использует consistent hashing. Например, Redis Cluster вместо этого использует подход с фиксированными hash slot. Он делит пространство ключей на 16 384 slot с помощью CRC16(key) mod 16384 и назначает диапазоны slot узлам. Так проще рассуждать о системе, но при ребалансировке требуется больше координации. Выбор между consistent hashing и фиксированными hash slot — это реальный trade-off в дизайне, который можно обсудить на интервью.

## Когда использовать Consistent Hashing на интервью

Большинство современных распределённых систем берут на себя [sharding](/lessons/core-concepts/sharding) и распределение данных. Когда ты проектируешь систему на DynamoDB, Cassandra и т. п., обычно достаточно упомянуть, что под капотом эти системы используют consistent hashing (или его вариацию) для масштабирования.

Однако consistent hashing становится ключевой темой на интервью, ориентированных на инфраструктуру, где тебя просят спроектировать распределённую систему с нуля. Вот типичные сценарии:

1. Спроектировать распределённую базу данных
2. Спроектировать распределённый cache
3. Спроектировать распределённый message broker

На таких глубоких инфраструктурных интервью нужно быть готовым объяснить несколько ключевых концепций:

1. Почему consistent hashing лучше простого [sharding](/lessons/core-concepts/sharding) на основе остатка от деления (modulo) для распределения данных
2. Как virtual node улучшают балансировку нагрузки по кластеру
3. Стратегии обработки отказов и добавления node
4. Как возникают hot spot и какими приёмами их смягчать (replication, key salting)
5. Как связаны consistent hashing и replication для отказоустойчивости

Главное — понимать, когда нужно копать глубоко, а когда достаточно признать, что эту сложность за тебя уже решили готовые системы. Большинство интервью по system design относятся ко второй категории!

## Итоги

Consistent hashing — один из тех алгоритмов, которые совершили переворот в распределённых системах, решив на вид простую задачу: как распределить данные по серверам, минимизировав перераспределение при изменении их числа.

Детали реализации могут быть сложными, но основная идея прекрасно проста: расположи всё на окружности и иди по часовой стрелке. Это элегантное решение сегодня встроено во многие распределённые системы, которыми мы пользуемся каждый день, от DynamoDB до Cassandra.

Стоит помнить: на практике термин «consistent hashing» используется вольно. Как отмечает Мартин Клеппман в Designing Data-Intensive Applications, некоторые системы, заявляющие об использовании consistent hashing, на самом деле применяют вариации вроде hash-based partitioning с фиксированными диапазонами slot. Важен сам принцип минимизации перемещения данных при ребалансировке, даже если конкретная реализация отличается от классического подхода с кольцом.

На следующем интервью по system design помни: обычно реализовывать consistent hashing самому не нужно. Достаточно знать, когда он работает под капотом, и приберечь deep dive для инфраструктурных вопросов, где он действительно важен.

Принципы и паттерны проектирования API для интервью по system design: REST, GraphQL, RPC, пагинация, идемпотентность, версионирование и безопасность.

На интервью по system design тебе нужно определить, как клиенты взаимодействуют с твоей системой. Это делается на [шаге API](/lessons/sd-prep/delivery) во [фреймворке Delivery](/lessons/sd-prep/delivery).

Проектирование API следует предсказуемым паттернам. Ты выбираешь протокол, определяешь ресурсы и описываешь, как клиенты передают данные и получают ответы. Эта статья не сделает тебя мастером в проектировании API, но она покрывает всё базовое, чтобы уверенно пройти эти 5 минут интервью.

Прежде чем углубляться, хочу прояснить одну вещь: большинству интервьюеров не важно, чтобы твой API был идеальным. Они хотят увидеть, что ты можешь спроектировать разумный API и перейти к более сложным частям системы.

При этом если ты проходишь интервью на frontend- или product-роль, API design важнее: с API ты будешь работать каждый день. Кроме того, от junior-кандидатов меньше ждут умения проектировать распределённые системы, поэтому на интервью может остаться больше времени на API.

## Типы API

На интервью обычно выбирают один из трёх основных протоколов API:

1. **REST (Representational State Transfer)** — REST использует стандартные HTTP-методы (GET, POST, PUT, DELETE) для работы с ресурсами, которые идентифицируются URL. Для стандартных CRUD-операций в веб- и мобильных приложениях REST естественно ложится на операции с базой данных и семантику HTTP, поэтому это основной протокол для большинства веб-сервисов. Он должен быть твоим выбором по умолчанию.
2. **GraphQL** — в отличие от фиксированных endpoint'ов REST, GraphQL использует один endpoint и язык запросов, который позволяет клиентам точно указать, какие данные им нужны. Представь мобильное приложение, которому нужна только базовая информация о пользователе, и веб-дашборд с подробной аналитикой. В REST пришлось бы либо делать несколько endpoint'ов, либо заставлять клиентов забирать больше данных, чем нужно, а GraphQL позволяет каждому клиенту запросить ровно то, что ему нужно, одним запросом. Если интервьюер упоминает «гибкую выборку данных» или говорит про избегание over-fetching и under-fetching, это сигнал, что стоит подумать о GraphQL.
3. **RPC (Remote Procedure Call)** — RPC-протоколы вроде gRPC используют бинарную сериализацию и HTTP/2 для эффективного взаимодействия между сервисами. REST рассматривает всё как ресурсы, а RPC позволяет мыслить действиями и процедурами. Когда твоему user service нужно быстро проверить права через auth service, вызов RPC вроде checkPermission(userId, resource) выглядит естественнее, чем попытка смоделировать это как REST-ресурс. Если интервьюер прямо упоминает микросервисы или внутренние API, рассмотри RPC для таких высокопроизводительных соединений. Используй RPC, когда критична производительность (подробнее о протоколах см. [Networking Essentials](/lessons/core-concepts/networking-essentials)).

По умолчанию бери REST, если нет конкретной причины выбрать другое. Он хорошо знаком всем, у него отличный инструментарий, и он подходит для 90% случаев. Если сомневаешься, просто скажи «я буду использовать REST API» и двигайся дальше.

Для функций реального времени, таких как уведомления, чат или live-обновления, понадобятся другие протоколы, например WebSockets или Server-Sent Events. Это не традиционные API, а постоянные соединения. Но знать о них важно, и подробнее ты можешь прочитать в нашем [Real-time Updates Pattern](/lessons/patterns/realtime-updates).

### REST

Раз REST — твой выбор по умолчанию, большую часть времени мы посвятим тому, как проектировать REST API, которые хорошо работают на интервью по system design.

#### Моделирование ресурсов

Основа хорошего REST API — правильно определить ресурсы. Если ты следовал [фреймворку delivery](/lessons/sd-prep/delivery), ресурсы — это просто твои [основные сущности](/lessons/sd-prep/delivery).

Возьмём для примера Ticketmaster. Твои основные сущности могут быть такими: events, venues, tickets и bookings. Они естественно превращаются в REST-ресурсы:

```
GET /events                    # Get all events
GET /events/{id}               # Get a specific event
GET /venues/{id}               # Get a specific venue
GET /events/{id}/tickets       # Get available tickets for an event
POST /events/{id}/bookings     # Create a new booking for an event
GET /bookings/{id}             # Get a specific booking
```

Важно: REST-ресурсы должны представлять *вещи* в твоей системе, а не *действия*. Вместо того чтобы думать, что пользователи могут делать (например, «забронировать» или «купить»), думай о том, что существует в системе (events, venues, tickets, bookings).

Ресурсы всегда должны быть существительными во множественном числе, то есть bookings, events, tickets и так далее. Большинству интервьюеров это безразлично, но некоторым нет, а сделать правильно несложно, так что лучше так и делать.

Для связей между ресурсами есть два основных подхода. Можно вкладывать ресурсы, когда есть чёткая связь «родитель — потомок», например /events/\{id\}/tickets для всех билетов конкретного события. Или можно оставить ресурсы плоскими и использовать query-параметры для фильтрации, например /tickets?event\_id=123.

Ключевое отличие в том, обязательна связь или опциональна. Используй path-параметры (или вложенные ресурсы), когда значение обязательно, как в /events/\{id\}/tickets, где всегда нужно указать, билеты какого события тебе нужны. Используй query-параметры, когда фильтр опционален, как в /tickets?event\_id=123&section=VIP, где тебе могут понадобиться все билеты, либо билеты, отфильтрованные по событию, либо по событию и секции одновременно.

На интервью это различие помогает быстро сделать правильный выбор. Если связь всегда нужна, чтобы запрос имел смысл, используй path-параметр. Если это опциональный фильтр среди множества возможных, используй query-параметр. Интервьюера больше волнует, можешь ли ты определить правильные ресурсы, чем идеальная структура URL, но понимание этого различия показывает хорошую интуицию в проектировании API.

#### HTTP-методы

Определив ресурсы, нужно решить, как клиенты с ними взаимодействуют. В HTTP есть набор методов (глаголов), которые естественно соответствуют типичным операциям, и понимать, когда какой использовать, важно для интервью.

**GET** предназначен для получения данных без каких-либо изменений. Используй GET для /events/\{id\}, чтобы получить детали события, или для /events, чтобы получить список всех событий.

**POST** создаёт новые ресурсы. Когда пользователь бронирует билеты, ты делаешь POST на /events/\{id\}/bookings с деталями бронирования в теле запроса. Сервер назначает ID и возвращает созданное бронирование. POST не является ни безопасным, ни идемпотентным. Иными словами, повторные вызовы создадут несколько бронирований.

**PUT** заменяет ресурс целиком на то, что ты отправил, или создаёт его, если он не существует. Если ты полностью обновляешь профиль пользователя, делай PUT на /users/\{id\} с полным объектом пользователя. В отличие от POST, PUT идемпотентен: отправка одних и тех же данных несколько раз приводит к одному и тому же итоговому состоянию.

**PATCH** обновляет часть ресурса. Когда пользователь меняет только адрес электронной почты, делай PATCH на /users/\{id\} только с полем email. В отличие от PUT, PATCH не гарантированно идемпотентен — результат зависит от реализации. PATCH вида «установить email в X» идемпотентен, а PATCH вида «добавить в список» — нет.

**DELETE** удаляет ресурс. DELETE /bookings/\{id\} отменяет бронирование. Он идемпотентен, потому что повторные вызовы оставляют сервер в том же состоянии (ресурс остаётся удалённым), даже если коды ответа отличаются (первый вызов может вернуть 204, последующие — 404).

Ключевое здесь — идемпотентность, то есть то, оставляют ли повторные запросы сервер в том же состоянии. GET, PUT и DELETE идемпотентны, потому что их многократный вызов не меняет итоговый результат. POST и PATCH не гарантированно идемпотентны, и это важно, когда сеть отказывает и клиенты повторяют запросы. Тебе не нужны дублирующиеся бронирования из-за повторной отправки.

#### Передача данных в API

Endpoint'ам API нужны входные данные, чтобы понимать, что делать серверу: какие ресурсы получить, какие данные обновить в базе или как отфильтровать результаты. Понимание того, куда класть разные типы входных данных, критично для чистого и интуитивного API.

Есть три основных способа передачи данных в REST API, и каждый служит своей цели.

**Path-параметры** определяют, с каким конкретным ресурсом ты работаешь. Когда нужно получить детали события, ты кладёшь ID события в путь: /events/123. ID является частью самой структуры URL, и это ясно показывает, что ты запрашиваешь конкретное событие, а не коллекцию событий. Используй path-параметры, когда значение необходимо для идентификации ресурса: без него запрос не имеет смысла.

**Query parameters** фильтруют, сортируют или иным образом изменяют то, как ты получаешь ресурсы. Когда нужно найти события в конкретном городе или за определённый период, ты используешь query parameters: /events?city=NYC&date=2024-01-01. Они необязательны: можно запросить все события без фильтров, а можно применить сразу несколько. Query parameters хорошо подходят и для pagination: /events?page=2&limit=20. Обрати внимание: первый параметр отделяется через ?, а все последующие через &.

**Request body** содержит данные, которые ты отправляешь, чтобы создать или обновить ресурс. Когда пользователь бронирует билеты, ты делаешь POST на /events/\{id\}/bookings, а детали бронирования передаёшь в request body: сколько билетов, предпочтения по местам и так далее. В request body кладут сложные структуры данных и всё, что слишком велико или слишком чувствительно для URL.

Каждый тип входных данных играет свою роль в контракте API. Path parameters структурные: они определяют, к какому endpoint ты обращаешься. Query parameters это модификаторы: они меняют поведение endpoint. Request body это payload: данные, с которыми ты на самом деле работаешь.

Вот практический пример. Допустим, ты строишь систему бронирования, и пользователь хочет забронировать VIP-билеты на конкретное событие. Запрос будет устроен так:

```
POST /events/123/bookings?notify=true
{
  "tickets": [
    {"section": "VIP", "quantity": 2},
    {"section": "General", "quantity": 1}
  ],
  "payment_method": "credit_card"
}
```

ID события (123) находится в path, потому что нужно указать, на какое именно событие ты бронируешь билеты. Настройка уведомлений передаётся как query parameter, потому что это необязательное поведение. Сами детали бронирования идут в request body, потому что это основные данные, которые ты создаёшь.

#### Возврат данных

Ответ API состоит из двух частей:

1. Status code, который показывает, успешно ли выполнен запрос.
2. Response body, которое содержит данные, возвращаемые клиенту (обычно JSON).

Для status code придерживайся распространённых: 200 для успеха, 201 для созданных ресурсов, 400 для некорректных запросов, 401, если требуется аутентификация, 404 для ненайденного ресурса и 500 для ошибок сервера.

Не усложняй это на интервью: интервьюеров больше волнует, понимаешь ли ты разницу между ошибками клиента (4xx) и ошибками сервера (5xx), а не то, помнишь ли ты каждый status code наизусть. Даже если ты скроешь код за иксами, это, как правило, совершенно нормально.

### GraphQL

GraphQL появился в Facebook в 2012 году для решения конкретной проблемы: мобильному приложению нужны были другие данные, чем веб-приложению, а команда застряла с REST endpoints, которые возвращали фиксированные структуры данных. Мобильная команда постоянно просила новые endpoints или изменения в существующих, и это тормозило разработку с обеих сторон.

С REST, когда разным клиентам нужны разные данные, обычно приходится выбирать из двух неприятных вариантов. Можно создать несколько endpoints под разные сценарии, и тогда получится разрастание числа endpoints и головная боль с их поддержкой. Или можно сделать так, чтобы endpoints возвращали всё, что может понадобиться любому клиенту, и тогда возникнет over-fetching: мобильные клиенты скачивают мегабайты данных, которые им не нужны.

GraphQL объединяет endpoints ресурсов в один endpoint, который принимает запросы с точным описанием нужных данных. Клиент задаёт форму ответа, а сервер возвращает данные именно в таком формате.

#### Как работает GraphQL

Вот простой пример на нашем сценарии с Ticketmaster. Вместо отдельных REST endpoints для событий, площадок и билетов у тебя будет единый GraphQL endpoint, который умеет обрабатывать запросы вроде такого:

```
query {
  event(id: "123") {
    name
    date
    venue {
      name
      address
    }
    tickets {
      section
      price
      available
    }
  }
}
```

Сервер возвращает ровно то, что ты запросил, ни больше ни меньше. Если мобильному приложению нужны только названия и даты событий, оно может запросить только эти поля. Если веб-панели нужны подробные данные о событии вместе с информацией о площадке и наличием билетов, она может запросить всё это одним запросом.

#### Когда использовать GraphQL на интервью

GraphQL подходит, когда у тебя разнородные клиенты с разными потребностями в данных. Если интервьюер упоминает сценарии вроде «мобильному приложению нужны другие данные, чем веб-приложению» или спрашивает про «как избежать over-fetching и under-fetching», скорее всего, он ждёт, что ты вспомнишь про GraphQL.

Он также хорошо подходит, когда frontend-командам нужно быстро итерироваться без изменений на backend. С REST добавление нового поля на экран мобильного приложения часто требует изменений на backend и деплоя API. С GraphQL frontend-команда может запрашивать дополнительные поля, если они есть в schema.

Однако GraphQL добавляет сложности. Нужно реализовать парсинг запросов, валидацию schema и, как правило, продуманные стратегии caching. Для большинства интервью по system design REST проще и понятнее, если только задача прямо не требует гибкости GraphQL.

#### Дизайн GraphQL schema

Если ты всё-таки выбираешь GraphQL, думать о дизайне придётся иначе. Вместо ресурсных endpoints, как в REST, ты проектируешь schema, которая описывает типы данных и связи между ними.

В нашем примере с Ticketmaster ты бы начал с моделирования основных сущностей в виде типов GraphQL:

```
type Event {
  id: ID!
  name: String!
  date: DateTime!
  venue: Venue!
  tickets: [Ticket!]!
}

type Venue {
  id: ID!
  name: String!
  address: String!
}

type Query {
  event(id: ID!): Event
  events(limit: Int, after: String): [Event!]!
}
```

Ключевое отличие от REST в том, что связи определяются прямо в schema. У Event есть Venue, и клиенты могут пройти по этой связи одним запросом.

Но такая гибкость порождает **проблему N+1**, главную ловушку GraphQL. Когда клиент запрашивает события вместе с их площадками, ты можешь выполнить один запрос за событиями, а затем N отдельных запросов за каждой площадкой. Для 100 событий это 101 запрос к базе данных вместо 2. Решение: паттерны batching/dataloader, которые группируют связанные запросы, но это добавляет сложности, которой нет в REST.

GraphQL также иначе подходит к авторизации. Вместо защиты целых endpoints, как в REST, ты защищаешь отдельные поля. Пользователь может видеть название и дату события, но не данные о площадке. Это можно контролировать на уровне полей в resolvers твоей schema.

На интервью упоминай GraphQL, когда видишь явные проблемы over-fetching или under-fetching, но не выбирай его по умолчанию. Большинство интервьюеров ценят, что ты знаешь про GraphQL, но обычно предпочитают сначала увидеть, как ты решаешь основные архитектурные задачи более простыми средствами.

### RPC

RPC (Remote Procedure Call) это парадигма взаимодействия, которая позволяет клиенту вызвать процедуру на сервере и дождаться ответа, не вникая в детали работы сети. Протоколы вроде gRPC используют бинарную сериализацию и HTTP/2, из-за чего они быстрее традиционных REST API на JSON поверх HTTP при взаимодействии между сервисами.

#### Как работает RPC

В отличие от ресурсно-ориентированного подхода REST, RPC ориентирован на действия. По сути, ты вызываешь функции по сети так, как будто это локальные функции в твоей кодовой базе. Вот как те же операции Ticketmaster могли бы выглядеть с RPC:

```
// Instead of GET /events/123
getEvent(eventId: "123")

// Instead of POST /events/123/bookings
createBooking(eventId: "123", userId: "456", tickets: [...])

// Instead of GET /events/123/tickets
getAvailableTickets(eventId: "123", section: "VIP")
```

Самый популярный сегодня RPC-протокол это [gRPC](https://grpc.io/), который использует Protocol Buffers для сериализации и HTTP/2 для транспорта. Эта связка заметно быстрее подхода REST с JSON поверх HTTP, особенно при взаимодействии между сервисами. Ещё один известный RPC-фреймворк это [Apache Thrift](https://thrift.apache.org/), изначально разработанный в Facebook и теперь с открытым исходным кодом; он поддерживает множество языков программирования и форматов сериализации.

#### Protocol Buffers и типобезопасность

gRPC использует Protocol Buffers (protobuf) для описания контрактов сервисов. Ты пишешь файл .proto, который описывает методы сервиса и структуры данных:

```
service TicketService {
  rpc GetEvent(GetEventRequest) returns (Event);
  rpc CreateBooking(CreateBookingRequest) returns (Booking);
  rpc GetAvailableTickets(GetTicketsRequest) returns (TicketList);
}

message GetEventRequest {
  string event_id = 1;
}

message Event {
  string id = 1;
  string name = 2;
  int64 date = 3;
  Venue venue = 4;
}
```

По этому единственному описанию gRPC генерирует клиентский и серверный код на разных языках программирования. Это значит, что твой backend-сервис на Go и платёжный сервис на Java могут общаться с типобезопасностью на этапе компиляции, и несоответствия обнаруживаются ещё до деплоя.

#### Когда использовать RPC на интервью

RPC хорошо проявляет себя в архитектурах на микросервисах, где сервисам нужно часто и эффективно общаться друг с другом. Если интервьюер упоминает внутреннее взаимодействие сервисов, высокие требования к производительности или polyglot-среды (разные сервисы на разных языках), RPC, скорее всего, хороший выбор.

Рассматривай RPC, когда:

* **Критична производительность**: бинарная сериализация и HTTP/2 делают RPC заметно быстрее JSON REST
* **Важна типобезопасность**: сгенерированный клиентский код предотвращает множество ошибок во время выполнения
* **Взаимодействие между сервисами**: внутренним API между твоими собственными сервисами не нужна ресурсная семантика REST
* **Нужен streaming**: gRPC поддерживает двунаправленный streaming для функций реального времени

В нашем примере с Ticketmaster ты мог бы использовать REST API для публичных endpoints, которыми пользуются мобильные приложения и веб-клиенты, а gRPC применить для внутреннего взаимодействия между booking-сервисом, payment-сервисом и inventory-сервисом.

Если тебя прямо не попросят, обычно ты не описываешь внутренние API на [шаге API](/lessons/sd-prep/delivery) интервью. Вместо этого сосредоточься здесь только на API, которые видит пользователь. Максимум, ты отметишь, что внутренние сервисы общаются по RPC, когда будешь описывать high-level design.

## Принципы проектирования API

Протоколы, ресурсы и endpoints — это механика проектирования API. Но когда интервьюер смотрит на твой API и называет его «чистым», он на самом деле сверяет его с несколькими принципами, которые работают независимо от выбранного протокола. Тебя вряд ли попросят пересказать принципы проектирования API напрямую. Скорее, по ним будут оценивать твой дизайн, а умение применить нужный принцип в нужный момент как раз и выдаёт человека, который уже строил настоящие API.

Большую часть важного покрывают девять принципов:

**1. Проектируй вокруг ресурсов, а не действий.** Открывай наружу сущности своей системы и позволяй методам выражать, что клиенты с ними делают. Если ловишь себя на endpoints вроде /getUserBookings или /processPayment, остановись и спроси себя, каким ресурсом ты на самом деле управляешь (GET /users/\{id\}/bookings, POST /payments). Это тот же совет из раздела про [моделирование ресурсов](#resource-modeling), повышенный до принципа, потому что интервьюеры проверяют его в первую очередь.

**2. Будь последователен во всём.** Одинаковые соглашения об именовании, одинаковые имена параметров, одинаковая форма ответов во всех endpoints. Если один endpoint фильтрует через ?status=paid, а другой через ?state=paid, твой API невозможно предсказать, его приходится заучивать. Последовательность скучна, и в этом её смысл. Тот, кто видел один из твоих endpoints, должен суметь угадать остальные.

**3. Следуй принципу наименьшего удивления.** Используй HTTP так, как это делают все остальные. GET никогда не меняет данные, DELETE удаляет, а 200 означает успех (а не ошибку, спрятанную в теле с "success": false). Каждое место, где твой API отклоняется от того, что угадал бы разумный разработчик, — это маленький налог, который каждый consumer платит вечно.

**4. Делай API stateless.** Каждый запрос должен нести всё, что нужно серверу для его обработки: auth token, параметры, payload. Когда ни одному серверу не нужно помнить ничего о предыдущих запросах, любой сервер может обработать любой запрос, и горизонтальное масштабирование превращается из проблемы приложения в задачу для load balancer. Во многом поэтому JWT так популярны в распределённых системах.

**5. Делай повторы безопасными.** Сеть отказывает посреди запроса, и клиент не знает, успел ли сервер выполнить работу, прежде чем всё развалилось. Ему остаётся только повторить запрос, поэтому проектируй API так, чтобы повторы были безвредны. GET, PUT и DELETE идемпотентны по своей природе. Для POST-endpoints, которые создают важные для пользователей вещи, вроде бронирований и платежей, используй idempotency keys (о них ниже).

**6. Добавляй пагинацию ко всему, что может расти.** List endpoint, возвращающий «все бронирования», прекрасно работает на 50 строках в разработке и падает на 5 миллионах в production. Каждый endpoint, возвращающий коллекцию, получает пагинацию с первого дня, а также ограничение на размер страницы, чтобы клиент не мог запросить ?limit=100000 и положить твою базу данных.

**7. Защищай каждый endpoint по умолчанию.** Аутентификация должна быть opt-out, а не opt-in: каждый endpoint требует валидный token, если только ты намеренно не пометил его публичным, а авторизация проверяет, что вызывающий может действовать именно с этим ресурсом (John может отменять свои бронирования, но не чужие). Всё это подкрепляется rate limiting. Подробнее обо всём этом в разделе [вопросы безопасности](#security-considerations).

**8. Развивай API, не ломая клиентов.** Как только кто-то зависит от твоего API, ты больше не контролируешь, когда он обновится. Старые версии мобильных приложений живут годами. Добавить новое поле безопасно, но переименование, удаление или изменение смысла существующего поля — это breaking change, для которого нужна стратегия версионирования.

**9. Делай ошибки пригодными для действий.** Хороший ответ с ошибкой говорит клиенту, что пошло не так и что с этим делать. Это значит правильный класс status code (4xx — «ты ошибся», 5xx — «ошиблись мы») плюс машиночитаемый код ошибки и понятное человеку сообщение в теле.

Баллы дают не за перечисление принципов в отвлечённом виде, а за их применение вслух. «Я использую idempotency key на этом endpoint, чтобы повтор не забронировал место дважды» звучит гораздо сильнее, чем лекция об идемпотентности. Используй принципы как обоснование своих решений, и ты продемонстрируешь все девять, ни разу их не назвав.

## Типовые паттерны API

Принципы выше описывают, как выглядит хороший API. Паттерны ниже показывают, как эти принципы проявляются в production-системах, и они применимы независимо от того, выберешь ты REST, GraphQL или RPC. Их стоит знать, потому что они встречаются в большинстве реальных систем.

### Пагинация

Когда работаешь с большими наборами данных, нельзя вернуть всё сразу. Представь API, который возвращает все когда-либо созданные события: это могут быть миллионы записей и много гигабайт данных.

Вместо этого нужна пагинация, которая разбивает большие результаты на удобные порции. Есть два основных подхода к пагинации: offset-based и cursor-based.

#### Offset-based пагинация

Offset-based пагинация — самый простой подход, и его используют большинство сайтов. Ты указываешь, сколько записей пропустить и сколько вернуть: /events?offset=20&limit=10 вернёт записи с 21 по 30. Это интуитивно и просто в реализации, но на больших наборах данных возникают проблемы. Если во время постраничного просмотра кто-то добавит новое событие, ты можешь увидеть дубликаты или пропустить записи из-за сдвига данных.

#### Cursor-based пагинация

Cursor-based пагинация решает это, используя указатель на конкретную запись вместо отсчёта от начала. Вот как это работает на практике:

Первый запрос: /events?limit=10
Ответ включает события и cursor, указывающий на последнюю запись:

```
{
  "events": [...],
  "next_cursor": "cmd9atj3p000007ky19w1dpy2"
}
```

Следующий запрос: /events?cursor=cmd9atj3p000007ky19w1dpy2&limit=10

Cursor обычно представляет собой закодированную ссылку на конкретную запись (например, ID или timestamp). Это стабильнее, потому что добавление новых записей на него не влияет, но так сложнее реализовать функции вроде «перейти на страницу 5». В примере cmd9atj3p000007ky19w1dpy2 — это id последнего события на первой странице.

Для интервью offset-based пагинации обычно достаточно, если только речь не о real-time данных или интервьюер прямо не спрашивает про сценарии с большим объёмом. Большинству интервьюеров важнее, чтобы ты не забыл включить пагинацию, чем то, какой именно подход ты выберешь.

### Фильтрация и сортировка

Как только появляется пагинация, клиенты захотят управлять тем, какой срез данных они получают и в каком порядке. Принято использовать query-параметры: /events?city=NYC&status=upcoming для фильтрации и /events?sort=date для сортировки, где ведущий минус означает убывающий порядок (?sort=-date — сначала новые).

Задача проектирования здесь не в том, чтобы придумать параметры, а в том, чтобы сохранить их единообразие. Если события фильтруются по status, то бронирования тоже должны, а не по state. Как только consumers выучили форму фильтров на одном endpoint, они будут считать, что она работает везде, а разнобой в именах между endpoints — одно из самых частых нарушений последовательности на реальных ревью API. На интервью не нужно перечислять все фильтры. Достаточно показать один endpoint с фильтрацией и сказать, что те же соглашения действуют по всему API.

### Idempotency keys

Вот сценарий, который обожают интервьюеры: пользователь бронирует билеты, запрос падает по таймауту, и клиент его повторяет. Прошёл ли первый запрос? Если да, то повтор только что забронировал второй комплект билетов и списал деньги дважды. POST не идемпотентен, а «просто не повторяй» — не ответ, потому что сеть постоянно отказывает.

Решение — idempotency key. Клиент генерирует уникальный ID для каждой логической операции и отправляет его вместе с запросом:

```
POST /events/123/bookings
Idempotency-Key: 8e03978e-740c-4c2e-abd1-52f427d5c177
{
  "tickets": [{"section": "VIP", "quantity": 2}]
}
```

Сервер сохраняет ключ вместе с результатом первого запроса. Когда приходит повтор с тем же ключом, сервер узнаёт его и возвращает сохранённый ответ, а не обрабатывает бронирование заново. Тот же ключ, тот же результат, никакого двойного списания. Именно так [API Stripe](https://docs.stripe.com/api/idempotent_requests) обрабатывает повторы платежей.

Если в твоём дизайне есть платежи, бронирования или заказы, упомянуть об этом на интервью — сильный сигнал. Он показывает, что ты думаешь о том, что происходит при сбоях, а не только о happy path.

### Единообразные ответы об ошибках

Status codes сообщают клиенту, к какой категории относится проблема, а тело ответа — это место, где ты говоришь, что именно произошло. Паттерн такой: единый конверт ошибки, который выглядит одинаково на каждом endpoint:

```
{
  "error": {
    "code": "SEAT_UNAVAILABLE",
    "message": "Section VIP has only 1 seat remaining"
  }
}
```

Код — это стабильная строка, по которой клиентский код может ветвиться, так что мобильное приложение может показать выбор места, увидев SEAT\_UNAVAILABLE. Сообщение предназначено для людей и может меняться, никого не ломая. Сохраняй одинаковую форму на каждом endpoint, чтобы consumers писали обработку ошибок один раз. На интервью это одна фраза: «ошибки возвращаются в едином конверте с машиночитаемым кодом», — и ты идёшь дальше.

### Стратегии версионирования

API со временем развиваются, и нужна стратегия внесения изменений без поломки существующих клиентов. Это особенно важно для публичных API, где ты не контролируешь, когда клиенты обновят свой код.

Самый распространённый подход — **URL versioning**: номер версии указывается прямо в пути, например /v1/events или /v2/events. Это явный и понятный вариант. Клиент сразу видит, какую версию использует, просто взглянув на URL. Реализовать тоже просто: разные версии можно направлять в разные ветки кода.

**Header versioning** выносит версию в HTTP-заголовок: Accept-Version: v2 или API-Version: 2. URL получаются чище, и это лучше соответствует стандартам HTTP, но разработчикам такой способ менее очевиден, а в браузере его сложнее тестировать.

На интервью URL versioning обычно надёжнее: его знают лучше и его проще быстро объяснить. Если интервьюер прямо не спрашивает про header versioning, придерживайся URL.

Ты заметишь, что в наших разборах версионирования в дизайне API нет вообще. Это скорее следствие того, что большинству интервьюеров оно неважно, а не признак того, что оно неважно на практике (на практике важно).

## Вопросы безопасности

Безопасность на интервью часто оставляют на потом, но если показать, что ты о ней думаешь, это выделит тебя среди других кандидатов. Строить неуязвимую систему безопасности не нужно, но понимание базовых принципов защиты API показывает, что ты мыслишь категориями production-систем.

### Authentication и authorization

Первый вопрос, на который должен отвечать твой API: «Кто отправляет этот запрос и разрешено ли ему то, о чём он просит?»

**Authentication** проверяет личность: подтверждает, что пользователь тот, за кого себя выдаёт. **Authorization** проверяет права: можно ли аутентифицированному пользователю выполнить именно это действие.

В нашем примере с Ticketmaster authentication может подтвердить, что запрос пришёл от пользователя "[john@example.com](mailto:john@example.com)", а authorization проверит, может ли John отменить конкретное бронирование, которое он пытается отменить (отменять он должен только свои бронирования, а не чужие).

#### API Keys vs JWT Tokens

Проектируя authentication для API, обычно выбирают между двумя основными подходами, в зависимости от того, кто будет пользоваться API и как.

На большинстве интервью (но не на всех) authentication и authorization не в фокусе. Мой совет: назови, каким endpoints нужна аутентификация пользователя, и скажи, что для этого ты бы использовал [JWT](https://jwt.io/) или хранил сессию пользователя в базе данных.

##### API Keys

API keys — это длинные случайно сгенерированные строки, которые работают как пароли для приложений, а не для людей. Клиент передаёт свой API key в заголовке Authorization, а сервер ищет этот ключ и определяет, какое приложение делает запрос.

Работает это так: ты генерируешь уникальный API key для каждого клиента (например, sk\_live\_abc123def456...), сохраняешь его в базе вместе с правами доступа и rate limits этого клиента, а затем проверяешь каждый входящий запрос, находя ключ в базе. Это отличный вариант для server-to-server взаимодействия, где ты контролируешь обе стороны. Когда твоему booking service нужно обратиться к payment service, API key — простое и эффективное решение. Он подходит и тогда, когда ты открываешь endpoints сторонним разработчикам, которым нужен программный доступ к твоей системе.

Если ты делаешь пользовательский продукт с пользовательскими API, API keys почти никогда не подходят. Пользователи не должны управлять длинными криптографическими строками, а API keys не истекают и не несут контекст пользователя так, как это нужно сессиям.

```
GET /events
Authorization: Bearer sk_live_abc123...
```

##### JWT (JSON Web Tokens)

JWT, наоборот, кодирует информацию о пользователе прямо в сам токен, а не хранит состояние сессии на сервере. Когда пользователь успешно входит в систему, сервер создаёт JWT с его user ID, правами и временем истечения, а затем подписывает весь токен секретным ключом.

Удобно, что когда этот JWT приходит с последующими запросами, ты можешь проверить его подлинность по подписи и прочитать информацию о пользователе прямо из токена, без обращений к базе данных. Токен сам несёт весь контекст, нужный для авторизации запроса.

JWT особенно хорошо работают в распределённых системах: любой сервис, у которого есть ключ для проверки, может независимо валидировать токены. Если мобильное приложение отправляет JWT на твой API gateway, gateway может проверить личность пользователя и уверенно переслать запрос в booking service.

```
// JWT payload
{
  "user_id": "123",
  "email": "john@example.com",
  "role": "customer",
  "exp": 1640995200
}
```

Используй API keys для взаимодействия внутренних сервисов и для доступа внешних разработчиков. Используй JWT для пользовательских сессий в веб- и мобильных приложениях. JWT может быть stateless (без обращения к базе данных) и нести контекст пользователя, поэтому он идеально подходит для пользовательских приложений.

#### Role-Based Access Control (RBAC)

В реальных системах бывают разные типы пользователей с разными правами. В нашей системе Ticketmaster клиенты могут бронировать билеты и просматривать свои бронирования, менеджеры площадок — создавать события и смотреть отчёты о продажах, а системные администраторы имеют доступ ко всему.

RBAC назначает роли пользователям, а права — ролям:

```
Roles:
- customer: can book tickets, view own bookings
- venue_manager: can create events, view sales for their venues
- admin: can access everything

User: john@example.com → Role: customer
User: manager@venue.com → Role: venue_manager
```

В дизайне API ты проверяешь и authentication, и authorization:

```
GET /bookings/{id}
1. Is the user authenticated? (valid JWT token)
2. Is the user authorized? (owns this booking OR is admin)
```

Максимум, что нужно на интервью, — упомянуть, к каким endpoints какие роли имеют доступ, хотя чаще всего это различие не имеет значения.

### Rate limiting и throttling

Rate limiting защищает от злоупотреблений, ограничивая число запросов, которые клиент может сделать за определённый период. Это защищает систему и от вредоносных атак, и от случайной перегрузки.

Распространённые стратегии:

* **Лимиты на пользователя**: 1000 запросов в час на одного аутентифицированного пользователя
* **Лимиты на IP**: 100 запросов в час для неаутентифицированных запросов
* **Лимиты на конкретные endpoints**: 10 попыток бронирования в минуту, чтобы помешать перепродаже билетов

Обычно rate limiting реализуют на уровне API gateway или через middleware в приложении. Когда лимит превышен, возвращай статус-код 429 Too Many Requests.

На интервью упоминание rate limiting показывает, что ты понимаешь заботы production-систем, но не трать время на проектирование конкретных алгоритмов, если об этом не просят. Обычно достаточно простой фразы: «мы реализуем rate limiting, чтобы предотвратить злоупотребления».

## Итоги

API design на собеседованиях по system design — это про демонстрацию здравого инженерного суждения, а не про идеальные спецификации. Сосредоточься на выборе подходящего протокола для твоей задачи (обычно REST), чётком моделировании ресурсов и понимании основ аутентификации и безопасности. Если не уверен в конкретном решении, опирайся на принципы: консистентность, предсказуемость, stateless и безопасность повторных запросов.

На собеседовании всё решает баланс. Потрать достаточно времени, чтобы показать, что умеешь проектировать разумный API, но не увязай в деталях, когда впереди более серьёзные архитектурные задачи. Интервьюер хочет увидеть, что ты можешь строить работающие системы, а не что ты выучил наизусть все HTTP-статусы. На практике кандидаты чаще ошибаются, тратя на API design слишком много времени, а не слишком мало. Постарайся не тратить на описание API на собеседовании больше 5 минут.
